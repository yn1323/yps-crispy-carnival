## 1. 結論

現在の「開始前、立ち上げ、運用中、休眠」という排他的な店舗ステージは廃止する。  
今後は、後戻りしない導入到達度と、時点によって変化する運用健全性を別の軸として扱う。

分析画面は、次の順に掘り下げられる内部BIへ作り直す。

1. サービス全体のKPI推移
2. グループ比較
3. 店舗比較
4. 店舗詳細
5. シフト周期詳細

分析用データは、運用テーブルと同じConvex deployment内に、分析専用のtable群として新設する。  
画面のqueryは、独立した`/requests`だけを例外として、運用テーブルを直接読まず分析専用tableだけを読む。

更新方式は、重要な状態変化を小さなsource eventとして残し、非同期projectionで分析用factへ反映し、日次snapshotを作るhybrid方式とする。  
通知配送のように件数が多く、既存の永続データから再計算できるものは、当初はeventを増やさず、indexを使った日次batchで集計する。

既存のAnalyticsデータは引き継がない。  
旧tableからのcopy、dual read、値の比較、履歴継承は行わない。

新基盤の初回構築では、運用テーブルから次だけを生成する。

- 現在存在するグループ、店舗、person、管理者所属、スタッフ所属
- タイムスタンプと対象者が十分に残っていて、正確に復元できる過去のシフト周期fact
- 初回構築時点のbaseline snapshot

復元できない過去の日次状態や提出率の分母は推測しない。  
KPI推移の正式な起点は新基盤の稼働日とし、`/requests`を除く分析画面にデータ蓄積開始日、集計基準日時、完全性を表示する。

## 2. 背景と現在の問題

現在のAnalyticsは、店舗を一つのステージへ分類して、その店舗数と遷移を中心に表示している。  
しかし、導入の進み具合と日々の運用状態は性質が異なる。

- 初回確定まで到達した店舗が、次回シフト未作成になることはある
- 一時的な通知失敗や提出低下は、店舗の導入段階を巻き戻すものではない
- 週次運用と月次運用では、同じ未作成日数でも意味が違う
- 複数の問題を抱える店舗を一つのステージへ押し込むと、対応理由が見えない
- 閾値の境界付近で分類が頻繁に変わり、実態とラベルがずれる

実装面でも、現在の構成には次の課題がある。

- 店舗詳細queryがrecruitments、recruitmentStats、staffsなどの運用tableを都度読む
- 日次集計が店舗ごとに複数tableを走査し、店舗数の増加に伴ってread amplificationが大きくなる
- 上限付き取得を正確な全件値のように扱える箇所があり、完全性が呼び出し元へ伝わらない
- 現在と前回だけを比較するため、長期的な改善か一時変動かを判断しにくい
- 過去の提出率へ現在のスタッフ数を使うと、当時の分母と一致しない
- 前期間取得の失敗を0として扱うと、実際には不明なのに増加として表示される
- point-in-timeのstageを、後戻りしないlifecycleのように扱っている

今回の再設計では、KPIの意味、時刻、分母、データ完全性を先に固定し、その契約に合わせてDBとUIを同時に作り直す。

## 3. 目的

### 3.1 Product上の目的

- 導入がどこまで進んだかを、後戻りしない到達度で把握できる
- 日常運用の問題を、複数のhealth signalとして把握できる
- サービス全体、グループ、店舗、シフト周期の順に原因を掘り下げられる
- KPIの点ではなく、日次、週次、月次の推移を確認できる
- 登録コホート、スタッフ規模、プラン、作成周期、LINE利用、提出傾向で比較できる
- 店舗ごとのスタッフ数、管理者数、累積シフト数、提出人数と対象人数を確認できる
- グループが抱える店舗数、実働店舗数、person数、スタッフ所属数、管理者数を確認できる

### 3.2 技術上の目的

- Analytics画面から運用tableへの直接queryをなくす
- dashboard queryのread量を、全運用データ量ではなく表示行数と期間に比例させる
- 日次集計を再実行可能かつ途中再開可能にする
- 上限超過や未集計を0件として返さない
- PIIを分析eventや個人単位factへ複製しない
- 新旧Analyticsデータを混ぜず、clean cutoverできるようにする

## 5. 分析モデル

### 5.1 二つの主軸

| 軸 | 性質 | 表示方法 |
|---|---|---|
| 導入到達度 | 原則として後戻りしない | milestone到達日、到達店舗数、到達率、到達までの日数 |
| 運用健全性 | 日々変わり、複数同時に成立する | health signal、対象店舗数、継続日数、変化量 |

店舗をどれか一つのhealth stageへ分類しない。  
一つの店舗が、次回未作成と通知失敗と提出低下を同時に持てるようにする。

### 5.2 時刻の契約

KPIには必ず次のいずれかの時刻を対応させる。

| 時刻 | 用途 |
|---|---|
| occurredAt | 登録、提出、確定、通知など、事実が発生した時刻 |
| effectiveAt | planや所属など、状態が有効になった時刻 |
| cutoffAt | 提出率など、母集団を固定した時刻 |
| snapshotDate | JST日次終了時点の状態 |
| computedAt | 集計処理が完了した時刻 |

画面の期間絞り込みはJSTの日付境界で統一する。  
APIはasOf、dataStartDate、computedAt、completenessを返す。

### 5.3 不明値の扱い

0、未発生、未集計、不完全、復元不能を区別する。

| 状態 | UI |
|---|---|
| 正確に0件 | 0 |
| 集計前 | 集計待ち |
| 一部のみ取得 | 一部集計 |
| 過去の分母を復元不能 | 算出不可 |
| 対象外 | 対象外 |

算出不可を0%へ変換しない。  
一部集計の値をランキングや全体率の分母へ含めない。

## 6. KPI定義

KPI名、粒度、分子、分母、基準時刻、除外条件、完全性を一つのregistryで管理する。  
UI側で独自に率を再定義せず、Convexがcountとrateを同じ契約で返す。

### 6.1 North Star

当面のNorth Starは、開始前確定周期率とする。

- 母集団: periodStartが集計期間内に到来した、削除されていないシフト周期
- 分子: confirmedAtが存在し、confirmedAtがperiodStart以前の周期
- 分母: 上記母集団の全周期
- 粒度: サービス全体、グループ、店舗、登録コホート、plan、店舗規模
- 推移: 日次保存し、画面では週次または月次へrollup

率をrollupするときは、店舗別率の平均ではなく、分子合計を分母合計で割る。

補助KPIとして、次を併記する。

- 期限内提出率
- 最終提出率
- cycle作成からperiodStartまでのlead time
- 作成から確定までのlead time
- periodStartから見た確定余裕日数

### 6.2 導入到達度

順序は次のとおりとする。

1. 店舗登録
2. 初回募集
3. 初回提出
4. 初回確定
5. 2回目確定

各店舗には、各milestoneの初回到達日時を一度だけ保存する。  
後から募集やスタッフが削除されても、監査上誤りと確定した場合を除き、到達を取り消さない。

表示するKPIは次のとおり。

| KPI | 定義 |
|---|---|
| 到達店舗数 | milestone到達日時が存在する店舗数 |
| 到達率 | 到達店舗数 ÷ 登録済み対象店舗数 |
| 前段からの転換率 | 現段階到達数 ÷ 直前段階到達数 |
| 到達所要日数 | 店舗登録日時から各milestone到達日時まで |
| cohort別到達率 | 登録週または登録月ごとの到達率 |
| cohort別中央値 | cohortごとの到達所要日数中央値 |

### 6.3 運用健全性

health signalは重複を許容する。

| signal | 初期定義 |
|---|---|
| 次回シフトあり | 今日以降のperiodを持つ、削除されていないcycleが存在する |
| 次回未作成 | 通常周期を推定でき、次回想定periodに対応するcycleがない |
| 通常周期からの遅れ | 次回想定日を許容幅以上過ぎてもcycleが作られていない |
| 通知失敗 | 過去30日で最終失敗した通知が1件以上ある |
| 提出低下 | 最新の完了cycleの最終提出率が、直前3cycleの中央値より15ポイント以上低い |
| 確定遅れ | 最新cycleが店舗通常値より遅い、またはperiodStart後も未確定 |
| 長期無活動 | 30日以上、募集作成、提出、確定のいずれもない |
| 判定材料不足 | 通常周期や比較基準を計算できるcycle数が不足している |

通常周期は、直近最大6件の完了cycleのperiodStart間隔の中央値から求める。  
2区間未満の場合は推定せず、判定材料不足とする。

遅れの許容幅は、max 3日、通常周期の20% とする。  
この値は初期仮説であり、稼働後に分布を見て再調整する。

提出低下は、比較対象cycleが3件未満、または対象人数が5人未満なら判定しない。  
小規模店舗の1人差を異常として強調しないためである。

### 6.4 ユーザー層とsegment

次のdimensionでKPIを絞り込み、比較できるようにする。

| dimension | 初期bucket |
|---|---|
| 店舗登録cohort | 週、月 |
| plan | trial、free、pro、business |
| グループ店舗数 | 1、2から3、4から10、11以上 |
| 店舗スタッフ規模 | 1から4、5から9、10から19、20から49、50以上 |
| 通常周期 | 週次、隔週、月次、その他、判定材料不足 |
| LINE利用 | 0%、1から49%、50から79%、80%以上 |
| 最近の提出傾向 | 高位、安定、低下、判定材料不足 |
| 導入cohort | 登録から30日以内、31から90日、91日以上 |

segmentの率も、各行の分子と分母を合算して計算する。

### 6.5 グループ分析

グループは課金と管理者のscopeであり、店舗の単純な合計とは別に見る。

| KPI | 注意点 |
|---|---|
| 総店舗数 | 削除済みを除く |
| KPI対象店舗数 | dataStartDate以降に観測できる店舗 |
| 稼働店舗数 | 直近の募集、提出、確定がある店舗 |
| health signal別店舗数 | signalは重複する |
| スタッフ所属数 | 店舗ごとのactive staff membership数。複数店舗所属は複数件 |
| unique person数 | organizationPeople単位。店舗間で重複排除 |
| シフト対象者数 | excludedFromShiftではないstaff membership数 |
| 有効管理者数 | activeなorganization manager membership数 |
| 管理者兼スタッフ数 | manager personとstaff personのintersection |
| person未接続staff数 | organizationPersonIdを安全に特定できないstaff数 |
| 2店舗目までの日数 | グループ作成または初店舗から2店舗目登録まで |
| 2店舗目の初回確定までの日数 | 多店舗展開後の活用到達度 |

person未接続staffをemailで推測結合しない。  
unique person数には確実に紐づくpersonだけを含め、未接続数を別に表示する。

### 6.6 店舗詳細

店舗詳細では、現在値と履歴を分ける。

現在値:

- グループ、plan、登録日
- 導入milestoneと各到達日
- active staff membership数
- シフト対象staff membership数
- unique person数
- 有効管理者数
- 管理者兼スタッフ数
- LINE連携人数、follow中人数、連携率
- 推定通常周期
- 現在成立しているhealth signalと開始日
- 最新集計日時と完全性

累積値:

- 作成cycle数
- 確定cycle数
- 開始前確定cycle数
- 提出人数合計
- 提出対象人数合計
- 期限内提出率
- 最終提出率
- 通知送信数、最終失敗数
- 確定lead timeの中央値とP90

cycle一覧:

| 列 | 内容 |
|---|---|
| 対象期間 | periodStartからperiodEnd |
| 作成日時 | cycle作成時刻 |
| 提出期限 | submitDeadline |
| 確定日時 | confirmedAt |
| 期限時対象人数 | deadline cutoffの母集団 |
| 期限時提出人数 | deadline cutoffまでに初回提出した人数 |
| 期限内提出率 | 上記二値から計算 |
| 最終対象人数 | cycle close時点の母集団 |
| 最終提出人数 | cycle closeまでに初回提出した人数 |
| 最終提出率 | 上記二値から計算 |
| 通知 | sent、failed、reminder |
| 完全性 | complete、partial、unavailable |

### 6.7 提出率の母集団

提出率の分母は、現在のスタッフ数ではなく、各cutoffの対象者集合を凍結して使う。

- 期限内提出率のcutoffはsubmitDeadline
- 最終提出率のcutoffはconfirmedAt。未確定ならperiodStart
- 分子はcutoffまでに初回提出した対象者
- 分母はcutoff時点のシフト対象者と、cutoffまでに提出済みの人の和集合

最後の和集合は、提出後に対象外へ変更された人を分子からだけ消して、100%を超える事態を避けるために必要である。

過去cycleについてcutoff時点の対象者集合を復元できない場合、提出件数は表示しても提出率は算出不可とする。  
recruitmentStatsのsnapshotや現在のstaff数を、正確性の根拠なしに分母へ代用しない。

## 7. UI構成

### 7.1 情報設計

stage別tabは廃止し、次のrouteへ置き換える。

| route | 役割 |
|---|---|
| / | 全体KPIと推移、導入到達度、health overview |
| /organizations | グループ比較と絞り込み |
| /organizations/:organizationId | グループ内の店舗、人、管理者、KPI推移 |
| /shops | 店舗比較、health signal、segment filter |
| /shops/:shopId | 店舗の現在値、milestone、推移、cycle一覧 |
| /shops/:shopId/cycles/:recruitmentId | 一つのcycleの提出、通知、確定詳細 |
| /requests | 現行の要望一覧 |

要望画面は分析モデルと混ぜず、独立routeとして残す。

### 7.2 Analytics画面共通filter

`/requests`を除くAnalytics routeで、次のfilterを必要な画面へ配置する。

- 期間
- 比較期間
- 集計単位の日、週、月
- グループ
- 店舗
- plan
- 店舗規模
- 登録cohort
- 通常周期
- LINE利用bucket
- health signal
- データ完全性

期間、比較、集計単位、filter、sortはURL query parameterへ保存する。  
共有URLとブラウザ履歴で同じ分析状態を再現できるようにする。

### 7.3 全体画面

上から次の順で配置する。

1. dataStartDate、asOf、completeness、最終集計状態
2. North Starと主要補助KPI
3. KPI推移chart
4. 導入milestone funnelとcohort推移
5. health signal別店舗数と増減
6. グループ比較
7. 要確認店舗

カードの前期間差は、前期間が完全な場合だけ表示する。  
前期間が取得不能なら、0との差ではなく比較不可と表示する。

### 7.4 比較一覧

一覧では、行clickで詳細へ遷移する。  
列の表示、sort、filterは一覧のURL状態に含める。

最初に用意する店舗一覧列:

- 店舗名、グループ名、plan
- 登録日、導入到達度
- active staff、shift target、manager
- 通常周期
- 次回cycle
- 期限内提出率、最終提出率
- LINE利用率
- health signals
- 最終活動日
- completeness

グループ一覧は、店舗数、稼働店舗数、unique person、staff membership、manager、North Star、health signal店舗数を表示する。

### 7.5 店舗とcycleの詳細

店舗詳細は、概要、KPI推移、cycle一覧の順にする。  
cycleをdialogへ詰め込まず、routeを持つ詳細画面へ遷移する。

cycle詳細では個人名を表示しない。  
対象者単位の検証が必要な場合も、opaqueな内部ID、提出有無、初回提出時刻、通知結果だけを表示し、通常運用では集計値を主表示にする。

### 7.6 loading、empty、error

- loading中は前回値を新しいasOfの値として見せない
- emptyはfilter対象0件とデータ蓄積前を区別する
- partialは警告付きで表示し、rateとrankingから除外する
- query error時はカードごとに0を置かず、取得失敗を表示する
- pipeline停止時は`/requests`を除くAnalytics route上部に最終成功日時を表示する

### 7.7 残す資産と作り直す資産

残す候補:

- apps/analytics-dashboardのpackage構成
- Chakra UI providerとtheme
- TanStack Query client
- Cloudflare Worker
- WorkerからConvex HTTP Actionへservice credentialで接続するBFF境界
- Recharts
- /requestsの機能

作り直す対象:

- DashboardPageとstage tab
- stage判定domain
- 現在と前期間だけを前提にしたderived KPI
- Analytics DTOとclient
- 店舗詳細dialog
- filter、table、chartの画面構成

共通componentは、複数画面で本当に同じ契約を持つものだけ残す。  
名前だけ付けた薄いwrapperは増やさない。

## 8. データ基盤

### 8.1 配置

分析tableは同じConvex deploymentに置くが、運用tableとは名前、writer、readerを分離する。

- 運用mutationは、必要な事実だけをanalyticsSourceEventsへ追記する
- internal functionがsource eventをprojectionへ反映する
- 日次jobがprojectionとcycle factからsnapshotを作る
- dashboard queryは、独立した`/requests`だけを例外として分析tableだけを読む
- browserはConvexへ直接接続せず、Worker BFFを通す

別projectは、負荷計測で同一deploymentの上限が問題になった時点で検討する。  
最初から別projectにすると同期、再送、secret、障害点が増えるため、現段階では採用しない。

### 8.2 source eventにする変更

次のうち、後から正確に復元しにくい変更だけをevent化する。

- グループ作成、更新、削除
- 店舗作成、更新、archive、再有効化、削除、グループ所属変更
- organization person作成、更新、削除、結合
- 管理者membershipの開始、終了、交換
- staff membershipの開始、終了、shift対象変更とbatch変更
- plan変更
- cycle作成、期間変更、期限変更、確定、削除
- 初回提出
- LINE accountの連携、解除、follow状態変更とbatch変更

提出内容、氏名、email、電話番号、LINE user IDはeventへ複製しない。  
cycleのdeadlineまたはclose時に、対象cycleのshiftSubmissionsを有界に読み、cycle opportunityへ凍結する。

LINE source batchは最大50件のstaff ID、linked・following状態、サービス受理時刻だけを持つ。provider timestampとevent IDは重複・順序判定にだけ使い、分析上の発生時刻やpayloadへ複製しない。  
Webhookのfollow、unfollowはprovider eventごとに別internal mutationで処理する。同じLINE userのactive accountは51件目までpreflightし、50件超過をoperational patch前に拒否する。連携確定時も結果account数と変更数をpatch前に検証する。

通知は当初source eventへ書かない。  
notificationOutboxをstatusと発生時刻のindexで日次走査し、cycle単位と日次単位へ集計する。

### 8.3 schema変更の境界

organizations、shops、organizationPeople、organizationMembers、staffs、recruitments、shiftSubmissions、recruitmentStats、notificationOutboxなど、既存の運用tableのfield、validator、indexは変更しない。  
運用documentのbackfillや形式変換も行わない。

ただし、新しい分析専用tableもConvexのroot schemaで管理するため、convex/schema.ts自体は変更する。  
この変更は、新Analytics tableとそのindexの追加、および安全なcleanup完了後の旧Analytics table定義削除に限定する。

初回bootstrapは、既存の運用indexとby_creation_timeで有界に読める範囲だけを使う。  
新しい分析要件のために運用tableへindexを追加しない。

旧Analytics tableの定義削除は、実装と同じdeployでは行わない。  
新基盤のcutover後に旧Analytics documentをbounded cleanupし、対象deploymentで0件を確認できた後のNarrowとして扱う。

## 9. 集計処理

### 9.1 projection

運用mutationとsource eventのinsertは同じtransactionで行う。  
payload検証、event key競合、insertに失敗した場合は業務mutationもrollbackする。commit後の分析projection失敗によって後続の業務mutationを失敗させないよう、重い処理はschedulerで分離する。

主consumerはanalyticsPipelineStatesのcursorからsource eventを一transaction一件ずつ読み、次を更新する。

- organization、shop、person、membershipのprojection
- shopとorganizationのmilestone
- cycleの基本fact
- cycle closeの集計job

同じeventを再処理しても、eventKeyまたはversionで同じ結果になるようにする。

一eventがstaff、LINE、plan差分など複数rowの更新を必要とする場合は、最大50件ずつのprojection子jobへ分ける。  
activeとbuildingの全対象generationで、そのeventの子jobが完了するまで主consumerを止め、後続eventを先行させない。  
通常のLINE更新経路は50件超過をoperational patch前に拒否する。防御上`isComplete: false`のLINE batchを受け取った場合は`analytics_line_batch_overflow`でfail-closedとし、generationを`degraded`にして新generationを再構築する。

### 9.2 cycle finalization

deadline到来時とcycle close時にjobを起動する。

1. 対象者集合を最大50件ずつopportunityへ保存
2. shiftSubmissionsを最大50件ずつ照合
3. notification集計を取得
4. 分子、分母、完全性をcycle factへ確定
5. 最終page完了後にfinalizedAtを設定

途中pageの値を完成済みfactとして公開しない。  
cycle factのcompletenessがcompleteになるまでは、上位のrateへ含めない。

### 9.3 daily aggregation

JST前日を対象に、次の順で集計する。

1. 最新projection watermarkを固定
2. 対象日の通知集計をreset
3. notificationOutboxのterminal `sent`と`failed`を別々に最大50件ずつ走査
4. service、shop、recruitment別通知集計とnotification watermarkを確定
5. 対象日までに期限を迎えたcycle finalizationの完了を待つ
6. shopごとにstaff、manager、cycle、確定lead time quantile、通知をpage集計
7. organization snapshotへrollup
8. segment snapshotへrollup
9. service snapshotへrollup
10. 日付とsource watermark固有のdaily invariantを確認
11. generationと日付のsnapshotをcompleteへ変更
12. latestCompleteSnapshotDateを進める

絶対値upsertとし、同じ日を再実行しても加算されないようにする。

### 9.4 通知集計

通知の各配信結果をsource eventへ複製しない。  
notificationOutboxのsent、failedの時刻indexを使い、対象日の半開区間だけをpage走査する。

保存するのは次の集計値である。

- channel別sent
- channel別final failed
- recruitment、reminder、confirmationなどのkind別件数
- recruitmentIdがある場合のcycle別件数

payload本文や宛先は分析tableへ保存しない。

### 9.5 再構築

projectionの定義を変える場合、新しいgenerationをbuildingとして作る。

1. operational dataからbootstrap
2. bootstrap中に追加されたsource eventをwatermarkまで追いつく
3. backlogとblocking projectionが0件のbarrierでsource cursorを捕捉し、baseline snapshotと日付・source watermark・source cursorが一致するbaseline invariantを確認
4. source event backlog、blocking projection子job、全job種別のfailedが0件であることを同じtransactionで再確認
5. activeGenerationを一度だけ切り替える
6. 旧generationのbounded cleanup jobを切替時に14日後として予約する

同一generationを破壊的に全件書き換えない。

手動の`invariant:<generation>:manual`は、milestone、参照整合性、rollupを広く確認する補助検査である。baseline daily jobが作る日付・watermark固有のinvariantとは別であり、manual invariantだけをcutover証明に使わない。  
invariant走査中にsource cursorが変わった場合は先頭から再検証する。非active generationのcleanupは切替から14日経過するまで手動で前倒ししない。

## 12. DB負荷とfunction budget

hybrid方式はread負荷を減らす一方、意味のある運用mutationごとに小さなwriteが増える。  
自動的に安くなるとはみなさず、Convex Insightsとtransaction metricsで実測する。

初期budget:

| 処理 | budget |
|---|---|
| 運用mutationのsource event追加 | event key重複確認の追加read最大1、source eventの追加write 1 |
| source event主consumer | 1 transaction 1 event |
| projection子job | 1 transaction最大50 row。子job完了まで後続eventを止める |
| cycle opportunity生成 | 1 transaction最大50人 |
| snapshot scan | 1 page最大100 analytics row |
| dashboard list | 初期50行、最大100行 |
| trend | 最大366点 |
| response | 512 KiB未満 |

開発deploymentでの代表実測:

| transaction | executed phase | read documents | read bytes | write documents | write bytes |
|---|---|---:|---:|---:|---:|
| 運用source tableのread-only形状確認 | - | 51 | 11,761 | 0 | 0 |
| source event主consumerのcatch-up | `events` | 6 | 3,907 | 2 | 1,280 |
| baseline dailyのinvariant待機 | `invariantWait` | 3 | 2,289 | 1 | 617 |
| 検証用generation cleanupの最終page | `dailySegmentCleanup` | 19 | 14,015 | 9 | 593 |

いずれも少量の開発データでのsampleであり、最大50件または100件pageのProduction負荷を証明しない。source event writerの追加分はコード上のdedupe read最大1件とinsert 1件を確認したが、運用documentを変更しないためbytesの差分実測は行っていない。対象deploymentでのrolloutでは全phaseと最大pageを別途採取する。

実装原則:

- dashboard queryで、独立した`/requests`以外は運用tableを読まない
- indexなしfilterと全件collectを使わない
- countのためだけにdocument本文を大量取得しない
- 日次snapshotをquery時に再計算しない
- 一つのorganizationやshop documentへ高頻度counterを集中させない
- source eventはappend onlyにしてOCC競合を避ける
- notification delivery単位の二重writeは当初追加しない
- 上限に達したらexactな値として返さず、pageまたはpartialにする

実装時は代表transactionで読み取りdocument数、bytes、書き込みdocument数、bytesを記録する。LINE active accountのpreflightなど既存業務安全性のreadと、Analytics source eventによる追加readを分ける。`lastTransactionMetrics`はphase処理とrecovery schedule後の実使用量を保存するが、その値自身を保存する最後のpatchは含まない。最新値で上書きされるため、`executedPhase`と`measuredAt`を使い、各phaseの実行中にdeployment別の外部証跡へ保存する。  
job完了後の最新一件から、全phaseの履歴を復元したことにしない。  
想定店舗数を超えた場合はbatch sizeを下げるのではなく、query形状とprojection粒度を見直す。

## 13. Security Lens

### 13.1 actor

- Cloudflare Accessを通過した内部owner
- Analytics Workerのservice credential
- Convex internal jobとscheduler
- 運用mutationからsource eventを作るserver code

### 13.2 asset

- グループ名、店舗名
- plan、店舗規模、利用傾向
- cycleと提出の集計
- opaqueなorganization、shop、person、staff、recruitment ID
- Analytics service credential
- pipeline watermarkと完全性

### 13.3 trust boundary

- browserからCloudflare AccessとWorker
- WorkerからConvex HTTP Action
- HTTP Actionからinternal Analytics query
- 運用mutationからanalyticsSourceEvents
- source eventからprojectionとsnapshot

### 13.4 主なabuse caseと対策

| abuse case | server-side control |
|---|---|
| credentialを使った巨大期間query | 期間、page size、metric、sortのallowlistと上限 |
| IDを変えて全データを列挙 | Access、service credential、固定endpoint、rate limit、監査log |
| eventへPIIを混入 | schemaで許可payloadを限定し、free-form objectを禁止 |
| partial generationの閲覧 | activeGenerationだけをqueryする |
| stale dataを正常値として表示 | watermark、asOf、completenessをresponse必須にする |
| 削除済み顧客データの残存 | 削除event、retention、bounded cleanup |
| error logへの名称やpayload流出 | IDとerror codeだけをlogし、payloadをlogしない |

group名とshop名は内部画面の識別に必要なのでprojectionへ保存する。  
ただしjob log、error log、metric labelへは含めない。

### 13.5 残留リスク

ユーザー方針によりAnalytics専用の自動testは追加しない。  
そのため、KPI式、cutoff、完全性、BFF入力制約の回帰を自動で検知できないリスクを受け入れる。

このリスクは、KPI registryを一か所に置くこと、分子と分母を保存すること、data invariant確認、function budget確認、環境確認で軽減する。  
認証境界やservice credentialなどAnalyticsの外にも影響する共通security契約を変更する場合は、この除外を拡張せず、変更先の正本に従って別途検証する。

## 14. Retention

初期案:

| data | retention |
|---|---|
| analyticsSourceEvents | 90日。active projectionがwatermarkを通過した後 |
| analyticsShiftCycles | 25か月 |
| analyticsShiftCycleOpportunities | 400日後にperson、staff linkを削除 |
| daily shop、organization、segment | 25か月 |
| daily service KPI | 5年 |
| aggregation jobs | 90日 |
| inactive generation | active切替から14日 |

グループまたは店舗削除時は、表示名を即時削除または匿名化し、cycle集計はretention方針に従う。  
個人単位opportunityは集計完了後の保持目的を限定し、期限後にidentifierを消す。

retentionはProductとSecurityの承認対象とし、実装前の確定事項とする。

## 15. schema rolloutとcutover

既存Analyticsデータは移行しないが、保存済みschemaを安全に削除するため、Widen、Build、Cutover、Narrowの順に進める。

### Phase 0: KPI契約を確定

- KPI registryを確定
- 時刻、母集団、unknown、削除の扱いを確定
- 通常周期とhealth thresholdを確定
- retentionを承認
- UIのrouteと主要filterを確定

完了条件:

- 同じKPI名に複数の式がない
- 分子、分母、cutoff、完全性が文書化されている

### Phase 1: Widen

- convex/schema.tsへ新tableを既存Analytics tableと共存する形で追加
- 新tableには既存documentがないため、移行都合でfieldをoptionalにせず、業務上の不明値だけを明示的にoptionalまたはdiscriminated unionで表す
- 既存の運用tableのfield、validator、indexは変更しない
- 運用documentのbackfillを作らない
- analyticsSourceEventsのwriterを追加
- organization、shop、person、staff、manager、billing、recruitment、初回提出、LINE状態の変更点へ小さいevent hookを追加
- analyticsPipelineStatesとjob runnerを追加
- 旧Analytics queryとtableは残す

完了条件:

- 運用mutationに追加されるwriteがbudget内
- eventにPIIがない
- event失敗時の運用影響が定義されている

### Phase 2: projectionとbootstrap

- 対象deploymentのDashboard exportまたはbackup ZIPを、リポジトリ、seed用backup、別deploymentのsnapshot、以前のexportと分離したアクセス制限付きの一意なパスへ保存
- ZIPまたは展開済みdirectoryへ`pnpm convex:verify-analytics-line-readiness -- --path <path>`を実行
- 新generationをbuildingで作成
- current organization、shop、people、membershipをpage生成
- 復元可能なcycle factをpage生成
- bootstrap開始後のsource eventへ追いつく
- dataStartDateのbaseline snapshotを作る
- activeGenerationへ切り替える

完了条件:

- buildingの途中結果がqueryされない
- offline verifierが`ok: true`、`overLimitLineUserCount: 0`、`maxActiveAccountsPerLineUser <= 50`を返す
- 対象revision、完全修飾deployment名、export取得時刻、export ZIPのSHA-256、`activeAccountCount`、`distinctLineUserCount`、`activeAssociationSetSha256`を一組の証跡にする
- verifier出力へPIIまたはLINE user IDを含めず、`overLimitLineUserCount`が1以上ならexit code 1のままbootstrapを止める
- row countと参照整合性invariantを満たす
- baseline invariantの日付、source watermark、source cursorがcutover時の値と一致する
- source event backlog、blocking projection子job、failed jobが0件である
- 復元不能な過去分母がunknownである
- 旧Analytics tableを一行も読んでいない

### Phase 3: daily snapshot

- cycle finalization jobを追加
- notificationOutboxの日次集計を追加
- shop、organization、segment、service snapshotを追加
- cronと再実行導線を追加
- watermarkとcompletenessを返す

完了条件:

- 同日再実行で値が増えない
- 途中停止からcursorで再開できる
- partial dayをlatest completeとして公開しない

### Phase 4: BFFとDTO

- analyticsDashboardのquery、schema、DTO、HTTP Actionを新contractへ書き換える
- Worker endpointを追加
- 入力allowlist、page上限、期間上限を追加
- metadataを全responseへ追加

完了条件:

- dashboard queryは、独立した`/requests`以外の運用tableを読まない
- browserへservice credentialを返さない
- response上限とpartial表現を満たす

### Phase 5: UI

- routeを導入
- 全体、グループ、店舗、cycle画面を実装
- URL filterとsortを実装
- dataStartDate、asOf、completenessを表示
- stage tabとstage domainを削除
- /requestsを独立routeとして維持

完了条件:

- KPI推移からgroup、shop、cycleへ到達できる
- milestoneとhealthを混同していない
- 0、unknown、partial、errorを区別する

### Phase 6: Cutover

- Workerの既定endpointを新queryへ切り替える
- Analytics UIを新routeへ切り替える
- 数日分のsnapshot完了と負荷を確認する
- 旧Analyticsのcronとbackfill入口を停止する

完了条件:

- 新UIのAnalytics queryがactiveGenerationだけを読み、`/requests`は独立した現在値契約だけを読む
- daily jobがbudget内
- error logにPIIがない
- old Analyticsへのreadがない

### Phase 7: Narrow

- 旧Analytics固有のfrontend componentとdomainを削除
- 旧convex/analytics実装を新構成に整理
- 旧analyticsDashboard endpoint、DTO、schemaを削除
- convex/analytics内とconvex/analyticsDashboard内の旧Analytics専用testを削除し、代替testは追加しない
- 旧三tableのdocumentをbounded jobで削除
- documentが0件であることを確認した後、別deployで旧table定義をschemaから削除
- 旧cronと不要indexを削除
- doc/features/analytics.mdとdoc/features/analytics-dashboard.mdを現行仕様へ更新

旧tableの行削除とschema定義削除を同じdeployで行わない。

### Phase 8: 後続候補

- active managerの操作履歴
- reminder前後の提出増分
- 通知失敗から復旧までの時間
- current digest
- 別Convex projectまたはwarehouse

active managerはactor履歴を新たに記録しないと正確に作れないため、初期scopeへ含めない。

## 16. rollback

Narrow前:

- Workerを旧endpointへ戻す
- 新pipelineを停止する
- 新tableは残したまま原因を調査する

Narrow後:

- 旧Analyticsデータへのrollbackはしない
- operational dataとsource event保持期間内のeventから新generationを再構築する
- 復元不能な期間はunknownとして扱う

旧Analyticsデータを引き継がない方針のため、Narrow完了後に旧画面の数値を復旧できることは要件にしない。

## 17. 検証方針

ユーザー方針とapps/analytics-dashboard/AGENTS.mdに従い、Analytics frontendとConvexのtestは追加、更新しない。  
旧実装と一緒に不要になるAnalytics専用testは削除する。`pnpm test`に含まれるlogic、`convex(logic)`、`convex(scenario)`、uiと、対象ファイルを指定する`pnpm vitest`は実行しない。test成功の結果は記録しない。

代わりに、実装時は次を確認する。

静的検証:

- pnpm analytics:lint
- pnpm analytics:type-check
- pnpm analytics:build
- pnpm lint
- pnpm type-check
- pnpm build
- pnpm docs:check

データinvariant:

- milestone日時は前段より前にならない
- secondConfirmedAtはfirstConfirmedAt以降
- submitted countは、completeなcycleでtarget count以下
- rateは分子と分母から再計算できる
- activeGenerationは一つ
- complete snapshotは一つの日付、scope、generationにつき一行
- service countはorganization rollupと一致する
- organization countはshop rollupと一致する
- unknown cycleはrate rollupへ含まれない

負荷確認:

- source event追加transactionのreadとwrite
- source event主consumer 1件のread bytesとwrite bytes
- projection子job 50件のread bytesとwrite bytes
- opportunity 50件のread bytesとwrite bytes
- daily snapshot各phaseの最大transaction
- 一覧100件とtrend366点のresponse bytes

各jobの`lastTransactionMetrics`は最新値で上書きされる。  
`executedPhase`と`measuredAt`を含む値を処理中に採取し、同じdeploymentの全phaseを外部証跡へ残す。

環境確認:

- Analytics LINE readiness: 対象deploymentの分離保存したexportをoffline verifierで確認し、件数、最大値、association set hashを記録する
- ENV-BI-01: Cloudflare Access未認証では閲覧できない
- ENV-BI-02: Workerのcredentialがbrowserへ露出しない
- ENV-BI-03: pipeline停止またはpartial時に古い値を正常値として表示しない
- ENV-BI-04: Content-Lengthなしの16 KiB超過requestを全量読取前に拒否する
- ENV-BI-05: 最大想定量でphase別負荷、一覧と`/requests`のpage上限、trend点数、response bytesを確認する

ブラウザをAI Agentが手動操作する確認は計画へ追加しない。

## 18. 受入条件

- 導入到達度と運用健全性が別軸で表示される
- KPIの経過を日次、週次、月次で確認できる
- サービス全体からgroup、shop、cycleへdrill downできる
- 店舗ごとのstaff、shift target、unique person、managerを確認できる
- 累積cycle数と、各cycleの提出人数、対象人数、率、完全性を確認できる
- グループの店舗数、稼働店舗数、人員構成を確認できる
- cohort、plan、規模、周期、LINE、提出傾向で比較できる
- 全responseにasOf、dataStartDate、completenessがある
- 過去の復元不能な値が0や推定値にならない
- dashboard queryは、独立した`/requests`だけを除いて運用tableを直接読まない
- 旧Analyticsデータをcopy、dual read、比較していない
- 旧Analytics tableを安全な二段階で削除できる
- Analytics testを追加または更新していない
- 静的検証、data invariant、負荷budget、環境確認を満たす

## 19. 採用した判断

| 判断 | 採用値 |
|---|---|
| North Star | 開始前確定周期率 |
| データ鮮度 | projectionは準リアルタイム、正式trendは日次 |
| 通常周期 | 直近最大6cycleのperiodStart間隔中央値 |
| 遅れ許容 | max 3日、周期の20% |
| 提出低下 | 直前3cycle中央値から15ポイント低下、対象5人以上 |
| cycle opportunity retention | 400日 |
| shop、organization、segment日次retention | 25か月 |
| service日次retention | 5年 |
| source event retention | 90日 |
| 旧Analyticsデータ | 全件非継承 |

この表の判断をPhase 0の契約として採用した。  
今後変更する場合は、schema、集計、BFF、UI、運用手順を同時に見直し、画面だけで独自変更しない。

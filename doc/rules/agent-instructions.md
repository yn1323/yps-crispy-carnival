# エージェント指示の配置方針

## 目的

この文書は、リポジトリ内の規則、エージェント指示、作業手順をどこへ置くかを定める。
同じ内容を複数箇所で管理せず、変更理由に合う一つの正本を選ぶ。

## 文書の役割

| 配置 | 役割 | 短く言うと |
|---|---|---|
| `doc/rules/` | 設計原則、責務、境界、判断基準、その理由 | 何を、なぜ守るか |
| `AGENTS.md` | 対象範囲で常に守る制約、禁止事項、参照すべき正本 | どこで、何を必ず守るか |
| `.agents/skills/` | 特定作業の発動条件、進め方、成果物、検証 | いつ使い、どう進めるか |
| `doc/features/` | 現行実装の機能概要、条件別仕様、入口、関連ファイル、API | 何が、どう動き、どこにあるか |
| `doc/specs/organization-billing-business-flow.md` | 実装が満たすべき業務要件。未実装の要件を含み得る | 何を実現すべきか |
| `doc/specs/full-regression-contracts.md` | 主要契約と主担当テスト層の対応 | 何を、どこで検証するか |
| `doc/manual/` | 人間が実行する運用手順、確認方法、復旧手順 | 人がどう運用するか |
| `doc/manual/release-status.md` | Production、deployment、migration、外部設定の実環境証跡 | 実環境で何を確認済みか |
| `doc/archive/` | 廃止、置換、棄却された資料と時点監査 | 過去に何を判断したか |
| コード、設定 | 実行可能な現在の挙動、schema、コマンド、workflow | 今どう動くか |

`doc/plans/` は、計画時点の判断と移行経緯を残す履歴である。
完了後の現行仕様や常設ルールの正本にはしない。
`doc/plans/INDEX.md`で、採否未決を`Proposed`、進行中を`Active`、完了済みを`History`に分類する。

`doc/archive/`は、廃止、置換、棄却された資料と特定時点の監査結果を保存する。
Archive本文を現行仕様へ追従させず、`doc/archive/INDEX.md`から理由と後継文書を案内する。

## 配置の判断

追加する内容は、次の順で所有者を決める。

1. 実行時に機械で保証できる現在の挙動は、コードまたは設定へ置く。
2. 現在のコードに実装されている機能の概要は、対応する `doc/features/` へ置く。
3. 実装が満たすべき業務要件は、対象の業務要件文書へ置く。
4. 主要契約と主担当テスト層の対応は、検証契約へ置く。
5. 実環境で確認した状態は、対象revisionと証跡を添えて`doc/manual/release-status.md`へ置く。
6. 複数作業で変わらない設計原則と理由は、既存の `doc/rules/` へ置く。
7. 特定ディレクトリで常に守る制約は、その範囲に最も近い `AGENTS.md` へ置く。
8. 特定作業の開始条件と手順は、既存のSkillへ置く。
9. 人間だけが行う運用は、既存の `doc/manual/` へ置く。
10. 該当する正本がない場合だけ、新しい文書またはSkillを作る。

一つの内容が複数の役割に関係する場合も、詳細は一箇所だけに置く。
ほかのファイルには発動条件と正本へのリンクだけを書く。

たとえば、テスト層を分ける理由と判断基準は `doc/rules/testing-strategy.md`、テストコードを書く手順は `test-strategy`、`e2e/` で常に守る禁止事項は `e2e/AGENTS.md` が所有する。

## 追加と変更の手順

1. 追加内容を、現行実装仕様、業務要件、検証契約、実環境状態、設計原則、常設制約、作業手順、人間の運用のいずれかに分類する。
2. `rg` で同じ主張と近い正本を探す。
3. 最も狭い既存の正本を更新する。
4. 発見に必要な入口だけ、上位の `AGENTS.md` または索引へ追加する。
5. 古い重複を削除し、必要な参照を正本へのリンクに替える。
6. `AGENTS.md`を追加、移動、削除した場合は、同じディレクトリの`CLAUDE.md`も同期する。互換入口の本文は`@AGENTS.md`だけにする。
7. Skillを追加、改名、削除した場合は、`.claude/skills/<name>`の個別相対シンボリックリンクも同期する。
8. 対象範囲の指示連鎖、CLAUDE互換入口、Skill metadata、Skillリンク、Markdownリンク切れを検証する。

レビュー指摘や一時的な判断を、そのまま常設ルールへ昇格させない。
同じ判断が再利用でき、適用範囲と理由を説明できる場合だけ正本へ反映する。

## 衝突時の扱い

コードまたは設定と機能文書が食い違う場合は、コードまたは設定を現在事実として扱い、機能文書を現状へ合わせる。
業務要件と現行実装が食い違う場合は、どちらかを暗黙に書き換えない。差分を「要件判断」として報告し、要件を変えるか実装を変えるか決まった後に、それぞれの正本を更新する。
Production、migration、外部サービス設定は、repositoryの実装やテストから確認済みと推測せず、`doc/manual/release-status.md`の実環境証跡で判定する。

上位と下位の `AGENTS.md` が食い違う場合は、対象に近い指示を優先する。
ただし、下位ファイルは上位の安全制約を暗黙に解除できないため、例外が必要なら理由と範囲を明記する。

## サイズの基準

ルートから対象ディレクトリまでに適用される `AGENTS.md` の合計は、32,768 byte未満を必須とし、24,576 byte以下を目標とする。
上限へ近づいたら、設計理由を `doc/rules/`、作業手順をSkillへ移し、`AGENTS.md` には常設制約と参照だけを残す。

`.agents/skills/*/SKILL.md` の `name` と `description` の合計は、6,000文字以下を目標とする。
descriptionには発動条件と対象範囲を短く書き、手順や背景は本文へ置く。

`.claude/skills/`はディレクトリ全体への一括リンクにしない。
利用可能にするSkillだけを個別リンクにし、リンク名とSkillの`name`を一致させる。

## 用語と文章

一般に定着した用語がある場合は、その用語を使う。
説明を短くするためだけの新語は作らず、初出で意味が曖昧な略語は定義する。

規則は一文一義で書き、禁止、例外、理由を混ぜない。
同じ主張の言い換え、現在のファイル一覧の転記、コードから自動的に分かる値は残さない。

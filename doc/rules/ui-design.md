# UI設計方針

## 目的

この文書は、シフトリのUIを設計するときに変えない製品原則と判断基準を定める。
具体的な作業手順は `ui-architect`、フロントエンドの配置と依存方向は `frontend-architecture.md` が所有する。

## プロダクトの約束

シフトリは、スタッフへ追加の負担を求めずに希望回収からシフト作成までを進められる状態を目指す。
シフト担当者だけが準備すれば運用を始められ、スタッフは届いたリンクから操作できることを基本とする。
アカウント登録やアプリのインストールを、スタッフ向け主要導線の前提にしない。

スタッフが提出した希望は、シフト担当者が転記しなくてもシフト表へ反映される。
LINEやメールの回答を一件ずつ表計算へ移す作業をなくすことが、製品価値の中心である。

## 利用者

主な利用者は、日常業務の途中でシフトを管理する非技術系の店舗運営者とスタッフである。
利用者が内部の状態名、通知基盤、権限モデルを知らなくても、現在の状態と次の行動が分かるUIにする。
特定の架空人物や業種だけを前提にせず、店舗運営に共通する仕事の言葉を使う。

## 判断基準

設計案は、次の順で評価する。

1. 利用者が目的を完了できるか。
2. スタッフやシフト担当者へ新しい転記、登録、確認作業を増やさないか。
3. 現在の状態、結果、次の行動を誤認しないか。
4. 日常的な操作を短い手順で終えられるか。
5. モバイルとデスクトップの双方で読み、操作できるか。
6. 見た目が既存UIと整合するか。

見た目の新しさは、業務上の意味と操作結果が伝わった後に評価する。

## タスクと画面構造

一つの画面では、利用者が最初に完了したい主作業を一つに絞る。
補助操作は主作業より弱く見せ、関係のない作業を同じ画面へ足さない。

一覧は日付や内部状態だけで並べず、利用者が次に行う仕事で分類する。
緊急性のない過去データや詳細は、主作業を妨げない位置へ分ける。

モバイルをデスクトップの縮小版にしない。
情報の順序、操作領域、Dialog、一覧の形を、片手で読み操作できる構造へ組み替える。

短い補助操作と最終確認はDialogに置いてよい。
URL共有、ブラウザバック、長時間の編集を必要とする作業は、独立したページを優先する。

## 状態の伝え方

Loading、Empty、Error、Success、処理中を別の状態として設計する。
空状態には、データがない理由と次にできる行動を示す。
エラーは、利用者が直せる入力、画面内の失敗、ページ全体の失敗を分ける。

非同期処理では、受け付けたこと、送信したこと、相手へ届いたことを区別する。
通知操作の成功は「送りました」または「再送しました」と表現し、配送確認がない状態で「届きました」と断定しない。

内部状態名、token、Outbox、schedulerなどの実装用語を、そのまま利用者へ見せない。
利用者が取るべき行動へ言い換える。

## 操作の安全性

主アクションは画面内で一つだけ強く見せる。
破壊的操作では、対象、結果、元に戻せるかを具体的に伝える。

ボタンの非表示や無効化だけで、認可、入力制約、二重送信を保証しない。
安全上の制約はサーバー側でも守り、UIは理由と回復方法を伝える。

スタッフ向け画面で操作を続けられない場合は、状態だけで終えず、「シフト作成担当者に連絡してください」など次の行動を示す。

## 一貫性と検証

既存のUI部品、語彙、色の意味を優先し、新しい表現を局所的に増やさない。
文言を変更したら、同じ事実を説明するStory、テスト、FAQ、HowTo、通知文面を確認する。

実装と文言が食い違う場合は、コードを現在事実として文言を直す。
望ましい将来像を、現在の挙動として先に説明しない。

代表状態は自動テストまたはStoryで契約として残す。
どのテスト層で守るかは `testing-strategy.md`、具体的な検証手順は `test-strategy` が所有する。

## 1. この文書の位置づけ

この文書は、シフトリにおける組織単位の課金と、有料機能に関係する業務要件を定める。

コード、DB Schema、API、Migrationの識別子は受入条件を一意にするため参照するが、現在の技術仕様や実環境状態の正本にはしない。

課金、複数店舗、複数管理者に関する既存の準備中資料と本書が矛盾する場合は、本書を業務要件の正本とする。

業務要件は現行実装より先に確定することがある。  現在の挙動はコード・設定と[現行実装仕様](../features/organization-billing.md)、検証状態は[Full Regression横断契約表](full-regression-contracts.md)、実環境状態は[リリース状態](../manual/release-status.md)を参照する。差分がある場合は本書を暗黙にコードへ合わせず、「要件判断」として扱う。

「AIシフトたたき台作成」は業務要件に記載済みだが、詳細は要件判断、コードは未実装である。  現行機能や検証済み契約として扱わない。

実装時は、本書の業務ルールを技術設計、画面設計、テスト設計へ分解する。

## 2. 目的

本仕様の目的は、次の三つを同時に満たすことである。

- 一つの契約で、同じ組織に属する複数店舗をまとめて利用できるようにする。
- 一つの組織を複数の管理者で運営できるようにする。
- 契約終了や支払い失敗が起きても、既存データを失わずに整理と復旧ができるようにする。

## 3. 用語

| 用語 | 定義 |
|---|---|
| 組織 | 契約、利用人数、店舗、管理者をまとめる単位であり、内部的なOrganizationに相当する。 |
| 店舗 | シフトを運用する単位であり、一つの組織に複数所属できる。 |
| 利用者 | 組織内で管理者またはスタッフとして有効な人物である。 |
| 利用人数 | 組織内の有効な利用者を人物単位で重複なく数えた人数である。 |
| 有効管理者 | 組織全体の管理と契約操作を行える管理者である。 |
| 元管理者 | 管理者所属を終了した人物である。組織人物と既存の店舗スタッフ所属は維持できるが、管理画面のデータは閲覧できない。 |
| Free | Freeプランを適用した`active.free`である。追加組織の作成、未契約のTrial終了、有料契約の解約確定、支払い猶予終了、Stripe上の想定外解約から移行する。 |
| 解約 | 有料契約を現在の支払い済み期間の終了時に終え、データを保持したまま`active.free`へ移す操作である。 |
| 旧Free変更予約 | `targetPlan: "free"`を持ち、`restrictAtPeriodEnd: true`を持たないdeployment前から保存済みの期間末変更である。 |
| 支払い不要Pro相当 | 既存の対象組織、移行対象組織、または有効なプロモーションコードを入力した初回Setupへ、期限と利用料金を設けずProと同じ機能を提供する状態である。canonicalな内部状態は`complimentary.pro`である。二つ目以降の追加組織には付与しない。 |
| 初回請求処理中 | 無料体験が終了し、Stripeから初回支払い結果が届くまでの状態である。 |
| 稼働店舗 | 現在のシフト運用対象として有効な店舗である。 |
| アーカイブ済み店舗 | 運用を終了したが、履歴閲覧のために残す店舗である。 |
| 上限超過 | 保存済みの現在プランに対し、未承認招待を除く実際の利用人数、稼働店舗数、有効管理者数のいずれかが上限を超えた状態である。DBへ保存せず、現在値から導出する。 |
| 利用上限評価不能 | bounded評価で利用上限内か確定できない状態である。上限超過とは区別して表示し、安全のため同じ操作制限を適用する。 |
| 課金通知 | 契約、プラン、請求、支払い方法、支払い結果に関する通知である。 |
| ログイン方法 | Clerkが管理する確認済みメール、パスワード、Google接続など、シフトリへの認証手段である。 |
| シフト連絡先 | 組織人物ごとに保持し、本人のシフト通知と管理者向け業務連絡に使うメールアドレスである。 |
| 請求先メールアドレス | 組織ごとに保持し、Stripeの請求書、領収書、カード関連通知に使うメールアドレスである。 |

利用者向け表示は「組織」とし、コード、DB、APIなどの内部名は`Organization` / `organization`を維持する。
画面では技術用語のOrganizationやOrgを原則として表示しない。

支払い不要Pro相当のcanonicalな保存状態は`complimentary.pro`だけとする。
Widen中だけ、versionのない`complimentary.business`を旧IDとして読み取り、`planIdVersion: 2`を伴うcanonical状態と区別する。  このDB側versionは移行中の曖昧性を解消する一時markerであり、旧writerと旧readerの共存が終わるNarrow時に旧ID互換とともに削除する。

プランIDを送受信するrequestとresponseは、Widen中だけ任意の`planIdVersion: 2`を受け付ける。  新clientはversion 2と`standard | pro`を使い、versionを送らない旧clientには旧`pro | business`へ投影したresponseを返す。  課金の外部副作用を開始するrequestはversion 2を必須とし、旧clientをfail closedにする。

現在のプランと決済ライフサイクルは課金状態として保存する。
上限超過と利用上限評価不能は、保存済みのプランと現在の実利用数から導出し、課金状態として保存しない。

## 4. 基本原則

### 4.1 契約単位

契約は店舗単位でもユーザー単位でもなく、組織単位とする。

通常課金を利用する一つの組織には、一つのStripe Customerと、一つ以下の有効なStripe Subscriptionを対応させる。

支払い不要Pro相当には、Stripe Customer、Subscription、Checkout Session、Portal Session、Invoice、Subscription Schedule、課金operation、課金通知を作成しない。

支払った個人を契約所有者として固定しない。

### 4.2 管理権限

無料体験中、有料契約中、または支払い不要Pro相当の有効管理者は、全員が同じ管理権限を持つ。

有効管理者は、組織内の現在の店舗と将来追加される店舗をすべて管理できる。

有効管理者は、契約開始、プラン変更、解約予約、変更予約の取消、支払い方法の更新を実行できる。

ただし、支払い不要Pro相当ではこれらの課金操作を提供せず、通常の管理者操作やStripeイベントから状態を変更しない。

BillingManagerや契約者専用ロールは設けない。

### 4.3 有料機能

有料機能は次の三つとする。

- AIシフトたたき台作成
- 3名以上の管理者
- 複数店舗

Featureフラグではなく、組織の契約状態とプランでUI表示と実行可否を決める。

UIを隠すだけでは認可とせず、実行時にも組織、管理者権限、契約状態、プラン上限を確認する。

### 4.4 通知チャネル

通常課金で課金通知が発生する場合は、LINE連携の有無にかかわらずメールで送る。

課金通知をLINEへ送らない。

支払い不要Pro相当では課金通知を発生させない。

店舗単位の管理通知のうち、スタッフ参加申請digest、シフト確定催促、店舗登録後の本番募集案内、通知不達digestは、対象店舗にスタッフとして所属するactive管理者だけへ送る。
対象者が0人なら送信しない。
組織共通のLINE連携が有効かつ友だち状態ならLINEを優先し、それ以外は組織人物の現在のシフト連絡先へメールで送る。

課金通知と管理者招待は組織単位の通知とし、店舗のスタッフ所属を受信条件にしない。

画面内のバナーやお知らせは、メールを補助する目的で併用できる。

### 4.5 メールアドレスの責務

ログイン方法、シフト連絡先、請求先メールアドレスは、それぞれ異なる目的と変更導線を持つ。

ユーザー詳細でシフト連絡先を変更しても、ログイン方法と請求先メールアドレスは変更しない。

ログイン方法を変更しても、各組織のシフト連絡先と請求先メールアドレスは変更しない。

請求先メールアドレスを変更しても、ログイン方法とシフト連絡先は変更しない。

初回セットアップでは一つの入力値から本人のシフト連絡先と組織の初期請求先を作るが、作成後は独立して管理する。

ログインアカウントに保存された初期メール値や、認証providerが返すprimary emailを、現在のシフト連絡先や請求先の暗黙の正本にしない。

## 5. プラン

### 5.1 プラン構成

| 状態またはプラン | 利用人数 | 稼働店舗 | 有効管理者 | 有料機能 |
|---|---:|---:|---:|---|
| 無料体験 | 50名まで | 5店舗まで | 5名まで | Pro相当 |
| Free | 5名まで | 1店舗まで | 2名まで | 利用不可 |
| Standard | 25名まで | 5店舗まで | 5名まで | すべて利用可 |
| Pro | 50名まで | 5店舗まで | 5名まで | すべて利用可 |
| 支払い不要Pro相当 | 50名まで | 5店舗まで | 5名まで | Pro相当 |

利用者向けのプラン名称はStandardとProとする。  内部ID、互換期間、migrationの現在仕様は[現行実装仕様](../features/organization-billing.md)と[組織課金の運用](../manual/organization-billing.md)を参照する。

利用人数は管理者を含む人物の合計であり、有効管理者数はその人物へ付与できる管理者権限の上限である。

現在の利用上限状態は、未承認の管理者招待を除く実際の利用人数、稼働店舗数、有効管理者数を、現在適用中のプラン上限と比較して導出する。
未承認招待の予約枠は、新しい招待の発行と承認の可否には使うが、現在の実利用数と上限超過の導出には含めない。

`pendingActivation`では、providerの結果が確定するまで`fallback`のFreeまたはStandardを適用する。
有料プランを有効にしない結果が確定した場合は、上限内かどうかにかかわらず`fallback`が示す`active.free`または`active.standard`へ移行する。
ローカルの処理期限だけでは`pendingActivation`を終了せず、Stripe上の結果を確認してから保存状態を変更する。

Localと開発用Convex deploymentはそれぞれ専用のStripe Sandboxへ接続する。  StandardとProは同じ通貨と請求周期のrecurring Priceを登録し、期間末処理の確認では必要に応じて日次や週次へ短縮できる。
両環境では`sk_test_`で始まるSecret keyを使用する。

本番deploymentは本番Stripeアカウントへ`sk_live_`で始まるSecret keyを使って接続する。
接続環境は`STRIPE_SECRET_KEY`の接頭辞から自動判定し、Stripeオブジェクトの`livemode`と一致しない場合は課金操作を拒否する。
税、返金、未払い請求の終端方針と本番用Stripe設定を確認するまでは対象Priceをアーカイブして新規販売を停止する。
発行済みのopen Checkout Sessionは別途失効させ、既存契約のWebhook受信と安全処理は継続する。

支払い不要Pro相当は、既にこの状態である組織、課金証跡がないことを確認して移行した対象組織、有効なプロモーションコードを入力した初回Setupの組織に適用する。

支払い不要Pro相当には利用期限、請求周期、支払い方法、請求書を設けない。

Freeの組織でも、有料機能を使うためにStandardまたはProを契約できる。

利用人数が減っても、自動で下位プランへ変更しない。

### 5.2 上限を超える操作

Standardでは26人目、Proでは51人目、Freeでは6人目を追加する操作を変更確定前に止める。

どのプランでも店舗上限を超える操作を変更確定前に止める。

管理者招待の発行と承認では、期限内の未承認招待が予約している利用人数枠と管理者枠も含め、確定後に上限を超えないことを確認する。

画面には現在の利用状況を表示する。  上位の有料プランを選べる場合だけプラン変更導線を表示し、Proの上限到達時に問い合わせ導線は表示しない。

上限を超える変更を一部だけ保存しない。

一方、Trial終了、解約、猶予終了、想定外解約、ProからStandardへの変更、`pendingActivation`のfallback確定では、上限超過を理由にプラン適用を拒否しない。
変更先の`active.free`または`active.standard`を保存し、上限超過だけを現在の実利用数から導出する。

上限超過または利用上限評価不能の間は、17章で定める整理、課金、終了操作だけを許可する。
実利用数が上限内になった時点で、課金状態の更新やschedulerを待たずに通常利用へ戻す。

## 6. 利用人数

### 6.1 数え方

利用人数は、組織内の人物を一意な組織内利用者IDで数える。

メールアドレスは同一人物の候補判定に使うが、恒久的な主キーにはしない。

同じ人物が複数の店舗に所属しても、一人として数える。

同じ人物が管理者とスタッフを兼ねても、一人として数える。

### 6.2 算入表

| 状態 | 利用人数への算入 |
|---|---:|
| 管理だけを行う有効管理者 | 1名 |
| スタッフ | 1名 |
| 管理者兼スタッフ | 1名 |
| 複数店舗に所属する同一人物 | 1名 |
| シフト対象外のスタッフ | 1名 |
| アーカイブ済み店舗にしか所属していないスタッフ | 1名 |
| 元管理者で、スタッフではない人物 | 0名 |
| 元管理者で、スタッフでもある人物 | 1名 |
| 管理者招待を承認していない人物 | 0名 |
| 店舗から削除されたが、組織には残っている人物 | 1名 |
| 組織から削除された人物 | 0名 |

### 6.3 Freeの5名の意味

Freeの上限は、「管理者とは別にスタッフ5名」ではない。

Freeは、管理者を含む利用人数の合計が5名までである。

管理者2名がどちらもスタッフを兼ねない場合は、管理者2名とスタッフ3名で合計5名になる。

管理者がスタッフも兼ねる場合は、その人物を含む5名まで利用できる。

### 6.4 利用人数と管理者上限の関係

利用人数はスタッフと管理者を合わせた人物数であり、管理者を利用人数とは別に追加できる枠ではない。

管理者上限は、利用人数に含まれる人物のうち管理者権限を付与できる人数を表す。

既存スタッフへ管理者権限を付与する場合は利用人数を増やさず、管理者数だけを一名増やす。

組織外の人物を管理者として招待する場合は、利用人数と管理者数の両方に空きが必要である。

この空きの判定では未承認招待の予約枠を加味するが、未承認者を現在の利用人数または現在の有効管理者数として表示しない。

## 7. 組織、店舗、利用者の関係

### 7.1 組織の作成

一人のユーザーが自分で作成して保持できる有効な組織は、三つまでとする。

所属0件からの初回Setupで作る組織は、プロモーションコードが空欄なら2か月のTrialとして開始し、入力値が前後空白除去・大文字化後にserver-only設定と一致する場合は期限と利用料金のない`complimentary.pro`として開始する。

プロモーションコードは6桁の英数字とする。  入力済みのコードが形式不正、設定不備、不一致のいずれかで適用できない場合は初回Setup全体を拒否し、Trialへfallbackしない。  コード値はDB、audit、analytics、ログへ保存しない。

二つ目以降に作る組織は、Freeプラン（内部状態`active.free`）として開始する。

二つ目以降を作成するときは、選択中組織にある操作本人の氏名とシフト連絡先だけを、新しい組織人物、最初の店舗スタッフ、初期請求先へ引き継ぐ。

サーバーは、引き継ぎ元の店舗と組織に操作本人が有効な管理者として所属し、本人の組織人物が一意であることを確認する。

操作本人は新しい組織の最初の管理者兼スタッフとして作成するが、引き継ぎ元の別人物、追加のスタッフ所属、店舗、シフト、他の役割状態は複製しない。

他の組織から招待されて所属する数には上限を設けない。

招待された組織への所属によって、新しい組織や課金状態は作成しない。

### 7.2 組織名

初回作成時および追加組織作成時は、最初の店舗名に「グループ」を付けた値を組織名の初期値として使う。

組織名の入力を初回登録の必須手順にはしない。

組織名は、複数組織に所属する利用者が誤操作しないために、後から組織設定で自由に変更できるようにする。初期値の「グループ」を削除する変更も許可する。

組織名は、通常利用中の有効管理者が変更できる。
上限超過または利用上限評価不能の間は整理操作に当たらないため変更できない。

### 7.3 同じ組織内での人物再利用

スタッフと管理者の追加には、メールアドレスを必須とする。

スタッフまたは管理者を追加するときは、入力されたメールアドレスを正規化して、同じ組織内だけを照合する。

正規化では、前後の空白を除去し、大文字と小文字の違いを同一として扱う。

同じ組織に既存人物がいる場合は、その人物を再利用し、登録済みの名前を正とする。

既存人物を別店舗へ追加する場合は、店舗所属だけを追加する。

既存スタッフを管理者へ変更する場合は、同じ人物へ管理者権限を追加する。

これらの操作では、人物が増えないため利用人数も増えない。

### 7.4 別組織の人物

別組織に同じメールアドレスの人物が存在しても、その所属、役割、名前、スタッフ情報を参照しない。

別組織の人物を検索できる共通名簿は設けない。

別組織へ追加するときは、現在と同じスタッフ追加または管理者招待の導線から開始する。

受信者が承認した後に、同じログインアカウントを再利用できる。

## 8. 管理者の権限

### 8.1 権限状態

| 状態 | 既存データ閲覧 | 業務操作 | 契約操作 | 支払い復旧 | 管理者として人数算入 |
|---|---:|---:|---:|---:|---:|
| 通常利用中の有効管理者 | 可 | 可 | 可 | 可 | 1名 |
| 上限超過または利用上限評価不能の有効管理者 | 可 | 整理操作のみ可 | 可 | 可 | 1名 |
| 元管理者 | 不可 | 不可 | 不可 | 不可 | 0名 |
| 組織から削除済み | 不可 | 不可 | 不可 | 不可 | 0名 |

元管理者がスタッフでもある場合は、管理画面には入れないが、既存のスタッフ所属に基づいて一人に数える。

上限超過では管理者所属を変更せず、有効管理者を一人ずつ実利用人数と有効管理者数へ含める。

### 8.2 最後の有効管理者

通常利用中の組織には、常に一名以上の有効管理者を置く。

最後の有効管理者は、引き継ぎを完了するまで組織から削除できない。

Freeで有効管理者が2名いる場合は、1名の管理者権限を外せる。

1名から0名にする権限解除は拒否する。

### 8.3 管理者ではなくなった人物

管理者所属を終了した人物は、ログインアカウントと組織人物を維持してもよい。

管理者だったことを根拠に、組織設定、店舗ダッシュボード、シフト、過去データ、スタッフ情報を閲覧させない。

その人物に既存の店舗スタッフ所属がある場合は、所属店舗、シフト対象設定、削除状態を変更せず、スタッフ向けのシフト募集と通知を継続する。

管理者交代を理由に、所属していなかった店舗へ新しいスタッフ所属を作成しない。

スタッフとして利用できる画面と操作は、管理画面とは分離したスタッフ向け認証と既存の店舗スタッフ所属だけで判定する。

### 8.4 管理権限を外す操作

管理権限を明示的に外した人物は、別の管理者状態へ自動変更しない。

その人物がスタッフでもある場合は、スタッフとしての所属だけを残す。

その人物がスタッフではない場合も、管理者権限の終了後に、組織から削除する別操作で影響を確認してアクセスを終了する。

明示的に管理権限を外された人物は、契約終了や再契約によって自動復元しない。

上限超過または利用上限評価不能の間も、最後の有効管理者を残す範囲で管理者権限を外せる。

activeな管理者でも、個別店舗または全店舗のスタッフ所属だけを解除できる。
店舗所属の解除では管理者権限と組織人物を維持する。

上限超過または利用上限評価不能の間は、利用人数を減らさない店舗スタッフ所属だけの解除を整理操作として許可しない。
利用人数を減らす場合は、影響確認を伴う組織からの人物削除を使う。

## 9. 必要な画面

### 9.1 組織設定

管理者向けに「組織設定」を設ける。

組織設定は、少なくとも次の三つの領域を持つ。

| 領域 | 主な内容 |
|---|---|
| 利用者 | 組織全体の管理者とスタッフ、所属店舗、役割、利用人数、管理者権限状態、削除操作 |
| 店舗 | 稼働、アーカイブ済みの店舗一覧、店舗追加 |
| プランと支払い | 現在のプラン、実利用人数、未承認の管理者招待数、店舗数、管理者数、上限評価状態、無料体験終了日、次回請求日、契約変更、支払い方法、請求書 |

上限超過では現在プランをそのまま表示し、超過した項目と上限内へ戻すための整理操作を案内する。
利用上限評価不能では上限超過と断定せず、通常操作を一時的に停止していること、管理画面での確認・整理、問い合わせを案内する。

支払い不要Pro相当では「Pro」と「支払い不要」を表示し、「Proの機能を料金なしで利用できます」と案内する。

支払い方法、請求先メールアドレス、請求書、Portal、プラン変更などの課金操作は表示しない。

### 9.2 複数組織と初期表示

管理者招待を承認した直後は、招待先の組織と店舗を表示する。

現在タブの店舗コンテキストは`?shop=`を正とする。

URLで指定された店舗は、認証済み利用者が利用できる店舗一覧と照合してから採用する。URLとlocalStorageは認可根拠にせず、管理者APIでも所属と店舗境界を再確認する。

URLに有効な店舗指定がない通常ログイン時は、最後に表示していた有効な店舗を初期表示する。

最後の店舗を利用できない、または前回値がない場合は、利用可能な店舗一覧の先頭を候補数にかかわらず表示する。

自動決定した店舗は`replace`でURLへ反映し、専用の店舗選択画面は設けない。

URLで明示された店舗が利用可能な候補にない場合は、別店舗へ自動的に切り替えず、店舗スコープのデータを表示しない汎用エラーを表示する。

Dashboardでは、現在の組織に属する店舗を作業対象として表示する。候補が一店舗の場合は静的表示とし、複数店舗の場合だけ同じ組織内で切り替え可能にする。

組織切り替えはアプリヘッダーで扱い、Dashboard内では組織を切り替えない。最終的な操作コンテキストは常に店舗とする。

契約操作の確認画面には、対象組織名、現在のプラン、対象店舗を必ず表示する。

## 10. 無料体験

### 10.1 開始

所属0件からの初回Setupでプロモーションコードを入力しない場合は、2か月のTrialとして無料体験を開始する。  既存のTrial状態を持つ組織も無料体験を継続する。  有効なコードで支払い不要Pro相当を適用する場合と、二つ目以降の組織作成時には無料体験を開始しない。

コード空欄の初回Setupは支払い方法を登録せず、Pro相当のTrial状態とTrial期限を作成し、期限処理を予約する。  Stripe Customer、Subscription、課金operationは作らない。

有効なコードの初回Setupはcanonicalな`complimentary.pro`を作り、Trial期限と期限処理を作らない。  Stripe Customer、Subscription、課金operation、課金通知も作らない。

無料体験中は、Proと同じ50名、5店舗、5管理者の上限と有料機能を利用できる。

### 10.2 期間

Trial状態の無料体験は、Trial開始日から2か月とする。

終了時刻は、登録開始日の2か月後にあたる日の午前0時JSTとする。
2か月後の月に同じ日が存在しない場合は、その月の末日午前0時JSTへ丸める。

たとえば2026年7月14日に作成した場合は、2026年9月13日まで無料で利用でき、2026年9月14日午前0時JSTに終了する。

この期間変更は、新規Setupで計算する`trialEndsAt`にだけ適用する。  保存済みの`trialEndsAt`は変更せず、保存shapeも変えないためmigrationとbackfillは行わない。

### 10.3 終了前の通知

無料体験終了の7日前に、全有効管理者へメールを送る。

契約済みの場合は、契約プラン、初回請求日、継続予約を取り消したときはTrial終了後にFreeへ移行することを案内する。

未契約の場合は、終了時にFreeへ移行すること、データを保持すること、Free上限を超える場合は整理または有料契約まで通常操作が制限されることを案内する。

### 10.4 継続予約の取消

無料体験中にStandardまたはProの継続を予約した管理者は、無料体験終了時刻まで継続予約を取り消せる。

取消時点ではTrialを維持し、無料体験終了時刻を変更しない。

取消後は初回請求を開始せず、無料体験終了時に`active.free`へ移行する。

継続予約の取消では管理者や稼働店舗を自動で削減しない。

画面と確認ダイアログには、取消後の終了日、データを保持すること、Free上限を超える場合は終了後に通常業務を停止することを表示する。

### 10.5 終了時の判定

| 終了時の状態 | 遷移 |
|---|---|
| 契約済み | 初回請求処理中へ移行 |
| 未契約 | `active.free`へ移行 |
| 終了前に継続予約を取り消した | `active.free`へ移行 |

無料体験終了によって、店舗、利用者、シフトを削除しない。

初回請求処理中の利用権限はStandard相当とし、画面には支払い結果の確認中であることを表示する。

初回支払い成功を確認した場合は、選択した有料プランへ移行する。

初回支払い失敗を確認した場合は、その失敗時刻から14日間の支払い猶予へ移行する。

支払い結果を一定時間確認できない場合は、Stripe上の最新状態を照合し、未確定のまま放置しない。

未契約または継続予約取消済みの無料体験から`active.free`へ移行するときは、直前の管理者と稼働店舗の状態を維持する。
人物、店舗、スタッフ所属、シフトを削除せず、Free向けの役割変更や店舗停止を行わない。
Free上限を超える場合は上限超過を導出し、17章の操作制限を適用する。

## 11. 契約開始

### 11.1 無料体験中の契約

無料体験中に契約する場合は、StandardまたはProの継続利用を選択してカードを登録する。

対象プランのPriceをStripeから取得できない場合は、そのプランの契約操作だけを停止する。

カード登録の完了時には請求せず、無料体験終了時に初回請求する。

無料体験終了時点では初回請求処理中へ移行し、Stripeから支払い成功または支払い失敗を確認した後に状態を確定する。

無料体験終了前に継続予約を取り消した場合は、初回請求しない。

無料体験終了時刻までは、有料機能を利用できる。

### 11.2 無料体験終了後の契約

無料体験終了後に初めて契約する場合は、その場で初回請求する。

支払い成功を確認した後に、選択したStandardまたはProを有効にする。

支払いに失敗した場合は、有料プランを有効にしない。

Freeの組織は既存Freeを維持する。

### 11.3 プラン選択

現在の実利用数が選択プランの上限を超えていても、StandardまたはProを選択できる。
画面には、選択プランの上限と、通常利用へ戻るために必要な削減数を表示する。

利用人数が1名から5名の場合でも、有料機能を使うためにStandardまたはProを選択できる。

Pro上限を超える場合も支払い成功後は`active.pro`を適用し、上限超過中は整理、課金、終了操作だけを許可する。

## 12. プラン変更

### 12.1 変更できる範囲

Freeまたは無料体験からStandardまたはProを利用する操作は、11章の契約開始として扱う。

StandardからProへの変更は即時変更とし、Stripeが算出した残期間の差額を日割り請求する。

支払い成功と変更後Subscriptionを確認するまではStandardの利用権限を維持する。

ProからStandardへの変更と、StandardまたはProの解約は、現在の支払い済み期間の終了時に適用する。

ProからStandardへの変更予約にはStripe Subscription Scheduleを使い、Stripe上のphase移行を確認してからアプリの状態を変更する。

期間末変更の予約は適用前に取り消せる。

解約とdeployment前の旧Free変更予約の適用手順は16章で定める。

### 12.2 人数が増えない操作

既存人物を別店舗へ追加する操作では、プラン変更を求めない。

既存スタッフを管理者へ変更する操作では、プラン変更を求めない。

既存スタッフを二人目以降の有効管理者へ変更できるのは、Free、無料体験、Standard、Pro、支払い不要Pro相当とする。

Freeでは、既存スタッフの管理者化を通常の管理者追加として扱い、有効管理者と期限内の追加招待を合計2名までに限定する。

組織から削除済みの人物を再追加する操作では、一人増えるものとして上限を確認する。

## 13. 管理者招待

### 13.1 招待の開始

有効管理者は、組織設定から専用の管理者設定を開く。

組織に登録済みのスタッフを招待するときは、候補一覧から一名だけを選び、現在の正規化済みメールアドレスへ送る。

新しい人物を招待するときは、氏名と招待先メールアドレスを入力する。招待発行時点では組織人物を作らず、本人確認と承認が完了したtransactionで初めて人物と管理者所属を作る。

招待前に、追加される管理者が組織内の全店舗を管理でき、契約操作も行えることを確認画面で説明する。

Freeでも、既存スタッフと新しい人物のどちらにも通常の管理者追加招待（`purpose: "managerAddition"`）を発行できる。
新しい人物では利用人数と管理者数の両方、既存スタッフでは管理者数の空きを発行時と承認時に確認する。

招待はメールで送る。

LINE連携済みの人物にも、管理者招待をLINEでは送らない。

### 13.2 既存アカウントと未登録者

既存アカウントの受信者は、ログイン後に招待を承認する。

招待対象の組織人物が既にログインアカウントへ接続されている場合は、同じアカウントでログインした本人だけが承認できる。

この場合は接続済みアカウントを本人性の根拠とし、ログイン用メールアドレスと招待先メールアドレスの現在値が同じであることを要求しない。

未登録の受信者は、アカウント登録後に同じ招待へ戻り、そのまま承認できる。

招待対象の組織人物がログインアカウントへ未接続、または組織人物がまだ存在しない場合は、Clerkが確認済みとして返すメールアドレスのいずれかと招待先メールアドレスの一致を要求する。

primary emailの値だけや、未確認のメールアドレスは承認根拠にしない。

登録画面をまたぐときも、招待を識別する情報を安全に引き継ぐ。

### 13.3 招待の安全条件

招待URLには、メールアドレス、組織ID、役割を直接含めない。

招待URLには、招待を識別する十分にランダムな値だけを含める。

招待は発行から7日間有効とする。

招待は一回だけ使用でき、管理者がいつでも取り消せる。

通常の追加招待を再送するときは、古い未使用招待を無効にする。

同じ対象に期限内の招待がある場合、新規発行操作を暗黙の再送として扱わない。管理者設定の招待中一覧から明示的に再送し、古いURLが無効になることを確認する。

未接続人物の承認では、サーバーがClerk Backend APIから確認済みメール一覧を取得し、招待先との一致を確認する。

Clerkの設定不足、一時障害、照会失敗では承認を完了せず、招待を未使用のまま残して再試行できる結果を返す。

確認済みメールの照合後も、同じ認証主体、招待、version、tokenに対する確認結果であることを確定処理で再検証する。

招待発行時と承認時の両方で、契約状態、管理者権限、利用人数上限、管理者上限を確認する。
上限超過または利用上限評価不能の間は、新しい招待の発行、再送、承認を許可せず、既存招待の取消だけを許可する。

既存スタッフへの招待は対象人物を招待へ記録し、承認時にも対象人物、現在の確認済みメールアドレス、招待先メールアドレスの一致を確認する。

招待後に対象スタッフのメールアドレスが変わった場合は、古い招待を承認させず、新しいメールアドレスへ新たに招待する。

招待を発行した管理者が組織から削除された場合は、その管理者が発行した未承認招待を無効にする。

一つの組織と正規化済みメールアドレスにつき、有効な管理者招待は一つまでとする。

同じメールアドレスへの招待が並行して要求されても、招待と予約枠を一つだけ作る。

### 13.4 利用枠

未承認の招待は利用人数に含めない。

未承認の招待は、現在の実利用人数、有効管理者数、上限超過の導出にも含めない。

新しい人物を招待する場合は、承認時に上限超過しないよう一人分の利用枠を予約する。

招待の取消または期限切れで、予約した利用枠を解放する。

同じ組織の既存スタッフを管理者へ変更する招待では、利用枠を追加で予約しない。

新しい管理者招待の発行と承認可否は、有効管理者と期限内かつ未承認の追加管理者招待を合計した見込み人数で判定する。

無料体験、Standard、Pro、支払い不要Pro相当では、見込み管理者人数を五名までとする。

Freeでは、有効管理者と期限内かつ未承認の追加管理者招待を合計2名までとする。

旧`freeManagerExchange`招待は管理者枠を追加で予約しないが、その招待が期限内で残る間は新しい追加招待を発行しない。

招待承認前に同じ人物がスタッフとして追加された場合は、予約した枠を実際の人物へ付け替え、二重に数えない。

### 13.5 承認完了

承認完了後は、受信者を組織全体の有効管理者にする。

Freeの通常の追加招待では、現在の管理者権限を維持したまま承認者を二人目の有効管理者にする。

既発行の旧`freeManagerExchange`招待だけは、期限内tokenの承認と招待の取消を許可する。
新規発行と再送は行わず、承認時は新しい管理者の有効化と旧管理者の管理者所属終了を同じトランザクションで確定する。

上限超過または利用上限評価不能の間は、旧`freeManagerExchange`招待も承認せず取消だけを許可する。

旧管理者の組織人物と既存の店舗スタッフ所属は変更せず、旧形式の店舗管理者所属だけを終了する。

承認完了を、承認者本人と他の全有効管理者へメールで通知する。

Trial、解約、支払い猶予、想定外解約から`active.free`へ移行するときは、契約終了時点の未承認招待を失効させる。
ProからStandardへの変更、通常の有料契約更新、上限超過の開始だけを理由に、未承認の追加管理者招待を自動で無効にしない。
上限超過中は承認と再送を止め、管理者による取消を許可する。

## 14. 店舗の追加と停止

### 14.1 店舗追加

無料体験、Standard、Pro、支払い不要Pro相当では、稼働店舗を5店舗まで追加できる。

6店舗目を追加する前に操作を止め、問い合わせへ誘導する。

アーカイブ済み店舗は、稼働店舗数へ含めない。

### 14.2 アーカイブ

店舗をアーカイブしても、店舗データと過去シフトを削除しない。

アーカイブ済み店舗にしか所属していない人物も、組織から削除されるまでは利用人数に含める。

アーカイブ済み店舗を再び稼働させる場合は、店舗上限を再確認する。

## 15. 店舗と組織からの削除

### 15.1 店舗から削除

「店舗から削除」は、対象人物と対象店舗の所属だけを解除する操作とする。

個別店舗から削除する場合は、他店舗への所属、組織内の人物情報、管理者権限を変更しない。

対象人物がactiveな管理者でも、個別店舗または全店舗のスタッフ所属を解除できる。

全店舗から削除する場合も、終了するのはスタッフ所属だけとし、組織人物と管理者権限を維持する。
対象店舗の店舗管理通知は、所属解除後もその店舗にスタッフとして所属するactive管理者だけへ送る。

最後の店舗から削除しても、組織に残っている限り利用人数から除外しない。

組織全体のユーザー一覧には、店舗所属がなくても利用人数に含まれる人物を「店舗未所属」として表示し、所属店舗を「店舗所属なし」と表示する。

画面には、「他の店舗と組織への所属は変わらず、利用人数にも引き続き含まれます」と表示する。

### 15.2 組織から削除

「組織から削除」は、その組織における全店舗所属、管理権限、スタッフ権限、閲覧権限を終了する操作とする。

対象人物がactiveな管理者でもある場合は、この操作を直接実行できない。
先に管理者設定で管理者権限を外し、その後に人物削除を行う。
人物削除mutationはこのserver-side guardを確定transaction内で再確認する。

操作完了時に、利用人数から除外する。

別組織への所属と、ログインアカウント自体には影響させない。

過去の確定シフト、操作履歴、通知履歴の参照は維持する。

組織からの削除はサービス上の所属解除であり、個人情報の完全消去とは別の手続きとする。

画面には、「すべての店舗から外れ、組織のデータを開けなくなりますが、過去のシフト記録は残ります」と表示する。

削除完了時に、その組織に対する既存のアプリ内セッション、スタッフ向けリンク、未使用招待を失効させる。

削除開始後は対象人物への新しい通知を予約せず、未送信通知を停止する。

外部送信の直前にも組織所属を確認する。

### 15.3 今日以降のシフトがある人物

今日または未来のシフトに割り当てられている人物も削除できる。

確認画面には、JSTの業務日付で数えた正確な件数を使い、「今日以降のシフトN件からも外れます」と表示する。

確認後に件数または対象が変わっていた場合は削除せず、最新の内容を再確認させる。

一度に安全に処理できる割当数を超える場合だけ削除を止め、先に対象シフトを整理するよう案内する。

削除確定時は、対象人物に紐づく今日以降の割当と人物の所属を同じ処理で削除する。

店舗から削除する場合はその店舗の割当だけを対象とし、組織から削除する場合は組織内の全店舗の割当を対象とする。

過去のシフト割当と監査履歴は保持し、削除済みの人物であることが分かる表示にする。

募集の状態、確定日時、残った人物の割当と提出は変更しない。

管理者権限だけを外す場合は、スタッフとしてのシフト割当を維持する。

### 15.4 再追加

同じ組織で同じメールアドレスの人物を再追加するときは、既存の組織内の人物を再利用する。

管理者手入力とQR申請の管理者承認は、削除済み人物と同じ正規化メールアドレスに一致しても削除履歴の特別確認を表示せず、通常のスタッフ追加として完了する。

内部では同じ組織人物をactiveへ戻し、今回の手入力または承認済み申請の氏名・正規化メールアドレスを現在の人物情報へ反映して、新しいstaff IDを作る。

再追加時は、現在のプラン上限を確認する。

旧staffの表示情報、旧staffのシフト提出と割当、管理者権限、ほかの店舗所属、session、magic link、LINE token、canonical LINE linkを変更・復元しない。

店舗所属だけを解除して組織人物をactiveのまま保つ場合はcanonical LINE連携を保持し得るが、組織から人物を削除した後の再追加ではcanonical LINE連携を復元せず、本人による新しいLINE連携を必要とする。

人物とstaffの対応が安全に一意解決できない不整合、account deletion受付済み、利用人数上限では、削除履歴や存在状態を示さない汎用的な追加・承認不可結果を返し、部分的に再有効化しない。

既存の人物状態、staff ID、正規化メールアドレスindexでこの再追加を表現できるため、schema変更とbackfillを必要としない。

必要な店舗所属と役割を改めて設定する。

## 16. プラン変更と解約

### 16.1 ProからStandardへの変更

ProからStandardへの変更は、現在の支払い済み期間の終了時に適用する。

予約時点で利用人数が25名を超えていても変更予約を妨げず、「あとN名削除してください」と必要な削減人数を表示する。

利用人数、店舗数、管理者数は自動で削減しない。

期間終了時にStripe上でStandardへのphase移行と請求結果を確認する。

Standard上限内かどうかにかかわらず、phase移行と支払い成功を確認した後は`active.standard`へ移行する。
上限を超えている場合はStandardを現在プランとして表示し、現在の実利用数から上限超過を導出する。

上限超過中に人物、管理者、店舗を整理してStandard上限内になった場合は、課金状態を更新せず通常利用へ戻す。

Standardの初回更新支払いに失敗した場合はProの14日間の支払い猶予へ入り、支払い成功後は`active.standard`へ移行して上限状態を導出する。

### 16.2 解約の名称と時期

有料契約を終える利用者向け操作名は「解約」とする。

「Freeプランに変更」は新しい操作として提供しない。

解約は現在の支払い済み期間の終了時に適用し、予約後も期間終了までは現在の有料機能を利用できる。

解約によって組織、店舗、人物、スタッフ所属、シフトを削除しない。

### 16.3 解約予約

全有効管理者が解約を予約できる。

解約ではFreeで残す管理者や店舗を選択せず、現在の管理者権限と稼働店舗をそのまま維持する。
復旧候補は新しく保存しない。

画面には解約日、Freeへ移行すること、データを保持すること、Free上限を超える場合に停止する業務操作を表示する。

予約はStripeの`cancel_at_period_end`へ反映し、providerから確認した結果だけを期間末の状態遷移へ使う。

新しい解約予約は、保存状態へ`restrictAtPeriodEnd: true`を付ける。
同じ`targetPlan: "free"`を持つdeployment前の旧Free変更予約とは、このmarkerで区別する。

### 16.4 解約予約の取消

支払い済み期間の終了前であれば、全有効管理者が解約予約を取り消せる。

取消はStripeで`cancel_at_period_end`が解除されたことを確認した後に確定する。

予約と取消は、全有効管理者へメールで通知する。

### 16.5 解約日の処理

Stripeで契約の期間末終了を確認した後、`active.free`へ移行する。

解約日の処理では、管理者所属、稼働店舗、人物、スタッフ所属、シフトを削除またはFree上限へ縮小しない。

直前の全有効管理者と稼働店舗を維持し、現在の実利用数からFreeの上限状態を導出する。
Free上限内であればFreeの通常機能を利用でき、上限を超えていれば17章の操作制限を適用する。

Stripe側の終了を確認できない場合は、ローカルの期限だけで`active.free`へ移さず再照合する。

### 16.6 deployment前のFree変更予約

deployment前から保存済みで、`targetPlan: "free"`かつ`restrictAtPeriodEnd: true`を持たない変更予約も、Stripe上の期間末終了を確認した後に`active.free`へ移行する。

旧予約からFreeへ移行しても、余剰管理者の管理者所属と店舗の稼働状態を自動で変更しない。

Free上限を超える場合は現在の実利用数から上限超過を導出し、整理後は課金状態の更新なしで通常利用へ戻す。

### 16.7 Freeで利用できること

`active.free`は、追加組織と既存のFree組織のどちらにも適用し、最大二名の有効管理者と最大一店舗で基本的なシフト運用を継続できる。

未契約のTrial終了、解約確定、猶予終了、Stripe上の想定外解約、旧Free変更予約から移行した組織にも、同じ`active.free`と上限を適用する。

Freeでは、利用人数の上限内でスタッフを管理し、シフト募集、シフト編集、シフト確定、通常の業務通知を利用できる。

AIシフトたたき台と複数店舗は利用できない。

元管理者は管理画面の既存データを閲覧できない。

Freeでは、既存スタッフまたは新しい人物を二人目の管理者として招待できる。
旧`freeManagerExchange`招待は新規発行と再送を行わず、既発行の期限内tokenの承認と招待の取消だけを互換処理する。

Free上限を超えている間は通常のスタッフ管理とシフト運用を停止し、17章の整理、課金、終了操作だけを許可する。

## 17. 上限超過

### 17.1 上限状態の導出

上限状態は、保存済みの現在プランと、未承認招待を除く現在の実利用人数、稼働店舗数、有効管理者数から要求ごとに導出する。

現在プランは`active.free`、`active.standard`、`active.pro`、`complimentary.pro`などの課金状態へ保存する。
上限超過の真偽、違反項目、超過数はDBへ保存しない。

bounded評価で上限内か確定できない場合は、上限超過と断定せず利用上限評価不能として扱う。
評価不能の間も通常業務を許可せず、管理画面での確認・整理と問い合わせを案内する。

### 17.2 プラン適用とデータの維持

未契約のTrial終了、解約確定、猶予終了、Stripe上の想定外解約では`active.free`を保存する。
ProからStandardへの変更確定では`active.standard`を保存する。
`pendingActivation`のfallbackがFreeまたはStandardで確定した場合は、それぞれ`active.free`または`active.standard`を保存する。

いずれも、変更先の上限を超えていることを理由にプラン適用を拒否しない。
管理者所属、稼働店舗、人物、スタッフ所属、シフトを自動で削減、停止、削除しない。

### 17.3 許可する操作

上限超過または利用上限評価不能の間も、有効管理者には既存データの閲覧を許可する。

通常利用へ戻すための整理、課金の管理、サービス利用の終了に必要な次の操作だけを許可する。

- 組織からの人物削除
- 最後の有効管理者を残す範囲での管理者権限解除
- 店舗のアーカイブと削除
- 未承認の管理者招待の取消
- 有料契約の開始、再開、上位プランへの変更
- 支払い方法と請求先メールアドレスの変更
- 組織の利用終了とアカウント削除に必要な操作

各操作は、対象組織、現在の管理者権限、操作種別をserver-sideで再確認する。
整理操作に見せかけて人物、店舗、管理者を増やす変更は許可しない。

### 17.4 停止する操作

上限超過または利用上限評価不能の間は、通常の業務を進める書き込みを停止する。

少なくとも次の操作を停止する。

- シフト募集の作成、編集、削除
- シフトの下書き保存、編集、確定
- スタッフによる希望シフト提出
- スタッフの追加と再有効化
- 管理者招待の発行、再送、承認
- 店舗の追加と再稼働
- 組織名など、上限整理に当たらない設定変更
- AIシフトたたき台作成
- 業務メール、LINE、provider連携を含む外部通知の新規送信

通知を伴う操作だけでなく、通知なしで業務を継続できる書き込みも停止する。
課金通知、請求処理、署名済みWebhook、上限整理に必要な監査記録は停止しない。

### 17.5 自動回復

人物削除、管理者権限解除、店舗のアーカイブまたは削除の後は、次の要求で現在プランと実利用数を再評価する。

すべての項目が上限内なら、課金状態の変更、上限超過フラグの更新、schedulerの実行を必要とせず、通常利用へ戻す。
停止済みの過去の外部通知は自動再送しない。

## 18. 支払い失敗

### 18.1 猶予の対象

有料契約の更新支払いが失敗した場合は、14日間の支払い猶予を設ける。

無料体験終了時に予定していた初回支払いが失敗した場合も、14日間の支払い猶予を設ける。

無料体験終了後に新しく契約する際の即時支払いが失敗した場合は、有料契約を開始していないため猶予を設けない。

### 18.2 14日間の定義

猶予開始は、対象請求に対する最初の支払い失敗時点とする。

猶予終了は、その時点から14日後の同時刻とする。

Stripeによる再試行回数や再試行時刻が変わっても、猶予終了時刻を延長しない。

### 18.3 猶予中

更新支払い失敗の猶予中は、失敗前の契約プランの全機能を通常どおり利用できる。
ただし、現在プランに対する上限超過または利用上限評価不能が導出された場合は、17章の操作制限を適用する。

TrialからProを選んだ初回支払い失敗では、Standard相当の利用権限を維持し、支払い成功後の移行先をProとして保持する。

ProからStandardへの期間末変更後にStandardの初回更新支払いが失敗した場合は、Proの利用権限を猶予中だけ維持する。

StandardからProへの即時変更が完了しなかった場合はProを有効にせず、Standardを継続する。

全有効管理者に、期限と支払い方法更新への導線を表示する。

支払い成功を確認した時点で警告を解除し、通常の契約状態へ戻す。

### 18.4 猶予終了

猶予終了時点で未払いの場合は、元のStripe Subscriptionの終了処理を開始する。
Stripe上の終了を確認した後に`active.free`へ移行し、ローカルの猶予終了時刻だけでは保存状態を変更しない。

Subscription終了処理が一時的に失敗した場合は、完了するまで再試行し、新しいSubscriptionとの二重契約を許可しない。

`active.free`への移行では、管理者権限、稼働店舗、人物、スタッフ所属、シフトを変更しない。
現在の実利用数がFree上限を超えている場合だけ17章の操作制限を適用し、上限内ならFreeの通常機能を利用できる。

旧Subscriptionに紐づく未払い請求は、新しい契約の請求と重複回収されない状態へ整理してから再契約を許可する。

旧未払い請求を無効にするか回収不能として扱うかは、会計方針を確定したうえで実装仕様に定める。

14日経過後に旧請求の支払い成功が届いても、自動復旧しない。

14日経過後の有料プランへの復旧は、新しい契約の支払い成功だけを根拠にする。

Free上限超過または利用上限評価不能となった場合は、未送信の業務通知を停止する。

支払い復旧に必要な課金メールは停止しない。
署名済みWebhookとinternal workerによる課金状態の収束も継続する。

通知送信の直前にも契約状態と利用上限状態を確認し、上限超過または評価不能の開始後に新しい業務通知の外部送信を始めない。

すでに外部サービスへの送信が始まった通知は、完全には取り消せない場合がある。

### 18.5 猶予中の支払い復旧

通常更新の猶予中に対象請求の支払い成功を確認した場合は、元の契約プランへ戻す。

TrialからProを選んだ初回請求の支払い成功では`active.pro`へ移行し、現在の実利用数からProの上限状態を導出する。

ProからStandardへの期間末変更後の支払い成功では`active.standard`へ移行し、現在の実利用数からStandardの上限状態を導出する。

支払い猶予への移行だけでは管理者権限と稼働店舗を停止しないため、支払い成功時にも権限と店舗状態を変更しない。

14日経過後にStripe側の契約が終了した場合は、自動復旧せず、新しい契約手続きを完了してから復旧する。

## 19. Freeからの有料契約

### 19.1 契約開始と再開

追加組織、未契約のTrial終了後、期間末の解約後、支払い猶予終了後、Stripe上の想定外解約後は、いずれも`active.free`からStandardまたはProを契約する。

契約終了によって管理者権限と稼働店舗を変更しないため、新しい契約で復元対象を選ばせない。
明示的に削除された人物、解除された管理者権限、アーカイブまたは削除された店舗を自動で復元しない。

### 19.2 契約後の上限

現在の実利用数が選択プランの上限を超えていても契約を開始できる。
支払い成功を確認した後は選択したプランのactive状態へ移行し、現在の実利用数から上限状態を導出する。

選択プランの上限を超える場合は、通常利用へ戻るために必要な削減数を契約確認画面と組織設定へ表示する。
上限内に戻るまでは17章の整理、課金、終了操作だけを許可する。

上限超過または利用上限評価不能によって停止した過去の業務通知は、再契約後に自動で再送しない。

## 20. Stripeの利用範囲

### 20.1 シフトリ側で行うこと

次の操作は、シフトリ側の画面と認可を通して行う。

- 契約開始
- StandardからProへの即時変更と日割り見積もり
- ProからStandardへの期間末変更予約
- 有料契約の期間末解約
- 期間末変更予約の取消
- 支払い復旧

### 20.2 Stripe Customer Portal

Stripe Customer Portalは、支払い方法の更新と請求書または領収書の確認に限定する。

Customer Portalでのプラン変更と契約取消は無効にする。

PortalのURLは、有効管理者であることを確認した後に、その都度発行する。

PortalのURLを恒久リンクとして保存または共有しない。

組織から削除された人物には、新しいPortal Sessionを発行しない。

発行済みのPortal Sessionは即時失効を保証できないため、Stripe側の短い有効期間を前提とする。

### 20.3 Stripe側の想定外変更

Stripe Dashboardなどから契約が直接変更または終了された場合も、Webhookで検知する。

シフトリ側で予定していないPriceや状態変更は、有料機能を追加で開放せず要対応として扱う。

Stripe上の想定外解約を確認した場合は`active.free`へ移行し、現在の実利用数からFreeの上限状態を導出する。
WebhookまたはStripe APIによる確認前に、ローカルの期限や推測だけで`active.free`へ移行しない。

管理者には、シフトリ上で変更内容の確認、上限整理、または再契約を完了するよう案内する。

## 21. 課金通知

### 21.1 基本ルール

契約、プラン、請求、支払いに関する外部通知は、LINE連携の有無にかかわらずメールで送る。

課金通知のためのLINE配送を作成しない。

複数の受信者へ送る場合は、メールアドレスを相互に見せないよう受信者ごとに個別送信する。

### 21.2 通知元と通知先

| 通知 | 送信元 | 通知先 |
|---|---|---|
| 管理者招待 | シフトリ | 招待先メールアドレス |
| 無料体験終了案内 | シフトリ | 全有効管理者 |
| 契約開始、プラン変更 | シフトリ | 全有効管理者 |
| 解約予約、取消、適用 | シフトリ | 解約直前までの全有効管理者 |
| deployment前の旧Free変更予約、取消、適用 | シフトリ | 変更直前までの全有効管理者 |
| 支払い失敗、期限前案内、Free移行、上限超過案内 | シフトリ | 各送信時点の全有効管理者 |
| 支払い復旧 | シフトリ | 各送信時点の全有効管理者 |
| 請求書、領収書、カード関連 | Stripe | 組織の請求先メールアドレス |

請求先メールアドレスは通知先であり、契約操作の権限を表さない。

人物のシフト連絡先と同じ値でも、その一致だけを人物・管理者・アカウント削除の拒否理由にしない。

請求先メールアドレスは、上限超過中を含む全有効管理者が変更できる。

組織から削除された人物は、すべての組織通知から除外する。

各課金メールの送信時点で有効管理者を抽出し、組織から削除された人物を除外する。

シフトリが有効管理者へ送るメールは、各組織人物の現在のシフト連絡先へ送る。

Clerkのログイン用メールアドレスと組織の請求先メールアドレスを、管理者向け業務通知の暗黙の代替先にはしない。

請求先メールアドレスを変更した場合は、現存する全有効管理者へメールで通知する。

### 21.3 支払い失敗時のメール

最初の支払い失敗を確認した直後に、全有効管理者へメールを送る。

猶予終了の3日前に、未払いであれば現存する全有効管理者へ再度メールを送る。

猶予終了後にStripe上の契約終了と`active.free`への移行を確定した時点で、現存する有効管理者へメールを送る。
Free上限を超える場合は、通常操作が制限される項目と整理またはプラン変更の導線を同じメールで案内する。

支払い成功時に、現存する全有効管理者へ復旧完了メールを送る。

Stripeの支払い失敗メールも有効にし、請求先メールアドレスへStripeの更新導線を送る。

シフトリのメールは組織内の全有効管理者への業務通知を担い、Stripeのメールは請求先への決済通知を担う。

### 21.4 契約状態変更時の業務通知

Trial終了、ProからStandardへの変更、解約、猶予終了、想定外解約、旧Free変更予約によるプラン移行だけを理由に、送信予定の業務通知を停止しない。

プラン移行後の実利用数が上限を超える場合、または上限評価が不能な場合は、適用時刻以降に送信予定だった業務通知を停止する。
課金通知、請求処理、署名済みWebhook、監査記録は停止しない。

外部送信の直前にも、組織の契約状態、利用上限状態、店舗状態、受信者の所属を確認する。

Freeで新しく行った操作から生じる業務通知は、Freeの利用範囲内で送信できる。

上限超過または評価不能によって停止した過去の業務通知は、上限内へ戻った後や再契約後に自動再送しない。

## 23. 業務上の不変条件

- 一つの組織に、複数の有効なStripe Subscriptionを作らない。
- 支払い不要Pro相当の組織にStripe Customer、Subscription、Checkout Session、Portal Session、Invoice、Subscription Schedule、課金operation、課金通知を作らない。
- 支払い不要Pro相当は既存の`complimentary.business`を`complimentary.pro`へ移行して維持するか、有効なコードの初回Setupでcanonicalな`complimentary.pro`を作成し、課金API、管理用処理、Stripeイベント、再同期処理で別の課金状態へ変更しない。
- 所属0件からの初回Setupでは、コード空欄なら2か月のTrialと期限処理、有効なコードなら期限処理のない`complimentary.pro`を一度だけ作成し、Stripe Customer、Subscription、課金operationを作らない。
- 追加組織作成、未契約のTrial終了、解約確定、猶予終了、想定外解約では`active.free`を保存する。
- ProからStandardへの変更確定では、Standard上限を超えていても`active.standard`を保存する。
- `pendingActivation`のFreeまたはStandardのfallbackは、providerの結果を確認した後に対応するactive状態へ必ず移行する。
- 上限超過と利用上限評価不能を課金状態として保存しない。
- 未承認の管理者招待を現在の実利用人数と有効管理者数へ含めない。
- StandardからProへ変更するときは、支払いとprovider状態を確認するまでStandardの権利を維持する。
- ProからStandardへ変更するときは、Stripe上の期間末変更を確認する前にローカル状態だけをStandardへ変更しない。
- 契約操作ごとに、対象組織の有効管理者であることを確認する。
- 複数組織に所属するユーザーの操作を、別組織の契約へ反映しない。
- 支払い完了画面だけを根拠に有料機能を開放しない。
- 組織から削除された人物へ、古い画面URL、招待、アプリ内セッションからアクセスさせない。
- 組織から削除された人物へ新しいPortal Sessionを発行しない。
- 最後の有効管理者を、引き継ぎなしで削除しない。
- 同じ契約操作の連続実行で、契約、請求、通知を重複させない。
- 上限超過または利用上限評価不能の開始後に、新しい業務通知の外部送信を開始しない。
- 実利用数が上限内へ戻ったときは、課金状態や上限フラグを更新せず通常利用へ戻す。
- Stripe上の変更を確認する必要がある遷移を、ローカルの期限だけで確定しない。
- 契約終了、論理的な所属削除、個人情報の完全消去を同じ状態として扱わない。

## 24. セキュリティと運用の前提

### 24.1 Security Lens

- Actor: 対象組織の有効管理者である。
- Asset: 組織の契約、支払い導線、管理権限、店舗、利用者、既存シフトである。
- Trust boundary: ログインアカウントから組織所属を確認する境界と、Stripe Webhookを検証する境界である。
- Abuse case: 他組織の契約変更、削除済み管理者の操作、招待の使い回し、Webhookの偽装、契約と通知の二重実行である。
- Server-side check: 対象組織、現在の管理権限、契約状態、利用上限を操作時に再確認する。
- Rate limit and idempotency: 招待、Checkout作成、Portal作成、契約変更、通知には回数制限、冪等性、重複排除を設ける。
- Lifecycle and recovery: 招待、Portal URL、契約変更予定、支払い猶予、削除後権限の有効期間と失効条件を持つ。
- Logs and PII: 生の招待値、カード情報、Webhook本文、完全なメールアドレスをログへ残さない。
- Regression test: 権限境界、組織分離、重複実行、順不同Webhook、期限切れ、削除競合を後続のテスト仕様で扱う。

### 24.2 Stripe Webhook

Stripe Webhookは、加工前のraw bodyと署名を使って検証した後だけ業務状態へ反映する。

同じイベントの再送を前提に、Stripe Event IDで重複処理を防ぐ。

別イベントとして届く同じ変更は、対象オブジェクトIDとイベント種別も使って重複を判定する。

イベントの到着順を前提にせず、必要に応じてStripe上の最新状態を確認する。

古いイベントによって、支払い済みや解約取消済みの状態を過去へ戻さない。

複雑な状態反映の前にWebhookへ正常応答し、後続処理を再開可能な非同期処理として進める。

Webhookの受信失敗、処理失敗、長時間未処理を運用上確認できるようにする。

### 24.3 監査

契約開始、プラン変更、解約予約、予約取消、deployment前の旧Free変更予約、管理者変更、組織からの削除を監査対象とする。

管理者招待の発行、再送、取消、承認、請求先メールアドレス変更、Portal Session発行を監査対象とする。

支払い失敗、猶予開始、Freeへの移行、支払い復旧、再契約を監査対象とする。

監査情報には、実行者、対象組織、操作、変更前後、発生時刻、安全な相関IDを記録する。

カード情報、招待の生値、完全なWebhook本文を監査情報へ保存しない。

## 25. Stripe実装上の制約

この章は業務ルールではなく、実装方式を決める際に守る外部制約を記録する。

### 25.1 無料体験終了日の指定

Stripe CheckoutのSubscriptionモードで指定する`subscription_data.trial_end`は、48時間以上先である必要がある。

無料体験終了まで48時間未満の時点で契約する場合は、CheckoutのSetupモードで将来の継続課金への同意を得て支払い方法を保存し、その後にSubscription APIで正確な終了時刻を指定する方式などを使う。

Setup完了時点で無料体験終了時刻を過ぎていた場合は、過去の`trial_end`を指定せず即時請求へ切り替える。

どの方式でも、2026年7月14日作成なら2026年9月14日午前0時JSTという業務上の終了時刻を変えない。

無料体験終了時刻は請求処理の開始時刻であり、実際のカード決済成功または失敗が同時刻に確定するとは限らない。

画面には初回請求日を2026年9月14日と表示するが、カード決済の厳密な時刻までは約束しない。

### 25.2 期間末の契約終了

Stripeは、支払い済み期間の終了時に契約を終了する設定と、終了前の取消をサポートしている。

有料契約の解約は、この期間末終了を利用する。
deployment前の旧Free変更予約も互換処理として同じ期間末終了を使う。

ProからStandardへの変更予約はStripe Subscription Scheduleを使い、期間末に同じSubscriptionのPriceを変更する。

請求周期はStripe Priceの`recurring.interval`と`recurring.interval_count`を正本とし、コード、環境変数、DBへ複製しない。

StandardとProは同じ通貨と請求周期を要求し、Subscription Scheduleの変更後phaseも対象Priceの請求周期から構築する。

請求周期の基準日は組織ごとのStripe Subscriptionが保持し、月初へ揃えない。

画面の次回更新日はStripeが返した期間終了日時を表示し、ローカルで次の請求日を計算しない。

### 25.3 支払い再試行

Stripe Smart Retriesは、2週間の再試行期間を設定できる。

Stripeの推奨初期値は2週間に8回である。

Stripeの再試行設定とは別に、シフトリ側で最初の失敗時刻と14日後の猶予終了時刻を保持する。

再試行期間終了後のStripe側の最終処理は、Subscriptionの取消とする。

取消後に復旧する場合は、新しいSubscriptionを作成する。

### 25.4 Customer Portal

Customer PortalのSessionは、有効管理者の認証後に作成する一時URLとして扱う。

Portal設定では、支払い方法更新と請求履歴を有効にし、契約取消とプラン変更を無効にする。

### 25.5 Stripe接続環境と環境変数

Stripeのtest環境とlive環境は`STRIPE_SECRET_KEY`の`sk_test_`または`sk_live_`接頭辞から自動判定する。

Localと開発用Convex deploymentは別々のStripe Sandboxへ接続し、本番deploymentは本番Stripeアカウントへ接続する。

Secret keyの接頭辞が不明な場合や、Price、Customer、Subscription、Invoiceの`livemode`が接続環境と一致しない場合は課金操作を拒否する。

新しいStandardまたはPro契約に使うCheckoutと無料体験の継続登録は、対象プランのPriceがactiveなrecurring Priceで、`interval_count`が正の整数である場合だけ開始する。

特定プランの新規販売を停止するときは、対象Priceをアーカイブする。
Priceのアーカイブ前に発行したopen状態のCheckout Sessionは別途失効させる。
Priceのアーカイブ前に作成されローカル同期済みのSubscriptionは既存契約として処理を継続する。未同期の作成結果はmetadataで一意な既存objectだけを回収して取り消し、Subscription作成自体は再送しない。

新規販売の停止中も、既存契約のCustomer Portal、解約、deployment前の旧Free変更予約、署名済みWebhook受信、再照合、Subscription取消、Invoice回収停止を継続する。

価格、税、請求周期、未払い請求の最終処理が確定するまでは対象Priceをアーカイブし、仮の価格やPrice IDを登録しない。

Stripe連携には、`STRIPE_SECRET_KEY`、`STRIPE_WEBHOOK_SECRET`、`STRIPE_STANDARD_PRICE_ID`、`STRIPE_PRO_PRICE_ID`、`STRIPE_PORTAL_CONFIGURATION_ID`、既存の`APP_URL`を使う。  StandardとProのPrice IDは明示設定を必須とし、欠損、不正、重複時は課金操作を開始しない。

Pro Priceだけが未設定または無効な場合は、Proの価格表示と変更操作だけを停止する。

その場合もStandardの契約開始、Customer Portal、既存SubscriptionのWebhook処理と再照合を継続する。

ブラウザでStripe.jsを直接使わないため、`VITE_STRIPE_PUBLISHABLE_KEY`は使わない。

秘密鍵、Webhook署名シークレット、Price ID、Portal Configuration IDの実値は、実装と検証の完了後に利用者が登録する。

テスト環境と本番環境の値を混在させない。

Secret keyとWebhook署名シークレットを新規販売の停止手段として削除しない。

既存契約がある環境では、署名済みWebhookの処理、状態照合、期間末終了、想定外終了の反映に必要な認証情報を維持する。

## 26. 業務受入条件

詳細なテストコードとテスト層は、実装計画時に別途定める。

本仕様の受入条件として、少なくとも次を確認する。

### 26.1 利用人数

- 管理者兼スタッフを一名として数える。
- 同じ人物が複数店舗に所属しても一名として数える。
- シフト対象外のスタッフを一名として数える。
- アーカイブ済み店舗にしか所属しないスタッフを一名として数える。
- スタッフではない元管理者を数えない。
- スタッフである元管理者を一名として数える。
- 店舗から削除しただけでは利用人数を減らさない。
- 組織から削除すると利用人数を減らす。
- Freeの五名に有効管理者を含める。
- 未承認の管理者招待を現在の実利用人数と有効管理者数へ含めず、招待中の人数として別に表示する。
- 招待発行と承認では、未承認招待が予約する利用人数枠と管理者枠を含めて上限を確認する。
- スタッフと管理者の追加時にメールアドレスを必須とする。
- 別組織の同じメールアドレスから、名前、所属、役割を取得しない。

### 26.2 プランと店舗

- Freeは5名、1店舗、2管理者まで利用できる。
- Trialは50名、5店舗、5管理者まで利用できる。
- Standardは25名、5店舗、5管理者まで利用できる。
- Proと支払い不要Pro相当は50名、5店舗、5管理者まで利用できる。
- Standardの26人目とProの51人目は追加しない。
- 稼働店舗の5店舗目までは利用できる。
- 6店舗目は追加せず、問い合わせへ誘導する。
- 人数が減っても自動でプランを変更しない。
- 支払い不要Pro相当のcanonicalな保存状態として`complimentary.pro`だけを作成し、Widen中だけ旧`complimentary.business`を読み取れる。
- 所属0件からの初回Setupはコード空欄なら2か月のTrial、有効なコードなら`complimentary.pro`で開始し、二つ目以降の追加組織は`active.free`で開始する。
- 自分で作成した有効な組織を三つまで保持でき、招待所属と削除済み組織はこの上限へ数えない。
- 二つ目以降の組織作成では、選択中組織にある操作本人の氏名とシフト連絡先だけを初期値として引き継ぐ。
- 所属していない店舗を引き継ぎ元に指定しても新しい組織を作成できず、同じ店舗にいる別人物の連絡先も引き継がない。
- 支払い不要Pro相当で50名、5店舗、5管理者、Proの機能を利用できる。
- 無料体験、Standard、Pro、支払い不要Pro相当で有効管理者と有効な追加招待を合わせて五名までに制限する。
- 六人目の管理者招待を発行時と承認時の両方で拒否する。
- Freeで有効管理者と有効な追加招待を合わせて2名までに制限し、3人目の発行と承認を拒否する。
- 取消、期限切れ、承認済みの招待を管理者上限へ含めない。
- 支払い不要Pro相当の設定画面で「Pro」、「支払い不要」の案内を確認でき、支払いとプラン変更の操作は表示されない。
- 支払い不要Pro相当にStripe Customer、Subscription、Checkout Session、Portal Session、Invoice、Subscription Schedule、課金operation、課金通知を作成しない。
- ProからStandardへの変更前に、Standard上限までの必要削減人数を表示する。
- 期間末にStandard上限を超えていても、Stripeのphase移行と支払い成功を確認した後は`active.standard`へ移行する。
- Standard上限超過中に人物削除などで上限内になった場合は、課金状態の更新なしで通常利用へ戻る。

### 26.3 無料体験、解約、Free移行

- 2026年7月14日作成の無料体験が2026年9月14日午前0時JSTに終了する。
- 無料体験中に契約しても、終了時刻まで初回請求しない。
- 無料体験終了前に継続予約を取り消すと初回請求せず、終了時に`active.free`へ移行する。
- 未契約のまま無料体験が終了すると`active.free`へ移行する。
- Trial終了によるFree移行では、管理者、店舗、人物、スタッフ所属、シフトを削除またはFree上限へ縮小しない。
- 有料プランの解約を期間末へ予約でき、期間末前なら予約を取り消せる。
- 解約予約は`restrictAtPeriodEnd: true`を持ち、Stripeで期間末終了を確認した後に`active.free`へ移行する。
- 解約によるFree移行では、データと直前の管理者・稼働店舗を変更しない。
- deployment前から保存済みのmarkerなしFree変更予約も、Stripeで期間末終了を確認した後に`active.free`へ移行する。
- 旧Free移行時に余剰管理者の組織人物、既存スタッフ所属、店舗、シフトを削除しない。
- Freeの通常の追加招待では現在の管理者を維持し、承認者を二人目の管理者にする。
- 既発行の旧`freeManagerExchange`招待は新規発行・再送せず、期限内tokenの承認と招待の取消だけを許可する。
  この招待が残る間は新しい追加招待を発行しない。
- 組織から削除済みの管理者を再契約で復元しない。

### 26.4 支払い

- 有効管理者なら誰でも契約操作を実行できる。
- 元管理者と削除済み管理者は契約操作を実行できない。
- 同じ契約操作を連続実行しても、Stripe契約とメールを重複させない。
- 支払い失敗から14日以内に成功した場合は、業務機能を停止しない。
- 14日経過後は元のSubscriptionを終了し、Stripe上の終了を確認してから`active.free`へ移行する。
- 猶予終了時刻だけでは`active.free`へ移行しない。
- `active.free`への移行後はFree上限状態を実利用数から導出し、上限内ならFreeの通常機能を利用できる。
- 14日経過後に有料プランへ戻るには新しい契約を要求する。
- 旧未払い請求と新しい契約の請求を重複回収しない。
- 支払い成功画面だけでは有料機能を開放しない。
- 重複または順不同のWebhookで、契約状態を過去へ戻さない。
- `STRIPE_SECRET_KEY`から接続環境を自動判定し、testとliveのStripeオブジェクトを混在させない。
- StandardまたはProの対象Priceが利用できない場合は、そのプランの新しい契約操作だけを開始できない。
- FreeからStandardまたはProを開始した日を、組織ごとの請求周期の基準にできる。
- StandardからProへの変更では、同じ時刻を基準にしたStripeの日割り見積もりを表示し、支払い確認後にProを開放する。
- ProからStandardへの変更では、Stripe Subscription Scheduleによる期間末変更を確認してからStandardを開放する。
- 次回更新日はStripeの期間終了日時を表示する。
- 新規販売の停止中も既存契約の署名済みWebhookと安全処理を継続できる。

### 26.5 通知

- 課金通知ではLINE配送を一件も作成しない。
- シフトリの課金メール宛先を、対象組織の有効管理者だけに限定する。
- 組織から削除された人物へ課金メールを送らない。
- 上限超過中の有効管理者が請求先メールアドレスを変更できる。
- 上限超過または利用上限評価不能の開始後は、未送信の業務通知を停止する。
- 無料体験から初回請求処理中または有料プランへ進む場合は、業務通知を停止しない。
- FreeまたはStandardへの移行後も上限内なら、業務通知をプランの利用範囲内で継続する。
- 上限超過によって停止した業務通知を、上限内へ戻った後や再契約後に自動再送しない。
- スタッフ参加申請digest、シフト確定催促、店舗登録後の本番募集案内、通知不達digestを、対象店舗にスタッフとして所属するactive管理者だけへ送る。
- 店舗管理通知の対象者が0人の場合は送信せず、店舗詳細に管理者を店舗所属に置く推奨案内を表示する。
- 店舗管理通知はLINE連携中ならLINEを優先し、それ以外は現在のシフト連絡先へメールで送る。
  送信直前にも管理者権限、店舗所属、宛先を再確認する。

### 26.6 招待と権限

- 未接続人物への管理者招待を招待先と異なる確認済みメールアドレスで承認できず、期限切れ、使用済み、取消済み、再送前の古いURLも承認できない。
- 接続済みの組織人物への招待を、その人物と異なるログインアカウントで承認できない。
- 未接続の組織人物への招待を、Clerkで確認済みの招待先メールアドレスを持たないアカウントで承認できない。
- Clerkの設定不足、一時障害、照会失敗では招待を消費せず、復旧後に再試行できる。
- 管理者設定で既存スタッフを一名だけ選び、対象スタッフの現在のメールアドレスへ管理者招待を送れる。
- 選択した対象人物と異なる人物や、招待後に変更された古いメールアドレスでは承認できない。
- 招待承認時にも、契約状態、利用人数上限、管理者上限を確認する。
- 上限超過または利用上限評価不能の間は招待の発行、再送、承認を拒否し、取消を許可する。
- Freeでも、管理者上限2名と利用人数上限の範囲で、既存スタッフまたは新しい人物を通常の追加管理者として招待できる。
- activeな管理者人物も個別店舗または全店舗のスタッフ所属を解除でき、管理者権限と組織人物を維持する。
- activeな管理者人物を組織から削除する操作は、先に管理者権限を外すまで拒否する。
- Freeで有効管理者を2名から1名にする権限解除は許可し、1名から0名にする解除は拒否する。
- 未登録者が登録後に同じ管理者招待へ戻って承認できる。
- 組織から削除された管理者が発行した未承認招待を利用できない。
- 同じメールアドレスへの並行招待で、招待と予約枠を重複させない。
- 最後の有効管理者を、引き継ぎなしで削除できない。
- 組織から削除した人物の既存セッション、権限リンク、未送信通知を利用できない。
- 今日以降の割当件数を確認画面に表示し、確認後に割当と人物を同じ処理で削除できる。
- 過去のシフト割当は削除せず、削除済み人物として参照できる。
- 組織から削除した人物へ新しいPortal Sessionを発行できない。
- 複数組織に所属する管理者の操作を、別組織へ反映しない。

### 26.7 上限超過

- Trial未契約終了、解約確定、猶予終了、Stripe上の想定外解約で、上限超過の有無にかかわらず`active.free`を保存する。
- ProからStandardへの変更確定で、上限超過の有無にかかわらず`active.standard`を保存する。
- `pendingActivation`のFreeまたはStandardのfallbackを、Stripe上の結果確認後に対応するactive状態へ必ず移行する。
- 上限超過と利用上限評価不能をDBへ保存せず、現在プランと実利用数から導出する。
- 上限超過または利用上限評価不能では、既存データの閲覧、人物削除、管理者権限解除、店舗のアーカイブと削除、招待取消、課金と請求先変更、組織とアカウントの終了に必要な操作だけを許可する。
- 上限超過または利用上限評価不能では、通常業務、スタッフの希望シフト提出、業務メール、LINE、provider連携を含む外部通知を停止する。
- 実利用数が上限内へ戻ると、課金状態または上限フラグの更新なしで通常利用へ戻る。
- 利用上限評価不能を上限超過と断定せず、管理画面での確認・整理と問い合わせを案内する。
- Stripe上の結果確認が必要な遷移を、ローカルの期限だけで確定しない。

## 27. 本仕様で決めないこと

次の項目は、別の仕様または実装計画で決める。

- StandardとProの実価格
- 税、インボイス制度、返金、クレジット、未払い請求の最終処理に関する法務と会計ルール
- 年間契約と年払い
- 51名以上または6店舗以上の個別契約
- カード以外の支払い方法
- 個人情報の完全消去と法定保持期間
- 組織全体の閉鎖とデータ消去手続き
- 詳細な自動テストケースとテストデータ
- Stripe販売停止と再開に伴うDashboard上の詳細な操作手順

## 28. 実装への対応

現在の実装境界は、[組織課金、複数店舗、複数管理者](../features/organization-billing.md)と、そこから参照する現行コードを正とする。

`doc/plans/`は意思決定と実装順序の履歴であり、現在仕様や実環境の公開状態の正本にはしない。

Business再導入、上限変更、人物削除、Stripeプラン変更、migration、テストの実装順序は、[`doc/plans/2026-07-21_課金プラン改定_Business再導入_実装計画.md`](../plans/2026-07-21_課金プラン改定_Business再導入_実装計画.md)に履歴として残す。

[`doc/plans/2026-07-20_Stripe課金連携_実装計画.md`](../plans/2026-07-20_Stripe課金連携_実装計画.md)は、Businessを廃止してProへ統合した時点の履歴計画として参照する。

店舗単位課金とBillingManagerを前提にした旧資料は、移行履歴または互換性確認のためだけに参照する。

現行の契約境界は組織単位とし、全有効管理者へ契約権限を与える。

管理者招待の新しい画面はNode actionによる承認を標準経路とし、旧`linkAccount`と`accept` mutationはrolling deploy中の互換入口としてだけ残す。

Clerk操作と実deploymentでの公開状態は、この仕様やローカルテストから完了と推測せず、環境ごとの検証証跡で確認する。

本書の受入条件は、実装時にLogic Test、Convex Function Test、Convex Scenario Test、UI Testへ分担する。

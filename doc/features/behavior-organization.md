# 条件別仕様: 組織・店舗・管理者・アカウント

> 文書種別: behavior（条件→結果の詳細仕様。機能文書・業務仕様・コードから導出）
>
> 作成日: 2026-08-16 ／ 基準commit: `37c908f`
>
> 正本: [組織課金、複数店舗、複数管理者](organization-billing.md)、[業務仕様](../specs/organization-billing-business-flow.md)、[店舗設定](shop-settings.md)、[店舗・組織削除](data-deletion.md)、[アカウント削除](account-deletion.md)、[認証画面とアカウント設定](auth-pages.md)

組織・店舗・管理者・ログインアカウントの操作について、条件の組み合わせごとの結果を定める。  
複数組織・複数店舗・管理者招待・課金は通常の画面とAPIから利用できる。  以下の契約は、認証、組織境界、管理者状態、契約状態、上限、token lifecycleをserver-sideで再確認する。

## 1. 組織の作成

| 条件 | 結果 |
|---|---|
| 組織所属0件の認証済み利用者が`/dashboard`の初回Setupを実行 | 最初の組織・店舗・人物・管理者本人・店舗スタッフを一度に作成。課金状態は**Pro相当・利用人数上限50名の3か月Trial**。Trial期限・課金deadlineを作り、Stripeオブジェクトは作らない |
| 所属がある利用者が初回Setupを試行 | server-sideで拒否（初回Setupは所属0件のみ） |
| 追加組織作成 | **`active.free`**（5名・1店舗・2管理者）で開始 |
| 自作組織を既に3つ保持 | 拒否（招待による所属と削除済み組織は数えない。削除すれば再作成可） |
| 1日の作成回数が10回に到達 | 拒否（rate limit） |
| 同じ`requestId`での再実行 | 冪等（組織を重複作成しない） |
| 追加組織作成時、所属していない店舗を`sourceShopId`に指定 | 拒否。同じ店舗の別人物の連絡先も引き継がない |

- 初回Setupで入力した氏名・シフト連絡先は、最初の人物・店舗スタッフ・組織の初期請求先へsnapshotする。以後は独立して管理し、自動同期しない。
- 追加組織へは操作本人の氏名とシフト連絡先**だけ**を引き継ぐ。既存組織の別人物・スタッフ所属・店舗・シフトは複製しない。
- 組織名の初期値は「＜最初の店舗名＞グループ」。80文字まで、後から自由に変更できる（「グループ」の削除も可）。

## 2. 組織名の変更・組織削除

| 操作 | 条件 | 結果 |
|---|---|---|
| 組織名変更 | 有効管理者。通常利用中、または旧`restricted`互換の契約復旧中。上限超過・利用数評価不能では不可 | 変更（80文字まで） |
| 組織削除 | 下表の全条件 | 論理削除＋全店舗の永続cleanup開始 |

組織削除が**拒否**される条件（1つでも該当すれば拒否）:

| # | 条件 |
|---|---|
| 1 | 操作者が組織で唯一の`active`管理者ではない（`readOnly`を含む他の管理者がいる場合は先に整理） |
| 2 | 課金状態が許可外。許可は「有料プラン未選択のTrial」「Free」「支払い不要Pro相当」のみ |
| 3 | Trialでも、Stripe Subscription・進行中のTrial作成operation・終了証跡のない過去のoperationが残っている |
| 4 | 未完了の店舗削除jobがある |

組織削除の効果は[店舗・組織削除](data-deletion.md)の表を正本とする。要点:

- 全店舗・全staff・組織人物・管理者所属を論理削除し、session・token・登録リンク・LINE連携（その組織分）・未送信通知を失効・停止する。
- **`users`（ログインアカウント）は変更しない**。最後の有効組織を削除した利用者は同じ認証のまま店舗登録画面へ戻り、新しい組織を作成できる。
- 氏名・メール・店舗名・組織名・請求先は業務履歴の識別のためDBに保持する（個人情報の完全消去ではない）。

## 3. 店舗の設定・追加・アーカイブ・削除

### 3.1 店舗設定の変更

- 店舗名（80文字）、希望シフトの提出方法（時間指定／日ごと／勤務区分）、定休日を1回のmutationで一括更新する。
- 勤務区分は最大4件。保存時に開始時間昇順（同時刻は終了時間昇順）へ整列する。
- **提出方法を変更しても既存募集には影響しない**。募集は作成時点の提出方法をsnapshotしている。
- 閲覧専用（`readOnly`）、上限超過・利用数評価不能、旧`restricted`互換の契約復旧中は編集導線が無効になり、mutationも拒否する。

### 3.2 店舗の追加・再稼働

| 条件 | 結果 |
|---|---|
| 稼働店舗が5店舗未満 | 追加できる |
| 6店舗目の追加 | **確定前に停止**し問い合わせへ誘導 |
| アーカイブ済み・プラン停止中の店舗 | 稼働店舗数に数えない |
| アーカイブ済み店舗の再稼働 | 店舗上限を**再確認**してから稼働へ戻す |

### 3.3 店舗のアーカイブ

- 店舗データと過去シフトは削除しない。
- アーカイブ済み店舗にしか所属していない人物も、組織から削除されるまで利用人数に含める。
- 上限超過中の有効管理者と、旧`restricted`互換の復旧担当者も実行できる（復旧のための整理操作）。

### 3.4 店舗削除

| 条件 | 結果 |
|---|---|
| 有効管理者が、最後ではない未削除店舗を削除 | 論理削除＋cleanup job開始 |
| **最後の未削除店舗**を削除 | 拒否 |
| clientの確認ID・更新時刻がサーバー最新と不一致 | 拒否（最新状態と照合） |

効果: 対象店舗のstaff・店舗LINE投影を論理削除、店舗用session・magic link・LINE連携token・法務同意token・登録リンクを失効、未送信通知を停止。  
`users`・`organizationPeople`・`organizationMembers`は変更せず、対象店舗のユーザーは組織人物として残る。  
削除成功後は、削除対象と異なる現在の店舗、なければ同組織の先頭の未削除店舗へ復帰する。

## 4. 管理者の追加（招待）・権限解除

### 4.1 招待の発行

| # | 条件 | 結果 |
|---|---|---|
| 1 | 有効管理者が、既存スタッフ1名を選択 or 新規の氏名＋メールを入力 | 招待メールを送付（**LINEでは送らない**）。tokenは7日有効・一回限り |
| 2 | 管理者上限超過（有効管理者＋期限内の未承認招待の合計が、通常5名／Free 2名を超える） | **発行時に拒否** |
| 3 | 新規人物の招待で利用人数に空きがない | 拒否（承認時の超過を防ぐため**1人分の枠を発行時に予約**。取消・期限切れで解放） |
| 4 | 既存スタッフの招待 | 利用人数の枠は追加予約しない（管理者数のみ+1見込み） |
| 5 | 同じ組織×同じ正規化メールに期限内の有効招待が既にある | 新規発行を拒否（**暗黙の再送にしない**。招待中一覧から明示的に再送する） |
| 6 | 同じメールへの並行発行 | 招待と予約枠を1つだけ作る |
| 7 | 旧`freeManagerExchange`招待が期限内に残っている（旧Free互換） | 新しい追加招待を発行しない |
| 8 | 再送 | 旧招待を失効させtokenをローテーション（**古いURLは使えなくなる**） |
| 9 | 同じメールの通常削除人物がいる | 既存人物を招待対象に固定する。承認までは人物・管理者所属を有効化しない |
| 10 | 同じメールのアカウント削除済み人物だけがいる | 旧人物を招待対象にせず、新規人物向けの招待として発行する |

- 初回招待は、既存スタッフの選択または新規人物の氏名・メールアドレス入力後、確認画面を挟まず送信する。
- 確認ダイアログは、招待の再送・取消と管理者権限の解除にだけ表示する。
- 招待URLにはメール・組織ID・役割を含めず、ランダム値だけを含める。
- 外部人物とアカウント削除後の再登録者の招待では、発行時点で人物・所属を作らない（承認transactionで初めて作る）。
- 招待発行者が組織から削除された場合、その発行済み未承認招待は無効になる。

### 4.2 招待の承認（受諾）

| # | 状況 | 承認できる条件 |
|---|---|---|
| 1 | 招待対象の組織人物がログインアカウントへ**接続済み** | **同じアカウントでログインした本人のみ**（メール照合は本人性の代わりにしない） |
| 2 | 未接続の人物、または人物がまだ存在しない | Clerkが**確認済み**として返すメールアドレスのいずれかが招待先メールと完全一致（primaryのみの値や未確認メールは根拠にしない） |
| 3 | 未登録の受信者 | アカウント登録後に同じ招待へ戻って承認できる |
| 4 | Clerkの設定不足・一時障害・照会失敗 | 承認を完了せず、**招待を未使用のまま**再試行可能な結果を返す |
| 5 | 期限切れ／使用済み／取消済み／再送前の古いURL | 承認不可 |
| 6 | 既存スタッフ招待で、招待後に対象スタッフのメールが変わった | 古い招待は承認不可。新しいメールへ再招待する |
| 7 | 承認時点で契約状態・利用人数上限・管理者上限に違反 | 承認拒否（発行時と承認時の**両方**で確認） |
| 8 | 通常削除人物を対象に固定した招待 | 同じ人物と削除済み管理者所属を再利用し、今回の招待で管理者権限だけを明示的に付与する |
| 9 | 同じメールのアカウント削除履歴だけがある対象未固定招待 | 新しいuser・人物・管理者所属を作り、旧user・人物・所属へ関連付けない |
| 10 | 対象固定後にその人物のアカウントが削除された | 別人物へ付け替えず承認不可。新しい招待を発行する |

- 承認完了で受信者は**組織全体の**有効管理者になる（全店舗を管理でき、契約操作も可能）。
- 通常削除人物を再利用しても、削除時に終了したstaff、シフト、LINE連携、旧招待、Free管理者・復旧担当者などの課金参照は復元しない。今回の招待が管理者所属だけを有効化する。
- アカウント削除後の再登録では、同じメールの旧人物を履歴として残す。旧IDを新しい認証主体の認可、利用人数、通知先、課金権限の根拠にしない。
- 承認完了は本人と他の全有効管理者へメールで通知する。
- 承認前に同じ人物がスタッフとして追加された場合は、予約枠を実際の人物へ付け替えて二重に数えない。
- Trial終了、有料契約の終了、支払い猶予終了によってFreeへ移行するときは、未承認の管理者追加招待を無効化する。
- 利用実数の増加だけで上限超過になった場合と、ProからStandardへ変更した場合は、未承認招待を自動で無効化しない。
  上限超過中も招待取消は許可し、利用者が整理できるようにする。

### 4.3 管理者権限の解除

| 条件 | 結果 |
|---|---|
| 2名以上の有効管理者がいる組織で1名の権限を解除 | 可。人物・シフト記録・スタッフ所属は維持 |
| **最後のactive管理者（1名→0名）** | **拒否** |
| Freeで2名→1名 | 可 |
| 解除された人物（元管理者）の以後 | 管理画面のデータ（組織設定・Dashboard・シフト・過去データ・スタッフ情報）を閲覧できない。スタッフ所属があればスタッフ向け機能（提出・通知）は継続 |
| 解除後の自動復元 | しない（契約終了や再契約でも復元しない） |
| 解除後に組織からも削除したい | 権限解除→人物削除の**2段階**（管理者のままの人物削除はserver guardで拒否） |

自分自身の権限を解除した場合は、失効した店舗をURLに残さずダッシュボードへ戻る。

## 5. アカウント（ログイン方法）の変更

ログイン方法はClerkが正本で、シフト連絡先・請求先とは独立している。3状態と可能な操作:

| 状態 | できる操作 |
|---|---|
| Googleのみ | メールアドレス＋パスワードの設定 |
| メール・パスワードのみ | メインのメールアドレス変更、パスワード変更、Google認証の追加 |
| 両方 | メールアドレス変更、パスワード変更、Google認証の解除 |

### 5.1 条件別の挙動

| # | 操作 | 条件 | 結果 |
|---|---|---|---|
| 1 | メインのメールアドレス変更 | 変更先が未確認 | `email_code`（6桁コード）で所有確認後にPrimaryへ切替 |
| 2 | 同上 | 旧Primaryが`oauth_google`にlink | 旧PrimaryをGoogleログイン維持のため**secondaryとして保持**（削除しない） |
| 3 | 同上 | 旧Primaryがgoogle-linkでない | 旧Primaryを削除。削除失敗時は可能な限り旧Primaryへ戻して再試行を案内 |
| 4 | パスワード変更 | 現在のパスワードをserver検証 | 変更成功で**他端末をログアウト**（現在の端末は維持） |
| 5 | パスワード初回設定（Googleのみ） | メール確認→パスワード設定 | 他端末はログアウトしない |
| 6 | Google認証の追加 | 選んだGoogleが**別のClerk Userに接続済み** | 自動統合せずエラー（既存のメール・パスワードは維持） |
| 7 | Google認証の解除 | 有効なパスワード＋確認済みPrimaryが残る | 解除できる |
| 8 | 同上 | **Googleのみの状態** | 解除不可。「先にメールアドレス・パスワードを設定」と赤いSnackbarで通知 |
| 9 | 応答喪失（通信断） | メール・Google系 | reloadして確定状態を確認し、完了条件を満たせば成功へ収束。EmailAddressを重複作成しない |
| 10 | 応答喪失 | パスワード変更 | 反映済みの可能性があるため**自動再試行しない**。成功も表示しない |
| 11 | 別端末・新しい端末相当でのパスワードログイン | Clerkが追加確認を要求 | メール確認コードによる本人確認。信頼済み端末の判定はClerkが正本（Cookie削除・シークレットモード等で再要求） |

- どのログイン方法変更も、**シフト連絡先・請求先メールアドレス・`users.email`を変更しない**（逆も同様）。Clerk・`users`・組織のメールが異なる状態は正常。
- 任意のEmailAddressを選んで削除する操作と、パスワードの削除は提供しない。
- LINEアプリ内ブラウザではGoogle OAuthを外部ブラウザで開き直す。メール・パスワード認証はLINE内でも利用可能。

## 6. アカウント削除

strict再認証（Clerk）を経て受け付ける。**受付＝完了ではない**（cleanup完了後にClerkユーザーを削除する）。

| # | 本人の有効な組織所属 | 管理者構成 | 結果 |
|---|---|---|---|
| 1 | なし | - | ローカル利用を停止し、Clerkユーザー削除へ進む |
| 2 | 1つ | 本人**以外**に有効な`active`管理者がいる | 本人のmanager・person・staff・session・token・LINE連携・未送信通知を終了し、今日以降の割当を削除。**組織・店舗・他の管理者・過去のシフト履歴は維持**。本人staffの通知履歴が消えたことを確認してからClerk削除 |
| 3 | 1つ | 本人が唯一の有効な`active`管理者 | **組織を論理削除**して全店舗cleanupを開始。cleanup完了を確認してからClerk削除 |
| 4 | **2つ以上**、または所属不整合 | - | **受付しない**。所属を1つ以下へ整理するか問い合わせを案内 |

追加の拒否条件:

- `readOnly`管理者は引き継ぎ先とみなさない（#3の判定で「他の管理者」に数えない）。
- 共有組織から退出する本人が**請求先メールアドレスの登録者**または**最後の復旧担当者**の場合、先に別の管理者へ移すまで受付しない。
- previewと受付の間に組織・管理者・店舗・課金状態・将来割当が変化した場合、stale fingerprintとして拒否する。
- Clerkの代理操作session（`actor`/`act` claim）は本人同意として扱わずfail-closedで拒否する。

削除後: `getCurrentUser`は`accountDeleted`のbooleanだけを返し、保持している氏名・メールを画面へ返さない。再登録した新しいClerkユーザーを過去の履歴へ自動関連付けしない。

## 7. 課金・契約の状態遷移

上限は[認可・制限](behavior-authorization.md)のプラン表、通知は[通知マトリクス](behavior-notification.md)を参照。ここでは遷移と操作条件だけを定める。

### 7.1 状態遷移表（業務仕様22章の要約）

| 現在 | イベント | 次の状態 |
|---|---|---|
| 組織未作成 | 所属0件の初回Setup | Trial |
| 組織所属あり | 追加組織作成（公開時） | Free |
| Trial | 継続予約して終了 | 初回請求処理中（Standard相当を継続） |
| 初回請求処理中 | 支払い成功／失敗 | 選択プラン／支払い猶予（14日） |
| Trial | 未契約または継続予約取消のまま終了 | Free。上限適合状態は移行後の利用実数から導出 |
| Standard | Pro即時変更を開始 | 支払い結果待ち（確定までStandard維持） |
| Pro | Standard変更予約 | 期間末変更予定（期間末までPro） |
| Standard／Pro | 解約予約 | 解約予定（`restrictAtPeriodEnd: true`。期間末まで現行プラン） |
| 変更・解約予定 | 予約取消（provider確認後） | 元のプラン |
| 期間末変更予定 | StripeでProからStandardへのphase移行を確認 | Standard。上限内なら通常利用、上限超過・評価不能なら整理操作のみ |
| 解約予定 | Stripeで期間末終了を確認 | Free。上限適合状態は移行後の利用実数から導出 |
| Standard／Pro | 更新支払い失敗 | 支払い猶予（14日、全機能継続） |
| 支払い猶予 | 支払い成功 | 元のプランまたは予約済み変更先。移行後の上限適合状態を再評価 |
| 支払い猶予 | 14日経過し、未払い確認・Subscription終了・invoice回収停止がすべて成功 | Free。上限適合状態は移行後の利用実数から導出 |
| Standard／Pro | Stripeで予約外のSubscription終了を確認 | Free。上限適合状態は移行後の利用実数から導出 |
| active Free／Standard／Pro | 利用者・稼働店舗・有効管理者がプラン上限を超える | 課金状態は変えない。上限超過を導出し、整理・課金・終了に必要な操作だけを許可 |
| active Free／Standard／Pro | 整理によって全項目が上限内へ戻る | 課金状態は変えない。通常利用へ自動復帰 |

### 7.2 主要ルール

- Trial期間は開始から3か月。終了は該当日の0:00 JST（同日がない月は末日へ丸め）。
- 支払い猶予は**最初の失敗時点から14日後の同時刻**で固定（Stripeの再試行回数で延長しない）。猶予中は失敗前プランの全機能を利用できる。
- 14日経過後は未払いを再確認し、旧Subscriptionの終了とinvoice回収停止が完了してからFreeへ移す。
  復旧には**新しい契約**を要求し、旧請求の遅延成功だけでは自動復旧しない。
- Trial・有料契約・支払い猶予の終了と下位プランへの変更では、店舗・利用者・管理者・シフトを自動削除または自動降格しない。
- 上限超過と利用数評価不能は課金状態へ保存せず、現在プランと現在利用数から都度導出する。
  人物削除、管理者権限解除、招待取消、店舗アーカイブなどで上限内へ戻れば、schedulerや状態更新なしで通常利用へ戻る。
- Productionには旧`restricted`の保存データが存在しないため、この変更ではデータMigrationを実行しない。
  rolling deploy中の旧shapeを新規作成しないまま、schema・validator・readerの互換だけを当面維持する。
- 支払い成功画面・復帰URLだけでは有料機能を開放しない（署名済みWebhookまたはprovider再取得が正本）。重複・順不同のWebhookで状態を過去へ戻さない。
- Customer Portalは支払い方法更新と請求書確認に限定し、Portalでのプラン変更・契約取消は無効。URLは都度発行の一時URL。
- 支払い不要Pro相当には、Stripeオブジェクト・課金操作・課金通知を一切作らず、どの処理からも別の課金状態へ変更しない。
- 上限整理専用と旧`restricted`互換の契約復旧中に許可される操作は、[認可・制限](behavior-authorization.md)の表を正本とする。

### 7.3 利用アクセス×操作の可否（○×早見表）

○＝可、△＝個別の契約状態または対象条件を満たす場合だけ可、×＝不可とする。
`pendingActivation`のFree/Pro fallbackと`grace`は、現在権利の上限内なら`normal`として業務利用を継続する。

| 操作 | `normal` | `limitRecoveryOnly`（上限超過・評価不能） | `billingRecoveryOnly`（旧`restricted`互換） |
|---|:-:|:-:|:-:|
| 既存データの閲覧 | ○ | ○ | ○（`readOnly`含む） |
| 募集・シフト・スタッフ提出などの業務書き込み | ○ | × | × |
| 組織名の変更 | ○ | × | △（有効管理者のみ） |
| 新規の業務通知（メール・LINE） | ○ | × | × |
| 有料プランの開始・上位プランへの変更 | △ | ○ | ○ |
| 支払い方法・請求先の変更 | △ | ○ | ○ |
| 人物削除・管理者権限解除・招待取消・店舗アーカイブ | △ | ○（上限整理に必要な操作） | △（既存の復旧capabilityだけ） |
| 組織・アカウントの終了に必要な整理 | △ | ○ | ○ |
| 店舗追加・スタッフ追加・管理者招待・再有効化 | △（変更後見込みが上限内） | × | × |

## 8. テスト観点への変換メモ

- 4.1・4.2の各行は「発行時拒否」と「承認時拒否」を**別ケース**として起こす（両方で検証する契約のため）。
- 5章は3状態×各操作の直積に、#9〜#11の異常系（応答喪失・別User接続済み・新端末）を加える。
- 6章は4分岐＋追加拒否3条件＋stale fingerprintで最低8ケース。
- 7章の遷移表は状態遷移テストとしてN+スイッチカバレッジを検討する。
  特に「Trial・解約・猶予終了→Free」「Pro→Standard」「猶予→成功→元または変更先プラン」と、各遷移後の上限内・上限超過・評価不能を分ける。

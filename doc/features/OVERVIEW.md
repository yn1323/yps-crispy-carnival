## 1. システムで解決できること

シフトリは、店舗スタッフのシフト管理SaaSである。  
シフト担当者とスタッフの間で毎回発生する次の作業を、Webとメール・LINE通知で置き換える。

| 課題 | シフトリでの解決 |
|---|---|
| 希望シフトの回収が紙・口頭・個別連絡でばらつく | 募集を作成すると全対象スタッフへ提出リンクをメール・LINEで自動送付し、締切前日に未提出者へ自動催促する |
| 誰が提出済みか分からない | Dashboardとシフト表で提出人数・提出内容をリアルタイムに確認できる |
| シフト表の作成と調整に時間がかかる | 希望と割当を同じ画面で比較しながら編集し、違反（店舗境界・休業日など）を保存前に検出する |
| 確定シフトの周知漏れ | 確定時に変更のあったスタッフへだけ確定通知と閲覧リンクを自動送付する |
| 確定の放置 | 締切翌日に管理者へ確定催促を自動送付し、要対応一覧にも表示する |
| スタッフの連絡先収集の手間 | 店舗専用QR/URLからスタッフ本人が参加申請し、管理者承認で登録が完了する |
| 通知が届かない事故に気づけない | 不達通知をDashboardの要対応に集約し、再通知・日次リマインダーを提供する |

スタッフはアカウント登録不要で、メール・LINEに届くリンク（magic link）だけで提出・閲覧できる。

## 2. 現在の公開範囲

repository artifactでは、複数組織、複数店舗、複数管理者（招待）、Stripe課金を常時利用できる。
初回登録で作る組織は`complimentary.business`（期限・料金なしでBusiness相当、利用人数40名まで）になり、カード登録やTrial期限は発生しない。  追加組織はFreeで開始する。

機能ごとの公開環境変数は使わない。  画面は組織作成、店舗追加、管理者、プランと支払いの導線を常時表示し、操作可否は認証・認可、所属状態、契約状態、プラン上限、Stripe設定などのサーバー判定に従う。  実deploymentへのartifact反映とcanaryは[リリース状態](../manual/release-status.md)の証跡で確認する。

なお、業務仕様（`doc/specs/organization-billing-business-flow.md`）に有料機能として挙がる「AIシフトたたき台作成」は、現時点でコード実装がない（仕様先行）。

## 4. 制限一覧

### 4.1 プランと利用上限

| プラン・状態 | 利用人数 | 稼働店舗 | 有効管理者 | 備考 |
|---|---:|---:|---:|---|
| 支払い不要Business（現行の初回登録） | 40名 | 5店舗 | 5名 | 期限・料金・Stripeオブジェクトなし |
| 無料体験（Trial、既存組織のみ） | 20名 | 5店舗 | 5名 | Pro相当。期間は開始から2ヶ月（終了は該当日0:00 JST） |
| Free（追加組織） | 5名 | 1店舗 | 2名 | 二つ目以降の組織はこの状態で開始する |
| Pro | 20名 | 5店舗 | 5名 | Stripe契約あり |
| Business | 40名 | 5店舗 | 5名 | Stripe契約あり |

- 利用人数は組織内の人物単位で重複なく数える。管理者兼スタッフ・複数店舗所属・シフト対象外・アーカイブ店舗のみ所属も1名。元管理者はスタッフでもある場合のみ1名。未承認招待は数えない。
- 上限を超える追加操作（21人目・41人目・6店舗目・6人目の管理者）は確定前に止め、問い合わせへ誘導する。一部だけの保存はしない。
- 人数が減っても自動でプランを下げない。
- 自分で作成して保持できる組織は3つまで、組織作成は1日10回まで（招待所属・削除済みは数えない）。

### 4.2 シフト運用の業務ルール

| 項目 | 制限・仕様 |
|---|---|
| 募集期間 | 最大31日（`RECRUITMENT_PERIOD_DAYS_MAX`） |
| 提出締切 | 募集作成時に設定し、後から編集できない（募集は作成・削除のみ） |
| 希望提出・再提出 | 提出締切日23:59 JSTまで |
| 締切後の提出 | 提出済みスタッフは閲覧のみ。未提出スタッフだけ確認ダイアログ後に初回提出できる |
| 提出リンクが開ける期間 | 募集が`open`かつシフト開始日0:00 JSTより前まで |
| シフト表の保存・確定・再通知 | シフト終了日を過ぎた募集は受け付けない（画面とmutation双方で確認） |
| 過去の扱い | シフト終了日当日は過去に含めず、翌日から過去として扱う |
| 確定済み募集の削除 | 可能（削除前に確認） |
| 提出方法 | 店舗設定で時間指定・日ごと・勤務区分から選択。募集は作成時点の設定をsnapshotし、店舗設定を後から変えても既存募集は変わらない |
| 勤務区分 | 最大4件 |
| シフト表の時間単位 | 30分 |
| 1回の提出の希望件数 | 最大31件 |
| シフト表のスタッフ・割当規模 | スタッフ200名、希望・割当各2000件が読み書きの上限 |
| スタッフ手入力追加 | 1回最大50名 |
| 承認待ち参加申請 | 1店舗最大20件（超過分は受け付けるが保存しない） |
| 人物削除時の将来割当 | 1回のtransactionで500件まで。超過時は先にシフト整理を求める |
| 名前・入力長 | 店舗名・組織名・氏名80文字、勤務区分名30文字、メール254文字、問い合わせ本文2000文字、要望200文字 |

| 対象 | 制限 |

### 4.5 データ保持・redaction

| 対象 | 保持 |
|---|---|
| 通知の宛先・本文（outbox payload） | 送信完了・失敗・キャンセルから30日でredact |
| 不達通知（FailureInbox） | 最終失敗から30日でエラーをredactし、表示・再通知対象から除外（`resolved/expired`） |
| 配送イベントログ | 90日で削除 |
| Stripe Webhook・operation | 90日 |
| 店舗・組織・人物の削除 | 論理削除。氏名・メール・店舗名・組織名・過去シフト・監査履歴は保持し、session・token・LINE連携・未送信通知を失効 |
| 通知履歴（metadata） | スタッフ・店舗の削除まで保持。削除時にcleanupで物理削除 |

## 5. ロール別にできること

### 5.1 ロールの定義

| ロール | 実体 | 認証 |
|---|---|---|
| 有効管理者（`active`） | `organizationMembers.active`。組織内の全店舗を管理し、契約操作も行える。プラン上限まで複数人を招待できる | Clerkログイン |
| 復旧担当者（`readOnly`） | 契約制限中に閲覧と復旧操作だけを許可された直前の管理者 | Clerkログイン |
| 元管理者（`removed`） | 管理者所属を終了した人物。管理画面のデータは閲覧できない | Clerkログイン（管理画面は拒否） |
| スタッフ | `staffs`（店舗別）＋`organizationPeople`（組織共通）。アカウント登録不要 | magic link → スタッフsession |
| 未ログイン | 公開サイト利用者・参加申請者 | なし（Turnstile等で保護） |

管理者・スタッフの追加にはメールアドレスが必須で、同一組織内の同じ正規化メールは同一人物として再利用する。  
別組織の情報は参照しない。

| 組織削除 | △（唯一の`active`管理者のみ。課金状態条件あり） | × | × | × | × |
| 契約操作（開始・変更・停止予約） | ○ | △（再契約・支払い方法更新・請求先変更のみ） | × | × | × |
| 管理者招待・権限解除 | ○（最後の1名の解除は不可） | × | × | × | × |
| 自分のスタッフ所属の解除 | ○（管理者権限と組織人物は維持） | ×（操作はactive管理者のみ） | - | -（本人操作なし。管理者が実施） | × |
| アカウント削除依頼 | △（所属構成による。複数組織所属は不可） | △ | ○ | ×（スタッフにアカウントなし） | × |
| 希望シフトの提出・再提出 | △（自分がシフト対象スタッフを兼ねる場合、スタッフとして） | 同左 | 同左 | ○（締切まで） | × |
| 確定シフトの閲覧・閲覧リンク再発行 | 同上 | 同上 | 同上 | ○ | × |
| 要望の送信 | ○ | ○ | × | ○（提出画面から） | × |
| 参加申請（QR/URL） | - | - | - | - | ○ |
| 問い合わせ・公開サイト・デモ | ○ | ○ | ○ | ○ | ○ |

補足:

- スタッフ所属の解除は「解除される対象」がactive/readOnlyの管理者人物でも実行できる（管理者権限と組織人物は維持される）。一方で「操作する側」はactiveな管理者に限られ、readOnlyの操作者は拒否される。
- 元管理者がスタッフを兼ねる場合、スタッフとしての提出・閲覧・通知は継続する。管理者だった事実を根拠にした閲覧は一切許可しない。
- シフト対象外スタッフは提出・閲覧・再発行の全スタッフ導線を失効し、シフト関連通知から外れる。LINE連携依頼や規約同意などシフト以外の通知は届く。
- URL・localStorage・クライアントが渡すIDは認可根拠にせず、全APIがサーバー側で所属・店舗境界・課金状態を再検証する。存在と権限不足は区別して漏らさない。

## 6. 状況別の挙動

### 6.1 募集のライフサイクル

募集の保存状態は`open`と`confirmed`の2値で、日付（提出締切・シフト開始・シフト終了）との組み合わせで画面の扱いが変わる。

```text
作成(open) → 提出締切(23:59 JST) → 確定(confirmed) → シフト終了日 → 翌日から過去
                                  ↑ 編集・再確定は終了日まで何度でも可
任意の時点で論理削除できる
```

| 状況 | 管理者ができること | スタッフができること |
|---|---|---|
| 募集作成〜締切前（`open`） | シフト表で割当編集・下書き保存。確定も日付・状態条件を満たせば可能（締切前の確定を禁止する条件はない） | 提出リンクから提出・再提出（締切日23:59 JSTまで）。提出済み内容の確認 |
| **締切後〜確定前（`open`のまま）** | 編集・保存・確定が可能。Dashboardで「要シフト調整」、`/actions`に表示。締切翌日17:00に確定催促が届く | **提出リンクは引き続き開ける（シフト開始日0:00 JSTまで）。提出済みなら閲覧のみ、未提出なら確認ダイアログ後に初回提出だけ可能** |
| 確定後（`confirmed`） | シフト終了日までは再編集・再確定できる。再確定時は前回通知との差分があるスタッフと、前回の確定通知が未配送のスタッフへ再通知。個別再送も可能 | 確定通知の閲覧リンクから確定シフトを閲覧。リンクを失った場合は再発行画面（登録メール一致で新リンク送付）。提出画面は「提出受付終了」 |
| シフト終了日の翌日以降 | 保存・確定・再通知は不可。過去のシフトとして閲覧のみ（Dashboardでは店舗filter時に遅延取得） | 確定シフトの個別再送対象外（再送は終了日が今日以降の募集のみ） |
| 削除済み | 一覧から消える。進行中の通知fanoutは同一transactionで停止 | 提出・閲覧リンクは「募集削除済み」の利用不可状態になる |

未提出スタッフへの割当、休み希望日への割当、希望時間外・希望外区分の割当は、確定を拒否しない「確認事項」として表示する。  
店舗境界違反や休業日割当などの違反は保存・確定を拒否する。

### 6.2 契約状態による制限（契約制限中 `restricted`）

Trial未契約終了、解約の期間末適用、支払い失敗14日経過などで契約制限中になると、業務を進める書き込みを止める。

| 分類 | 契約制限中の扱い |
|---|---|
| 停止する操作 | 募集の作成・編集・削除、シフトの保存・編集・確定、スタッフ追加・再有効化、管理者招待、店舗追加・再稼働、新規の業務メール・LINE送信 |
| 継続できる操作 | 既存データの閲覧（復旧担当者）、組織名変更（有効管理者）、再契約・支払い方法更新・請求先メール変更、利用者の組織からの削除、店舗アーカイブ、activeな管理者によるLINE明示解除 |
| データ | 店舗・利用者・シフトは削除しない。直前の管理者と稼働店舗を復旧候補として保持する |
| 画面 | 契約制限へ切り替わった画面は書込ダイアログを閉じ、ShiftBoardの未保存編集を破棄する。閲覧専用表示になる |

支払い失敗の14日猶予中は、失敗前プランの全機能を通常どおり利用できる（警告と支払い導線を表示）。  
`readOnly`の組織所属では、要対応・スタッフ一覧などの画面は閲覧でき、操作だけがサーバー由来の理由付きで無効になる。

### 6.3 スタッフ導線の失効条件

次のいずれかで、発行済みの提出・閲覧セッションとmagic linkは使えなくなる。

- シフト対象外への切替（`excludedFromShift`）
- 店舗からの所属解除（本日以降の割当も削除。過去の提出・割当は履歴として保持）
- 組織からの人物削除（全店舗の所属とLINE連携を終了）
- 店舗削除・組織削除
- 募集の削除、シフト開始日0:00 JSTの到来（提出リンクが開けるのはここまで。提出締切ではリンク自体は失効しない）、リンク・sessionの有効期限切れ

解除後に同じ人物を再追加した場合は、旧staffのsession・magic link・提出・割当を復元せず、新しいstaffとして未提出から開始する。  
店舗所属の解除だけでは組織共通のLINE連携を保持し得るが、組織から削除した後の再追加では本人による新しいLINE連携が必要になる。

### 6.4 自動通知の一覧（時刻はJST）

| 通知 | タイミング | 宛先 |
|---|---|---|
| 募集開始 | 募集作成時 | 対象店舗のシフト対象スタッフ |
| 提出催促 | 締切前日17:00（作成時点で未来の場合のみ予約） | 未提出のシフト対象スタッフ |
| 確定シフト | 確定時（前回通知と差分のあるスタッフ＋前回の確定通知が未配送のスタッフ） | 対象スタッフ |
| シフト確定催促 | 締切翌日17:00、未確定の場合 | 対象店舗にスタッフ所属するactive管理者 |
| 参加申請digest | 毎日17:00、直近24時間に承認待ちがある店舗 | 同上 |
| 通知不達digest | 毎日17:00、直近24時間にopen不達がある店舗 | 同上 |
| 本番募集リマインダー | 初回店舗登録7日後17:00、本人以外のシフト対象スタッフ未登録の場合 | 同上 |
| LINE連携依頼・法務同意依頼 | スタッフ追加時（未連携・未同意の場合） | 対象スタッフ |
| 課金通知（Trial終了予告・支払い失敗等） | 各イベント時 | 有効管理者・復旧担当者（メールのみ。LINEへは送らない） |

店舗単位の管理通知は「対象店舗にスタッフとして所属するactive管理者」だけに送る。  
対象者が0人なら送信せず、店舗詳細に管理者を店舗所属へ置く推奨を表示する。  
チャネルは、組織共通のLINE連携が有効かつ友だち状態ならLINE優先、それ以外は現在のシフト連絡先へメール。課金通知と管理者招待は常にメール。

## 7. 文書とコードの突き合わせで確認した注意点

マニュアル・テストケースに影響し得る既知の差分・未実装・運用前提を挙げる。

- **AIシフトたたき台作成**は業務仕様の有料機能として定義されているが、コード実装がない。マニュアル・テスト対象から除外する。
- `confirmRecruitment`は確定時に共通validation全体を再実行せず、募集の存在・終了日・状態・休業日だけを再確認する（既知の差分として`doc/plans/2026-07-23_doc現行コード差分調査.md`に記録あり）。
- 提出催促・確定催促は募集作成時にschedulerへ予約するため、**機能デプロイ前から存在する募集には催促が付かない**（既知の割り切り）。
- 通知不達の個別再送`resendFailure`は、ID直指定の`other` context失敗にactionable判定を再適用しない（既知の差分）。
- Dashboardお知らせと通知使用量（`notificationUsage`）には管理UIがなく、Convex Dashboardでの直接操作・確認が運用手順になる。
- 実環境で利用できる機能は`doc/manual/release-status.md`の証跡が正であり、コードの存在から公開済みと判断しない。
- 機能文書の形式は新旧が混在している（`shift-submission.md`などはヘッダー・保証範囲の章立てがない旧形式）。内容の照合日も文書ごとに異なるため、テスト設計時は対象文書の「最終コード照合」日付を確認する。

## 8. マニュアル・テストケースへの展開

- **マニュアル**: 1章（解決する課題）と3章（機能一覧）を目次の骨格にし、公開範囲（2章）で対象機能を絞る。操作手順の本文は`/help`と`/help/:slug`（`src/components/features/HelpCenter/content/`）に集約し、`write-help-content`の規約に従って追加する。

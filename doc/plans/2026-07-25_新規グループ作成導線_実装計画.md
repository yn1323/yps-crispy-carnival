# 新規グループ作成導線 実装計画

作成日: 2026-07-25

状態: 提案

対象checkout: 現在のcheckout（`feat/0723`）

## 1. 解決する問題

現在、グループ（`organizations`）を作れるのは初期設定の一度だけである。

`convex/setup/mutations.ts`の`setupShopAndManager`は、自分が作成した非削除グループが一件でもあれば`自分で作成できるグループは一つまでです`で拒否する。
画面側も`src/components/features/Dashboard/DashboardContent/index.tsx`が`!shop`のときだけ`Setup`を描画するため、どこかの店舗に所属した時点で作成導線へ到達できない。

一方で、複数グループへの所属自体は成立している。
`api.dashboard.queries.getMyShops`はグループ横断で候補を返し、Dashboardの店舗切替と`/settings`のグループ切替も複数グループに対応している。
不足しているのは作成だけである。

この計画は、既存の管理ユーザーが自分で二つ目以降のグループを立ち上げる導線を追加する。

## 2. 確定した判断

実装中に次を再検討しない。

| 項目 | 判断 | 理由 |
|---|---|---|
| 初期課金状態 | 二つ目以降は`active.free`で開始する | 支払い不要Businessは製品を体験してもらうための一度きりの提供であり、既に一つ目で体験を終えた利用者へ繰り返し配る理由がない。無償Business量産の余地もここで消える |
| 一つ目の初期課金状態 | `complimentary.business`のまま変更しない | 初回セットアップの体験と既存グループの状態には手を入れない |
| 作成上限 | 自分で作成した非削除グループを3件まで | `by_createdByUserId_and_isDeleted`で数えられる。Free開始にしたことで配布の問題は消えるが、作成ごとに店舗、staff、通知予約が増えるため、churnの上限は残す |
| 招待による所属 | 上限に数えない | 上限の対象は自分が契約主体になるグループの数であり、他人のグループへの参加ではない |
| 作成の入口 | `/settings`の「設定」タブ | グループ自体のライフサイクル操作（削除）と同じ場所に置く |
| 切替の入口 | 現状のまま変更しない | Dashboardの店舗切替メニューと`/settings`のグループ切替が既にある |
| グループ名 | 最初の店舗名をグループ名にも使う | 初期設定と同じ挙動。作成後に「グループ名」から変更できる |
| 現在のグループの課金状態 | 作成可否に影響させない | グループは独立した契約単位であり、制限中のグループの管理者でも別グループの契約主体にはなれる。量産は上限3で抑える |
| 利用規約の同意 | 既存ユーザーの同意状態を上書きしない | `legalConsentStates`のuser状態は`by_userId`のsingletonであり、同意済みの利用者へ再同意を求める理由がない。新しく作るstaffの同意だけ記録する |
| LINE連携案内メール | 初期設定と同じく送る | `staffLineAccounts`は店舗ごとのstaff単位であり、新グループの店舗で通知を受け取るには新しいstaffとしての連携が要る。同じLINEアカウントを複数店舗のstaffへ紐づける経路は`convex/line/service.ts`の`findStaffLineAccountsByLineUserId`で既に対応済みである |
| 店舗有効化リマインダー | 初期設定と同じく予約する | 7日後に募集がない場合だけ届く条件付きの補助通知であり、作ったまま放置しているグループにこそ意味がある。失敗inboxにも載せない |
| schema変更 | 行わない | 上限は保存する値ではなく、書き込み時に既存indexから数える導出値である。詳細は次節 |

### 2.1 schemaを変えない理由

作成上限を導入しても、保存するデータの形は変わらない。
「何グループ作ったか」は`organizations`の行そのものが表しており、別に持つカウンタは新しい真実を増やさずズレる余地だけを増やす。

上限判定に必要なものは揃っている。

- `organizations.createdByUserId`は既にあり、`by_createdByUserId_and_isDeleted`のindexも定義済みである（`convex/schema.ts:82`）。
- 複数グループ所属は`organizationMembers`と`organizationPeople`がグループ単位で持つ形になっており、1利用者あたりの件数を制限するschema上の仮定はない。
- rate limitの新しいbucketは実行時のkeyであり、`rateLimitTables`は既にschemaへ取り込まれている（`convex/schema.ts:45`）。
- 二つ目以降を`active.free`にしても、`organizationBillingStates.state`は既存unionの`{ kind: "active", plan: "free" }`にそのまま収まる。

既存documentが新しい形に合わなくなる変更もbackfillも発生しないため、`convex-migration-helper`の対象にならない。

一点だけ、schemaの形ではなく意味の面で触れておく。
`legalConsentStates`のuser行は`by_userId`のsingletonで`shopId`を一つだけ持つ。
これは招待で複数グループに所属している既存利用者にも既に当てはまる状態であり、この計画で新しく壊れるものではない。
だからこそ、2つ目のグループ作成時にこの行を上書きしない。

## 3. Security Lens

- **Actor**：認証済みの管理ユーザー本人。招待やcapabilityは関与しない。
- **Asset**：`organizations`の作成、通知とリマインダーのスケジュール、staffとLINE連携tokenの発行。二つ目以降は`active.free`で作るため、支払い不要Businessの発行はこの経路に含まれない。
- **Trust boundary**：ブラウザとConvex backend。新しいHTTP routeやWebhookは追加しない。
- **Abuse case**：連打による二重作成、削除と再作成の反復によるスケジュールとメールの水増し、削除申請済みアカウントからの作成、契約制限中のグループから逃れるための作成。
- **Server-side enforcement**：`ctx.user`の存在と非削除・削除申請なしを確認し、作成上限をサーバー側で数える。clientから`userId`や作成可否を受け取らない。作成可否のUI非表示だけに依存しない。
- **Rate limit / idempotency**：`requestId`由来のcorrelationIdで冪等化し、actor単位の短時間・日次budgetを重ねる。削除と再作成の反復は日次budgetで抑える。
- **Lifecycle / recovery**：作成したグループは既存の`deleteOrganization`で削除でき、削除済みは上限に数えない。作成失敗時は同じ`requestId`で再試行できる。
- **Logs / PII**：監査は既存の`recordOrganizationAuditEvent`だけを使い、メールアドレスや生の`requestId`を保存しない（`toAuditRequestKey`でSHA-256化する）。
- **Regression test**：上限超過、冪等再実行、rate limit、削除申請済みアカウントの各拒否で、DB、scheduler、監査が増えないことをFunction Testで固定する。

## 4. サーバー設計

### 4.1 共通処理の抽出

`convex/setup/service.ts`を新設し、`setupShopAndManager`の後半にある作成処理を`createOrganizationWithFirstShop`として切り出す。

この関数が作るものは次のとおりで、課金状態を除いて現在の`setupShopAndManager`の副作用と同一にする。

- `organizations`（`createdByUserId`、`name`、`billingEmail`）
- `organizationPeople`と`organizationMembers`（`active`）
- `shops`（`operatingStatus: "active"`）と既定`position`
- `organizationBillingStates`（初期状態は引数で受け取る、`version: 1`）
- 互換書き込みの`shopBillingStates`と`shopMembers`（既存の`TODO[narrow]`コメントを移設する）
- 管理者自身の`staffs`と`recordStaffLegalConsent`
- `organization.created`の監査
- `internal.line.actions.sendInviteEmail`と店舗有効化リマインダーの予約

呼び出し側で分かれるのは次だけである。

| 処理 | `setupShopAndManager` | `createOrganization` |
|---|---|---|
| `users`の作成 | 未登録なら作る | 既存ユーザーを必須とする |
| `users`の名前・メール更新 | 行う | 行わない |
| `acceptedLegal`引数 | 必須 | 受け取らない |
| `recordUserLegalConsent` | 記録する | 記録しない |
| 初期課金状態 | `{ kind: "complimentary", plan: "business" }` | `{ kind: "active", plan: "free" }` |
| 監査の`toState` | `complimentary.business` | `active.free` |
| 上限 | 既存グループが0件 | 自分が作成した非削除グループが3件未満 |

`organizationBillingStates.state`は既存unionの`{ kind: "active", plan: "free" }`をそのまま使う。
互換書き込みの`shopBillingStates`は現在も`planKey: "free"`で入れているため、こちらは変わらない。

作成直後の新グループは、Freeの上限（利用人数5名、稼働店舗1件、有効管理者1名）をちょうど使い切った状態になる。
店舗追加と管理者招待は既存のFree判定でそのまま止まり、この計画で新しい分岐を足す必要はない。

### 4.2 新しいpublic mutation

`convex/setup/mutations.ts`へ`createOrganization`を追加する（`authenticatedMutation`）。

```ts
args: {
  shopName: v.string(),
  regularClosedDays: v.optional(v.array(weekdayValidator)),
  submissionPattern: submissionPatternValidator,
  requestId: v.string(),
}
returns: v.object({ shopId: v.id("shops"), created: v.boolean() })
```

入力検証は`convex/shop/schemas.ts`の`updateShopSettingsSchema`を使う（`addShop`と同じ）。

処理順は次のとおりとする。

1. `ctx.user`がない、`isDeleted`、`accountDeletionRequestedAt`がある場合は拒否する。
2. `toAuditRequestKey(args.requestId)`から`user:${userId}:organization:create:${requestKey}`のcorrelationIdを作る。
3. `by_correlationId`で先行監査を引く。見つかった場合は`actorUserId`が自分、`action`が`organization.created`、`targetKind`が`organization`であることを確認し、そのグループの最古の非削除店舗を`created: false`で返す。確認できなければ`以前の操作結果を確認できません`とする。
4. rate limitを消費する（先行監査の確認より後に置き、同じ`requestId`の再試行でbudgetを減らさない）。
5. `by_createdByUserId_and_isDeleted`で自作の非削除グループを`take(4)`し、3件以上なら拒否する。
6. 移行互換として、`organizationId`を持たない非削除の旧店舗も1件を1グループとして同じ上限へ数える（現在の`既に店舗が登録されています`ガードを置き換える`TODO[narrow]`扱い）。
7. `createOrganizationWithFirstShop`を呼び、`shopId`を`created: true`で返す。

先行監査の確認は`deleteOrganization`の実装（`convex/organization/mutations.ts:602`）と同じ形にする。

### 4.3 上限とrate limit

`convex/constants.ts`へ追加する。

```ts
export const ORGANIZATION_SELF_CREATED_LIMIT = 3;
export const ORGANIZATION_CREATE_DAILY_LIMIT = 10;
```

`convex/_lib/rateLimits.ts`へactor単位のbucketを追加する。

| 名前 | key | 制限 | 目的 |
|---|---|---|---|
| `organizationCreateShort` | `userId` | 1回/分 | 連打と、`requestId`を変えた二重作成の抑止 |
| `organizationCreateDaily` | `userId` | 10回/日 | 削除と再作成を繰り返す churn の抑止 |

日次budgetを上限と同じ3にしない。
同時に持てるグループ数は上限3で決まっており、日次budgetが抑えるのは作り直しの回数だけである。
名前を間違えて作り直すような正当な操作を1日3回で止めると、利用者は自分のグループを作れないまま待つことになる。

### 4.4 作成可否のquery

`api.organization.queries.getSettings`の返却へ次を追加する。

```ts
canCreateOrganization: v.boolean(),
createOrganizationDisabledReason: v.optional(v.string()),
```

判定はactor単位であり、選択中グループの課金状態や`memberStatus`に依存しない。
数える処理はmutationと同じhelperを共有し、二か所で条件がずれないようにする。

`getSettings`は設定画面のDTOを既に所有しているため、専用queryを追加せずここへ載せる。
作成可否をDashboardなど他画面でも使う必要が出た時点で、`authenticatedQuery`として切り出す。

## 5. フロントエンド設計

### 5.1 利用者のタスク

主タスクは、既に一つのグループを運用している管理者が、既存グループのデータと混ぜずに別グループを立ち上げ、その最初の店舗のDashboardまで到達することである。

補助タスクは、作成できない理由（上限到達）の確認である。
この画面では、グループの切替、既存グループへの店舗追加、招待を扱わない。

### 5.2 配置

`src/components/features/OrganizationSettings/OrganizationCreation/`を新設する。

| ファイル | 責務 |
|---|---|
| `OrganizationCreationSection.tsx` | 「設定」タブの説明と作成ボタン、無効時の理由表示 |
| `OrganizationCreationDialog.tsx` | `StepperDialog`と既存の`ShopForm`による入力 |
| `useOrganizationCreationController.ts` | mutation接続、`useSingleFlight`、`requestId`生成、Toast、遷移 |
| `types.ts` | Dialog stateと操作の型 |
| `*.stories.tsx` | 代表状態 |

`OrganizationSettingsView.tsx`の「設定」タブで、`OrganizationDeletionSection`の上に`OrganizationCreationSection`を置く。
破壊的操作は最下部に残す。

`ShopForm`（`src/components/features/ShopForm/`）をそのまま使い、初期値は`ShopManagementDialog`の`ADD_SHOP_DEFAULT_VALUES`と揃える。

### 5.3 状態

| 状態 | 表示 |
|---|---|
| Success | Toast「新しいグループを作りました」の後、`/dashboard?shop=<新しい店舗ID>`へ遷移する |
| Error | 既存の`showErrorToast`でサーバーのメッセージを表示し、Dialogは開いたままにする |
| 利用不可 | ボタンをdisabledにし、理由文をボタン下に表示する（`ShopsSection`の`addShopDisabledReason`と同じ形） |
| 送信中 | `useSingleFlight`で二重送信を止め、サーバー側は`requestId`で冪等化する |

遷移は`await`したmutationの解決後に行う。
Convexはmutation解決時点で購読中の`getMyShops`を同時刻以降へ更新するため、`AuthGuard`の`invalidRequestedShop`（「この店舗を開けません」）には落ちない想定である。
実装時にこの遷移を手で確認し、候補反映が間に合わない事象が出た場合は、新しい`shopId`が候補へ現れてから遷移する形へ変える。

### 5.4 マイクロコピー

「同じグループに店舗を増やす」操作との違いが読み取れる文言にする。

開始プランが今のグループと違うため、作る前に分かる位置へ書く。
作成後に「思っていたプランと違う」と気付く状態にしない。

- セクション見出し：新しいグループ
- 説明：別の会社や別ブランドのお店を、いまのグループとは分けて管理できます。ユーザー、プラン、支払いはグループごとに分かれます。同じ会社でお店を増やす場合は、「店舗」タブから店舗を追加してください。
- ボタン：新しいグループを作る
- Dialog見出し：新しいグループを作る
- Dialogの注意：新しいグループは無料プランで始まります。ユーザー5名、お店1つ、管理者1名まで使えます。増やす場合は、作成後に「プランと支払い」から変更してください。
- 送信ボタン：グループを作る
- 上限到達時：作成できるグループは3つまでです。使っていないグループを削除すると、また作成できます。

Dialogの注意は、送信ボタンの近くへ常時表示する。
`ShopForm`の下に置き、入力途中でも視界へ入る位置にする。

### 6.1 E2E

契約ID`MG-P0-02`として、単一actorの`e2e/fixtures/e2eTest.ts`で追加する。
既存の`MG-P0-01`（`e2e/scenarios/multiActor/multiple-organization-switching.test.ts`）は、seedで用意した2グループの切替を守る。
この計画で守るのは、画面操作で2つ目のグループが生まれた直後の接続であり、失敗の理由が異なる。

E2Eでしか検知できない失敗が具体的にある。
`AuthGuard`はURLの`shop`を`getMyShops`の候補と照合し、一致しなければ「この店舗を開けません」を表示する（`src/components/features/AuthenticatedApp/shopContextResolver.ts`の`invalidRequestedShop`）。
作成直後の遷移で候補の反映が間に合うかは、実backendと実ブラウザの購読更新でしか確かめられない。

構成は`e2e/scenarios/organization-shop-lifecycle.test.ts`の`MS-P0-01`に倣う。

| Step | 操作と確認 |
|---|---|
| 1 | 既存グループの`/settings`の「設定」タブから新しいグループを作る |
| 2 | 新グループの最初の店舗でDashboardが表示され、`この店舗を開けません`にならない |
| 3 | 店舗切替メニューに2グループが並ぶ（`DashboardPage.expectOrganizationGroupsInShopSwitcher`） |
| 4 | 新グループのスタッフ一覧が自分だけで、既存グループのスタッフが混入しない |
| 5 | 新グループの「プランと支払い」が無料プランを表示し、既存グループは元のプランのままである |
| 6 | reload後も新グループの店舗選択を維持する |

Step 5を入れるのは、開始プランが利用者への約束だからである。
どのプランで始まるかは、mutationの引数ではなく画面に出た結果で確かめる。

`e2e/pages/OrganizationSettingsPage.ts`へ`createOrganization`相当の操作を追加する。
`addShop`と同じ形にし、Dialogの開閉と入力をPage Objectへ閉じる。

作成上限、rate limit、冪等再実行はE2Eに含めない。
3件作る操作は遅く、失敗理由もサーバー側の判定であり、Function Testが主担当である。

teardownは既存のactor単位resetで足りる。
`convex/testing.ts`の`resetManagerScenarioDataForAuth`は`by_createdByUserId`で対象ユーザーのグループを全件削除するため、画面操作で作ったグループも回収される。
日次budgetは`userId`をkeyにするが、resetが孤立したuserを削除して次回runで新しいuserを作るため、繰り返し実行でも枯渇しない。

6. Frontend Unit TestとVRT対象Storyを整える。
7. 文書を更新する。
8. `pnpm lint`、`pnpm type-check`、`pnpm test`、`pnpm build`を実行する。

## 9. 対象外

- Dashboard側への作成導線の追加。
- グループ名と店舗名を別々に入力する画面。
- 二つ目以降のグループへ別の初期プランを与える仕組み。
- 作成上限の管理者向け緩和や運用ツール。
- グループ間での人物、店舗、シフトの移動。

## 10. 後から変えられるようにしておく点

未決のまま実装を止める判断はない。
次の二つは決定済みだが、変更が一か所で済む形にしておく。

**通知の扱い**：LINE連携案内メールと店舗有効化リマインダーは初期設定と同じく送る。
不要と判断した場合に備え、予約は`createOrganizationWithFirstShop`の内部に閉じ、呼び出し側の引数一つで止められる形にする。

**開始プラン**：二つ目以降は`active.free`で始める。
課金状態は`createOrganizationWithFirstShop`の引数として呼び出し側が渡すため、キャンペーンなどで一時的にTrialや別状態へ変える判断が出ても、mutation側の一行で切り替わる。

作成状況の観測に追加実装は要らない。
`organizationAuditEvents`の`organization.created`は`actorUserId`と`toState`を持ち、`by_actorUserId_and_occurredAt`で利用者ごとの作成回数と開始プランを後から数えられる。

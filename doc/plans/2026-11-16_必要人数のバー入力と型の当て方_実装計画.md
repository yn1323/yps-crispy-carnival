## 目的と前提

### 誰がどの場面で困っているか

1日の中で必要な人数が何度も変わる店舗の担当者が、型を作る場面で困っている。  
初版は、時間帯ごとに開始と終了をプルダウンで選び、人数を−／＋で1人ずつ増減する。  
「昼3人、直後に1人、夜5人」を入れるには、時間帯を3つ足してプルダウンを6回、＋を9回押す。  
シフト表では、時間帯の箱に全ポジションの数字が詰まり、どの時間に何人足りないかを読み取りにくい。

### どうなれば完成か

担当者が、シフト表と同じバーの操作で1日分の必要人数を作れる。  
祝日や年末年始のような日にも、名前を付けた型を当てられる。  
シフト表では、時間の軸にそろった帯で、足りない時間と多い時間が一目で分かる。

### すでに決まっていること

ユーザーとの検討で、次の内容が決まっている。

| 項目 | 決めた内容 |
|---|---|
| 型の作り方 | 時間指定の店舗は、行とバーで作る。  1本のバーが1人分で、ある時刻の必要人数は重なったバーの本数になる |
| 行の意味 | 行は人を表さない置き場所である。  1ポジションで10行程度を想定する |
| 操作 | シフト表の時間入力のバーと同じ操作にする。  ボタンと時刻の選択で足す方法も用意する |
| 取り消し | 作らない |
| 型の当て方 | 型に名前を付けて複数作る。  使う日は曜日と祝日。  日付の範囲で当てる機能は作らない |
| 祝日 | 日付を持つ表をデータベースに置いて判定する。  表の更新は運営者が行う |
| まとめて当てる | シフト表で複数の日を選び、型を1回で当てる |
| その日だけ | 当たっている型を写して、その日だけバーを直す |
| 確定済み | 確定した時点の必要人数をそのまま残す |
| 人数の見せ方 | ポジションごとの帯を時間の軸にそろえる。  足りない時間は危険色、多い時間は別の色で示し、中に人数を書く |
| 熟練度 | スタッフ単位の「新人／標準／責任者」のままにする。  新人だけの時間帯を伝える |
| スマートフォン | 凝った操作は求めない。  ボタンと時刻の選択で同じことができればよい |

### 業務上の決まり

- 何も設定していない店舗と、スタッフ10人以下の店舗の流れは変えない。
- 労務の領域には入らない。  人件費は扱わず、多い時間は表示にとどめる。
- 必要人数と過不足は、いま在籍しているシフト対象のスタッフだけを数える。
- 設定は、対象店舗が属する組織の有効な管理者だけが変更できる。

## 設計の要点

### 型の持ち方

時間指定の型は、バーの集合だけを保存する。  
1本のバーは、ポジション、開始、終了を持つ。  
行は保存せず、表示のときに「開始の早い順に、その時間が空いている一番上の行へ置く」決まりで作る。

行を保存しない理由は2つある。  
行は置き場所で意味を持たないため、保存すると「同じ行で重なる」「途中の行が空く」という不正な状態を検証する必要が出る。  
人数の集計と、今後AIへ渡す枠は、どちらもバーだけで足りる。

パターン選択の型は勤務パターンごと、日付選択の型は1日ごとに、ポジション別の人数を持つ。

### バーの操作

利用者から見た操作は、シフト表の時間入力のバーと同じにする。  
空いた場所をなぞるとバーが引け、端をなぞると伸び縮みする。  
刻みは30分で、置いたバーは手を離したときに一番上の空いた行へ寄る。

部品は、座標の計算（`timelineGeometry.ts`）だけをシフト表と共有し、型の編集用に薄い実装を書く。  
シフト表のバーは「1人は同時に2か所へ入れない」前提で、重なった区間を上書きし、隣り合う区間をつなげる。  
型のバーは重なりを許すため、同じ処理を使えない。  
シフト表のドラッグ処理（`useDrag.ts`）と塗りの処理（`operations.ts`）には手を入れず、動いている画面の回帰を避ける。

型のバーは、隣り合っても自動でつなげない。  
10時〜14時と14時〜18時は、人数は同じでも「2人の交代」と「1人の通し」で意味が違う。  
今後AIで人を割り当てるときに、この違いを使う。

ドラッグを使わない方法として、ボタンから「ポジション、開始、終了、本数」を選んで足せるようにする。  
バーを押すと、開始と終了を変える欄と削除が開く。  
削除はこの欄だけに置き、長さが0になる操作ではバーを消さない。  
取り消しを作らないため、誤って消える経路を減らす。

### 型の当て方

その日に当たる型は、次の順で決める。

1. その日だけの指定（別の型を当てた日、その日だけバーを直した日）
2. 祝日に使う型（その日が祝日の表にある場合）
3. 曜日に使う型

祝日の表は、店舗に属さない全体の表として持つ。  
既存コードの`holidays`は店舗の休業日を指すため、新しい表は`nationalHolidays`と呼んで取り違えを避ける。  
読むのはサーバーのqueryだけで、書き込みはpublic APIに置かず、運営者がinternal mutationを実行する。

その日に当たる型の解決は、サーバーで行う。  
シフト表のqueryは、日ごとに解決済みの必要人数と、その理由（その日だけ、祝日、曜日、未設定、確定時）を返す。

### 確定した時点の必要人数

募集を確定するときに、募集期間の各日の必要人数を、確定と同じtransactionで保存する。  
確定済みの募集のシフト表は、保存した必要人数だけを表示する。  
確定済みの募集では、型の当て直しと「この日だけ変える」を受け付けない。

### シフト表の帯

「くわしく」表示の人数は、ポジションごとに1行の帯にして、時間の軸にそろえる。  
区切る時刻は、バー、勤務、休憩の開始と終了を合わせたものにし、同じ状態が続く区間は1つにまとめる。  
初版の「時間帯の中で最も少ない時点の人数」という数え方と、型のない日の「1時間ごとの人数」は、この帯へ統一してなくす。

| 状態 | 表示 |
|---|---|
| 足りない | 赤の薄い地と実線の枠、「2/3 ▲1」 |
| 多い | 青の薄い地と点線の枠、「2/1 ＋1」 |
| ちょうど | 地と枠なし、「3/3」 |
| 未設定 | 人数だけ |

ポジションの色は店舗が10色から選ぶため、過不足の色はどれを選んでもポジションの色と重なりうる。  
ポジションの色は行の先頭の丸だけに使い、過不足は薄い地色、枠の線の種類、記号の3つで示す。  
狭い区間では「▲1」のように差だけを出し、全文は押したときの欄に出す。

バーが1本もないポジションと、型が当たらない日は、未設定として過不足を出さない。  
決めていないポジションに人を入れただけで、全部が「多い」になることを避ける。

`.claude/rules/ui-colors.md`は、赤を「削除、破壊的操作」としている。  
シフト表はすでにエラーの行に赤を使っているため、同じ規約に「シフト表の不足」を足す。

### 新人だけの時間帯

あるポジションに入っている人が全員新人の区間に、「新」の印を出す。  
確定の前の確認事項にも、日、ポジション、時間帯の単位で出す。  
既存の確認事項はスタッフ1人に結び付く形のため、別の一覧として持ち、件数へ足す。  
保存と確定は止めない。

### 受付時間の外に出たバー

店舗が受付時間を短くすると、範囲の外に出るバーができる。  
初版は黙って隠し、次の保存で消していた。  
今回は保存済みのバーを残し、設定ページに本数と「受付時間に合わせる」を出す。  
シフト表は、募集の受付時間の内側だけを数える。

募集を作ったあとで店舗が集め方の種類を変えた場合、その募集では必要人数を未設定として扱う。

### 移行

`convex-migration-helper`の基準では、本番とdevelop環境にデータがない変更は移行の対象にならない。  
`shiftDayTemplates`と`shiftDayTemplateOverrides`の形は、同じPull Requestの中で置き換える。  
ローカルのdeploymentに初版のdocumentが残っている場合は、schemaを変える前に2つのテーブルを空にする。  
Pull Requestのプレビュー環境は、置き換え後の最初のdeployの結果を確かめる。

## 検討で分かれた点と決めたこと

設計と画面を、別々のサブエージェントに検討させた。  
意見が分かれた点と、採った案は次のとおりである。

| 論点 | 設計の担当 | 画面の担当 | 採った案 |
|---|---|---|---|
| 既存のバー操作の流用 | 座標の計算だけ共有し、別実装にする | 意見なし | 別実装にする。  操作は同じにする |
| 隣り合うバー | つなげない | 意見なし | つなげない |
| 行の名前 | 行を保存しない | 「ホール 1」は人やレジの番号に読める。  番号だけにする | ポジション名は見出しに1回、行は番号だけ |
| ボタンで足す方法 | バーごとの欄で足りる | 人数を持たせて「この時間を3人にする」 | 本数を選んで足す。  置き換えにすると既存のバーを切り分ける処理が要るため、追加だけにする |
| 「多い」の色 | 意見なし | 無彩色を勧める。  青は次点、暖色は不足に見える | 青の薄い地と点線の枠。  ユーザーが図で見やすいと評価した形を保つ |
| 型の一覧 | 上限を20件にする | タブで切り替える | PCは左の一覧、スマートフォンはセレクト。  20件はタブに収まらない |
| できあがる必要人数の位置 | 意見なし | 下端に固定し、ポジションを畳めるようにする | 下端に固定する |
| 確定済みでの「この日だけ変える」 | 拒否する | 意見なし | 拒否する |
| 祝日の表が翌年分を欠く場合 | シフト表に知らせる | 意見なし | 店舗には出さない。  店舗が対処できないため、運営の手順に書く |

## 実装中に変えた判断

実装で分かった事実に合わせて、次の点を計画から変えた。

1. 受付時間の外に出たバーは、読み込みでは消さずに返し、保存は拒否する。  設定ページで「受付時間に合わせる」を押してから保存する流れにした。  黙って消さない方針は保つ。
2. 新しく足した型の必要人数は、空で始める。  初版は直前の型を写していたが、バーは1本ずつしか消せないため、写すのは「ほかの型からコピー」に任せた。
3. 「この型を削除」に確認を足した。  取り消しを作らないため、組んだ型を誤って消す経路を減らす。
4. スマートフォンの設定ページでは、「できあがる必要人数」を下端に固定せず、バーの一覧のすぐ下に置いた。  一覧が縦に長く、下部のメニューと保存のバーに重なるためである。
5. 型が当たらない日は、確定時の保存に行を作らない。  型を持たない店舗の確定の流れを変えないためである。  行のない日は未設定として返す。
6. 「ほかの日もまとめて変える」では、型のほかに「曜日の設定に戻す」も選べるようにした。
7. その日だけ人数を変えた日は、元の型の名前を持たず、「この日だけ変更」と表示する。
8. 「新人だけの時間帯」は、確定の前の確認に「シンプル」と「くわしく」のどちらでも出す。  既存の「入れないポジション」の確認事項と同じ扱いにした。  日付の印へ足すのは、印の出どころが見える「くわしく」のときだけである。
9. 「この日だけ人数を変える」のDialogの中では、バーを足す入力をDialogで開かず、その場に出す。  Dialogの上にDialogを重ねない決まりに合わせた。
10. 型の種類が募集の集め方と違う型は、その募集の日へ当てられないようにした。
11. 祝日の表は開発用のシードに入れていない。  シードはシナリオ単位の作りで、店舗に属さない表が合わないためである。  シードを流すと祝日の表も空になるため、運営の手順に入れ直しを書いた。
12. パターン選択と日付選択の人数は、セル全体の赤地をやめ、帯と同じ決まりの色と枠で示す。
13. 確定済みの募集でも、削除済みのポジションを指すバーと人数は、読み取りのときに除く。  保存した行は書き換えない。  確定のあとでポジションを削除した店舗では、そのポジションの必要人数が確定済みのシフト表から消える。
14. 型の編集では、ポジションごとに行を畳めるようにした。  シフト表の帯は、ポジションが4つ以上ある日に、過不足のあるポジションだけを出して残りを1行にまとめる。  どちらも、行が増えたときの縦の長さへの対処である。
15. 受付時間が30分刻みにそろっていない店舗では、バーを置ける範囲と切りそろえる位置を、刻みに乗る内側の時刻へ寄せる。  店舗設定の画面は30分刻みだけを選ばせるが、保存の形は分単位を受け付けるためである。

利用者が画面を使ったあとの指摘を受けて、次の点を変えた。

16. 隣り合うバーは、同じ行で1本にまとめる。  「つなげずに2人の交代として持つ」とした当初の判断は撤回した。  足したバーがつながらず、ばらばらに見えるためである。  まとめても時間帯ごとの必要人数は変わらない。
17. スマートフォンでも、一覧ではなくバーの表で入力する。  1日を画面の幅に収め、指でなぞってバーを引く。  一覧では、本数が足し算だと伝わらず、できあがる必要人数も遠かったためである。
18. 保存の操作は、画面の下端に出すのをやめ、ページの見出しの右に置いた。  スクロールしても上端に残る。  変更のたびに下端へ現れて、操作のじゃまになったためである。  自動保存は、AIの下書きを保存の前に確かめる流れと両立しないため、採らなかった。
19. PCのバーの行を44px、バーを32pxへ高くし、できあがる必要人数は表の下へ置いた。
20. バーを押して開く欄の中の操作が、バーを引く操作として始まる不具合を直した。
21. 設定ページから「休憩の決まり」の入力を外した。  保存のAPIとシフト表の初期値の動きは残している。
22. スタッフの熟練度は、スタッフごとの1つの値から、ポジション別の値へ変えた。  「入れない」も同じ値の1つとして持つ。  設定ページでは、スタッフとポジションの表で選ぶ。
23. 最初からあるポジション「シフト」の固定をやめた。  並び替えができ、2件以上あれば削除できる。  既定のポジションを削除すると、一覧の先頭が新しい既定になる。
24. 設定ページの見出しの下の店舗名、必要人数の説明文、「まだどの型にも入っていない曜日」の表示を外した。

## Security Lens

- Actor: 店舗の管理者（組織の有効なメンバー）、運営者（祝日の表の更新）。
- Asset: 型、その日だけの指定、確定時の必要人数、祝日の表。
- Trust boundary: public mutationが受け取る型のID、ポジションのID、日付、バー。
- Abuse case: 別店舗の型やポジションを指定する。  大量のバーや日付を送ってデータを肥大させる。  確定済みの募集の必要人数を書き換える。  祝日の表を書き換える。
- Server-side enforcement: 既存の`managerMutation`と`managerQuery`を使う。  受け取ったIDは取得後に同じ店舗で有効かを確かめ、違えば`Not found`に寄せる。  バーの本数、刻み、範囲、同時の重なり、日付の件数と重複を検証する。  確定済みの募集への変更は拒否する。  祝日の表の書き込みはinternal mutationだけに置く。
- Rate limit / idempotency: 型の保存は全置換で、同じ入力を繰り返しても同じ状態になる。  まとめて当てる操作は、日付ごとの指定を置き換える。  確定時の保存は、未確定から確定へ変わるときの1回だけ行う。
- Lifecycle / recovery: 型を削除すると、その型を指す日は曜日の型へ戻る。  店舗の削除では、関連する4つのテーブルを消す。  その日だけの指定は店舗ごとに日数分たまるが、古い指定を消す仕組みは今回作らない。
- Logs / PII: 個人情報を含まない。  AIサポートの入力文は、初版と同じく保存もログ出力もしない。
- Regression test: 別店舗の型とポジションの拒否、上限の拒否、確定済みへの変更の拒否、確定後に型を直しても表示が変わらないこと。

## 実装の順序

1. ローカルのdeploymentで、初版の型と日ごとの指定を空にする。
2. Convex: validator、schema、上限の定数。
3. Convex: 型の検証と、その日に当たる型の解決（純粋処理）。
4. Convex: 型の保存、祝日の表、まとめて当てる処理、その日だけのバー。
5. Convex: 確定時の保存と、シフト表のquery。
6. 純粋処理: 行への詰め方、バーの追加・伸縮・削除、帯の区切り、新人だけの判定。
7. 部品: 座標の計算を`src/components/shared/`へ移し、バーの編集部品を作る。
8. 設定ページ: 型の一覧、バーの表、できあがる必要人数、ボタンで足す方法、スマートフォンの構成。
9. シフト表: 帯、日付の印、まとめて当てる操作、この日だけ変える操作、新人だけの印。
10. AIサポートの下書き。
11. 追従: 開発seed、`convex/testing.ts`、機能文書、契約表、祝日の表を更新する運営の手順、`ui-colors.md`。

## 検証

- 完成条件ごとの対象テストを先に実行し、そのあとで`pnpm lint`、`pnpm type-check`、`pnpm test`、`pnpm build`を実行する。
- E2Eは、承認のときのユーザーの指示により今回は実行しない。  `E2E-STAFFING-01`が通ることはCIで確かめる。
- 見た目を変えた箇所は`.claude/rules/stories.md`に従って目視で確かめる。  VRTはCIに任せる。
- 検証が通ったら、`plan-reviewer`で完成条件と変更したファイルを照合する。

# GA4計測基盤とSkill整備 実装計画

## 文書の状態

- 状態: `Proposed / reviewing`
- 作成日: 2026-08-12
- 基準commit: `00753faad2a2d43ffa19b57326394dcba77fb91a`
- 対象: メインWebアプリ、Google Tag Manager、GA4、Microsoft Clarity、計測用Skillと関連文書

この文書は、GA4イベントの方向性、安全な計測基盤、GTM・GA4の外部設定、計測作業を再利用するSkillの導入順序を定める。

現在仕様の正本は`doc/features/`、恒常規約は`doc/rules/`、人が行う外部設定は`doc/manual/`とする。
この文書は実装時点の判断と順序を残す計画であり、実装完了後の現在仕様の正本にはしない。

## 採用する方向性

1. GA4は、流入、閲覧、CTA、デモ、登録、画面上の成功信号を把握するために使う。
2. 店舗登録、募集、提出、確定、継続などの永続的な業務成果は、既存のConvex Analyticsを正本とする。
3. SPAの`page_view`はアプリだけが送信し、GTM・GA4側の自動計測と重複させない。
4. featureはraw URLや任意parameterを送らず、型付きイベントとeventごとのexact allowlistだけを使う。
5. イベントはDOMクリックの推測ではなく、意味のある選択時または処理成功後に一度だけ発火する。
6. `user_id`、個人情報、credential、内部ID、自由入力、高cardinality値は初期計測へ含めない。
7. リポジトリ実装、GTM・GA4設定の公開、Productionでの安全な観測を別々の完了状態として扱う。

Googleが定義する自動収集、拡張計測、推奨イベント、カスタムイベントの順を使い、既存の意味へ合わない場合だけカスタムイベントを追加する。

## 目的と対象外

### 目的

- 検索・記事・TOPからデモ、登録、初期設定までの離脱箇所を匿名かつ低粒度で把握する。
- SPAの各画面遷移を、動的IDとqueryを除外したroute単位で重複なく把握する。
- イベント名、発火条件、parameter、key event候補を一つの契約として実装する。
- tokenや個人情報をdataLayer、GTM、GA4、Clarity、テストartifactへ出さない。
- 今後のGA4計測計画、実装、レビュー、運用確認へ同じ判断手順を適用できるSkillを作る。

### 対象外

- GA4を課金、認可、利用上限、正式な業務KPIの判定に使うこと。
- Google Measurement Protocol、server-side tagging、広告、remarketing、Google Signals、User-IDを導入すること。
- GA4のためだけにConvex schema、mutation、migration、永続イベントを増やすこと。
- 全クリック、全フォーム入力、全文検索語、店舗別・人物別の行動履歴を収集すること。
- Microsoft Clarityの導入範囲を本計画だけで拡大すること。

## 現在の実装

### 実装済みの境界

- `src/client.tsx`は`VITE_GTM_ID`を使い、初期描画後にGTMを動的ロードする。
- `src/lib/gtm/index.ts`はdataLayer、GTM script、初期化前イベントのbufferを管理する。
- `src/routes/__root.tsx`の`PageViewTracker`はpathname変化ごとに`page_view`を送る。
- `src/lib/gtm/index.ts`には任意のイベント名と`Record<string, unknown>`を受け取る`sendEvent`がある。
- 調査時点で、production codeに`sendEvent`のcallsiteはない。
- `reportWebVitals()`はcallbackなしで呼ばれ、実利用性能を外部へ送っていない。

### 先に閉じる問題

| 問題 | 現在の状態 | 影響 | P0の修正契約 |
|---|---|---|---|
| 動的IDを含むpage path | queryは除外するが、`shopId`、`personId`、`recruitmentId`を含むpathnameを送る | tenant、人物、募集を外部サービス上で識別できる | TanStack Routerのroute templateから有限の`page_key`と安全なlocationを作る |
| GTM側の自動page view | コンテナとGA4 streamはリポジトリ外で未確認 | 有効な場合、手動計測との重複やtoken付き完全URL送信が起こり得る | アプリの手動`page_view`へ一本化し、自動・History計測を停止する |
| 任意payload | `sendEvent(event, Record<string, unknown>)`をexportしている | featureからPII、内部ID、自由入力を渡せる | 閉じたevent unionとeventごとのserializerへ置き換える |
| 初期化前buffer | GTMを3秒から5秒遅延し、先行eventを後からflushする | 短時間離脱を欠測し、Consent方式によっては許可前行動を遡及送信する | Consent確定後にcore tagを初期化し、許可前eventはflushしない |
| 外部設定の状態 | GTM、GA4、Clarity、Consent、環境分離を未確認 | コードだけでは二重計測、データ混入、公開状態を判断できない | read-only棚卸しと公開前checklistを運用手順へ分ける |

## 計測ごとの責務

| 計測先 | 担当する契約 | 正本にしない契約 |
|---|---|---|
| GA4 | 流入、route、CTA、デモ、登録、ログイン、問い合わせ、クライアント上の成功信号 | 課金、認可、業務上の正式な到達数 |
| Convex Analytics | 店舗登録、初回募集、初回提出、初回確定、2回目確定、North Star、継続 | ブラウザ内のクリック順序 |
| RUM | Web Vitals、route別性能、release別性能、欠測率 | conversionと業務成果 |
| Search Console | 検索query、表示回数、CTR、index、canonical | アプリ内の画面遷移 |

GA4はad blocker、同意、通信失敗、別端末、別actorによって欠測する。
管理者が募集し、スタッフが別端末のcapability URLから提出する流れを、同一userまたは同一sessionの連続funnelとして扱わない。

既存Convex Analyticsにあるdurable milestoneをGA4へmirrorする場合も、UI導線の方向性を見る補助信号と明記する。

## 最初に答える問い

P0では、次の二つのfunnelを分けて観測する。

### 匿名訪問者から管理者になるまで

```text
検索・参照元・owned campaign
  -> landing page
  -> 登録またはデモCTA
  -> デモ開始
  -> デモ完了
  -> 登録成功
  -> 初期設定成功
```

### スタッフが希望を提出するまで

```text
スタッフ向け安全なroute key
  -> 入力画面表示
  -> 提出成功
```

スタッフfunnelには`actor_kind = staff_capability`を付け、管理者funnelと同じ利用者として結合しない。
募集、提出、確定の店舗単位到達率はConvex Analyticsで確認する。

Preview、DebugView、Productionでの安全性と重複率を確認してから、`sign_up`など事業上の意味がある少数だけをGA4管理画面で指定する。

## ParameterとURLの契約

### 許可する値

- `actor_kind`: `visitor | manager | staff_capability`
- `page_key`: route catalogに定義した有限値
- `content_type`: `cta | article | demo`
- `content_id`: リポジトリ内で定義したCTA・コンテンツの有限ID
- `method`: `email | google`
- `flow_name`: `demo_flow`など定義済みの有限値
- `step_name`: `recruit | submit | adjust | share`など定義済みの有限値
- `result`: 定義済みの成功結果だけを必要時に使用する
- 件数: 生値が不要な場合は有限bucketへ変換する
- campaign: owned campaignの事前登録値だけを安全な値へ写像する

### 送信しない値

- 氏名、メールアドレス、電話番号、LINE user IDと、そのhash値。
- 問い合わせ本文、検索語、シフト希望、店舗名、組織名などの自由入力。
- Clerk ID、organization ID、shop ID、person ID、staff ID、recruitment ID、notification IDなどの内部ID。
- capability token、manager invite token、OAuth `code`・`state`、authorization header。
- `redirect`、`token`、`code`、`state`、`recruitmentId`を含むraw query。
- raw `location.href`、raw `document.referrer`、raw UTM。
- `user_id`とuser property。

型だけに依存せず、serializerがeventごとの許可keyだけを新しいobjectへ射影する。
Feature codeからunknown keyを渡せても、dataLayerへ残らないruntime契約にする。

### Page viewの生成

`PageViewTracker`はpathnameを直接受け取らない。
TanStack Routerが持つmatched route IDまたは`fullPath`を入力にして、route catalogへ明示的に写像する。

| Route template | `page_key` | 送信しないもの |
|---|---|---|
| `/shops/$shopId` | `shop_detail` | 実際の`shopId` |
| `/users/$personId` | `person_detail` | 実際の`personId` |
| `/users/$personId/shops/$targetShopId` | `person_shop_detail` | 二つの実ID |
| `/shiftboard/$recruitmentId` | `shift_board` | 実際の`recruitmentId` |
| `/manager-invite?token=...` | `manager_invite` | tokenとquery全体 |
| `/shifts/submit?token=...` | `staff_shift_submit` | tokenとquery全体 |
| `/line/callback?code=...&state=...` | `line_callback` | code、state、query全体 |
| `/login?redirect=...` | `login` | redirectとquery全体 |

内部referrerは直前の安全なroute templateから作る。
外部referrerはoriginだけへ縮小するか省略し、raw pathとqueryを送らない。

owned campaignは`utm_source`、`utm_medium`、`utm_campaign`、必要な場合の`utm_content`を専用mapperへ通す。
登録されていない値は`other`へ丸めるか省略し、page locationへraw queryを戻さない。

## Consentと外部タグ

### 推奨案

法務・製品判断が未確定の場合は、Basic Consent Modeを技術上の初期案とする。

- analytics許可前は、Google tagとClarity scriptをロードしない。
- 許可前に起きたpage viewやcustom eventをbufferし、許可後に過去行動としてflushしない。
- 許可後は現在の画面を一度だけpage viewとして送る。
- 拒否または後日のrevoke後はcustom eventを停止し、pending eventを破棄する。
- 広告を導入しない初期段階では、`ad_storage`、`ad_user_data`、`ad_personalization`を`denied`に固定する。
- ClarityはGoogle Consent Modeの設定だけに依存せず、独立したload gateを持つ。

Advanced Consent Modeは拒否中もcookieless pingを送るため、法務・製品がその送信を認めた場合だけ別判断で採用する。

既存の利用規約・プライバシーポリシーへの同意を、Analytics同意へ自動変換しない。
Consent UIが必要になった場合は`ui-architect`を使い、許可、拒否、設定変更、revokeをBehavior Testで検証し、必要な代表状態だけVRTへ追加する。

## Security Lens

- **Actor**：匿名訪問者、Clerkで認証した管理者、bearer capabilityで操作するスタッフ、OAuth callback利用者、GTMコンテナ編集者。
- **Asset**：capability・OAuth credential、個人情報、tenant・人物・募集の識別子、利用行動、計測の完全性。
- **Trust boundary**：browser URL・routerからdataLayer、GTM container、Google Analytics、Clarityへ渡る境界。browserからConvex Analyticsへ渡る業務イベントは別境界とする。
- **Abuse case**：token、code、state、redirectの第三者送信、path IDによるtenant追跡、自由入力の混入、誤設定tag、同意前送信、page view二重送信、欠測するGAを正式KPIとして扱うこと。
- **Server-side enforcement**：GAイベントを認可、課金、業務事実の判定に使わない。durable milestoneは既存の業務mutationとConvex Analyticsを正本にし、Measurement Protocolや新しいpublic APIは追加しない。
- **Rate limit / idempotency**：route遷移と成功状態の変化ごとに一度だけ送る。analyticsのretryを業務処理のretryへ結合せず、analytics失敗で業務成功をrollbackしない。
- **Lifecycle / recovery**：consent revoke、pending破棄、GTM container version rollback、event rename・廃止、GA4の保持・削除方針を運用手順へ持たせる。
- **Logs / PII**：dataLayer、console、Tag Assistant、DebugView、trace、video、screenshot、HTML reportへ禁止値を出さない。
- **Regression test**：route sanitize、exact payload、Consent順序、成功時だけの発火、SPA exactly once、禁止値不在を主担当層で検証する。

P0では`user_id`自体を設定しない。
将来User-IDが必要になった場合は、cross-device分析の必要性、専用random analytics ID、同意、保持、削除、revoke、managerとstaffのactor modelを別のSecurity Lensと承認で確定する。

## 実装アーキテクチャ

### 純粋な計測契約

`src/domains/webMeasurement/`に、React、DOM、router、GTMへ依存しない純粋契約を置く。

- discriminated unionによるイベントcatalog。
- eventごとのexact serializer。
- route templateから`page_key`と安全なlocationを作るcatalog。
- owned campaignのallowlist mapper。
- 禁止値と高cardinalityを持ち込まない有限型。

### GTM transport

`src/lib/gtm/`は業務イベントの意味を持たず、dataLayerとGTM scriptのtransportだけを担当する。

- scriptの重複load防止。
- 初期化状態とConsent状態に応じた送信・破棄。
- analyticsの失敗を利用者の業務操作から隔離。
- featureから任意のevent名とparameterを渡せる公開APIを廃止。
- JavaScript実行後に動的追加している`noscript` fallbackは、役割を再評価して不要なら除去する。

### 外部SDKのlifecycle

Consent状態と外部SDK初期化をReact treeで共有する必要がある場合は、`src/providers/WebMeasurementProvider.tsx`が所有する。

- GTMとClarityのload gate。
- consent default、update、revoke。
- typed measurement API。
- cleanupとpending破棄。

Consent状態を持たない決定になった場合は、薄いProviderを作らず、client entryと既存transportの最小差分で実装する。

### Route tracker

`src/routes/__root.tsx`のtrackerはrouterのmatched route templateを読み、計測契約へ安全なroute情報だけを渡す。
初回hydrationと意味のあるroute遷移で各1件とし、credential queryだけの変化では発火しない。

### Featureの成功境界

初期イベントは次の既存成功境界へ接続する。

- 問い合わせ：`useContactFormController`で`onSubmit`成功後。
- 登録・ログイン：Clerk sessionのfinalize完了後、`window.location.assign`より前。
- 初期設定：`setupShopAndManager`成功後。
- デモ：各操作が実際に状態を進めた時。直接step移動は除く。
- 募集：`createRecruitment`成功後（P1）。
- スタッフ提出：提出mutation成功後、navigate前（P1）。
- 確定：通常のconfirm mutation成功後。再送と`no_changes`は除く（P1）。

componentへ`gtag`や`dataLayer.push`を直接埋め込まない。

7. リポジトリ実装、GTM設定、GA4設定、Production証跡を分けて報告する。

## 実装フェーズ

### Phase 0: 外部設定のread-only棚卸し

GTM container exportまたはPreviewとGA4 stream設定を確認する。
この段階ではpublishしない。

確認対象は次のとおりとする。

- Google tagと送信先Measurement ID。
- 初回自動page viewと`send_page_view`。
- Enhanced Measurementのbrowser history。
- History Change trigger、All Clicks、広い正規表現trigger。
- Microsoft Clarityのload条件とmasking。
- Consent default、update、Consent Initialization。
- Google Signals、Ads連携、User-ID、cross-domain。
- data retention、data redaction、internal traffic、developer traffic。
- develop、preview、productionのcontainerまたはproperty分離。
- Search Consoleとのlink状態。

完了条件は、外部設定の現在値、変更予定、公開対象、rollback用container versionを`doc/manual/ga4-gtm.md`へ記録できることとする。

- `demo-ux`の固定イベント名を意味上のcheckpointへ整理する。
- ルート`AGENTS.md`、`doc/INDEX.md`、project mapへ入口だけを追加する。
- 本計画を`doc/plans/INDEX.md`の`Proposed`へ登録する。

完了条件は、Skillの静的検証とForward testが通り、Rule、Skill、TypeScript、Manualの正本が重複していないこととする。

### Phase 2: 安全な計測core

- event catalog、exact serializer、route catalog、campaign mapperを実装する。
- `src/lib/gtm/`をtransportへ限定する。
- raw URL、generic event name、generic parameterをfeature境界から除く。
- Consent方式に合わせてGTM初期化とbufferを変更する。
- analytics失敗が業務成功へ影響しない契約を固定する。

完了条件は、禁止値をfeatureから表現できず、runtime serializerも余分なkeyをdataLayerへ残さないこととする。

### Phase 3: SPA page viewの一本化

- matched route templateから安全な`page_view`を送る。
- 初回hydrationとsemantic navigationでexactly oneを保証する。
- search credentialだけの変化では送信しない。
- GTMの初回自動page view、Enhanced Measurement History、History Change triggerを停止する。
- 全GA tagへ安全なlocationとreferrerを明示する。
- data redactionに`token`、`code`、`state`、`redirect`、`recruitmentId`を追加する。

Data redactionは防御の補助に使い、raw URLを送らないアプリ側の契約を主防御にする。

完了条件は、PreviewとDebugViewで各画面遷移が1件、禁止値が0件であることとする。

### Phase 4: P0イベントの接続

- CTA、デモ開始・完了、登録、ログイン、問い合わせ、初期設定を既存成功境界へ接続する。
- validation失敗、API失敗、session確立失敗では送らない。
- 連打、StrictMode、二重callbackでも一度だけ送る。
- event送信失敗では画面遷移と業務成功を止めない。

完了条件は、各featureの主担当テストで失敗時0件、成功時1件、二重操作時1件が確認できることとする。

### Phase 5: 外部設定とProduction確認

- 明示的なCustom Event triggerとGA4 Event tagを設定する。
- Google tagとGA4 eventはGTMのnative templateを使い、Custom HTMLで配信しない。
- GTM Preview、Tag Assistant、GA4 DebugViewでevent名、parameter、件数、Consent順序を確認する。
- ユーザー承認後にcontainerとproperty設定を公開する。
- Productionで安全なeventだけが観測されることを確認する。

リポジトリ実装済み、container・property公開済み、Production観測済みを同じ状態として報告しない。

### Phase 6: P1とkey event

P0データで改善判断に必要な分解が不足すると確認できた場合だけ、demo step、募集、提出、確定、Web Vitalsを追加する。
品質確認後、`sign_up`など少数をkey eventへ指定し、`page_view`と全CTAをkey eventにはしない。

Search Console link、internal traffic、bot除外、Exploration、dashboard、event rename・廃止もP1で整備する。

## Release gate

| 状態 | 必要な証跡 | この状態だけでは証明しないもの |
|---|---|---|
| リポジトリ実装済み | code、test、Skill、Rule、Feature Doc、Manual | GTM・GA4の公開状態 |
| container・property設定済み | container version、Preview、DebugView、設定記録 | Production利用者からの実event |
| Production観測済み | 同一revision、Consent状態別のsafe event、重複なし、禁止値なし | 正式な業務KPIの完全性 |

外部公開時は、変更前のGTM container versionをrollback先として記録する。
異常があれば新規event tagを停止し、アプリの業務処理は継続できる状態を保つ。

## 受入条件

- `page_view`は初回表示と意味のあるSPA遷移で各1件だけ送られる。
- query、hash、動的ID、token、code、state、redirect、内部ID、PII、自由入力がdataLayerへ含まれない。
- featureから任意event名や任意parameterを送信できない。
- event payloadはeventごとのexact allowlistへ射影される。
- 失敗した業務処理はイベント0件、成功した業務処理は1件、二重操作も1件になる。
- analytics失敗でmutation結果、画面遷移、利用者向け成功状態が失われない。
- Basic Consent Modeを採用する場合、許可前のGoogle・Clarity requestと遡及flushが0件になる。
- GTM PreviewとGA4 DebugViewでevent名、parameter、件数、Consent順序を確認できる。
- `page_view`や全CTAをkey eventへ指定していない。
- GA4とConvex Analyticsの責務がRule、Skill、Feature Doc、Manualで矛盾しない。
- リポジトリ実装、外部設定公開、Production観測を別々に報告できる。
- 既存の未コミット変更を上書き、削除、stageしていない。

# ログイン方法とシフト連絡先の分離 実装計画

作成日: 2026-08-04  
状態: rollout  
対象: 初回セットアップ、ユーザー詳細、ログイン設定、Clerk認証方法、管理者通知、管理者招待  
置換元: [管理者メールアドレス変更とClerk同期](2026-08-03_管理者メールアドレス変更_実装計画.md)

> 本計画は、合意済みの完成形を実装に落とすための計画である。  
> 旧計画で実装した「Clerk primary emailと全所属のメールを一致させ、以前のメールを削除する」フローは撤去対象とする。

## 1. 目的

利用者が「どのメールが本物か」を意識しなくて済むように、画面の文脈ごとに扱う対象を明確にする。

- サインアップとログイン画面は「シフトリに入る方法」を扱う。
- スタッフ詳細と初回セットアップは「そのグループで使うシフト連絡先メールアドレス」を扱う。
- 請求先は「そのグループの請求連絡先」とし、上記2つから独立させる。

「ログイン用メール」と「通知用メール」を同じ画面に並べて管理するUIは作らない。  
それぞれを「ログイン方法」と「シフト連絡先メールアドレス」として、利用者がいま行っている作業に必要な言葉だけを見せる。

## 2. 完成時の利用者体験

### 2.1 新規登録と初回セットアップ

新規登録は現状どおり、Googleまたはメールアドレスとパスワードで行う。  
ここで登録するメールアドレスはClerkのログイン方法である。

ログイン後の初回セットアップでは、入力項目を残したまま、次の文言へ変更する。

```text
あなたの情報

管理者として表示する名前と、
シフト連絡先メールアドレスを登録します。

シフト連絡先メールアドレス
[　notify@example.com　]

ご自身のシフトのお知らせや確認・再発行リンク、
管理者向けの連絡を送ります。
最初の請求先にも設定され、請求先は後からグループ設定で変更できます。
```

初期値は、既存`getCurrentUser.email`にある、新規user作成時のClerk identity由来のbootstrap snapshotを候補として入れる。  
SetupModalからliveな`useUser()`へ新しく依存せず、この値はあくまで最初の入力候補とする。  
利用者はその場で別の連絡先に変更でき、以後はClerkのメールに自動追従しない。

### 2.2 ユーザー詳細

アカウント連携の有無や、本人・他者の違いにかかわらず、権限を持つ管理者は同じフォームでシフト連絡先を変更できる。

```text
シフト連絡先メールアドレス
[　notify@yahoo.co.jp　]

このグループのすべての店舗で、
シフト通知やシフトリからの連絡に使用します。
```

利用者が自分自身の情報を編集している場合だけ、次の注意書きを表示する。

```text
ここで変更するのは、このグループで使う連絡先です。
ログイン方法は変わりません。
ログインに使うメールアドレスやGoogle連携は、
画面右上の「ログイン設定」から変更できます。
```

他の人を編集しているときは、この注意書きを表示しない。  
画面右上のログイン設定は、編集対象ではなく操作中の利用者自身の設定だからである。

### 2.3 ヘッダーとログイン設定

ヘッダー右上のユーザーメニューに、全認証済み利用者が使える「ログイン設定」を追加する。  
現在、利用者名の下にラベルなしで表示しているClerk primary emailは削除する。

```text
山田 太郎
──────────
グループ設定
ログイン設定
使い方・ヘルプ
お問い合わせ
ログアウト
```

遷移先は、グループや店舗に依存しない本人専用の`/account/security`とする。  
メニューは「ログイン設定」、ページ見出しは「ログイン方法とセキュリティ」とする。

ページを既存`_auth`レイアウトに置くだけでは、現行`AuthGuard`の店舗一覧取得、`?shop=`正規化、無効店舗blockに依存したままになる。  
`/account/security`は`requiresShopContext: false`相当の明示的なmodeで、認証、削除済みアカウント判定などの共通契約だけを維持し、店舗取得、selected shop解決、invalid shopの全体blockを行わない。  
メニュー遷移とOAuth帰還先はshop searchを引き継がず、`?shop=<invalid>`付きの直接アクセスもsearchを破棄してログイン設定を開けるようにする。

```text
ログイン方法とセキュリティ

シフトリへログインする方法を管理します。
ここで変更しても、シフト連絡先メールアドレスは変わりません。

┌ Google ──────────────────┐
│ g••••@gmail.com       接続済み     │
│                                  [解除] │
└──────────────────┘

┌ メールアドレスとパスワード ────┐
│ y••••@yahoo.co.jp      設定済み     │
│ [ログインに使うメールを変更]       │
│ [パスワードを変更]                   │
└──────────────────┘
```

Clerk内部では複数のverified EmailAddressを保持し得るが、製品UIではprimary・secondaryという用語を使わない。  
各ログイン方法の中で、利用できるアドレスをマスクして表示する。

パスワードログインに使えるEmailAddressが複数あると実験で確定した場合は、特定の1件を「ログインメール」として偽らず、利用可能なアドレスをすべてマスク表示する。  
どのアドレスが利用できるか判定できない状態では、「パスワード設定済み」だけを表示し、EmailAddressの削除操作を出さない。

自由にメールを増やす「追加・整理」は主操作にしない。  
利用者には「ログインに使うメールを設定・変更」として見せ、内部で安全に新しいEmailAddressを追加・確認してから、以前のアドレスをどうするかを別に判断する。

### 2.4 ログイン画面

ログイン画面は「Googleでログイン」と「メールアドレスとパスワードでログイン」の2つの方法として整理する。  
現在の障害告知「メールアドレス変更時は旧メールアドレスでログインしてください」は削除する。

メール入力のラベルまたは補足で、ログイン設定に登録済みのアドレスを入力することを伝える。  
パスワード再設定画面も同じ用語にそろえる。

## 3. データと責務の境界

| データ | 役割 | スコープ | 書き込み契約 |
|---|---|---|---|
| Clerk UserのEmailAddress、パスワード、ExternalAccount | ログイン方法の正本 | 利用者全体 | 本人が`/account/security`または認証フローで変更 |
| `organizationPeople.email` | シフト・業務連絡先の正本 | グループ単位 | 同じグループの権限を持つ管理者が変更 |
| `staffs.email` | 人物の連絡先の店舗projection | 店舗単位 | personの変更と同じtransactionで、同じグループの有効staffへ反映 |
| `users.email` | 初期値snapshotとlegacy fallback | 利用者単位 | 新規userのbootstrapまたは最初のsetupで設定し、通常の連絡先変更やClerk変更では同期しない |
| `organizations.billingEmail` | 請求連絡先の正本 | グループ単位 | 初回はシフト連絡先で初期化し、以後はグループ設定だけで変更 |
| `organizationInvitations.email` | 発行時の配送先snapshot | 招待単位 | 招待発行時に固定し、受諾時に現在のpersonと再照合 |

次を不変条件とする。

- Clerkのメールと`users.email`、`organizationPeople.email`が異なる状態は正常である。
- あるグループの連絡先変更は、同じuserが所属する別グループへ波及しない。
- 有効な`organizationPeople.email`とそのpersonへ紐づく未削除`staffs.email`は、同じ正規化値を持つ。
- シフト連絡先の変更は、`users.email`、Clerk、`organizations.billingEmail`を書き換えない。
- ログイン方法の変更は、Convexのperson、staff、billingを書き換えない。
- 少なくとも1つの検証済みログイン方法を常に残す。
- 送信済み通知、完了済み招待、過去auditのメールsnapshotは書き換えない。

## 4. Clerkの成立性実験

カスタムUIの実装前に、現在固定している`@clerk/react 6.12.5`と対象Clerk development instanceで実験する。  
実験結果が未確定のまま、パスワード削除、Google解除、EmailAddress削除を公開しない。

### 4.1 実験方法

開発環境だけでClerk標準の`<UserProfile />`を一時的にmountし、Clerkが提供する標準動作を比較対象にする。  
標準UIは氏名変更やアカウント削除も表示し得るため、本番へ配信せず、最終コードから削除する。

実験前にClerk development instanceで次を確認し、本番相当instanceで同じ設定という証跡を`ENV-CLERK-02`に残す。

- Google social connectionが対象environmentで有効である。
- メールアドレスとパスワードによるsign-inと、email codeによるEmailAddress verificationが有効である。
- OAuth account-linkingの設定が想定契約と一致する。
- developmentとproductionの許可redirectに`/account/security`を含め、他originへの任意redirectを許可しない。
- reverificationがemail追加、パスワード変更、ExternalAccount追加・削除で要求される。

実験用Clerk Userは次の4種類を用意する。

| ケース | 初期状態 |
|---|---|
| A | Googleのみ |
| B | メールアドレスとパスワードのみ |
| C | 同じGmailでGoogleとパスワードの両方 |
| D | GoogleはGmail、メールアドレスとパスワードはYahoo |

実験で次を確定する。

1. GoogleのみのUserに、サインイン中の`User.updatePassword()`で初回パスワードを設定できるか。
2. 複数のverified EmailAddressがあるUserで、どのアドレスがパスワードログインに使えるか。
3. 新しいverified EmailAddressの追加だけでログイン可能になるか、内部的なprimary変更が必要か。
4. `User.createExternalAccount({ strategy: "oauth_google" })`で、同じメールのGoogleを現在のUserへ連携できるか。
5. 現在のUserと異なるメールのGoogleを連携する際、先にGoogle側メールの追加・確認が必要か。
6. 同じGoogle providerのExternalAccountを1つのClerk Userへ複数接続できるか。
7. Google、パスワード、EmailAddressの各削除で、最後のログイン方法をClerk serverが拒否するか。
8. GoogleにlinkedなEmailAddress、primaryかつunlinkedなEmailAddress、primaryではないunlinked EmailAddressの各削除可否とerror code。
9. `useReverification()`の成功、キャンセル、期限切れ後に、Clerk resourceがどの状態になるか。
10. Google連携の成功、キャンセル、provider error後に同じページへ戻り、`user.reload()`で収束できるか。
11. パスワード変更時の他session無効化と、現在sessionの維持。
12. 2つのtabから同時に解除を行ったときも、最後のログイン方法が残るか。
13. LINEアプリ内browserからGoogle連携を始めた場合に、既存の外部browser誘導が使えるか。
14. Google-linked Gmail、Yahooのverified EmailAddress、Yahooのperson連絡先という既存トラブル相当の状態を、削除や同期なしで読み込めるか。
15. パスワード設定済みUserへ招待先をverified EmailAddressとして追加した場合、そのアドレスがパスワードログイン識別子になるか。
16. 現在固定しているClerk SDKの`removePassword(params)`が求める引数と、current password入力またはreverificationで成立する条件。

### 4.2 実験ゲート

安全判定はページ全体の一つのflagにせず、操作能力ごとに分ける。

| 操作能力 | 公開の必須条件 | 条件を確認できない場合 |
|---|---|---|
| 同じメールのGoogle連携 | 常に現在のClerk UserへExternalAccountが追加され、OAuth戻りを収束できる | Google連携を非表示にする |
| 異なるメールのGoogle連携 | 別Clerk Userを作らず、必要なEmailAddress確認順序を一意にできる | 異メールのGoogle連携を公開しない。provider選択後まで判定できない場合はGoogle連携全体を閉じる |
| メールとパスワードの設定・変更 | 初回パスワード、利用可能なEmailAddress、primaryの必要性、未確認resourceの再開を説明・検証できる | 新しいemail/password設定を公開しない。既存passwordの変更も別に成立を確認できた場合だけ出す |
| Google解除 | reload後の代替手段判定とClerk serverの最後の方法の削除拒否を確認できる | 解除ボタンを出さない |
| パスワード削除 | `removePassword`の引数、reverification、代替Google、server拒否を確認できる | 削除ボタンを出さない |
| EmailAddress削除 | linked、primary、最後の識別子、複数tab競合の各動作を確認できる | 削除ボタンを出さず、保持を正常状態とする |
| Google再接続 | 現在のExternalAccountの`reauthorize()`またはverification URLから同じaccountを再確認できる | 再接続を出さず、局所errorと再読み込みだけを出す |

安全ゲート不成立時のfallbackは途中releaseを安全に保つための縮退であり、希望する全操作が実現したことにはしない。  
本計画を完了するには各必須条件を満たすか、実験結果に基づくスコープ変更を別途合意する。

本番相当の結果は、`doc/manual/security-validation.md`の`ENV-CLERK-02`を新契約に書き換えて証跡化する。  
個人のメール、確認コード、Clerk User ID、tokenは証跡に残さない。

## 5. ログイン設定の実装契約

### 5.1 状態モデル

Clerk resourceをそのままViewで判定せず、純粋関数で次のViewModelへ変換する。

- `user.passwordEnabled`
- verifiedとunverifiedを含む`user.emailAddresses`と各verification status
- `emailAddress.linkedTo`
- `user.primaryEmailAddressId`
- `user.externalAccounts`内のGoogle accountとverification status

製品UIで扱う代表状態は次のとおりとする。

| 現在の状態 | 表示する主操作 | 解除条件 |
|---|---|---|
| Googleのみ | 「メールアドレスとパスワードを設定」 | Googleは解除不可 |
| メールアドレスとパスワードのみ | 「Googleを連携」「パスワードを変更」 | パスワードは削除不可 |
| Googleとパスワードの両方 | 両方を利用可能と表示 | 代替方法を再取得して確認後だけ解除可 |
| Googleとパスワードのメールが異なる | 2つの正常な方法として表示 | 同上 |
| Googleの再確認が必要 | 「Googleを再接続」 | 利用可能と判定しない |
| 未確認EmailAddressが残っている | 「メール確認を続ける」とコード再送 | パスワードログイン可能と判定しない |
| verified EmailAddressはあるがパスワードなし | 「パスワードを設定」 | EmailAddressを単独のログイン方法と判定しない |
| 利用可能な方法を確認できない | 局所errorと「再読み込み」 | すべての削除操作を無効化 |

カード単位でloading、success、error、reverification待ちを表示する。  
一つの操作の失敗でページ全体や認証後アプリをブロックしない。

### 5.2 Googleを連携する

1. 操作開始直前に`user.reload()`し、現在のExternalAccountを再取得する。
2. `useReverification()`で包んだ`user.createExternalAccount()`を`oauth_google`で呼ぶ。
3. `redirectUrl`は`/account/security`自身とする。
4. Clerkが返す外部verification URLへ遷移する。
5. 戻り後に`user.reload()`し、verifiedなGoogle ExternalAccountが現在のClerk Userへ追加されたことを成功条件とする。

サインイン・サインアップ完了専用の既存`/sso-callback`は流用しない。  
同じメールと異なるメールの差は、前節の実験で確定した手順にコントローラーを分岐させる。

既存のGoogle ExternalAccountがあるがverificationが完了していない場合は、新しいExternalAccountを作らない。  
対象resourceの`reauthorize({ redirectUrl: "/account/security" })`またはそのClerk SDK versionが返す既存のexternal verification URLから再開し、帰還後のreloadで同じaccountがverifiedになったことを成功条件とする。  
キャンセルやprovider errorではresourceを自動削除せず、再接続または再読み込みから収束させる。

### 5.3 Googleを解除する

1. 確認Dialogを開く前と、実行直前の2回`user.reload()`する。
2. verified EmailAddressとパスワードが利用可能であることを再判定する。
3. `useReverification()`で包んだ`externalAccount.destroy()`を呼ぶ。
4. Clerk serverの拒否を最終安全条件とし、拒否時は現在状態を再読み込みする。

代替手段がない場合、操作ボタンはdisabledとし、「先にメールアドレスとパスワードを設定してください」と表示する。

### 5.4 メールアドレスとパスワードを設定・変更する

Googleのみの利用者がYahooなどのメールログインを追加する場合は、次の順で行う。

1. 操作開始前に`user.reload()`し、入力を正規化して同じEmailAddress resourceがあるかを確認する。
2. 同じverified resourceがあれば再利用し、unverified resourceがあれば新規作成せずそのresourceの確認を再開する。存在しない場合だけ、`useReverification()`で包んだ`user.createEmailAddress()`で作る。
3. unverified resourceで`prepareVerification({ strategy: "email_code" })`を呼び、確認コードを新規送信または再送する。
4. `attemptVerification()`後にresourceを再取得し、verifiedであることを確認する。
5. 実験結果に応じ、パスワードログインに必要な場合だけ内部的なprimaryを変更する。
6. `useReverification()`で包んだ`user.updatePassword()`で初回パスワードを設定する。
7. `user.reload()`後に、verified EmailAddressと`passwordEnabled`の両方が成立したことを完了条件とする。

メール確認後にパスワード設定だけ失敗した場合は、検証済みメールが追加された状態を画面に出し、「パスワードを設定」から再開できるようにする。  
ロールバックのために新しいEmailAddressを自動削除しない。

メール確認前にDialogを閉じたり画面を再読み込んだりした場合も、unverified resourceをClerkから読み戻し、「メール確認を続ける」から再送・再開する。  
確認コードや独自のresume stateはstorageへ保存しない。

パスワード変更は、現在のパスワードの有無で「設定」と「変更」の入力を分ける。  
他sessionを無効化する場合は、実行前に利用者へ明示する。

### 5.5 パスワードとEmailAddressを削除する

パスワード削除は、verifiedなGoogleが利用可能なときだけ表示する。  
実行直前にresourceを再取得し、実験で確定した`removePassword(params)`の引数とcurrent password入力条件を使う。  
引数objectが必要なinstalled typeに対し、引数なしの呼び出しを計画しない。

EmailAddress削除はパスワード変更とは分け、利用者が明示した場合だけ行う。

- `linkedTo`にGoogleがあるEmailAddressは削除操作を出さず、「Googleと接続中のため、メールアドレスだけを削除できません」と説明する。
- 代替の利用可能な方法がないEmailAddressは削除できない。
- 対象が`primaryEmailAddressId`の場合は、実験で確定した動作に従う。別のverified EmailAddressへのprimary変更から削除までを安全に収束できなければ、primaryの削除操作は出さない。
- 削除の直前に`user.reload()`し、Clerk serverの拒否を最終条件とする。
- 削除失敗でも、それまでに成功したメール確認やパスワード設定を「変更失敗」として扱わない。
- primary変更後に削除だけ失敗した場合も、新しいprimaryを自動で戻さず、以前のEmailAddressが残っている状態として表示する。
- Google解除後に不要な旧Gmailを削除するかは利用者が別に選ぶ。自動削除しない。

この契約により、`Deleting a linked email address is not allowed`は「メール変更全体の失敗」ではなく、初めから選択不可の状態として説明される。

## 6. シフト連絡先のConvex実装

### 6.1 人物プロフィール更新

`convex/organization/personProfile.ts`の「アカウント連携済みはメール変更不可」分岐を削除する。

変更は次の1 transactionで行う。

1. actorの対象グループに対する管理権限とbusiness write可否を、既存のserver-side policyで確認する。
2. `personId`がactorのグループに属するactive personであることを確認する。
3. グループ内personと各店舗staffのメール重複を既存どおり拒否する。
4. `organizationPeople.email/emailNormalized`を更新する。
5. 同じpersonへ紐づく、同じグループの未削除`staffs.email/emailNormalized`を更新する。
6. 募集中シフトの確認・再発行リンクの追送予約とauditを、連携済みpersonにも適用する。

本人を編集した場合も`users.email`は更新しない。  
氏名の既存同期契約は本計画で変更しない。

legacyのstaff更新経路に`users.email`への逆同期が残る場合も同じ契約へそろえる。  
ただし、依頼と無関係なlegacy経路の大規模な再構成は行わない。

### 6.2 管理者通知の宛先

`convex/_lib/shopManagerRecipients.ts`は、canonicalな`organizationMembers`からuserだけでなくpersonも解決するように変更する。

宛先解決時にorganizationを特定できる業務通知は、原則としてそのorganizationのperson emailを使う。  
例外は、請求専用の`organizations.billingEmail`、Clerkが送る認証・セキュリティ通知、canonical personがないlegacy membershipだけとする。

- canonical管理者の宛先と表示名は`organizationPeople.email/name`を使う。
- `users.email/name`の宛先fallbackは、canonical personを持たないlegacy `shopMembers`に限定する。
- LINE通知先staffは`userId`に加え`organizationPersonId`でも解決し、連携直後のlegacy staffでも取りこぼさない。
- LINE用staffは同じorganization、対象shop、activeかつ未削除、同じ`organizationPersonId`であることを確認する。`staff.userId`がある場合はcanonical userとの一致も必須とする。
- 同じshopとpersonにactive staffが複数ある場合や`userId`が衝突する場合は、任意の1件を選ばずLINEを除外し、person emailへ安全にfallbackする。
- dry-runも実配送と同じperson emailで判定する。
- Outbox配送直前の`person?.email ?? user.email`再検証は維持する。連絡先変更後の旧宛先jobは現行契約どおり停止する。

共通helperの変更により、スタッフ承認依頼、店舗有効化催促、通知失敗リマインダー、シフト確定催促を同じ宛先契約へそろえる。

### 6.3 初回作成と追加グループ

初回セットアップの入力値は、次の初期化に使う。

- `organizationPeople.email`
- 最初の`staffs.email`
- `users.email`のbootstrap snapshot
- `organizations.billingEmail`の初期値

その後の更新経路は分離する。  
フロントの公開引数`managerEmail`をすぐに改名するかは互換性に合わせて判断し、service内では`managerContactEmail`と`initialBillingEmail`の意味を分ける。

2つ目以降のグループ作成では、古い`users.email`を無条件に使わない。  
新frontendは操作元の`sourceShopId`を渡し、serverがactorのcanonical personを検証した上で、そのpersonの名前とシフト連絡先を新グループの初期値にする。  
serverはactorがsource shopのactive memberであることと、shop、organization、person、membershipの整合を確認する。  
検証済みpersonの氏名と連絡先を同じmutation内でsnapshot化し、新organizationのperson、staff、初期billing emailへ同じ値を使う。  
`sourceShopId`は旧frontend互換中はoptionalとし、未指定またはcanonical personがないlegacy状態だけ`users`をfallbackにする。  
使用した経路はメール値なしで検証できるようにし、既存`requestId`の冪等性は保つ。

## 7. 管理者招待の本人確認

招待先メールをログインprimary emailとみなす現在の契約を廃止する。  
ただし、未連携personや外部招待では、招待メールの所有確認を弱めない。

### 7.1 受諾契約

| 招待対象 | 本人確認 | 受諾後の連絡先 |
|---|---|---|
| `targetPersonId`があり、personに現在の`userId`がある | 受諾中の`ctx.user._id`とpersonの`userId`が一致する場合だけ受諾。Clerkのメール一致は不要 | 既存の`organizationPeople.email`を維持 |
| `targetPersonId`があり、personが未連携 | 招待先が現在のClerk Userのverified EmailAddressに含まれることをserverで確認 | 既存の`organizationPeople.email`を維持し、`userId`だけを設定 |
| `targetPersonId`がない外部招待 | 招待先が現在のClerk Userのverified EmailAddressに含まれることをserverで確認 | 招待snapshotのメールでpersonを作成 |

既存JWTの`identity.email`はprimaryの1件しか示さないため、この判定に使わない。  
新frontendの受諾をNode actionに変更し、次の順で処理する。

1. `ctx.auth.getUserIdentity()`のissuer、subject、token identifierを検証する。
2. internal mutationでtoken digest、TTL、rate limit、single-use、reserved seat、対象personの現在状態を確認し、invitation ID、version、token digest、正規化招待先をprepare結果として返す。
3. 既連携targetはuser ID一致で完了し、他のuserに対象情報を開示しない。
4. 未連携・外部招待では、Clerk Backend APIから対象Clerk Userのverified EmailAddress一覧を取得し、正規化した招待先を含むことを確認する。
5. 信頼済みactionからinternal mutationへ、actorの`tokenIdentifier`とClerk subject、invitation ID、version、token digest、正規化招待先をひとまとまりの証明結果として渡す。
6. final mutationはactor、invitation、target person、membership、reserved seat、versionをすべて再読み込みし、prepare結果と一致する場合だけ原子的に受諾する。

rate limitの消費はprepareの1回に寄せ、provider照会後のfinalizeで同じbudgetを二重に消費しない。  
Clerk providerがtimeoutまたは一時失敗した場合は招待を消費せず、retryableな固定statusで返す。  
verified EmailAddressの一覧、生のprovider error、メール値はclient response、log、auditへ出さない。

`convex/accountEmail/provider.ts`のClerk接続、timeout、error分類は、メール同期の責務を外した小さなverified-email providerに改名・一般化し、招待actionから再利用する。  
新しいtable、永続capability、jobは追加しない。

### 7.2 招待先の確認導線

未連携者の招待先をClerkへ追加する操作は、通知先の自動同期ではなく、招待を受ける本人が行う明示的な所有確認とする。  
実験でそのアドレスがログイン識別子にもなると確認した場合は、確認開始前にその事実を表示する。  
受諾後にpersonのシフト連絡先を変更してもClerkは同期せず、Clerk側の追加済みアドレスはログイン設定で別に管理する。

招待先が現在のClerk Userにverified EmailAddressとしてない場合は、「別のアカウントでログイン」ではなく、招待先の所有確認を案内する。

```text
招待先メールアドレスの確認が必要です。
このアカウントに招待先を追加し、
メールで届く確認コードを入力してください。
確認後、このメールアドレスがログインにも使える場合があります。

[招待先メールアドレスを確認]
```

既存のEmailAddress追加・email code確認と同じClerkフローを再利用し、確認後に受諾actionを再実行する。  
メール本文のtokenだけ、またはfrontendの申告だけで未連携personを紐づけない。

受諾では次も維持する。

- 招待後にpersonのシフト連絡先が変わった場合、古い招待は使わず新しい宛先へ再発行する。
- 同じグループに受諾userの別personがある場合はconflictとする。
- 既存userの`users.email`とperson emailをClerk emailで上書きしない。
- 新規userが必要な場合だけ、招待先を`users.email`のbootstrap snapshotにする。
- 旧frontend互換中は既存mutationも残す。既連携targetはuser ID一致で安全に受諾させ、未連携targetはJWTのverified primary emailが招待先と一致する場合だけ受諾させる。
- 旧mutationの`emailMismatch`のDTOは互換中だけ残し、新actionとUIは「招待先の確認が必要」という状態を使う。

## 8. 既存トラブル中ユーザーの救済

次の既存状態は、修復対象ではなく新契約の正常状態とする。

```text
Googleログイン: Gmail
シフト連絡先: Yahoo
Clerk primary: GmailまたはYahoo
Clerkの旧・新EmailAddress: 複数残っていてもよい
```

救済のために、次を行う。

- `AuthGuard`からClerk primaryと`currentUser.email`の一致判定を削除する。
- `AuthGuard`からClerk `useUser()`と「verified primary emailを取得できなければアプリ全体を開かない」判定を削除し、Clerk resourceの詳細はログイン設定内の局所状態として扱う。
- メール不一致画面と旧メール削除復旧画面を削除する。
- `sessionStorage` の`account-email-cleanup-session`は認証後の初回読み込みで削除し、内容を再実行しない。
- 古い`?panel=email`は不正なsearchとして静かに破棄し、通常のユーザー詳細を開く。
- 旧メール削除、Clerk primaryの強制変更、Convex全所属の一括同期を自動再開しない。
- 一括backfillや個別のClerk修正を公開条件にしない。

救済後のログイン設定では、Googleは「接続済み」、YahooはClerkの実状に応じて「パスワード未設定」または「利用可能」と表示する。  
利用者に過去の失敗の後始末を要求せず、必要な設定がある場合だけ次の操作を案内する。

## 9. 旧メール同期機能の廃止

`src/components/features/AccountEmailChange/`と`convex/accountEmail/`は、ログイン方法と全グループ連絡先の同期、旧EmailAddressの削除を一体化している。  
新しいログイン設定のcontrollerとして部分再利用せず、責務ごと置き換える。

削除対象は次のとおりとする。

- `src/components/features/AccountEmailChange/`
- `src/stores/accountEmail.ts`と対応test
- `AccountEmailMismatchRecovery`と`AccountEmailCleanupRecovery`
- UserDetailの`panel=email`、`onOpenEmailChange`、`onAccountEmailFinished`
- `convex/accountEmail/`の同期service、action、mutation、schemaと対応test
- `accountEmailPreflight`と`accountEmailSync`のrate limit設定

`EmailCodeVerificationForm`、`useSingleFlight`、共通のメールvalidation、Clerk error presentationは新フローで責務が一致する範囲だけ再利用する。  
`organization.account_email_synced`のaudit actionは過去データを読めるようにunionへ残し、新規書き込みは停止する。

## 10. 公開順序と互換契約

通常の機能分割ではなく、古いfrontendを開いたままの利用者もログイン不能にしないための安全順序として、次の順序を守る。

### 10.1 実装ゲート

1. Clerk development instanceで第4節の実験を行い、状態モデル、API手順、削除可否を確定する。
2. 確定結果に合わせてLogic Testの入出力を先に書く。
3. 最後のログイン方法を守れない場合は、削除操作をスコープから外してから実装を続行する。

### 10.2 協調リリースA: backendを先に安全側へ閉じる

まずConvexをdeployし、旧clientが新しい旧メール同期を始められない状態を作る。

- 旧`accountEmail.preflight`はClerk変更より前に「画面を再読み込み、ログイン設定を使ってください」と安全に拒否する互換stubにする。
- 旧`syncMyPrimaryEmail`とinternal syncは、全所属を更新せず`unavailable/conflict`で収束する。
- personとstaffのシフト連絡先契約、管理者通知routing、追加グループ初期値、招待受諾actionを有効にする。
- 旧招待受諾mutationは、既連携targetまたはJWTのverified primary email一致に限る安全な互換経路として残す。

この短い期間、古いclientのメール変更画面は継続できず、再読み込みが必要になり得る。  
利用できない旧フローを一時的に残すより、Clerkや全グループのデータを誤って変更しないことを優先する。

すでにpreflight後だったclientはClerk変更後にsync stubで止まる可能性があるが、Convex全所属は更新しない。  
次のfrontend反映後は不一致を正常として読み込み、旧cleanupを自動再開しない。

### 10.3 協調リリースB: 救済とシフト連絡先UI

backend反映直後に、次のfrontendを同じ作業窓で反映する。

- `AuthGuard`の不一致、verified primary email必須、cleanup分岐を外す。
- UserDetailから旧メール変更入口を削除し、新しいシフト連絡先編集へ置き換える。
- 初回セットアップをシフト連絡先の文言へ変更する。
- 古いsearchとsession storageを静かに破棄する。
- ログイン画面の障害告知を削除し、2つのログイン方法を明示する。
- 管理者招待の「メール不一致」を「招待先の所有確認」へ置き換える。

この反映後、ClerkとConvexのメールが異なる人は通常画面へ戻り、シフト連絡先も通常のプロフィールとして変更できる。

### 10.4 リリースC: ログイン設定UI

- `/account/security`とユーザーメニュー導線を追加する。
- 成立性実験と安全ゲートを通過した追加・連携・削除操作だけを有効にする。
- 標準`<UserProfile />`の実験コードが本番buildに含まれないことを確認する。

### 10.5 互換期間の終了

少なくとも1回の本番frontend releaseと監視期間を経過し、旧clientの呼び出しが収束した後に次を行う。

- 互換stubを含む旧`convex/accountEmail/`を削除する。
- 旧rate limitと生成API参照を削除する。
- 招待受諾を新actionへ一本化し、旧mutationの互換分岐と`emailMismatch`のDTOを削除する。
- 追加グループ作成で`sourceShopId`を送らない旧clientが収束したことを確認し、fallbackを残すか別のNarrowで外すかを判断する。
- 旧frontend、store、recovery、Story、testの残存がないことを`rg`で確認する。
- 過去auditのvalidatorだけを残す。

実際のdeploy手順はfrontendとConvexの反映時間を記録し、協調リリースAとBの間隔を最小化する。  
rollbackは各反映を独立して行えるようにするが、旧account email同期APIを再有効化するrollbackは用意しない。

## 12. Migration判定

本計画では、新しいtable、field、validatorのrequired化、既存documentのbulk rewriteを必要としない。  
そのため、新しいConvex migrationとbackfillは追加しない。

根拠は次のとおりである。

- `organizationPeople.email/emailNormalized`はすでにrequiredである。
- `staffs.email/emailNormalized`はすでにpersonの店舗projectionとして存在する。
- `organizations.billingEmail`はすでに独立fieldである。
- 招待には`targetPersonId`と配送先snapshotがある。
- `users.email`を削除、rename、optional化しない。

既存のClerk、`users`、personのメールが異なるデータは、書き換えずそのまま有効化する。  
公開前に読み取り専用の検証で、active personとactive staffのprojection不一致だけを確認し、既存不整合が見つかった場合は本計画の実装に混ぜず、別のmigration判定へ分ける。

## 13. Security Lens

### 13.1 Actor、asset、trust boundary

| 分類 | 内容 |
|---|---|
| Actor | ログイン中の本人、同じグループの管理者、招待受諾者、Clerk、メール配送provider |
| Asset | Clerk Userへのアクセス、グループ管理権限、シフト・管理者通知の宛先、メールという個人情報 |
| Trust boundary | browserとClerk、browserとConvex public API、Convex Node actionとClerk Backend API、tokenを含むメールと招待受諾 |

### 13.2 Abuse caseとserver-side enforcement

| Abuse case | 防止契約 | 主な検証層 |
|---|---|---|
| 別グループのperson連絡先をID直接指定で更新 | actorのorganizationとpersonのorganizationをserverで照合 | Convex Function Test |
| 他のユーザーのログイン方法を変更 | `/account/security`はClerkのcurrent User resourceだけを操作し、target user IDを受けない | Frontend UnitとClerk実環境 |
| 最後のログイン方法を複数tabで削除 | 直前reload、UI再判定、reverification、Clerk server拒否の4条件。server拒否が不十分なら削除を公開しない | Logic Test、Frontend Unit、Clerk canary |
| 招待tokenの転送や漏えいで別人が管理者化 | 既連携targetはuser ID一致、未連携targetはClerk verified email所有。token digest、TTL、single-use、rate limitも維持 | Convex FunctionとScenario Test |
| OAuth callbackをsign-inとaccount linkingで混同 | `createExternalAccount`とaccount page専用redirectを使い、sign-inの`/sso-callback`を流用しない | Frontend UnitとClerk canary |
| 連絡先変更が別グループや請求先へ波及 | personのorganization範囲だけをtransaction更新し、`users`とbillingをpatchしない | Convex Function Test |
| メール、確認コード、provider payloadがlogやauditへ残る | UIはマスク表示、errorはcodeへ変換、auditにはactionとIDだけを保存 | コードレビュー、テスト、実環境証跡 |

### 13.3 外部失敗と保存

- Clerkが一時的に利用できない場合、ログイン設定と未連携招待だけを局所errorにし、シフト管理全体を停止しない。
- ClerkのメールやExternalAccountをConvexへ複製せず、新しいsession・recovery tableも作らない。
- 確認コードはbrowser stateの一時入力として扱い、storage、log、auditに残さない。
- Clerkの操作auditと既存provider logを運用証跡に使い、メール値自体をアプリ独自で追加保存しない。

## 16. Rollbackと運用

ログイン設定で問題が起きた場合は、メニュー導線または破壊操作を無効化する。  
既存のGoogleログインとemail/passwordログインは維持する。

シフト連絡先や通知routingで問題が起き、対象実装をrollbackする場合も、次の旧契約には戻さない。

- ClerkとConvexのメール不一致でアプリ全体をブロックする。
- Clerk primaryを全グループのperson・staffへ強制同期する。
- 変更完了条件として以前のEmailAddressを強制削除する。

管理者招待のClerk provider確認に問題がある場合は、既存の管理者招待feature flagで新規受諾を停止し、メール所有確認を省略して続行しない。

新しい監視tableや汎用telemetry基盤は作らない。  
協調リリースとcanary中に、既存のClerk Dashboardのaudit、Convex function log、Outbox queryで確認できる結果だけをsnapshotとして`doc/manual/release-status.md`の証跡先へ記録する。  
旧API stubと招待provider失敗に観測が必要な場合は、`account_email_retired`、`organization_invitation_provider_unavailable`などの固定event codeだけをbest-effortでlogに残し、user ID、invitation ID、token digest、メール、provider payloadを含めない。

主に確認するのは次である。

- Clerkで実行したログイン方法変更と固定化されたprovider error code
- 旧account email APIの拒否logが監視期間の後半で収束したか
- 招待受諾の`provider_unavailable`と`conflict`に新しい急増がないか
- 管理者通知の古い宛先に対する`recipient_inactive`と新しい宛先への配送結果

# スタッフ詳細モーダル設計

**ステータス: 設計検討（実装未着手）**

スタッフ一覧の行メニューが増え、操作の見通しが悪くなっている。

この設計では、スタッフ一覧の三点リーダーメニューを廃止し、スタッフ行の押下でスタッフ詳細モーダルを開く。

利用者の多くがスマホで操作する前提に合わせ、SPを主設計にする。
PCでも同じ情報構造を使い、実装と保守の分岐を増やさない。

## 1. 結論

スタッフ詳細は、**全画面モーダル + 上部タブ** とする。

タブは `基本`、`通知`、`LINE連携`、`設定` の4つに固定する。

パスワード項目は存在しないため置かない。

削除は独立タブにせず、`設定` タブの末尾に `危険な操作` として置く。

```text
+-------------------------------+
| スタッフ詳細              [×] |
|-------------------------------|
| y  yn1323                     |
|    管理者  LINE未連携         |
|    シフト対象                 |
|-------------------------------|
| 基本 | 通知 | LINE連携 | 設定 |
|-------------------------------|
| 選択中タブの中身              |
+-------------------------------+
```

## 2. 解決したい問題

現状のスタッフ行メニューには、次の操作が同じ階層で並んでいる。

- 編集
- 現在募集中のシフトを送る
- 現在の確定シフトを送る
- LINE連携リンクを表示
- LINE連携リンクをメールで送る
- シフト対象外にする、またはシフト対象に戻す
- 削除

これらは同じ種類の操作ではない。
基本情報の編集、通知の再送、LINE連携の案内、シフト対象設定、削除が混在している。

そのため、操作数が増えるほどメニュー全体が重くなり、利用者は「何をどこで触ればよいか」を判断しにくくなる。

今回の変更では、操作をスタッフ単位の詳細画面に集約し、タブで作業の文脈を分ける。

## 3. 対象範囲

対象はダッシュボードのスタッフ一覧と、スタッフ1人に対する操作導線である。

含めるもの:

- スタッフ行の押下でスタッフ詳細モーダルを開く
- スタッフ行の三点リーダーメニューを廃止する
- 基本情報編集を `基本` タブへ移す
- 募集中シフト通知と確定シフト通知を `通知` タブへ移す
- LINE連携リンク表示とLINE連携リンクメール送信を `LINE連携` タブへ移す
- シフト対象切替と削除を `設定` タブへ移す

含めないもの:

- 新しい認証方式
- スタッフ用パスワード変更
- 通知履歴の新設
- 対象シフトを個別選択して送る機能
- LINE連携トークンや通知再送APIの仕様変更

## 4. スタッフ行

スタッフ行は、詳細を開く入口として扱う。

三点リーダーは置かない。
右端には詳細へ進むことが分かるアイコンを置く。

```text
+------------------------------------------------+
| y  yn1323        管理者  LINE未連携       >    |
|    yn1323@gmail.com                            |
+------------------------------------------------+
```

行全体を押下可能にする。
ただし、行内のテキストやバッジが押下対象であることを邪魔しないよう、hover、focus、pressedの状態を行単位で出す。

行の情報は、スタッフ名、メールアドレス、管理者状態、LINE連携状態、シフト対象状態を表示する。

メールアドレスが空の場合は、メール欄の表示方針を別途メール任意化設計に合わせる。
この設計では、現行の `staff.email` をそのまま表示対象とする。

## 5. スタッフ詳細モーダル

SPでは全画面モーダルにする。
PCでは中央に大きめのDialogとして表示し、内部構造はSPと同じにする。

モーダル上部には、常にスタッフの概要を表示する。
タブを切り替えても、対象スタッフを見失わないようにするためである。

```text
+-------------------------------+
| スタッフ詳細              [×] |
|-------------------------------|
| y  yn1323                     |
|    管理者  LINE未連携         |
|    シフト対象                 |
|    yn1323@gmail.com           |
|-------------------------------|
| 基本 | 通知 | LINE連携 | 設定 |
|-------------------------------|
| 選択中タブの中身              |
+-------------------------------+
```

タブは横スクロールを許容する。
ただし、4タブを基本とし、折り返し表示はしない。

タブのラベルは短く保つ。
`LINE` ではなく `LINE連携` とする。
スタッフに何をする場所かが分かるためである。

## 6. `基本` タブ

`基本` タブには、スタッフ名とメールアドレスの編集を置く。

パスワード項目は置かない。
スタッフはパスワードを持たないためである。

```text
基本

名前
[ yn1323                    ]

メールアドレス
[ yn1323@gmail.com          ]

[変更を保存]
```

保存ボタンは、このタブ内の主操作にする。

メールアドレスを変更した場合の通知追送は、既存の `api.staff.mutations.editStaff` の挙動に従う。
UIでは「メール変更時に何が送られるか」を過剰に説明しない。

## 7. `通知` タブ

`通知` タブでは、スタッフに送る対象シフトを事前に見せる。

対象シフトは、ダッシュボードで取得済みの募集情報から表示する。
このタブ内では、対象シフトを個別選択させない。
既存APIが送る対象を利用者に見せることが目的である。

```text
通知

対象とするシフト

募集中
+-----------------------------+
| 7/18 〜 7/25        募集中  |
| 締切 7/16                  |
+-----------------------------+
[募集中のシフトを送る]

確定シフト
+-----------------------------+
| 7/1 〜 7/15        確定済み |
| 現在の期間に含まれます      |
+-----------------------------+
[確定シフトを送る]

通常は自動で送っています。
届いていない場合だけ、ここからもう一度送れます。
```

募集中シフトは、既存のダッシュボード募集データのうち、現在送れる募集を表示する。
実装では `getDashboardRecruitmentGroupKey(...) === "collecting"` に相当する募集を基準にする。

確定シフトは、既存の `currentRecruitments` を表示する。
現在期間に含まれる確定済みシフトだけを対象にする。

対象がない場合は、ボタンを無効化し、空状態を表示する。

```text
募集中
送信できる募集中シフトはありません。

確定シフト
送信できる現在の確定シフトはありません。
```

シフト対象外スタッフには、募集通知と確定シフト通知を送れない。
この場合は、通知タブ上部に理由を出す。

```text
このスタッフはシフト対象外です。
シフト表、提出依頼、確定シフト通知の対象から外れています。
```

## 8. `LINE連携` タブ

`LINE連携` タブでは、連携状態、案内文、連携リンク操作をまとめる。

未連携の場合は、スタッフ本人に何をしてもらうかを説明する。

```text
LINE連携

LINE未連携

スタッフ本人に連携リンクを開いてもらうと、
次回からシフト通知がLINEに届きます。

[LINE連携リンクを表示]
[メールでLINE連携リンクを送る]

連携リンクを表示した場合は、
QRコードをスマホで読み取ってもらうか、
リンクをコピーして共有してください。
```

連携済みの場合は、ボタンの主役を消し、状態確認を中心にする。

```text
LINE連携

LINE連携済み

このスタッフには、次回からシフト通知がLINEに届きます。
```

`isLineLinked === true` かつ `isLineFollowing === true` の場合を `LINE連携済み` と表示する。

`isLineLinked === true` かつ `isLineFollowing === false` の場合は、LINEアカウントは紐づいているが受信できない状態として扱う。

```text
LINE連携

LINEで受け取れません

LINE連携はありますが、スタッフが友だち追加を解除している可能性があります。
もう一度LINE連携リンクを案内してください。

[LINE連携リンクを表示]
[メールでLINE連携リンクを送る]
```

メールアドレスがない場合は、メール送信ボタンを無効化する。
この場合でも、連携リンク表示は使える。

```text
メールアドレスがないため、メールでは送れません。
QRコードかリンクを直接共有してください。
```

## 9. `設定` タブ

`設定` タブには、シフト対象トグルと削除を置く。

シフト対象はトグルで表示する。
トグルの近くに、ONとOFFの意味を短く説明する。

```text
設定

シフト対象
[ ON ] シフト対象にする

ONのスタッフは、シフト表、提出依頼、確定シフト通知の対象になります。
OFFにすると、今後のシフト作成やシフト関連通知から外れます。
LINE連携など、シフト以外の案内には使えます。
```

対象外にする操作は、既存の `api.staff.mutations.setShiftExclusion` を使う。
対象外にした場合、既存のシフト用セッションとマジックリンクは失効する。
この仕様は `doc/features/shift-exclusion.md` に従う。

削除は `危険な操作` として、設定タブの末尾に置く。

```text
危険な操作

[このスタッフを削除]
```

管理者本人のスタッフ行では、削除ボタンを無効化する。
サーバー側でも既存の `deleteStaff` ガードを維持する。

## 10. 確認操作

モーダルの中で別モーダルを重ねると、SPで現在地を見失いやすい。

そのため、通知送信、LINE連携リンクのメール送信、スタッフ削除は、できるだけ同じタブ内のインライン確認に寄せる。

```text
募集中のシフトを送る

yn1323さんに、現在送れる募集中シフトを送ります。
通常はシフト作成時に自動で送っています。

[やめる] [送る]
```

削除だけは破壊的操作であるため、既存Dialogの利用を残してもよい。
ただし、実装時にモーダル重ねが操作しづらい場合は、設定タブ内の確認パネルにする。

```text
このスタッフを削除しますか？

削除すると元に戻せません。
既存のシフト用リンクやLINE連携も使えなくなります。

[やめる] [このスタッフを削除]
```

## 11. データとAPI

新しいConvex public APIは追加しない方針とする。

既存API:

| 操作 | API |
|---|---|
| 基本情報の保存 | `api.staff.mutations.editStaff` |
| 募集中シフト通知 | `api.staff.mutations.sendOpenRecruitmentNotifications` |
| 現在の確定シフト通知 | `api.staff.mutations.sendCurrentShiftNotification` |
| LINE連携リンク表示 | `api.line.mutations.generateLinkToken` |
| LINE連携リンクのメール送信 | `api.line.mutations.sendInvite` |
| シフト対象切替 | `api.staff.mutations.setShiftExclusion` |
| スタッフ削除 | `api.staff.mutations.deleteStaff` |

スタッフ詳細表示に使うデータ:

| 表示 | 取得元 |
|---|---|
| スタッフ名、メールアドレス | `Staff` |
| 管理者状態 | `Staff.isManager` |
| LINE連携状態 | `Staff.isLineLinked`、`Staff.isLineFollowing` |
| シフト対象状態 | `Staff.excludedFromShift` |
| 募集中シフト | ダッシュボードの募集一覧 |
| 現在の確定シフト | `currentRecruitments` |

通知タブの表示対象シフトは、フロントで既存Dashboardデータから組み立てる。
ただし、送信可否の最終判定は既存mutationを正とする。
フロントの表示制御を認可や送信条件の根拠にしない。

## 12. Security Lens

Actor: Clerk認証済みの店舗管理者。

Asset: スタッフの名前、メールアドレス、LINE連携トークン、シフト通知、シフト用セッション、スタッフ削除状態。

Trust boundary: `staffId`、通知送信、LINE連携リンク発行、シフト対象切替、削除操作はすべてクライアントからConvex public mutationへ渡る。

Abuse case: 他店舗スタッフへの通知送信、他店舗スタッフのLINE連携リンク発行、削除済みスタッフへの操作、対象外スタッフへのシフト通知、短時間の連続クリックによる通知の過剰予約。

Server-side check: 既存の `managerMutation` と各mutation内の `staff.shopId === ctx.shop._id`、`isDeleted` チェックを正とする。

Rate limit / idempotency: 既存の通知再送rate limit、LINE招待rate limit、フロントの `useSingleFlight` を維持する。

Logs / PII: メールアドレス、LINE連携トークン、認可URLを不要にログ出力しない。

Regression test: 他店舗スタッフ、削除済みスタッフ、対象外スタッフ、LINE未連携スタッフへの操作可否は既存Convex Function Testを維持する。
UI変更はStorybook Behavior Testで代表状態を検証する。

## 13. 実装手順

1. `StaffRow` からChakra `Menu` を削除し、行押下で詳細を開く。
2. 新規 `StaffDetailDialog` を追加する。
3. `StaffDetailDialog` に `基本`、`通知`、`LINE連携`、`設定` のタブを実装する。
4. 既存の編集Dialog、LINE QR Dialog、LINE招待確認Dialog、通知確認Dialogの中身を、必要に応じてタブ内コンポーネントへ移す。
5. `DashboardContent` の状態管理を `selectedStaff` 中心に整理する。
6. 通知タブ用に、対象シフト表示を組み立てる純粋関数を必要なら追加する。
7. StaffRosterとStaffDetailDialogのStorybookを追加、更新する。
8. ドキュメント `doc/features/shift-exclusion.md` と `doc/features/line-notification.md` の「スタッフ行メニュー」表現を、実装後に新しい導線へ更新する。

## 14. テスト計画

Storybookに以下の代表状態を置く。

- 通常スタッフ
- 管理者スタッフ
- LINE未連携
- LINE連携済み
- LINE連携済みだが友だち追加されていない
- シフト対象外
- 対象シフトなし

Behavior Testでは、次を検証する。

- スタッフ行押下でスタッフ詳細モーダルが開く。
- `基本`、`通知`、`LINE連携`、`設定` のタブを切り替えられる。
- パスワード項目が表示されない。
- LINE連携済みのスタッフは `LINE連携済み` と分かる。
- シフト対象外のスタッフは通知ボタンが使えず、理由が表示される。
- 管理者本人のスタッフ行では削除操作が使えない。

Logic UTは、通知タブの対象シフト抽出を純粋関数に切り出す場合だけ追加する。

Convex APIの仕様を変えないため、新規のConvex Function Testは原則追加しない。
ただし、実装中にAPIの戻り値や送信条件を変更する場合は、該当mutationのFunction Testを追加、更新する。

## 16. 前提と未決事項

前提:

- タブは4個から増やさない。
- `LINE連携` タブは、未連携時の案内と連携済み時の状態確認の両方を担う。
- 通知タブでは対象シフトを選択させず、既存APIが送る対象を事前に見せる。
- 送信や削除の二重実行は、既存の `useSingleFlight` とサーバー側のrate limit、ガードで防ぐ。

未決事項:

- 削除確認を既存Dialogで残すか、設定タブ内のインライン確認に移すか。
- `LINEで受け取れません` の表示文言を、実際のLINE状態モデルに合わせてどこまで断定するか。
- 募集中シフトが複数ある場合に、通知タブで全件を表示するか、最新数件 + 件数表示にするか。
- PC表示でDialog幅を何pxにするか。

その後、主要業務契約、public surface、通知purpose、browser-only契約を現行のFull Regression表へ対応付け、監査で確定したリポジトリ内のgapを実装した。

## 判定基準

テスト件数やcoverage率だけでは充足を判定しない。

`doc/features/`、route、利用中のpublic query・mutation・action、HTTP route、通知と復旧導線を先に棚卸しし、壊れた場合の利用者影響ごとに主担当層を確認した。

単一APIの認証、認可、入力、返却、直接副作用はFunction Test、複数API後の永続状態と非同期workflowはScenario Test、操作後のUI状態はFrontend UnitまたはBehavior Test、実browser接続だけはE2Eを主担当とした。

同じ導線を複数層へ置く場合は、各層が検知する失敗境界を分ける。

## 維持する判断

### Analytics Dashboard UIを本体Full Regressionへ戻さない

`apps/analytics-dashboard/`は内部BIとして分離され、現在の規約では本体のLogic、Storybook、VRT、E2Eへ含めない。

以前の監査で挙がったanalytics-dashboard用Vitest projectのCI不足は、現在はproject自体を廃止し、lint、type-check、buildで確認する方針へ変更されたため、そのまま現行gapとして扱わない。

ただし、代替として必須になった`analytics:lint`、`analytics:type-check`、`analytics:build`は現在のworkflowに配線されていない。

rootの`tsconfig.json`は`apps/**`を除外するため、rootの`pnpm type-check`でも内部BIの型退行を検知できない。

ただし、同appから利用するConvexの`POST /analytics-dashboard/query`はprovider・service HTTP境界であり、本体UIの除外とは別にFunction Testが必要である。

### スタッフ参加QRを無条件にE2Eへ戻さない

実public submitを安全に自動化できない間は、この分担を維持する。

ProductionのTurnstile、Origin、body上限は自動テストの成功から推測せず、同一revisionのdeployed canaryをrelease evidenceとして別に確認する。

## Findings

優先度は、`P0`を次の公開または変更前に必ず閉じる境界、`P1`を優先改善、`P2`を保守性または限定的な未保証として扱う。

### P0: Analytics Dashboardの公開HTTP Actionが未検証

`convex/http.ts`は`POST /analytics-dashboard/query`を公開し、`convex/analyticsDashboard/httpActions.ts`はservice secret、global rate limit、content type、body上限、request schema、12種類のquery dispatch、response上限、404・503変換、安全なrequest ID loggingを担う。

このrouteは全tenantの分析値に加え、`requests` endpointでは要望データへ到達するため、service credentialが主要な信頼境界になる。

現在は`schemas.test.ts`と`queryHelpers.test.ts`だけで、routeを`convexTest().fetch()`するテストはない。

主担当をConvex Function Testとし、`convex/analyticsDashboard/httpActions.test.ts`を追加する。

最低限、POST以外、環境secret未設定、secret欠落・不一致・上限超過、`415`、`413`、不正JSON・schema、`429`と`retry-after`、12 endpointのdispatchと最小引数、not found、response上限、query例外時の`503`と`no-store`を確認する。

secret拒否ではrate limitを含むmutationとqueryが0件、rate limit・入力拒否では分析queryと業務mutationが0件であることを確認し、secret、要望本文、個人情報をresponseまたはlogへ出さないことを守る。

テストは`apps/analytics-dashboard/`へ追加しない。

### P1: Analytics Dashboardの代替検証がCIにない

`apps/analytics-dashboard/AGENTS.md`は、app変更時に`pnpm analytics:lint`、`pnpm analytics:type-check`、`pnpm analytics:build`を実行する契約を持つ。

しかし、現行のGitHub Actionsには3 commandの実行がなく、rootのlint、type-check、buildも内部BIを完全には代替しない。

自動テストを持たない判断を維持するなら、少なくとも`apps/analytics-dashboard/**`とapp側の関連設定を変更した時に3 commandを実行するpath-filter付きCIを追加する。

`convex/analyticsDashboard/**`を変更した時はroot lint・type-checkに加え、P0で追加するConvex Function Testを実行し、app側のAPI型やBFF入力にも影響する変更だけ`analytics:type-check`と`analytics:build`を重ねる。

内部BIのUI testを本体suiteへ戻す変更とは分け、現行のcompile・build契約を常に実行するためのCI修正として扱う。

### P1: Trial継続取消のpublic Action開始境界が未検証

本番UIは`api.organizationStripe.actions.cancelTrialContinuation`を呼ぶが、現行の`convex/organizationStripe/actions.test.ts`は作成済みoperationを処理するinternal recoveryを中心に検証し、public Action自体を直接呼んでいない。

主担当を既存のConvex Function Testとし、未認証、read-only、他組織の店舗IDによるIDOR、trial以外、選択済み有料プランなし、同一`requestId`の再利用と競合を追加する。

拒否時はbilling operation、scheduler、Stripe retrieve・cancelが0件であることを確認する。

成功時は現在Subscriptionのscopeとlivemode、provider idempotency key、local stateの収束、provider成功後のlocal失敗からのrecovery予約を確認する。

既存recoveryと異なる失敗境界が見つからない限り、新しいScenario fileは作らない。

### P1: Full Regressionの全機能トレーサビリティがない

現在の機械可読な契約一覧は`assertE2ECoreResults.mjs`の8個のE2E契約が中心であり、Function、Scenario、Behavior、VRTを横断する全機能の現行表はない。

そのため、今回のような時点監査を再実行しない限り、未テスト機能の追加やE2E移管漏れを検出できず、「十分」という結論を継続的に再現できない。

`doc/specs/full-regression-contracts.md`を現行の横断契約表として新設し、`doc/INDEX.md`から参照する案を設計レビューする。

各行には、安定した契約ID、actor、triggerと状態遷移、永続化、下流影響、負の契約、通知、主担当層、端末、実装状態、根拠testを持たせる。

最初にP0契約、public HTTP、課金、capability、通知再送を登録し、P0に未分類を残さない。

件数下限、coverage率、workflow YAMLの文字列検査を新しいgateにはしない。

### P1: VRT baseline不在が成功扱いになる

`.github/workflows/vrt.yml`はbaseline directoryがなければ`found=false`とし、`vrt:assert`をskipする。

後続の`has_diff`も`false`になるため、Pull Requestでbaselineが取得できなくても`No baseline`のコメントだけを残してcompare jobが成功する。

`scripts/prepareRegSuitBaseline.ts`もbaseline不在を空baselineとしてexit 0にする。

Pull Requestでは、期待するbaseline directoryが存在しない場合と画像が0件の場合をfail-closedにする。

developまたはmainへの明示的なbase pushだけをbootstrap・更新経路とし、通常PRが暗黙にbaselineを作成しないようにする。

workflow YAMLのstep名をLogic Testで固定せず、判定を純粋関数へ切り出す場合だけその入出力をテストし、最終的なgateはGitHub Actionsで確認する。

### P1: Deployed Smokeの2契約に欠落検知がない

PR PreviewのDeployed Smokeは、公開route・CSR shell・404を確認するHTTP testと、代表公開ページのhydrationを確認するbrowser testを持つ。

一方、core E2Eのような安定した契約IDとresult JSON gateはなく、片方が誤って削除またはskipされても、残ったtestが成功すればworkflow全体は成功できる。

HTTP境界とbrowser hydrationへ別の契約IDを付け、exactly once、expected、skipなし、retryなしを`test-results-deployed.json`から検査する。

Productionの実到達はこのPreview契約から推測せず、`release.yml`後の自動Smokeを追加するか、現行の手動確認を維持するかを別の運用判断にする。

### P1: E2E縮小時のFrontend移管が一部未完了

法務同意はFunctionとScenarioが厚い一方、`StaffLegalConsent`のrootが持つmutation引数、二重送信抑止、成功後の`accepted`遷移、失敗表示を直接検証していない。

Consent Storyは代表状態を表示するが、現在の`Default`に`play`はない。

LINE callbackもtoken・OAuthのbackend契約はあるが、`LineCallback` controllerのcode・state欠落、Actionの各status、reject、重複実行抑止を直接検証していない。

`LineCallbackView` Storyは静的状態だけである。

法務同意はFrontend UnitとBehavior、LINE callbackはFrontend Unitを主担当にする。

外部LINE Loginを通常E2Eへ戻さず、法務version変更が主要提出導線を止めるreleaseだけ既存の`E2E-SHIFT-01`への統合を判断する。

### P1: 通知再送と問い合わせreplayは期待契約を先に決める

`doc/features/notification-failure-dashboard.md`は、`other`をDashboard対応対象外としながら、IDを直接指定した`resendFailure`にはactionable判定を再適用しない差分を明記している。

拒否へ揃える場合は、同一店舗managerでも非actionableなOutbox失敗を直接指定すると業務副作用0件で拒否するFunction Testを先に置く。

許可を維持する場合は、非表示UIとpublic mutationの差、rate limit、対象scopeを現行仕様として説明してから期待値を固定する。

`POST /contact/submit`はPOST routeのFunction Testを持つが、content typeの要求と同一`requestId` replay時のResend・Slack副作用集合が未定義である。

外部通知コストと二重送信を守るため、replayを同一処理意図として抑止するか、各providerの冪等性をどう保証するかを決め、HTTP FunctionまたはScenarioで検証する。

### P2: 限定的な未保証とテスト作法の負債

`/account-deletion/request`はhandler helperの認証、CORS、body上限、副作用ゼロが厚いが、routerを`convexTest().fetch()`するテストがない。

`OPTIONS /contact/submit`もroute-levelの直接テストがないため、両routeにはpath、method、CORS wiringだけを守る薄いFunction Testを追加し、handler分岐を重複させない。

Dashboard onboardingは進捗の純粋ロジックと一部Behaviorを持つが、DB dismiss mutationのbinding、pending申請時の自動dismiss、3/4から4/4へ進める`sessionStorage`のread・write・破損fallbackが未検証である。

`DashboardOnboarding` rootのFrontend Unit Testを追加する。

組織店舗削除は正常系、冪等性、OCC、権限制限、cleanup完了が既存Function Testで強いため、新しいScenarioを重複追加しない。

既存Function Testへ未認証拒否と、拒否時のshop、audit、cleanup job、scheduler完全不変を追加するだけに留める。

利用箇所と直接テストがない`line/queries.getLinkStatusByShop`と`getQuotaStatus`、旧client用のStripe wrapperは、テスト追加より前に削除またはinternal化を判断する。

Storybookでは16 files、55箇所で`fn()`が使われ、`test-strategy`の直接callback方針と一致しない。

また、`HeroSummary`の3個の`vrt-mobile1` StoryはVRT projectでは320×568でcaptureされるが、Story自身に対応viewport globalがなく、tagとviewportをセットにする規約と一致しない。

247個の`play`付きStoryのうち59件は`screenshot.skip`がなく、Behavior実行後の状態もVRT候補になる。

操作後の最終状態を意図してcaptureするStoryと、静的Storyへ分離すべき重複を棚卸しするが、一括でskipにはしない。

Logic、Convex、lint、type-checkのworkflowは`push`のみであり、外部forkのPull Requestではupstream側のsecret不要suiteが実行されない。

E2Eのsame-repository制限はcredential保護として維持し、secret不要suiteだけ`pull_request`追加の必要性を判断する。

これらは現時点のcoverage blockerではないため、対象Storyを次に変更する時か、小さな専用PRで解消する。

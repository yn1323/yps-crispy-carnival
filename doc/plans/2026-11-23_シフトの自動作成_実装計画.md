> 方針: [シフトの自動作成の方針](2026-11-21_シフトの自動作成_方針.md)

方針の3章で決めた「希望シフトから自動で作成する」の処理を実装する。  
AIで作るほうは、この計画に含めない。

## 目的と前提

### 誰がどの場面で困っているか

必要人数を設定した店舗のシフト担当者が対象である。  
「くわしく」表示は勤務を入れずに開くため、担当者は希望と必要人数を見比べながら、全員分の勤務を手で入れている。

### どうなれば完成か

担当者が「シフトを自動作成」のダイアログで「作成する」を押すと、募集期間の勤務が下書きに入る。  
入った勤務には、確認事項が1件も出ない。  
担当者は人数が足りない所だけを直し、いまの操作で保存して確定する。

### すでに決まっていること

2026-11-23に、次の内容をユーザーと決めた。

| 項目 | 決めた内容 |
|---|---|
| 設定 | 細かい条件を店舗に設定させない。直近のいくつかのシフトを参考にして組む |
| 希望のない所 | 希望のない日と時間、未提出のスタッフには入れない。人が足りない時間は不足のまま残す |
| 下書き | 作った勤務ですべて上書きする。画面に入れるだけで、保存はしない |
| 案内 | 提出が出そろう前に作る場合の案内は出さない |
| 希望が通らなかったスタッフ | 作成の結果として持たない |
| ポジション | 時間指定では、1人の1日の勤務を複数のポジションに分けて作れる |
| 勤務パターン | パターン選択では、1人を同じ日の複数の勤務パターンへ入れられる |
| 休憩 | 労務の基準の分を自動で入れる。休憩を入れても、その時間帯の人数が必要人数になるように組む |
| 45分の休憩のずれ | 見越して人を多めに入れるか、15分の不足なら許す |

### この計画で採った値

方針の4章のおすすめの案を、そのまま採った。  
値を決めていなかった所は、次のように置いた。  承認のときに、違う場合は指摘してほしい。

| 項目 | 採った値 |
|---|---|
| 参考にする過去 | 直近に確定した募集を3回分まで |
| 公平の単位 | 3つの募集方式とも、日数で数える（希望した日数のうち、勤務が入った日数） |
| 時間指定の勤務の最短 | 2時間。希望が2時間より短い日は、希望どおりの長さで入れられる場合だけ作る |
| 1つのポジションを続ける最短 | 1時間 |
| 休憩を置ける範囲 | 勤務の開始から1時間後より後で、終了の1時間前より前 |
| 休憩のあとの埋め直し | 3回まで |

## 設計の要点

### 全体の流れ

1. 担当者がダイアログで「作成する」を押す。
2. 画面が過去の確定シフトを人ごとに数えた結果を、サーバーから1回だけ読む。
3. 画面の中で、決まった手順の処理が勤務を作る。
4. 作った勤務で、下書きを置き換える。
5. 結果を知らせる。

サーバーへ書き込む処理は新しく作らない。  
置き換えた下書きは保存済みの内容と違うため、いまある「保存していない変更」の確認がそのまま働く。

### 置く場所

| 対象 | 置く場所 | 内容 |
|---|---|---|
| 作る手順 | `src/domains/shift/autoAssign/`（新規） | 希望、必要人数、熟練度、過去の集計から勤務を作る、画面に依存しない処理。募集方式ごと、選ぶ順、休憩にファイルを分ける |
| 過去の集計 | `convex/shiftBoard/autoCreateHistory.ts`（新規） | 過去の希望と勤務を、人ごとの日数に数える処理 |
| 過去の集計を返すquery | `convex/shiftBoard/queries.ts`の`getAutoCreateHistory`（新規） | 管理者だけが呼べる。集計した数だけを返す |
| 入力の変換 | `src/components/features/ShiftBoard/ShiftBoardPage/`（`staffingAdapter.ts`の近く） | サーバーの必要人数と集計を、作る手順の入力の形へ直す |
| 接続 | `useShiftBoardDetailActions.ts`、`ShiftForm/detailParts.tsx`、`ShiftForm/index.tsx`、`AutoCreateDialog/` | 「前回の勤務を仮で入れる」と同じ経路で、下書きへ取り込む |

作る手順を`src/domains/shift/`の下のフォルダにまとめるのは、いまの配置にない形である。  
3つの募集方式の手順と休憩を1つのファイルに書くと長くなるため、フォルダに分ける。

下書きへ取り込む経路では、勤務を入れたときの休憩の初期値が入らない。  
このため、休憩は作る手順の中で入れる。

### 作る対象

- スタッフは希望を提出済みで、シフト対象で、削除されていない人だけにする。
- 日は募集期間のうち、定休日でなく、必要人数がある日だけにする。
- 必要人数のない日と、必要人数を入れていないポジションには入れない。
- 下書きにあった勤務は作る対象でない日とスタッフの分も含めてすべて消す。  仮の勤務も消える。

### 誰を選ぶか

枠は日付選択では「日×ポジション」、パターン選択では「日×勤務パターン×ポジション」、時間指定では「日×ポジション×30分」である。  
どの枠も必要人数ちょうどで止め、それより多くは入れない。

埋める順は候補の人数を必要人数で割った値が小さい枠からにする。  候補はその枠を希望していて、そのポジションが担当外でない人である。

1つの枠で候補が必要人数より多いときは、次の順で選ぶ。

1. 枠の1人目はそのポジションで見習いでない人から選ぶ。  見習いしか候補がいない枠には、見習いを入れる。  2人目からは熟練度で差をつけない。
2. 「今回これまでに入った日数 ÷ 目安の日数」が小さい人から選ぶ。
3. 同じなら、直近の1回で、希望が通らなかった日数が多い人を選ぶ。
4. 同じなら、過去にそのポジションへ入った日数が多い人を選ぶ。
5. それでも同じなら、スタッフのIDと募集の開始日から作る値で決める。  スタッフの並び順は使わない。

目安の日数は「今回希望した日数 × 目安の割合」である。  
目安の割合は本人の過去の割合と、店舗全体の過去の割合の平均にする。  過去の割合は「勤務が入った日数 ÷ 希望した日数」である。  
本人の過去がない場合は、店舗全体の過去の割合を使う。  店舗に過去がない場合は、全員を同じ割合にする。

本人の過去だけを使わないのは、偏りが回を追うごとに強まるのを防ぐためである。  自動作成の結果は次回の過去になる。

全部の枠を見終えたあとで、不足の残った枠を1回だけ見直す。  
別の枠に入っている人をその枠へ移し、空いた枠を別の候補で埋められる場合に、入れ替える。  担当できる人の少ないポジションを先に埋めるためである。

### 日付選択とパターン選択

日付選択は上の順で「日×ポジション」の枠を埋める。  1人は1日に1つのポジションだけに入る。

パターン選択は2回に分ける。

1. 1人を1日に1つの勤務パターンだけへ入れて、枠を埋める。
2. 不足の残った枠に、その日すでに別のパターンへ入っている人を入れる。  入れるのは、本人が希望していて、時間が重ならないパターンだけである。

保存の検査は、1人が時間の重なる別のパターンへ入ることを止めていない。  自動作成では重なる組み合わせを作らない。

### 時間指定

1日ごとに、次の順で作る。

1. その日の必要人数を、ポジションごと、30分ごとの人数に直す。
2. 選ぶ順に従って1人ずつ、希望の時間の中で、まだ足りない時間を最も長く埋められるポジションと、続いた時間を決める。  両端の、足りない時間がない部分は切る。
3. 勤務は2時間以上にし、1日に離れた2つの勤務は作らない。
4. 全員を見終えたら、ポジションを分け直す。  ある人の勤務の一部で、いまのポジションは足りていて、担当できる別のポジションが足りない時間が1時間以上続く場合に、その時間だけ替える。
5. 休憩を入れる（次の節）。
6. 休憩で足りなくなった時間を埋め直す。

### 休憩

対象は時間指定だけである。

長さは、休憩を引いた時間が基準を超えないように決める。

| 勤務の開始から終了まで | 休憩 |
|---|---|
| 6時間まで | なし |
| 6時間を超え、8時間45分まで | 45分 |
| 8時間45分を超える | 1時間 |

店舗に休憩の決まりが残っていて、その勤務に当てはまり、上の表より長い場合は、長いほうを使う。  
基準の値は作る手順の中に決まった値として持つ。  店舗の設定と保存の形は変えない。

置く位置は次のように決める。

- 15分単位で、勤務の開始から1時間後より後、終了の1時間前より前に置く。
- その範囲で、休憩によって不足が出ない時刻を選ぶ。  複数ある場合は、勤務の中央に近い時刻にする。
- 不足が出ない時刻がない場合は、不足が最も小さくなる時刻にする。
- 勤務の開始が早い人から順に置く。  前の人の休憩を数えに入れるため、時刻が人ごとにずれる。

休憩で足りなくなった時間は、次の順で埋め直す。

1. そのポジションを担当できる人の勤務を、希望の範囲で30分単位に伸ばす。
2. まだ勤務のない希望者を入れる。

伸ばした結果として出る15分の余りは許す。  
埋められる人がいない不足は残す。  15分の不足を埋めるために、ほかの勤務を変えることはしない。  
人数を合わせるために、休憩を短くすることもしない。  
伸ばした勤務は休憩の長さを決め直す。  埋め直しは3回までにする。

許した15分の不足はいまのシフト表では不足として出る。  見せ方は今回変えない。

### 過去の集計

`getAutoCreateHistory`は、今回の募集のIDを受け取り、次を返す。

| 項目 | 内容 |
|---|---|
| 集計に使った募集の数 | 0から3 |
| 人ごとの数 | スタッフのID、希望した日数、勤務が入った日数、直近の1回の希望した日数と入った日数、ポジションごとの入った日数 |

- 対象は同じ店舗の、削除されていない、確定済みの、今回より開始日が前の募集である。  新しい順に3件を取り、今回と募集方式が同じものだけを使う。
- 数えるのは、その募集で希望を提出した人の、希望のある日だけである。  仮の勤務は希望のない日にあるため、数に入らない。
- 返すのは、いまシフト対象のスタッフの分だけである。
- 日付メモは読まない。
- 読む件数は1つの募集につき、勤務2000件、希望2000件、提出200件までである。  3つの募集で約12,600件になり、Convexの1回の実行の上限（32,000件）に収まる。  上限を超える募集はいまのシフト表のqueryと同じくエラーにする。
- 画面は「作成する」を押したときに1回だけ読む。  購読はしない。

### 画面に出す言葉

画面の構造は増やさない。  文言は実装の前に選んでほしい。

| 画面と位置 | 条件 | 案 |

| ダイアログの選択肢の下 | 期間に必要人数のある日が1日もない | 「作成する」を押せなくし、「必要人数を設定すると、自動作成を使えます」と「必要人数設定を開く」を出す |
| ダイアログの「作成する」 | 作成中 | ボタンに進行の表示を出し、ダイアログを閉じる操作を止める |

### 自分で決めた設計判断

承認のときに、違う場合は指摘してほしい。

1. 期間の一部にだけ必要人数のない日がある場合は、その日を作らずに飛ばす。  下書きは全体を上書きするため、その日の勤務は空になる。
2. 作れる勤務が1件もない場合は、下書きを消さずにそのままにする。
3. 過去の集計は勤務と希望そのものではなく、人ごとの日数だけを画面へ返す。  画面に要るのが数だけだからである。
4. 過去の集計を読めなかった場合は、作成を止める。  過去なしで作って結果が変わることを避ける。
5. 時間指定の公平も時間ではなく日数で数える。  希望の時間の幅は人によって書き方が違い、時間で比べると、幅を広く書く人が不利になる。
6. 作る手順はスタッフの並び順を入力に使わない。  並び順を変えても同じ結果になる。
7. 作った勤務には「仮」を付けない。  提出済みの人だけに入れるためである。
8. 複数の店舗に所属する人の、ほかの店舗の勤務との重なりは見ない。  いまのシフト表も手で入れる場合に見ていない。
9. 自動作成の使用にrate limitは付けない。  読むだけで、件数に上限があり、外部の費用がかからないためである。
10. 「シンプル」表示と、確定済みの募集には出さない。  方針の2章のとおりである。

### Security Lens

- Actor: 対象店舗が属する組織の有効な管理者。  スタッフ用sessionと匿名は対象外である。
- Asset: 過去の希望と確定シフトから数えた、人ごとの日数。  店舗が誰をどれだけ入れてきたかが分かるため、店舗内の評価に近い情報である。
- Trust boundary: ブラウザとConvexのpublic query。  新しいmutation、action、HTTP route、capabilityは作らない。
- Abuse case: 別店舗、別組織の募集のIDを渡して、その店舗の過去を読む。  削除済みの募集や、シフト対象外にした人の数を読む。
- Server-side enforcement: `managerQuery`を使う。  今回の募集は`getActiveRecruitmentInShop`で同じ店舗の有効な募集であることを確かめ、違えば`null`を返す。  過去の募集は認可済みの店舗のIDをindexの先頭に置いて探すため、ほかの店舗の募集に届かない。  スタッフは`listShiftTargetStaffsInShop`で絞る。
- Rate limit / idempotency: 読むだけで、状態を変えない。  読む件数は定数で上限を決める。
- Lifecycle / recovery: 募集の論理削除で、その募集は集計から外れる。  スタッフの論理削除とシフト対象外で、その人の数は返らなくなる。
- Logs / PII: 氏名、メールアドレス、日付メモを返さない。  集計の結果をログへ出さない。
- Regression test: `getAutoCreateHistory`のFunction Testで、未認証、別組織、別店舗の募集で`null`になること、対象でない募集と人を含まないこと、返す形が完全に一致することを確かめる。

| 19 | 必要人数を設定した店舗で、提出済みの希望から自動作成し、下書き保存して再読み込みしても、作った勤務が残る | core E2E（`E2E-AUTOCREATE-01`、Desktop Chrome） |
| 20 | 自動作成を使わない場合の、シフト表、保存、確定、通知、出力の動きが変わらない | 既存のテストがそのまま通ること |

`E2E-AUTOCREATE-01`は、スタッフが提出した希望と、設定した必要人数を、自動作成が使うという受け渡しを1つだけ確かめる。  
誰が選ばれるか、休憩、不足の扱いは下位の層に置き、E2Eへ持ち込まない。  
開始状態は既存のseedで作り、`scripts/assertE2ECoreResults.mjs`の期待契約と契約表を同じ変更で更新する。  
契約表には`SHIFT-AUTOCREATE-01`の行を足す。

## 実装中に変えた判断

実装で分かった事実に合わせて、次の点を計画から変えた。

1. 作る手順は`src/domains/shift/autoAssign/`ではなく`convex/shiftBoard/autoCreate/`に置いた。  動かす場所は画面のままである。  画面はConvexのファイルを読み込めるが、逆はしていないため、Convex側に置くと、サーバーで動くAIの処理からも同じ手順と検査を使える。  保存の検査（`convex/shiftBoard/validation.ts`）と同じ置き方である。
2. 結果を下書きへ取り込む処理は、画面の勤務の形を扱うため、`src/domains/shift/autoAssignments.ts`に置いた。
3. 過去の集計で、読む件数が上限を超える募集は、エラーにせず、その募集を数えずに外す。  過去は参考であり、1つの募集を読めないだけで自動作成を使えなくなることを避ける。
4. 目安の割合に下限（0.1）を置いた。  過去に1日も入っていない人の目安が0になり、選ばれないままになることを防ぐ。
5. 時間指定のポジションの「分け直し」は、勤務を隣り合う別のポジションの足りない時間へ伸ばす形と、まだ勤務のない人へ複数のポジションをつないだ勤務を入れる形にした。  必要人数ちょうどで止める作りでは、「いまのポジションは足りていて余っている」時間が生まれないためである。
6. 時間指定で、埋める時間を選ぶ順に「候補の少ない時間を先にする」を足した。  その時間に入れる人が、ほかの時間で先に使われて不足が残ることを防ぐ。
7. 休憩はほかの人の休憩と重ならない時刻のうち、勤務の中央にいちばん近い時刻へ置く。  同じポジションの人とは、休憩を置ける範囲の全体でずらす。  ポジションの違う人とは、休憩の中央が勤務の中央の前後2時間に入る範囲でずらし、収まらない人数のときは重ねる。  はじめは休憩で出る不足が小さい時刻を先に選んでいたが、休憩が中央から離れた。  次に中央を先にしたが、人数がもともと足りない時間帯で全員の休憩が重なった。  同じポジションの人だけをずらす形でも、ポジションの違う人の休憩が同じ時刻に並んだ。  このため、休憩を順番に取る形に改めた（2026-11-23、ユーザーの指示）。
8. 休憩で足りなくなった時間を埋めるときは、伸ばすと休憩が長くなる勤務を伸ばさない。  1つの穴を埋めるために、別の穴を作らないためである。
9. 不足が残ったときの知らせは出さない。  どの場合も「シフトを自動作成しました」だけを知らせる。  作ったのは下書きで、不足はシフト表の人数の表示で分かるためである（2026-11-23、ユーザーの指示）。
10. 「AIで作成する」は選べなくする案も出さない案も採らず、いまの表示のままにした。  AIの処理はあとで実装するためである（2026-11-23、ユーザーの指示）。  AIを選んで「作成する」を押すと、何も作らずにダイアログを閉じる。
11. 完成条件18のテストは`ShiftBoardPage/index.test.tsx`ではなく`useShiftBoardPageController.staffing.test.tsx`に置いた。  「前回の勤務を仮で入れる」のテストがそこにあるためである。
12. 完成条件1と2は、結果を下書きへ取り込んだあとの勤務で確かめるため、`ShiftBoardPage/autoCreateAdapter.test.ts`に置いた。
13. 完成条件17の「AIは選べない」は外した。  10のとおり、AIの選択肢をいまの表示のままにしたためである。
14. E2Eの準備データ（`seedOpenRecruitmentNotificationScenario`）に、管理者自身のスタッフが募集の全日に希望を提出済みの状態を足した。  希望の提出は別の契約が画面から確かめているため、準備データで作る。  必要人数は設定ページから画面で入れる。
15. 必要人数のある日がない場合の案内は、計画の「必要人数を設定すると、自動作成を使えます」から「自動作成には必要人数の設定が必要です」へ変えた（2026-11-23、ユーザーの指示）。
16. 休憩の長さは、開始から終了までが6時間45分以上の勤務に45分、9時間以上の勤務に1時間にした。  それより短い勤務には入れない。  6時間を少し超える勤務（6時間30分）は作らず、早く上がるか遅く入る形で6時間に縮める。  計画の「6時間を超える勤務に45分」では休憩を入れすぎ、短い勤務を休憩で調整することにもなる、という指示による（2026-11-23、ユーザーの指示）。
17. 店舗の休憩の決まりは使わないことにした。  計画では、決まりが当てはまり基準より長い場合に長いほうを使うとしていた。  「6時間以上の勤務に60分」の決まりが残る店舗で、6時間ちょうどの勤務に休憩が入ったためである（2026-11-23、ユーザーの指摘）。  決まりは設定ページに入力がなく、店舗が中身を確かめられない。  手で勤務を入れたときに決まりから休憩の初期値を入れる、いまの動きは変えていない。
18. 時間指定の公平は日数ではなく勤務時間で数えることにした。  計画の設計判断5では日数で数えるとしていた。  日数では、12時間の勤務も2時間の勤務も同じ1日になり、早い時間から入れる人ばかりが長く入る偏りが見えなかった。  必要人数が9時から21時に2人、9時から希望する人が2人、13時から希望する人が2人の7日間で、前者は84時間ずつ、後者は8時間と6時間になった（2026-11-23、ユーザーの指摘）。
19. 時間指定で、希望者の入れる時間が必要な時間より多い日は、必要な時間を希望者で均等に分けた長さを、1人の勤務の上限にした。  上限は4時間より短くせず、分けた残りが4時間に満たない場合は分けない。  その人にしか埋められない時間は削らない。  18と合わせて、上の例は4人とも42時間になる。  勤務の長さがまちまちなら時間でそろえる、という考え方は、Zoho Shifts、Deputy、Timefoldの資料にある。  時間を人ごとに切り分ける決め方は、読んだ資料には見つからず、シフトリ独自の設計である。
20. 時間指定の募集のダイアログに、「休憩時間も自動作成する」のチェックを足した。  初めは入れた状態にする。  休憩を置く時刻は店ごとの流儀があり、設定なしでは合わない店が出るため、外して作り直せるようにした（2026-11-23、ユーザーの指示）。  外した場合は、休憩に合わせて勤務を縮めることも伸ばすこともしない。

21. 時間指定の勤務は3時間以上を目指すことにした。  まず3時間以上の勤務だけで埋め、すでに入った人の勤務を伸ばしても埋まらない時間だけを、2時間以上の勤務で埋める。  19の上限と、分けた残りの下限も、4時間から3時間へ変えた。  2時間の勤務が多い、という指摘による（2026-11-23、ユーザーの指摘）。  48人・31日の募集で、2時間以下の勤務は88件から4件になった。
22. 時間指定の上限に、その人の希望の時間に限った取り分を足した。  希望者の多い時間帯だけを希望した人の上限が短くなる。  分けた残りの長さにはその人の希望の外へ続く足りない時間も数えるようにした。  希望の時間が遅い人ほど入れていない、という指摘による（2026-11-23、ユーザーの指摘）。  同じ募集で、勤務は1,190件から1,300件に増え、不足は803.5時間から772.75時間に減った。  希望した日のうち勤務が入った日の割合は、希望の始まりが10時から15時の日で80%から94%、15時以降の日で73%から77%になった。  15時以降の日の割合がほかより低いのは、この募集では17時から20時台に入れる希望者が、必要人数の1.5倍から2倍いるためである。  勤務時間の割合（希望した時間のうち勤務が入った時間）は、希望の始まりの時刻によらず60%から64%にそろっている。
23. AIの指示文にも21と22の考え方を足した。  AIが返した勤務の検査は2時間以上のまま変えていない。

24. 時間指定の公平さを数える指標を決め、その指標が良くなるように手順を直した（2026-11-23、ユーザーの指示）。  人を選ぶ順の目安を取り分から作る、取り分から決める上限を切り捨てる、勤務を伸ばす順を変える、入れない日が続いた人を優先する、縮める位置を希望者の少ない時間へ寄せる、の5つである。  22の上限の説明のうち、時間帯ごとの取り分を切り上げる点は、この変更で切り捨てに変わった。  指標の定義と、試した10案の値は[シフトの自動作成の公平さの指標](../features/shift-auto-create-fairness.md)にある。

## 実装の順序

段階ごとに、対応するテストを通してから次へ進む。

1. 過去の集計とquery（完成条件15、16）。
2. 選ぶ順と、日付選択、パターン選択の手順（完成条件1から9のうち、この2方式の分）。
3. 接続とダイアログ（完成条件17、18）。  この時点で、日付選択とパターン選択の募集で使える。
4. 時間指定の手順。  1つのポジションだけで、休憩は入れない（完成条件10）。
5. 時間指定のポジションの分け直し（完成条件11）。
6. 休憩と埋め直し（完成条件12から14）。
7. core E2E（完成条件19）。
8. 追従。  [シフト表](../features/shift-board.md)の「自動作成」、[必要人数設定](../features/shift-setup.md)の「労務の基準は示さない」と担当外の説明、`doc/specs/full-regression-contracts.md`、方針の文書と[計画の一覧](INDEX.md)の状態、`ui-architect`の選ばれた形の記録を直す。

時間指定の手順が6までそろう前に、時間指定の募集で「作成する」を使えるようにはしない。

## 検証

- 完成条件ごとの対象テストを先に実行し、そのあとで`pnpm lint`、`pnpm type-check`、`pnpm test`、`pnpm build`を実行する。
- E2Eは`E2E-AUTOCREATE-01`を`--retries=0 --workers=1`で実行し、成功したら`pnpm e2e:burn-in`を実行する。  サーバーはユーザーが起動しているものを使い、新しく起動しない。
- 画面の操作の流れが変わるため、完了を報告する前に`first-use-reviewer`で、初めて使う担当者の立場の確認をする。
- Pull Requestを作る前に、ブランチ全体の差分を`code-review`でレビューする。
- ローカルの確認用データは日付メモを先に決め、その日の希望をメモに合わせる。

- `first-use-reviewer`による、初めて使う担当者の立場の確認。  ログイン済みのブラウザがなく、シフト表を開けなかった。

## 今回やらないこと

- AIで作る処理、AIの回数の制限、個人情報のヘルプ。
- 手で入れた勤務を残して、残りだけを埋める作り方。
- 希望が通らなかったスタッフの一覧。
- 連勤や勤務時間の上限の判定。  休憩のほかの労務の基準は扱わない。
- 許した15分の不足の見せ方の変更。
- 複数の店舗に所属する人の、店舗をまたぐ重なりの確認。
- 店舗の休憩の決まりを2段で持つ形への変更。
- 自動作成のあとで手で直した量の計測と、Web計測のイベントの追加。
- ヘルプの追加、公開ページとデモへの反映。
- `doc/manual/release-status.md`の更新と、実環境への反映。

## 確かめていないこと

- 労働基準法第34条第2項は休憩を一斉に与えると定める。  ただし書きと、業種による例外は確かめていない。  休憩の時刻を人ごとにずらす作りは、この項と関係する。  画面と文書で「法律を守れる」と言わないのは、このためでもある。
- 上限に近い大きさ（スタッフ200人、期間31日）で、画面の中の処理にかかる時間は測っていない。  実装のときに測る。
- 作った結果が、担当者が手で組んだシフトにどれだけ近いかは確かめていない。  実装のあとで、過去の希望から作った結果と、確定したシフトを比べる。

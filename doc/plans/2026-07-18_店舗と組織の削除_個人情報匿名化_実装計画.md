## 1. 結論

店舗削除は、グループ設定の店舗タブ、店舗詳細モーダル、Convex mutation、永続cleanupへ接続した。

店舗名、店舗所属スタッフの氏名とメールアドレス、LINE IDは削除済みの値へ置き換える。

組織削除は、グループ設定の「設定」タブ、削除可否query、Convex mutation、永続cleanupへ接続した。

組織、全店舗、組織所属、店舗所属を利用不可にしたうえで、主要マスタの組織名、店舗名、氏名、メールアドレス、LINE IDを削除済みの値へ置き換える。

Clerkのユーザーと認証設定は削除しない。

この機能は、全テーブル、外部provider、端末、ログ、バックアップから個人情報を完全消去する機能ではない。

rate limit、監査履歴、自由入力欄、実行待ち処理の引数、送信済みメールとLINEを含む残存データは許容し、主要マスタの置換とアプリからの利用停止を保証範囲とする。

この計画は、Clerkユーザー削除を前提にした `doc/plans/2026-07-16_店舗とアカウント削除_実装計画.md` を置き換える。

現行機能の概要と保証範囲は `doc/features/data-deletion.md` を参照する。

### 2.1 実装前に解消するリスク

| 優先度 | リスク | 計画上の対処 |
| --- | --- | --- |
| P0 | 共有userを無条件に削除すると、対象外組織へのアクセスまで失われる | 対象外の有効所属をserverで確認し、組織専属userだけを論理削除する |
| P0 | 現在のcleanupが途中停止すると、主要マスタの直接識別子が残り続ける | 永続job、cursor、lease、reaper、完了確認を追加する |
| P1 | 削除受付と通知workerが競合すると、削除後に新しい通知が送信される | 親削除guard、未送信Outboxの取消、外部送信直前の再検証を追加する |
| P1 | 削除済みuserが初期セットアップへ入り、保存時だけ拒否される | `accountDeleted` stateと専用終了画面を追加する |
| P2 | 削除操作を行ったタブのlocalStorage、client cache、確認Dialogに削除対象名が残る | atom破棄、hard navigation、alertdialogへの変更を行う |

### 2.2 Security Lens

- Actor: 店舗削除は対象店舗のactive manager、組織削除は対象組織で唯一のactive manager。
- Asset: 店舗と組織の利用権限、主要マスタの店舗名、組織名、氏名、メールアドレス、LINE ID。
- Trust boundary: clientから渡す店舗ID、組織ID、確認ID、更新時刻、request IDは認可の根拠にせず、Clerk identityとserver上の所属から再検証する。
- Abuse case: 他組織の削除、古い画面からの削除、二重要求、削除開始後のCapability発行と通知送信。
- Server-side check: active membership、対象店舗と組織の関係、唯一の管理者条件、課金状態、削除状態、更新時刻をmutation内で検証する。
- Rate limit / idempotency: 既存rate limitは変更せず、フロントの同期ガードと固定request IDによる冪等性を使う。
- Lifecycle / recovery: 親を先に論理削除し、sessionとtokenを失効させ、主要マスタ置換は再開可能なbounded jobで完走する。
- Logs / PII: cleanupは元の値を新しいjobやログへ複製しない。既存ログ、rate limit、監査、自由記述、外部providerは置換対象外とする。
- Regression test: Function Testで認可、冪等性、主要マスタ置換、対象外データの維持を確認し、Scenario Testで複数batchと復旧、E2Eで画面導線と再アクセス後の利用停止を確認する。

## 3. 削除契約

### 3.1 論理削除の表現

トップレベルの削除対象は、既存schemaに合わせて次の値を使う。

- 店舗は `shops.isDeleted = true` とする。
- 組織は `organizations.isDeleted = true` とする。
- 組織以外に有効な所属を持たない管理ユーザーは `users.isDeleted = true` とする。
- 店舗所属は `shopMembers.isDeleted = true` とする。
- スタッフとLINE連携は、それぞれの `isDeleted = true` とする。
- 組織人物と組織管理者所属は、既存の論理削除表現である `status = "removed"` とする。
- 招待、未送信通知、Capabilityは、それぞれの既存schemaにある `revoked`、`cancelled`、`revokedAt` を使って終端化する。

削除済みの親を先に確定し、子データの終端化と主要マスタ置換中もmanager query、staff session、公開登録、通知enqueueを通さない。

### 3.2 保証する置換範囲

この機能で置き換える値は、次の主要マスタに保存された直接識別子に限定する。

- `shops.name`
- `organizations.name`、`billingEmail`、`billingEmailNormalized`
- `staffs.name`、`email`、`emailNormalized`
- `staffLineAccounts.lineUserId`
- 組織削除時の `organizationPeople.name`、`email`、`emailNormalized`
- 組織削除時に対象外の有効所属を持たない `users.name`、`email`、`emailNormalized`

店舗削除では `users` と `organizationPeople` を変更しない。

組織削除でも、対象外の有効組織に所属する共有userは変更しない。

次の値は置換対象外として許容する。

- `rateLimits.key` に含まれるメールアドレス
- `organizationAuditEvents.fromState` と `toState` を含む監査履歴
- ポジション名、勤務区分名、お知らせ本文、要望、登録申請、招待、通知payloadなどの自由入力または履歴データ
- `shopMembers.userId`、staff、同意、通知、監査などからuserへ向く内部参照
- scheduled functionの引数
- raw tokenとsessionの保存値。ただし、サーバー側では必ず失効させる
- 配信済みまたは送信処理中のメールとLINEメッセージ、provider側の保持データ
- Clerk、ログ、export、バックアップ、ブラウザ履歴、別タブ、別端末に残るデータ

このため、本文とUIでは「個人情報の完全消去」または「全システムからの匿名化」と表現しない。

保証するのは、主要マスタの直接識別子を削除済みの値へ置き換え、削除対象をアプリから利用できなくすることである。

### 3.3 店舗削除の範囲

店舗削除では、対象店舗と店舗ローカルの情報だけを削除する。

- 対象店舗を論理削除し、店舗名を削除済みの値へ置き換える。
- 対象店舗の `staffs` を論理削除し、氏名、メールアドレス、正規化メールを削除済みの値へ置き換える。
- 対象店舗の `staffLineAccounts` を論理削除し、LINE IDを削除済みの値へ置き換える。
- 店舗用session、magic link、LINE連携token、法務同意token、登録リンクを失効する。
- 未送信の通知をcancelし、削除後の新しい通知enqueueと外部送信を拒否する。
- `staffs.userId`、`staffs.organizationPersonId`、`shopMembers.userId` を含む内部参照は変更しない。
- 登録申請、通知payload、通知エラー、自由記述、履歴に含まれる値は変更しない。
- `users`、`organizationPeople`、`organizationMembers`、組織名は変更しない。
- シフト履歴は、直接識別子を置換したstaff IDにひもづく業務履歴として保持する。

この範囲は「店舗削除時はユーザーをそのままにする」という要件と、店舗専属スタッフを「店舗所属なし」の組織人物として残す既存E2Eの契約に一致する。

### 3.4 組織削除の範囲

組織削除では、対象組織に属する全店舗と全人物の利用権限を終了する。

- 組織を論理削除し、組織名、請求先メールアドレス、正規化メールを削除済みの値へ置き換える。
- 組織の全店舗を論理削除し、各店舗名を削除済みの値へ置き換える。
- `organizationPeople` を `removed` にし、氏名、メールアドレス、正規化メールを置き換える。
- `organizationMembers` を `removed` にし、グローバルuserへのリンクは保持する。
- 組織配下のstaff、LINE連携、店舗所属を論理削除し、招待、未送信通知、Capabilityを終端状態へ移す。
- 登録申請の氏名、メールアドレス、状態は履歴として保持し、削除済みの親を確認するguardにより承認、通知、公開取得を利用不可にする。
- staff、member、監査、同意、通知、要望などに残るグローバルuserへの内部参照は保持する。
- シフト、同意、請求、監査、分析の履歴は、内部IDと状態を含む既存形式のまま保持する。

Clerk側の氏名とメールアドレスは残るため、画面とドキュメントでは「全システムから完全消去」と表現しない。

この機能が保証する範囲は、Convexの主要マスタにある直接識別子の置換と、アプリからのアクセス停止である。

すでに配信したメールやLINEメッセージ、Clerk、Resend、LINE、バックアップの保持データは対象外とする。

### 3.5 複数組織に所属するユーザー

`users` は全組織で共有するレコードであり、同じユーザーが複数組織へ所属できる。

対象組織の全ユーザーを無条件に `isDeleted = true` にすると、削除対象ではない組織へのアクセスまで失われる。

そこで、グローバルuserは次の規則で処理する。

- 対象外の非削除組織に有効な `organizationMembers`、`organizationPeople`、`staffs`、legacy `shopMembers` のいずれも持たないuserだけを論理削除し、氏名とメールアドレスを削除済みの値へ置き換える。
- 対象外に有効な所属がある共有userは、グローバルな `users` を変更しない。
- 共有userについて、削除組織側のperson、member、staff、監査、通知からuserへのリンクは外さない。
- `users.authTokenIdentifier` は、Clerk主体とのtombstoneと再登録防止に必要なため、userを論理削除する場合も保持する。

この規則により、主要マスタの組織内人物情報を置き換え、別組織の利用権限を壊さない。

内部参照から共有userへ辿れる状態は、今回の許容範囲に含める。

## 4. UI設計

### 4.1 店舗削除

既存の `/settings?tab=shops` と店舗詳細モーダルを維持する。

削除確認は、現在の `role="group"` の確認領域を `role="alertdialog"` の確認状態へ変更する。

別モーダルを重ねず、店舗詳細モーダルの内容を確認状態へ切り替える。

確認状態では、次の影響を表示する。

- 店舗を利用できなくなる。
- 店舗のスタッフ所属、通知先、登録リンクを停止する。
- 店舗とスタッフの基本情報に保存した店舗名、氏名、メールアドレス、LINE IDを削除済みの値へ置き換える。
- グループのユーザーと管理者権限は残る。
- 過去のシフト、登録申請、通知履歴、送信済みメールとLINEは残る。
- 操作は元に戻せない。

削除後の主要マスタ置換は非同期で完走するため、toastは「店舗の削除を受け付けました」とする。

選択中の店舗を削除した場合は、対象をlocalStorageから即時に外す。

旧URLは既存E2Eと同じ利用不可状態を表示し、「ダッシュボードへ戻る」操作で利用可能な別店舗へ移す。

この状態では削除した店舗名を表示しない。

最後の一店舗は既存APIと同じく店舗モーダルから削除できない。

削除不可理由から設定タブのグループ削除へ案内する。

### 4.2 組織削除

グループ設定の末尾に「設定」タブを追加する。

設定タブには「グループ情報」と「危険な操作」を置き、削除操作は危険な操作の中に一つだけ配置する。

`getSettings` が返す `canDeleteOrganization` と拒否理由を使い、UIだけで削除可否を推測しない。

削除できない場合も入口を隠さず、先に必要な操作を説明する。

| 状態 | 表示 |
| --- | --- |
| 他の有効な管理者がいる | ほかの管理者を整理してから実行するよう案内する |
| 有料契約中または課金遷移中 | 契約終了を先に完了するよう案内する |
| 削除処理中 | 重複要求を送らず、受付済みであることを表示する |
| 削除可能 | 「このグループを削除」を有効にする |

組織にはownerロールがないため、最初の実装では、操作者自身が `active` であり、操作者以外の `active` または `readOnly` 管理者がいない場合だけ削除できる。

課金については、`selectedPaidPlan` がないTrial、active Free、無償提供だけを削除可能とする。

Pro、Business、支払い待ち、猶予、制限、プラン変更中、移行状態不明は、外部契約終了を確認できる処理が入るまで拒否する。

### 4.3 組織削除の確認

確認画面は `role="alertdialog"` とし、現在の組織名を完全一致で入力するまで確定ボタンを無効にする。

組織名の一致判定は誤操作防止のUI契約であり、認可の根拠にはしない。

mutationには入力した名称を保存せず、対象組織ID、確認用組織ID、画面取得時の更新時刻、同じ削除意図で固定した `requestId` を渡す。

サーバーは認証identityから操作者を解決し、対象組織、選択店舗、更新時刻、権限、課金状態を確定時に再検証する。

確認画面には次の内容を表示する。

- グループとすべての店舗を利用できなくする。
- グループ、店舗、人物、スタッフの基本情報に保存した名称、氏名、メールアドレス、LINE IDを削除済みの値へ置き換える。
- 他のグループに所属するユーザーの利用権限は残る。
- Clerkのログインアカウントは削除しない。
- 過去のシフト、同意、請求、監査、通知、送信済みメールとLINEの記録は残る。
- 操作は元に戻せない。

確定ボタンはフロントの同期ガードとバックエンドの `requestId` 冪等性を併用する。

Dialogを閉じて開き直した場合は新しい削除意図として `requestId` を作り、通信結果が不明なまま再試行する場合は同じ値を使う。

### 4.4 削除後の状態

組織削除成功時は `selectedShopAtom` を消し、削除操作を行ったタブのlocalStorageから対象組織の店舗名と組織名を外す。

対象組織専属userの場合は `userAtom` も消す。

その後に店舗queryを付けない `/dashboard` へ `replace` するhard navigationを行い、対象組織のquery結果を保持するConvex client cacheを破棄する。

対象外の組織に利用可能な店舗がある場合は、その店舗へ遷移する。

対象外の組織がない場合は、Clerk sessionを維持したまま「アプリ上のアカウントは削除済みです」という終了状態を表示し、サインアウト操作だけを提供する。

`getCurrentUser` は削除済みuserを `isNewUser` として返さず、`{ accountDeleted: true }` という明示的な状態へ変更する。

この分岐はClerk identity由来の `name` と `email` をDTOへ含めず、新規user用DTOへフォールバックさせない。

これにより、削除後に初期セットアップを表示してからmutationで拒否する行き止まりをなくす。

削除済みuserの自動再作成と再有効化は、この実装の対象外とする。

## 5. バックエンド設計

### 5.1 公開DTOとmutation

`api.organization.queries.getSettings` に次の値を追加する。

- `organizationId`
- `organizationUpdatedAt`
- `canDeleteOrganization`
- `deleteOrganizationDisabledReason`

`organizationId` と `organizationUpdatedAt` は移行済み組織で返し、legacy migration pendingの返値では未設定かつ `canDeleteOrganization = false` とする。

新しい `api.organization.mutations.deleteOrganization` は次の引数を受け取る。

```ts
{
  shopId: Id<"shops">;
  organizationId: Id<"organizations">;
  confirmOrganizationId: Id<"organizations">;
  expectedOrganizationUpdatedAt: number;
  requestId: string;
}
```

公開APIはjobのphase、cursor、内部エラー、対象人物一覧を返さない。

応答は `{ organizationId, changed, accepted }` に限定する。

同じ組織と `requestId` の要求は、親が削除済みでも同じ受付結果を返す。

同じ `requestId` で異なる対象を指定した場合は副作用なしで拒否する。

### 5.2 受付transaction

店舗削除は既存mutationを拡張し、次の処理を一つのtransactionで行う。

1. 既存の認証、認可、課金、最後の一店舗、確認ID、冪等性を再検証する。
2. `shops.isDeleted = true` と店舗名の置換を確定する。
3. PIIを含まない監査イベントを記録する。
4. 対象店舗の永続cleanup jobを一件だけ作成する。

組織削除は次の処理を一つのtransactionで行う。

1. 操作者、組織、選択店舗、唯一の管理者条件、課金状態、更新時刻、既存jobを再検証する。
2. `organizations.isDeleted = true` を確定し、組織名と請求先メールを置き換える。
3. 課金stateのversionと通知cutoffを更新し、古いdeadlineを無効にする。
4. 操作者が対象組織専属であれば、操作者の `users.isDeleted` と氏名、メールアドレスの置換も確定する。
5. PIIを含まない監査イベントを記録する。
6. 対象組織の永続cleanup jobを一件だけ作成する。

親の論理削除後は、子データの終端化と主要マスタ置換の完了を待たずに全アクセスを拒否する。

### 5.3 再開可能なcleanup

新しい `deletionCleanupJobs` tableと `convex/deletionCleanup/` を追加する。

jobは次の情報だけを保持し、元の氏名、メールアドレス、LINE ID、店舗名、組織名を保存しない。

- `scope`（`shop` または `organization`）
- `shop` scopeでは必須の `shopId` と任意の `organizationId`
- `organization` scopeでは必須の `organizationId`
- `requestId`
- `status`（`queued`、`processing`、`retrying`、`actionRequired`、`completed`）
- `phase` と `resource`
- tableごとの `cursor`
- `version`
- `attemptCount`
- `nextRunAt`
- `leaseId` と `leaseExpiresAt`
- 安全な `lastErrorCode`
- `createdAt`、`updatedAt`、`completedAt`

各workerは一回100件程度を上限に処理する。

更新時は期待する `version`、`leaseId`、`phase` を照合し、回収済みの古いworkerが新しい状態を上書きしないようにする。

受付直後のscheduleに加えて、期限切れleaseと再試行待ちjobを回収するcronを追加する。

jobの主なphaseは次の順で進める。

1. 未送信通知をcancelし、session、token、登録リンクを失効する。
2. 店舗、staff、店舗所属、LINE連携を論理削除し、`shops`、`staffs`、`staffLineAccounts` の対象fieldを置き換える。
3. 組織scopeでは、person、member、招待をremovedまたはrevokedにし、`organizationPeople` の対象fieldを置き換える。
4. 組織scopeでは、対象外に有効な所属がないuserだけを論理削除し、`users` の氏名とメールアドレスを置き換える。
5. 主要マスタの対象fieldと、論理削除または失効対象resourceの終端状態を確認する。
6. jobを `completed` にする。

Outboxの送信直前gateを通過してprovider呼び出しを開始した一件は、受付後に止められない可能性がある。

送信済みまたは送信処理中の通知内容とprovider eventは置換対象外とする。

### 5.4 置換値

名称は固定の削除済み表記を使い、メールアドレスとLINE IDは行IDから決定的に作る。

いずれも再試行時に同じ値になるようにする。

| 値 | 形式 |
| --- | --- |
| 店舗名 | `削除済み店舗` |
| 組織名 | `削除済みグループ` |
| 人物名 | `削除済みユーザー` |
| メールアドレス | `deleted+<table>.<documentId>@example.invalid` |
| 正規化メール | 上記メールと同じ値 |
| LINE ID | `deleted:<documentId>` |

メールとLINE IDはindex衝突を避けるため、全行を同じ空文字へ置き換えない。

置換処理は元の値をjob、監査、エラー、console logへ新たに複製しない。

### 5.5 遅延処理の停止

削除済みの親を参照する遅延処理は、入口でno-opにする。

対象には少なくとも次の処理を含める。

- 組織課金deadline
- 組織招待の期限切れ処理
- 通知Outboxのclaimと送信
- スタッフ登録申請の日次通知
- 店舗登録リンクと各種Capabilityの検証

`authenticatedQuery` と `authenticatedMutation` は削除済みuserを一律には拒否しないため、組織削除後も呼べる公開関数を列挙し、deleted stateで許可する関数を終了状態表示とサインアウトに必要なqueryだけへ限定する。

## 7. migrationと展開

### 7.1 Widen

最初のdeployでは、既存データと既存コードを受け入れる追加変更だけを行う。

- `deletionCleanupJobs` と必要なindexを追加する。
- 主要マスタ置換中に値を変更してもpaginationが崩れない、組織IDまたは店舗IDと作成時刻によるstable indexを追加する。

`convex/_generated/` は手動編集せず、ユーザーが実行中のConvex開発プロセスで再生成する。

### 7.2 既存削除済みデータ

現在のmigration runnerは `m017` まで登録済みである。本番migrationは未実行である。

`@convex-dev/migrations` の一migration一table方針に合わせ、既存店舗と既存組織を別migrationで走査する。

- `m016_deleted_shops_enqueue_cleanup_jobs` は `shops` を走査し、削除済み店舗へ決定的な `requestId` でshop jobを一件だけ作る。
- `m017_deleted_organizations_enqueue_cleanup_jobs` は `organizations` を走査し、削除済み組織へ決定的な `requestId` でorganization jobを一件だけ作る。

`m016` は親組織も削除済みである店舗をskipし、その店舗は `m017` のorganization jobだけで処理する。

旧形式の店舗は `organizationId` がない場合もあるため、shop scopeのjobは店舗IDだけでも完走できるようにする。

通常の削除APIでも、organization jobと配下のshop jobを同時実行しない。

組織削除の受付時に未完了のshop jobがある場合は `cleanupInProgress` として副作用なしで拒否し、完了後の再実行を案内する。

shop job作成時も未完了のorganization jobを検出し、同じchild graphを別leaseで処理しない。

本番exportで対象が0件と確認できた場合だけ、このbackfillを省略できる。

migrationはPIIを引数やログへ出さず、件数と安全な状態codeだけを返す。

### 7.3 完了確認

展開は次の順で行う。

1. Widen schema、job worker、reaper、旧read互換をdeployする。
2. 店舗削除を新しいjobへ接続する。
3. `m016` と `m017` を実行し、既存削除済みデータのjobを完走させる。
4. jobの `queued`、`processing`、`retrying`、`actionRequired` が0件であることをinternal status queryで確認する。
5. 主要マスタprobeで削除済みscopeの店舗名、組織名、氏名、メール、LINE IDが規定の置換値になっていることを確認する。
6. 組織削除APIとUIを有効にする。
7. `pnpm convex:migrate:status` でmigration完了を確認する。

ロールバック時も、既に置き換えた主要マスタの値は元に戻さない。

UIを無効化して新規受付を止め、受付済みjobは完了まで動かす。

- cleanup jobが途中停止後に再開でき、重複実行しても同じ結果になる。
- 削除受付後に新しいCapability発行と通知送信が始まらない。
- 削除操作を行ったタブのlocalStorageとclient cacheを破棄し、旧URLと再読み込み後のアプリ画面に主要マスタの元の名称、氏名、メール、LINE IDを表示しない。
- 別タブ、別端末、ブラウザ履歴、ログ、export、バックアップ、外部providerは消去保証の対象外とする。
- Logic、Function、Scenario、Storybook、VRT、E2E、axe、lint、type-check、buildが通る。
- `doc/features/data-deletion.md`、`doc/features/shop-settings.md`、`doc/features/organization-billing.md`、`doc/INDEX.md` が実装内容と一致する。

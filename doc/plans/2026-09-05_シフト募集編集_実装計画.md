# シフト募集編集の実装計画

> 文書種別: plan（実装計画）  
> 作成日: 2026-09-05  
> 状態: Active（主要仕様合意済み・実装計画作成済み・未実装）

## 方針と範囲

[合意仕様](2026-09-05_シフト募集編集_仕様.md)に従い、未確定・シフト開始前・提出期限前の募集を編集できるようにする。  
募集作成フォーム、提出データ、シフト表、通知基盤を再利用する。新しい画面上のステータス、提出URL、通知キュー、編集履歴テーブルは追加しない。

下書きと割当は既存の扱いを維持できる。変更の中心は、現在の提出状態の判定、古い募集条件からの保存防止、催促の再設定である。  
この計画の作成ではアプリケーションコードや実環境を変更しない。

主要仕様の確認は完了とする。細部は既存の挙動に合わせて実装側で判断し、合意仕様の変更や大きな追加工数が必要になった場合は、差分と理由をまとめて示す。

## 実装順序

| 順序 | 作業 | 完了条件 |
|---|---|---|
| 1 | データ項目と募集編集API | 日付差分、提出状態、対象外データの削除が一度の保存で整合する |
| 2 | 提出・集計・シフト表への接続 | 未提出化しても希望と提出履歴を保持し、古い画面から保存できない |
| 3 | 変更通知と催促 | 変更ごとに通知し、新しい締切に対応する催促だけが有効になる |
| 4 | 編集画面と再読み込み案内 | 既存の募集一覧から編集でき、変更の影響を確認して保存できる |
| 5 | 対象テスト・文書更新 | 下記の受入条件を検証し、実装後の機能文書を更新する |

### 1. データ項目と募集編集API

既存テーブルへ次の項目を追加する。項目名は実装案であり、画面に新しいステータスとして表示しない。

| 保存先 | 項目案 | 意味・既存データの扱い |
|---|---|---|
| `recruitments` | `editVersion?: number` | 募集条件の変更ごとに増やす番号。未編集の既存募集は省略を `0` と扱う |
| `shiftSubmissions` | `needsResubmission?: boolean` | 既存の提出行を保持したまま未提出扱いにする印。省略は `false` と扱う |
| 催促の予約引数・Outbox | `recruitmentVersionAtOrigin?: number` | 予約時の募集の版。古い催促を送らないために使用し、変更通知の取消には使用しない |

`shiftSubmissions` が存在し、`needsResubmission !== true` のときに「提出済み」と判定する。  
`firstSubmittedAt` は初回提出の履歴として保持する。再提出成功時は印を解除し、既存の `submittedAt` を更新する。新しい提出テーブルや提出履歴の複製は不要である。

`convex/recruitment/mutations.ts` に編集用の `managerMutation` を追加する。  
募集ID、画面を開いた時点の版、期間・定休日・締切を受け取り、以下を一つのトランザクションで行う。

1. 既存の管理者認証と店舗境界で対象募集を取得し、削除状態、確定状態、変更前の開始日・締切、版の一致を確認する。
2. 募集作成と同じ日付制約を検証し、定休日の重複と順序を正規化する。変更前後の勤務対象日から追加日・削除日を求める。
3. 削除日の希望・割当を物理削除する。追加日があれば、募集の既存提出行に再提出が必要な印を付け、対象スタッフの提出人数を更新する。残る日の希望・割当は保持する。
4. 募集条件と版を更新する。通知対象は既存の有効なシフト対象スタッフの判定を使う。
5. 同じ保存の中で変更通知の処理と将来の催促を予約する。通知の外部送信は既存の非同期処理に任せる。

正規化後に条件が同じなら変更なしとして終了し、通知、版の更新、催促の追加は行わない。  
別募集との重複を探す作成時のチェックは編集APIへ持ち込まない。募集の `submissionPattern` も作成時の値を維持する。

読み取りは募集IDの既存インデックスと既存の件数上限を使い、上限超過を検出して保存全体を中止する。途中まで削除・更新する処理にはしない。  
通常の対象件数では一つのmutationで完結する設計とし、分割削除のジョブは先に追加しない。

### 2. 提出・集計・シフト表への接続

「提出行が存在するか」だけで現在の提出済みを判定している箇所を更新する。判定の共通化は既存の提出ユースケース内で行い、汎用的な状態管理基盤は作らない。

| 対象 | 対応 |
|---|---|
| 希望の取得・提出・完了画面 | 保持した希望を初期表示する。未提出に戻った人を完了扱いにしない。締切後は未確定・開始前の未提出者だけ提出を許可する |
| 募集一覧・提出人数 | 再提出待ちを未提出として数え、再提出で人数を戻す。所属変更時の再集計や既存の集計フォールバックも同じ判定にする |
| シフト表 | 現在の提出状況と、下書き作成時の提出履歴を分ける。`firstSubmittedAt` と `draftSavedAt` を編集で書き換えない |
| 下書き保存後の再提出 | 合意したケースでは追加日の希望を表示し、管理者が割り当てる。未提出化を理由に既存の希望を割当へ戻さない |
| 帳票・提出リンク | 対象外の日のデータ削除と最新の募集条件を反映する。同じ提出URLを使い、リンクの一括失効・再発行は行わない |

スタッフの提出、管理者の募集編集、シフト表の保存・確定では、画面を開いた時点の版を送信し、サーバーで現在の版と比較する。  
不一致なら保存せず、変更を知らせて再読み込みを案内する。最新queryの版だけを送信して、古い入力を新しい条件への回答として受け付けないようにする。

募集queryの更新では既存フォームの入力日は自動で初期化されないため、変更検知時は新しい見出しと古い入力欄が混在したまま操作できないようにする。  
ユーザーが再読み込みしたら保存済みの希望から初期化し、未保存入力は引き継がない。管理者画面も自動統合せず、同じ考え方で復旧する。

募集を縮小してから再拡張した場合も、古いシフト表から削除済みの割当が再保存されることを版の比較で防ぐ。  
開始日を延長して既存のスタッフセッションが先に失効した場合は、同じ提出URLを開き直す既存の再認証を使い、セッションの一括延長は追加しない。

Analyticsの既存提出率は「初回提出」を数える定義のため、今回独自に再定義しない。  
既存構成では募集編集時の `cycle.changed` を記録して期間・締切を更新し、初回提出事実を保持する。別の[Analytics再設計計画](2026-09-05_Analytics日次利用指標と問い合わせ閲覧_設計実装計画.md)が先行する場合は、その提出成功記録へ再提出も通す。未提出への変更自体を提出実績には数えない。

### 3. 変更通知と催促

変更通知は既存の `kind: recruitment` の処理に変更用の `purpose` を追加し、LINE・メールの選択、fallback、再試行、通知履歴を再利用する。  
通知の識別キーに募集の版を含め、同じ編集の再試行による重複を防ぎつつ、別々の編集の通知はそれぞれ送る。初回募集通知の固定キーと混同しない。

連続編集の通知をまとめたり、古い変更通知を取り消したりしない。  
通知本文は生成時点の募集条件を使う。厳密な変更前後の履歴や編集別の保存データは新設しないため、通知が届く順序と編集の順序は保証せず、提出URLで最新条件を確認できる形にする。文言は後で決める。

変更通知は、本文の生成時と送信直前に、未削除・未確定・開始前であることと対象スタッフの有効性を確認する。  
締切経過だけでは止めない。既存の募集開始通知には従来の締切判定を残す。変更用の目的はfallbackや失敗通知の再送にも引き継ぐ。

| 通知 | 編集時の扱い | 送信時の確認 |
|---|---|---|
| スタッフへの自動催促 | 新締切の前日17時が未来なら予約し直す。同時刻または過去なら追加予約しない | 現在の版、未確定、締切前、現在も未提出、有効な対象スタッフ |
| 管理者への確定催促 | 既存の締切翌日17時を変更後の締切から計算し直す | 現在の版、現在の締切を経過、未確定、有効な対象管理者 |
| 変更通知 | 保存ごとに対象スタッフ全員へ予約する | 未確定・開始前。後続の編集との版の違いでは止めない |

実際の編集ごとに版を更新するため、締切が同じでも、まだ未来の催促は同じ時刻に新しい版で予約し直す。  
古い予約は実行時の版の比較で何もせず終了する。既存の `reminderScheduledAt` と `lastReminderSentAt` は、新しい催促予定に合わせて更新・クリアし、古い処理による送信済み記録の上書きも版で防ぐ。

既にOutboxへ入った催促にも送信直前の版・提出状態の確認を適用する。同じ催促を作る既存経路とfallback・再試行にも必要な情報を通す。  
予約取消専用のテーブルや追加の時間しきい値は作らない。外部サービスへの送信開始後の取り消しは保証の対象にせず、送信直前の確認までをアプリ側の契約にする。

### 4. 編集画面

Dashboardと組織の募集管理で共用している募集行のメニューに編集導線を追加する。  
既存の `CreateRecruitmentForm` を編集モードでも使い、店舗を固定し、保存済みの期間・定休日・締切を初期表示する。新しいルートは作らない。

作成用フォームの期間変更処理は、現在、定休日を店舗の曜日設定から作り直すため、そのまま流用しない。  
編集では残る日の選択を保持し、新しく期間に入る日の初期値に既存の曜日設定を使う。最終的な定休日は利用者が確認・変更できる。

既存の確認ステップに変更後の条件、全員が未提出になるか、対象外の日の希望・割当が削除されることを表示する。  
個々の割当を列挙する専用プレビューや追加の確認ダイアログは作らず、現在のフォーム内で保存の影響を伝える。ボタン、完了表示、催促予定の表示を編集に合わせる。

| 一覧から編集、影響確認、保存・失敗時の操作 | Storybook Behavior | 募集一覧・募集フォーム・希望提出の既存Storyを更新 |

日付のケースはAPI側を主担当とし、UIやE2Eへ同じ組合せを重複させない。  
Functionで時刻・権限・通知集合を検証し、Scenarioには複数APIをまたぐ代表的な永続化の確認だけを置く。手動ブラウザ確認や新規E2E基盤は追加しない。

実装時は対象テストから実行し、最後に `pnpm lint`、`pnpm type-check`、`pnpm test`、`pnpm build` を実行する。  
実装が完了した範囲の `doc/features/shift-recruitment-management.md`、`shift-submission.md`、`shift-board.md` と、通知・催促の関連文書を更新する。現時点では計画文書だけを更新する。

## 互換性・認可・運用

追加する保存項目には省略時の意味があるため、既存データの一括書換えは不要とする。  
既存APIと予約引数の版は省略を `0` として受け付け、未編集募集の旧画面・旧予約を継続利用できるようにする。編集済み募集へ版のない旧画面から保存する場合は、再読み込みを案内する。新しい編集APIでは版を必須とする。

変更後のデータと予約を扱うコードが揃ってから編集導線を公開する。  
この計画には実deploymentへの接続・反映・migration実行を含めない。互換性を確認せず旧コードへ戻すと未提出の判定や予約が崩れるため、問題時は編集導線を止め、対応済みのデータ読取・通知判定を維持する。

| Security Lens | 対応 |
|---|---|
| Actor / Asset | 店舗管理者による募集編集と、スタッフ自身の希望提出。対象は募集、希望、割当、提出人数、通知先 |
| Trust boundary / Abuse case | 別店舗の募集ID、権限喪失、期限・確定との競合、古い画面からの再保存、古い催促の再実行 |
| Server-side enforcement | 既存wrapperから権限・店舗を確定し、保存時の募集状態・版・日付を検証。通知直前も対象と状態を再確認 |
| Rate limit / Idempotency | 既存の送信制限とフォームの多重実行防止を使う。版の比較、変更なし判定、同一編集の通知キーで再試行の重複を防ぐ |
| Lifecycle / Recovery | 提出URLは維持し、古い画面は再読み込み。対象外データは削除し、自動復元しない。催促の旧予約は版で無効化 |
| Logs / PII | tokenや通知先の個人情報を新たなログへ出さない。既存の通知履歴・エラーの伏せ字処理を使う |
| Regression test | 別店舗・権限なし・期限後・古い版を拒否し、通知の対象人数と不要な通知がないことを検証 |

## 工数と残る判断

合意仕様を変更する必要や、大きな追加基盤を作る必要は、今回の調査では見つかっていない。  
UIの追加だけではなく、提出状態を参照する複数箇所と通知の再試行への対応が必要であり、そこを実装・レビューの重点にする。

| 項目 | 工数を抑える判断 |
|---|---|
| 未提出化の影響範囲 | 提出行と履歴を保持し、一つの印で現在状態を判定する。初回提出時刻を作り直さない |
| 古い画面の扱い | 一つの募集の版を共用し、自動入力統合を行わない |
| 通知と催促 | 既存基盤を使い、変更通知の集約・厳密な編集履歴・新しい時間しきい値を設けない |
| 通常件数を超える保存 | 実装検証で一括処理が成立しないと判明した場合だけ、必要な追加工数と対応案をまとめて示す |
| 通知文言とAnalyticsの接続順 | 文言は後決めのまま進める。Analyticsは別計画の進捗に合わせ、今回の機能で独自再設計しない |

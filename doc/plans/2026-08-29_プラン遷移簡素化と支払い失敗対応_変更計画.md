# プラン遷移簡素化と支払い失敗対応 変更計画

- 状態: `rollout verification`
- 作成日: 2026-08-29
- Repository実装: 2026-08-29完了。Stripe Sandbox canary、顧客向けメール設定と実到着、Production反映は未確認
- 対象: Trial、Free、Standard、Proの遷移、Stripe決済、確認ダイアログ、支払い失敗の画面表示
- 対象外: 料金改定、返金、有料契約全体を終了する支払い失敗での未払いInvoiceの`void` / `uncollectible`判断、年払い、カード以外の支払い、支払い失敗を知らせるシフトリ独自メール

## 1. 結論

利用者に見せるプランはTrial、Free、Standard、Proだけとする。

支払い結果待ち、支払い失敗、変更予約は「プラン」として表示しない。
支払い結果待ちは内部workflow、変更予約は現在プランに付属する予約情報、支払い失敗はFreeへの変更理由として分けて扱う。

支払いの猶予期間は設けない。
Trial終了時の初回請求、Standard / Proの通常更新、ProからStandardへの変更適用時の初回請求を確認できない場合は、終了処理中からFree権限へ変更する。
Stripe側の契約終了と請求回収停止を確認した後に、通常のFree状態へ確定する。

StandardからProだけは即時変更と日割り請求を行う。
支払いを確認できなければProを有効にせず、Standardを維持する。

## 2. プラン遷移マトリクス

| 現在 \ 変更後 | Trial | Free | Standard | Pro |
|---|---|---|---|---|
| **Trial** | ＝ そのまま継続 | △ 未契約または継続予約取消後、Trial終了時 | △ 継続登録後、Trial終了時の支払い成功 | △ 継続登録後、Trial終了時の支払い成功 |
| **Free** | × Trialは再開できない | ＝ 変更なし | ○ Stripe支払い成功後 | ○ Stripe支払い成功後 |
| **Standard** | × | △ 解約予約後、契約期間終了時 | ＝ 変更なし | ○ 日割り支払い成功後 |
| **Pro** | × | △ 解約予約後、契約期間終了時 | △ 変更予約後、契約期間終了時の支払い成功 | ＝ 変更なし |

上表の「△」は予約の確定であり、操作直後に現在プランを変えない。
同じプランと実行不可能な遷移では確認ダイアログを開かない。

`complimentary.pro`は運用が付与する支払い不要のPro相当であり、通常のプラン変更導線の対象外とする。

## 3. 状態の簡素化

### 3.1 利用者に見せる商品状態

| 状態または付属情報 | 役割 |
|---|---|
| `trial` | Trial終了日と、登録済みの継続先Standard / Proを持つ |
| `active.free` | Freeの利用権限を持つ |
| `active.standard` | Standardの利用権限を持つ |
| `active.pro` | Proの利用権限を持つ |
| `complimentary.pro` | 支払い不要のPro相当を持つ |
| `scheduledChange` | 現在プランと変更先、適用日、Stripe対応関係を持つ。画面では現在プランと予約を分けて表示する |
| `lastPlanChange` | 最後のプラン変更理由、変更前プラン、発生日時を持つ |

`scheduledChange`は予約という業務状態のため保存する。
参照APIは`currentPlan`と予約内容を分けて返し、ProからStandardへの変更予約中の現在プランをProと表示する。

`lastPlanChange.reason` は少なくとも`paymentFailed`を持つ。
これは新しいプラン状態ではなく、Freeへ変更された理由を画面で説明するための有限なメタデータとする。
新しい有料プランの支払い成功を確認したときに消去する。

### 3.2 中間状態の扱い

| 現行state kind | 変更後 |
|---|---|
| `initialPaymentPending` | 内部workflowとして残す。Trial終了時のInvoice確定までの短期状態とし、プラン名やバッジに表示しない。支払い未確認中にStandard権限を付与しない |
| `pendingActivation` | 内部workflowとして残す。Checkoutや即時変更の重複防止に使い、画面にはFreeまたはStandardのfallbackを現在プランとして表示する |
| `grace` | 削除する。支払い失敗後の14日猶予と有料権限維持を廃止する |
| `paymentTerminationPending` | 内部workflowとして追加する。検証済み未払いからStripe側の契約終了までを追跡し、開始時点からFree権限を適用する。プラン名やバッジに表示しない |
| `scheduledChange` | 保存する。変更予約と解約予約の取消、期間末適用に必要である。利用者には現在プランと予約として表示する |

外部APIの応答待ちや再試行中は、内部workflowとStripe operationの`queued | processing | retrying | actionRequired | failed | succeeded`で追跡する。
この技術的な収束期間を利用者向けのプランまたは支払い猶予期間として扱わない。

現行の`paymentFailed`は保存stateではなく、`pendingActivation`をfallbackへ戻す特殊な遷移命令である。
Checkout取消、Checkout期限切れ、provider障害、実際の請求失敗を同じ表示理由にしないため、内部workflowの解消命令と、検証済み請求失敗の`lastPlanChange.reason`を分ける。

## 4. 支払い失敗の対象と結果

| シナリオ | 支払いを確認できない場合 | 表示理由 |
|---|---|---|
| Trial終了時のStandard / Pro初回請求 | 直ちにFree権限へ変更し、Stripe側の契約終了と請求回収停止の確認後に`active.free`へ確定 | `paymentFailed` |
| Standard / Proの通常更新 | 直ちにFree権限へ変更し、Stripe側の契約終了と請求回収停止の確認後に`active.free`へ確定 | `paymentFailed` |
| ProからStandardへの変更適用時のStandard初回請求 | Standardを有効にせず直ちにFree権限へ変更し、Stripe側の契約終了と請求回収停止の確認後に`active.free`へ確定 | `paymentFailed` |
| FreeからStandard / Proへの新規契約 | 有料プランを有効にせず、Freeのまま | 新規契約未完了として扱い、Freeへの変更通知は出さない |
| StandardからProへの日割り請求 | 当該変更のInvoiceを`void`し、`pending_update`解消とStandardのPrice維持を再取得で確認する。Proを有効にせず、Standardのまま | 変更未完了として扱い、Freeへの変更通知は出さない |

`invoice.payment_failed`と`invoice.payment_action_required`は、一律にFreeへ変更する指示として使わない。
対象Invoiceと最新Subscription、現在のプラン、予約、operationを照合し、上表のどのシナリオかをサーバー側で決める。

## 5. Stripeからの検知と収束

| 順序 | 確認または処理 | 保証 |
|---:|---|---|
| 1 | `/stripe/webhook`でraw bodyと署名を検証する | 検証前にDBへ反映しない |
| 2 | Stripe Event IDを受信台帳へ保存し、workerを起動する | 同じイベントの再送を一回に収束する |
| 3 | Stripe APIからEvent、Invoice、Subscriptionを再取得する | Webhook本文だけを根拠にしない |
| 4 | mode、Customer、Subscription、Price、最新Invoice、予約とoperationの世代を照合する | 別組織、test / live混在、古いイベントを拒否する |
| 5 | Invoiceが`open`、`amount_remaining > 0`、Subscriptionが`incomplete`、`past_due`、`unpaid`のいずれかであることを確認する | 支払い済みと不明な状態を失敗と断定しない |
| 6 | `paymentTerminationPending`と`reason = paymentFailed`を保存し、Free権限を即時適用する | 外部処理の再試行中も未払いの有料権限を残さない |
| 7 | Subscription終了と対象Invoiceの`auto_advance: false`を冪等に実行する | 途中失敗はleaseと安定したidempotency keyで再開し、新契約を開始させない |
| 8 | Stripe側の終了と自動回収停止を確認後、`active.free`と`lastPlanChange.reason = paymentFailed`を同じmutationで保存する | Free権限を維持したまま内部workflowだけを完了する |
| 9 | 未承認の管理者招待を失効させ、安全な監査記録を残す | 人物、店舗、シフトは削除しない |

`customer.subscription.deleted`だけで支払い失敗と表示しない。
利用者の解約、運用操作、支払い失敗を区別できないため、署名検証済みの支払い失敗ワークフローからの因果を引き継ぐ。

古い`invoice.paid`や支払い失敗後に停止したSubscriptionのイベントで、Freeから自動復帰しない。
復帰は新しい契約の支払い成功だけを根拠にする。

Subscription終了または請求回収停止が一時的に失敗した場合は、Free権限の`paymentTerminationPending`を維持して再試行する。
これは外部処理を安全に完了するための技術的な収束であり、有料権限を維持する猶予や支払い復旧期間は提供しない。

有料契約全体を終了する支払い失敗で保証するInvoice処理は自動回収停止までとする。
この経路では`void`または`uncollectible`への変更は会計方針を別途確定してから扱い、未確定のまま自動実行しない。  StandardからProへの未完了変更だけは、Standardを維持するために当該日割りInvoiceを`void`する。
古いInvoiceが後から支払い済みになっても自動復帰せず、運用上の要対応として記録する。

## 6. 支払い失敗の画面表示

支払い失敗はプランバッジへ集約せず、確認モーダルも自動表示しない。
現在プランはFreeと表示し、失敗の事実と対応はAlertで説明する。

| 表示場所 | 表示条件 | 表示内容 |
|---|---|---|
| ダッシュボード | 現在組織の有効権限がFreeかつ変更理由が`paymentFailed` | 同じAlertと「有料プランを契約する」導線 |
| プランと支払い | 現在組織の有効権限がFreeかつ変更理由が`paymentFailed` | 失敗理由の正本表示と再契約導線 |

Alertの文言は次とする。

| 要素 | 文言 |
|---|---|
| ヘッダー | 支払いを確認できなかったため、Freeプランへ変更されました |
| 本文 | 請求通知先メールアドレスにStripeから案内が届いている場合があります。有料プランを利用する場合は、支払い方法を確認して、もう一度契約してください。 |
| ボタン | 有料プランを契約する |

Alertは新しい有料プランの支払い成功を確認するまで表示する。
プラン一覧のバッジは「Free」のままとし、「支払い失敗」または「エラー」をプラン名として表示しない。

`paymentTerminationPending`では同じAlertを表示し、「有料プランを契約する」は無効にする。
ボタン付近に「支払い処理を終了しています。完了後に有料プランを契約できます。」と表示し、`active.free`への確定後に有効化する。

Stripeからの支払い失敗メールは、Stripe Dashboardの顧客向けメール設定が有効で、Stripe Customerの`email`に請求通知先メールアドレスが同期されている場合に限られる。
シフトリは同じ目的のメールを重ねて送らない。
Productionの設定と実到着はリポジトリから判定せず、実環境証跡があるまで未確認とする。

## 7. 確認ダイアログ

各ダイアログの「プラン」は、`Free → Standard`のように変更前と変更後を一行で表示する。
通常料金は`¥3,000(税込) / 1か月`の順で表示する。
通貨記号、3桁カンマ、税込表示、`/`の後の請求期間を一つの値にまとめる。

| 操作 | ヘッダー | 主なサマリ | 注釈 | 確定ボタン |
|---|---|---|---|---|
| Trial → Standard / Proを継続登録 | トライアル終了後も{Standard / Pro}プランを継続しますか？ | 対象組織、`Trial → Standard`、`¥3,000(税込) / 1か月`、請求開始日`2026年9月1日` | トライアル最終日までは料金がかからず、その翌日から請求が始まります。 | 支払いへ進む |
| Free → Standard / Pro | {Standard / Pro}プランを開始しますか？ | 対象組織、`Free → Standard`、`¥3,000(税込) / 1か月`、請求開始日「Stripeでの支払い完了日」 | 支払い成功の確認後に有料プランを利用できます。 | 支払いを続ける |
| Standard → Pro | Proプランへ変更しますか？ | 対象組織、`Standard → Pro`、Proの通常料金、今回の日割り請求額、次回更新日 | 日割り料金がすぐに請求されます。支払いを確認するまでStandardを維持します。 | Proへ変更 |
| Pro → Standard | Standardプランへの変更を予約しますか？ | 対象組織、`Pro → Standard`、`¥3,000(税込) / 1か月`、変更予定日、必要な整理数 | 変更予定日までProを利用できます。Standardの初回支払いを確認できない場合はFreeへ変更されます。 | プラン変更を予約 |
| Standard / Pro → Free | 期間末で解約しますか？ | 対象組織、`Standard → Free`、プラン変更日 | 変更日まで現在のプランを利用できます。店舗・ユーザー・過去のシフトは削除されません。 | 解約する |
| Trialの継続予約を取り消す | 有料プランの継続を取り消しますか？ | 対象組織、取り消す変更`トライアル → {Standard / Pro}`、プラン変更日 | Trial最終日まで利用でき、終了後はFreeへ変更されます。 | 支払い予約を取り消す |
| Pro → Standard予約を取り消す | プラン変更の予約を取り消しますか？ | 対象組織、取り消す変更`Pro → Standard`、変更予定日 | 予約を取り消し、次回更新後もProを継続します。 | 変更予約を取り消す |
| 解約予約を取り消す | 解約予約を取り消しますか？ | 対象組織、取り消す変更`{Standard / Pro} → Free`、契約終了日 | 予約を取り消し、次回更新後も現在のプランを継続します。 | 解約予約を取り消す |

対象Priceを取得できない場合は、料金を推測せず確定ボタンを無効にする。
プラン変更日と請求開始日はStripeから取得した値を日本語の日付で表示し、クライアントで請求日を推測しない。

## 8. 実装順序

### Phase 1: ドメインと保存状態

1. 利用者向けのプラン投影をTrial、Free、Standard、Proに統一する。
2. `grace`、`PAYMENT_GRACE_PERIOD_MS`、14日deadline、猶予復旧分岐を削除する。
3. `initialPaymentPending`、`pendingActivation`、`paymentTerminationPending`を内部workflowに限定し、支払い成功前または検証済み未払い後の有料権限を付与しないpolicyに更新する。
4. `paymentFailed`遷移命令を通常のworkflow解消と実請求失敗に分け、終了処理中の理由と、確定後の`lastPlanChange.reason = paymentFailed`を保存する。

主な対象は`convex/organization/validators.ts`、`convex/schema.ts`、`convex/organizationBilling/policy.ts`、`convex/organizationBilling/mutations.ts`、`convex/organizationBilling/deadline.ts`とする。

### Phase 2: Stripeの支払い失敗ワークフロー

1. Trial初回請求、通常更新、ProからStandardへの変更適用時を分類する。
2. 失敗検証後にFree権限の`paymentTerminationPending`へ移し、Subscription終了とInvoiceの`auto_advance: false`を確認後に`active.free`へ収束する。
3. StandardからProへの日割り請求失敗はStandardへ、FreeからのCheckout未完了はFreeへ収束する。
4. 重複、順不同、古い成功イベント、再試行、同時契約操作を同一のワークフローで収束させる。

主な対象は`convex/http.ts`、`convex/organizationStripe/webhook.ts`、`convex/organizationStripe/mutations.ts`、`convex/organizationStripe/actions.ts`、`convex/organizationStripe/subscriptionEvidence.ts`とする。

### Phase 3: 参照APIと画面

1. プラン参照APIは現在プラン、予約、支払い失敗Alertに必要な最小情報だけを返す。
2. 請求失敗の正本Alertを「プランと支払い」、同じ導線をダッシュボードへ追加する。
3. ダイアログstateへ変更前プランを渡し、全パターンを`Before → After`で表示する。
4. 共有料金formatterを`¥3,000(税込) / 1か月`に統一し、プランcard、確認ダイアログ、公開料金表示への波及をテストする。
5. ダイアログの日付、ヘッダー、注釈を7章に統一する。
6. バッジは実際のプランだけを表示する。現在実画面から使われていない`PlanStatusCard`の支払い問題バッジは再利用しない。

主な対象は`convex/organization/queries.ts`、`convex/dashboard/queries.ts`、`src/components/features/OrganizationSettings/BillingSettings/`、`src/components/features/OrganizationSettings/PlanAndPaymentSection.tsx`、`src/domains/organizationBilling/pricePresentation.ts`、`src/pages/dashboard/index.tsx`とする。

### Phase 4: 不要状態と開発用シナリオの削除

1. `grace`の分岐、deadline、scheduler、猶予復旧テストを削除する。
2. `payment-grace`のStory、seed、表示を支払い失敗後Freeのシナリオへ置き換える。
3. `planIdVersion`、旧`pro | business`のread / response投影、未公開プランID切替だけのreadinessとm042〜m047のrunnerを削除する。
4. 現行実装仕様と運用手順を実装結果に合わせ、実環境の設定とcanaryは証跡取得後にリリース状態へ記録する。

| 失敗境界 | 主担当層 | 検証内容 |
|---|---|---|
| プラン遷移と遷移理由 | Convex Function / Scenario | マトリクスの可能、予約、即時、不可能、同一プラン、Freeへの変更と`paymentFailed`理由の原子性 |
| Webhook受信 | Convex Function | 署名不正の拒否、Event ID dedupe、対象外event、再送 |
| 支払い失敗収束 | Convex Function / Scenario | Trial初回請求、通常更新、ProからStandardへの初回請求、終了処理中からFree権限、cleanup失敗の再試行、旧Invoiceの遅着、二重契約防止 |
| 即時契約とアップグレード | Convex Function / Scenario | Freeからの失敗はFree、StandardからProの失敗はStandard、支払い成功前の権限非開放 |
| 参照DTO | Convex Function | 別組織非開示、現在プラン、予約、最小の支払い失敗表示情報、再契約成功時の理由消去 |
| ダイアログとAlert | Frontend Unit / Storybook Behavior / VRT | プランの矢印表示、`¥3,000(税込) / 1か月`、全パターンの文言、料金取得失敗、PC / SP、長い組織名 |

実StripeのWebhook到着、契約終了、顧客向けメール到着は自動E2Eの正本にしない。
Stripe Sandboxのcanaryと実環境証跡で別に確認する。

## 10. Security Lens

- Actor: Stripe、組織の有効管理者、内部workerである。
- Asset: 有料機能の利用権限、契約、未払い請求、請求通知先メールアドレス、Freeへの変更理由である。
- Trust boundary: Stripeから`/stripe/webhook`への境界、Webhook受信台帳からinternal workerへの境界、サーバーから管理画面への境界である。
- Abuse case: 偽造Webhook、重複・順不同event、test / live混在、別組織のCustomer・Subscription参照、古いInvoiceによる誤ったFree変更、解約を支払い失敗と誤表示することである。
- Server-side check: 署名、mode、Customer、Subscription、Invoice、Price、組織mapping、最新性、operationの世代、現在状態を再確認する。
- Rate limit and idempotency: Stripe Event ID、operationの安定したidempotency key、lease、retryで一回に収束する。
- Lifecycle and recovery: Stripe側の契約終了と請求回収停止を確認するまで再試行し、古い成功eventで自動復帰せず、新契約成功時に表示理由を消す。
- Logs and PII: カード情報、Webhook raw body、完全なメールアドレス、Stripe Secretをログへ残さない。
- Regression test: 上記の組織分離、改ざん防止、冪等性、順不同、権限非開放、理由の正確性、UI表示と消去を検証する。

## 11. Migrationと互換性

このプラン機能は公開前であり、旧状態を読み替える移行互換は作らない。
Widen、backfill、旧writerと旧readerの併存、migration jobは追加しない。

Schema、seed、fixture、test、実装を同じ変更で直接置き換える。
削除する`grace`と未公開のplan ID互換に対し、保存済みの旧課金stateや進行中operationを引き継ぐことを受入条件にしない。

既存の`planIdVersion`、旧`pro | business`互換、m042〜m047とそのreadinessは、未公開プランID切替だけを目的とする範囲を削除対象とする。
管理者招待など別機能のmigration、汎用migration基盤、過去の意思決定を示すplan文書は対象外とし、目的を照合せず一括削除しない。

Productionへの反映済み、Stripe設定済み、データが空であることはこの計画から推定しない。
公開前の対象環境に旧課金stateが残っている場合は、その環境のテストデータ再作成を別の運用作業として扱う。

## 13. 受入条件

- 利用者向けプランとしてTrial、Free、Standard、Pro以外を表示しない。
- マトリクス以外の遷移をサーバー側で拒否し、StandardからProだけを即時の日割り請求にする。
- Trial初回請求、通常更新、ProからStandardへの初回請求を確認できない場合に猶予を付与せず、終了処理中からFree権限を適用し、Stripe側の停止確認後に`active.free`へ確定する。
- 支払い失敗でFreeへ変更した事実をダッシュボードと「プランと支払い」で確認でき、新しい有料契約成功後は表示しない。
- 確認ダイアログが変更前プラン、変更後プラン、金額、請求・適用日、即時または予約を一意に説明する。
- プラン機能の旧state向けmigration、backfill、互換分岐を追加しない。
- 自動テストとStripe Sandbox canaryの役割を分け、Productionの反映とメール到着を証跡なしに確認済みとしない。

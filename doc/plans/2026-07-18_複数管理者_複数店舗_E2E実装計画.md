# 複数管理者・複数店舗 E2E実装計画

作成日: 2026-07-18

状態: 完了

対象差分: `develop...HEAD`

## 1. この計画の位置づけ

この文書は、`develop`との差分で追加された複数管理者・複数店舗機能と、その変更が影響する既存機能へ自動テストを追加するための実行計画である。

課金機能そのものは検証対象にしない。

ただし、複数管理者・複数店舗の操作を可能にする固定entitlementは、テストfixtureの前提として作成する。

業務仕様の正本は`doc/specs/organization-billing-business-flow.md`、現行機能の配置とAPI一覧は`doc/features/organization-billing.md`とする。

テスト層の分担は`doc/rules/testing-strategy.md`、E2Eの実装規約は`e2e/AGENTS.md`を正とする。

この文書は、過去の`doc/plans/2026-07-13-e2e-full-regression.md`で複数店舗・複数管理者を準備中として対象外にした判断を、今回のP0契約について上書きする。

課金、Stripe、プラン変更、請求、provider実到着を対象外にする判断は上書きしない。

## 2. Goal開始時の目的文

Goalには次の目的文をそのまま使用する。

```text
doc/plans/2026-07-18_複数管理者_複数店舗_E2E実装計画.mdを唯一の実行計画として、課金機能を検証対象にせず、MM-P0-01からREG-P0-03までを実装・検証する。各フェーズの着手条件と完了条件を満たしたら人への確認を挟まず次へ進み、全体終了条件を満たすまでテスト失敗とレビュー指摘を自己修正する。新しいブランチまたはworktree、production操作、実配送、migration、招待取消UI、課金UIの変更へは広げない。
```

明示的なtoken budgetは設定しない。

## 3. 目的

次の状態を自動テストで保証する。

- 管理者Aが既存スタッフBを管理者として招待し、別のClerkアカウントBが本人確認後に連携できる。
- 連携後の管理者Bが同じグループの全店舗へアクセスし、代表的な管理操作を完了できる。
- 管理者権限だけを外した場合は管理画面アクセスが失効し、既存のスタッフ所属は維持される。
- 人物をグループから削除した場合は対象グループへのアクセスが失効し、別グループの所属は維持される。
- 管理者が店舗を追加し、店舗を切り替え、店舗固有データを編集しても別店舗へ混入しない。
- 同じグループの他店舗スタッフを新しい店舗へ追加しても、人物や既存店舗所属を壊さない。
- 選択中店舗を削除した場合は削除済み店舗を描画せず、安全なエラーから残存店舗へ復旧できる。
- シフト作成、スタッフ登録申請、通知など既存の主要導線が、正規のグループ・複数店舗モデル上でも動作する。

## 4. 対象範囲

### 4.1 対象

- 管理者招待、アカウント連携、複数管理者での代表管理操作。
- 管理者権限解除とグループからの人物削除。
- 店舗追加、店舗切り替え、店舗編集、店舗削除。
- グループ内の他店舗スタッフ再利用。
- 複数店舗に影響するシフト作成、提出、下書き、確定、通知、閲覧。
- 複数店舗に影響するスタッフ登録申請と承認。
- 複数管理者に影響する代表通知と、管理者権限変更後の通知対象。
- 上記E2Eに必要な正規グループseed、owner単位reset、複数actor fixture、Page Object、redacted probe、CI設定。
- 管理者連携完了通知のCTAへ、対象グループの代表店舗を示す`?shop=`を付ける最小の既存機能修正。
- 管理者権限解除とグループ削除の確認Dialogに対するBehavior Test。

### 4.2 対象外

- Stripe Checkout、Customer Portal、Webhook、支払い成功・失敗、プラン変更、請求書、課金通知。
- プラン名、料金、利用上限、支払い状態、課金画面の表示または操作のassertion。
- `organizationBilling/actions.ts`にある課金通知CTAの変更。
- providerへのメール・LINE実到着とClerk認証画面内部の検証。
- 管理者招待の取消UIと取消E2E。
- 招待取消のtoken失効、期限、IDOR、予約枠解放の再網羅。
- 最後の管理者、最後の店舗、上限、rate limit、並行mutation、requestId冪等性のブラウザ網羅。
- schema変更、migration、backfill、Narrow、table、job、queue、汎用テスト基盤の新設。
- P1候補である複数tab、全画面のモバイルE2E、プロフィール同期、店舗単位の人物削除、設定画面全体のaxe追加。
- `apps/analytics-dashboard/`。

管理者の「削除」は、`removeManagerRole`による管理者権限解除と、`removePersonFromOrganization`によるグループ所属削除を指す。

未連携の招待を取り消す`organizationInvitation.revoke`はバックエンド契約が既存Function Testにあるが、現行UIから到達できないため今回のE2Eへ含めない。

## 5. 変更しない決定事項

実装中に次の判断を再検討しない。

| 項目 | 固定する判断 |
|---|---|
| 課金前提 | fixtureは期限と外部課金処理を持たない`complimentary.business`相当の利用可能状態に固定する |
| 課金assertion | 課金状態、プラン名、上限、支払いUIをassertしない |
| 無効な`?shop=` | 別店舗へ黙ってfallbackせず、「この店舗を開けません」を表示する |
| 削除後の復旧 | 「ダッシュボードへ戻る」から残存するA店を解決する |
| 管理者権限解除 | Bの管理画面権限だけを失効し、Bの既存スタッフ所属を維持する |
| グループ削除 | Bの対象グループ内アクセスを失効し、Bの別グループ所属を維持する |
| 招待受諾 | Bは連携後に対象グループの全店舗へアクセスできる |
| 招待メールtoken | 通常probeへ混ぜず、E2E限定の専用token helperからだけ取得する |
| 通知probe | PII、raw token、本文、provider error全文を返さない |
| 連携完了CTA | 通知送信時点で対象グループの代表店舗を再解決し、`/settings?shop=<shopId>`とする |
| 招待の永続shape | CTAのために`organizationInvitations`へ`shopId`を追加しない |
| 招待取消 | UIを追加せず、既存Function Testを主担当として残す |
| E2E browser | Desktop Chromeを主担当とし、今回の管理画面ケースをMobileへ複製しない |
| 店舗削除E2E | コメントアウトを解除するのではなく、現行グループ設定導線で全面的に書き直す |

## 6. 自律実行ルール

### 6.1 判断順序

実装判断は次の順で行う。

1. `AGENTS.md`、配下の`AGENTS.md`、テスト・セキュリティ・アーキテクチャ規約。
2. この文書の対象範囲、固定判断、契約ID、終了条件。
3. `doc/specs/organization-billing-business-flow.md`と`doc/features/organization-billing.md`。
4. 同じ層にある最も近い現行コードとテスト。
5. 過去のplan。

過去のplanと現行コードが異なる場合は、現行の機能文書とコードを優先する。

ファイル名やsymbolが移動している場合は`rg`で現行の同等責務を特定し、最小の配置変更だけを行う。

### 6.2 人へ確認せず進める範囲

- この文書に列挙したファイルの追加・更新。
- テスト失敗、型エラー、lint warning、セレクタードリフトの自己修正。
- 既存helperの小さな共通化と、200行を超えるE2Eファイルのユーザーストーリー単位の分割。
- task-ownedな変更ファイルだけのformat。
- 対象テスト、全テスト、E2E、build、lint、型チェックの実行。
- Codex sandboxでブラウザまたはIPC権限が必要なコマンドの権限付き実行。

通常の実装判断、テスト名、helper名、セレクター選択について人へ質問しない。

### 6.3 行わない操作

- 新しいブランチまたはworktreeの作成と切り替え。
- commit、push、PR作成。
- production、develop、共有Previewのデータ変更、migration、backup、provider canary。
- Vite、Convex、Storybookの起動コマンド。
- `convex/_generated/`、`src/routeTree.gen.ts`、`pnpm-lock.yaml`の手動編集。
- 作業開始時から存在する未関連差分の修正、削除、format。
- P0完了後にP1候補へ自動的に拡張すること。

### 6.4 既存作業の保護

開始時に`git status --short`を記録する。

2026-07-18時点では`convex/_generated/api.d.ts`に既存の未commit差分があるため、今回の変更として上書き、復元、stageしない。

ユーザーが起動しているConvexにより自動生成ファイルが変化した場合も、手動で内容を合わせない。

task-owned差分と既存差分が同じ非生成ファイルで衝突する場合だけ、衝突箇所を根拠付きで切り分ける。

## 10. E2Eシナリオ契約

### 10.1 `MM-P0-01` 管理者招待と共同管理

前提:

- 主グループに管理者A、A店、B店がある。
- BはA店の既存スタッフで、現在のメールはE2E ClerkアカウントBの確認済みメールと一致する。
- CはBと異なる確認済みメールのE2E Clerkアカウントである。
- 主グループは固定の利用可能entitlementを持つ。

操作と期待値:

1. Aが`/settings?shop=<A店>`のユーザータブからBを選び、管理者招待を一回送る。
2. 確認Dialogと成功Toastを確認する。
3. organization-scopeのredacted probeで、招待Outboxが目的、channel、対象招待、dedupeを含めて一件だけ受け付けられたことを確認する。
4. 専用token helperから現在有効な招待URLを取得する。
5. Cのbrowser contextでURLを開き、メール不一致の画面を確認する。
6. 同じURLをBのbrowser contextで開き、自動連携後に`/dashboard?shop=<A店>`へ移動することを確認する。
7. BがA店とB店の両方を切り替えられることを確認する。
8. BがB店で代表募集を作成し、AがB店へ切り替えて同じ募集を確認する。
9. A店にはB店の代表募集が表示されないことを確認する。
10. 連携完了通知がA/Bを対象として受け付けられ、CTAが`/settings?shop=<A店>`を指すことを確認する。

Cの不一致で招待が消費されないことのDB詳細と、A/B以外の宛先がないことの完全一致はScenarioまたはFunction Testへ置く。

### 10.2 `MM-P0-02` 管理者権限だけの解除

前提:

- 主グループに管理者A/Bがいる。
- BはA店の有効スタッフでもある。
- Bは別グループの管理者でもよいが、対象グループでは最後の管理者ではない。

操作と期待値:

1. AがBのユーザー詳細から「管理者権限を外す」を実行する。
2. スタッフ所属を維持する確認内容と成功Toastを確認する。
3. Aのユーザー一覧でBの管理者表示が外れ、スタッフ表示とA店所属が残ることを確認する。
4. Bが開いていた主グループのDashboardと設定画面をreloadし、対象店舗を表示できないことを確認する。
5. 明示した`?shop=<主グループ店舗>`から別グループへ黙ってfallbackしないことを確認する。

Bがmanager digest対象から外れ、スタッフ通知対象には残ることは`convex/_scenario/staffManagerInvitation.test.ts`で完全一致させる。

### 10.3 `MM-P0-03` グループからの削除

前提:

- 主グループに管理者A/Bがいる。
- Bは別グループと別店舗にも有効な管理者所属を持つ。
- Bに削除を妨げる将来シフトや請求先制約を作らない。

操作と期待値:

1. AがBのユーザー詳細から「グループから削除」を実行する。
2. 全店舗の所属と権限を終了する確認内容と成功Toastを確認する。
3. Aの主グループのユーザー一覧からBが消えることを確認する。
4. Bが主グループの既存URLをreloadし、汎用アクセスエラーになることを確認する。
5. Bが別グループの明示的な`?shop=`を開き、Dashboardを利用できることを確認する。

### 10.4 `MS-P0-01` 店舗追加・切り替え・編集

前提:

- Aが管理する主グループにA店だけがある。
- 主グループは固定の利用可能entitlementを持つ。

操作と期待値:

1. Aがグループ設定の店舗タブからB店を追加する。
2. 成功Toastと店舗一覧へのB店追加を確認する。
3. Dashboardの店舗切り替えからB店を選び、URLが`/dashboard?shop=<B店>`になることを確認する。

- Actor: 管理者A、招待先かつスタッフのB、メール不一致のC、管理者storage stateを持たないスタッフ利用者。
- Asset: グループ管理権限、店舗データ、スタッフ所属、招待token、通知対象、店舗コンテキスト。
- Trust boundary: Clerk identityと確認済みメール、`?shop=`、管理者招待token、user-controlledなshop/person/staff ID、E2E限定internal helper。
- Abuse case: CがBの招待で管理者化する、Bが権限解除後も管理画面へ入る、削除済み店舗URLが別店舗データへfallbackする、別店舗のスタッフ・募集・通知が混入する、raw tokenまたはPIIが通常ログ・probe・公開artifactへ残る、共有actorの並列resetで他scenarioを壊す。
- Server-side check: `linkAccount`で招待状態と確認済みメールを再確認し、manager wrapperでactiveなグループ所属と選択店舗を再確認し、権限解除・削除後は新しいrequestを拒否する。
- Rate limit / idempotency: 既存Function Testを主担当とし、E2Eは一回のUI操作と一回だけの可視結果を確認する。Behavior Testで確認callbackの連打を一回に抑える。
- Lifecycle / recovery: `issued -> linked`、`active manager -> staff only`、`active person -> removed`、`active shop -> deleted`と、削除済み店舗URLから残存店舗への明示復旧を確認する。
- Logs / PII: redacted probeへメール、LINE user ID、本文、raw token、provider error全文を含めない。招待tokenは専用helperからbrowserへ直接渡し、ログ、snapshot、test titleへ出さない。
- Regression test: 単一API境界はFunction、複数API後の対象集合と通知はScenario、実認証・URL・画面完了はE2E、Dialog状態遷移はBehaviorへ分担する。

## 13. 軽量ゲートと停止条件

### 13.1 ゲート一覧

| Gate | 次へ進む条件 | 次へ進まない条件 |
|---|---|---|
| `G0` | scope、baseline、規約、実行環境を把握した | 対象外をP0へ混ぜている |
| `G1` | canonical seed、reset、multi-actor、probe、CI preflightが対象テストを通った | shared actorが並列利用される、probeがPII/tokenを返す |
| `G2` | 管理者3契約、CTA、Scenario、Behaviorが成功した | skip/fixme/comment-out、スタッフ維持または別グループ維持が未確認 |
| `G3` | 店舗3契約と既存影響3契約が成功した | A/B非混入、削除後の汎用エラー、既存主導線のどれかが未確認 |
| `G4` | 全検証、結果ゲート、自己レビューが成功した | 未実行コマンド、flaky、lint warning、未修正findingがある |

### 13.2 継続して自己修正する条件

次はblockerではない。

- 実装またはテストの失敗。
- selector、文言、ファイル配置の現行コードとのドリフト。
- 型エラー、lint warning、format差分。
- fixtureの不足、テスト間のデータ競合、web-first assertionの待機不足。
- 近い既存helperを再利用するための小さな修正。

これらは原因を切り分け、P0契約と規約を変えずに修正して再実行する。

### 13.3 作業を広げずに除外する条件

次を発見しても今回の実装へ含めない。

- 課金UIまたはStripeの未完成。
- 管理者招待取消UIの未接続。
- P1候補の未実装。
- provider実到着、production challenge、production migration。
- 既存Full Regression全体の一般的な契約registry化。

対象外の不足は最終報告のfollow-upへ一行で残し、P0完了を妨げない。

### 13.4 Goalをblockedにする条件

Goalを`blocked`にできるのは、次の同じ外部条件が3回の連続するgoal turnで解消せず、非browser実装、対象下位層テスト、静的検証まで完了していて、これ以上安全に進めない場合だけとする。

- E2E Clerk credentialsが利用できない。
- ユーザー管理のViteまたはConvexが到達不能で、規約により新規起動できない。
- 必要なsandbox権限または外部Preview権限が継続して得られない。
- task-ownedでない同一箇所の変更と安全に統合できない。

blocked時は、失敗した正確なコマンド、終了code、環境由来と判断した根拠、完了済みgate、未完了契約IDを報告する。

設計上の軽微な選択、テスト失敗、作業量、残token量をblocked理由にしない。

### 13.5 完了にしてはいけない条件

次のどれかがあればGoalを`complete`にしない。

- P0契約IDが未実装、skip、fixme、コメントアウト、未実行である。
- E2Eだけがあり、対応する必要なFunction、Scenario、Behavior契約が不足している。
- billing assertionまたは対象外機能が混入している。
- raw tokenまたはPIIが通常probe、ログ、snapshot、公開artifactへ露出している。アクセス制御された失敗診断artifactは外部公開せず、7日間の保持だけを許容する。
- multi-actor scenarioと通常workerが同じClerk accountを並列使用する。
- 対象テストまたは全体検証が失敗している。
- 結果ゲートや自己レビューを省略している。

## 14. 全体終了条件

- `MM-P0-01`から`REG-P0-03`までの9契約が実装されている。
- 既存E2Eの共通seedがcanonical organization modelを通る。
- multi-actor E2Eが3つのstorage stateを直列かつ独立contextで使う。
- 管理者招待、権限解除、グループ削除が実browserと実Convex backendで完了する。
- 店舗追加、切り替え、他店舗スタッフ再利用、選択中店舗削除が実browserと実Convex backendで完了する。
- B店の代表シフト主導線と登録申請がA店へ混入しない。
- 連携完了通知と代表manager digestのCTAが対象店舗の`?shop=`を保持する。
- 4種manager digestとスタッフ通知継続がScenario Testで完全一致している。
- 管理者権限解除とグループ削除の確認状態がBehavior Testで保証されている。
- 課金機能、招待取消UI、provider実到着を検証していない。
- lint、型チェック、対象テスト、全テスト、build、Full Regression E2E、JSON結果ゲート、diff checkが成功している。
- skip 0件、flaky 0件、未修正レビューfinding 0件である。
- taskと無関係な既存変更を上書きしていない。

これらをすべて満たした時だけGoalを`complete`にする。

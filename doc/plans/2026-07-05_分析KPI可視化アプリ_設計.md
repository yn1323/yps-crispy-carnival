# 分析KPI可視化アプリ設計

作成日: 2026-07-05

## 1. 背景と目的

`convex/analytics/` で日次蓄積しているKPIを、Convexダッシュボードや `npx convex run` ではなく、専用の画面で見えるようにする。
本体アプリのドメインや画面導線へ混ぜず、このリポジトリ内に別アプリを作り、Cloudflare Pagesへ別プロジェクトとしてデプロイする。

日次蓄積は「後で傾向を見られる状態」を作るための土台であり、実際の価値は次の判断を速くすることにある。

- サービス全体の利用状況が伸びているか、停滞しているかを把握する
- 募集作成、提出、確定、通知、LINE連携のどこで詰まりが起きているかを見る
- productionの実データから、改善施策や不具合調査の優先度を判断する
- develop / previewでは、集計ロジックや表示ロジックのデバッグに使う
- 店舗単位の差分を見て、導入状況や運用状態の偏りを把握する

既存の本体アプリは、店舗運営者・スタッフが日々使うプロダクトUIである。
一方、この可視化アプリは開発者兼運営者が見る内部BIであり、利用者、操作頻度、必要な密度、セキュリティ境界が異なる。
そのため、本体アプリのドメインへ混ぜると、プロダクト導線の複雑化、権限境界の曖昧化、公開bundleへの不要な分析UI混入が起きやすい。

同じリポジトリに置く理由は、Convex schema、生成型、lint / type-check、デプロイ運用、集計ロジックへの近さを保つためである。
ただし、同じリポジトリだからといって、本体アプリのUI部品やrouting構造を過度に共有しない。
内部BIとして必要な密度と速度を優先し、共通化は「明確に重複コストが出た時」に限定する。

この可視化アプリは公開プロダクトではなく、運営者本人が見る内部BIとして扱う。
そのため、Storybook / E2E / VRT のようなプロダクト本体向けのUI検証は初期スコープから外す。
一方で、KPIには店舗運用データが含まれるため、画面入口の保護だけでなくConvexデータ取得経路も保護する。

## 2. 確定方針

| 論点 | 方針 |
|---|---|
| 配置 | `apps/analytics-dashboard/` に Vite + React の別アプリを作る |
| データソース | 既存 `convex/analytics/` の日次テーブルを読む。蓄積ロジックは変更しない |
| Frontend stack | Vite + React + Chakra UI v3 + TanStack Query + `@chakra-ui/charts` / Recharts を基本にする |
| Routing | 初期は単一Dashboard + URL search paramsで十分。店舗詳細を独立URLにしたくなったら、このアプリ内だけでTanStack Routerを導入する |
| 環境切替 | 画面内に production / develop / preview の切替UIは持たない。デプロイ環境やローカルenvが接続しているConvexを見る |
| production | 別Cloudflare Pages project + 別サブドメインで運用する |
| develop / preview | デバッグ目的。接続先Convex URLが該当環境ならそれでよい |
| 認証 | 初期はBasic認証相当をCloudflare Pages Functions middlewareで実装する。後からCloudflare Accessへ置き換え可能にする |
| Convex公開面 | ブラウザからConvex public queryを直接叩かない。Pages Functions経由でConvex HTTP actionへサーバー間通信する |
| UI範囲 | 既存分析KPIをすべて複数角度から見られるDashboardにする。サービス全体、イベント、通知、LINE、プラン、店舗別ドリルダウンを含める |
| 共通化 | 本体アプリと思想は合わせるが、UI部品・feature構造・状態管理を早期に共有しない。まずはアプリローカルに閉じる |
| AGENTS.md | `apps/analytics-dashboard/AGENTS.md` を作成し、このアプリの目的、責務、共通化しすぎない方針、セキュリティ境界を書く |
| テスト | Storybook / E2E / VRT は不要。セキュリティ境界だけは最小の回帰確認を推奨する |

## 3. 推奨アーキテクチャ

### 3.1 全体像

```text
[Browser]
  |
  | GET https://analytics.example.pages.dev/
  | Authorization: Basic ...
  v
[Cloudflare Pages: apps/analytics-dashboard]
  |
  | functions/_middleware.ts
  |   - Basic認証
  |
  | functions/api/analytics.ts
  |   - server-side envからConvex HTTP URLと秘密値を読む
  |   - ブラウザへConvex URL / secretを渡さない
  v
[Convex HTTP action: /analytics-dashboard/query]
  |
  | - x-shiftori-internal-api-secret を検証
  | - request bodyをvalidator相当で検証
  | - internal queryを呼ぶ
  v
[convex/analyticsDashboard/queries.ts]
  |
  | - 既存 analytics fetch helper / analytics tables を読む
  | - 画面用の最小DTOに整形
  v
[analyticsDailyServiceSnapshots]
[analyticsDailyShopSnapshots]
[analyticsDailyEventCounts]
```

Cloudflare Pages は複数アプリを同一リポジトリから別プロジェクトとして扱える。
Cloudflare Pages Functions middleware は静的ファイルの前段にも置けるため、Basic認証の入口として使える。
Convex HTTP actions は `.convex.site` のHTTP APIとして公開され、HTTP actionから `ctx.runQuery` で内部queryを呼べる。

### 3.2 Basic認証だけでConvexを直接読まない理由

Basic認証で画面HTMLを守っても、SPAがConvex public queryを直接呼ぶ構成では、Convex function名と引数が分かれば画面を経由せずに呼べる。
また、秘密値をViteの `VITE_*` 環境変数へ入れるとブラウザbundleへ埋め込まれる。

そのため初期実装では次を守る。

- ブラウザは `/api/analytics` のみを呼ぶ
- Convex URL、HTTP action用secret、Basic認証の正解値はCloudflare Pages Functionsのサーバー側envに置く
- Convex側はHTTP actionでsecretを検証し、secret不一致なら `401` を返す
- Convexの通常 public query は追加しない

`apps/analytics-dashboard/` は本体 `src/` の route/page/feature 境界とは独立させる。
共通化は依存パッケージ、Biome、TypeScript、Convex生成型の参照に留め、画面コンポーネントは内部BIとして小さく保つ。

本体アプリの構造から引き継ぐもの:

- page / feature / domain の責務分離
- Chakra UI v3 を前提にしたUI実装
- 日付やKPI算出を表示コンポーネントへ埋め込まない方針
- lint / type-check / Convex生成型を使った型安全性

初期段階で共有しないもの:

- 本体 `src/components/ui/` のUI wrapper
- 本体 `src/pages/` / `src/routes/` のrouting構造
- 本体アプリのJotai atomやフォーム部品
- Storybook stories、E2E、VRTの運用
- 共通UI packageの新設

共通化の再検討ライン:

- 同じ純粋関数が両アプリで3箇所以上に増えた
- 本体アプリと分析アプリで同じ型変換を保守する必要が出た
- Chakra theme tokenの差分が運用コストになった
- Convex DTOの境界を共有しないと型ずれが頻発する

それまでは、分析アプリ内に小さくコピーまたは再実装する。
このアプリは本人用の内部BIなので、早すぎる共通化より、変更しやすさとセキュリティ境界の明瞭さを優先する。

`pnpm-workspace.yaml` は次のように広げる。

```yaml
packages:
  - "."
  - "apps/*"

catalog:
  "@chakra-ui/react": "3.36.0"
  "@vitejs/plugin-react": "5.1.2"
  react: "19.2.5"
  react-dom: "19.2.5"
  typescript: "5.9.3"
  vite: "7.3.5"
```

root `package.json` の `dependencies` を、分析アプリが暗黙に借りる形にはしない。
pnpm workspaceでは各packageが自分の直接依存を `package.json` に明示するのが基本であり、rootの `node_modules` にたまたま存在する依存へ寄りかかると、Cloudflare Pagesのbuild条件や将来のworkspace分離で壊れやすい。

代わりに、たまたま本体アプリと分析アプリで共通になった依存だけを `pnpm-workspace.yaml` の `catalog` に昇格する。
各packageは依存を明示しつつ、versionだけroot側のcatalogを見る。

例:

```json
{
  "dependencies": {
    "@chakra-ui/react": "catalog:",
    "react": "catalog:",
    "react-dom": "catalog:"
  },
  "devDependencies": {
    "@vitejs/plugin-react": "catalog:",
    "typescript": "catalog:",
    "vite": "catalog:"
  }
}
```

分析アプリだけで使う依存は、最初は分析アプリ側に通常のversionで宣言する。
後から本体アプリでも使うことになった時点でcatalogへ移す。
これにより、「共通化したいものだけroot側を見る」状態にできる。

root `package.json` には将来、次のようなスクリプトを追加する。

```json
{
  "analytics:dev": "pnpm --filter @shiftori/analytics-dashboard dev",
  "analytics:build": "pnpm --filter @shiftori/analytics-dashboard build",
  "analytics:type-check": "pnpm --filter @shiftori/analytics-dashboard type-check"
}
```

`apps/analytics-dashboard/package.json` の主な依存候補:

```json
{
  "dependencies": {
    "@chakra-ui/react": "catalog:",
    "@chakra-ui/charts": "...",
    "@tanstack/react-query": "...",
    "recharts": "...",
    "react-is": "...",
    "react": "catalog:",
    "react-dom": "catalog:"
  },
  "devDependencies": {
    "@vitejs/plugin-react": "catalog:",
    "typescript": "catalog:",
    "vite": "catalog:"
  }
}
```

Chakra UI ChartsはRecharts上に作られているため、グラフは `@chakra-ui/charts` と `recharts` をセットで扱う。
React 19系でRecharts 3.6以降を使う場合は、Chakra UI Chartsの案内どおり `immer >= 11.0.1` の互換性を確認する。
既存root lockfileはpnpm管理なので、手動編集しない。

## 5. フロントエンドアーキテクチャ

### 5.1 設計思想

本体アプリと同じく、UI、データ取得、ドメイン計算を分ける。
ただし、内部BIは「操作」より「比較・把握・調査」が中心なので、画面は密度高め、状態は少なめ、テーブルとチャートを主役にする。

```text
DashboardPage
  |
  |-- FilterBar
  |     - period
  |     - tab
  |     - plan / metric group filters
  |
  |-- feature tabs
  |     - useQueryで必要なDTOを取得
  |     - domains/analyticsで派生KPIとchart seriesへ変換
  |     - componentsで表示
  |
  |-- api/analyticsClient
        - /api/analytics へのfetch client
        - Convex URLやsecretは持たない
```

表示コンポーネントは、取得方法を知らない。
API clientは、Chakra UIやグラフライブラリを知らない。
派生KPIとchart series変換は純粋関数にして、必要ならLogic UTだけで検証できる形にする。

### 5.2 Chakra UI

UIはChakra UI v3を使う。
本体アプリと同じデザイン思想を保ちつつ、分析アプリでは次を優先する。

- 一覧性の高いヘッダー、タブ、テーブル、コンパクトなKPIカード
- `Badge` で環境、最新集計日、データ欠損状態を常に見えるようにする
- `Card` はKPIカードや個別パネルに限定し、ページ全体をカードで囲まない
- 色は本体アプリの雰囲気に寄せるが、内部BIとして中立的で読みやすい配色にする
- app-localの `KpiCard` / `ChartPanel` / `DataTable` / `FilterBar` を作り、最初から本体UI wrapperへ依存しない

Chakra providerとthemeは `src/app/providers.tsx` と `src/styles/theme.ts` に置く。
テーマは最小から始め、本体アプリとの完全一致は目的にしない。

### 5.3 TanStack Query

ブラウザはConvex React clientではなく、Cloudflare Pages Functionsの `/api/analytics` を呼ぶ。
そのため、server state管理にはTanStack Queryを使う。

主な方針:

- `QueryClientProvider` は `src/app/providers.tsx` に置く
- query keyは `["analytics", kind, envLabel, from, to, filters]` の形にする
- `staleTime` は5から15分程度、または手動更新を前提に長めにする
- `refetchOnWindowFocus` は `false` を基本にする
- `retry` は1回程度に抑える
- mutationやoptimistic updateは初期不要
- 選択中タブのqueryを優先し、全タブを常時重く読まない

例:

```ts
useQuery({
  queryKey: ["analytics", "overview", envLabel, from, to],
  queryFn: () => fetchAnalytics({ kind: "overview", from, to }),
  staleTime: 10 * 60 * 1000,
  refetchOnWindowFocus: false,
});
```

TanStack Queryは「取得、キャッシュ、同期、更新」を扱う役割に限定する。
グラフ用の系列変換や前期間比較は `domains/analytics/` に寄せ、query hook内へ埋め込まない。

### 5.4 Routing

初期は単一Dashboardで十分なので、タブと期間はURL search paramsで表現する。
この段階ではTanStack Routerを必須にしない。

TanStack Routerを導入する条件:

- 店舗詳細を `/shops/$shopId` のように独立URLで共有したくなった
- 複数ページ化し、URL単位でloaderやsearch params validationを持ちたくなった
- analytics-dashboard内だけでroute treeを閉じられる

導入する場合でも、本体アプリのrouter設定を共有しない。
このアプリ内の `src/routes` または `src/app/router.tsx` に閉じる。

### 5.5 グラフ化ライブラリ

初期方針は `@chakra-ui/charts` + Recharts。
理由:

- React向けの宣言的なチャート実装ができる
- Chakra UIの見た目と組み合わせやすい
- line / area / bar / stacked bar / donut など、今回必要な可視化を広く扱える
- 自前SVGより、tooltip、軸、凡例、responsive対応の実装量を抑えられる

使い分け:

| 用途 | Chart |
|---|---|
| KPI推移 | line / area |
| 通知 channel / kind 内訳 | stacked bar |
| 店舗別ランキング | horizontal bar |
| plan構成 | donutまたはstacked bar |
| KPIカード内の小さな傾向 | sparkline相当のline |

グラフの入力データは `domains/analytics/chartSeries.ts` で整形する。
色は `Chart.Root` / `useChart` などChakra Chartsの仕組みに寄せ、同じmetricは画面をまたいでも同じ色にする。
データ欠損日は `0` と `null` を区別し、未集計を0件扱いしない。

TanStack Tableは初期導入しない。
店舗別ランキングのsort / filter / paginationが増え、Chakra Tableだけでは保守しづらくなった時点で検討する。

## 6. Convex設計

### 6.1 既存分析基盤は変更しない

既存の役割は維持する。

| ファイル | 役割 |
|---|---|
| `convex/analytics/metrics.ts` | metric名の定義 |
| `convex/analytics/dailyAggregation.ts` | 日次集計 |
| `convex/analytics/backfill.ts` | イベント系KPIのバックフィル |
| `convex/analytics/queries.ts` | internal参照APIとfetch helper |
| `convex/schema.ts` | 日次KPIテーブル |

`doc/features/analytics.md` にある「将来ダッシュボード画面等で公開する場合は、`analytics/queries.ts` の `fetch*` 関数をadminQueryラッパーで包み直す」という拡張ポイントを使う。
ただし今回はClerk前提のadminQueryではなく、Cloudflare Pages Functions -> Convex HTTP action -> internal query のBFF構成にする。

### 6.2 新規 `convex/analyticsDashboard/`

`analyticsDashboard` は「内部BI画面が読むDTO」を返すuse-case sliceにする。
DBテーブル名ではなく、画面用途で切る。

候補API:

| API | 種別 | 用途 |
|---|---|---|
| `internal.analyticsDashboard.queries.getOverview` | internalQuery | 期間内の主要KPI、前期間比較、最新スナップショット |
| `internal.analyticsDashboard.queries.getEventTrends` | internalQuery | metricカテゴリ別の時系列 |
| `internal.analyticsDashboard.queries.getNotificationBreakdown` | internalQuery | channel / kind / outcome 別の通知集計 |
| `internal.analyticsDashboard.queries.getShopRanking` | internalQuery | 店舗別スナップショットのランキング |
| `internal.analyticsDashboard.queries.getShopDetail` | internalQuery | 1店舗の時系列ドリルダウン |
| `analyticsDashboard.httpActions.query` | httpAction | Pages Functionsからの単一入口 |

HTTP route:

```ts
// convex/http.ts
http.route({
  path: "/analytics-dashboard/query",
  method: "POST",
  handler: analyticsDashboardHttp.query,
});
```

`OPTIONS` / CORS は初期不要。
ブラウザはConvexへ直接アクセスせず、Cloudflare Pages Functionsがサーバー間で呼ぶため。

### 6.3 HTTP actionの入力

HTTP actionはConvex functionの `args` validatorを持てないため、`schemas.ts` でZod相当の入力検証を行う。

```ts
type AnalyticsDashboardRequest =
  | { kind: "overview"; from: string; to: string }
  | { kind: "eventTrends"; from: string; to: string; metrics: string[] }
  | { kind: "notificationBreakdown"; from: string; to: string }
  | { kind: "shopRanking"; date: string; sort: ShopRankingSort; limit: number }
  | { kind: "shopDetail"; shopId: Id<"shops">; from: string; to: string };
```

制約:

- `from` / `to` は `YYYY-MM-DD`
- 最大期間は既存 `ANALYTICS_QUERY_RANGE_LIMIT` と同じ731日
- `metrics` は `analytics/metrics.ts` で定義済みのmetricか通知metricパターンのみ
- `shopRanking.limit` は上限100程度
- 返却DTOはドキュメントそのものではなく、画面に必要な値だけ

### 6.4 DTO方針

返すもの:

- 日付
- 集計済み件数
- 派生KPI
- 店舗ID
- 店舗名
- planKey
- スナップショット値

返さないもの:

- staff名 / email
- manager email
- raw outbox payload
- token / session
- provider error body
- Convex内部エラー詳細
- ドキュメント全体

店舗名はドリルダウンに必要なので返す。
ただし個人データではなく店舗単位の運用データとして扱い、一覧では必要最小限にする。

## 7. 画面設計

### 7.1 プライマリータスク

「直近の利用状況と変化を見て、どこに伸び・詰まり・通知問題があるかを把握する」。

内部BIなので、作業アクションより読み取り・比較・ドリルダウンを優先する。

### 7.2 ページ構成

```text
Header
  - 環境バッジ（production / develop / preview / local）
  - 最終集計日
  - 期間プリセット（7日 / 30日 / 90日 / 180日 / 365日 / カスタム）

Overview
  - KPIカード
  - 前期間比較

Tabs
  1. サービス全体
  2. 募集・提出
  3. 通知
  4. LINE
  5. 店舗別

各タブ
  - 主要グラフ
  - breakdown
  - 詳細テーブル
```

### 7.3 見たい角度

#### サービス全体

- 店舗数
- plan別店舗数
- スタッフ数
- シフト対象スタッフ数
- open募集数
- pending参加申請数
- LINE連携率 / follow率

#### 募集・提出

- 募集作成数
- シフト確定数
- 初回提出数
- 確定日ベース提出率
- 平均確定リードタイム
- 募集作成 -> 確定の推移

#### 通知

- email / line 別送信数
- email / line 別最終失敗数
- recruitment / reminder / confirmation / lineInvite / other 別内訳
- 催促送信数（`notification.*.sent.reminder`）
- 最終失敗率

#### LINE

- LINE連携スタッフ数
- LINE follow中スタッフ数
- LINE連携率
- 新規LINE連携数（`line.linked`）
- follow率

#### 店舗別

- plan
- staffCount
- shiftTargetStaffCount
- lineLinkedStaffCount
- lineFollowingStaffCount
- openRecruitmentCount
- LINE連携率
- 店舗詳細時系列

### 7.4 派生KPI定義

| KPI | 算出 |
|---|---|
| 確定日ベース提出率 | `recruitment.confirmed.submittedTotal.valueSum / recruitment.confirmed.expectedStaffTotal.valueSum` |
| 平均確定リードタイム | `recruitment.confirmed.valueSum / recruitment.confirmed.count` |
| LINE連携率 | `lineLinkedStaffCount / shiftTargetStaffCount` |
| LINE follow率 | `lineFollowingStaffCount / lineLinkedStaffCount` |
| 通知最終失敗率 | `failed / (sent + failed)` |
| 催促送信数 | `notification.email.sent.reminder + notification.line.sent.reminder` |

0除算は `null` とし、UIでは `-` 表示にする。

### 7.5 UIコンポーネント

内部BIとして密度を優先する。

- KPIカード: 数値 + 前期間差分 + ミニトレンド
- Chart: line / stacked bar / bar を中心にする
- Table: 店舗別・metric別の詳細
- Filter: 期間プリセット、plan、metric group
- Empty: `この期間のデータはありません`
- Error: `データを読み込めませんでした。期間を変えるか、少し時間をおいて再読み込みしてください`

チャートライブラリは初期から `@chakra-ui/charts` + Recharts を使う。
複数角度の可視化が前提なので、簡易SVGを手作りするより、tooltip、axis、legend、responsiveをライブラリに任せる方が実装と保守が軽い。
ただし、グラフ表示用のデータ変換はコンポーネントへ埋め込まず、`domains/analytics/chartSeries.ts` に置く。

## 8. 環境とデプロイ

### 8.1 環境の考え方

画面内で接続先を切り替えない。
どのConvexを見るかは、Cloudflare Pages project / branch / local envで決める。

| 用途 | Cloudflare Pages | Convex |
|---|---|---|
| production閲覧 | `analytics-dashboard` など別project | production Convex |
| develop閲覧 | `analytics-dashboard-dev` または同projectのdevelop branch | develop Convex |
| preview閲覧 | 必要になったらPR preview workflowを追加 | Convex preview |
| local | `pnpm analytics:dev` | workspace rootの `.env` / `.env.local` 等で指定したConvex |

ヘッダーには必ず環境バッジとConvex接続先の短い表示を出す。
productionとdebug環境を取り違えないため。

### 8.2 Cloudflare Pages project

本体アプリとは別のCloudflare Pages projectにする。
既存 `dev-yps-crispy-carnival` / `shiftori` とはデプロイ単位を分ける。

候補:

```text
shiftori-analytics-dashboard
shiftori-analytics-dashboard-dev
```

GitHub workflowは本体 `deploy.yml` に混ぜず、別workflowにする。

```text
.github/workflows/analytics-dashboard.yml
```

処理:

1. checkout
2. setup
3. `pnpm analytics:build`
4. `npx wrangler pages deploy apps/analytics-dashboard/dist --project-name shiftori-analytics-dashboard`

Cloudflare Pages側のbuild設定を使う場合は、root directoryを `apps/analytics-dashboard` にして、build command / output directoryを個別設定する。
既存リポジトリの運用に合わせるなら、GitHub Actionsから `wrangler pages deploy` する方が差分を制御しやすい。

### 8.3 Secrets / env

Cloudflare Pages Functions側:

| env | 用途 |
|---|---|
| `ANALYTICS_BASIC_USER` | Basic認証ユーザー名 |
| `ANALYTICS_BASIC_PASSWORD` | Basic認証パスワード |
| `VITE_CONVEX_SITE_URL` | `https://<deployment>.convex.site` |
| `SHIFTORI_INTERNAL_API_SECRET` | Pages Functions / Vite dev proxy -> Convex HTTP action の共有秘密値 |

Convex側:

| env | 用途 |
|---|---|
| `SHIFTORI_INTERNAL_API_SECRET` | HTTP actionが検証する共有秘密値 |

`VITE_CONVEX_SITE_URL` は `.convex.cloud` ではなく `.convex.site` を使う。
HTTP actionは `.convex.site` 側で公開されるため。
未設定の場合は `VITE_CONVEX_URL` の `.convex.cloud` を `.convex.site` に変換する。
`SHIFTORI_INTERNAL_API_SECRET` は呼び出し側とConvex側で同じ値にする。

## 9. Security Lens

- Actor: Basic認証を通過した運営者本人。攻撃者はURLを知った第三者、Basic credentialを総当たりするbot、Convex HTTP actionを直接叩く第三者
- Asset: 店舗数、スタッフ数、募集・提出・通知・LINE連携などの運用KPI、店舗名、plan情報
- Trust boundary: Browser -> Cloudflare Pages Functions、Pages Functions -> Convex HTTP action、HTTP request body -> internal query
- Abuse case: Basic認証を迂回して静的ファイルやAPIへアクセスする、Convex HTTP actionを直接叩いてKPIを取得する、長期間・大量limitで集計APIを重くする、raw docsやPIIを返してしまう
- Server-side check: Pages middlewareでBasic認証、Convex HTTP actionで `SHIFTORI_INTERNAL_API_SECRET` を検証、入力期間・limit・metricをサーバー側で検証
- Rate limit / idempotency: 読み取り専用なので冪等。期間は最大731日、店舗ランキングlimitは最大100。Basic認証の総当たりが気になる場合はCloudflare Accessへ移行する
- Logs / PII: 認可失敗はstatusとsafe metadataのみ。Basic password、shared secret、staff email、raw outbox payload、provider error bodyをログに残さない
- Regression test: UI系は省略可。HTTP action secret不一致で401、期間上限超過で400、DTOにstaff email等が含まれないことだけ最小確認を推奨

## 10. テスト・検証方針

ユーザー方針として、私用内部BIのため Storybook / E2E / VRT は作らない。
UIの代表状態テストも初期スコープ外にする。

ただし次はセキュリティ境界なので、実装時には最小限だけ検討する。

| 対象 | 推奨 | 理由 |
|---|---|---|
| `derivedKpis.ts` | Logic UT 任意 | 0除算や前期間比較の退行を防ぐ。複雑化するまで省略可 |
| Convex HTTP action | 最小テスト推奨 | secret不一致・入力不正・DTO最小化は私用でも漏洩境界 |
| Pages Functions middleware | 手動確認でも可 | Cloudflare実行環境差分があり、単体テストの費用対効果は低め |
| Storybook | 不要 | 公開UIではない |
| E2E | 不要 | 本人用の閲覧画面で主要業務導線ではない |
| VRT | 不要 | 見た目退行の影響が限定的 |

実装完了後の最低限:

```bash
pnpm lint
pnpm type-check
pnpm analytics:build
```

Convex HTTP actionやinternal queryを追加した場合は、可能なら該当の `pnpm test:convex:logic` を追加実行する。
ユーザーが完全にテスト不要を選ぶ場合は、レビュー時に「セキュリティ境界の自動回帰なし」という残リスクを明記する。

## 12. 残論点

| 論点 | 初期判断 | 後で決めること |
|---|---|---|
| Cloudflare Accessへ移行するか | 初期はBasic認証middleware | 総当たりや端末管理が気になったらAccessへ移行 |
| チャートライブラリ | `@chakra-ui/charts` + Recharts | React / Recharts / immer の互換性を実装時に確認 |
| TanStack Router | 初期は使わない | 店舗詳細を独立URLにしたくなったらanalytics-dashboard内だけで導入 |
| TanStack Table | 初期は使わない | 店舗別テーブルのsort / filter / paginationが複雑化したら導入 |
| 共通UI package | 初期は作らない | 両アプリで同じ部品や純粋関数が増えたら再検討 |
| 店舗名表示 | 表示する | 必要なら店舗名をマスクするモードを追加 |
| preview閲覧 | 必要時に追加 | PRごとのConvex preview URLをdashboard previewへ渡すworkflow |
| APIキャッシュ | 初期は `no-store` | データ量が増えたらPages Function側で短時間cache |

## 13. `apps/analytics-dashboard/AGENTS.md` 作成方針

このアプリのディレクトリには専用の `AGENTS.md` を置く。
本体アプリとは利用者と責務が違うため、作業開始時に目的と制約をすぐ確認できるようにする。

書く内容:

- このアプリは、Shiftoriの分析KPIを本人だけが確認する内部BIである
- productionの実データを主に見るが、develop / previewはデバッグ目的で接続先Convexに従う
- 本体アプリの顧客向け導線には入れない
- データ取得はCloudflare Pages Functions -> Convex HTTP action -> internal queryのBFF経路に限定する
- ブラウザbundleへConvex secret、Basic password、HTTP action secretを入れない
- staff email、manager email、token、raw notification payload、provider error bodyを画面やログに出さない
- Chakra UI v3、TanStack Query、`@chakra-ui/charts` / Rechartsを基本スタックにする
- 本体アプリと似たpage / feature / domain分離は採用するが、UI部品やrouterを過度に共通化しない
- Storybook / E2E / VRTは初期不要。必要なら派生KPIやセキュリティ境界だけ最小テストを検討する
- Vite / Storybook / Convex dev serverはユーザーが起動する前提にし、エージェントが勝手に起動しない

候補文面:

```md
# AGENTS.md

このディレクトリは、Shiftoriの分析KPIを可視化する本人用の内部BIアプリです。
本体アプリの顧客向け導線とは分離し、Cloudflare Pagesの別project / 別サブドメインで運用します。

主な目的は、日次蓄積されたproductionデータをサービス全体、通知、LINE、募集・提出、店舗別の角度から確認し、施策判断とデバッグを速くすることです。
develop / previewはデバッグ目的で使い、画面内の環境切替ではなく、デプロイ環境やローカルenvが接続しているConvexを見る方針です。

実装では、Vite + React + Chakra UI v3 + TanStack Query + @chakra-ui/charts / Rechartsを基本にします。
本体アプリと同じpage / feature / domain分離の考え方は使いますが、UI部品、router、状態管理を早期に共有しません。
共通化は、重複コストが明確になってから検討します。

ブラウザからConvex public queryを直接呼ばないでください。
データ取得は Cloudflare Pages Functions -> Convex HTTP action -> internal query のBFF経路に限定します。
ブラウザbundleへConvex secret、Basic password、HTTP action secretを入れてはいけません。

画面やログに、staff email、manager email、token、raw notification payload、provider error bodyを出さないでください。
返却DTOは画面に必要な集計値と店舗単位の情報に限定します。

Storybook / E2E / VRTは初期スコープ外です。
必要な場合は、派生KPIの純粋関数やHTTP actionのsecret検証など、セキュリティ境界に絞って最小テストを追加してください。

Vite、Storybook、Convex dev serverはユーザーが起動する前提です。
エージェントは勝手に開発サーバーを起動しないでください。
```

# 分析KPI蓄積基盤（convex/analytics/）設計書

作成日: 2026-07-04

## 1. 背景と目的

サービス全体の利用状況KPI（店舗数、スタッフ数、シフト提出率、確定リードタイム、通知送信/失敗数、LINE連携率、催促送信数など）を時系列で分析したい。現状の課題:

- KPIを横断的に集約する基盤がなく、都度DBを直接調べるしかない
- `notificationDeliveryEvents` は90日TTL（`expiresAt`）で消えるため、長期の通知分析が不可能
- `recruitments.lastReminderSentAt` は最終1回分しか持たず、催促履歴が残らない

日次cronでKPIを専用テーブルに蓄積し、後から時系列で参照できるようにする。

### 確定済みの決定事項

1. **参照はinternal専用のみ** — 公開queryは一切作らない。Convexダッシュボード / `npx convex run` で確認する。ただし将来 adminQuery を追加しやすい設計にしておく
2. **状態スナップショット系KPIは導入日から蓄積開始** — 過去分の疑似復元はしない。イベント系KPI（タイムスタンプが残っているもの）は全期間バックフィルする
3. **日次cronは03:00 JST（= 18:00 UTC）** — `notification-delivery-event-prune`（03:30 JST）より前に実行

## 2. 全体アーキテクチャ

新ユースケーススライス `convex/analytics/` を追加する（Use-Case Slices + CQRS 規約準拠）。

```
日次cron 03:00 JST
  └─ internal.analytics.dailyAggregation.run（前日分を集計）
       ├─ Phase 1: 店舗別スナップショット   → analyticsDailyShopSnapshots
       ├─ Phase 2: サービス全体rollup       → analyticsDailyServiceSnapshots
       └─ Phase 3〜6: イベント日次カウンタ   → analyticsDailyEventCounts

バックフィル（1回だけ手動実行）
  └─ internal.analytics.backfill.start
       └─ Phase 3〜6 のみを最古の店舗作成日〜前日まで1日ずつ直列実行
```

### KPIの2分類

| 分類 | 性質 | テーブル | 過去分 |
|---|---|---|---|
| 状態スナップショット | 「その日時点の値」。後から復元不可 | `analyticsDailyShopSnapshots` / `analyticsDailyServiceSnapshots` | 導入日から蓄積 |
| イベントカウンタ | 「その日に起きた件数」。タイムスタンプから再計算可能 | `analyticsDailyEventCounts` | 全期間バックフィル |

### 通知KPIの取り方: 日次バッチのみ（フックなし）

`notificationOutbox` の `markSent` / `markFailed` へのリアルタイムフックは**追加しない**。

- outboxはプルーニングされず永続なので、`sentAt` / `failedAt` からいつでも完全に再計算できる
- リアルタイムフックは書き込み増幅と二重管理（フック+バッチ）のコストに見合わない
- リアルタイム用途（月次の通知使用量）は既存の `notificationUsage` が既にカバーしている

## 3. テーブル設計（convex/schema.ts に追加）

### 3.1 analyticsDailyServiceSnapshots（サービス全体×日次、1日1行）

```ts
analyticsDailyServiceSnapshots: defineTable({
  date: v.string(),                    // "YYYY-MM-DD"（JST基準）
  shopCount: v.number(),               // isDeleted=false の店舗数
  shopCountByPlan: v.object({
    free: v.number(),
    standard: v.number(),
    premium: v.number(),
  }),
  staffCount: v.number(),              // isDeleted=false のスタッフ数
  shiftTargetStaffCount: v.number(),   // 上記から excludedFromShift=true を除外した数
  lineLinkedStaffCount: v.number(),    // staffLineAccounts isDeleted=false
  lineFollowingStaffCount: v.number(), // 上記のうち following=true
  openRecruitmentCount: v.number(),    // status="open" かつ isDeleted=false
  pendingRegistrationRequestCount: v.number(), // staffRegistrationRequests status="pending"
  computedAt: v.number(),              // 集計実行時刻 Unix ms
}).index("by_date", ["date"])
```

- LINE連携率 = `lineLinkedStaffCount / shiftTargetStaffCount`（分母はシフト対象スタッフ）
- `shopBillingStates` が無い店舗は `planKey="free"` 扱いで集計する

### 3.2 analyticsDailyShopSnapshots（店舗別×日次）

```ts
analyticsDailyShopSnapshots: defineTable({
  date: v.string(),                    // "YYYY-MM-DD"（JST基準）
  shopId: v.id("shops"),
  planKey: v.union(v.literal("free"), v.literal("standard"), v.literal("premium")),
  staffCount: v.number(),
  shiftTargetStaffCount: v.number(),
  lineLinkedStaffCount: v.number(),
  lineFollowingStaffCount: v.number(),
  openRecruitmentCount: v.number(),
  computedAt: v.number(),
})
  .index("by_date_shopId", ["date", "shopId"])   // upsertキー + 日次rollupスキャン
  .index("by_shopId_date", ["shopId", "date"])   // 店舗別時系列
```

**粒度の判断**: スナップショットは店舗別+全体の両方を持つ。cronはどのみち全店舗を走査するため店舗別行の追加コストがほぼゼロで、後のプラン別セグメント分析・店舗ドリルダウンに効く。サービス全体行は店舗別行のrollupとして導出する（Phase 2）。

### 3.3 analyticsDailyEventCounts（イベント日次カウンタ、date × metric 縦持ち）

```ts
analyticsDailyEventCounts: defineTable({
  date: v.string(),                    // "YYYY-MM-DD"（JST基準、イベント発生日）
  metric: v.string(),                  // analytics/metrics.ts の AnalyticsMetric
  count: v.number(),                   // 件数
  valueSum: v.optional(v.number()),    // 合計値が意味を持つmetricのみ（リードタイム合計ms等）
  updatedAt: v.number(),
})
  .index("by_date_metric", ["date", "metric"])   // upsertキー / 1日分の全metric取得
  .index("by_metric_date", ["metric", "date"])   // 単一metricの時系列取得
```

- `metric` はスキーマ上 `v.string()` とし、型は `metrics.ts` のTypeScript型で担保する。メトリクス追加のたびにスキーマ変更・デプロイバリデーションを発生させないため（縦持ちの利点を活かす）
- イベントは**サービス全体粒度のみ**。店舗別イベントは既存 `notificationUsage`（店舗×月）と重複するため見送り。将来必要になれば `shopId: v.optional(v.id("shops"))` を追加して拡張できる

### 3.4 既存テーブルへのインデックス追加（日次窓のレンジスキャン用）

```ts
notificationOutbox:
  .index("by_status_sentAt", ["status", "sentAt"])
  .index("by_status_failedAt", ["status", "failedAt"])
recruitments:
  .index("by_status_and_confirmedAt", ["status", "confirmedAt"])
staffLineAccounts:
  .index("by_linkedAt", ["linkedAt"])
staffRegistrationRequests:
  .index("by_status_and_reviewedAt", ["status", "reviewedAt"])
```

- optionalフィールド（`sentAt` 等）へのindexはConvexで有効（未定義ドキュメントはレンジに現れない）
- `staffLineAccounts.linkedAt` は再連携時も初回値を保持する（`convex/line/service.ts:51` で確認済み）ため「初回連携日」として使える
- 以下はConvexのシステムindex `by_creation_time` のレンジクエリで取れるため追加インデックス不要:
  - 店舗作成（`shops`）、スタッフ作成（`staffs`）、募集作成（`recruitments`）、参加申請（`staffRegistrationRequests`）
  - 初回提出（`shiftSubmissions` は初回提出時にinsertされるため `_creationTime ≒ firstSubmittedAt`）
- フィールド追加はゼロなので**マイグレーション不要**。インデックスはデプロイ時に自動構築される

## 4. メトリクス定義（新規 convex/analytics/metrics.ts）

純粋定義のみ（DBアクセス・Convex APIのインポート禁止）。

### 4.1 イベント系メトリクス（バックフィル対象）

| metric | 数えるもの | 日付の根拠 | valueSum |
|---|---|---|---|
| `shop.created` | 店舗登録数 | `shops._creationTime` | — |
| `staff.created` | スタッフ登録数 | `staffs._creationTime` | — |
| `recruitment.created` | 募集作成数 | `recruitments._creationTime` | — |
| `recruitment.confirmed` | シフト確定数 | `recruitments.confirmedAt` | 作成→確定リードタイム合計ms（`confirmedAt - _creationTime`） |
| `recruitment.confirmed.submittedTotal` | 確定した募集の提出者数合計 | 同上 | `recruitmentStats.submittedCount` の合計 |
| `recruitment.confirmed.expectedStaffTotal` | 確定した募集の提出対象者数合計 | 同上 | `recruitmentStats.activeStaffCountSnapshot` の合計 |
| `submission.first` | 希望シフト初回提出数 | `shiftSubmissions._creationTime` | — |
| `line.linked` | LINE連携完了数 | `staffLineAccounts.linkedAt` | — |
| `staffRegistration.requested` | 参加申請数 | `staffRegistrationRequests._creationTime` | — |
| `staffRegistration.approved` | 参加承認数 | `reviewedAt`（status="approved"） | — |
| `staffRegistration.rejected` | 参加却下数 | `reviewedAt`（status="rejected"） | — |

派生KPIの算出定義:

- **確定日ベースの提出率** = `recruitment.confirmed.submittedTotal.valueSum / recruitment.confirmed.expectedStaffTotal.valueSum`
- **平均確定リードタイム** = `recruitment.confirmed.valueSum / recruitment.confirmed.count`

### 4.2 通知系メトリクス（テンプレートリテラル型）

```
notification.{channel}.{outcome}.{kind}
  channel: email | line
  outcome: sent | failed
  kind:    recruitment | reminder | confirmation | lineInvite | other
```

- `kind` の分類は `describeNotificationFailureContext()`（`convex/notificationOutbox/failureResend.ts:23`、通知種別分類の正典）を再利用
- **催促送信数** = `notification.*.sent.reminder`（context="notification.sendReminderEmails"）。専用metricは持たない
- **失敗数の定義** = 「最終失敗」（`status="failed"` かつ `failedAt` が当日）。リトライ中の一時失敗は数えない（一時失敗は `notificationDeliveryEvents` にしか残らずTTLで消えるため対象外と割り切る）
- context の取得: outbox行の `payload.kind==="email"` なら `payload.context`、LINEなら `fallbackEmail.payload.context ?? dedupeKeyの先頭2セグメント`。この導出は `notificationOutbox/mutations.ts:953` の `notificationContextForJob()` に既実装なので **export化して再利用**する

```ts
// metrics.ts の構成イメージ
export const ANALYTICS_METRICS = { shopCreated: "shop.created", ... } as const;
export type AnalyticsMetric =
  | (typeof ANALYTICS_METRICS)[keyof typeof ANALYTICS_METRICS]
  | `notification.${"email" | "line"}.${"sent" | "failed"}.${NotificationFailureKind}`;
export function notificationMetric(channel, outcome, kind): AnalyticsMetric;
```

## 5. JST日付処理（convex/_lib/dateFormat.ts に追加）

```ts
/** "YYYY-MM-DD"（JST）の日の [開始, 終了) をUnix msで返す（半開区間） */
export function jstDayRangeMs(date: string): { startMs: number; endMs: number } {
  const startMs = dateToUtcMs(date) - JST_OFFSET_MS;
  return { startMs, endMs: startMs + MS_PER_DAY };
}
```

- 既存 `getSubmitLinkCutoff()` と同形のパターン
- CIの `check-convex-timezone.ts` チェックを通すため、日付演算は必ず `_lib/dateFormat.ts` に置く（`new Date().toISOString()` 等の直書き禁止）

## 6. 書き込み: upsertプリミティブ（新規 convex/analytics/mutations.ts）

すべて**絶対値セットのupsert**（インクリメントではない）。これが冪等性の要 — 同じ日を何度集計し直しても常に上書きになり、二重カウントが構造的に起きない。

```ts
// mutation ctx を受ける内部ヘルパー（export function、internalMutationではない）
export async function setDailyEventCount(ctx, { date, metric, count, valueSum? });
  // by_date_metric で既存行を .first() → あれば patch / なければ insert
export async function setShopSnapshot(ctx, { date, shopId, ...values });
  // by_date_shopId で同様
export async function setServiceSnapshot(ctx, { date, ...values });
  // by_date で同様
```

パターン踏襲元: `convex/notificationOutbox/mutations.ts:236` の `incrementNotificationUsage`（index → `.first()` → patch/insert）。

## 7. 日次集計（新規 convex/analytics/dailyAggregation.ts）

### 7.1 実行モデル: internalMutation の自己再帰チェーン

パターン踏襲元: `convex/notificationOutbox/mutations.ts:631` の `pruneExpiredEvents`（internalMutation + バッチ + `ctx.scheduler.runAfter(0, self, {...})` 自己再帰）。大量データでも1 mutationの読み取り上限を超えないよう、`.paginate({ cursor, numItems: ANALYTICS_AGGREGATION_PAGE_SIZE })` でページングする（`.collect()` 禁止規約準拠）。

**冪等性の設計（重要）**: 各フェーズは `{ date, cursor, acc, followUp? }` を引数に自己再帰し、途中ページではDBに書かず累積値 `acc` をschedulerの引数で運ぶ。**最終ページでのみ絶対値をupsert**する。

- 同日再実行 → 常に上書き（二重カウントなし）
- 途中クラッシュ → 中途半端な書き込みが残らない（accはscheduler引数上にしかない）

```ts
// convex/constants.ts に追加
export const ANALYTICS_AGGREGATION_PAGE_SIZE = 100; // NOTIFICATION_DELIVERY_EVENT_PRUNE_BATCH_SIZE と同水準
```

### 7.2 エントリポイントとフェーズチェーン

```ts
export const run = internalMutation({
  args: { date: v.optional(v.string()) }, // 省略時: addDays(todayJST(), -1) = 前日JST
  handler: // Phase 1 の先頭を scheduler.runAfter(0, ...) で起動
});
```

フェーズは線形チェーン（各フェーズ完走時に次フェーズをschedule）。`followUp` 引数はバックフィルの日付継続用（7.3参照）。

| Phase | 対象 | 使用index | 出力 |
|---|---|---|---|
| 1 `aggregateShopSnapshots` | `shops` をページング走査。各店舗ごとに `staffs`（by_shopId_isDeleted）/ `staffLineAccounts`（by_shopId_and_isDeleted）/ `shopBillingStates`（by_shopId）/ `recruitments`（by_shopId_status, "open" かつ isDeleted=false）を集計 | 上記 | 店舗ごとに `setShopSnapshot()`。店舗単位の読み取りは有界なのでページ内で完結してよい |
| 2 `rollupServiceSnapshot` | `analyticsDailyShopSnapshots` の当日分をページング合算。pending申請数は `staffRegistrationRequests`（by_status_and_createdAt, status="pending"）を別途カウント | by_date_shopId | 最終ページで `setServiceSnapshot()` |
| 3 `aggregateNotificationEvents` | `jstDayRangeMs(date)` の窓で sent / failed をレンジページング。`channel × describeNotificationFailureContext(notificationContextForJob(job)).kind` でaccを積む | by_status_sentAt / by_status_failedAt | 最終ページで全通知metricを `setDailyEventCount()`（発生ゼロのmetricは0行を書く: 「未集計」と「ゼロ件」を区別するため） |
| 4 `aggregateLifecycleEvents` | `by_creation_time` レンジで `shops` / `staffs` / `recruitments` / `shiftSubmissions` / `staffRegistrationRequests` をそれぞれカウント（テーブルごとにサブフェーズ） | by_creation_time（システムindex） | `shop.created` / `staff.created` / `recruitment.created` / `submission.first` / `staffRegistration.requested` |
| 5 `aggregateConfirmationEvents` | `recruitments`（status="confirmed", confirmedAtが当日窓）。各行で `confirmedAt - _creationTime` を積み、`recruitmentStats`（by_recruitmentId）から `submittedCount` / `activeStaffCountSnapshot` を積む | by_status_and_confirmedAt | `recruitment.confirmed`（count+valueSum）/ `.submittedTotal` / `.expectedStaffTotal` |
| 6 `aggregateLineAndRegistrationEvents` | `staffLineAccounts`（linkedAtが当日窓）、`staffRegistrationRequests`（reviewedAtが当日窓、status別） | by_linkedAt / by_status_and_reviewedAt | `line.linked` / `staffRegistration.approved` / `staffRegistration.rejected` |

注意点:

- Phase 4 の作成カウントでは論理削除を**フィルタしない**（「その日に作成された数」は削除後も不変であるべき。ファネル分析用）
- Phase 1 のスナップショットは isDeleted=false のみ（「現在生きている数」なので）

## 9. バックフィル（新規 convex/analytics/backfill.ts）

### 9.1 方式: one-shot internalMutation（migrations/ は使わない）

`@convex-dev/migrations` は「1テーブルを走査して各ドキュメントをpatchする」用途向けで、本件は「日付を軸に複数テーブルを横断集計」なので構造が合わない。日次集計のフェーズ（7.2 の Phase 3〜6）を日付ループでそのまま再利用することで、バックフィルと日次運用が単一コードパスになり乖離しない。

```ts
export const start = internalMutation({
  args: { fromDate: v.optional(v.string()), toDate: v.optional(v.string()) },
  // fromDate 既定値: 最古の shops._creationTime（by_creation_time 昇順 .first()）のJST日付
  // toDate   既定値: addDays(todayJST(), -1)
  // → Phase 3 の先頭を followUp={untilDate: toDate} 付きで schedule
});
```

### 9.2 動作

- 日付 d の**イベント系フェーズ（Phase 3〜6）のみ**実行。スナップショット系（Phase 1〜2）は対象外（決定事項2: 状態の過去復元はしない）
- Phase 6 完了時、`followUp.untilDate` に未到達なら `addDays(d, 1)` を同じ followUp 付きで schedule（1日ずつ直列に前進。並列にしない — mutation負荷の平準化とデバッグ容易性のため）
- 全書き込みが絶対値upsertなので、**途中失敗しても任意の fromDate から再実行するだけで復旧**
- 催促送信数の過去分も outbox（context="notification.sendReminderEmails", status="sent"）から自動復元される。`lastReminderSentAt` は使わない

### 9.3 実行手順（デプロイ後に1回）

```bash
npx convex run analytics/backfill:start '{}'
# 進捗はダッシュボードの analyticsDailyEventCounts の date 最大値で確認
```

### 新規 convex/analytics/dailyAggregation.test.ts

- **スナップショット**: plan違いの2店舗 + 論理削除スタッフ + excludedFromShift スタッフを混在させ、shop行とservice rollupの各数値を検証

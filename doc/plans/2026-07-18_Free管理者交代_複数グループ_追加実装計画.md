## 4. 固定する仕様

実装中に次の判断を再検討しない。

| 項目 | 固定する判断 |
|---|---|
| 送信前確認 | Free交代の初回送信と再送の全入口で、最終送信操作の前に交代結果を明示する |
| 交代の時点 | 案内メールの送信時点では交代せず、後任のアカウント連携完了時に既存バックエンドが原子的に交代する |
| 後任側の操作 | 現行どおり招待URLを開いた後に自動連携する。追加の同意画面、チェックボックス、確認ボタンは設けない |
| 候補 | 同じグループの有効な人物であり、既存の非削除スタッフ所属とメールアドレスを持つ人だけを候補にする |
| 所属店舗の状態 | 候補のスタッフ所属先が`active`、`archived`、`planSuspended`のどれかでは絞り込まない。現行の非削除判定を維持する |
| 外部後任 | 現行どおり不可とし、新規人物をFreeの後任として招待する導線は追加しない |
| 連携前 | 現管理者Aは対象グループを引き続き管理できる |
| 連携後 | Bが対象グループの唯一の管理者になり、Aは対象グループの管理画面と店舗情報へアクセスできなくなる |
| 前任者の既存データ | Aのスタッフ所属、シフト対象、通知設定を維持する |
| 別グループ | Aが別グループにも所属する場合、その管理権限と店舗アクセスを維持する |
| 完了通知 | 前任者向けの交代完了通知を追加せず、E2Eでも有無を契約にしない |
| 緊急復旧 | 唯一の管理者が交代開始前に退職、死亡、ログイン不能となった場合は問い合わせ対応とし、復旧UIやAPIを追加しない |
| 同名データ | 同名グループ、同名店舗を識別する追加UIやE2Eを作らない。fixtureは異なる名前を使う |

「グループに所属している」は、この計画では削除されていない既存グループスタッフであることを含む。

店舗がアーカイブ済みであることだけを理由に後任候補から外さない。

- `convex/organizationInvitation/mutations.ts`は、連携完了時に後任をactive、前任をremovedへ同一mutationで変更する。
- `convex/_scenario/organizationManagerExchange.test.ts`は、前任者のスタッフ所属、通知設定、別グループ権限を維持し、対象グループ権限だけを失効させる。

- Full Regression結果ゲートは`MM-P0-04`と`MG-P0-01`を認識しない。

## 6. 送信前確認UI

### 6.1 対象入口

Free交代の送信入口は次の3つである。

1. グループ設定上部の`ManagerInvitationDialog`。
2. グループ設定の`OrganizationUserDetailDialog`。
3. Dashboardの`StaffDetailSettingsTab`。

3入口の初回送信と再送で、同じ意味の最終確認を表示する。

### 6.2 画面遷移

`ManagerInvitationDialog`のFreeモードだけを2段階にする。

1. 現在のスタッフから後任を選択する。
2. 一次CTAの「交代内容を確認」を押す。
3. この時点では`onSubmit`を呼ばず、選択した後任を含む確認状態を表示する。
4. 「交代の案内を送る」を押した時だけ、既存の`onSubmit({ kind: "person", personId })`を一回実行する。
5. 「戻る」または「やめる」では送信せず、候補選択へ戻れる。

候補選択中は既存Dialog footerの一次CTAを使い、確認中は`hideFooter`で外側のfooterを隠して`ManagerAssignmentConfirmation`の操作だけを表示する。

Dialogのclose、Free以外へのmode変更、選択候補の消失では確認状態をリセットする。

通常の管理者追加、外部入力、通常の再送は現在の導線を変えない。

スタッフ詳細とユーザー詳細は、既存の`ManagerAssignmentConfirmation`を引き続き使う。

新しいDialog、確認wrapper、汎用state machineは追加しない。

### 6.3 表示契約

Free初回送信の確認では、少なくとも次の意味を明示する。

- 「Bさんがアカウントを連携すると、このグループの唯一の管理者になります。」
- 「その時点で、あなたのこのグループの管理者権限は終了し、グループ設定と店舗情報へアクセスできなくなります。」
- 「交代が完了するまでは、あなたが引き続き管理できます。」
- 「スタッフ所属、シフト対象、通知設定は変更されません。」

推奨見出しは「Bさんへ管理者交代の案内を送りますか？」とする。

推奨確定CTAは「交代の案内を送る」とする。

Free再送も同じ交代結果を表示し、「以前のURLは利用できなくなります」を追加する。

再送の推奨確定CTAは「交代の案内を再送」とする。

「取り消せない」とは表示しない。

緊急復旧、問い合わせ、前任者への完了通知は、この確認内で説明しない。

## 7. テスト層の分担

同じ負系やDB内部状態を各層へ複製しない。

| 契約 | 主担当層 | 追加する検証 |
|---|---|---|
| Free送信前の確認状態 | Storybook Behavior Test | 候補選択後の一次操作ではcallback 0回、cancelでも0回、最終確認で正しいpayloadが1回 |
| Free初回・再送の重要文言 | Storybook Behavior Test | 唯一の管理者、現管理者の権限終了、連携前の継続、再送URL失効 |
| 確認状態のPC・モバイル操作 | Storybook Behavior Test | 代表viewportで重要文言とCTAへ到達でき、最終callbackが一回だけ呼ばれる |
| Free交代の原子的なDB遷移 | 既存Convex Scenario Test | 新しいDB完全一致テストをE2Eへ重複しない |
| 不正候補、IDOR、期限、使用済み、rate limit、冪等性 | 既存Convex Function Test | E2Eへ追加しない |
| Free交代の画面と認証の結合 | E2E | 送信前確認、Outbox 1件、連携前後のA/B権限、Aの別グループ、Aのスタッフ表示 |
| 2グループの画面切替と代表更新 | E2E | Dashboard、グループ設定、URL、reload、Bだけの更新、A/B非混入 |
| providerへの実メール到着 | 対象外 | 実行しない |

静的な初期文言の存在だけをBehavior Testへ重複させない。

Behavior Testは操作後に初めて現れる確認状態とcallback回数を検証する。

今回は新しいVRT Storyとbaseline更新を追加せず、確認状態の主担当をBehavior Testに固定する。

## 8. E2E fixture

既存のcanonical organization helperを再利用し、Free交代と複数グループに必要な前提だけを作る専用seedを追加する。

汎用fixtureやproduction public APIは追加しない。

fixtureはテストごとに独立して次を作る。

### 8.1 対象Freeグループ

- 管理者Aが唯一のactiveな`organizationMember`である。
- Aは対象店舗の既存スタッフでもある。
- スタッフBは同じグループのactiveな`organizationPerson`と非削除スタッフ所属を持つが、manager memberを持たない。
- BのメールはClerk actor Bの確認済みメールと一致する。
- active店舗を1件だけ持つ。
- `organizationBillingStates`はFreeで、`freeManagerPersonId`にA、`freeShopId`に対象店舗を設定する。

### 8.2 無関係な別グループ

- Aをactiveな管理者として登録する。
- Free対象グループとは別のorganization、person、member、shop、staffを持つ。
- 対象グループと判別できる固有のグループ名、店舗名、表示データを持つ。

### 8.3 fixture契約

- Free状態はseedで直接作り、課金UI、プラン変更API、Stripeを通さない。
- seedとresetは`E2E_TESTING_ENABLED`とdeployment種別の既存二重安全ゲートを維持する。
- actor A、B、Cの既存storage stateを再利用し、同じactorを通常workerと並列利用しない。
- resetは対象actorから到達するテスト用グループだけを削除し、別scenarioを巻き込まない。
- seedの再実行で前回データが残らないことを`convex/testing.test.ts`で検証する。
- schema、自動生成ファイル、migrationは変更しない。

## 9. E2Eシナリオ

### 9.1 `MM-P0-04` Free管理者交代

実装先は`e2e/scenarios/multiActor/free-manager-exchange.test.ts`とする。

タグは`@release`、`@notification`、`@security`とする。

前提:

- AはFree対象グループの唯一の管理者であり、別グループの管理者でもある。
- BはFree対象グループの既存スタッフである。
- AとBは別のClerk actorである。

操作と期待値:

1. AがFree対象グループのグループ設定を開く。
2. AがBを後任として選択し、「交代内容を確認」を押す。
3. 唯一の管理者、Aの権限終了、連携前はAが管理を継続することを画面で確認する。
4. Aが最終確認を行い、交代案内Outboxが一件だけ受け付けられたことを既存redacted probeで確認する。
5. Bが未連携の間は、Aが対象グループの設定をreloadして利用できることを確認する。
6. Bが既存の招待URLを開き、追加確認なしで自動連携して対象店舗のDashboardへ遷移することを確認する。
7. Bが対象グループのDashboardとグループ設定を利用できることを確認する。
8. Aが対象店舗URLをreloadすると汎用エラーになり、別グループへ黙ってfallbackしないことを確認する。
9. Aが別グループの明示した`?shop=`を開き、引き続き管理できることを確認する。
10. Bの画面からAが既存スタッフとして残っていることを確認する。

確認前のcallback 0回とcancel 0回はBehavior Testを主担当とする。

前任者への交代完了通知の有無はassertしない。

### 9.2 `MG-P0-01` 複数グループ切り替え

実装先は`e2e/scenarios/multiActor/multiple-organization-switching.test.ts`とする。

タグは`@release`、`@security`とする。

前提:

- 同じClerk actor Aが、互いに無関係なグループAとグループBのactiveな管理者である。
- 各グループに異なる店舗名と識別データがある。
- 各テストは新しいseedから開始し、`MM-P0-04`の実行結果へ依存しない。

操作と期待値:

1. AがグループAのDashboardを開く。
2. 店舗切替UIからグループBの店舗を選ぶ。
3. `?shop=`、店舗見出し、グループ表示、識別データがグループBへ切り替わることを確認する。
4. グループBの店舗名を設定UIから一度変更し、reload後も変更が残ることを確認する。
5. DashboardからグループAへ戻り、グループAの店舗名と識別データが不変で、グループBのデータが表示されないことを確認する。
6. グループ設定を開き、グループセレクターからグループBを選ぶ。
7. URLがグループBの代表店舗へ変わり、グループ名、ユーザー、店舗一覧がグループBへ切り替わることを確認する。
8. グループAへ戻し、URLと表示がグループAへ戻ることを確認する。

同名グループ、同名店舗、複数tab、Mobile E2Eは追加しない。

## 10. Security Lens

- Actor: Free対象グループの唯一の管理者A、同じグループの既存スタッフB、Aが管理する無関係な別グループ、招待対象ではないactor C。
- Asset: 対象グループの唯一の管理権限、店舗情報、前任者と後任者の人物・スタッフ所属、招待token、通知宛先、別グループの管理権限。
- Trust boundary: Clerk identityと確認済みメール、user-controlledな`personId`と`shopId`、`?shop=`、管理者招待token、E2E限定internal helper。
- Abuse case: 別グループ人物を後任にする、候補表示後に無効化された人物へ送る、連打で招待を複数作る、第三者がtokenを消費する、交代後のAが対象グループへ再アクセスする、Aの別グループ権限まで失う、別グループの表示や更新が混入する。
- Server-side check: 候補表示を信用せず、既存の招待作成と連携mutationでFree状態、唯一の現管理者、同一グループ、既存スタッフ、招待状態、確認済みメールを再確認する。
- Rate limit / idempotency: 既存Function Testを主担当とし、UIは既存`useSingleFlight`とloading状態を維持する。E2Eは一回の最終操作に対してOutboxが一件であることだけを確認する。
- Lifecycle / recovery: `issued`まではAをactiveのまま維持し、Bの連携完了時だけAをremoved、Bをactiveへ同一mutationで変更する。取消、期限、失敗時のA維持は既存Function Testを主担当とする。
- Emergency recovery: Aが交代開始前に操作不能となった場合の復旧は問い合わせ対応とし、新しい権限昇格経路を作らない。
- Logs / PII: 通常probe、ログ、snapshot、公開artifactへメール本文、raw token、provider error全文を含めない。tokenは既存のE2E専用helperからbrowserへ直接渡す。
- Data retention: 新しい永続field、table、監査payload、通知種別を追加しない。
- Regression test: UIの送信前状態はBehavior、単一API境界は既存Function、原子的な業務遷移は既存Scenario、実認証・画面切替・tenant非混入はE2Eへ分担する。

## 12. 軽量な停止条件

### 12.1 自己修正して継続する条件

次はblockerではない。

- 実装またはテストの失敗。
- selector、文言、ファイル配置の現行コードとのドリフト。
- 型エラー、lint warning、format差分。
- fixture不足、reset競合、web-first assertionの待機不足。
- 結果ゲートの契約抽出漏れ。
- 近い既存helperを再利用するための小さな修正。

原因を切り分け、契約IDと固定仕様を変えずに修正して再実行する。

### 12.2 今回へ広げない条件

次を発見しても実装対象に加えない。

- 唯一の管理者が操作不能になった場合の復旧UI、復旧API、代理交代。
- 既存スタッフではない人物へのFree交代。
- 同名グループ、同名店舗の識別UI。
- 前任者への交代完了通知。
- 後任側の追加承認。
- アーカイブ店舗だけに所属する後任候補の専用分岐または専用E2E。

- 新しいVRT Storyとbaseline更新。

対象外の不足を理由に追加2契約の完了を止めない。

### 12.3 Goalをblockedにできる条件

同じ外部条件が3回の連続するGoal turnで解消せず、非browser実装、対象下位層テスト、静的検証まで完了していて、これ以上安全に進めない場合だけ`blocked`にする。

- E2E Clerk credentialsが利用できない。
- ユーザー管理のViteまたはConvexへ到達できず、規約により新規起動できない。
- 必要なsandbox権限またはPreview権限を継続して得られない。
- task-ownedでない同一箇所の変更と安全に統合できない。

blocked時は、失敗した正確なコマンド、終了code、環境由来と判断した根拠、完了済みGate、未完了契約IDを報告する。

作業量、設計上の軽微な選択、テスト失敗、残token量をblocked理由にしない。

# AIシフト下書き機能 詳細設計

作成日: 2026-07-03 / ステータス: 設計レビュー待ち（実装は本設計書承認後）

## 1. 概要

回収したシフト希望をもとに管理者が手作業でシフトを組む煩わしさを解消するため、シフトボード画面に「AIで下書き」ボタンを追加する。押すとAIが希望と過去実績の傾向からシフトのたたき台を生成し、編集中のボードに反映する。

**設計思想: AIはあくまでたたき台。** 生成結果はDBに書かず編集状態にのみ反映し、管理者が目検・手直しした上で既存の保存/確定フローで永続化する。

### 確定要件

| # | 要件 |
|---|------|
| 1 | シフトボード画面（ShiftForm）にボタン設置。押下でAIがたたき台を生成 |
| 2 | 希望提出済みスタッフのみ割当対象。**未提出者は含めない** |
| 3 | 割当は**希望時間の範囲内のみ**（はみ出す割当はしない） |
| 4 | 必要人数は過去2〜3回の確定シフト実績から「曜日×時間帯の配置人数」を**自動推定**（マスタ設定は作らない） |
| 5 | Claude Haiku 4.5 + Convex `"use node"` action。API呼び出し・プロンプトは隔離モジュールで差し替え可能。tool use強制でJSON出力を固定 |
| 6 | 確認ダイアログを経て**全体上書き**で編集状態（`shiftsAtom`）に反映。DB書き込みなし |
| 7 | 提出パターン3種（time / shiftType / dateOnly）**全対応** |
| 8 | ポジションは全員デフォルト（AIは「誰がいつ入るか」のみ決める） |
| 9 | 乱用対策は既存Rate Limiter基盤でレート制限のみ |
| 10 | **過去期間と現募集で営業時間帯・提出パターンが変わっているケースに頑健な傾向分析**（`recruitments.submissionPattern`は募集ごとのスナップショットなので普通に起きる） |

## 2. 全体データフロー

```
[ShiftForm Shellヘッダー「AIで下書き」ボタン]（Provider内）
  └─ 確認ダイアログ「既存の入力を置き換えます」→ OK
       └─ await onGenerateDraft()  ← ShiftBoardPage が注入するコールバック
            │
   ┌───── Convex 公開action: api.aiShiftDraft.actions.generateShiftDraft ─────┐
   │ 1) ctx.runMutation(internal.aiShiftDraft.mutations.prepareDraftInput)     │
   │      認証 + IDOR検証 + rateLimit("aiShiftDraft") + 入力収集 + 傾向前処理  │
   │ 2) 提出者0件などの早期リターン判定                                        │
   │ 3) prompt.ts でsystem/user/toolスキーマ構築                               │
   │ 4) anthropicClient.ts でAnthropic API呼び出し（Haiku 4.5, tool強制）      │
   │ 5) tool_useブロックからJSON抽出（失敗→parse_error）                       │
   │ 6) validateDraft.ts で検証。不正な割当は1件ずつドロップ（全体失敗にしない）│
   │ 7) return { status:"ok", assignments, droppedCount }                      │
   └───────────────────────────────────────────────────────────────────────────┘
            │
       ShiftBoardPage: assignments → ShiftData[] に変換（既存buildShiftData再利用）
            └─ ShiftData[] を戻り値でボタンに返す
                 └─ ボタン（Provider内）が setShifts で shiftsAtom を全体上書き
                      └─ onShiftsChange 発火 → computeAssignmentWarnings 自動再評価
                           └─ 以降は既存の保存/確定ボタン（buildAssignments → saveShiftAssignments）
```

- DBへは一切書かない（`draftSavedAt`等も触らない）。上書き後はbaselineと差分が出るため、既存の未保存検知・離脱ブロックが自然に働く。
- 所要時間は数秒〜十数秒を想定（生成中はボタンにスピナー表示）。

## 3. Convex API設計（`convex/aiShiftDraft/` スライス）

### 3.1 方式: 公開actionの同期呼び出し

`useAction(api.aiShiftDraft.actions.generateShiftDraft)` をクライアントから直接呼ぶ。

- 前例: `src/components/features/Line/useRedeemLineToken.ts` → `api.line.actions.redeemLineToken`
- `rateLimit()` は`rateLimits`テーブルへ書き込むためmutation ctx必須。actionから直接呼べないので、**action冒頭で`internalMutation`（認証+IDOR+レート制限+データ収集）に委譲**する。`redeemLineToken` → `internal.line.mutations.validateLinkToken` と同型
- mutation+scheduler+結果テーブル+購読方式は不採用: 実装量が大きく、結果の一時保存が「DBに書かない」方針と衝突する。生成は単発・短時間なので同期で十分

### 3.2 ファイル構成

```
convex/aiShiftDraft/
├── actions.ts          "use node"。公開action generateShiftDraft（薄いオーケストレータ）
├── mutations.ts        internalMutation prepareDraftInput（認証/IDOR/rateLimit/収集/傾向前処理）
├── schemas.ts          Zod: DraftAssignment等（フロント共有。純粋Zod定義のみ）
├── prompt.ts (+test)   system/userプロンプト・toolスキーマ構築（純粋関数）
├── trend.ts (+test)    過去実績→正規化ヒートマップ→目標人数（純粋関数。§5の中核）
├── validateDraft.ts (+test)  AI出力の検証パイプライン（純粋関数。§7）
├── anthropicClient.ts  Anthropic API呼び出しの隔離モジュール（要件5: 差し替え可能）
└── types.ts            DraftInput / DraftAssignment / GenerateDraftResult
```

### 3.3 関数シグネチャ

```ts
// mutations.ts
export const prepareDraftInput = internalMutation({
  args: {
    recruitmentId: v.id("recruitments"),
    shopId: v.optional(v.id("shops")),
    userTokenIdentifier: v.string(), // actionのctx.authから引き渡し
  },
  handler: async (ctx, args): Promise<
    | { status: "ok"; input: DraftInput }
    | { status: "rate_limited"; retryAt: number | null }
    | { status: "unauthorized" }   // 未認証・所属外recruitmentは区別しない（列挙攻撃対策）
    | { status: "no_submitters" }
  > => { ... },
});

// actions.ts ("use node")
export const generateShiftDraft = action({
  args: { recruitmentId: v.id("recruitments"), shopId: v.optional(v.id("shops")) },
  handler: async (ctx, args): Promise<GenerateDraftResult> => { ... },
});

// types.ts
type DraftAssignment = { staffId: string; date: string; startTime: string; endTime: string; optionId?: string };
type GenerateDraftResult =
  | { status: "ok"; assignments: DraftAssignment[]; droppedCount: number }
  | { status: "rate_limited"; retryAt: number | null }
  | { status: "unauthorized" }
  | { status: "no_submitters" }
  | { status: "parse_error" }
  | { status: "api_error" };
```

- **throwせずstatus unionを返す**（既存actionの流儀）。API例外はtry/catchで`api_error`に丸める
- 認証: actionの`ctx.auth.getUserIdentity()`で得た`tokenIdentifier`をmutationに渡し、mutation内でuser→shop所属を解決（`convex/_lib/functions.ts`の`resolveShopForUser`相当のロジックを共有化）。`recruitment.shopId !== shop._id`は`unauthorized`
- `DraftAssignment`は`saveShiftAssignments`のassignments引数と同形（positionIdなし=デフォルトポジション）。既存の保存契約にそのまま合流する

## 4. 入力データ収集とプロンプト用DTO

### 4.1 収集内容（`prepareDraftInput`内。すべてindexedクエリ）

| データ | 取得方法 |
|--------|---------|
| 現募集 | `ctx.db.get(recruitmentId)` → periodStart/End, shopClosedDates, submissionPattern |
| 提出者集合 | `shiftSubmissions.by_recruitmentId`（存在=提出済み。前例: `convex/shiftBoard/queries.ts:66`） |
| 提出者の希望 | `shiftSubmissionSlots.by_recruitmentId`（time/shiftType）/ `shiftSubmissionDates.by_recruitmentId`（dateOnly） |
| スタッフ | `staffs.by_shopId_isDeleted`。`excludedFromShift`は除外 |
| 過去実績 | `recruitments.by_shopId_and_isDeleted_and_status_and_periodEnd` で `status="confirmed" && periodEnd < today` をdesc取得し`take(3)`（前例: `convex/dashboard/queries.ts` getDashboardPastRecruitments）→ 各期間の`shiftAssignments.by_recruitmentId` |

件数上限は `convex/constants.ts` の `SHIFT_BOARD_STAFF_LIMIT` / `SHIFT_ASSIGNMENT_LIMIT` に準拠。

### 4.2 プロンプト用コンパクトDTO（トークン節約 + ハルシネーション対策）

```jsonc
{
  "period": { "start": "2026-07-16", "end": "2026-07-31", "closed": ["2026-07-20"] },
  "pattern": { "kind": "time" },  // shiftTypeなら {kind, options:[{id,name,st,et}]}
  "staff": [ {"i": 0, "n": "田中"}, {"i": 1, "n": "佐藤"} ],  // AIは i のみ返す
  "requests": {  // 提出者の希望のみ。未提出者はそもそも載せない
    "0": { "2026-07-16": [["10:00","15:00"]] },   // time: 希望時間帯（複数可）
    "1": { "2026-07-16": "day" }                    // dateOnly: 日のみ。shiftType: optionId配列
  },
  "target": {  // §5で算出した曜日×時間帯の目標同時在籍人数
    "mon": [["10:00","14:00",2], ["14:00","18:00",3]]
    // 現募集がshiftTypeの場合は区分単位: { "mon": {"opt_morning": 2, "opt_evening": 3} }
  }
}
```

- **過去実績の生データは渡さない。** 集計値（target）のみ渡すのが最大のトークン削減
- 概算: スタッフ20名×16日で入力5〜8kトークン、出力2〜4kトークン。Haiku 4.5で1回あたり1円未満・数秒〜十数秒

## 5. 傾向分析の正規化設計（要件10の中核: `trend.ts`）

**方針: 過去実績をパターン非依存の共通表現「曜日×30分スロットの在籍人数ヒートマップ」に正規化してから集計し、現募集の営業時間帯・パターンへ再投影する。** これにより「募集の時間帯が前回と変わった」「提出パターンが前回と変わった」ケースに頑健になる。

### 5.1 正規化パイプライン（すべて純粋関数）

1. **時間展開**: 過去の各`shiftAssignments`行を実時間区間`[startTime, endTime)`として扱う
   - 過去がtime: そのまま
   - 過去がshiftType: `optionId`→**当時の**recruitmentの`submissionPattern.options`の時間に展開（`ShiftTypeOption = {id, name, startTime, endTime, sortOrder}`、`convex/_lib/submissionPattern.ts:10`）
   - 過去がdateOnly: 確定時に管理者が時間を付けているので`shiftAssignments`にはstartTime/endTimeがある。そのまま使える
   - → **どのパターンの過去実績も実時間に落ちるため、パターン不一致でも除外不要**
2. **曜日×30分スロット集計**: 各区間を30分刻みスロットに展開し、曜日×スロットの在籍人数を加算
3. **期間按分**: 過去N期間で「その曜日が営業日として何日あったか」で割り、**1営業日あたりの平均同時在籍人数**へ。定休日（`shops.regularClosedDays`）・`shopClosedDates`は母数から除外。期間の長さ・営業日数の違いを吸収
4. **現営業時間帯へクランプ**: 現募集の`getBoardTimeRange(現pattern)`（`convex/shiftBoard/validation.ts:54`）の外側スロットは捨てる。**現在の方が営業時間が広い区間は最近傍スロット値で補間**（0埋めだと端の時間帯が誰も居ない下書きになるため）
5. **現パターンへ再投影**:
   - 現time / dateOnly: 人数が同水準の連続スロットを帯にまとめ `[[start, end, count], ...]`
   - 現shiftType: 各optionの`[st, et)`に重なるスロット目標の**時間加重平均（四捨五入）**をoption単位の目標人数に按分

### 5.2 頑健性の整理

| 変化 | 扱い |
|------|------|
| 提出パターンが変わった（time↔shiftType↔dateOnly） | 手順1で実時間に正規化するため影響なし。出力側は手順5で現パターンに合わせる |
| 営業時間帯が広がった | 過去データがないスロットは最近傍補間（手順4） |
| 営業時間帯が狭まった | 単純クランプ（手順4） |
| shiftTypeのoption改廃 | 過去は当時のoptionで時間展開、targetは現optionに按分。AIに渡すenumは現optionのみ |
| スタッフ総入れ替え | targetは「延べ配置人数」で個人非依存。AIは現在の提出者の希望内で埋めるだけ |
| 過去確定期間0件（初回店舗） | targetなしの**希望ベースモード**にフォールバック: プロンプトを「各提出者を希望範囲で無理なく割当てる」指示に切り替えて生成は続行 |

## 6. プロンプト設計とtoolスキーマ（`prompt.ts`）

### 6.1 systemプロンプト（要旨）

- 役割: 店舗シフト作成アシスタント。管理者が手直しする「たたき台」を作る
- 厳守ルール:
  1. `staff[].i` に存在するインデックスのみ使用（名前・IDを出力しない）
  2. 割当は各スタッフの`requests`に示された**希望の範囲内のみ**。希望のない日・`closed`の日は割当禁止
  3. `target`（曜日×時間帯の目標人数）に近づける。**超過より不足を許容**（たたき台なので）
  4. ポジション・区分の創作禁止（shiftTypeは希望された区分IDから選ぶだけ）
  5. 必ず指定toolを1回呼び、散文を書かない
- パターン別の出力単位指示（time=時間帯 / dateOnly=希望日に過去傾向から妥当な時間帯を補完 / shiftType=区分ID選択のみ）

### 6.2 userプロンプト

§4.2のDTOをJSONで埋め込み。「以下のデータでシフトの下書きを作成してください」の一文のみ添える。

### 6.3 toolスキーマ（`tool_choice: {type: "tool", name: "submit_shift_draft"}` で強制）

```jsonc
// time / dateOnly（時間帯を出力させる）
{ "name": "submit_shift_draft",
  "input_schema": { "type": "object", "properties": { "assignments": { "type": "array",
    "items": { "type": "object",
      "properties": {
        "i":    { "type": "integer" },  // staff index
        "date": { "type": "string" },   // "YYYY-MM-DD"
        "start":{ "type": "string" },   // "HH:MM"
        "end":  { "type": "string" } },
      "required": ["i","date","start","end"], "additionalProperties": false } } },
    "required": ["assignments"], "additionalProperties": false } }

// shiftType（区分IDのみ出力させ、時間はサーバ側でoptionから復元）
"items": { "properties": {
    "i": {...}, "date": {...},
    "optionId": { "type": "string", "enum": ["opt_morning", "opt_evening"] } },  // 実在IDを列挙=区分の創作防止
  "required": ["i","date","optionId"] }
```

- `temperature: 0`（再現性・コスト）、`max_tokens`は割当上限から算出（目安4096）
- モデルIDは`AI_SHIFT_DRAFT_MODEL`環境変数で差し替え可能

### 6.4 隔離モジュール（`anthropicClient.ts`）

```ts

export const anthropicDraftClient: AiDraftClient = async (req) => { /* SDK呼び出し + tool_use抽出 */ };
```

actionは`AiDraftClient`型に依存し、テスト時・モデル変更時はこの1ファイルだけ差し替える（要件5）。

## 7. AI出力の検証パイプライン（`validateDraft.ts`）

**方針: 不正な割当は1件ずつドロップし、全体失敗にしない。** ドロップ数は`droppedCount`で返しトーストで軽く通知する。

検証順（各assignment）:

1. `i`がstaff index範囲内 → 実`staffId`へ解決。範囲外→ドロップ
2. `staffId`が**提出者集合に含まれる**（未提出者除外の二重防御）
3. `date`がISO妥当（`isValidIsoDateString`）・期間内・`shopClosedDates`でない
4. **希望範囲内チェック**（`src/domains/shift/assignmentWarnings.ts`の`OUTSIDE_REQUESTED_TIME`と同じ判定基準）:
   - time: 割当`[start, end)`がその日の希望帯に収まる
   - dateOnly: その日に希望提出あり + 営業時間内
   - shiftType: `optionId`がそのスタッフのその日の希望区分集合に含まれる
5. shiftTypeは`optionId`→optionの時間を**サーバ側で付与**（AIに時間を作らせない）
6. 同一`staffId×date`の時間重複を除去
7. **最終ゲート**: 生き残った全件を既存`validateShiftAssignments`（`convex/shiftBoard/validation.ts:77`。OUT_OF_PERIOD / CLOSED_DAY / SHIFT_TYPE_* / OVERLAP等12種）に通し、issueが出た行をドロップ

クライアント反映後は既存`computeAssignmentWarnings`が自動で再評価される。AI出力は希望範囲内に制約するため、**警告が出る＝検証漏れの検知**としても機能する。

## 8. フロントUX設計

### 8.1 ボタン配置と反映経路（Providerスコープ制約）

`ShiftForm`はJotai `<Provider>`でラップされており（`src/components/features/Shift/ShiftForm/index.tsx:330-334`）、`shiftsAtom`はインスタンスごとに分離されている。**親のShiftBoardPageから`useSetAtom(shiftsAtom)`は届かないため、反映はShiftForm内部で行う**:

- `ShiftFormProps`に `onGenerateDraft?: () => Promise<ShiftData[] | null>` を追加（undefinedならボタン非表示。StaffView・Demoでは渡さない）
- 新規 `AiDraftButton`（`ShiftForm/components/`または独立ディレクトリにコロケート）をShellヘッダー（index.tsx:299-304）のSaveButtonの左隣に配置。sparkleアイコン+「AIで下書き」
- ボタンはProvider内にいるので:
  1. クリック → 確認ダイアログ「既存の入力を置き換えます。AIが作るのはたたき台です。」
  2. OK → ローカル`isGenerating`をtrueにし `await onGenerateDraft()`
  3. 戻り値が`ShiftData[]`なら `useSetAtom(shiftsAtom)` で全体上書き（nullなら何もしない=親がトースト表示済み）
- 表示条件: `!isReadOnly && !isConfirmed && onGenerateDraft`。提出者0人（`staffs.some(s => s.isSubmitted)`がfalse）ならdisabled+ツールチップ

### 8.2 ShiftBoardPage側（features層 = action呼び出しの置き場所）

新規 `src/components/features/ShiftBoard/useAiShiftDraft.ts`:

```ts
const generateAction = useAction(api.aiShiftDraft.actions.generateShiftDraft);
// handleGenerateDraft: () => Promise<ShiftData[] | null>
```

### 8.3 AI結果 → ShiftData[] 変換

既存`buildShiftData`（`src/components/features/ShiftBoard/ShiftBoardPage/index.tsx` L77-236）は`getShiftBoardData`の`shiftAssignments`からShiftData[]を組み立てる。AI結果は同形（`{staffId, date, startTime, endTime, optionId?}`）なので、**`shiftAssignments`をAI結果に差し替えた擬似データを`buildShiftData`に通して再利用する**（必要なら関数を`src/domains/shift/`へ外出しして`toDraftShiftData.ts (+test)`とする）。

- デフォルトポジションの付与、shiftTypeのoption→segment変換、希望表示（requestedTime等）が既存ロジックで一貫する
- baseline（保存済み状態）は更新しない → 既存の未保存検知・離脱ブロッカーが機能

| 過去確定期間0件（初回店舗） | 希望ベースモードで生成続行（§5.2） |
| スタッフ総入れ替え | targetは個人非依存なので問題なし |
| 定休日・臨時休業日 | プロンプト`closed`で禁止指示 + 検証CLOSED_DAYで二重防御 |
| AI応答パース失敗（tool未使用/JSON壊れ） | `parse_error`。既存入力は上書きしない |
| APIタイムアウト・例外 | `api_error`。同上 |
| レート制限超過 | mutation段で遮断（Anthropic課金前）。`retryAt`付きトースト |
| 希望はみ出し・未提出者・期間外の出力 | 検証パイプラインでドロップ（§7） |
| 生成中に希望が更新された（購読でデータ変化） | 生成は都度スナップショット。管理者が手直しする前提で許容（要件1） |
| 全件ドロップ（valid 0件） | okだが空配列 → 「生成結果が希望と合いませんでした」トースト、上書きしない |

# LP改善と機能ページ 計画

## 文書の状態

- 状態: `Active`
- 作成日: 2026-09-25
- 対象: `src/components/features/LandingPage/`、`src/components/features/ProductFeatures/`、`src/pages/features/`、`src/routes/features*.tsx`
- 現在の正本: [公開サイト](../features/public-pages.md)と、上記のコード

この文書は、Search Consoleとキーワード調査のデータ、他社のLPと機能ページの調査をもとに、TOPを作り直し、機能ページを追加した判断の記録である。  
現在仕様の正本ではない。

## 決定事項

- TOPの説明を「課題 → 毎月の流れ → スタッフ側 → 主な機能 → 使えるお店 → 料金 → FAQ」の順に組み直す。  
  課題、毎月の流れ、主な機能は、希望シフトの回収、催促、シフト作成、共有という同じ4つの仕事で並べ、説明の粒度をそろえる。
- 旧TOPの「自動で回収・催促・共有」「3ステップ」「比較」の3sectionは同じ内容を別の粒度でくり返していたため、「毎月やることは3つだけ」の1sectionへまとめる。
- Heroの見出しは、抽象的な「やり取りをひとつに」から、仕組みと結果が分かる「希望シフトをLINEで集めて そのままシフト表に」へ変える。  
  検索語の「シフト管理」はHero上部の小見出しとtitleで示す。
- `/features`を機能一覧とし、`/features/:featureSlug`に5つの機能ページを置く。
- 2026-09-24には、中身が薄くなる懸念から機能ページを見送り、Search Consoleで需要を確認してから再検討すると決めていた。  
  今回はSearch Consoleのデータで機能に対応する検索語の表示が確認でき、ユーザーから機能ページの追加を依頼されたため、需要のある機能に絞って作る。
- TOPのtitleは変えない。  
  TOPはクリック率11.4%、平均掲載順位4.6で、主な検索語を既に含んでいるため、本文とFAQの改善を先に行う。
- ヘッダーの「導入事例」は、実際の導入事例がないため「活用例」へ変える。
- 新しいイラストはCodex CLIのgpt-6-solで生成し、既存と同じタッチのまま、1枚ごとに構図を変える。  
  当面はPNGで置き、WebPへの変換は別作業で行う。

## データから読んだこと

調査データは、ユーザーのGoogle Driveにある`20260701_キーワードSEO`フォルダのCSVである。

- 過去3か月のクリックは924件で、TOPが830件を占める。  
  指名検索「シフトリ」を除くと、「line シフト 無料」「line シフト管理 無料」「シフト希望 line」「line シフト提出」などLINEと組み合わせた検索語が中心である。
- 「シフト提出 line」は表示229回で平均掲載順位5.9だが、クリック率は0.44%にとどまる。  
  スタッフが提出方法を調べる意図が混ざるため、店長向けの回収方法を説明するページで受ける。
- 表示の75%以上がモバイルである。
- キーワードマップでは、LINEでの提出・回収、未提出の催促、シフト作成ツール、無料アプリの比較に店長の意図が集まる。  
  「AIでシフト作成」は検索量があるが、シフトリにない機能のため狙わない。

## 調査で参考にしたこと

- 機能ページは一つの意図、一つの主張、実際の製品画面、一つのCTAに絞ると、検索と成約の両方に効く（[SAGEOBOT](https://sageobot.com/blog/saas-landing-page-content-checklist)）。
- ハブとスポーク構成では、ハブがすべての機能ページへリンクし、各ページはハブと関連ページへ説明的なアンカーでリンクする（[Virayo](https://virayo.com/blog/hub-and-spoke-seo)）。
- 1位の機能ページの本文は170〜970語程度で、文章量より意図との一致が重要である（[Search Engine Journal](https://www.searchenginejournal.com/non-branded-keywords-organic-traffic/472978/)）。
- Heroの見出しは一つの主張に絞り、ファーストビューには抽象イラストより実際の製品画面を置く（[Studio Maydit](https://studiomaydit.com/blog/saas-landing-page-best-practices-2026)）。
- 競合のらくしふとAirシフトは、TOPで主要機能を短く示し、機能ページで「収集・作成・調整・共有」を詳しく説明し、関連機能とFAQへつなぐ構成である（[らくしふ](https://rakushifu.jp/function/shift-management/)、[Airシフト](https://airregi.jp/shift/function/management/)）。

## 機能ページ

| slug | 主な検索意図 |
|---|---|
| `shift-request-collection` | LINEでシフト提出・希望を集めたい、提出アプリを探している |
| `submission-reminder` | 未提出の催促を減らしたい |
| `shift-schedule` | シフト作成ツール、スマホでシフトを作りたい |
| `shift-sharing` | 確定シフトをLINEで共有したい |
| `multi-store` | 複数店舗や複数人でシフトを管理したい |

LINE連携そのものを説明する独立ページは作らない。  
「line シフト管理」系の検索はTOPが受けており、同じ意図のページを増やすとTOPと競合するためである。

## やらないこと

- 業種別ページは作らない。TOPの「活用例」で、提出方法とお店の働き方の相性として示す。
- 導入事例、導入店舗数、効果の数値など、根拠のない実績は書かない。
- シフトの自動作成、勤怠管理、給与計算をできるように書かない。機能一覧の「シフトリにない機能」で明示する。

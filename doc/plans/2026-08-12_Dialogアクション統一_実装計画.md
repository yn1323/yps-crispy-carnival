# Dialogアクション統一 実装計画

作成日: 2026-08-12

状態: completed

対象: 共通`Dialog` / `StepperDialog`、`src/components/features/`のproduction Dialog、関連するStorybook、VRT、UI設計方針、`ui-architect`

## 1. 結論

Dialogのアクションは、意味、配置スロット、閉じられる状態を共通部品で表現する。
安定した設計契約は[UI設計方針](../rules/ui-design.md#dialogのアクション)だけを正本とし、featureとSkillへ同じ表を複製しない。

デスクトップでは最終アクションを右端へ置く。
モバイルでは単一アクションを全幅、短い二アクションを同幅の横並び、長い二アクションを縦積みにする。
footerのグローバルアクションは最大二つとする。
閲覧専用の「閉じる」は右端またはモバイルの最下段を占めるが、Primary配色にはせずSecondaryのoutlineを維持する。

実装開始時点のsource宣言は`Dialog`が36、`StepperDialog`が6の計42件だった。
このうち`StaffInvitationDialogView`の1件はStory専用の合成shellでproductionから到達しないため、本計画のproduction対象は41件（`Dialog` 35件、`StepperDialog` 6件）とする。
現行の再監査では、feature側のproduction宣言は`Dialog`が32、`StepperDialog`が6の計38件である。
D04、D07、D10のnested確認を既存shellのinline confirmationへ統合したため、実装開始時点のproduction 41件から3件減少した。
このほか、共通の`DeferredDialogBoundary`に遅延読込Error用の`Dialog`が1宣言あるため、共通fallbackを含むuser-facing宣言は計39件である。`StepperDialog`内部の`Dialog`は同じmodal shellの実装詳細であり、別のuser-facing Dialogとして二重計上しない。

## 2. 共通部品の契約

共通`Dialog`は、通常footerとcustom footerのどちらでも同じaction areaを使う。

| API | 責務 |
|---|---|
| `DialogActionArea.startAction` | Secondaryのうち、Stepperの「戻る」など左側へ分離する操作 |
| `DialogActionArea.endAction` | 右端または最下段を占める最終アクション。単一の「閉じる」もここへ置く |
| `DialogActionArea.layout="standard"` | 標準Dialogのアクションを右側へまとめる |
| `DialogActionArea.layout="flow"` | StepperやDialog内フローで、開始側と最終側を左右へ分ける |
| `DialogActionArea.mobileLayout="inline"` | モバイルで短い二アクションを同幅の横並びにする |
| `DialogActionArea.mobileLayout="stacked"` | 長い二アクションを縦積みにする |
| `Dialog.actionLayout` | 既定footerのデスクトップ配置を選ぶ。既定値は`standard` |
| `Dialog.mobileActionLayout` | 既定footerのモバイル配置を選ぶ。既定値は`inline` |
| `Dialog.mobileFullScreen` | モバイル全画面の高さ、角丸、本文scroll、footer safe areaを共通化する |
| `StepperDialogContent.mobileActionLayout` | Stepperの短い二操作は`inline`、長い二操作は`stacked`を明示する |

`Dialog`にsubmitがない場合は、Secondary配色の「閉じる」を`endAction`へ置く。
custom footerは任意の`Flex`を直接渡さず、`DialogActionArea`へ`startAction`と`endAction`の少なくとも一方を渡す。
`startAction`だけの構成は、本文内の候補追加を局所操作として残し、footerのグローバル操作が内部フローの「戻る」だけになる状態に限定する。
閲覧終了の単独「閉じる」は常に`endAction`を使う。
`StepperDialog`のaction barは同じ配置契約を共通`StepperDialogActionBar`で実装し、本文scroll、footer配置、safe areaをfeatureごとに再実装しない。

### Production件数から除外する宣言

実装開始時点の`Dashboard/StaffManagement/StaffInvitationDialog.tsx`にあった`StaffInvitationDialogView`は、Storyが直接使うstandalone shellだった。
当時のproductionは`StaffManagementView.tsx`の遅延読込shellと`StaffInvitationDialogContent`を合成していたため、この1宣言をproduction 41件へ含めない。
移行中に両者のshellは`StaffInvitationDialogShell.tsx`へ共通化され、D07の確認もD08と同じshellの状態へ統合された。
現行の再監査では、この統合による宣言数の減少とproduction / Storyの到達先が一致していることを確認した。

`Line/LineLinkQrDialog/index.tsx`は名前に`Dialog`を含むが、Dialog shell、overlay、focus trapを持たないinline QR contentである。
`StaffDetailLineTab.tsx`と`UserShopLineSection.tsx`の本文へ埋め込まれるため、モーダル件数と移行対象から除外する。

fallbackは閲覧・Errorとして右端のSecondary「閉じる」を持ち、呼出側が`mobileFullScreen`を指定した場合は同じFS・常設契約を使う。

この状態だけはCloseを出さず「再実行する」を単独の最終アクションにし、完了または再試行可能な失敗へ移るまで全close経路をlockする理由付き例外とする。

## 4. 移行順

### 4.1 共通primitive

1. `DialogActionArea`、既定footer、`mobileFullScreen`を`Dialog`へ実装する。
2. `StepperDialogActionBar`へ同じDOM順とPC/SP配置の契約を実装する。
3. 共通Storyでstandard、flow、inline、stacked、単一Close、scroll、safe area、close lockを固定する。

### 4.2 構造上の不整合

1. D04、D07、D10の二重Dialogをinline confirmationへ変える。
2. D11、D27、D37など、閲覧時にfooterの「閉じる」がない状態を直す。
3. D08の方法別footer欠落を直し、D31は三つの選択肢を保ちながらfooterを二アクションへ整理する。

### 4.3 custom footerとclose lock

LoginMethods、組織設定、スタッフ/店舗所属、削除、締切後提出のcustom actionを共通APIへ移す。
処理中に閉じると結果が不明になる操作だけclose lockを使い、header、footer、Escape、外側click、ブラウザバックをまとめて制御する。

### 4.4 標準DialogとStepper

残る標準Dialogを既定footerへ寄せ、feature固有の`Flex`、幅、DOM順を削減する。
六つのStepper shellは、最初の段階、途中、最終段階の語彙とaction位置を揃える。

### 4.5 最終監査

production sourceを再検索し、宣言数、到達性、`hideFooter`、custom footer、`preventClose`、Dialogの入れ子を再分類する。
実装により宣言を統合した箇所は、減少理由と移行先をこの計画の実施結果へ記録する。

## 5. 受入条件

| 契約 | 完了条件 | 主担当層 |
|---|---|---|
| 意味とDOM順 | Secondaryが先、PrimaryまたはDestructiveが最後で、見た目の順と一致する | 共有DialogのBehavior Test |
| PC配置 | standardは右側へまとまり、flowはstart側とend側に分かれ、最終アクションが右端にある | 共有DialogのVRT |
| SP配置 | 単一は全幅、短い二つは同幅横並び、長い二つは最終アクションを下にした縦積みになる | 共有Dialogのmobile VRT |
| 閲覧専用 | productionの閲覧、結果、通知、Error DialogすべてにSecondaryの「閉じる」がある | 各featureの代表Storyと最終監査 |
| Stepper | 初段のキャンセル、途中の戻る、次へ/確認へ、最終操作が同じaction areaで切り替わる | StepperDialogのBehavior Test |
| scrollとsafe area | 長い本文だけがscrollし、header/footerが残り、SP footerのsafe areaが重複しない | 共有DialogのVRT |
| close lock | lock中はheader、footer、Escape、外側click、ブラウザバックのどれでも閉じず、解除後は閉じられる | 共有DialogのBehavior Test |
| inline confirmation | Dialog内確認で同時に存在する`dialog` / `alertdialog`が一つで、取消時に元状態とfocusを復元する | 対象featureのBehavior Test |
| 語彙 | `戻る`、`キャンセル`、`閉じる`と完了動詞が正本の意味で使われ、`Submit`、`OK`、対象不明の`確定`を残さない | 最終監査と代表Story |
| 回帰範囲 | backend API、認可、永続データ、通知副作用を変更しない | 差分レビュー |

共通の配置とclose経路を各featureのBehavior Testへ重複させない。
各featureでは、inline confirmation、read-only切替、複数段階など、そのfeatureだけが持つ状態遷移を確認する。
見た目はPCと`vrt-mobile1`または`vrt-mobile2`の代表Storyへ分け、E2Eは追加しない。

feature側のproduction 38宣言（`Dialog` 32件、`StepperDialog` 6件）と、共通`DeferredDialogBoundary`のfallback 1宣言への移行を実装した。

共通footerとcustom footerは、Dialog全体のglobal actionを最大二つに統一した。

最終静的監査では、feature側のproduction宣言を`Dialog` 32件と`StepperDialog` 6件、共通fallbackを1件と再集計した。
Dialog全体のglobal actionが三つ以上、feature固有のfooter配置、`hideFooter`、nested Dialog、閲覧専用の「閉じる」欠落、SPの逆順・自動折り返し、処理中のclose lock欠落に該当する残件はなかった。

`ui-architect`のSkill検証、`pnpm docs:check`、`pnpm lint`、`pnpm type-check`、`pnpm build`、`git diff --check`を実施した。

# グループ追加、店舗追加、支払いのダークローンチ 実装計画

作成日: 2026-07-25

状態: 提案

対象checkout: 現在のcheckout（`feat/0723`）

## 1. 解決する問題

実装は揃っているが、公開したくない機能が三つある。
二つ目以降のグループ作成、店舗の追加、プランと支払いである。

これらを公開したまま出すと、実環境で確認していない外部設定に依存する導線が利用者へ見える。
[リリース状態](../manual/release-status.md)では、StripeのPrice、Webhook、Portal設定が全環境で未登録である。
`getStripeBillingConfiguration()`は未設定なら`misconfigured`を返すため、利用者が「プランと支払い」から操作しても設定不備のエラーに行き着く。

この計画は、コードを消さずに三つの導線を閉じ、後から定数一つで開け直せる状態にする。

現在Stripeへ到達しうる経路は一つだけである。
初回セットアップで作るグループは`complimentary.business`で始まり、Stripe objectを一切作らない隔離契約を持つ。
Stripeに触れるのは、二つ目以降のグループが`active.free`で始まり、そこから有料プランのCheckoutへ進む場合に限られる。
つまりグループ追加を閉じた時点で、支払い経路は実質的に閉じる。

## 2. 確定した判断

実装中に次を再検討しない。

| 項目 | 判断 | 理由 |
|---|---|---|
| 閉じ方 | コードのコメントアウトと削除は行わず、公開フラグで分岐する | 削除するとlint、type-check、58ファイルのテストが崩れる。解除時のconflictも避けたい |
| 公開フラグの位置 | `convex/constants.ts`の定数をサーバー側の正本とし、`getSettings`のDTOで画面へ配る | frontendのbuild-time flagを増やさない。[アカウント削除](../features/account-deletion.md)で採った方針と揃える |
| 解放の段取り | 店舗追加、支払い、グループ追加の順に開ける。詳細は10節 | 店舗追加は支払いと独立して開けられる。グループ追加はFree開始の設計を通じて支払いと結び付いているため、支払いより先に開けない |
| 店舗追加 | UIの非表示に加えて`addShop`をサーバー側で拒否する | `addShop`はpublic mutationであり、画面を経由せず呼べる。表示制御を認可根拠にしない |
| プラン上限 | `ORGANIZATION_PLAN_LIMITS`は変更しない | Businessの定義を書き換えると、解除時に元の意味へ戻す作業が増える。閉じるのは導線側で行う |
| 課金状態 | m022で全`organizationBillingStates`を`complimentary.business`へ寄せる | 支払い不要Businessは既にStripe隔離契約を持つ。新しい状態を増やさずに支払い経路を閉じられる |
| 移行時のデータ損失 | 許容する | trial、free、有料プランのグループは現時点で存在しない。寄せることで失われる情報がない |
| `/settings`画面 | 残す | グループ削除の入口がここにしかない。所属があるとアカウント削除を依頼できないため、画面ごと閉じると退会できなくなる |
| 管理者招待 | ダークローンチの対象に含めない | 複数管理者は今回の制限対象ではない。`complimentary.business`の管理者5名上限のまま運用する |
| Stripe Webhook route | 残す | 既存契約の署名済みWebhook、取消、請求停止、再照合は止めない。[販売停止の運用手順](../manual/organization-billing.md)と同じ扱いにする |
| Stripe回収cron | 残す | 対象が0件でも、回収経路を消すと再開時の復旧手段がなくなる |

### 2.1 ダークローンチ中の実効上限

全グループが`complimentary.business`になり、店舗追加が閉じるため、実効上限は次のとおりになる。

| 項目 | 上限 | 根拠 |
|---|---|---|
| 利用人数 | 40名 | `ORGANIZATION_PLAN_LIMITS.business.maxPeople` |
| 稼働店舗 | 1件 | 作成時の1件から増やせない |
| 有効管理者 | 5名 | `ORGANIZATION_PLAN_LIMITS.business.maxActiveManagers` |
| 自分で作れるグループ | 1件 | 初回セットアップの1件から増やせない |

`ORGANIZATION_SELF_CREATED_LIMIT`は`3`のまま残す。
この定数は`createOrganization`が閉じている間は評価されず、解除時にそのまま効く。

## 3. Security Lens

- **Actor**：認証済みの管理ユーザー本人。招待とcapabilityは関与しない。
- **Asset**：`organizations`と`shops`の作成、Stripe Customer・Subscription・Checkout Sessionの発行、課金状態。
- **Trust boundary**：ブラウザとConvex backend。新しいHTTP routeとWebhookは追加しない。`/stripe/webhook`の署名検証は現状のまま維持する。
- **Abuse case**：画面に導線がないことを利用して、`createOrganization`と`addShop`を直接呼ぶ。ダークローンチ中に作られたグループや店舗が、解除後の上限判定と食い違う。
- **Server-side enforcement**：公開フラグをサーバー側で評価し、`createOrganization`と`addShop`を`ConvexError`で拒否する。clientから公開可否を受け取らない。`getSettings`が返すフラグは表示用であり、認可根拠にしない。
- **Rate limit / idempotency**：既存の`organizationCreateShort`と`organizationCreateDaily`、`requestId`由来のcorrelationIdをそのまま残す。拒否は上限判定とrate limitより前に行い、閉じている間にbudgetを消費させない。
- **Lifecycle / recovery**：m022は再実行しても同じ最終状態になる。Stripeの痕跡がある行はpatchせずconflictへ残す。解除は定数の反転だけで行い、m022の逆migrationは作らない。
- **Logs / PII**：監査は既存の`recordOrganizationAuditEvent`だけを使う。拒否理由の文言に内部設定と環境変数名を含めない。
- **Regression test**：`createOrganization`と`addShop`が拒否され、DB、scheduler、監査のいずれも増えないことをConvex Function Testで固定する。

## 4. サーバー設計

### 4.1 公開フラグ

`convex/_lib/config.ts`へ、公開状態を読む関数を追加する。
TypeScriptのトップレベル定数にすると、テストから値を差し替えられない。
この文書内の他の設定値と同じく、呼び出しのたびに`process.env`を読む関数にする。

```ts
export function isOrganizationCreationEnabled(): boolean {
  return (process.env.FEATURE_ORGANIZATION_CREATION ?? "").trim() === "enabled";
}
```

店舗追加と支払いも同じ形で`FEATURE_SHOP_ADDITION`、`FEATURE_BILLING`を読む。

三つに分けるのは、解除の順序が同じとは限らないためである。
店舗追加だけを先に開ける判断も、支払いだけを後回しにする判断もあり得る。

未設定を閉じた状態として扱う。
新しいpreview deploymentと、変数を設定し忘れた環境が、既定で閉じる側に倒れる。

`scripts/setupEnv.ts`の`CONVEX_ENV_KEYS`へ三つのキーを追加する。
これにより、Convex deploymentとE2Eが同じ`.env`を正本にできる。
`playwright.config.ts`は既に`dotenv.config()`を呼んでいるため、E2Eからも同じ値を読める。

環境変数にすることで、段階解放は`convex env set`で完結し、再デプロイが要らなくなる。
画面側は`getSettings`の購読を通じて変化を受け取るため、frontendの再ビルドも要らない。

### 4.1.1 `getSettings`のDTO

`api.organization.queries.getSettings`の返り値へ、この三つを反映したフラグを足す。
既存の`canAddShop`と`canCreateOrganization`は、上限に達した状態と未公開の状態を区別できない。
画面は「上限に達したので理由を出す」と「未公開なので何も出さない」を描き分ける必要があるため、可否とは別のフィールドで渡す。

```ts
features: v.object({
  organizationCreation: v.boolean(),
  shopAddition: v.boolean(),
  billing: v.boolean(),
}),
```

### 4.2 グループ追加

`convex/setup/mutations.ts`の`createOrganization`の冒頭で拒否する。
`ctx.user`の確認より後、correlationIdの解決とrate limitより前に置く。
閉じている間に冪等record、rate limit budget、監査のいずれも消費させないためである。

`getOrganizationCreationAvailability`（`convex/setup/service.ts`）は変更しない。
上限判定の意味を保ったまま、公開フラグを別の層で重ねる。

`setupShopAndManager`は変更しない。
初回セットアップは今回の制限対象ではなく、`complimentary.business`で始まる挙動も維持する。

### 4.3 店舗追加

`convex/organization/mutations.ts`の`addShop`で、`requireOrganizationActorForShop`の直後に拒否を入れる。
actorの解決より前に拒否すると、所属していない利用者へ機能の有無を返してしまう。
既存の`requireOrganizationPaidFeature`と`requireOrganizationCapacity`は残す。

`archiveShop`と`reactivateShop`は変更しない。
1店舗しか持たないグループが唯一の店舗をarchiveできるかは既存の挙動であり、この計画で新しく変えない。

### 4.4 支払い

`convex/organizationStripe/actions.ts`のpublic actionは個別に閉じない。
全グループが`complimentary.business`になれば、既存のStripe隔離契約が拒否側に回るためである。
新しい拒否を重ねると、解除時に外す箇所が増える。

画面から「プランと支払い」タブを外すことで、これらのactionへ到達する導線がなくなる。
`getSettings`が返す`features.billing`は、その描画判定に使う。

## 5. データ移行

### 5.1 変更前後のshape

schemaは変更しない。
`organizationBillingStates.state`は既存unionの`{ kind: "complimentary", plan: "business" }`にそのまま収まるため、widenとnarrowの期間を設けない。

| 対象 | 変更前 | 変更後 |
|---|---|---|
| `organizationBillingStates.state` | 任意の課金状態 | `{ kind: "complimentary", plan: "business" }` |
| `organizationBillingStates.version` | 現在値 | 現在値 + 1 |
| `organizationBillingStates.freeManagerPersonId` / `freeShopId` | 設定されている場合がある | 削除する |

`freeManagerPersonId`と`freeShopId`はFree選択の結果を保持するfieldであり、支払い不要Businessでは意味を持たない。
残すと、解除後にFreeへ戻した際に古い選択が復活する。

### 5.2 migrationの単位と再実行性

`convex/migrations/m022_organization_billing_to_complimentary_business.ts`を追加し、`migrations.define`の`migrateOne`で`organizationBillingStates`を1行ずつ処理する。
`convex/migrations/index.ts`のrunner配列末尾へ追加する（連番の欠番を作らない）。
限定実行とdry run用に`runM022`を用意する。

既に`complimentary.business`の行は何もせずreturnする。
これにより再実行しても最終状態が変わらない。

`.collect()`は使わない。
グループ単位の確認は`by_organizationId`のindexで`take`する。

### 5.3 fail-closedの条件

m021は8種類のconflictでStripeの痕跡を分類している。
m022では同じ細かさを持たせない。

`origin/main`（2026-07-12の`v0.0.63`）のschemaは`shopBillingStates`だけを持ち、`organizations`も`organizationBillingStates`も存在しない。
migrationもm008までである。
`convex/organizationStripe/`の初出は2026-07-22であり、mainの最終リリースより後にあたる。
つまりProductionには組織モデル以前のコードが載っており、Stripe関連のtableは存在しない。
m009からm021も未実行であり、Productionで照合すべきStripeの痕跡は原理的に0件である。

一方、developには新しいコードが載っており、動作確認で作られたStripeのテスト行が残っている可能性がある。
m022はdevelopで先に走るため、最小限のガードだけ残す。

conflictに落とす条件は次の三つとする。

- グループが存在しない。
- 同じグループの課金状態が一意でない。
- Stripe CustomerまたはSubscriptionがある。

operation、Webhook証跡、課金通知は個別に見ない。
CustomerもSubscriptionも無い行にそれらだけが存在する状態は、develop環境でも想定しない。

conflictの記録は既存の`recordOrganizationMigrationConflict`を使う。
監査のcorrelationIdは`${organizationId}:migration:m022:to-complimentary-business`とする。

### 5.4 完了条件とrollback

完了条件は次の三つを別々に確認する。

1. `organizationBillingStates`のうち`complimentary.business`以外が0件である。
2. m022のconflictが0件である。
3. `pnpm convex:migrate:status`でm022が`done`である。

逆migrationは作らない。
元の状態がtrialだったのかfreeだったのかを復元する情報は残らないためである。
現時点でその情報を持つ行が存在しないことが、この判断の前提である。
実行前にexport snapshotを取り、前提が崩れていた場合はforward repairをm023以降で設計する。

## 8. テスト計画

契約ごとに主担当層を一つ選ぶ。

| 契約 | 主担当層 | 配置 |
|---|---|---|
| `createOrganization`が拒否され、グループ、監査、scheduler、rate limit budgetが増えない | Convex Function Test | `convex/setup/mutations.test.ts` |
| `addShop`が拒否され、店舗、position、監査が増えない | Convex Function Test | `convex/organization/shopManagement.test.ts` |
| `getSettings`が`features`を返す | Convex Function Test | `convex/organization/queries.test.ts` |
| m022が対象行を寄せ、Stripe対応のある行をconflictへ残し、再実行で同じ最終状態になる | Convex Function Test | `convex/migrations/m022_*.test.ts` |
| 未公開時にタブ、ボタン、セクションが描画されない | UI Component Test | `src/components/features/OrganizationSettings/index.stories.tsx` |
| 公開状態と画面の導線が一致する | E2E | `e2e/scenarios/organization-creation-flow.test.ts` |

### 8.1 既存テストの扱い

公開フラグを環境変数にしたことで、Convex Function TestとScenario Testは`vi.stubEnv`で開閉を切り替えられる。
`convex/_scenario/accountDeletion.test.ts`と`convex/organizationStripe/actions.test.ts`が既に同じ方法を使っている。

グループ作成と店舗追加の既存テストは、開状態を検証する資産として残す。
各`beforeEach`へ`vi.stubEnv`で公開値を入れるだけで、期待値は現在のまま通る。
解除時にテストを開状態へ書き戻す作業が発生しない。

閉状態の拒否契約は、同じファイルへ別の`describe`として足す。

### 8.2 E2Eの扱い

E2Eは実deploymentへ接続するため、テストごとにフラグを切り替えられない。
`playwright.config.ts`は既に`dotenv.config()`を呼んでおり、Convex deploymentへ同期する`.env`と同じ値を読める。

そこで、公開状態を前提条件として分岐する1本を置く。
閉じていれば`/settings`に支払いタブとグループ作成の導線が無いことを確認し、開いていれば作成できることを確認する。
常に実行できるため、`.env`とdeploymentの設定がずれた場合もここで検知できる。

`e2e/scenarios/organization-billing-plan-change.test.ts`と`e2e/scenarios/trial-ending-notice.test.ts`は、対象の導線が閉じている間は成立しない。
削除せず、同じ前提条件で`test.skip`する。

`e2e/scenarios/organization-shop-lifecycle.test.ts`は、店舗追加を前提とする部分だけを同じ扱いにする。

### 8.3 重複させない層

- 拒否契約はConvex Function Testだけに置き、Behavior TestとE2Eへ重ねない。
- VRTは代表状態の見た目だけを見る。タブの有無をVRTの契約にしない。
- E2Eは導線の有無だけを見る。拒否時のerror messageをE2Eの契約にしない。

## 9. 実装順序

1. m022とそのFunction Testを追加し、developmentでdry runと限定実行を行う。
2. 公開フラグの読み出し関数、`scripts/setupEnv.ts`のキー追加、サーバー側の拒否、`getSettings`のDTO拡張を入れる。
3. 既存のグループ作成・店舗追加テストへ`vi.stubEnv`を足し、閉状態の拒否契約を追加する。
4. `OrganizationSettings`配下の描画分岐とStoryを直す。
5. E2Eへ前提条件による分岐を入れる。
6. `doc/features/organization-billing.md`、`doc/features/trial-ending-dashboard-callout.md`へ、公開していない導線を追記する。

## 10. 段階解放

四段階で開ける。
グループ追加は支払いより後に置く。

| 段階 | 開ける対象 | 設定 |
|---|---|---|
| 1 | なし（全制限） | 三つとも未設定 |
| 2 | 店舗追加 | `FEATURE_SHOP_ADDITION=enabled` |
| 3 | 支払い | `FEATURE_BILLING=enabled` |
| 4 | グループ追加 | `FEATURE_ORGANIZATION_CREATION=enabled` |

### 10.1 段階2で店舗追加を開ける

`convex env set`で値を入れ、UIの未公開分岐を戻すだけで足りる。

全グループが`complimentary.business`であり、`canUsePaidFeatures`はtrue、`maxActiveShops`は5である。
支払いが閉じたままでも、店舗追加の判定は既存の経路をそのまま通る。
段階2での実効上限は5店舗になる。

### 10.2 段階3で支払いを開ける

1. Stripeの外部設定と実環境証跡を[リリース状態](../manual/release-status.md)へ登録する。
2. `FEATURE_BILLING`を設定し、「プランと支払い」タブの描画分岐を戻す。

既存グループの課金状態は`complimentary.business`のまま残す。
通常プランへ移す判断が必要になった場合は、別のmigrationとして設計する。
この計画には含めない。

### 10.3 段階4でグループ追加を開ける

グループ追加を支払いより後に置くのは、二つ目以降が`active.free`（利用人数5名、稼働店舗1件、有効管理者1名）で始まる設計だからである。
支払いが閉じている間にグループ追加を開けると、利用者は二つ目のグループを作れるものの、そこから上げる手段がない状態で固定される。
一つ目のグループが40名と複数店舗で動いているのに、二つ目が5名1店舗になる。

段階3を先に済ませておけば、`createOrganization`と`createOrganizationWithFirstShop`に手を入れずに開けられる。
Free開始のまま、有料プランへの導線が既に存在する状態になるためである。

段階3と段階4を同じタイミングで開けてもよい。
順序を逆にできないという制約だけがある。

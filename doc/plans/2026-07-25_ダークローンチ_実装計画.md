# グループ追加、店舗追加、支払い、管理者招待・交代のダークローンチ 実装計画

作成日: 2026-07-25

更新日: 2026-08-09（店舗追加フラグの廃止を注記）

状態: ローカル実装完了・ロールアウト待ち

対象checkout: 現在のcheckout（`feat/0728`）

> 2026-08-09に店舗追加と既存人物の複数店舗所属を常時公開へ変更し、`FEATURE_SHOP_ADDITION`を廃止した。以下の同フラグに関する記述は当時の判断履歴として残し、現在の公開契約は[組織課金、複数店舗、複数管理者](../features/organization-billing.md)を正とする。

## 1. 解決する問題

実装は揃っているが、公開したくない機能が四つある。
二つ目以降のグループ作成、店舗の追加、プランと支払い、そして管理者の招待・交代である。

管理者の招待・交代は、当初この計画の対象外としていた。
2026-07-28の更新で、複数管理者の運用を初回公開の範囲から外す判断に変え、他の三つと同じく導線を閉じてUIを非表示にする対象へ加えた。

これらを公開したまま出すと、実環境で確認していない外部設定に依存する導線が利用者へ見える。
[リリース状態](../manual/release-status.md)では、StripeのPrice、Webhook、Portal設定を含む実環境証跡が未登録であり、現在値は未確認である。
`getStripeBillingConfiguration()`は未設定なら`misconfigured`を返すため、利用者が「プランと支払い」から操作しても設定不備のエラーに行き着く。

この計画は、コードを消さずに四つの導線を閉じ、後から対象ごとの公開フラグ一つで開け直せる状態にする。

現在のcheckoutで確認できるコード上の状態は次のとおりであり、実環境への設定反映とmigrationの実行状況は[リリース状態](../manual/release-status.md)を正本とする。

| m022 | 実装済み | migration本体とFunction Testが入っている。各環境での実行完了はこの計画書だけでは判定しない |

以降の設計は、実装済みの三機能を作り直すものではなく、同じダークローンチ方式を管理者招待・交代へ追加するための差分を含む。

現在Stripeへ到達しうる経路は一つだけである。
初回セットアップで作るグループは`complimentary.business`で始まり、Stripe objectを一切作らない隔離契約を持つ。
Stripeに触れるのは、二つ目以降のグループが`active.free`で始まり、そこから有料プランのCheckoutへ進む場合に限られる。
つまりグループ追加を閉じた時点で、支払い経路は実質的に閉じる。

## 2. 確定した判断

実装中に次を再検討しない。

| 項目 | 判断 | 理由 |
|---|---|---|
| 閉じ方 | コードのコメントアウトと削除は行わず、公開フラグで分岐する | 削除するとlint、type-check、58ファイルのテストが崩れる。解除時のconflictも避けたい |
| 公開フラグの位置 | `convex/_lib/config.ts`で環境変数を読む関数をサーバー側の正本とし、`getSettings`と`getCurrentUser`のDTOで画面へ配る | frontendのbuild-time flagを増やさず、テストから環境値を差し替えられる形に揃える。全認証画面の入口判定は店舗に依存しないため`getCurrentUser`を使う |
| 解放の段取り | 店舗追加、支払い、グループ追加の順に開ける。詳細は10節 | 店舗追加は支払いと独立して開けられる。グループ追加はFree開始の設計を通じて支払いと結び付いているため、支払いより先に開けない |
| 店舗追加 | UIの非表示に加えて`addShop`をサーバー側で拒否する | `addShop`はpublic mutationであり、画面を経由せず呼べる。表示制御を認可根拠にしない |
| プラン上限 | `ORGANIZATION_PLAN_LIMITS`は変更しない | Businessの定義を書き換えると、解除時に元の意味へ戻す作業が増える。閉じるのは導線側で行う |
| 課金状態 | m022で全`organizationBillingStates`を`complimentary.business`へ寄せる | 支払い不要Businessは既にStripe隔離契約を持つ。新しい状態を増やさずに支払い経路を閉じられる |
| 移行時のデータ損失 | 対象deploymentの実行前snapshotで失われる状態がないと確認できた場合に限り許容する | Productionとdevelopの実データは未確認であり、trial、free、有料プランのグループが存在しないと推定しない。前提を証跡で満たせない場合はm022を実行せず、保持またはconflict化を再設計する |
| `/settings`画面 | routeと直URLは残す。四つのフラグがすべて閉じている間は、UserMenu、Dashboard、警告表示からの通常入口だけを描画しない | 直URLでの運用・復旧手段とグループ削除は維持しつつ、未公開利用者へ設定画面の存在を通常導線から見せない。設定画面を起点にした詳細画面の戻り先は維持する |
| ユーザーの店舗所属追加 | `FEATURE_SHOP_ADDITION`が閉じている間は、ユーザー詳細の追加ボタン・Dialog・案内文と、スタッフ招待の他店舗候補タブを非表示にする | 物理的な新店舗作成と同じ複数店舗公開段階へ揃える。`addOrganizationPersonToShop`自体は既存店舗のスタッフ運用APIなので、今回のUI公開制御だけを理由に停止しない |
| 管理者招待・交代 | ダークローンチの対象に含める（2026-07-28に変更）。発行、再送、preview、受諾、通知配送をサーバー側で拒否し、関連UIを非表示にする | 当初は対象外としていたが、複数管理者の運用を初回公開の範囲から外す判断に変えた。UIを消すだけではpublic APIと発行済みtokenから迂回できる |
| 発行済み招待の受諾・取消・再送 | `resend`、`linkAccount`、legacy `accept`は閉じる。`revoke`とinternal `expire`は残す | 再送は新しい招待とTTLを発行し、受諾は管理者を増やすため停止対象である。取消と期限処理は残存招待を減らす整理経路なので維持する |
| 管理者権限の解除 | `removeManagerRole`へ新しい拒否を足さない。UIだけ非表示にする | 「最後の有効管理者の管理者権限は外せません」の既存ガードにより、管理者1名の間は状態を変えられない。developの複数管理者グループで直接呼ばれても、管理者が減る方向にしか働かない |
| `/manager-invite`受諾ページ | routeは残し、閉状態では`getPreview`と受諾APIが`unavailable`を返す | routeを消さず再開時の復旧作業を抑えつつ、発行済みtokenからの受諾とグループ名のpreviewを止める |
| Stripe Webhook route | 残す | 既存契約の署名済みWebhook、取消、請求停止、再照合は止めない。[販売停止の運用手順](../manual/organization-billing.md)と同じ扱いにする |
| Stripe回収cron | 残す | 対象が0件でも、回収経路を消すと再開時の復旧手段がなくなる |

### 2.1 ダークローンチ中の実効上限

m022が完了し、店舗追加・支払い・グループ追加・管理者招待の全フラグを閉じた後の目標状態では、実効上限は次のとおりになる。

| 項目 | 上限 | 根拠 |
|---|---|---|
| 利用人数 | 40名 | `ORGANIZATION_PLAN_LIMITS.business.maxPeople` |
| 稼働店舗 | 1件 | 作成時の1件から増やせない |
| 有効管理者 | 1名 | 初回セットアップの1名から増やせない |
| 自分で作れるグループ | 1件 | 初回セットアップの1件から増やせない |

`ORGANIZATION_SELF_CREATED_LIMIT`は`3`のまま残す。
この定数は`createOrganization`が閉じている間は評価されず、解除時にそのまま効く。
`ORGANIZATION_PLAN_LIMITS.business.maxActiveManagers`（5名）も同じ扱いで、閉じている間は評価されず、解除時にそのまま効く。

developに既に複数管理者のグループがある場合も、そのまま残す。
管理者を退任させるmigrationは作らない。

## 3. Security Lens

- **Actor**：認証済みの管理ユーザー本人と、発行済み招待tokenの持参者。
- **Asset**：`organizations`と`shops`の作成、Stripe Customer・Subscription・Checkout Sessionの発行、課金状態、`organizationInvitations`の発行と管理者の構成。
- **Trust boundary**：ブラウザとConvex backend。新しいHTTP routeとWebhookは追加しない。`/stripe/webhook`の署名検証と、招待tokenの署名・TTL検証は現状のまま維持する。
- **Abuse case**：画面に導線がないことを利用して、`createOrganization`、`addShop`、`organizationInvitation.mutations`の`create`系を直接呼ぶ。閉じる前に発行された招待を受諾して管理者を増やす。ダークローンチ中に作られたグループや店舗が、解除後の上限判定と食い違う。
- **Server-side enforcement**：公開フラグをサーバー側で評価し、`createOrganization`、`addShop`、招待の`create`、`createExternal`、`createForPerson`、`createForStaff`、`resend`を`ConvexError`で拒否する。`getPreview`、`linkAccount`、legacy `accept`は`unavailable`へ寄せ、新規enqueueと投入済みOutboxの配送も止める。clientから公開可否を受け取らない。`getSettings`と`managerInvitationState`が返す表示用の状態は、認可根拠にしない。
- **Rate limit / idempotency**：既存の`organizationCreateShort`と`organizationCreateDaily`、`requestId`由来のcorrelationIdをそのまま残す。拒否は上限判定とrate limitより前に行い、閉じている間にbudgetを消費させない。招待の拒否も、招待作成・通知enqueue・監査より前に置く。
- **Lifecycle / recovery**：m022は再実行しても同じ最終状態になる。Stripeの痕跡がある行はpatchせずconflictへ残す。閉じる前に発行された招待も受諾・再送・配送できないままTTLで失効し、招待ごとに予約されたinternal `expire`と`revoke`は残す。アプリ機能の解除は環境変数で行い、静的FAQは同じ公開変更で復元する。m022の逆migrationは作らない。
- **Logs / PII**：監査は既存の`recordOrganizationAuditEvent`だけを使う。拒否理由の文言に内部設定と環境変数名を含めない。
- **Regression test**：`createOrganization`、`addShop`、招待の発行・再送が拒否され、受諾が`unavailable`となり、DB、scheduler、監査、Outboxのいずれにも意図しない副作用がないことをConvex Function Testで固定する。招待を前提とする既存E2Eは閉状態で`test.skip`する。

## 4. サーバー設計

### 4.1 公開フラグ

`convex/_lib/config.ts`へ、公開状態を読む関数を追加する。
TypeScriptのトップレベル定数にすると、テストから値を差し替えられない。
この文書内の他の設定値と同じく、呼び出しのたびに`process.env`を読む関数にする。

```ts
export function isOrganizationCreationEnabled(): boolean {
  return (process.env.FEATURE_ORGANIZATION_CREATION ?? "").trim() === "enabled";
}
```

店舗追加、支払い、管理者招待も同じ形で`FEATURE_SHOP_ADDITION`、`FEATURE_BILLING`、`FEATURE_MANAGER_INVITATION`を読む。

四つに分けるのは、解除の順序が同じとは限らないためである。
店舗追加だけを先に開ける判断も、支払いだけを後回しにする判断もあり得る。

未設定を閉じた状態として扱う。
新しいpreview deploymentと、変数を設定し忘れた環境が、既定で閉じる側に倒れる。

`scripts/setupEnv.ts`の`CONVEX_ENV_KEYS`へ四つのキーを追加する。
四つのキーに限り、`.env`で未設定または空なら`disabled`をdeploymentへ同期する。
これにより、deployment側に過去の`enabled`が残っていても、`.env`の閉状態へ戻せる。
これにより、Convex deploymentとE2Eが同じ`.env`を正本にできる。
`playwright.config.ts`は既に`dotenv.config()`を呼んでいるため、E2Eからも同じ値を読める。

アプリ内の段階解放は`convex env set`で完結し、frontendの再デプロイは要らない。
画面側は`getSettings`または`getCurrentUser`の購読を通じて変化を受け取るため、frontendの再ビルドも要らない。
ただし公開FAQはdeployment flagを購読できない静的コンテンツなので、管理者招待・交代を開けるreleaseで操作手順を復元する。

### 4.1.1 `getSettings`のDTO

`api.organization.queries.getSettings`の返り値へ、この四つを反映したフラグを足す。
混在deployのWiden期間は`features`自体をoptionalにし、新しいfrontendはobjectまたはfieldが欠損した旧backendの応答を四機能すべてfalseへ正規化する。
既存の`canAddShop`、`canCreateOrganization`、`canInviteManager`は、上限に達した状態と未公開の状態を区別できない。
画面は「上限に達したので理由を出す」と「未公開なので何も出さない」を描き分ける必要があるため、可否とは別のフィールドで渡す。

```ts
features: v.object({
  organizationCreation: v.boolean(),
  shopAddition: v.boolean(),
  billing: v.boolean(),
  managerInvitation: v.boolean(),
}),
```

`canInviteManager`と`managerInvitationMode`の意味は変えない。
上限判定の意味を保ったまま、公開フラグを別のフィールドで重ねる。

### 4.1.2 `getCurrentUser`の表示DTO

認証後の全画面で使う入口判定は、店舗ごとのDTOへ同じ値を複製せず`getCurrentUser`へ載せる。
Widen期間は`featureVisibility`自体をoptionalにし、新しいfrontendはobjectまたはfieldが欠落した旧backendの応答をすべてfalseへ正規化する。

```ts
featureVisibility: {
  organizationSettingsNavigation: boolean,
  billing: boolean,
  shopMembershipAddition: boolean,
}
```

`organizationSettingsNavigation`は四つの公開フラグのORである。
`billing`と`shopMembershipAddition`は、それぞれ`FEATURE_BILLING`と`FEATURE_SHOP_ADDITION`が`enabled`のときだけtrueにする。
これは表示用の正のcapabilityであり、`/settings`の直URL認可には使わない。

### 4.2 グループ追加

`convex/setup/mutations.ts`の`createOrganization`の冒頭で拒否する。
`ctx.user`の確認より後、correlationIdの解決とrate limitより前に置く。
閉じている間に冪等record、rate limit budget、監査のいずれも消費させないためである。

`getOrganizationCreationAvailability`（`convex/setup/service.ts`）は変更しない。
上限判定の意味を保ったまま、公開フラグを別の層で重ねる。

`setupShopAndManager`は変更しない。
初回セットアップは今回の制限対象ではなく、`complimentary.business`で始まる挙動も維持する。

### 4.3 店舗追加

`convex/organization/mutations.ts`の`addShop`で、`requireOrganizationActorForShop`の直後に拒否を入れる。
actorの解決より前に拒否すると、所属していない利用者へ機能の有無を返してしまう。
既存の`requireOrganizationPaidFeature`と`requireOrganizationCapacity`は残す。

`archiveShop`と`reactivateShop`は変更しない。
1店舗しか持たないグループが唯一の店舗をarchiveできるかは既存の挙動であり、この計画で新しく変えない。

### 4.4 支払い

`convex/organizationStripe/actions.ts`のpublic actionは個別に閉じない。
全グループが`complimentary.business`になれば、既存のStripe隔離契約が拒否側に回るためである。
新しい拒否を重ねると、解除時に外す箇所が増える。

画面から「プランと支払い」タブを外すことで、これらのactionへ到達する導線がなくなる。
`getSettings`が返す`features.billing`は、その描画判定に使う。

### 4.5 管理者招待と交代

`convex/organizationInvitation/mutations.ts`の`create`、`createExternal`、`createForPerson`、`createForStaff`で、`requireOrganizationActorForShop`の直後に拒否を入れる。
actorの解決より前に拒否すると、所属していない利用者へ機能の有無を返してしまう（4.3と同じ理由）。
招待の作成、通知のenqueue、監査より前に置く。
四つすべてを閉じることで、追加招待もFree管理者交代の招待も発行できなくなり、交代は入口ごと閉じる。

`resend`も同じ公開フラグで拒否する。
再送は単なる通知再試行ではなく、旧tokenを失効させて新しい招待とTTLを発行するため、開けたままではダークローンチを迂回できる。

`linkAccount`とlegacy `accept`が共有する`linkAccountWithToken`の先頭で、閉状態を`{ status: "unavailable" }`へ寄せる。
token長の検査、digest、rate limit、人物・所属更新より前に返し、閉じている間のbudgetとDB状態を変えない。
`getPreview`もtoken digestを計算する前に`unavailable`を返し、発行済みtokenからグループ名や期限を表示しない。
`/manager-invite`のrouteは残し、既存の利用不可表示を使う。

新規通知は`getEnqueueData`で`null`を返してOutboxへ積まない。
フラグを閉じる前に既に積まれたメール・LINE招待は、`notificationOutbox`のprovider呼出直前の適格性確認で`invitation_inactive`として取消し、外部送信を開始しない。
受諾直後にフラグが閉じられた場合も、`getAcceptanceNotificationData`は`null`を返して管理者連携完了メールを新たに積まない。
既にOutboxへ積まれた`organizationInvitation.linked`メールもprovider呼出前に取消す。

`revoke`とinternal `expire`は変更しない。
どちらも残存招待を減らす整理経路であり、管理者を増やさない。

`resolvePersonManagerInvitationState`（`convex/organization/managerInvitationState.ts`）の冒頭で公開フラグを読み、閉じている間は新しい`{ kind: "hidden" }`を返す。
既存の`unavailable`を流用しないのは、`unavailable`が理由テキストの表示を前提とした状態であり、ダークローンチでは機能の存在自体を見せないためである。
`managerInvitationStateValidator`へ`hidden`を追加し、この状態を購読する`UserDetail`とスタッフ管理の画面が、そのまま非表示判定に使えるようにする。
`useUserManagerActions`と`useStaffManagerInvitation`の`kind !== "unavailable"`による実行可否判定は、`available`と`pending`だけを実行可能とする判定へ改める。
`hidden`が実行可能側に倒れることを防ぐためである。

`removeManagerRole`は変更しない。
「最後の有効管理者の管理者権限は外せません」の既存ガードにより、管理者1名のグループでは状態を変えられない。
UI側は、`managerInvitationState`が`hidden`のとき`UserDetail`の管理者権限セクションごと描画しないため、解除の導線も同時に消える。

## 5. データ移行

### 5.1 変更前後のshape

schemaは変更しない。
`organizationBillingStates.state`は既存unionの`{ kind: "complimentary", plan: "business" }`にそのまま収まるため、widenとnarrowの期間を設けない。

| 対象 | 変更前 | 変更後 |
|---|---|---|
| `organizationBillingStates.state` | 任意の課金状態 | `{ kind: "complimentary", plan: "business" }` |
| `organizationBillingStates.version` | 現在値 | 現在値 + 1 |
| `organizationBillingStates.freeManagerPersonId` / `freeShopId` | 設定されている場合がある | 削除する |

`freeManagerPersonId`と`freeShopId`はFree選択の結果を保持するfieldであり、支払い不要Businessでは意味を持たない。
残すと、解除後にFreeへ戻した際に古い選択が復活する。

### 5.2 migrationの単位と再実行性

`convex/migrations/m022_organization_billing_to_complimentary_business.ts`を追加し、`migrations.define`の`migrateOne`で`organizationBillingStates`を1行ずつ処理する。
`convex/migrations/index.ts`のrunner配列末尾へ追加する（連番の欠番を作らない）。
限定実行とdry run用に`runM022`を用意する。

既に`complimentary.business`の行は何もせずreturnする。
これにより再実行しても最終状態が変わらない。

`.collect()`は使わない。
グループ単位の確認は`by_organizationId`のindexで`take`する。

### 5.3 fail-closedの条件

m021は8種類のconflictでStripeの痕跡を分類している。
m022では同じ細かさを持たせない。

`origin/main`の履歴は設計時の参考情報にはなるが、現在のProduction artifact、Convex deployment、migration完了状態を証明しない。
[リリース状態](../manual/release-status.md)に証跡がないため、Productionとdevelopのいずれについても、Stripe関連行やm009からm021の実行有無を0件・未実行と推定しない。

m022を実行する前に、対象を完全修飾deployment名で固定し、export snapshotとmigration statusを取得する。
課金状態、Stripe Customer、Subscription、operation、Webhook証跡、課金通知の件数を確認し、「移行で失う状態がない」という前提を証跡で満たせない場合はm022を実行しない。
その場合は、保持・conflict化する対象を再設計し、forward migrationとして扱う。

conflictに落とす条件は次の三つとする。

- グループが存在しない。
- 同じグループの課金状態が一意でない。
- Stripe CustomerまたはSubscriptionがある。

operation、Webhook証跡、課金通知は個別に見ない。
CustomerもSubscriptionも無い行にそれらだけが存在する状態は、develop環境でも想定しない。

conflictの記録は既存の`recordOrganizationMigrationConflict`を使う。
監査のcorrelationIdは`${organizationId}:migration:m022:to-complimentary-business`とする。

### 5.4 完了条件とrollback

完了条件は次の三つを別々に確認する。

1. `organizationBillingStates`のうち`complimentary.business`以外が0件である。
2. m022のconflictが0件である。
3. `pnpm convex:migrate:status`でm022が`done`である。

逆migrationは作らない。
元の状態がtrialだったのかfreeだったのかを復元する情報は残らないためである。
その情報を持つ行が存在しないことを、対象deploymentの実行前snapshotで確認できた場合だけ、この判断を適用する。
実行前にexport snapshotを取り、前提が崩れていた場合はforward repairをm023以降で設計する。

## 10. 段階解放

グループ追加、店舗追加、支払いは四段階で開ける。
グループ追加は支払いより後に置く。
管理者招待・交代にはこの三機能との依存関係がないため、承認したタイミングで独立して開ける。
明示的に開けるまでは未設定のまま維持する。

現行のrelease workflowはConvex、Pagesの順でdeployする。
そのため、初回反映ではConvexの拒否が先に有効になり、Pagesのdeploy完了までの間だけ旧frontendの導線が残り得る。
反映完了の判定はPagesのdeploy後に行う。導線が一瞬も見えないことが必要な場合は、欠損フラグを全閉にするfrontend互換releaseを先行し、次のreleaseでbackendの拒否を入れる。

| 段階 | 開ける対象 | 設定 |
|---|---|---|
| 1 | なし（全制限） | 四つとも未設定 |
| 2 | 店舗追加 | `FEATURE_SHOP_ADDITION=enabled` |
| 3 | 支払い | `FEATURE_BILLING=enabled` |
| 4 | グループ追加 | `FEATURE_ORGANIZATION_CREATION=enabled` |
| 独立 | 管理者招待・交代 | `FEATURE_MANAGER_INVITATION=enabled` |

### 10.1 段階2で店舗追加を開ける

`convex env set`で値を入れ、UIの未公開分岐を戻すだけで足りる。

全グループが`complimentary.business`であり、`canUsePaidFeatures`はtrue、`maxActiveShops`は5である。
支払いが閉じたままでも、店舗追加の判定は既存の経路をそのまま通る。
段階2での実効上限は5店舗になる。

### 10.2 段階3で支払いを開ける

1. Stripeの外部設定と実環境証跡を[リリース状態](../manual/release-status.md)へ登録する。
2. `FEATURE_BILLING`を設定し、「プランと支払い」タブの描画分岐を戻す。

既存グループの課金状態は`complimentary.business`のまま残す。
通常プランへ移す判断が必要になった場合は、別のmigrationとして設計する。
この計画には含めない。

### 10.3 段階4でグループ追加を開ける

グループ追加を支払いより後に置くのは、二つ目以降が`active.free`（利用人数5名、稼働店舗1件、有効管理者1名）で始まる設計だからである。
支払いが閉じている間にグループ追加を開けると、利用者は二つ目のグループを作れるものの、そこから上げる手段がない状態で固定される。
一つ目のグループが40名と複数店舗で動いているのに、二つ目が5名1店舗になる。

段階3を先に済ませておけば、`createOrganization`と`createOrganizationWithFirstShop`に手を入れずに開けられる。
Free開始のまま、有料プランへの導線が既に存在する状態になるためである。

段階3と段階4を同じタイミングで開けてもよい。
順序を逆にできないという制約だけがある。

### 10.4 管理者招待・交代を開ける

管理者招待・交代は、店舗追加、支払い、グループ追加のどの段階でも独立して開けられる。
`FEATURE_MANAGER_INVITATION=enabled`を設定すると、既存の`canInviteManager`、`managerInvitationMode`、プラン上限、招待tokenの検証をそのまま使って導線を再表示する。
同じ公開releaseで、静的FAQの管理者追加・交代の操作手順と、利用不可中の文言を公開状態へ戻す。

解放前に、管理者追加とFree管理者交代の両方について、招待作成、メール受信、受諾、権限反映、取消、再送を対象環境で確認する。
コードだけ先に入れる場合は、対象deploymentでこの環境変数を未設定にして閉状態を維持する。

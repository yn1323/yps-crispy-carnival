# 人数が多い店舗のシフト作成 実装計画

> 状態: リポジトリ実装済み（2026-11-16に範囲を広げて整理し直し、同日に承認。実装中に変えた点は「実装中に変えた判断」を参照）
>
> 作成日: 2026-11-16
>
> 方針: [人数が多い店舗のシフト作成方針](2026-11-14_人数が多い店舗のシフト作成_方針.md)

方針で「必要」とした13要素を実装する。  
あわせて、設定の入力を減らすAIサポートを、実際のAIにつながない仮の処理で作る。

## 目的と前提

### 誰がどの場面で困っているか

スタッフ11人以上の店舗のシフト担当者が対象である。  
人数が増えると、店が必要とする枠と人の条件を覚えきれなくなる。  
現行のシフトリは希望と勤務時間しか持たないため、担当者は別の表へ写してシフトを組んでいる。

### どうなれば完成か

シフト担当者がポジション、必要人数、休憩、人の条件をシフトリに持たせ、過不足を確かめながらシフト表の上で組み終えられる。  
組んだシフトは、ポジションと休憩が載った紙として出力できる。  
何も設定していない店舗のシフト表は、今と同じ見え方のままである。

### すでに決まっていること

2026-11-16に、次の内容をユーザーと決めた。

| 項目 | 決めた内容 |
|---|---|
| 範囲 | 方針の「必要」13要素すべて。「あるとよい」の働く量の目安と中抜けは含めない |
| 日の型 | 1日分の「時間帯の区切り＋必要人数」のセットを型として持つ。曜日に型を割り当て、特別な日は日付に別の型を当てる |
| 必要人数の粒度 | ポジション別 |
| 休憩 | 開始と終了の時刻で持つ。時間指定、パターン選択、日付選択のどれでも指定できる |
| 未提出者の仮の勤務 | 直近に確定した募集の同じ曜日の勤務を引き継ぐ（方針の未決事項1を決定） |
| AIサポート | 実際のAIにつながない。AIサポートの画面を作り、仮の処理が日の型をランダムな値で埋める |
| シフト表の表示 | 「シンプル / くわしく」の2段で切り替える。シンプルは今の画面と同じにする |
| 設定の場所 | 店舗ごとの専用ページ「シフト作成の設定」を新設する |
| 日の型の編集 | 時間帯×ポジションの表で、人数を−／＋で増減する |
| スタッフの設定 | 設定ページの一覧でまとめて編集する |
| PCとスマートフォン | レイアウトは分けてよい。できることは同じにする |
| 募集方式 | 時間指定、日付選択、パターン選択のそれぞれに合わせた形で適用する |
| PDF・Excel出力 | ポジションと休憩を出力へ反映する |
| テスト | core E2Eの契約を1件足す。ほかの既存テストは通る状態を保つ |

### 業務上の決まり

- スタッフ10人以下の店舗の流れは変えない。  このため、仮の勤務は自動で入れず、担当者が操作したときだけ入れる。
- 労務の領域には入らない。  休憩の基準をシフトリから示さず、合計時間は表示にとどめ、超過の判定をしない。
- 必要人数、過不足、合計時間は、シフト対象のスタッフだけを対象にする。
- 設定は既存の店舗設定と同じく、対象店舗が属する組織の有効な管理者だけが変更できる。

## 設計の要点

### 募集方式ごとの形

| 要素 | 時間指定 | パターン選択 | 日付選択 |
|---|---|---|---|
| 勤務のポジション | 勤務区間ごとに1つ | スタッフ×勤務パターンごとに1つ | スタッフ×日付ごとに1つ |
| 日の型の区切り | 時間帯（開始・終了） | 勤務パターン | 終日の1区分 |
| 人数と過不足 | 時間帯ごと | 勤務パターンごと | 1日ごと |
| 休憩 | 勤務の時間内で時刻を指定する | 勤務パターンの時間内で時刻を指定する | 勤務の時刻がないため、1日のどの時刻でも指定できる |
| 休憩中の人の数え方 | 休憩と重なる時間帯の人数から外す | 人数から外さない | 人数から外さない |
| 人ごとの合計 | 時間（休憩を引く） | 時間（休憩を引く） | 出勤日数 |

時間指定で必要人数が未設定の場合は、1時間ごとの人数だけを出す。  
パターン選択と日付選択の人数は、パターンまたは1日の単位で数えるため、休憩で人数を変えない。

### 保存するデータ

既存のdocumentを書き換えない形で足す。  
backfillとmigrationは不要である。

| 対象 | 変更 |
|---|---|
| `positions`（既存） | 形は変えない。追加・名前と色の変更・並び替え・論理削除のAPIを足す |
| `staffs` | `unavailablePositionIds`（入れないポジション）と`skillLevel`（`newcomer` / `lead`）をoptionalで足す。省略は「全ポジション可」「標準」を表す |
| `shops` | `breakRule`（何分以上の勤務に何分）をoptionalで足す。省略は「決まりなし」を表す |
| `shiftDayTemplates`（新規） | 店舗の日の型。名前、割り当てた曜日、区切りと必要人数を持つ |
| `shiftDayTemplateOverrides`（新規） | 特別な日。店舗、日付、当てる型を持つ |
| `shiftAssignments` | `breaks`（開始・終了の配列）と`isProvisional`（仮の勤務）をoptionalで足す |

上限は`convex/constants.ts`に定数で置く。  
有効なポジションは10件、日の型は6件、型の中の区切りは8件、勤務1件の休憩は3件までとする。

### AIサポートの作り

- 設定ページに「AIで下書きを作る」を置く。  担当者が店の状況を文章で入力すると、日の型の下書きが編集中の表に入る。
- 下書きを返すactionは、入力された文章を読まない。  店舗の提出方法とポジションから区切りを作り、各マスの必要人数をランダムな値で埋める。
- 下書きは編集中の表に入るだけで、担当者が「保存する」を押すまで設定は変わらない。
- 生成の処理は1つの関数にまとめ、あとから実際のAIの呼び出しへ差し替えられる形にする。
- ランダムな値を「AIの提案」として本番の店舗に見せると、根拠のない人数を信じさせてしまう。  このため、環境変数で有効にした環境だけにAIサポートを出す。  本番では有効にしない。  本番でも出す場合は、承認のときに指示してほしい。

### 自分で決めた設計判断

承認のときに、違う場合は指摘してほしい。

1. 削除したポジションを参照する勤務は、シフト表では既定のポジションとして表示する。  既定のポジションは削除できない。
2. ポジションの色は用意した色の中から選ぶ。  自由な色指定は作らない。
3. 仮の勤務はシフト表の「前回の勤務を仮で入れる」を押したときだけ入る。  勤務のない未提出者の日にだけ入れ、「仮」の印を付ける。
4. 仮の勤務を入れたあとでスタッフが提出した場合、そのスタッフの仮の勤務は表示から外し、希望を勤務の候補として出す。  確定のときにも提出済みスタッフの仮の勤務をサーバー側で取り除く。
5. 休憩は勤務を作るときに自動では入らない。  店舗が休憩の決まりを設定している場合だけ、決まりの時間以上の勤務に、決まりの長さの休憩を勤務の中央へ初期値として入れる。  担当者は動かすことも消すこともできる。  日付選択には勤務の長さがないため、初期値を入れない。
6. 今の画面が「休憩」として斜線で示している勤務と勤務の隙間は、今の表示のまま残す。  時刻で入れた休憩は勤務のバーの内側に示す。
7. 既存の週の「計」は最初の開始から最後の終了までの幅を出している。  これを、勤務時間の合計から休憩を引いた値へ直す。
8. スタッフが入れないポジションへ割り当てた場合は、保存を止めず、既存の「確認事項」に理由を足す。
9. 2つ以上のポジションを持つ店舗では、スタッフ向けの確定シフト表示と確定通知の本文にポジション名を出す。  休憩の時刻も出す。  今はポジションだけを変えても再通知が届くが、本文に違いが出ないためである。
10. 表示の切り替えは端末に覚える。  ポジションが1つで必要人数も未設定の店舗では、初期状態をシンプルにする。
11. 設定の変更に監査ログとrate limitは付けない。  既存の店舗設定の更新に合わせる。  AIサポートのactionにはrate limitを付ける。
12. AIサポートが出ない環境では、日の型を手で作る。  最初の型には店舗の提出方法から区切りを初期値として入れる（時間指定は受付時間を1つの時間帯、パターン選択は各勤務パターン、日付選択は終日）。
13. 出力ページに「ポジションと休憩も出力する」を足す。  ポジションが2つ以上あるか、休憩のある勤務が1件以上ある場合だけ表示する。  初期状態は、シフト表を「くわしく」で開いていたときはオン、「シンプル」のときはオフにする。  オフの出力は今と同じ内容になる。

### Security Lens

- Actor: 対象店舗が属する組織の有効な管理者。  スタッフ用sessionと匿名は対象外である。
- Asset: 店舗の設定（ポジション、日の型、休憩の決まり）、スタッフの属性（入れないポジション、熟練度）、勤務の割当。
- Trust boundary: ブラウザとConvexのpublic function。  新しいHTTP routeとcapabilityは作らない。
- Abuse case: 別店舗・別組織の`positionId`、`staffId`、`templateId`を渡して読み書きする。  上限を超える件数や長い文字列を送る。  無効な環境でAIサポートのactionを直接呼ぶ。  AIサポートを連打する。
- Server-side enforcement: `managerQuery`と`managerMutation`を使う。  受け取ったIDは取得後に同じ店舗・非削除を確かめ、違えば`Not found`に寄せる。  件数、文字数、時刻、曜日の重複をサーバーで検証する。  actionはinternal queryで店舗への権限を確かめ、環境変数が無効なら`unavailable`を返す。
- Rate limit / idempotency: 設定の保存は全置換で、同じ入力を繰り返しても同じ状態になる。  AIサポートのactionにはrate limitを付ける。
- Lifecycle / recovery: 店舗の論理削除で設定へは到達できなくなる。  既存の`positions`と同じ扱いにする。  所属を外したスタッフの属性は`staffs`とともに残る。
- Logs / PII: AIサポートへ入力した文章は保存せず、ログにも出さない。  熟練度は店舗内の評価にあたるため、管理者向けのqueryだけが返し、スタッフ向けのqueryと出力は含めない。
- Regression test: 各public functionのFunction Testで、未認証、別組織、別店舗のID、削除済み、上限超過を拒否し、拒否時にDBが変わらないことを確かめる。
- E2E: 新しいtesting helperとcapabilityは作らない。  開始状態は既存のseedで作る。

## 実装中に変えた判断

実装で分かった事実に合わせて、次の点を計画から変えた。

1. 日付選択の休憩は、時刻として正しければ受け付ける。  日付選択には受付時間がなく、割当に保存される09:00〜22:00は置き場所としての値だったためである。
2. 確定通知の休憩は、ポジションの数にかかわらず出す。  休憩だけを変えた再通知で、本文に違いが出るようにするためである。  ポジション名は2つ以上の店舗だけに出す。
3. 契約IDは`E2E-STAFFING-01`にした。  結果を検査するscriptが、`E2E-`のあとに1語だけを持つIDを前提にしているためである。
4. スマートフォンの「シンプル / くわしく」の切り替えは、日付見出しの「表示設定」メニューに置いた。  ヘッダーの幅に2段の切り替えが収まらないためである。  PCはヘッダーに置く。
5. スマートフォンの編集シートは、シンプル表示でも「勤務時間を追加」から2件目の勤務を足せるようにした。  PCはシンプル表示でも2件目を塗れるためである。
6. ポジションの色は、白い文字が読める濃さの10色にした。  最初からあるポジションの色（`#3b82f6`）は、保存済みのデータに合わせて残した。
7. 既定のポジションも、ほかのポジションと同じく保存した並び順で返す。  設定ページは、既定のポジションの並び替えを出していない。
8. 設定ページのWeb計測は、店舗詳細と同じ分類（`shop_detail`）と同じ集計用のpathで数える。  新しい計測の値を足さないためである。
9. 入れるものの選択には、ポジションに加えて「休憩」を置いた。  休憩を選んで勤務を押すと休憩の編集が開く操作を、3方式とPC・スマートフォンでそろえるためである。
10. 既定のポジションをまだ持たない店舗で保存した場合は、既定を作って先頭に残す。  入力の色が既定と重なるときは、使っていない色へ置き換える。
11. 休憩の決まりによる初期値は、「くわしく」表示のときだけ入れる。  シンプル表示は休憩を見せないため、見えない休憩が保存されて通知に載ることを避ける。
12. 表示の初期状態は、ポジションが2つ以上、型、休憩の決まり、スタッフの属性のどれかがある店舗を「くわしく」にする。  設計判断10の「ポジションが1つで必要人数も未設定ならシンプル」より広い。  休憩の決まりやスタッフの属性だけを設定した店舗でも、設定した内容が見えるようにするためである。
13. 画面を開いている間に提出したスタッフの仮の勤務は、保存のときにサーバー側で落とす。  開いたままの画面から保存・確定しても、提出済みスタッフの仮の勤務が確定に残らないようにするためである。
14. PDF・Excel出力の休憩は、「休憩」、開始、終了の3行で出す。  31日分を並べた列の幅では、1行にまとめると末尾が省略されるためである。
15. 入れないポジションへの割当は、確認事項の一覧に「入れないポジションにシフトを設定」として出す。
16. スタッフ向けの確定シフト表示には、ポジションの色と名前の対応を凡例で出す。  編集用の「入れるもの」が出ない画面では、色だけでポジションを読み分けられないためである。
17. 人ごとの合計は、管理者の画面だけに出す。  スタッフ向けの表示へ出すと、ほかのスタッフの勤務時間の合計が全員に見えるためである。
18. 休憩を選んでいる間に勤務のバーを押したときは、休憩の編集だけを開く。  勤務の欄を同時に開くと、2つの入力が重なるためである。
19. 人数と過不足には、削除済みのスタッフに残った勤務を数えない。  いない人の勤務で、不足が隠れるためである。
20. ポジションの削除で、残ったポジションのすべてが「入れない」になったスタッフは、全ポジションに入れるものとして読む。  どこにも入れないスタッフを作らないためである。

## 実装の順序

依存関係に従って、次の順で進める。

1. Convex: schemaの追加、`convex/shiftSetup/`の設定API、割当の休憩と仮の勤務、仮の勤務のquery、AIサポートのaction、通知の文面。
2. 純粋処理（`src/domains/shift/`と`src/domains/shop/`）: 集計、休憩の操作、日の型の解決、仮の勤務の差し込み、確認事項。
3. 設定ページ: route、ページ、ポジション、日の型、休憩の決まり、スタッフの一覧、AIサポート。
4. シフト表: 表示の切り替え、ポジションの選択と色、休憩、人数と過不足、合計、印、仮の勤務、スマートフォンの編集シート、特別な日。
5. スタッフ向けの表示と、PDF・Excel出力。
6. core E2E。
7. 追従: `doc/features/`（シフト表、店舗設定、新規の「シフト作成の設定」）、`doc/specs/full-regression-contracts.md`の契約行とsurface表、`convex/developmentSeed/`のテーブル一覧、`convex/testing.ts`の店舗単位の削除。

## 検証

- 完成条件ごとの対象テストを先に実行し、そのあとで`pnpm lint`、`pnpm type-check`、`pnpm test`、`pnpm build`を実行する。
- E2Eは`E2E-STAFFING-01`を`--retries=0 --workers=1`で実行し、成功したら`pnpm e2e:burn-in`を実行する。  サーバーはユーザーが起動しているものを使い、新しく起動しない。
- ローカルでブラウザやサーバーに届かずE2Eを実行できない場合は、コードの失敗と分けて、未実行として報告する。
- 見た目を変えた箇所は`.claude/rules/stories.md`に従って目視で確かめる。  VRTはCIに任せる。

# スタッフのメールアドレス任意化 設計・問題点整理

**ステータス: 設計検討（実装未着手）**

スタッフ登録時のメールアドレスを必須→任意にするための影響範囲調査・設計方針・問題点の整理。
メールアドレスを持たない／教えたくないスタッフ（LINEのみで連絡を取りたい層）を登録できるようにすることが目的。

対象は**スタッフ（`staffs`）のメールアドレスのみ**。管理ユーザー（`users.email`）はClerk認証由来のため必須のまま変更しない。

---

## 1. 現状整理

### 1.1 DBスキーマ（`convex/schema.ts`）

| テーブル | フィールド | 現状 |
|---|---|---|
| `staffs` | `email: v.string()` | 必須。空文字を許容しない前提のバリデーションが上流にある |
| `staffs` | `emailNormalized: v.optional(v.string())` | 小文字化・trim済み。過去データ互換のためoptional |
| `staffs` | index | `by_shopId_email_isDeleted` / `by_shopId_emailNormalized_isDeleted` / `by_email` / `by_emailNormalized` |
| `staffRegistrationRequests` | `email: v.string()` / `emailNormalized: v.string()` | QR参加申請。**両方とも必須**。`by_shopId_emailNormalized_status` で重複申請を排除 |
| `users` | `email: v.string()` | Clerk由来。**変更対象外** |

### 1.2 メールアドレスが担っている役割

メールアドレスは単なる連絡先ではなく、**4つの役割**を兼ねている。任意化の影響が広いのはこのため。

1. **通知チャネル**: シフト募集・確定・催促・再発行・法務同意・LINE連携依頼の配送先
2. **スタッフの同一性キー**: 追加時・QR申請時の重複検出（`findActiveStaffByEmail`）、申請承認時の既存スタッフ突合
3. **本人確認キー**: シフト閲覧リンク再発行（`staffAuth`）でスタッフ自身がメールを入力して本人性を示す
4. **LINEフォールバック**: LINE送信失敗・Quota超過時の `fallbackEmail`（通知outbox）

### 1.3 すでに空メールを考慮している箇所（下地あり）

バックエンドの通知系は防御的に書かれており、部分的に空メール耐性がある。

- `convex/staff/mutations.ts:24` — `canSend = staff.email.length > 0 || LINE連携済み`（個別再送のガード）
- `convex/notification/actions.ts:60` — `if (selectedChannel === "email" && !staffData.email) continue;`
- `convex/legal/actions.ts:17` — `if (!data?.staffEmail) return;` + `fallbackEmail` はoptional組み立て
- `convex/_lib/validation.ts:46` — `optionalEmail` refinement（空文字は素通し、入力ありなら形式チェック）が既に存在

## 2. 設計方針（案）

### 2.1 DB表現: 「空文字 `""`」方式を推奨

| 方式 | 内容 | 評価 |
|---|---|---|
| **A. 空文字方式（推奨）** | `email: v.string()` のまま、`""` = 未登録とする | スキーマ変更・マイグレーション不要。既存の `staff.email.length > 0` 判定と整合。Widen→Migrate→Narrow が丸ごと不要 |
| B. optional方式 | `email: v.optional(v.string())` に変更 | 「未登録」の意味論は綺麗だが、既存全ドキュメントとの互換確認、`staff.email` 参照箇所全て（テンプレート、outbox、テスト）に `undefined` 分岐が波及。得られるメリットが小さい |

**推奨A**。ただし空文字方式には index の罠がある（§3.6）ため、**メール空のときは email 系 index を絶対に引かない**ガードをヘルパーに集約する。

- `emailNormalized` も同様に `""` を格納（`normalizeEmail("")` は `""` を返すので現行実装と整合）。

### 2.2 バリデーション

- `convex/_lib/validation.ts` に `optionalEmailSchema` を追加（既存の `optionalEmail` refinement を schema 化して再利用）。
  - 空文字 or 空白のみ → OK（`""` に正規化）
  - 入力あり → 形式・最大長・制御文字チェック（`requiredEmailSchema` と同一ルール）
- `convex/staff/schemas.ts`
  - `requiredStaffEntrySchema.email` → `optionalEmailSchema`
  - `staffEntrySchema` の空行判定（`name === "" && email === ""`）は維持。**「メールだけ入力・名前なし」はエラー、「名前だけ・メールなし」は有効行になる**よう superRefine を調整
  - `editStaffSchema` も同様
- フォーム側（`AddStaffForm` / `EditStaffForm` / `SetupStep2`）: ラベルを「メールアドレス（任意）」に変更。Submitボタン常時Enabled方針（CLAUDE.md）は変更なし。

### 2.3 重複検出

- **メールありスタッフ同士**: 現行どおり `emailNormalized` で重複拒否。
- **メール空のスタッフ**: 重複チェックを**スキップ**（同名スタッフの登録を許容する）。
  - `addStaffs` の入力内重複チェック（`inputEmails` Set）は `""` 同士が衝突するため、**空文字は Set に入れない**修正が必須。
  - `findActiveStaffByEmail` は先頭で `if (emailNormalized === "") return null;` の早期returnを入れる（§3.6の index 誤ヒット防止と兼用）。
- 同名重複の誤登録リスクはUI側で緩和（追加確認時に「同じ名前のスタッフがいます」警告を出す等。任意）。

### 2.4 通知チャネル

`selectChannel`（`convex/_lib/notification.ts`）のロジック自体は変更不要。変わるのは「emailに振り分けられたが宛先がない」ケースの扱い。

- **原則**: `email === ""` かつ LINE 未連携のスタッフは「**通知手段なし**」状態。各通知 action で enqueue をスキップ（既にその実装が多いが、全 action で網羅する）。
- **fallbackEmail**: LINE送信時にメールが空なら `fallbackEmail` を付けない（`legal/actions.ts` に同パターン既存）。Quota超過・LINE失敗時は通知不達 → 既存の通知不達Inbox（`notification-failure-dashboard`）に載せて担当者に見せる…かどうかは要検討（§3.5）。
- スキップした事実は `logSuppressedNotification` 相当のログに残し、サイレント喪失を防ぐ。

### 2.5 LINE連携導線（メールなしスタッフの紐付け）

現状のLINE連携開始手段は2つ:

1. 連携依頼**メール**（`internal.line.actions.sendInviteEmail`）→ メールなしでは使えない
2. 担当者が **QR/URLを直接見せる**（`LineLinkQrDialog`、StaffRowメニュー「LINE連携リンクを表示」）→ メール不要。`lineLinkTokens` は staffId 単位発行なのでスタッフレコード作成後なら使える

**方針**: メールなしスタッフは **(2) の対面QR連携を正規ルート**とする。

- スタッフ追加時に自動スケジュールしている `sendInviteEmail` / `sendOpenRecruitmentNotificationEmailsForStaff` は、メール空なら**スキップ**。
- 代わりに、追加完了UI（`staffAdditionCopy` / Dashboard通知）で「メール未登録のスタッフにはLINE連携QRを見せてください」と明示し、**追加直後にQRダイアログへ直行できる導線**を付ける。
- LINE連携完了（`finalizeLinking` / follow webhook）時に募集中シフトの提出リンクをLINEで送る既存フローは、メールなしスタッフでもそのまま機能する（ここが救済路になる）。
- 発展案（スコープ外・将来検討）: 店舗単位QRからスタッフ本人が自分の名前を選んで連携する方式。対面の手間は減るが**なりすまし（他人の名前を選ぶ）リスク**があるため、承認ステップなしでは導入しない。

### 2.6 法務同意

- 手入力追加スタッフへの同意依頼は現在メールで送信（`legal.sendStaffConsentEmail`、LINE連携済みならLINE）。
- メールなし＆LINE未連携 → **同意依頼を送る手段がない**。
- **方針**: LINE連携完了時に同意依頼をLINEで送る既存フック（follow時の同意依頼スケジュール）に乗せる。つまり「メールなしスタッフの同意はLINE連携後に取得」となり、**LINE連携までは同意未取得のまま**になる点を仕様として許容するか要判断（§4）。
- QR自己登録（`staffRegistration`）は申請時に同意を取るため影響なし（ただし§2.8参照）。

### 2.7 シフト閲覧リンク再発行（`staffAuth`）

- `ReissueForm` はスタッフがメールを入力して本人確認する仕組み。メールなしスタッフは**利用不可**（変更しても代替の本人確認手段がない）。
- **方針**: 機能自体は変更しない。再発行画面の案内文に「メールアドレスを登録していない場合はシフト担当者に連絡してください」を追記。担当者側はStaffRowメニューの「募集通知を再送」「確定シフト通知を再送」（LINE連携済みならLINEで届く）で救済。
- `reissueSchema` は `requiredEmailSchema` のまま（空入力での照会を許すと `emailNormalized=""` のスタッフに誤ヒットする事故を防ぐ意味でも必須のまま）。

### 2.8 QR自己登録（`staffRegistration`）もメール任意化する

QR参加申請でメールを任意にすると、素朴にやれば以下が壊れる:

- `staffRegistrationRequests.emailNormalized` と `by_shopId_emailNormalized_status` による**pending重複申請の排除**
- 承認時の**既存スタッフ突合**（`findActiveStaffByEmail`）
- いたずら申請の抑止力（メール入力が一定のハードルになっている）

**方針**: 登録ページで**LINE連携（LINE Login）を同時に済ませられるようにし、「メール or LINE連携のどちらか必須」とする**。メールの3つの役割（通知チャネル・同一性キー・申請ハードル）を `lineUserId` がそのまま代替できるため、上記3点が同時に解決する。詳細設計は§6。

なお `staffRegistrationRequests.email` / `emailNormalized` は `v.string()` のまま `""` を格納すればよいため、**この任意化にスキーマ移行（Widen→Migrate→Narrow）は不要**。追加フィールド（`lineUserId` 等）はすべて `v.optional` の追加のみで済む。

### 2.9 メール変更検知（`editStaff`）

`editStaff` の `emailChanged` 分岐（変更後メールへ募集提出リンクを追送）に空文字遷移のケースが増える:

| 遷移 | 挙動 |
|---|---|
| あり → 別のあり | 現行どおり追送 |
| **なし("") → あり** | `emailChanged = true` になる。新規登録と同等なので、提出リンク追送に加えて**LINE連携依頼メールも送る**のが自然（現行の追加時フローに揃える） |
| **あり → なし("")** | `emailChanged = true` だが宛先がないので**追送しない**（送信側の空ガードで自然にスキップされることを確認・テストする） |

## 3. 問題点・リスク一覧

### 3.1 【最重要】通知手段ゼロのスタッフが構造的に発生する

メールなし＆LINE未連携のスタッフには、**シフト募集・確定・催促・提出用マジックリンクが一切届かない = シフト提出が物理的に不可能**。

- 現状、担当者が提出リンクを直接コピーしてスタッフに渡す機能は**存在しない**（StaffRowメニューは再送のみで、宛先チャネルが必要）。
- 対策（いずれか、または組み合わせ）:
  - (a) スタッフ一覧に「通知手段なし」バッジを表示し、LINE連携QR導線を強調（最低限これは必須）
  - (b) 追加フローで「メール未登録ならその場でLINE連携QRを見せる」ことを前提にしたUI（推奨）
  - (c) 提出リンクを担当者が手動コピーして任意の手段で渡せる機能の新設（マジックリンクが担当者の手を経由するためセキュリティ上の検討が必要。トークンはワンタイム・72h期限であることに注意）
- **推奨**: (a)+(b)。(c)は本設計のスコープ外とし、必要になったら別途設計。

### 3.2 重複スタッフを機械的に検出できなくなる

メール空のスタッフは同一性キーがないため、同一人物の二重登録を防げない。名前は同姓同名がありうるためキーにできない。運用上は「担当者が一覧を見て気づく」に頼ることになる。UI警告（同名検知）で緩和はできるが根絶はできない。**許容するリスクとして明記しておく**。

### 3.3 法務同意が「LINE連携するまで未取得」になる

手入力＆メールなしのスタッフは、LINE連携完了まで利用規約・プライバシーポリシー同意を取得できない。同意前にシフト通知（LINE連携後は送れる）を送ってよいかを含め、**法務観点の確認が必要**。

### 3.4 閲覧リンク再発行のセルフサービスが使えない

§2.7のとおり。担当者経由の再送で救済するが、スタッフの自己解決手段が減ることは体験上のマイナス。

### 3.5 LINE失敗時のフォールバックがなく、不達が増える

LINEのみのスタッフは、Quota超過・友達解除・Push失敗時に代替チャネルがない。通知不達Inboxに載せると「再送してもまた失敗する」エントリが溜まりやすい（`failureSuppress` の既存抑制ロジックとの整合を確認）。**友達解除（unfollow）されたLINEのみスタッフは実質「通知手段なし」に転落する**ため、§3.1のバッジ判定は `email === "" && !(lineUserId && lineFollowing)` とし、unfollowも拾うこと。

### 3.6 空文字とindexの罠

`by_shopId_email_isDeleted` / `by_shopId_emailNormalized_isDeleted` / `by_email` / `by_emailNormalized` を `""` で引くと、**メール未登録スタッフ全員がヒット**する。

- `findActiveStaffByEmail`、`staffAuth` の照会、`staffRegistration` の突合など、email系indexを引く箇所すべてに「空文字なら引かない」ガードが必要。1箇所でも漏れると「未登録スタッフ同士が同一人物扱いされる」「空メール入力で他人のスタッフ行に誤マッチする」重大バグになる。
- **ガードは `staff/service.ts` のヘルパーに集約**し、生indexアクセスを増やさないこと。テスト（`_scenario/securityBoundaries.test.ts` 系）で空文字照会の挙動を固定する。

### 3.7 テスト・シナリオ・シード・E2Eへの波及

`convex/_test/seed.ts`・scenarioBuilders・各 mutation テスト・E2E（スタッフ追加フォーム）がメール必須前提。メール空スタッフのシナリオ（追加→LINE連携→通知→提出）を新設する必要があり、テスト工数が本体実装と同程度かかる見込み。

### 3.8 メールtypo警告との共存

`StaffRegistration/emailTypo.ts` のtypo警告・確認表示は「空ならスキップ」にするだけで共存可能（Phase 1ではQR登録はメール必須のままなので実質影響なし）。

## 6. QR自己登録のメール任意化＋LINE同時連携 設計

### 6.1 実現性の確認

既存のLINE連携OAuthフロー（`convex/line/actions.ts` の `redeemLineToken`）は、

1. state用ワンタイムトークンをDBに発行（`lineLinkTokens`、staffId単位）
2. LINE Login認可 → `/line/callback` でcode受領
3. **サーバー側**でcode交換 → `fetchLineProfile` で `lineUserId` 取得、`fetchLineFriendshipStatus` で友達状態取得
4. `finalizeLinking` で `staffLineAccounts` 作成

という構造で、**「staffIdに紐付くトークン」を「登録リンク（shopId）に紐付くトークン」に差し替えれば申請前のスタッフにもそのまま転用できる**。承認前は `staffs` レコードが存在しないため、`lineUserId` を申請レコードに一時保持し、承認時に `staffLineAccounts` を作成する。

```
  |                                |                                    | 申請レコードに lineUserId 保存
  |                                |                                    |
  ==== 承認時（シフト担当者）: staff作成 + staffLineAccounts作成 + LINEで募集通知 ====
```

### 6.3 スキーマ変更（すべて追加のみ・マイグレーション不要）

**新テーブル `staffRegistrationLineTokens`**（OAuth state用。既存 `lineLinkTokens` は `staffId` 必須のため広げず、別テーブルにする）:

```
shopId: v.id("shops")
registrationLinkId: v.id("shopRegistrationLinks")
token: v.string()                      // UUID v4 = OAuth state
expiresAt: v.number()                  // 短命（例: 30分。フォーム入力中の連携なので72hは不要）
lineUserId: v.optional(v.string())     // callback成功後にサーバーが書き込む
lineDisplayName: v.optional(v.string())
lineFollowing: v.optional(v.boolean())
redeemedAt: v.optional(v.number())     // OAuth完了
consumedAt: v.optional(v.number())     // 申請で使用済み（ワンタイム）
index: by_token
```

**`staffRegistrationRequests` への追加**（`v.optional` のみ）:

```
lineUserId: v.optional(v.string())
lineDisplayName: v.optional(v.string())
lineFollowing: v.optional(v.boolean())
lineLinkedAt: v.optional(v.number())
index追加: by_shopId_lineUserId_status   // LINEでの重複申請排除用
```

`email` / `emailNormalized` は `v.string()` のまま `""` を許容（§2.1と同じ空文字方式）。

### 6.4 バリデーション・重複排除

- **申請条件: `email !== "" || LINE連携済み` のどちらか必須**。両方なしは申請不可（「通知手段なしスタッフ」をQR経由では作らせない。§3.1のリスクをQR側には持ち込まない）。
- 重複排除は**持っているキーで二段構え**:
  - email あり → 現行どおり `emailNormalized` で既存スタッフ・pending申請をチェック
  - LINE連携あり → `lineUserId` で pending申請（新index）と既存スタッフ（`staffLineAccounts.by_lineUserId_and_isDeleted` を shopId でフィルタ）をチェック
  - 両方ある場合はどちらかヒットで `already_registered` / `already_applied`
- `logSkip` の `emailDomain` ログは email 空のときのガードを追加（`"".split("@")[1]` は `undefined` になるだけだが、`lineUserId` 有無をログに含める方が調査しやすい）。

### 6.5 セキュリティ設計

- **`lineUserId` はクライアントから絶対に受け取らない**。OAuth callbackでサーバーがcode交換して取得し、stateトークンレコードに書き込む。`submitRegistrationRequest` は `lineLinkToken`（state）だけを受け取り、サーバー側でレコードから読む。クライアント申告を許すと他人のLINE IDでのなりすまし申請が可能になる。
- stateトークン: UUID v4・ワンタイム（`consumedAt`）・短命TTL。`redeemRegistrationLineLink` には既存 `lineLinkRedeem` と同等のレートリミット（state先頭8文字キー）を適用。
- `startRegistrationLineLink`（トークン発行）にもレートリミットを追加（登録リンクtokenキー。トークン濫造によるDB肥大防止）。
- `submitRegistrationRequest` 自体のレートリミットは現状存在しない。メール入力ハードルが下がる分、**登録リンクtoken単位のレートリミット追加を推奨**（LINE連携必須化である程度抑止されるが、email側の申請は従来どおり入力自由なため）。
- 承認時に同一shopで同一 `lineUserId` が既に別スタッフに連携済みだった場合（申請〜承認の間に連携された等）は、`finalizeLinking` の同一店舗内重複ルールに合わせるのではなく**承認をエラーにして担当者に判断させる**（自動で旧アカウントを消すのは承認文脈では乱暴）。

### 6.6 承認フローの変更

`approveRequest` に以下を追加:

1. staff作成（`email` は `""` の場合あり）
2. `request.lineUserId` があれば `staffLineAccounts` を作成（`following` は申請時スナップショット。作成後はwebhook follow/unfollowが `lineUserId` 起点で全店舗更新するため自然に追随する）
3. 通知スケジュールの分岐:
   - LINE連携あり → `sendInviteEmail` は**送らない**（連携済みのため不要）。募集中シフトがあれば `sendOpenRecruitmentNotificationLinesForStaff`（LINE）で提出リンクを送る
   - LINE連携なし・emailあり → 現行どおり `sendInviteEmail` + `sendOpenRecruitmentNotificationEmailsForStaff`

### 6.7 フロント（登録ページ）の変更

- `/staff/register`: 「LINEで連携する」ボタンを主導線として追加。メール欄は「メールアドレス（LINE連携する場合は任意）」に変更。**どちらも未入力での申請はバリデーションエラー**（Submitボタン常時Enabled方針は維持し、エラーメッセージで案内）。
- OAuth往復でフォーム入力（名前・同意チェック）が消えないよう、**リダイレクト前に sessionStorage へ退避**し、callback復帰時に復元する。stateトークンも sessionStorage に保持。
- callback用ルートは既存 `/line/callback` を共用せず **`/staff/register/line-callback` を新設**（LINE Loginチャネルのcallback URLは複数登録可能）。既存callbackは「連携完了」で終わる画面だが、登録用は「フォームに戻って申請を続ける」導線が必要で、画面の責務が異なるため。
- 認可URLに **`bot_prompt=aggressive`** を付与し、LINE Loginの途中で公式アカウントの友だち追加を促す（`buildLineAuthorizeUrl` にオプション追加）。友だち未追加だと通知が届かないため（§6.8）。
- 連携完了後のフォームには「LINE連携済み: {displayName}」を表示。申請確認画面（既存の大きな確認表示）にも連携状態を含める。
- シフト担当者側の申請カード（`StaffRegistrationRequests`）: メールの代わりにLINEバッジ＋表示名を表示。

### 6.8 このスコープ特有のリスク

- **友だち未追加のままの連携**: LINE Loginだけ完了して友だち追加をスキップすると `lineFollowing: false` = Pushが届かない。`bot_prompt` で促しても保証はないため、`needs_follow` 状態を登録ページで警告し、申請自体は許容（emailなしなら§3.1の「通知手段なし」に近い状態になるが、webhook followで自動回復する）。
- **friendship状態の鮮度**: 申請〜承認の間にunfollowされてもスナップショットは古いまま。承認後の初回通知が失敗して通知不達Inboxに載る、が既存の回復経路（許容）。
- **LINE表示名を本名代わりにできない**: displayNameはニックネームが多く、なりすまし・取り違えの検知には使えない。申請の本人性はこれまで同様「担当者が名前を見て承認する」運用が担保する（emailも本人性を証明していなかったので、実質的な後退はない）。
- **LINE環境変数未設定の店舗**: `LINE_LOGIN_CHANNEL_ID` 未設定環境ではLINE連携ボタンを非表示にし、メール必須の従来フォームにフォールバック（既存の「未設定でもメールは動く」方針を踏襲）。
- **外部ブラウザ問題の逆パターン**: QRをLINEアプリ内カメラで読むとLINEアプリ内ブラウザで登録ページが開き、そこからのLINE Loginは**むしろスムーズ**（アプリ内認可）。逆に外部ブラウザからのLINE Loginはログイン入力が挟まる。どちらでも動くが、E2E/実機での動作確認項目に含めること。

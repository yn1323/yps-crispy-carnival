# 削除後の業務識別情報保持と認証切り離しの実装計画

作成日: 2026-07-19

状態: ローカル実装完了（公開前に保持目的と保持期間のプロダクト判断が必要）

## 1. 結論

店舗削除、グループ削除、スタッフ削除、明示的なアカウント削除では、氏名、メールアドレス、店舗名を削除済みの値へ置き換えない。

同じ業務履歴を構成するグループ名と請求先メールアドレスも保持する。

削除後も保持する値は、`organizations.name`、`organizations.billingEmail`、`shops.name`、`organizationPeople.name/email`、`staffs.name/email`、既存の`users.name/email`である。

一方、削除を「利用停止」として成立させる状態変更は維持する。

店舗、グループ、スタッフ、所属は論理削除または`removed`へ変更し、session、magic link、登録リンク、招待、未送信通知、LINE連携を失効させる。

所属なしユーザーが明示的にアカウント削除を依頼した場合は、現在のdurable jobでClerkユーザーを削除し、provider識別子をjobから除去する処理を維持する。

既存のローカル`users`行は氏名とメールアドレスを保持し、`isDeleted`と`accountDeletionRequestedAt`だけで利用を停止する。

この変更後の「削除」は個人データの消去ではない。

本人から別途データ消去要求を受けた場合の法務判断、本人確認、対象データの抽出、消去または匿名化は、通常の削除導線から分離した運用または将来機能として扱う。

schemaと永続データ形状は変えないため、新しいConvex migrationは追加しない。

Clerkユーザーを実際に削除するE2Eも追加しない。

## 2. この計画が置き換える契約

この計画は、次の文書にある「氏名、メールアドレス、店舗名、グループ名をtombstoneへ置換する」という契約を置き換える。

- `doc/plans/2026-07-18_店舗と組織の削除_個人情報匿名化_実装計画.md`
- `doc/plans/2026-07-18_所属なしユーザーのアカウント削除_実装計画.md`のローカル`users` tombstone化に関する箇所
- `doc/features/data-deletion.md`
- `doc/features/account-deletion.md`

既存の認可、冪等性、cleanup job、Clerk provider削除、provider識別子のredaction、削除済みデータの非表示は変更しない。

## 3. 用語と対象範囲

この計画では、削除後もDBに残す氏名、メールアドレス、店舗名、グループ名を**業務識別情報**と呼ぶ。

業務識別情報は過去のシフト、同意、請求、通知、監査などを人が確認するための情報であり、削除後も個人データまたは個人情報に該当し得る。

「DBに残っているが通常画面から見えない」状態を、個人データの消去や匿名化とは表現しない。

### 3.1 ユーザー依頼の解釈

- 「名前」には人物の氏名とグループ名を含める。
- 「メールアドレス」には通常のメールアドレスと請求先メールアドレスを含める。
- 「店舗名」は`shops.name`を指す。
- 「Clerkのログイン情報と切り離しはそのまま」は、明示要求時のClerkユーザー削除、削除前のstrict再認証、provider識別子の完了時redactionを維持することを指す。

`users.authTokenIdentifier`は、削除受付後に残った古いJWTを削除済み状態へ解決して拒否するため、現行どおり保持する。

この値は画面、公開response、運用ログへ出さず、新しいClerkアカウントへの再関連付けにも使わない。

### 3.2 業務識別情報に含めない認証識別子

LINE ID、session、token、Capability、招待、登録リンクは業務履歴の表示名ではなく、連絡またはアクセスの能力を与える値である。

このため、次の処理は変更しない。

- 店舗またはグループのcleanupでは、`staffLineAccounts.lineUserId`を行ID由来の削除済み値へ置き換える。
- `staffLineAccounts`を`isDeleted = true`、`following = false`にする。
- staff session、magic link、LINE連携token、法務同意token、店舗登録リンクを失効させる。
- 組織招待と未送信通知を取消または終端化する。
- account deletion jobの`clerkUserId`と`expectedIssuer`をClerk削除完了transactionで除去する。

通常のスタッフ削除と人物の所属解除では、現行どおり`lineUserId`自体は上書きせず、`isDeleted`、`following`、sessionとtokenの失効によって利用不能にする。

## 4. 実装前の状態

実装前のコードでは、削除経路ごとに業務識別情報の扱いが異なっていた。

| 経路 | 実装前の業務識別情報 | 実装前の利用停止 | 根拠 |
| --- | --- | --- | --- |
| 旧スタッフ削除 | 氏名とメールを保持 | `staffs.isDeleted = true`、LINE連携を停止 | `convex/staff/mutations.ts` |
| 店舗から人物を外す | 氏名とメールを保持 | 対象`staffs`を論理削除し、session、token、通知を停止 | `convex/organization/mutations.ts` |
| グループから人物を外す | 氏名とメールを保持 | personとmemberを`removed`にし、全店舗所属と権限を停止 | `convex/organization/mutations.ts` |
| 店舗削除 | 受付時に店舗名を置換し、cleanupでスタッフ氏名とメールを置換 | 店舗、staff、member、LINE連携、token、通知を停止 | `convex/organization/mutations.ts`、`convex/shop/mutations.ts`、`convex/deletionCleanup/mutations.ts` |
| グループ削除 | 受付時とcleanupでグループ名、請求先メール、店舗名、人物とstaffの氏名、メールを置換 | グループ、全店舗、person、member、staff、LINE連携、token、招待、通知を停止 | `convex/organization/mutations.ts`、`convex/deletionCleanup/mutations.ts` |
| 明示的アカウント削除 | 受付時に既存`users`の氏名とメールを置換 | ローカルuserを停止し、durable jobでClerkユーザーを削除 | `convex/accountDeletion/mutations.ts` |

通常のスタッフ削除と人物の所属解除は、すでに今回の保持方針を満たしている。

実装の中心は、店舗とグループの削除受付、`deletionCleanup` worker、明示的アカウント削除受付の修正になる。

## 5. 完成後のデータ契約

| tableまたは外部対象 | 保持する値 | 削除時に変える値 | 削除後の用途 |
| --- | --- | --- | --- |
| `shops` | `name` | `isDeleted = true` | 過去の店舗識別。active店舗一覧には返さない |
| `organizations` | `name`、`billingEmail`、`billingEmailNormalized` | `isDeleted = true`、`updatedAt`、課金通知cutoff | 過去のグループと請求記録の識別 |
| `organizationPeople` | `name`、`email`、`emailNormalized` | `status = "removed"`、`updatedAt` | 過去の人物と履歴の識別 |
| `organizationMembers` | 関連IDと履歴 | `status = "removed"`、`updatedAt` | 権限を失効した所属履歴 |
| `staffs` | `name`、`email`、`emailNormalized` | `isDeleted = true` | 過去のシフトなどの業務履歴の識別 |
| `shopMembers` | 関連ID | `isDeleted = true` | 旧管理権限の復活防止 |
| `users` | 既存行の`name`、`email`、`emailNormalized`、`authTokenIdentifier` | 明示的アカウント削除時だけ`isDeleted = true`と`accountDeletionRequestedAt` | 過去の内部参照と古いJWTの拒否 |
| `staffLineAccounts` | 行IDと履歴時刻 | 店舗またはグループcleanupでは`lineUserId`を削除済み値へ置換する。対象LINE連携を処理する削除経路では`following = false`、`isDeleted = true`にする | LINEへの再送と再認証を防止 |
| session、token、登録リンク | 既存行と失効状態。保存値は公開しない | `revokedAt`を設定 | 古いCapabilityの再利用防止 |
| Clerk user | 保持しない | 明示的アカウント削除jobでprovider userを削除 | ログイン不能化 |
| `accountDeletionJobs` | 状態、試行回数、安全なerror code、時刻 | 完了時にprovider識別子を除去し、90日後にjobを削除 | 運用確認と再試行 |

削除済みの人物、staff、店舗、グループは、active一覧や通常の編集APIへ再表示しない。

過去履歴を表示する既存画面が削除済み行を参照する場合だけ、保持した業務識別情報を表示できる。

この計画では、削除済みデータを検索または一括取得する新しい管理画面と公開APIは追加しない。

## 6. アカウント削除の契約

明示的アカウント削除は、ローカルの業務識別情報保持とClerk認証主体の削除を分けて処理する。

### 6.1 既存userがある場合

`convex/accountDeletion/mutations.ts`の受付transactionから`userTombstone()`の適用を外す。

既存の`name`、`email`、`emailNormalized`、`authTokenIdentifier`は変更せず、`isDeleted = true`と`accountDeletionRequestedAt`だけを設定する。

受付と同じtransactionで作る`accountDeletionJobs`、所属の再検査、Clerk provider worker、再試行、完了時redactionは変更しない。

### 6.2 user行がない場合

user行がない認証主体には、保持すべきローカル氏名とメールアドレスが存在しない。

schema必須値と古いJWT拒否用の行を作るため、現在の非PIIな`example.invalid`値を使う最小user insertは維持する。

この経路でClerk claimの氏名やメールアドレスを新たにDBへ複製しない。

### 6.3 削除済み状態の公開response

`api.dashboard.queries.getCurrentUser`は、削除済みuserへ`accountDeleted`と`accountDeletionRequested`のbooleanだけを返す契約を維持する。

DBに氏名とメールアドレスを保持しても、削除済み本人の通常画面、別tenant、公開APIへ返さない。

## 7. 実装手順

### 7.1 削除受付で業務識別情報を上書きしない

`convex/organization/mutations.ts`では、店舗削除受付を`shops.isDeleted = true`だけに変更する。

グループ削除受付では、`organizationTombstone()`を外し、`organizations.isDeleted = true`、`updatedAt`、課金通知cutoffだけを更新する。

`convex/shop/mutations.ts`のlegacy店舗削除も、店舗名を変えず`isDeleted = true`だけを設定する。

`convex/accountDeletion/mutations.ts`では、既存userへの`userTombstone()`を外す。

### 7.2 cleanup workerをアクセス失効へ限定する

`convex/deletionCleanup/mutations.ts`は、永続済みjobとの互換に必要なphaseとresourceを削除・改名せず、各phaseの業務識別情報に関する更新内容を変える。

別機能に必要なphase追加は妨げないが、既存jobが保存済みのphaseとresourceから再開できる契約は維持する。

- `shopCore`は店舗名を変えず、`isDeleted = true`だけを保証する。
- `organizationCore`はグループ名と請求先メールを変えず、論理削除と課金通知cutoffだけを保証する。
- `organizationShops`は店舗名を変えず、各店舗の`isDeleted = true`だけを保証する。
- `organizationPeople`は氏名とメールを変えず、`status = "removed"`だけを保証する。
- `staffs` resourceは氏名とメールを変えず、`isDeleted = true`だけを保証する。
- `lineAccounts`、session、token、登録リンク、招待、Outboxの処理は維持する。

最終verificationも同じ契約へ変更する。

店舗名、グループ名、氏名、メールのtombstone一致は検査せず、親の論理削除、所属の終了、LINE ID切断、Capability失効、通知停止だけを再走査する。

`organizationCreatedByUser`と`organizationShopMemberUsers`の旧phaseまたはresourceは、永続済みjobとの互換no-opとして残す。

### 7.3 tombstone helperを縮小する

`convex/deletionCleanup/tombstone.ts`から、コード上の参照がなくなった次のhelperと定数を削除する。

- `DELETED_SHOP_NAME`
- `DELETED_ORGANIZATION_NAME`
- `DELETED_PERSON_NAME`
- `deletedEmail()`
- `organizationTombstone()`
- `personTombstone()`
- `staffTombstone()`
- `userTombstone()`

LINE連携を切断する`deletedLineUserId()`は維持する。

ファイル名の変更は、永続データ互換に寄与せず差分だけを増やすため行わない。

### 7.4 UI文言を保持契約へ合わせる

削除確認UIから「氏名、メール、店舗名を削除済みの値へ置き換える」という説明を除く。

店舗削除ダイアログでは、店舗とスタッフを利用不能にすること、店舗名、氏名、メール、履歴を保持すること、LINE連携とリンクを停止することを伝える。

グループ削除ダイアログでは、グループと全店舗を利用不能にすること、グループ名、店舗名、氏名、メール、履歴を保持すること、権限と連絡手段を停止することを伝える。

アカウント削除ダイアログでは、Clerkのログイン情報を削除する一方、シフトリ内の氏名、メール、店舗名、過去履歴を業務記録として保持することを伝える。

「法令や不正防止のため一定期間残る場合があります」という一律の法的説明は使わず、現在のプロダクト契約で保持する対象を具体的に書く。

再登録時は、保持した履歴を新しいClerkアカウントへ自動で関連付けないことも明記する。

対象ファイルは次のとおり。

- `src/components/features/OrganizationSettings/ShopManagement/ShopManagementDialog.tsx`
- `src/components/features/OrganizationSettings/OrganizationDeletion/OrganizationDeletionDialog.tsx`
- `src/components/features/AccountDeletion/AccountDeletionDialog.tsx`
- `src/components/features/AuthenticatedApp/DeletedAccountState.tsx`
- `src/pages/account-deletion-accepted/index.tsx`

実装と同じ変更で、次の現行仕様書を更新する。

- `doc/features/data-deletion.md`
- `doc/features/account-deletion.md`

過去の実装計画は履歴として本文を残し、冒頭にこの計画で置き換えた範囲とリンクを追記する。

`convex/schema.ts`の`deletionCleanupJobs`コメントも、主要マスタ置換ではなくアクセス失効と通知停止を再開可能にするjobという説明へ直す。

### 7.6 プライバシーポリシーとの整合を取る

現在の管理ユーザー向けとスタッフ向けプライバシーポリシーには、利用終了後の業務識別情報の保持目的と保持期間が書かれていない。

公開前に、履歴確認、問い合わせ対応、請求または監査などのうち実際に採用する保持目的と、table群ごとの保持期間をプロダクト判断として確定する。

確定した内容を次の文書へ反映する。

- `src/components/features/PrivacyPolicy/content/manager.mdx`
- `src/components/features/PrivacyPolicy/content/staff.mdx`

本文を変更した場合は、`doc/manual/legal-versioning.md`に従って`convex/legal/documents.ts`の`documentVersion`を更新する。

今回の変更は利用者の削除判断に影響するため、法務またはプロダクト責任者が軽微な説明補足と判断しない限り、`requiredConsentVersion`も更新して再同意を求める。

保持期間が未確定のまま「法令のため一定期間残る」とだけ記載して公開しない。

## 8. 互換性と展開

### 8.1 schemaとmigration

保持対象のfieldも論理削除fieldも現行schemaに存在するため、Widen、backfill、Narrowは不要である。

固定migration seriesの`m016_deleted_shops_enqueue_cleanup_jobs`と`m017_deleted_organizations_enqueue_cleanup_jobs`は、処理内容を変更しない。

`m016`の説明コメントだけは、実際のworker契約に合わせて主要マスタ置換jobからaccess失効jobへ更新する。

両migrationが新しく作るjobは、展開後のworkerによって業務識別情報を保持しながらアクセス失効を完走する。

両migrationが対象deploymentで未実行の場合は、新しいworkerを先に展開し、保持契約へ切り替わったことを確認してから実行する。

### 8.2 進行中jobの扱い

cleanup jobはphaseとcursorをDBへ保存するため、worker展開時に旧jobが進行中だと、処理済み行だけが旧契約でマスキングされ、未処理行は新契約で保持される混在状態になり得る。

展開前に対象deploymentのexportまたはbackupを取得し、非終端job件数と既にマスキングされた対象件数を別々に記録する。

展開前に`internal.deletionCleanup.queries.getStatus`を実行し、`queued`、`processing`、`retrying`、`actionRequired`が0件であることを確認する。

0件でない場合は、旧workerのまま完了または要対応解消まで進めてから展開する。

jobごとのpolicy version追加は、この展開ゲートで混在を防げるため初回実装には含めない。

### 8.3 すでにマスキング済みのデータ

`削除済み店舗`、`削除済みグループ`、`削除済みユーザー`、`example.invalid`へ置換済みの値から、元の業務識別情報は復元できない。

この実装は既存値を推測して復元せず、展開後に発生する削除と、まだ処理されていない対象へ適用する。

事前exportまたはバックアップからの復元が必要になった場合は、対象ID、backup時点、後続更新、tenant境界を照合する別の運用計画を作る。

### 8.4 ロールバック

旧workerへ戻すと、新しい削除jobが業務識別情報を再びマスキングする。

このため、backendの保持契約は通常のコードロールバック対象にせず、問題があれば削除受付を止めてforward fixする。

frontendだけを戻す場合も、backend workerの保持契約は戻さない。

## 9. Security Lens

- Actor: 店舗削除は対象グループの有効管理者、グループ削除は削除条件を満たす唯一の有効管理者、スタッフ所属解除は同一グループの許可済み管理者、アカウント削除はstrict再認証を通った所属なし本人、cleanupはinternal workerである。
- Asset: 業務識別情報、過去履歴、tenant境界、管理権限、staff向けCapability、Clerk認証主体である。
- Trust boundary: clientから渡す店舗ID、グループID、person ID、確認値、request IDは認可の根拠にせず、Clerk identityとserver上のactive所属へ照合する。
- Abuse case: 削除済み人物の氏名とメールがactive一覧または別tenantへ漏れること、古いJWTやtokenで再アクセスできること、削除後に通知が送られること、別組織の削除済み履歴をIDORで取得できることである。
- Server-side check: 既存のauthenticatedまたはmanager wrapper、active membership、親子関係、課金状態、唯一管理者条件、`isDeleted`、`status`、所属なしscanを維持する。
- Rate limit and idempotency: 固定request ID、監査correlation、cleanup jobの一意化、account deletion rate limit、provider jobのleaseとversionを維持する。
- Lifecycle and recovery: 親を先に利用不能にし、後続jobで権限、連絡手段、Capabilityを失効する。Clerk削除はprovider確認後に実行し、完了時にprovider識別子を除去する。
- Logs and PII: 保持した氏名とメールをcleanup job、error code、運用probe、ログへ複製しない。運用probeはIDと安全な状態codeだけを返す。
- Regression test: Function Testで保存値と失効状態を同時に検証し、Scenario Testで複数batchとlease回収後も同じ契約を確認する。公開queryは削除済みPIIを返さないことを既存テストで維持する。

## 10. テスト計画

### 10.1 Convex Function Test

`convex/organization/shopManagement.test.ts`と`convex/shop/mutations.test.ts`では、店舗削除受付直後も元の店舗名が残り、店舗だけが`isDeleted = true`になることを確認する。

`convex/organization/deletion.test.ts`では、グループ削除の受付直後とcleanup完了後に次を確認する。

- グループ名と請求先メールが変わらない。
- 全店舗の店舗名が変わらない。
- `organizationPeople`と`staffs`の氏名、メール、正規化メールが変わらない。
- personとmemberは`removed`、staffとshop memberは論理削除になる。
- LINE IDは削除済み値へ置換され、session、token、リンク、招待、未送信通知は失効する。
- 元のメールアドレスを保持しても新しい通知をenqueueできず、claim済み通知も外部送信直前のactive状態確認で停止する。
- 削除前のmanager JWT、staff session、同意token、登録リンクから業務識別情報を取得できない。
- global `users`と別tenantは変更されない。

`convex/deletionCleanup/mutations.test.ts`では、各phaseと最終verificationが業務識別情報を上書きせず、未失効resourceだけを修復することを確認する。

旧phaseと旧verification resourceを持つ永続済みjobが、新しい契約でも`completed`へ進むことを残す。

`convex/accountDeletion/acceptance.test.ts`と`convex/accountDeletion/mutations.test.ts`では、既存userの氏名、メール、正規化メールを保持したまま削除jobを一件だけ作ることを確認する。

user行がない経路は、元PIIを持たない合成行を作る現在のテストを維持する。

`convex/dashboard/queries.test.ts`では、実際の氏名とメールを保持した削除済みuserをseedしても、公開DTOが`accountDeleted`と`accountDeletionRequested`だけを返すことを確認する。

`convex/staff/mutations.test.ts`と`convex/organization/mutations.test.ts`では、すでに保持している通常のスタッフ削除と人物所属解除について、氏名とメールが変わらないことを明示的な回帰条件に加える。

### 10.2 Convex Scenario Test

`convex/_scenario/organizationDeletion.test.ts`の100件超データとlease回収シナリオを、新しい保持契約へ変更する。

複数batchをまたいでも、全行の業務識別情報が元の値のまま、アクセス状態だけが終了することを検証する。

`convex/_scenario/accountDeletion.test.ts`では、既存userの業務識別情報保持、Clerk fakeによるprovider削除、旧subjectの拒否、新しいsubjectでの別アカウント作成を同じシナリオで確認する。

### 10.3 Frontend LogicとBehavior Test

既存のcontroller二重送信ガード、確認入力、完了画面、削除済みuserの非表示契約は維持する。

文言変更に伴って既存testの期待値だけを更新する。

Storybookの初期表示にある静的説明文を、存在確認だけのplay functionで新たに重複検証しない。

操作後に現れる確認状態や送信状態を検証する既存play functionは維持する。

### 10.4 法務文書のバージョン契約

プライバシーポリシーを更新する場合は、`convex/legal/documents.ts`の文書版と再同意版を計画どおり変更する。

`convex/legal/mutations.test.ts`、`convex/setup/mutations.test.ts`、`convex/shiftSubmission/mutations.test.ts`などの版期待値は、現行版を検証する箇所だけ追従させる。

Storyとfixtureに直書きされた版も同じ基準で更新し、過去同意版や旧版互換を表すfixtureまで機械的に置換しない。

### 10.5 E2E

新しいE2Eは追加しない。

保持契約はDBの保存値と失効状態の組合せであり、Convex Function TestとScenario Testが主担当になる。

既存の`e2e/scenarios/shop-deletion-flow.test.ts`と`e2e/scenarios/organization-deletion-flow.test.ts`は、削除後の画面遷移、旧URL遮断、active一覧からの非表示をすでに検証しており、その契約は変わらない。

Clerkユーザーを実際に削除するE2Eは、E2Eアカウントを破壊するため引き続き実施しない。

新規E2Eを追加しないため、`pnpm e2e`の追加実行は必須確認に含めない。

## 12. 展開後の確認

展開後は、PIIを返さない運用probeと管理画面の代表操作で次を確認する。

1. 新しい店舗削除で、店舗とstaffが利用不能になり、店舗名、氏名、メールはDB上で変わらない。
2. 新しいグループ削除で、グループ、全店舗、人物所属、staffが利用不能になり、業務識別情報はDB上で変わらない。
3. LINE連携、session、token、登録リンク、招待、未送信通知が失効する。
4. 削除済み店舗と人物がactive一覧、通常の編集API、別tenantへ現れない。
5. `deletionCleanupJobs`の非完了statusが0件へ収束する。
6. account deletionのread-only readinessが成功し、実Clerkユーザーの取得または削除を行わない。
7. 公開中のプライバシーポリシーが、採用した保持目的、保持期間、問い合わせ方法と一致する。

## 13. 今回含めないもの

- すでにマスキング済みの値をbackupから復元する処理。
- 本人からのデータ消去要求を受け付ける画面、本人確認、法務判定、全保存先の探索、消去workflow。
- 削除済みデータを検索またはexportする新しい管理者画面。
- retention期間をtableごとに確定し、自動物理削除する共通基盤。
- Clerk webhookによる削除同期。
- cleanup jobの新しいpolicy version field。
- 保持目的と保持期間が未確定のままプライバシーポリシーへ曖昧な法的根拠を追加すること。

# Stripeセキュリティ対策 テスト計画

- 作成日: 2026-07-20
- 対象: Stripe Checkoutを使うオンライン課金と、日本向けセキュリティ対策措置状況申告書の確認項目
- ステータス: 計画作成済み、Stripe sandbox canaryと運用証跡は未完了
- 関連計画: `doc/plans/2026-07-20_Stripe課金連携_実装計画.md`

## 1. 目的

この計画は、Stripe連携のコードが正しく動くことと、セキュリティ申告で求められる対策を実施していることを分けて確認する。

コードの自動テストだけでは、Clerk、Cloudflare、Stripe Dashboard、開発端末、脆弱性診断の実施状況を証明できない。

そのため、確認を次の四層へ分ける。

| 層 | 主な対象 | 確認方法 |
|---|---|---|
| 自動テスト | 認証、認可、Webhook、課金状態、入力検証、二重送信、復旧 | Logic、Frontend Unit、Convex Function、Convex Scenario |
| Provider canary | Stripe Checkout、3DS、Radar、実Webhook、Customer Portal | Stripe sandboxで人が実施する隔離試験 |
| 環境設定確認 | Clerk MFA、ロック、Cloudflare Access、Stripe Dashboard | 設定画面、設定export、使い捨てアカウントによる動作確認 |
| 運用確認 | 脆弱性診断、端末保護、定期スキャン、アカウント棚卸し | レポート、実施記録、承認記録 |

この文書は適合性の認証書ではない。

各対策を申告済みにする判断は、完了条件と証跡を確認した責任者が行う。

## 2. 対象範囲

### 2.1 対象

- Stripe Hosted CheckoutとCustomer Portal。
- `POST /stripe/webhook`と後続の再照合、状態遷移、回復処理。
- Free、Trial、Pro、Pro（先行登録特典）の課金境界。
- Clerkを使う管理者ログイン、別端末確認、管理者招待。
- Cloudflareで公開するメインアプリと内部BI。
- 公開ディレクトリ、ビルド成果物、環境変数、ログの秘密情報非露出。
- 開発者と運用担当者が利用する端末のマルウェア対策。

### 2.2 対象外

- Stripe Payment ElementとStripe.jsを使う自前カード入力フォーム。
- Stripe Connect。
- 実カード情報を使う自動テスト。
- AI AgentがStripe、Clerk、Cloudflareの管理画面を操作するE2E。
- この文書だけを根拠とした法的な適合判断。

カード番号、CVC、有効期限はシフトリへ入力、送信、保存しない。

この前提が変わった場合は、本計画を流用せずPCI DSSの対象範囲を再評価する。

## 4. Security Lens

| 観点 | 内容 |
|---|---|
| Actor | 有効な管理者、Stripe Webhook、期限処理job、開発者、運用担当者 |
| Asset | Pro権限、請求状態、CustomerとSubscriptionの対応、管理画面、秘密情報、顧客データ |
| Trust boundary | Clerk identity、organization所属、ブラウザからの入力、Stripe署名、Stripe最新snapshot、Cloudflare公開境界 |
| Abuse case | 他organization操作、アカウント乗っ取り、カードテスティング、Webhook偽造、秘密情報露出、内部BIへの未認証アクセス |
| Server-side check | Clerk identity、active membership、billing policy、Stripe署名、PriceとCustomerとSubscriptionとInvoiceの関係検証 |
| Rate limit / idempotency | Checkout single-flight、request ID、Stripe idempotency key、Webhook event dedupe、ログインと再送のprovider側制限 |
| Lifecycle / recovery | Webhook retry、lease回収、猶予終了、Subscription取消、Pro Priceのアーカイブ、open Checkout Sessionの失効、鍵rotation、アカウント失効 |
| Logs / PII | secret、署名、raw Webhook、カード情報、完全なメールアドレスを保存しない |
| Regression test | Function Testで単一境界、Scenario Testで状態収束、sandbox canaryでStripe実接続を確認する |

## 12. Stripe sandbox canary

### 12.1 前提

- Stripe sandboxのSecret key、Price、Portal Configuration、Webhook secretを使用する。
- Local用とdevelopment用に別々のStripe Sandboxを作り、対象deploymentを`sk_test_`で始まるSecret keyへ接続する。
- 接続環境がSecret keyからtestと自動判定され、testとliveのStripeオブジェクトを混在させない。
- development専用organizationと、受信確認用の隔離メールを使用する。
- Webhook destinationへ実装が対応するイベントだけを登録する。
- 無償Proを通常課金canaryへ流用しない。
- 失敗時にPro Priceをアーカイブし、発行済みのopen Checkout Sessionを失効できることを確認する。

### 12.2 シナリオ

| Canary ID | シナリオ | 確認する結果 |
|---|---|---|
| CNY-01 | Freeまたは制限中から通常カードでProへ進む | Checkout、Customer、Subscription、paid、Proが一度だけ成立する |
| CNY-02 | 3DS challengeを成功させる | 認証成功後だけProとなる |
| CNY-03 | 3DS challengeを取消または失敗させる | Proを開放せず、再試行可能な状態に戻る |
| CNY-04 | Stripe公式の高リスク試験を実行する | Radarまたは採用したStripe対策が拒否か追加認証を行う |
| CNY-05 | Trial中に支払い方法を登録する | SetupIntentだけが成立し、Trial中に請求されない |
| CNY-06 | Trial終了時の初回請求を成功させる | 初回確認中を経てProへ収束する |
| CNY-07 | 初回請求または更新請求を失敗させて復旧する | 失敗Webhookで猶予を開始し、支払い成功後にProへ復旧する |
| CNY-08 | 同じWebhook Eventを再送する | receipt、scheduler、状態遷移が一回に収束する |
| CNY-09 | 支払い成功と失敗のイベント順を入れ替える | Stripe最新snapshotとgenerationで同じ最終状態へ収束する |
| CNY-10 | Customer Portalで支払い方法を変更する | 対象Customerだけが変更され、次回請求へ反映される |
| CNY-11 | 無償Proから課金導線を試す | CheckoutとPortalを作らず、Stripe objectが0件のままになる |

Stripe Test ClockまたはBilling SimulationはStripe側の時刻だけを進める。

ConvexのTrial期限jobと14日猶予jobは進まないため、期限到来後の取消、Invoice回収停止、制限移行はConvex Scenario Testを正とし、sandbox canaryの完了条件へ含めない。

各シナリオの後に、内部probeで重複Customer、複数の現在Subscription、未処理Webhook、`actionRequired`、無償ProのStripe対応を確認する。

4. Checkout Session作成時の`payment_method_types: ["card"]`を契約として固定する。
5. `invoice.payment_action_required`専用の状態遷移テストを追加する。

### 13.2 P1

BFFとConvex間の共有secretは利用者認証の代わりにならないため、ADM-03はデプロイ済みURLと`/api/analytics`を未認証ブラウザから直接確認する。

## 14. 証跡

各手動確認とcanaryは次の項目を残す。

- Test ID。
- 実施日時とタイムゾーン。
- test、preview、productionの別。
- 対象git commit SHA。
- 実施者と確認者。
- 期待結果と実結果。
- PASS、FAIL、BLOCKED。
- Stripe、Clerk、Cloudflare、CI、診断レポートの証跡URL。
- FAIL時のissueまたは対応期限。

証跡にはSecret key、Webhook secret、カード番号、CVC、raw Webhook body、完全なメールアドレスを含めない。

スクリーンショットと診断レポートは公開リポジトリへ保存せず、アクセス制限された保管先へ置く。

リポジトリには、Test ID、実施日、結果、証跡URL、確認者だけを記録してよい。

### 14.1 実施責任

| 対象 | サービスが提供する範囲 | シフトリ側の責任 |
|---|---|---|
| Stripe | Hosted Checkout、3DS、Radar、Webhook配信 | Dashboard設定、アプリ実装、sandbox canary、証跡確認 |

SaaSを利用しているだけで、申告書の実施主体を委託先企業へ移したとは扱わない。

外部企業へ診断または運用を実際に委託した場合は、契約範囲、実施日、報告書を証跡へ追加する。

## 18. 失敗時の扱い

Stripe canaryで重複課金、誤ったPro開放、署名不一致、未収束Webhook、無償ProのStripe objectを検出した場合は、Pro Priceをアーカイブして新しいPro販売を停止する。

販売停止前に発行したopen状態のCheckout Sessionは列挙して失効させる。

新規販売の停止中も既存契約の安全に必要なWebhook受信、再照合、取消、Invoice回収停止は継続する。

秘密情報の露出が疑われる場合は、証跡の公開を止め、影響範囲を確認してからStripe、Clerk、Convex、Cloudflareの該当secretとsessionをrotationまたは失効する。

FAILを期待値の緩和だけで通さず、実装不良、テスト不良、環境設定不良、外部provider障害へ分類する。

# 管理者招待の参加確認の実装計画

作成日: 2026-11-18  
状態: Active（2026-11-19にrepositoryへ実装済み。E2Eの実行、VRT基準画像の承認、CI、実環境への反映待ち）

管理者招待を受けるときのメールアドレスの確認をやめ、参加の前に「どのアカウントで参加するか」を確かめる画面へ置き換える。  
ログイン中の画面にはどの状態でもログアウトできる行を置く。

## 1. 問題

招待URLを開いた人がログイン済みだと、確認の画面を挟まずに参加の処理が始まる。  
ログイン中のアカウントが招待先のメールアドレスを確認済みとして持っていなければ、招待先のメールアドレスを入力させ、確認コードで所有を確かめている。

この流れには、次の行き止まりと分かりにくさがある。

| 状況 | 今の結果 |
|---|---|
| 招待した管理者がログインしたままのブラウザで招待URLを開く | 「本人確認ができませんでした」と「もう一度確認する」だけが出て、ログアウトできない |
| 招待先と違うメールアドレスで登録またはログインした | 招待先のメールアドレスを入力し、確認コードを受け取る手順が増える。別のアカウントへ切り替える導線はない |
| `xxxx@gmail.com`のアカウントで、`xxxx+yyy@gmail.com`宛ての招待を開く | シフトリは2つを別のメールアドレスとして扱うため、上と同じ手順になる。Clerkの設定によっては追加を拒否され、抜け出せない |
| ログインから時間が経っている | メールアドレスの追加の前にClerk標準の再確認が挟まる可能性があり、確認コードが2通になる（ブラウザでは未確認） |

招待URLは招待メールでしか渡らず、値は推測できない（HMAC-SHA256の署名値）。  
URLを開けた時点で、その人は招待先の受信箱を読めている。  
確認コードも同じ受信箱に届くため、同じことを2回確かめている。

確認コードでしか止められないのは、招待メールが転送された場合と、URLが受信箱の外へ出た場合だけである。

## 2. 方針

| 項目 | 変更後 |
|---|---|
| メールアドレスの確認 | やめる。招待URLを持ち、ログインしている人は、確認済みメールアドレスが招待先と違っても参加できる |
| 参加の開始 | ログイン済みでも自動で始めない。「参加する」を押したときに始める |
| アカウントの表示 | ログイン中はどのメールアドレスのアカウントでログインしているかを画面に出す |
| ログアウト | ログイン中はどの状態でも押せる「ログアウト」を置く。ログアウト後は同じ招待URLへ戻る |

次の確認は残す。

- 招待先の人がすでにアカウントとつながっている場合は、そのアカウントでログインした本人だけが参加できる。
- ログイン中のアカウントが、その組織に別の人として登録済みの場合は参加させない。
- ログインが必要であること、期限、使用済み、取消、再送前のURL、契約状態、利用人数と管理者数の上限、回数の制限。

schemaの変更とmigrationは行わない。  
発行済みで未使用の招待URLはそのまま使える。  
これまでの確認でClerkのアカウントに追加されたメールアドレスは、そのまま残す。

## 3. 画面

招待URLの画面（`/manager-invite`）の主な作業は、招待された人が管理者として参加することである。  
アカウントの切り替えは補助の操作として、主な操作より弱く見せる。

### 3.1 状態ごとの表示

| 状態 | 見出し | 本文と操作 |
|---|---|---|
| 未ログインで招待が有効 | {組織名}に参加します | 今と同じ。「はじめてシフトリを利用する」「すでにアカウントを持っている」 |
| ログイン済みで招待が有効 | {組織名}に参加します | 「管理者ができること」は今と同じ。主な操作は「参加する」。その下に共通の行を出す |
| 参加の処理中 | 同上 | 「参加する」を処理中の表示にし、もう一度押せないようにする |
| ログイン中のアカウントが、その組織に登録済み | このアカウントでは参加できません | 「このアカウントは、すでに{組織名}に登録されています。別の方が招待を受ける場合は、その方のアカウントでログインしてください。」主な操作は「別のアカウントでログインする」 |
| そのほかの理由で、このアカウントでは参加できない | このアカウントでは参加できません | 「招待された方とは別のアカウントでログインしている可能性があります。ログインし直しても参加できない場合は、担当者に確認してください。」主な操作は「別のアカウントでログインする」 |
| 期限切れ、取消、使用済み、利用できない、通信の失敗 | 今と同じ | 今と同じ。ログイン中は共通の行を足す |
| 参加が完了 | 今と同じ | 今と同じ。共通の行は出さない |

「本人確認が必要」の画面（メールアドレスの入力と確認コードの入力）は削除する。  
「このアカウントでは参加できない」の画面から、「もう一度確認する」を外す。  
同じアカウントでやり直しても結果が変わらないためである。

参加できない画面は理由によって2つに分ける（2026-11-19に決定）。  
ログイン中のアカウントがその組織に登録済みであることは、本人の状態なので本文に書く。  
招待された人がすでに別のアカウントとつながっているかどうかは、招待URLを持つだけの人に知らせないため、本文に書かない。

「招待URL無効です」は助詞が抜けていたため、「招待URLが無効です」に直す。

### 3.2 共通の行

ログイン中はカードの下端に次の行を出す。

- 「{メールアドレス}でログイン中」
- 「ログアウト」

メールアドレスにはログイン中のアカウントの主なメールアドレスを省略せずに出す。  
本人が自分のアカウントを見分けるための表示で、ログインしていない人には出さない。

「ログアウト」と「別のアカウントでログインする」は、どちらもログアウトして同じ招待URLへ戻す。  
戻った画面は未ログインの状態になり、登録とログインのボタンが出る。

### 3.3 ログアウトの置き方

ログアウトの置き方には2つの案があり、2026-11-19に案Aが選ばれた。

| 案 | 内容 | 既存の配置への影響 |
|---|---|---|
| A（採用） | ログイン中のすべての状態に共通の行を出す | カードの下端に1行増える。既存の要素は動かさない |
| B | 確認の画面と、失敗した画面のそれぞれに「別のアカウントでログインする」を置く。共通の行は出さない | 状態ごとにボタンが1つ増える。読み込み中のまま止まった場合はログアウトできない |

Aは想定していない状態でもログアウトできる。  
Bは画面ごとの要素が少ないが、ボタンを置き忘れた状態が行き止まりになる。

## 4. 実装

### 4.1 サーバー

1. `convex/organizationInvitation/mutations.ts`の`prepareAcceptance`と`finalizeAcceptance`を、1つの内部mutationにまとめる。準備と確定の間で結果を引き継ぐためのproofは削除する。
2. まとめたmutationから、確認済みメールアドレスの照合を外す。2章で「残す」とした確認は、今の順序のまま残す。
3. `convex/organizationInvitation/acceptanceActions.ts`の`accept`は公開している名前と引数を変えない。Clerkへの問い合わせとissuerの照合を外し、まとめたmutationを呼ぶだけにする。Nodeの実行環境の指定も外す。
4. `accept`の返り値から`verificationRequired`と、Clerkの照会失敗を表していた`retryable`を外す。参加できない結果には、ログイン中のアカウントが登録済みかどうかを加える。
5. `convex/_lib/clerkVerifiedEmailProvider.ts`とそのテストを削除する。使っているのは招待の受諾だけである。
6. `convex/_test/scenarioFixtures.ts`の受諾の呼び出しを、新しい入口に合わせる。

公開している名前を変えないのは、開いたままの古い画面からの呼び出しを失敗させないためである。  
古い画面は自動で参加の処理を始めるが、新しいサーバーはそのまま参加させる。

### 4.2 画面

1. `src/components/features/ManagerInvitationAcceptance/index.tsx`から、ログイン済みで自動的に受諾を始める処理を外す。「参加する」を押したときだけ`accept`を呼ぶ。
2. メールアドレスの入力、確認コードの送信と確認、再送、Clerkの再確認の呼び出しを削除する。
3. ログアウトは同じ招待URLを戻り先に指定して行う。失敗したときは画面内にエラーを出す。
4. `ManagerInvitationAcceptanceView.tsx`に、確認の画面の「参加する」、共通の行、「このアカウントでは参加できません」の画面を実装する。「本人確認が必要」の画面を削除する。
5. `src/components/features/AuthPage/errorPresentation.ts`の「すでに登録されています」の文から、招待リンクを開き直す案内を外し、以前の「ログインをお試しください。」へ戻す。この文は登録の画面でも使われている。

文言は3章のとおりとし、実装の仕上げに`ui-architect`の検証と`first-use-reviewer`の確認を行う。

### 4.3 参加完了のメール

参加完了のメールに、参加した人の氏名を書く。  
文面は宛先によらず共通とし、参加した本人にも同じ内容を送る（2026-11-19に決定）。

1. `convex/organizationInvitation/queries.ts`の`getAcceptanceNotificationData`が参加した人の氏名を返すようにする。氏名には招待を受けて管理者になった組織のユーザーの名前を使う。
2. `convex/organizationInvitation/actions.ts`の`enqueueAcceptanceNotifications`で、見出しを「{氏名}さんが管理者として参加しました。」にする。
3. 件名を見出しに合わせて変える。`convex/notification/templates.ts`の件名と見出しの定数を、氏名を受け取る形にする。
4. `src/devtools/NotificationPreview/OrganizationManagerInvitationAccepted/index.stories.tsx`のプレビューを新しい文面に合わせる。

## 5. Security Lens

- Actor：招待された本人、招待メールを転送された人、招待URLを見た第三者、同じ端末でログイン中の別の人
- Asset：組織の管理者権限（全店舗のスタッフ情報、シフト、支払い設定）、招待URL（7日間有効、1回だけ使える）
- Trust boundary：ログイン済みのブラウザから呼ばれる`organizationInvitation.acceptanceActions.accept`
- Abuse case：転送された招待メールから別の人が参加する。共用の端末でログイン中の別のアカウントが、気づかないうちに参加する。接続済みの人に別のアカウントがなり代わる。同じ人が組織へ二重に登録される。
- Server-side enforcement：招待URLの値、期限、取消、使用済み、再送前のバージョンを確認する。接続済みの人はアカウントの一致を求める。ログイン中のアカウントが別の人として登録済みなら拒否する。契約状態と上限を確認する。拒否したときは、人、所属、招待を変更しない。
- 今回外すもの：招待先のメールアドレスを、ログイン中のアカウントが確認済みとして持つことの確認。転送された招待メールからの参加は、サーバーでは止められなくなる。
- 外したあとの歯止め：参加の前に、アカウントを表示した確認の画面を挟む。招待は1回しか使えず、7日で切れ、管理者がいつでも取り消せる。参加が完了すると、参加した本人を含む管理者全員にメールが届く。今の文面には誰が参加したかが書かれていないため、参加した人の氏名を書き足す（4.3）。
- Rate limit / idempotency：アカウントごとと招待URLごとの回数の制限を維持する。同じ招待への並行した受諾は1人だけを参加させる。
- Lifecycle / recovery：招待の状態とバージョンの扱いは変えない。誤って参加した人は管理者設定で権限を外せる。
- Logs / PII：メールアドレスと確認コードをサーバーへ渡す経路がなくなる。画面に出すメールアドレスは、ログイン中の本人のものに限る。

外したあとに残る弱点が1つある。  
管理者の一覧には招待したときの氏名とメールアドレスが出て、ログインに使うメールアドレスは出ない。  
転送された招待メールから別の人が参加しても、一覧では見分けられない。  
この計画では扱わず、7章の別の提案に挙げる。

## 7. この計画で扱わないこと

次の4点は関連するが、別の提案として分ける。

- 使用済みの招待URLを別のアカウントで開いたときの「すでに参加済みです」の文言
- 回数の制限に達したときに出る「招待URLが現在利用できません」の文言
- 招待メールへ「このメールを転送しないでください」と書き足すこと
- 管理者の一覧へ、ログインに使うメールアドレスを出すこと

- 招待先と違うメールアドレスのアカウントでも、「参加する」を押すと管理者として参加できる。

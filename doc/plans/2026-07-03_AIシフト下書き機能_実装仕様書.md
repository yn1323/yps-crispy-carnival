## 1. 概要とスコープ

### 1.1 目的

回収したシフト希望をもとにシフト担当者が手作業でシフトを組む負担を減らす。シフトボード画面に「AIで下書き」ボタンを追加し、押すとAIが**希望と過去実績の傾向**からシフトのたたき台を生成して編集中のボードに反映する。

### 1.2 設計思想

**AIはあくまでたたき台。** 生成結果はDBに一切書き込まず、編集状態（Jotai `shiftsAtom`）にのみ反映する。担当者が目検・手直しした上で、既存の「保存」「確定して通知」フローで永続化する。

### 1.3 スコープ

| 区分 | 内容 |
|------|------|
| **In** | 「AIで下書き」ボタン / おまかせ度選択ダイアログ（3段階。§2.3, §10.3） / Convex action によるAI生成 / 過去実績からの必要人数自動推定・個人別傾向推定 / 出力検証・不正割当ドロップ / 編集状態への全体上書き反映 / レート制限 |
| **Out（将来拡張）** | ポジション別の割当 / 必要人数マスタ / 労働時間制約（週40h等）の考慮 / ストリーミング表示 |

### 1.4 対象ユーザー・画面

- **対象**: シフト担当者（Clerk認証済みマネージャー）のみ
- **画面**: シフトボード（`/_auth/shift-board/$recruitmentId`）の `ShiftForm` ヘッダー
- **非対象**: スタッフ閲覧画面（StaffView）、デモサンドボックス — `onGenerateDraft` propを渡さないことでボタン非表示

## 2. 要件定義

### 2.1 機能要件

| ID | 要件 | 実現箇所 |
|----|------|---------|
| FR-1 | シフトボード画面（ShiftForm）にボタンを設置し、押下でAIがたたき台を生成する | §10.2, §10.3 |
| FR-2 | 「ひかえめ」では希望提出済みスタッフのみ割当対象とする（未提出者は含めない） | §2.3, §5.2（DTOに載せない）+ §9（検証で二重防御） |
| FR-3 | 「ひかえめ」では割当は**希望時間の範囲内のみ**。はみ出す割当はしない | §2.3, §7.2（プロンプト厳守ルール）+ §9 ルール4 |
| FR-4 | 必要人数は過去2〜3回の確定シフト実績から「曜日×時間帯の配置人数」を**自動推定**する（マスタ設定は作らない） | §6 |
| FR-5 | Claude Haiku 4.5 + Convex `"use node"` action。API呼び出し・プロンプトは隔離モジュールで差し替え可能。tool use強制でJSON出力を固定 | §4, §7.4, §8 |
| FR-6 | 確認ダイアログを経て**全体上書き**で編集状態（`shiftsAtom`）に反映。DB書き込みなし | §10.3 |
| FR-7 | 提出パターン3種（time / shiftType / dateOnly）**全対応** | §5, §6, §7, §9 の各パターン分岐 |
| FR-8 | ポジションは全員デフォルト。AIは「誰がいつ入るか」のみ決める | §10.5（デフォルトポジション付与） |
| FR-9 | 乱用対策は既存Rate Limiter基盤でレート制限のみ | §4.5 |
| FR-10 | 過去期間と現募集で営業時間帯・提出パターンが変わっているケースに頑健な傾向分析 | §6.3 |
| FR-11 | 生成の積極度を「おまかせ度」3段階（ひかえめ / おまかせ / とことん）から選択できる | §2.3, §10.3 |
| FR-12 | 「おまかせ」以上では未提出者を本人の過去傾向（曜日×時間帯）から割り当てる | §6.6, §7.2, §9 |
| FR-13 | 「とことん」では目標人数に足りない時間帯を、希望時間の外（営業時間内）にも伸ばして埋める | §7.2, §9 |
| FR-14 | どのモードでも、提出者が希望を出さなかった日（休み希望日）には割り当てない | §2.3 共通ガード, §9 |

### 2.2 非機能要件

| ID | 要件 |
|----|------|
| NFR-1 | 生成の所要時間は数秒〜十数秒を想定。生成中はボタンにスピナーを表示し、二重実行を防止する |
| NFR-2 | 1回あたりのAPIコストは1円未満を目安とする（入力5〜8k / 出力2〜4kトークン想定、Haiku 4.5） |
| NFR-3 | AI応答の一部が不正でも全体失敗にしない（不正割当の個別ドロップ） |
| NFR-4 | 生成失敗時（API例外・パース失敗）は既存の編集内容を一切変更しない |
| NFR-5 | AI通信はテストで必ずモックし、CIから実APIを呼ばない |
| NFR-6 | 店舗単位で毎時10回・バースト3のレート制限（Anthropic課金の前段で遮断） |

### 2.3 おまかせ度（生成モード）

生成の積極度を3段階から選ぶ。内部enumは `DraftMode = "strict" | "standard" | "full"`（§4.2）。

| 段階 | UI名 | 割当対象 | 割当範囲 |
|------|------|---------|---------|
| 1 | **ひかえめ**（strict） | 提出者のみ | 希望の範囲内のみ |
| 2 | **おまかせ**（standard） | + 過去実績のある未提出者 | 提出者は希望内 / 未提出者は本人の過去傾向の曜日×時間帯（§6.6） |
| 3 | **とことん**（full） | 同上（全員） | 目標人数に足りない帯は希望・傾向の外にも伸ばす（営業時間内）。「①希望内 → ②未提出者の過去傾向 → ③希望外」の優先順位で埋める |

**全モード共通ガード（不変条件）**:

1. 募集期間外・休業日・営業時間外（boardRange外）・同一人物の時間重複は禁止（§9 最終ゲート）
2. **提出者の休み希望日（希望を出さなかった日）には割り当てない**（FR-14）。緩和されるのは時間帯のみで、日単位の意思は常に尊重する
3. 希望も過去実績もないスタッフ（新規の未提出者）は割当対象外
4. 提出者0人なら全モードで生成しない（未提出者だけのたたき台は作らない。`no_submitters`）
5. レート制限・ダイアログ・全体上書き反映のフローはモードによらず同一

**安全性の担保**: 「おまかせ」以上でAIが行った未提出・希望外の割当は、既存の確認事項ワーニング（`NOT_SUBMITTED` / `OUTSIDE_REQUESTED_TIME`。`src/domains/shift/assignmentWarnings.ts`）がすべて⚠フラグを立てる。おまかせ度を上げるほど「担当者が確認すべき箇所」が可視化される設計であり、たたき台思想（AIは提案・人が確定）は崩れない。生成後は⚠件数をサマリートーストで知らせる（§10.4）。

**UI文言（確定案）**:

| 段階 | 選択肢ラベル | 説明文 |
|------|------------|--------|
| 1 | ひかえめ | 提出された希望の範囲内だけで作ります |
| 2 | おまかせ | 未提出のスタッフにも、過去の傾向から入ってもらいます |
| 3 | とことん | 足りない時間帯は希望の外でも埋めます（要確認マーク付き） |

## 3. 全体アーキテクチャ

### 3.1 データフロー

```
[ShiftForm Shellヘッダー「AIで下書き」ボタン]（Jotai Provider内）
  └─ おまかせ度選択ダイアログ（ひかえめ / おまかせ / とことん。§2.3）→「下書きを作成」
       └─ await onGenerateDraft(mode)  ← ShiftBoardPage が注入するコールバック
            │
   ┌───── Convex 公開action: api.aiShiftDraft.actions.generateShiftDraft ─────┐
   │ 1) ctx.runMutation(internal.aiShiftDraft.mutations.prepareDraftInput)     │
   │      認証 + IDOR検証 + rateLimit("aiShiftDraft") + 入力収集 + 傾向前処理  │
   │ 2) 提出者0件 / 期間終了済み などの早期リターン判定                        │
   │ 3) prompt.ts で system / user / toolスキーマを構築（純粋関数）            │
   │ 4) anthropicClient.ts で Anthropic API 呼び出し（Haiku 4.5, tool強制）    │
   │ 5) tool_useブロックからJSON抽出（失敗 → parse_error）                     │
   │ 6) validateDraft.ts で検証。不正な割当は1件ずつドロップ（全体失敗にしない）│
   │ 7) return { status: "ok", assignments, droppedCount }                     │
   └───────────────────────────────────────────────────────────────────────────┘
            │
       ShiftBoardPage(useAiShiftDraft): assignments → ShiftData[] に変換
       （既存 buildShiftData を擬似データで再利用。§10.5）
            └─ ShiftData[] を戻り値でボタンに返す
                 └─ ボタン（Provider内）が useSetAtom(shiftsAtom) で全体上書き
                      └─ onShiftsChange 発火 → 既存の警告再評価・未保存検知が自然に働く
                           └─ 以降は既存の保存/確定ボタン（buildAssignments → saveShiftAssignments）
```

### 3.2 アーキテクチャ上の決定事項

| 決定 | 理由 |
|------|------|
| 公開actionの**同期呼び出し**（`useAction`） | 前例: `src/components/features/Line/useRedeemLineToken.ts` → `api.line.actions.redeemLineToken`。生成は単発・短時間なので同期で十分。mutation+scheduler+結果テーブル+購読方式は実装量が大きく、結果の一時保存が「DBに書かない」方針と衝突する |
| action冒頭で `internalMutation` に委譲 | `rateLimit()` は `rateLimits` テーブルへ書き込むため mutation ctx 必須で、actionから直接呼べない。`redeemLineToken` → `internal.line.mutations.validateLinkToken` と同型（`convex/line/actions.ts:45-76` / `convex/line/mutations.ts:70-77`） |
| **throwせずstatus unionを返す** | 既存actionの流儀（`redeemLineToken` 参照）。API例外はtry/catchで `api_error` に丸め、内部情報を漏らさない |
| DBへは一切書かない | `draftSavedAt` 等も触らない。上書き後はbaselineと差分が出るため、既存の未保存検知・離脱ブロック（`useBlocker`）が自然に働く |
| 反映はShiftForm内部（Provider内）で行う | `ShiftForm` はJotai `<Provider>` でラップされ（`src/components/features/Shift/ShiftForm/index.tsx:330-334`）、`shiftsAtom` はインスタンスごとに分離されている。親のShiftBoardPageから `useSetAtom(shiftsAtom)` は届かない |

├── trend.test.ts
├── validateDraft.ts    AI出力の検証パイプライン（純粋関数。§9）

- `prompt.ts` / `trend.ts` / `validateDraft.ts` は**純粋関数のみ**（DBアクセス・`_generated/server` インポート禁止）。`"use node"` 不要なので `logic` プロジェクトのvitestでそのままテストできる
- `actions.ts` のみ `"use node"`（Anthropic SDK使用のため）。前例: `convex/notification/actions.ts`, `convex/line/actions.ts`

### 4.2 型定義（types.ts）

```ts
import type { Id } from "../_generated/dataModel";
import type { ShiftSubmissionPattern } from "../_lib/submissionPattern";

/** AIが返す割当1件（検証済み）。saveShiftAssignments の assignments 引数と同形（positionIdなし=デフォルトポジション） */
export type DraftAssignment = {
  staffId: Id<"staffs">;
  date: string;        // "YYYY-MM-DD"
  startTime: string;   // "HH:MM"
  endTime: string;     // "HH:MM"
  optionId?: string;   // shiftType募集のみ
};

/** 曜日キー。shops.regularClosedDays のリテラルと一致させる */
export type DayOfWeekKey = "sun" | "mon" | "tue" | "wed" | "thu" | "fri" | "sat";

/** おまかせ度（§2.3）。API引数では未指定 = "strict" */
export type DraftMode = "strict" | "standard" | "full";

/** スタッフ個人別の過去傾向: 曜日 → 典型時間帯（§6.6） */
export type StaffTendency = Partial<Record<DayOfWeekKey, Array<[string, string]>>>;

/** 曜日×時間帯の目標人数（現募集パターンへ再投影済み。§6.2 手順5の出力） */
export type TrendTarget =
  // time / dateOnly: 人数が同水準の連続帯 [開始, 終了, 人数]
  | { kind: "bands"; byDay: Partial<Record<DayOfWeekKey, Array<[string, string, number]>>> }
  // shiftType: 区分IDごとの目標人数
  | { kind: "options"; byDay: Partial<Record<DayOfWeekKey, Record<string, number>>> };

/** スタッフの希望（提出者のみ）。パターンごとに形が変わる */
export type DraftRequests =
  | { kind: "time"; byStaffIndex: Record<number, Record<string, Array<[string, string]>>> } // date → [start,end][]
  | { kind: "shiftType"; byStaffIndex: Record<number, Record<string, string[]>> }           // date → optionId[]
  | { kind: "dateOnly"; byStaffIndex: Record<number, string[]> };                            // date[]

/** prepareDraftInput が action に返す生成入力一式 */
export type DraftInput = {
  recruitmentId: Id<"recruitments">;
  mode: DraftMode;
  period: { start: string; end: string; closedDates: string[] };
  pattern: ShiftSubmissionPattern;
  /** getBoardTimeRange(pattern) の結果。dateOnly時間補完・検証の枠 */
  boardRange: { startTime: string; endTime: string };
  /**
   * シフト対象スタッフ。index はプロンプト内の参照ID。
   * strict: 提出者のみ / standard・full: 提出者 + 過去傾向のある未提出者（§2.3）
   */
  staff: Array<{ index: number; staffId: Id<"staffs">; name: string; isSubmitted: boolean }>;
  requests: DraftRequests;
  /** 個人別過去傾向（staff index → 傾向。§6.6）。strictでは空 / standard=未提出者分のみ / full=全員分 */
  tendencies: Record<number, StaffTendency>;
  /** null = 過去実績なし（希望ベースモード。§6.4） */
  target: TrendTarget | null;
};

export type GenerateDraftResult =
  | { status: "ok"; assignments: DraftAssignment[]; droppedCount: number }
  | { status: "rate_limited"; retryAt: number | null }
  | { status: "unauthorized" }   // 未認証・所属外recruitment・削除済みを区別しない（列挙攻撃対策）
  | { status: "past_period" }    // 募集期間が終了済み（保存もできないため生成しない）
  | { status: "no_submitters" }
  | { status: "parse_error" }    // tool未使用・JSON壊れ・スキーマ不一致
  | { status: "api_error" };     // Anthropic API例外・タイムアウト

export type PrepareDraftInputResult =
  | { status: "ok"; input: DraftInput }
  | { status: "rate_limited"; retryAt: number | null }
  | { status: "unauthorized" }
  | { status: "past_period" }
  | { status: "no_submitters" };
```

### 4.3 mutations.ts — `prepareDraftInput`（internalMutation）

```ts
export const prepareDraftInput = internalMutation({
  args: {
    recruitmentId: v.id("recruitments"),
    shopId: v.optional(v.id("shops")),
    // 未指定は "strict"（後方互換・段階リリース用。§14.1）
    mode: v.optional(v.union(v.literal("strict"), v.literal("standard"), v.literal("full"))),
  },
  handler: async (ctx, args): Promise<PrepareDraftInputResult> => { ... },
});
```

認証は `ctx.auth.getUserIdentity()` を mutation 内で直接呼ぶ（Convexはactionから `ctx.runMutation` した先へ認証コンテキストを伝播する。convex-testの `t.withIdentity()` も同様に伝播する）。元設計書の「tokenIdentifierを引数で渡す」案は不要になるため採用しない。

処理ステップ（この順で早期リターン）:

| # | 処理 | 失敗時の返却 |
|---|------|------------|
| 1 | `ctx.auth.getUserIdentity()` — 未認証チェック | `unauthorized` |
| 2 | `users.by_authTokenIdentifier` でuser解決 → `resolveShopForUser(ctx, user, args.shopId)` でshop解決（`convex/_lib/functions.ts:43-55` の既存privat関数を **export して共有**）。`user.isDeleted` / `shop.isDeleted` も弾く | `unauthorized` |
| 3 | `ctx.db.get(recruitmentId)` → `!r \|\| r.isDeleted \|\| r.shopId !== shop._id` | `unauthorized`（Not found/Forbiddenを区別しない） |
| 4 | `isPastShiftPeriod(r.periodEnd)`（`convex/_lib/dateFormat.ts`）— 過去期間は保存もできないため生成不可 | `past_period` |
| 5 | `rateLimit(ctx, { name: "aiShiftDraft", key: shop._id })` — **Anthropic課金前に遮断** | `rate_limited`（`retryAt` を透過） |
| 6 | `shiftSubmissions.by_recruitmentId` を `take(SHIFT_BOARD_STAFF_LIMIT)` — 提出者集合。0件なら中断 | `no_submitters` |
| 7 | データ収集（下表）+ `trend.ts` で target を算出。standard・fullでは個人別傾向（§6.6）も算出 + DraftInput 組み立て | — |

**ステップ7の収集内容**（すべてindexedクエリ。件数上限は `convex/constants.ts` 準拠）:

| データ | クエリ | 上限 |
|--------|--------|------|
| スタッフ | `staffs.by_shopId_isDeleted (isDeleted=false)` → `isShiftTargetStaff` でフィルタ（`excludedFromShift` 除外。`convex/staff/service.ts`）。**strict**: 提出者集合と積を取る / **standard・full**: 提出者 ∪ 個人別傾向（§6.6）を持つ未提出者 | `SHIFT_BOARD_STAFF_LIMIT` (200) |
| 希望（time/shiftType） | `shiftSubmissionSlots.by_recruitmentId` | `SHIFT_BOARD_SHIFT_REQUEST_LIMIT` (2000) |
| 希望（dateOnly） | `shiftSubmissionDates.by_recruitmentId` | `SHIFT_BOARD_SHIFT_REQUEST_LIMIT` (2000) |
| 過去実績 | `recruitments.by_shopId_and_isDeleted_and_status_and_periodEnd` で `status="confirmed" && periodEnd < todayJST()` を `order("desc")` → `take(3)`（前例: `convex/dashboard/queries.ts:236-250` getDashboardPastRecruitments）。各期間の `shiftAssignments.by_recruitmentId` を `take(SHIFT_ASSIGNMENT_LIMIT)` | 3期間 × 2000件 |

補足仕様:

- **staff配列の並びと index**: 対象スタッフを `_creationTime` 順に並べ、`index` は 0 起点の連番。`staffId` はDTOに載せず、AIには `index` と `name` のみ渡す（ハルシネーション対策 + トークン節約）
- **「全休み提出」の扱い**: `shiftSubmissions` に行があるが希望スロット/日付が0件のスタッフは、staff配列に**含めた上で** requests を空にする。プロンプトの厳守ルール（希望のない日は割当禁止）により割当対象外になる。staff配列から外すと「提出したのに無視された」ように見えるログ調査が困難になるため含める
- 過去実績として現募集自身が混ざることはない（`periodEnd < today` 条件と、生成対象はステップ4で未来期間に限定されるため）

## 5. 入力DTO仕様

### 5.1 設計方針

- **過去実績の生データは渡さない。** 集計値（target）のみ渡すのが最大のトークン削減
- スタッフは `index`（整数）で参照させ、名前・IDをAIに出力させない
- 未提出者はDTOに**そもそも載せない**（FR-2の第一防御）
- キー名は1文字〜短縮形にしてトークンを節約する

### 5.2 プロンプトに埋め込むJSON（userプロンプト用のコンパクト表現）

```jsonc
{
  "period": { "start": "2026-07-16", "end": "2026-07-31", "closed": ["2026-07-20"] },
  "pattern": { "kind": "time" },
  // shiftTypeの場合: { "kind": "shiftType", "options": [{ "id": "opt_am", "name": "早番", "st": "08:00", "et": "13:00" }, ...] }
  // dateOnlyの場合: { "kind": "dateOnly", "board": ["09:00", "22:00"] }  ← 時間補完の枠
  "staff": [ { "i": 0, "n": "田中" }, { "i": 1, "n": "佐藤" }, { "i": 2, "n": "鈴木" } ],
  // i=2 は未提出者（requestsに現れない）。おまかせ以上でのみstaffに載る
  "requests": {
    // time: 日付 → 希望時間帯の配列（複数可）
    "0": { "2026-07-16": [["10:00", "15:00"]], "2026-07-17": [["10:00", "15:00"], ["17:00", "21:00"]] },
    // dateOnly: 日付のみ提出 → "day"
    "1": { "2026-07-16": "day" }
    // shiftType: 日付 → 希望区分IDの配列 例: { "2026-07-16": ["opt_am", "opt_pm"] }
  },
  "past": {
    // 個人別過去傾向（§6.6）: 曜日 → 典型時間帯。おまかせ=未提出者分のみ / とことん=全員分。ひかえめでは省略
    "2": { "mon": [["10:00", "15:00"]], "fri": [["17:00", "22:00"]] }
  },
  "target": {
    // time / dateOnly: 曜日 → [開始, 終了, 目標同時在籍人数] の帯
    "mon": [["10:00", "14:00", 2], ["14:00", "18:00", 3]],
    "tue": [["10:00", "18:00", 2]]
    // shiftType: 曜日 → 区分別目標人数 例: { "mon": { "opt_am": 2, "opt_pm": 3 } }
  }
  // 過去実績0件のときは "target" キー自体を省略（希望ベースモード。§6.4）
}
```

### 5.3 フィールド仕様

| キー | 型 | 説明 |
|------|----|------|
| `period.start` / `period.end` | `"YYYY-MM-DD"` | 募集期間（両端含む） |
| `period.closed` | `string[]` | `recruitment.shopClosedDates`。割当禁止日 |
| `pattern.kind` | `"time" \| "shiftType" \| "dateOnly"` | 現募集の提出パターン |
| `pattern.options[].id/name/st/et` | shiftTypeのみ | 現募集の区分。**AIに渡すのは現募集の区分のみ**（過去の廃止区分は渡さない） |
| `pattern.board` | dateOnlyのみ | `getBoardTimeRange(pattern)` の `[startTime, endTime]`。時間補完の許容枠 |
| `staff[].i` | 整数 | スタッフ参照index（0起点連番） |
| `staff[].n` | 文字列 | 表示名。AIが文脈を掴むために渡すが、出力には使わせない |
| `requests` | パターン依存 | **提出者の希望のみ**。キーは `staff[].i` の文字列化 |
| `past` | 曜日→時間帯 | 個人別過去傾向（§6.6）。キーは `staff[].i` の文字列化。**おまかせ以上のみ**（おまかせ=未提出者分 / とことん=全員分。誰の時間を伸ばすかの判断材料） |
| `target` | パターン依存 | §6で算出した曜日×時間帯の目標人数。キーは `"sun".."sat"`（`shops.regularClosedDays` のリテラルと同一） |

**おまかせ度によるDTO差分**:

| 要素 | ひかえめ | おまかせ | とことん |
|------|---------|---------|---------|
| `staff` | 提出者のみ | + 過去傾向のある未提出者 | 同左 |
| `requests` | 提出者全員分 | 同左 | 同左 |
| `past` | なし | 未提出者分のみ | 全員分 |
| `target` | あり（過去実績があれば） | 同左 | 同左 |

### 5.4 トークン試算

スタッフ20名 × 16日間の募集で、入力5〜8kトークン・出力2〜4kトークン。Haiku 4.5で1回あたり1円未満・数秒〜十数秒（NFR-1, NFR-2）。おまかせ以上では `past` の追加で入力が+1〜3kトークン増える（それでも1円強のオーダー）。

## 6. 傾向分析アルゴリズム仕様（trend.ts）

### 6.1 方針

**過去実績をパターン非依存の共通表現「曜日×30分スロットの在籍人数ヒートマップ」に正規化してから集計し、現募集の営業時間帯・パターンへ再投影する。** これにより「募集の時間帯が前回と変わった」「提出パターンが前回と変わった」ケース（FR-10）に頑健になる。

### 6.2 関数シグネチャと処理パイプライン

```ts
export type PastPeriod = {
  periodStart: string;              // "YYYY-MM-DD"
  periodEnd: string;
  closedDates: string[];            // その募集当時の shopClosedDates
  assignments: Array<{ date: string; startTime: string; endTime: string }>;
};

export type BuildTrendTargetInput = {
  pastPeriods: PastPeriod[];        // 直近確定3期間まで（新しい順でなくてよい）
  currentPattern: ShiftSubmissionPattern;
  currentBoardRange: { startTime: string; endTime: string }; // getBoardTimeRange(currentPattern)
};

export function buildTrendTarget(input: BuildTrendTargetInput): TrendTarget | null;
```

定数:

```ts
const SLOT_MINUTES = SHIFT_BOARD_TIME_UNIT_MINUTES;          // 30（convex/constants.ts:33）
const SLOT_COUNT = MAX_SHIFT_TIME_MINUTES / SLOT_MINUTES;    // 72（"29:00"のような翌日跨ぎ表記に対応。convex/_lib/time.ts:1）
```

曜日算出（Convexバックエンドはdayjs不可。TZずれしない純粋計算）:

```ts
const DAY_KEYS = ["sun", "mon", "tue", "wed", "thu", "fri", "sat"] as const;
const dayOfWeek = (date: string): DayOfWeekKey =>
  DAY_KEYS[new Date(`${date}T00:00:00Z`).getUTCDay()];
// "YYYY-MM-DD" をUTC固定で解釈するため実行環境TZの影響を受けない。
// 深夜帯（24:00超の endTime）は「シフト開始日の曜日」に帰属させる。
```

#### 手順1: 時間展開

過去の各 `shiftAssignments` 行を実時間区間 `[timeToMinutes(startTime), timeToMinutes(endTime))` として扱う。

> **元設計書からの簡略化**: `shiftAssignments` はどのパターンでも実時間（startTime/endTime）を必ず持つ（shiftTypeは確定時に `SHIFT_TYPE_TIME_MISMATCH` 検証で区分時間と一致することが保証済み。dateOnlyも確定時に担当者が時間を付けている）。したがって**当時のrecruitmentの `submissionPattern.options` を引いて時間展開する必要はなく、保存済み startTime/endTime をそのまま使う**。過去recruitmentドキュメントの取得目的は periodStart/End と closedDates のみになる。

#### 手順2: 曜日×30分スロット集計

各区間を30分刻みスロット `[floor(start/30), ceil(end/30))` に展開し、`count[dow][slot] += 1` で在籍人数を加算する。

#### 手順3: 期間按分（1営業日あたりの平均へ）

```
businessDays[dow] = Σ(過去期間) |{ date ∈ [periodStart..periodEnd] : dayOfWeek(date)=dow ∧ date ∉ closedDates }|
heat[dow][slot]   = businessDays[dow] > 0 ? count[dow][slot] / businessDays[dow] : (データなし)
```

- 母数は**各募集当時の** `closedDates` で除外する（現店舗設定の `regularClosedDays` は使わない。当時の実態が正）
- 期間の長さ・営業日数の違いをここで吸収する
- `businessDays[dow] === 0` の曜日は target から**曜日ごと省略**する（AIはその曜日を希望ベースで埋める）

#### 手順4: 現営業時間帯へクランプ + 最近傍補間

- 現募集の枠: `[bs, be) = [timeToMinutes(boardRange.startTime)/30, ceil(timeToMinutes(boardRange.endTime)/30))`
- 過去データの被覆範囲: `cover = [minSlot, maxSlot]`（全曜日を通じて `count > 0` の最小/最大スロット）
- 出力対象スロット `s ∈ [bs, be)` について:
  - `s ∈ cover` → `heat[dow][s]` をそのまま使う（過去にない狭い時間帯は自然にクランプされる）
  - `s < minSlot` → `heat[dow][minSlot]` で補間 / `s > maxSlot` → `heat[dow][maxSlot]` で補間（**現在の方が営業時間が広い**ケース。0埋めだと端の時間帯が誰も居ない下書きになるため最近傍値を使う）

#### 手順5: 現パターンへ再投影

- **現time / dateOnly**: `Math.round(heat)` して人数が同値の連続スロットを帯にまとめ、`[[start, end, count], ...]` を生成。`count === 0` の帯は出力しない
- **現shiftType**: 各optionの `[st, et)` に重なるスロット値の**時間加重平均を四捨五入**し、option単位の目標人数にする

  ```
  target[dow][optionId] = round( Σ(s ∈ option区間∩[bs,be)) heat[dow][s] × overlapMinutes(s) / Σ overlapMinutes(s) )
  ```

### 6.3 頑健性マトリクス（FR-10）

| 過去→現在の変化 | 扱い |
|------|------|
| 提出パターンが変わった（time↔shiftType↔dateOnly） | 手順1で実時間に正規化するため影響なし。出力側は手順5で現パターンに合わせる |
| 営業時間帯が広がった | 過去データがないスロットは最近傍補間（手順4） |
| 営業時間帯が狭まった | 単純クランプ（手順4） |
| shiftTypeのoption改廃 | 過去は保存済み実時間をそのまま使い、targetは現optionに按分。AIに渡すoption enumは現募集のもののみ |
| スタッフ総入れ替え | targetは「延べ配置人数」で個人非依存。AIは現在の提出者の希望内で埋めるだけ |
| 期間の長さが違う（週次→月次等） | 手順3の営業日数按分で吸収 |
| 過去確定期間0件（初回店舗） | `null` を返し希望ベースモードへ（§6.4） |

### 6.4 希望ベースモード（フォールバック）

`buildTrendTarget` が `null` を返した場合（過去確定期間0件、または全曜日で営業日数0）、生成は中断せず、プロンプトを「targetに近づける」指示から「**各提出者を希望範囲で無理なく割り当てる**（週の中で偏りすぎない・全員をまんべんなく）」指示に切り替えて続行する（§7.2）。

### 6.5 数値例

過去2期間（各期間に月曜が2営業日）で、月曜10:00-14:00に延べ8人分の30分スロット在籍があった場合:

```
businessDays[mon] = 4
count[mon][20..28) = 8         // slot20 = 10:00
heat[mon][20..28)  = 8 / 4 = 2.0
→ target（現timeパターン）: "mon": [["10:00", "14:00", 2]]
→ target（現shiftType、早番=09:00-13:00）: 09:00-10:00は補間 or 0、10:00-13:00は2.0 → 加重平均→ "mon": { "opt_am": 2 }
```

### 6.6 個人別傾向（buildStaffTendencies。おまかせ・とことん用）

「おまかせ」以上で使う、スタッフ個人の過去の入り方（曜日×典型時間帯）。targetと同じ正規化パイプライン（手順1〜2）を **staffId 別**に回した副産物として算出する。

```ts
export function buildStaffTendencies(input: {
  pastPeriods: Array<PastPeriod & {
    assignments: Array<{ staffId: Id<"staffs">; date: string; startTime: string; endTime: string }>;
  }>;
  targetStaffIds: Id<"staffs">[];   // 現在の在籍スタッフ（過去実績との照合対象）
  currentBoardRange: { startTime: string; endTime: string };
}): Map<Id<"staffs">, StaffTendency>;
```

アルゴリズム（閾値はすべて初期値。実データでチューニングする前提で定数化する）:

1. staffIdごと・曜日ごとに、過去期間で**その曜日に勤務した日数** `workedDays[dow]` と、勤務日における30分スロット別の出現日数 `slotDays[dow][slot]` を集計する
2. **曜日の採用判定**: `workedDays[dow] >= 2` かつ `workedDays[dow] / businessDays[dow] >= 0.3`（たまたま1回入っただけの曜日を「傾向」と見なさない）
3. **典型時間帯の抽出**: 採用した曜日について `slotDays[dow][slot] / workedDays[dow] >= 0.5` のスロット（勤務した日の半分以上で入っていた帯）を連続帯にまとめ、`currentBoardRange` でクランプする。帯が空になった曜日は不採用
4. 全曜日が不採用のスタッフは戻り値のMapに**含めない**（＝§2.3 共通ガード3「希望も過去実績もないスタッフは割当対象外」がここで自然に成立する）

### 7.2 systemプロンプト（全文テンプレート）

```
あなたは店舗のシフト作成アシスタントです。シフト担当者が手直しする前提の「たたき台」を作ります。

# 厳守ルール
1. スタッフは staff[].i に存在するインデックス番号だけで参照する。名前やIDを出力しない。
{strict時:
2. 割当は各スタッフの requests に示された希望の範囲内のみ。希望のない日への割当、closed の日への割当は禁止。}
{standard時:
2. requests のあるスタッフは、requests に示された希望の範囲内のみ。requests がなく past のあるスタッフは、past に示された曜日・時間帯の範囲でのみ割り当ててよい。requests のあるスタッフを希望のない日に入れること、closed の日への割当は禁止。}
{full時:
2. まず requests の範囲内で埋め、次に past のある未提出スタッフを past の範囲で使う。それでも target に足りない時間帯に限り、希望時間を同じ日の中で前後に伸ばしてよい（伸ばせるのは requests がある日だけ）。requests のあるスタッフを希望のない日に入れること、closed の日への割当は禁止。}
3. target（曜日ごとの目標人数）にできるだけ近づける。ただし超過よりも不足を許容する（たたき台のため、埋めすぎない）。
4. 勤務区分やポジションを創作しない。{shiftType時: 割当は options に列挙された区分IDから選ぶだけ。}
5. 必ず submit_shift_draft ツールを1回だけ呼ぶ。ツール呼び出し以外の文章を書かない。

# 出力単位
{time時:
- 各割当は date / start / end（"HH:MM"）で表す。start < end。希望時間帯の内側に収めること。}
{dateOnly時:
- 希望日（"day" と示された日）にのみ割り当てる。時間帯は target の傾向と pattern.board の範囲から妥当なものを補完する。}
{shiftType時:
- 各割当は date / optionId で表す。optionId はそのスタッフがその日に希望した区分IDから選ぶ。時間は出力しない。}

# 割り当ての方針
{targetあり時:
- target は過去実績から推定した曜日×時間帯の目標人数。曜日が target にない場合は他の曜日の水準を参考にする。}
{targetなし時（希望ベースモード）:
- 過去実績がないため、各提出者を希望範囲で無理なく割り当てる。特定の人に偏らせず、全員をまんべんなく使う。}
{full時:
- 希望外・傾向外の割当は「target に足りない時間帯」に限り、最小限にとどめる。}
- 同じスタッフを同じ日に重複して割り当てない。
- 全日埋める必要はない。判断に迷う枠は空けたままでよい（担当者が手直しする）。
```

`{...}` はパターン・target有無・おまかせ度（§2.3）による分岐。分岐込みの最終文字列を `prompt.test.ts` でスナップショット的に検証する。

## 8. AIクライアント仕様（anthropicClient.ts）

import type { DraftToolSchema } from "./prompt";

export type AiDraftClientRequest = { system: string; user: string; tool: DraftToolSchema };

/** tool_useブロックのinputを返す。tool_useがなければnull。API例外はそのままthrow（actionでapi_errorに丸める） */
export type AiDraftClient = (req: AiDraftClientRequest) => Promise<unknown | null>;

export const anthropicDraftClient: AiDraftClient = async ({ system, user, tool }) => {
  const client = new Anthropic({ apiKey: getAnthropicApiKey() });

};

## 9. 出力検証仕様（validateDraft.ts）

### 9.1 方針

**不正な割当は1件ずつドロップし、全体失敗にしない**（NFR-3）。ドロップ数は `droppedCount` で返し、フロントで情報トーストとして軽く通知する。

### 9.2 パース（Zod。schemas.ts に定義しactionで使用）

```ts
// schemas.ts（純粋Zod定義のみ）
export const rawDraftAssignmentSchema = z.object({
  i: z.number().int(),
  date: z.string(),
  start: z.string().optional(),
  end: z.string().optional(),
  optionId: z.string().optional(),
});
export const draftToolOutputSchema = z.object({ assignments: z.array(rawDraftAssignmentSchema) });
```

`safeParse` 失敗 → `parse_error`（配列全体が読めない場合のみ。個別要素の意味的不正は次の検証でドロップ）。

### 9.3 検証パイプライン

```ts
export function validateDraft(
  raw: z.infer<typeof draftToolOutputSchema>,
  input: DraftInput,
): { assignments: DraftAssignment[]; droppedCount: number };
```

各assignmentを以下の順でチェックし、最初に引っかかった時点でドロップ（ドロップ理由は `console.warn` でログに残す）:

| # | ルール | 判定 |
|---|--------|------|
| 1 | staff index解決 | `i` が `input.staff` の範囲内 → 実 `staffId` へ解決。範囲外はドロップ |
| 2 | 対象スタッフチェック（FR-2の二重防御） | 解決した `staffId` が `DraftInput.staff` に含まれる（staff配列＝§2.3のモード別許可対象そのもの。strictでは提出者のみ、standard・fullでは+傾向あり未提出者） |
| 3 | 日付チェック | `isValidIsoDateString(date)`（`convex/_lib/validation.ts`）∧ `period.start <= date <= period.end` ∧ `date ∉ closedDates` |
| 4 | **モード別の範囲チェック**（FR-3/12/13/14の中核。詳細は下の「ルール4詳細」） | 時間形式（`isSupportedShiftTime` ∧ `start < end`）は全モード共通。範囲の判定はモード×提出状態×パターンで分岐 |
| 5 | shiftTypeの時間付与 | `optionId` → 現募集optionの `startTime/endTime` を**サーバ側で付与**（AIが時間を出力していても無視する） |
| 6 | 同一 `staffId × date` の重複除去 | 既に採用済みの区間と時間が重なる割当をドロップ（shiftTypeは同一optionIdの重複をドロップ） |
| 7 | **最終ゲート** | 生き残った全件を既存 `validateShiftAssignments`（`convex/shiftBoard/validation.ts:77-160`。INVALID_DATE_FORMAT / OUT_OF_PERIOD / CLOSED_DAY / SHIFT_TYPE_* / OUT_OF_BOARD_RANGE / OVERLAP 等11種）に通し、issueが出た行をドロップして再実行（issue 0件になるまで。通常1周で収束） |

**ルール4詳細（モード別範囲チェック）**

提出者（requestsを持つスタッフ）:

| パターン | strict / standard | full |
|---------|------------------|------|
| time | その日の希望帯のいずれかに `[start, end)` が完全に収まる（`src/domains/shift/assignmentWarnings.ts` の `OUTSIDE_REQUESTED_TIME` と同じ判定基準） | **その日に希望があること** ∧ `boardRange` 内（希望帯からのはみ出しは許容し、⚠ `OUTSIDE_REQUESTED_TIME` に委ねる） |
| dateOnly | その日に希望提出あり ∧ `[start, end)` が `boardRange` 内 | 同左（dateOnlyは時間粒度の希望がないため差なし） |
| shiftType | `optionId` がそのスタッフのその日の希望区分集合に含まれる | **その日に希望があること** ∧ `optionId` が現募集の実在区分（非希望区分は許容し⚠に委ねる） |

未提出者（requestsを持たないスタッフ）:

| mode | 判定 |
|------|------|
| strict | すべてドロップ（そもそもstaff配列に載らないためルール2で落ちる） |
| standard・full | `tendencies` に本人のエントリがあること ∧ `boardRange` 内（shiftTypeは実在区分であること）。傾向の曜日・帯からの多少のずれはドロップせず ⚠ `NOT_SUBMITTED` に委ねる |

どのモードでも「requestsを持つスタッフの希望なし日」はドロップする（FR-14）。日付チェック（ルール3）と最終ゲート（ルール7）は全モード不変。

- `droppedCount` = 入力件数 − 採用件数
- クライアント反映後は既存 `computeAssignmentWarnings` が自動で再評価される。**strictでは**AI出力を希望範囲内に制約するため、反映後に警告が出る＝検証漏れの検知として機能する。standard・fullでは未提出・希望外の割当に⚠が付くのは仕様どおりの正常動作で、件数はサマリートースト（§10.4）で知らせる

### 10.5 AI結果 → ShiftData[] 変換

既存 `buildShiftData`（`src/components/features/ShiftBoard/ShiftBoardPage/index.tsx:77-236`、export済み）は `ShiftBoardData.shiftAssignments` から `ShiftData[]` を組み立てる。`DraftAssignment` は同形（`{staffId, date, startTime, endTime, optionId?}` + positionId）なので、**`shiftAssignments` をAI結果に差し替えた擬似データを `buildShiftData` に通して再利用**する:

```ts
// src/domains/shift/toDraftShiftData.ts（+ .test.ts）
export function toDraftShiftData(args: {
  data: ShiftBoardData;
  draftAssignments: DraftAssignment[];   // @/convex/aiShiftDraft/types
  staffs: StaffType[];
  dates: string[];
}): ShiftData[] {
  const defaultPositionId =
    args.data.positions.find((p) => p.isDefault)?._id ?? args.data.positions[0]?._id ?? "";
  const pseudo: ShiftBoardData = {
    ...args.data,
    shiftAssignments: args.draftAssignments.map((a) => ({ ...a, positionId: defaultPositionId })),
  };
  return buildShiftData(pseudo, args.staffs, args.dates);
}
```

## 12. エッジケース仕様

| ケース | 扱い |
|--------|------|
| 提出者0人 | サーバ `no_submitters` + フロントでボタンdisabled（二重防御） |
| 全員が「全休み」提出 | staff配列には載るがrequestsが空 → AIは割当できない → 全件ドロップまたは空配列 → 「生成結果が希望と合いませんでした」 |
| 過去確定期間0件（初回店舗） | 希望ベースモードで生成続行（§6.4） |
| 過去実績はあるが該当曜日の営業日0 | その曜日をtargetから省略。プロンプトが「他の曜日の水準を参考」と指示 |
| スタッフ総入れ替え | targetは個人非依存なので問題なし |
| 定休日・臨時休業日 | プロンプト `closed` で禁止指示 + 検証ルール3 + 最終ゲートCLOSED_DAYの三重防御 |
| 深夜跨ぎシフト（endTime > 24:00） | スロットは `MAX_SHIFT_TIME_MINUTES`（36h）まで確保。曜日帰属は開始日 |
| AI応答パース失敗（tool未使用/JSON壊れ） | `parse_error`。既存入力は上書きしない |
| APIタイムアウト・例外 | `api_error`。同上 |
| レート制限超過 | mutation段で遮断（Anthropic課金前）。`retryAt` 付きトースト |
| 希望はみ出し・未提出者・期間外・区分創作の出力 | 検証パイプラインで個別ドロップ（§9.3） |
| 全件ドロップ（valid 0件） | `ok` だが空配列 → 上書きせず「生成結果が希望と合いませんでした」 |
| 生成中に希望が更新された（購読でデータ変化） | 生成は都度スナップショット。担当者が手直しする前提で許容 |
| 生成中に画面離脱 | actionは完了するが結果は捨てられる（DBに書かないため副作用なし） |
| 未提出者に過去実績がない（standard・full） | 個人別傾向が算出されず staff / past に載らない → 割当対象外（§2.3 共通ガード3） |
| 提出者はいるが未提出者は全員実績なし（standard・full） | 実質strictと同じ結果になる（未提出者の割当候補が0のため） |
| モードを変えて再生成 | 全体上書きなので直前の生成結果は単純に置き換わる（都度おまかせ度選択ダイアログを経由） |
| 募集期間が過去 | `past_period` で生成しない（保存もできないため） |
| ANTHROPIC_API_KEY未設定 | `getAnthropicApiKey()` がthrow → actionのtry/catchで `api_error` |

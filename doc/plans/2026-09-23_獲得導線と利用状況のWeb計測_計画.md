# 獲得導線と利用状況のWeb計測 計画

## 文書の状態

- 状態: `Active`
- 作成日: 2026-09-23
- 対象: GTM container、GA4 property、`src/domains/webMeasurement/`、`src/lib/webMeasurement/`、計測イベントを送る画面
- 現在の正本: [全ページのWeb計測](../features/web-measurement.md)、[GA4・GTM・Clarity運用](../manual/ga4-gtm.md)

この文書は、登録数の減少を分析した結果から、GA4で何をどこで計測するかを決めた記録である。  現在仕様の正本ではない。  アプリ側の実装、GTM containerのインポートファイル、運用手順は2026-09-23に作成した。  GTMの公開、GA4 propertyの設定、アプリのリリースは未実施である。

## 背景

2026-09-23に、Search Console、Clerk、GA4の3つのデータを突き合わせた。

| 分かったこと | 根拠 |
|---|---|
| Google検索のクリックは、v0.1.7（2026-08-24公開）の前後4週間で327件から319件と横ばい | Search Consoleの日別データ |
| 同じ期間に、Clerkの新規登録は約77件から約47件へ減った | Clerkの週次グラフ |
| 検索クリックの44%は「シフトリ」の指名検索で、指名以外は最大でも週40件程度 | Search Consoleのクエリ別データ |
| AIアシスタント経由のセッションは350件で、エンゲージメント率は全チャネルで最も高い80% | GA4のチャネル別レポート |

登録の減少が「来訪者が減った」ためか「来訪しても登録しなくなった」ためかは、GA4で答えられなかった。  原因は次の計測側の不備である。

- 公開中のGTM containerには、Google tag（page view自動送信）とClarityしかなく、アプリがdataLayerへ送るCTAクリックとWeb VitalsをGA4へ渡すタグがない。
- キーイベントが1件もない。
- `route_family`が`auth`一つにまとまっており、登録ページとログインページを区別できない。
- 拡張計測機能のフォーム操作が有効で、スタッフの提出フォームの`form_start`が件数の大半を占める。
- 2026-08-24から2026-09-03までは、同意バナーで許可した利用者の公開ページだけを計測しており、この期間のデータがほぼ欠けている。

## 目的

| 問い | 使う計測 |
|---|---|
| Q1. どのチャネルから来た人が、登録ページまで進み、初期設定を完了したか | 最初のユーザーのチャネル、`page_view`、`select_content`、`setup_complete` |
| Q2. 料金を見て離脱しているか | `section_view`（料金）、登録系CTA、`setup_complete` |
| Q3. 記事、AIアシスタント、指名検索のうち、登録につながる入口はどれか | ランディングページ、最初のユーザーのチャネル、`setup_complete` |
| Q4. 既存の管理者は、どの画面をどの端末で使っているか | `page_view`の`route_family`と`route_area`、デバイス |
| Q5. スタッフは、提出を始めてから完了まで進んでいるか | `staff_submit`と`staff_submit_completed`の`page_view`、デバイス |
| Q6. シフト出力、ヘルプ検索、プラン申込みはどれだけ使われているか | `shift_export`、`help_search`、`plan_checkout_start` |

### 対象外

- 店舗、組織、人物を識別するIDをGA4へ送ること。  `user_id`とGoogle Signalsも使わない。
- 業務成果の件数をGA4で数えること。  提出、確定、新規登録店舗の件数は、Convex Analyticsを正本とする。
- LINE内ブラウザかホーム画面からの起動かの判定、配布リンクへのUTM付与。  2026-09-23の判断で不要とした。
- OAuthとLINE連携のcallbackのpage view。  通過するだけの画面なので送らない。

## 決定事項

| 項目 | 決定 |
|---|---|
| 運用手順の旧契約（synthetic page context、route familyのallowlist） | 廃止する。GA4とClarityの閲覧者はサービス運営者だけなので、分析しやすさを優先する |
| `page_location` | queryとhashを除き、IDを含むpathを固定pathへ置き換えたURLを送る。GA4のページ、ランディングページのレポートをそのまま使うため。未知URLと静的404は、入力されたpathを送らず`/404`にする（PR #937の自動レビュー指摘） |
| `page_referrer` | 初回はGA4の既定値（documentの参照元）、SPA遷移では直前の`page_location` |
| GA4のイベントデータ保持期間 | 14か月へ延長する |
| 拡張計測機能 | スクロールと離脱クリックだけを残す |
| 過去にGA4へ保存されたURLの削除依頼 | 行わない |
| developとpreviewの計測 | GTMのトリガーを`shiftori.app`のhostnameに限定し、本番のpropertyへ混ぜない |

## 追加・変更した計測

### route familyとroute area

`auth`を`auth_signup`、`auth_login`、`auth_password_reset`へ分けた。  `capability`を`staff_submit`、`staff_submit_completed`、`staff_view`、`staff_reissue`、`staff_register`、`staff_legal_consent`、`manager_invite`へ分けた。

全イベントに`route_area`（`public`、`auth`、`manager`、`staff`、`other`）を付けた。  `manager_invite`は管理者の登録導線なので`auth`に含める。

### イベント

| イベント | 送る場所 | パラメータ |
|---|---|---|
| `select_content` | 既存のTOPのCTAに、記事末尾の`article_cta`を追加 | `content_type`、`content_id` |
| `setup_complete` | `Dashboard/Setup`と`OrganizationCreation`の作成成功後 | `setup_kind`、`submission_pattern` |
| `section_view` | TOPの料金sectionの上端が画面の上60%へ入ったとき | `section` |
| `shift_export` | `ShiftExport/useExportDownload`でファイルの保存を始めたとき | `format` |
| `help_search` | ヘルプ検索の入力が1.5秒止まったとき | `has_results` |
| `plan_checkout_start` | `useStripeBillingController`でStripeへ移動する直前 | `plan` |

## GTMとGA4

GTM containerは、インポートファイル[ga4-gtm-container.json](../manual/ga4-gtm-container.json)として作成した。  Google tag、イベントごとのGA4イベントタグ8つ、hostnameで絞ったトリガー、dataLayer変数を含む。  既存のClarityタグは対象外である。

GA4 propertyでは、保持期間、拡張計測機能、カスタム定義、キーイベント（`setup_complete`）、除外する参照、Search Consoleとのリンクを設定する。  手順は[GA4・GTM・Clarity運用](../manual/ga4-gtm.md)に置いた。

GTMは、アプリのリリースより先に公開してよい。  現在のアプリが送る`page_view`、`select_content`、`web_vital`はすぐにGA4へ届き、新しいイベントはアプリの反映後に届き始める。

## Security Lens

- **Actor**: 見込み客、管理者、Capability linkを開くスタッフ、GA4・GTM・Clarityの閲覧者（サービス運営者のみ）、第三者のtag
- **Asset**: スタッフの提出・閲覧token、法務同意token、管理者招待token、OAuthの`code`と`state`、画面に表示される個人情報
- **Trust boundary**: browserからGTM containerを経て、GA4とClarityへ送る境界
- **Abuse case**: 新しいイベントのパラメータに店舗名や検索語が混ざる。  GTMのタグが、queryを含むURLを送る。
- **Server-side enforcement**: 計測の追加でpublic APIは増やさない。  tokenの権限は既存のサーバー側検証と有効期限のまま変えない。
- **Rate limit / idempotency**: 対象外。  イベントは成功後に1回だけ送る。
- **Lifecycle / recovery**: GA4のイベントデータを14か月保持する。  問題があればGTMの以前のバージョンを公開して止める。
- **Logs / PII**: serializerは型で決めた有限値だけを送る。  `help_search`は結果の有無だけを送り、検索語は送らない。  `page_location`はqueryとIDを除く。
- **Regression test**: 下の「テスト」のとおり。

## テスト

| 契約 | 主担当層 | 配置 |
|---|---|---|
| pathからroute family、`route_area`、集計用pathを決める | Logic Test | `src/domains/webMeasurement/routePolicy.test.ts` |
| 各イベントを決まったkeyの集合と有限値だけでserializeする | Logic Test | `src/domains/webMeasurement/events.test.ts` |
| 計測が有効なときだけ送り、SPA遷移で参照元を付け、callbackではpage viewを送らない | Frontend Unit Test | `src/lib/webMeasurement/index.test.ts` |
| シフト出力の成功時だけ`shift_export`を送り、失敗時と古いリクエストでは送らない | Frontend Unit Test | `src/components/features/ShiftExport/useExportDownload.test.tsx` |
| token付きのCapability documentでも、dataLayerにcredentialを載せない | E2E | `e2e/scenarios/measurement-enabled.test.ts`の`MEASUREMENT-BROWSER-01`と`02` |

初期設定、組織作成、プラン申込みは、成功後の1行の呼び出しなので個別のテストを追加しない。  ヘルプ検索と料金sectionも、表示を伴うcomponentのため自動テストを追加せず、GTMのプレビューで確認する。  GTMとGA4の設定は自動テストで証明できないため、運用手順の確認項目で確かめる。

# 所属なしユーザーのアカウント削除 実装計画

- 作成日: 2026-07-18
- 状態: 実装前
- 対象: 所属するグループがないログインユーザーによる、シフトリのアカウントとClerkユーザーの削除
- テスト方針: アカウント削除フローのE2Eは追加・実行しない

## 1. 結論

グループ削除とアカウント削除を別の操作として扱う。

グループを削除してもClerkユーザーとグローバルな`users`は削除せず、ほかに所属がなければログイン後に店舗登録画面を表示する。

店舗登録画面の登録カード直下に、主操作から視覚的に分離した「アカウントを削除」ボタンを置く。

ユーザーがこのボタンから明示的に削除を確定し、Clerkの再認証を通過した場合だけ、ローカル利用停止とClerkユーザー削除を開始する。

Clerk APIは外部副作用なので、受付transactionとdurable jobを分け、失敗やプロセス停止があっても再試行できる構成にする。

削除処理はFunction Test、Convex Scenario Test、Logic Test、StorybookのBehavior TestとVRTで検証する。

アカウント削除を操作するE2Eと、実Clerkユーザーを削除するprovider canaryは本計画に含めない。

## 2. 決定事項

| 項目 | 決定 |
| --- | --- |
| グループ削除時のClerkユーザー | 削除しない |
| グループ削除時のグローバル`users` | 削除しない |
| アカウント削除の入口 | 所属なしの店舗登録画面と、既存legacy削除状態の補助導線 |
| 店舗登録画面での配置 | 登録カードの外側、直下、デスクトップは右寄せ、モバイルは中央寄せ |
| 操作名 | 「アカウントを削除」 |
| 「完全に削除」の表現 | 使用しない |
| 本人確認 | Clerkのstrict reverificationをserverでも検証する |
| ClerkユーザーID | 公開入力から受け取らず、検証済みClerk sessionから確定する |
| 外部削除 | 専用の`accountDeletionJobs`で非同期実行する |
| 受付後の状態 | ローカル利用を即時停止し、公開の受付完了画面へ遷移する |
| 既存`users.isDeleted`行 | 自動復活もClerk削除への自動変換もしない |
| Clerk webhook | 初回実装では追加しない |
| E2E | アカウント削除フローには使用しない |

### 2.1 初回実装の対象外

- Clerk DashboardやClerk標準UIから直接削除されたuserをローカルへ同期するwebhook。
- 監査、同意、請求、法定保持対象、バックアップの即時物理削除。
- 過去にtombstone化されたローカルuserの自動復活。
- 既存`users.isDeleted`を根拠にしたClerk userの一括削除。
- グループまたは店舗データの削除を、アカウント削除jobへ再統合すること。
- アカウント削除のE2Eと実Clerk userを削除するprovider canary。

初回公開中はClerk標準の自己削除UIを別経路で露出せず、管理者がClerk Dashboardから直接削除する場合はローカル保持が残ることを運用上明記する。

アプリ外起点の同期が必要になった時点で、Clerk webhook、identity mapping、署名検証、再送冪等性を別計画として追加する。

## 3. 現状と解消する不整合

### 3.1 最後のグループ削除だけ挙動が異なる

現状は、管理者から全所属を外されたユーザーには有効な`users`が残るため、店舗登録画面へ戻る。

一方、自分で最後のグループを削除したユーザーは、`convex/organization/mutations.ts`で即時に`users.isDeleted: true`となる。

さらに`convex/deletionCleanup/mutations.ts`でも、対象外の有効所属がないユーザーをtombstone化する。

その結果、`convex/dashboard/queries.ts`と`src/components/features/AuthenticatedApp/AuthGuard.tsx`により、店舗登録画面ではなく`DeletedAccountState`へ送られる。

今回の完成形では、`users.isDeleted`を明示的なアカウント削除要求による利用停止へ寄せ、グループ削除では変更しない。

### 3.2 削除済みグループの履歴が再セットアップを妨げる

`convex/setup/mutations.ts`は、現在のユーザーが過去に作成したグループを`isDeleted`に関係なく検索し、1件でも存在すると初期セットアップを拒否する。

グループ削除後に店舗登録画面へ戻しても、このままでは「お店を登録する」が失敗する。

`organizations`へ`by_createdByUserId_and_isDeleted` indexを追加し、有効な自己作成グループだけをセットアップ重複として扱う。

### 3.3 通常のConvex mutationだけでは再認証鮮度を検証できない

Convexの`ctx.auth.getUserIdentity()`ではClerkの`fva`が除外されるため、通常のpublic mutation内で再認証鮮度を安全に判定できない。

削除受付は専用のConvex HTTP Actionにし、raw Clerk session tokenを`@clerk/backend`で検証する。

HTTP Action内で`auth.has({ reverification: "strict" })`を確認し、不足時はClerkの`reverificationErrorResponse("strict")`をそのまま返す。

フロントはHTTP呼び出しを`useReverification()`で包み、Clerkの本人確認が完了した場合だけ自動再送する。

## 4. 完成後のユーザーフロー

1. 所属グループがないユーザーがログインする。
2. 店舗登録カードの下に「シフトリを利用しない場合　アカウントを削除」が表示される。
3. 「アカウントを削除」を押すと確認ダイアログが開く。
4. 赤い確定ボタンを押すと、必要に応じてClerkの再認証が開く。
5. 再認証後、serverが最新の所属状態を再確認する。
6. 所属がない場合、ローカルユーザーを利用停止にし、Clerk削除jobを作成する。
7. UIは「アカウントの削除を受け付けました」と表示してサインアウトする。
8. workerがClerkユーザー削除を実行し、成功または安全な再試行状態へ収束する。
9. 同じメールアドレスで後日登録し直した場合は、新しいClerk subjectと新しいシフトリアカウントとして扱い、過去データを復元しない。

再認証をキャンセルした場合は削除要求を作らず、確認ダイアログへ戻す。

確定直前に別グループへ所属した場合はserverで拒否し、「所属情報が更新されたため削除できません。画面を更新してご確認ください」と表示する。

## 5. UI設計

### 5.1 店舗登録画面での配置

`WelcomeHero`は店舗登録という一つの主タスクだけを描くカードとして維持する。

削除入口は`WelcomeHero`の内側へ入れず、`SetupView`でカードと削除入口を一つの`Stack`にまとめる。

`ContentWrapper`直下の兄弟にすると既定の間隔が広すぎるため、カードとの間隔は`gap={3}`程度とする。

デスクトップではカード右端に合わせて右寄せし、モバイルでは通常フロー内で中央寄せにする。

固定配置や絶対配置は使わない。

削除操作は画面遷移リンクではなくダイアログを開くため、`a`要素ではなく`Button variant="plain"`を使用する。

想定する構造は次のとおり。

```tsx
<Stack gap={3}>
  <WelcomeHero {...welcomeHeroProps} />
  <Flex
    direction={{ base: "column", sm: "row" }}
    justify={{ base: "center", md: "flex-end" }}
    align="center"
    gap={{ base: 1, sm: 2 }}
    px={{ base: 1, md: 2 }}
  >
    <Text fontSize="sm" color="fg.muted">
      シフトリを利用しない場合
    </Text>
    <Button
      variant="plain"
      colorPalette="red"
      size="sm"
      minH={{ base: "44px", md: "auto" }}
    >
      アカウントを削除
    </Button>
  </Flex>
</Stack>
```

主CTAは引き続き「お店を登録する」とし、削除操作の色・面積・余白を主CTAより弱くする。

### 5.2 確認ダイアログ

既存の`src/components/ui/Dialog/index.tsx`とグループ削除ダイアログの構造を再利用する。

`role="alertdialog"`、赤いsubmit、キャンセル、loading、処理中のclose抑止を適用する。

メールアドレスやユーザー名の再入力は追加しない。

破壊操作の確認は、警告ダイアログとClerkの再認証で成立させる。

文言は次を基準とする。

- タイトル: `アカウントを削除`
- 強調文: `この操作は元に戻せません。`
- 説明1: `ログイン情報を削除し、シフトリを利用できない状態にします。`
- 説明2: `同じメールアドレスで登録し直しても、削除前のデータは復元されません。`
- 説明3: `過去の操作、同意、請求、監査などの記録は、法令や不正防止のため一定期間残る場合があります。`
- 確定ボタン: `アカウントを削除`
- キャンセルボタン: `キャンセル`

「完全に削除」は、監査記録、法定保持、バックアップまで即時消去される誤解を招くため使用しない。

### 5.3 受付後

新しい公開route`/account-deletion-accepted`を追加する。

受付成功後はToastだけに依存せず、サインアウト後も確認できる受付完了画面へ遷移する。

画面にはrequest ID、メールアドレス、Clerk user ID、job状態を表示しない。

- 見出し: `アカウントの削除を受け付けました`
- 説明: `このログインではシフトリを利用できません。処理の完了まで時間がかかる場合があります。`
- 補足: `同じメールアドレスで登録し直しても、削除前のデータは復元されません。`
- 操作: `トップページへ戻る`

`signOut()`が失敗した場合も、認証済み画面へ戻さず、クライアントの認証依存stateを破棄して受付完了画面へ移す。

### 5.4 既存legacy削除ユーザー

既存の`users.isDeleted`には、過去のグループ削除によって作られた行が含まれ得る。

これらを新しい仕様だけを根拠に自動復活させない。

`accountDeletionRequestedAt`がないlegacy行の`DeletedAccountState`には、同じアカウント削除ダイアログを補助導線として表示する。

明示的な削除要求を受け付け済みの行では再度の削除ボタンを出さず、受付中の文言とサインアウトだけを表示する。

## 6. フロントエンド構成

Dashboard固有ではなく認証済みアプリの複数compositionから利用するため、トップレベルfeatureとして配置する。

```text
src/components/features/AccountDeletion/
  index.tsx
  useAccountDeletionController.ts
  AccountDeletionTrigger.tsx
  AccountDeletionDialog.tsx
  submitAccountDeletionRequest.ts
  index.stories.tsx
```

責務は次のように分ける。

| ファイル | 責務 |
| --- | --- |
| `index.tsx` | controllerとViewの接続、表示variantの選択 |
| `useAccountDeletionController.ts` | ダイアログ状態、request ID、single-flight、Clerk再認証、受付後遷移 |
| `AccountDeletionTrigger.tsx` | 店舗登録画面用とlegacy画面用の入口表示 |
| `AccountDeletionDialog.tsx` | 確認表示とintent callbackだけを受けるView |
| `submitAccountDeletionRequest.ts` | `CONVEX_SITE_URL`へのHTTP要求と安全なresponse分類 |
| `index.stories.tsx` | desktop、mobile、dialog、running、error、Behavior Test |

controllerでは次を守る。

- ダイアログを開いた時点でUUID request IDを一つ生成する。
- Clerkによる自動再送とネットワーク再試行でも同じrequest IDを使う。
- キャンセル後に開き直した場合だけ新しいrequest IDへ切り替える。
- `useSingleFlight`で同期的な二重送信を防ぐ。
- 処理中はダイアログのclose、cancel、再submitを受け付けない。
- `useAuth().getToken({ skipCache: true })`でdefault session tokenを取得し、Convex用JWT template tokenは使わない。
- HTTP要求全体を`useReverification()`で包む。
- `useReverification()`が`null`を返した場合、または`@clerk/clerk-react/errors`の`isReverificationCancelledError()`に一致するerrorを投げた場合はキャンセルとして扱い、受付成功にも一般errorにも進めない。
- 受付成功後は既存の認証・店舗選択stateのreset手段を再利用し、局所的なatom resetを重複実装しない。

`src/configs/env.ts`の既存`CONVEX_SITE_URL`を利用する。

## 7. HTTP受付境界

`convex/http.ts`へ`POST /account-deletion/request`と`OPTIONS`を登録する。

HTTP Actionは`convex/accountDeletion/httpActions.ts`へ置く。

### 7.1 Request

```json
{
  "requestId": "UUID"
}
```

外部入力はrequest IDだけとし、`userId`、`clerkUserId`、メールアドレス、組織IDを受け取らない。

### 7.2 Response

| status | body | 意味 |
| --- | --- | --- |
| `202` | `{ "status": "accepted" }` | 新規受付または同じ要求の冪等再送 |
| `400` | 安全なerror code | body、content type、request IDが不正 |
| `401` | 安全なerror code | 未認証または無効なsession token |
| `403` | Clerk reverification response | 再認証が必要 |
| `409` | 安全なerror code | 有効所属あり、判定不能、または状態競合 |
| `429` | 安全なerror code | rate limit超過 |
| `503` | 安全なerror code | kill switchまたは必須設定不足 |

providerのresponse body、Clerk user ID、内部job状態を公開responseへ含めない。

### 7.3 HTTP Actionの検証順

1. `POST`以外を拒否する。
2. `Origin`を`APP_URL`のorigin allowlistと照合する。
3. JSON content typeと小さいbody上限を確認する。
4. `@clerk/backend`の`authenticateRequest()`でsession tokenを検証する。
5. `acceptsToken: "session_token"`と`authorizedParties`を明示する。
6. `RequestState.toAuth()`の結果で`isAuthenticated === true`、`tokenType === "session_token"`、`userId`と`sessionId`が存在することを確認する。
7. tokenのissuerが`CLERK_JWT_ISSUER_DOMAIN`と一致することを確認する。
8. 認証成立後のAuth objectで`auth.has({ reverification: "strict" })`を確認する。
9. 再認証不足ならClerk responseのstatus、body、headersを保ったままCORS headersだけを追加して返す。
10. 検証済みissuer、`auth.userId`、UUID request IDだけをinternal mutationへ渡す。

Clerkのsecretやsession tokenをConvex table、function引数のログ、例外メッセージへ残さない。

## 8. 受付transaction

`convex/accountDeletion/mutations.ts`にinternal mutationとして実装する。

処理順は次のとおり。

1. issuerとsubjectから既存と同じ`authTokenIdentifier`を構成する。
2. 同じ`authTokenIdentifier`を持つ`users`が複数ないことを確認し、重複時はfail closedにする。
3. 既存userにaccount deletion jobがあれば、request IDやjob statusにかかわらず新しいjobを作らず`accepted`を返す。
4. 既存jobがない新規受付だけserver側kill switchと必須設定を確認する。
5. issuerとsubjectから生成した非PIIの安定hash keyでrate limitを適用する。
6. 除外対象を持たない全所属scanを実行する。
7. `found`または`unknown`の場合はローカル状態を変更せず拒否する。
8. 既存userがあれば、PIIを既存tombstone helperで置換し、`isDeleted: true`と`accountDeletionRequestedAt`を設定する。
9. user行がなければ、最小のtombstone user行を作成し、同じ認証主体の古いJWTをセットアップへ通さない。
10. 同じtransactionで`accountDeletionJobs`を1件作成する。
11. commit後にworkerをscheduleし、公開DTOは`{ status: "accepted" }`だけ返す。

kill switchをoffにした後も、受付済み要求のnetwork再送には`202 accepted`を返す。

`actionRequired`を含む既存jobがある場合、clientから別request IDで新しいjobを作って自動回避させない。

必要な再開は原因を解消したoperatorだけがinternal functionから行う。

user行がない場合の仮メールアドレスはUUID request IDから`example.invalid`配下へ作り、insert後に既存のID由来tombstoneへ置き換える。

schema上必須の`role`には`manager`を設定するが、同じtransactionで`isDeleted: true`にし、すべての認証wrapperがrole判定より先に削除済みuserを拒否する契約を回帰テストする。

仮値にも元メールアドレス、Clerk user ID、token文字列を含めない。

## 9. 所属判定

`convex/deletionCleanup/service.ts`の`getOtherActiveUserAssociationStatus()`を一般化する。

グループ削除向けの除外あり判定と、アカウント削除向けの除外なし判定を同じbounded scanの上に置く。

アカウント削除では次を確認する。

- `organizationMembers`の`active`または`readOnly`
- `organizationPeople`の`active`
- 未削除`staffs`
- 未削除`shopMembers`
- 各関連先の親グループまたは店舗が有効であること

scan上限を超えた場合は`unknown`を返し、削除を許可しない。

店舗登録画面が表示されていることや、clientの`myShops.length === 0`は削除権限の根拠にしない。

### 9.1 受付後の再所属を防ぐ

受付transactionでuserをtombstone化してからClerk削除が完了するまでの間に、新しい所属を作れる抜け道を残さない。

認証済みuserを新しい`organizationMembers`、`organizationPeople.userId`、`staffs.userId`、`shopMembers`へ結び付けるすべてのwrite pathを確認する。

通常のセットアップに加え、管理者招待の承諾、人物とのアカウント連携、manager assignment、magic linkや登録導線を含め、対象`users.isDeleted`または`accountDeletionRequestedAt`がある場合は関連付け前に拒否する。

既存の認証wrapperで一元的に拒否できる経路はwrapperへ寄せ、匿名またはCapability起点で別userを関連付ける経路は対象userを再取得して同じ条件を検証する。

Clerk削除workerも外部APIを呼ぶ直前に除外なし所属scanを再実行する。

この最終scanが`found`または`unknown`の場合はClerk userを削除せず`actionRequired`とし、関連付け経路の不変条件違反として運用へ通知する。

## 10. `accountDeletionJobs`

既存の`deletionCleanupJobs`は店舗・グループcleanup専用なので拡張せず、専用tableを追加する。

外部送信の構造は`notificationOutbox`のclaim mutation、Node action、mark mutationを参考にする。

### 10.1 状態

```text
queued -> processing -> completed
           |     |
           |     +-> retrying -> processing
           +-------> actionRequired
```

`completed`を完了状態、`actionRequired`を自動処理の終端状態とする。

### 10.2 主なfield

| field | 目的 |
| --- | --- |
| `userId` | ローカルtombstone userとの関連 |
| `requestId` | 受付の冪等性 |
| `clerkUserId` | provider削除までだけ保持する一時的な対象ID |
| `expectedIssuer` | 認証instanceの取り違え防止 |
| `status` | `queued / processing / retrying / actionRequired / completed` |
| `phase` | `verifyProviderUser / deleteProviderUser / complete` |
| `version` | stale workerによる上書き防止 |
| `attemptCount` | bounded retry |
| `nextRunAt` | backoff後の再実行時刻 |
| `leaseId`、`leaseExpiresAt` | worker排他と停止回復 |
| `lastErrorCode` | PIIを含まない運用分類 |
| `providerUserVerifiedAt` | 初回404と削除後404の区別 |
| `deleteAttemptedAt` | 削除要求送信後の再開判定 |
| `providerDeletedAt`、`completedAt` | 完了時刻 |
| `createdAt`、`updatedAt` | 運用確認 |

`clerkUserId`と`expectedIssuer`はoptionalにし、完了後にjobから除去する。

古いJWTを拒否するための`authTokenIdentifier`は`users`のtombstoneへ残す。

### 10.3 index

- `by_userId_and_requestId`
- `by_userId`
- `by_userId_and_status`
- `by_status_and_nextRunAt`
- `by_status_and_leaseExpiresAt`

Clerk webhookを初回範囲に含めないため、`clerkUserId`による検索indexは追加しない。

### 10.4 保持とredaction

`clerkUserId`と`expectedIssuer`はprovider削除完了と同じtransactionでjobから除去する。

完了jobには`userId`、UUID request ID、status、試行回数、安全なerror code、時刻だけを残す。

完了jobは90日間の運用確認後に物理削除する。

`actionRequired`は解消まで保持し、再開して完了した時点から90日を数える。

90日という期間は`doc/features/account-deletion.md`に明記し、将来プロジェクト共通のretention policyが定まった場合はその短い方へ合わせる。

ローカル`users`のtombstoneと`authTokenIdentifier`は、古いJWT拒否と内部参照のため、このjob削除には連動させない。

## 11. Clerk削除worker

`convex/accountDeletion/actions.ts`を`"use node"`のinternal actionとして実装し、`@clerk/backend`の`createClerkClient()`を利用する。

provider client生成とerror分類を薄いadapterへ分け、テストでは外部通信を行わずtest doubleへ差し替える。

workerは次を守る。

1. mutationでjobをclaimし、lease IDとversionを取得する。
2. Clerk secret、publishable key、expected instance設定が揃わなければ外部APIを呼ばず`actionRequired`にする。
3. secret keyが指すinstance情報を取得し、`CLERK_EXPECTED_INSTANCE_ID`とissuer環境が一致しなければfail closedにする。
4. `getUser(clerkUserId)`で対象が現在のinstanceに存在することを確認する。
5. 確認成功をtransactionへ記録してから削除phaseへ進む。
6. `deleteAttemptedAt`を記録して`deleteUser(clerkUserId)`を呼ぶ。
7. 成功後に`completed`へ進め、jobのprovider識別子を消去する。
8. stale leaseまたはversion不一致のworkerは状態を書き戻さない。

初回`getUser()`が404の場合は、instanceまたは対象取り違えを成功扱いにせず`actionRequired`とする。

対象確認済み、かつ削除試行記録後の再実行で404となった場合だけ、既に削除済みとして`completed`へ進める。

429、5xx、timeout、接続切断は上限付き指数backoffで`retrying`とする。

認証失敗、権限不足、instance不一致、その他の恒久4xxは`actionRequired`とする。

providerの生error body、メールアドレス、Clerk user ID、secret、session tokenをログへ出さない。

cronには期限切れleaseの回収とdue jobの再開だけを追加する。

serverの`ACCOUNT_DELETION_ENABLED`をoffにした場合、新規受付は停止するが、受付済みjobは安全な終端へ進める。

`actionRequired`は自動再試行の終端とするが、原因解消後にだけ使うinternal operator functionを用意する。

operator functionはjob IDと期待versionを必須にし、provider対象が残っていることを再確認してから`retrying`へ戻す。

provider削除の証拠なしに手動で`completed`へ変更するfunctionは作らない。

PIIを返さないinternal probeで、status別件数、最古の更新時刻、error code別件数を確認できるようにする。

## 12. グループ削除契約の変更

今回の入口を全経路で成立させるため、次を同時に変更する。

### 12.1 受付時

`convex/organization/mutations.ts`から、最後の所属を失うactorの`users`を即時tombstone化する処理を削除する。

グループ、店舗、メンバー、人物、スタッフなどtenant配下の削除受付は従来どおり行う。

### 12.2 cleanup時

`convex/deletionCleanup/mutations.ts`から、人物、メンバー、作成者、スタッフ、shop member経由でグローバル`users`をtombstone化する処理を除く。

tenant配下の`organizationPeople`、`staffs`、LINE識別子、招待、session、Capability、通知などの匿名化・失効は維持する。

最終検証からも「専属userがtombstone済みであること」という条件だけを除く。

### 12.3 画面と文言

グループ削除ダイアログは「Clerkのログインアカウントは削除しません」という契約を維持する。

必要に応じて「ほかの所属がない場合は、次回ログイン後に新しい店舗を登録できます」と補足し、削除後の実挙動と文言を一致させる。

### 12.4 再セットアップ

`convex/setup/mutations.ts`の自己作成グループ重複判定を、有効な`isDeleted: false`のグループだけに変更する。

有効な所属や有効な自己作成グループが残る場合は、従来どおり重複セットアップを拒否する。

## 13. schemaとmigration

schemaはWidenとして次を追加する。

- `users.accountDeletionRequestedAt?: number`
- `accountDeletionJobs` tableと必要なindex
- `organizations.by_createdByUserId_and_isDeleted` index
- rate limit用のaccount deletion bucket

新しいtableとoptional fieldにはbackfillを行わない。

既存の`users.isDeleted`からClerk削除jobを作ってはいけない。

既存行の`isDeleted`は過去のローカル削除契約であり、Clerk削除への明示的同意ではない。

既存tombstone userを自動復活させてもいけない。

元のPIIが置換済みであり、削除理由も一意に証明できないためである。

公開前に、個人情報を返さないinternal probeで既存データの状況を必ず確認する。

- `isDeleted: true`かつ`accountDeletionRequestedAt`なしのuser数
- そのうち有効所属が見つかる件数
- 判定が`unknown`となる件数

復旧が必要になった場合は、対象条件と運用承認を持つ別計画・別migrationに分ける。

probeでlegacy行が1件でも見つかった場合は、「legacy状態を維持してClerk削除の補助導線だけ提供する」か、「別計画で明示的に復旧する」かをリリース前に記録する。

この判断が終わるまで、既存利用者を含めて全員が店舗登録画面へ戻るとは表現しない。

完了済みまたは本番実行予定の`m016`、`m017`を編集しない。

補正migrationが必要と判断された場合だけ、固定seriesの末尾へ新しい番号で追加する。

## 14. 環境変数とsecret管理

追加するConvex環境変数は次を想定する。

| key | 用途 |
| --- | --- |
| `CLERK_SECRET_KEY` | Clerk Backend API |
| `CLERK_PUBLISHABLE_KEY` | `authenticateRequest()` |
| `CLERK_EXPECTED_INSTANCE_ID` | secret取り違えのfail-closed確認 |
| `ACCOUNT_DELETION_ENABLED` | server側kill switch |

既存の`APP_URL`と`CLERK_JWT_ISSUER_DOMAIN`も受付検証に使用する。

frontendの表示制御には`VITE_ACCOUNT_DELETION_ENABLED`を追加し、server flagより先にUIを露出しない。

client flagは認可に使用しない。

`scripts/setupEnv.ts`へsecretを追加する前に、Convex CLIの値をcommand line argumentへ渡す現行方式を変更する。

`convex env set NAME`へ値をstdinで渡し、process list、shell history、成功・失敗ログへsecretを出さない。

実装レビューではchild processの引数にsecret値が含まれず、ログがkey名だけであることを確認する。

各deploymentでflagを有効にする前に、userを取得・削除しないread-only internal readiness actionを実行する。

readiness actionは必須env、issuer、publishable keyとsecret keyの組み合わせ、expected instanceだけを確認し、値そのものは返さない。

現在のClerk instanceで、Googleログインを含むすべての許可済みサインイン方法に対してpassword、email code、phone codeなどの再認証factorが少なくとも一つ利用できることも公開前条件とする。

再認証factorを利用できないユーザーには削除受付を成功扱いにせず、問い合わせ導線を示す。

## 15. セキュリティレビュー要点

| リスク | 対策 |
| --- | --- |
| 他人のClerk user IDを指定する | provider IDを公開入力にせず、検証済みsessionから確定する |
| 古い画面状態で所属中アカウントを削除する | 受付transactionで全所属を再走査する |
| scanの取りこぼし | bounded scanの`unknown`をfail closedにする |
| CSRF、漏れたsubdomain cookie | Bearer session token、`authorizedParties`、Origin allowlistを併用する |
| 盗まれた古いsessionによる破壊操作 | serverでstrict reverificationを必須にする |
| 二重クリック、Clerk自動再送、network retry | frontend single-flight、固定request ID、server idempotencyを併用する |
| Convex成功、Clerk失敗の不整合 | ローカル利用を先に止め、durable jobで外部削除を収束させる |
| 誤ったClerk instanceのuserを削除する | publishable/secret/issuer/expected instanceを照合してfail closedにする |
| 成功後の応答欠落 | provider確認済みとdelete試行済みを記録し、404を条件付きで成功扱いする |
| secret、token、PIIのログ流出 | safe error codeだけを保存し、生responseを記録しない |
| 古いJWTからの再セットアップ | `authTokenIdentifier`を持つローカルtombstoneを残す |
| 既存削除行からの意図しないClerk削除 | backfillを禁止し、明示的な新規要求だけjob化する |

# Stripe課金連携・4プラン化 実装計画

- 作成日: 2026-07-20
- 改訂日: 2026-07-20
- 対象: Free、Trial、Pro、Pro（先行登録特典・支払い不要）への再編とStripe Billing連携
- ステータス: 実装済み・Stripe公開前（mode off、環境変数・migration・deploy未実施）
- 上書き対象: 本文書の旧版にあったBusinessプラン前提
- 関連テスト計画: `doc/plans/2026-07-20_Stripeセキュリティ対策_テスト計画.md`

## 1. 結論

ユーザー向けのプラン表示は、次の4区分へ統一する。

| ユーザー向け区分 | 内部の主状態 | 利用人数 | 稼働店舗 | 有料機能 | Stripe |
|---|---|---:|---:|---|---|
| 無料 | `active.free` | 5名 | 1店舗 | 利用不可 | なし |
| トライアル | `trial` | 30名 | 5店舗 | Proと同じ | 継続登録した場合だけ |
| Pro | `active.pro` | 30名 | 5店舗 | すべて利用可 | あり |
| Pro（先行登録特典） | `complimentary.pro` | 30名 | 5店舗 | Proと同じ | 一切なし |

Businessプランは廃止する。

画面では「無料」「トライアル」と表示し、コード上のdiscriminatorは既存の`free`、`trial`を維持する。

通常課金の有料プランをPro一つにするため、ProとBusiness間の即時変更、日割り、pending update、期間末Scheduleは実装しない。

Trial、支払い確認中、猶予中、制限中は、商品プランを増やすものではなく、Pro契約のライフサイクルを安全に扱う内部状態として残す。

既存の`organizationBillingStates`を利用権限の正本とし、Stripeの画面、戻りURL、metadataだけではProを有効化しない。

署名検証済みWebhookを受けた後にStripe上の最新状態を再取得し、Customer、Subscription、Invoice、Price、provider世代が一致した場合だけ状態を更新する。

Stripe関連の環境変数は、実装では宣言、未設定時の安全停止、同期スクリプトへの追加まで行う。

API key、Webhook secret、Price ID、Portal Configuration IDの実値は、全実装と自動テストが完了した後にユーザーが登録する。

Proの価格、税、請求周期、未払いInvoiceの終端方針は未決定である。

これらが決まるまでCheckoutを公開せず、画面へ仮の価格を表示しない。

## 2. 固定する前提

### 2.1 利用人数

5名または30名は、既存仕様と同じ「利用人数」の数え方を使う。

管理者を別枠にせず、グループ内の同一人物は一人として数える。

未承認の追加招待が利用枠を予約する既存契約も維持する。

Freeは合計5名まで、Trial、通常Pro、無償Proは合計30名までとする。

### 2.2 管理者上限

今回の変更では管理者上限の指定がないため、現行値を維持する。

- Free: 有効管理者1名
- Trial、通常Pro、無償Pro: 有効管理者と有効な追加招待を合わせて5名

この値を変更する場合は、管理者交代、追加招待、削除後権限の契約を別途見直す。

### 2.3 Trial期間

Trialはグループ作成月とその翌月の末日までとする。

終了時刻は翌々月1日午前0時JSTである。

既存の`calculateTrialEndsAt()`はこの契約を満たしているため、期間計算は変更しない。

Trial中はProと同じ機能、30名、5店舗の上限を適用する。

### 2.4 先行登録特典

先行登録特典の対象は、現行の旧店舗モデルから移行したグループとする。

表示は「Pro」「支払い不要」「先行登録特典」とする。

対象者を登録日など別条件で追加する場合は、公開操作ではなく、別の明示migrationまたは管理用internal commandとして設計する。

### 2.5 初期の支払い方法

初期リリースの支払い方法はカードだけに限定する。

CheckoutとSetupIntentでもカードだけを許可し、非同期支払い方法は有効化しない。

カード以外を追加する場合は、対応Webhook、pending状態、返金と取消の契約を別途設計する。

## 3. 旧計画から削除するもの

次のBusiness固有実装は不要になる。

- Business ProductとPrice
- `STRIPE_BUSINESS_MONTHLY_PRICE_ID`
- ProからBusinessへの即時変更
- 差額請求と日割り
- `payment_behavior=pending_if_incomplete`によるpending update
- BusinessからProへの期間末Subscription Schedule
- `pendingActivation.fallback: pro`の追加
- `grace.resumePlan`の追加
- `customer.subscription.pending_update_applied`
- `customer.subscription.pending_update_expired`
- `subscription_schedule.*`
- 15人目でBusiness変更を促すUI
- Business変更予定と変更不成立通知
- ProとBusinessを選ぶ二択画面
- Business専用Story、Scenario Test、Price allowlist

次の仕組みは引き続き必要である。

- Trial終了時の初回請求
- Freeまたは制限中からProを始める即時Checkout
- ProからFreeへの期間末変更
- Pro更新失敗から14日間の猶予
- 支払い失敗後の制限と再契約
- 想定外Subscription終了
- Webhook署名検証、重複排除、順不同収束
- Stripe外部副作用の冪等性と回復
- 無償Proの完全なStripe隔離

## 4. 変更しない「business」識別子

リポジトリ内の`business`という語を一括置換しない。

次の識別子はBusinessプランではなく、店舗の業務データや業務通知を意味するため変更しない。

- `canWriteBusinessData`
- `businessWriteBlockReason`
- `businessNotificationCutoffAt`
- `businessNotificationCutoffVersion`
- 通知originまたはpurposeの`business`
- `BusinessHours`

実行済みmigrationのファイル名、既存conflict code、過去の監査イベントに含まれる`business`も履歴識別子として維持する。

削除対象は、料金プラン、利用上限、状態、UI表示を意味する`business`だけである。

## 5. 目標状態モデル

### 5.1 ユーザー向け区分と内部状態

内部では支払い処理の安全性のため、次の状態を維持する。

| 内部状態 | ユーザー向け表示 | 利用権限 |
|---|---|---|
| `trial` | トライアル | Pro相当 |
| `initialPaymentPending` | トライアル終了後・初回支払い確認中 | Pro相当 |
| `pendingActivation` | Pro反映待ち | Freeまたは制限中のfallback |
| `active.free` | 無料 | Free |
| `active.pro` | Pro | Pro |
| `complimentary.pro` | Pro、支払い不要、先行登録特典 | Pro |
| `scheduledChange(pro -> free)` | Free変更予定 | 期間末までPro |
| `grace.pro` | 支払い猶予中 | 14日間Pro |
| `restricted` | 契約制限中 | 閲覧、整理、復旧操作だけ |

支払い確認中、猶予中、制限中をプラン選択肢として表示しない。

プラン名と状態ラベルを分けて表示する。

### 5.2 Validatorの完成形

Narrow後の形は次のとおりとする。

- `organizationPaidPlanValidator`: `pro`
- `organizationActivePlanValidator`: `free | pro`
- `trial.selectedPaidPlan`: 未設定または`pro`
- `initialPaymentPending.plan`: `pro`
- `pendingActivation.plan`: `pro`
- `pendingActivation.fallback`: `free | restricted`
- `active.plan`: `free | pro`
- `complimentary.plan`: `pro`
- `scheduledChange.currentPlan`: `pro`
- `scheduledChange.targetPlan`: `free`
- `grace.plan`: `pro`
- `restricted.previousPlan`: 未設定または`free | pro`

Trialの`selectedPaidPlan`は、有料プランの選択肢ではなく、Trial終了後のPro継続を登録済みか示すために残す。

### 5.3 利用上限

`ORGANIZATION_PLAN_LIMITS`は次へ変更する。

| entitlement | 最大利用人数 | 最大稼働店舗 | 最大有効管理者 |
|---|---:|---:|---:|
| Trial | 30 | 5 | 5 |
| Free | 5 | 1 | 1 |
| Pro | 30 | 5 | 5 |
| 無償Pro | Proの値を使用 | Proの値を使用 | Proの値を使用 |

無償Pro用に別の上限定数を複製しない。

`complimentary.pro`は常にProのentitlementを参照する。

## 6. Widen-Migrate-Narrow

Business literalを即時削除すると、既存ドキュメントを持つdeploymentへSchemaを適用できない。

次の複数deployで移行する。

### 6.1 Deploy 1: Widenと新規書込み停止

一時的に旧Businessと新Proの両方をstorage validatorで受け入れる。

読み取り時は旧BusinessをProとして正規化する。

新規の公開操作、期限処理、テストseedはBusiness状態を書かず、Proだけを書く。

Business固有のプラン変更操作はこの時点で閉じる。

Free上限を5、Pro上限を30へ変更する。

旧Businessも移行中だけProと同じ30名、5店舗として扱う。

### 6.2 変換表

新しい`@convex-dev/migrations` migrationを追加し、次の形を変換する。

現時点の連番では`m018_organization_billing_business_to_pro.ts`を想定する。

実装時に新しいmigrationが追加済みなら、利用可能な次番号へ読み替える。

| 旧状態 | 新状態 |
|---|---|
| `trial.selectedPaidPlan: business` | `trial.selectedPaidPlan: pro` |
| `initialPaymentPending.plan: business` | `initialPaymentPending.plan: pro` |
| `pendingActivation.plan: business` | `pendingActivation.plan: pro` |
| `active.business` | `active.pro` |
| `complimentary.business` | `complimentary.pro` |
| `scheduledChange(business -> free)` | `scheduledChange(pro -> free)` |
| `scheduledChange(business -> pro)` | `active.pro` |
| `grace.business` | `grace.pro` |
| `restricted.previousPlan: business` | `restricted.previousPlan: pro` |
| `pendingActivation.restrictedFallbackState.previousPlan: business` | `pro` |

`scheduledChange(business -> pro)`を`active.pro`へ畳むときはbilling versionを進め、古いdeadline jobをno-opにする。

過去の監査イベントの`fromState`、`toState`、既存migration名、conflict codeは書き換えない。

未送信の課金通知に旧Business表記が含まれる場合は、対象を限定して取消または現在状態から再作成する。

店舗運営に関する通常の業務通知は取消対象にしない。

### 6.3 実行ゲート

merge前はdevelopment deploymentだけへローカルコードをpushし、専用runnerで一batchのrollbackを確認する。

```bash
npx convex run migrations/index:runM018 '{"dryRun":true}' --push --deployment dev
```

`DryRun: No changes were committed.`は一batchがrollbackされたことだけを示し、全件完走を示さない。
developへmergeすると`deploy.yml`が`migrations/index:run`の固定seriesを自動実行するため、手動の本実行を重ねない。
developでm018のstatusがsuccess、未解消m018 conflictが0件、cursor付き全page検証でlegacy Businessが0件になった後だけ本番向け`release:*`を進める。
本番releaseでも`release.yml`が固定seriesを自動実行する。
本計画の実装作業ではdry run、本実行、環境変数同期を行わない。

### 6.4 Free条件の再評価

Free上限が4名から5名へ広がるため、単純な文字列変換だけでは完了しない。

次の理由で制限中のグループだけを再評価する。

- `trialFreeConditionsNotMet`
- `freeConditionsNotMet`

有効管理者1名、利用人数5名以下、稼働店舗1件以下、保存済みFree選択が現在も有効という全条件を満たす場合だけ、追加する原因ベースcommandで`active.free`へ移行する。

現状の`applyFreeOrRestricted`はprivate helperであり、migrationから安全に再利用できるinternal commandは存在しない。

実装では、期待billing versionと対象restriction reasonを受け取り、Free選択、利用人数、管理者、店舗を再検証して、状態、権限、店舗status、監査、通知cutoffを一貫して更新する`reconcileFreeEligibilityAfterLimitChange`相当のinternal commandを追加する。

migrationからstateを直接patchせず、この共有commandまたは同じservice関数を使う。

支払い猶予切れ、支払い有効化失敗、想定外取消による制限は自動でFreeへ変更しない。

### 6.5 既存migrationの互換

`m012_organizations_add_complimentary_business.ts`と`m013_former_managers_remove_manager_access.ts`のファイル名、runner名、conflict codeは変更しない。

Widen期間に、未実行環境での新規書込みは`complimentary.pro`となるよう互換処理を追加する。

`m013`の判定は移行期間だけ`complimentary.business`と`complimentary.pro`の双方を受け入れる。

既存deploymentで完了済みのmigrationを再実行しない。

新規deploymentでm009から最新migrationまでを順番に実行するreplay testを追加する。

### 6.6 ProbeとNarrow

migration前後に次を件数確認する。

- 状態形ごとのBusiness literal件数
- 一つのグループに複数billing stateがある件数
- 無償ProにStripe対応がある件数
- BusinessからProの古いdeadlineが残る件数
- 旧Business表記を持つ未送信課金通知件数
- Free条件再評価の候補、成功、要手動確認件数

dry run、development実行、件数ゼロ確認、production実行の順に進める。

すべてのBusiness状態が0になった後にstorage validator、public DTO、frontend型からBusiness literalを削除する。

## 7. Stripe専用モデル

`organizationBillingStates`へStripe object IDを混在させない。

次の小さい専用テーブルを追加する。

### 7.1 `organizationStripeCustomers`

通常課金グループとStripe Customerの一対一対応を保存する。

`organizationId`と`stripeCustomerId`の双方へindexを作る。

無償Proでは行を作らない。

### 7.2 `organizationStripeSubscriptions`

終了済みを含むPro Subscriptionの世代を保存する。

主なfieldはCustomer ID、Subscription ID、Subscription Item ID、Price ID、status、trial end、current period end、cancel at period end、latest Invoice ID、generation、終了時刻、同期時刻とする。

終了済み世代を保持し、古い`invoice.paid`で制限後の契約を誤って復旧しない。

### 7.3 `organizationStripeOperations`

Customer作成、Trial Setup、trialing Subscription作成、即時Checkout、Free変更予約、予約取消、猶予終了取消、請求先メール同期を論理operationとして保存する。

request key、Stripe idempotency key、期待billing version、provider世代、status、attempt、retry時刻、lease、安全なerror codeを持つ。
Trial Subscription作成では、Customer ID、PaymentMethod ID、trial endの有無と値を作成前に不変snapshotとして保存し、同じrequest keyを別payloadへ差し替えない。

同じグループに有効な契約作成operationを一つだけ許可する。

### 7.4 `stripeWebhookEvents`

署名検証済みEventのID、type、API version、livemode、対象object ID、status、attempt、retry時刻、安全なerror code、受信・処理時刻だけを保存する。

raw body、署名header、完全なメールアドレス、カード情報は保存しない。

保持期間は暫定90日とし、本番切替前に確定する。
ただし、最新terminal世代の`cancelSubscription`と`stopInvoiceCollection`成功行は新しいprovider世代が作成されるまで日次で保持期限を延長し、再契約gateの証拠を先に削除しない。
不正または作成結果不明のTrial Subscriptionについては、作成元operationと専用取消operationを、一意なprovider終端snapshotが得られるまで削除せず24時間ごとに保持期限を再評価する。

## 8. Stripe契約フロー

### 8.1 Trial開始

グループ作成時にTrialを開始し、カード登録を求めない。

Trial終了時刻は既存のJST月境界計算を使う。

価格未決定またはStripe設定未登録の間も、Trialの利用権限には影響させない。

### 8.2 Trial中のPro継続登録

Proの価格、税、請求周期が確定するまで、この入口は無効化する。

確定後はHosted Checkoutの`mode=setup`で将来の支払い方法を登録する。

SetupIntentとCustomerを検証した後、Subscription APIでProのtrialing Subscriptionを作り、業務上のTrial終了時刻を`trial_end`へ設定する。

SetupIntentが`succeeded`であり、`usage=off_session`、PaymentMethodがcard、対象Customerに属することを再取得して確認する。

検証済み`setup_intent.payment_method`をtrialing Subscriptionの`default_payment_method`へ明示指定する。

必要に応じて同じPaymentMethodをCustomerの`invoice_settings.default_payment_method`へ同期するが、対象Customerとの一致を確認する前に設定しない。

CheckoutのSubscription modeにあるTrial終了時刻の制約へ依存せず、短い残期間でも同じ経路を使う。

trialing SubscriptionをTrial中に作ることで、終了時のInvoiceを通常のSubscription更新請求として扱い、Stripeの支払い回復経路へ接続する。

Subscription、Price、trial endが一致した後だけ`trial.selectedPaidPlan = pro`を保存する。

Trial終了前に継続を取り消した場合はtrialing Subscriptionを即時取消し、最新snapshotと取消Webhookを確認してから`selectedPaidPlan`を消す。

アプリ内のTrial権限とTrial終了時刻は変えない。

### 8.3 Trial終了

Pro継続登録済みなら、deadline jobは`initialPaymentPending.pro`へ移行する。

Trial中に作られた0円Invoiceの`invoice.paid`ではProを確定しない。

Trial終了時の対象InvoiceがpaidでSubscriptionがactiveなら`active.pro`へ移行する。

最初の支払い失敗は、その時刻から固定14日間の`grace.pro`へ移行する。

Pro継続未登録で、終了時点にFree条件を満たす場合は`active.free`へ移行する。

Free条件を満たさない場合は`restricted(reason: trialFreeConditionsNotMet)`へ移行する。

deadline jobとWebhookの到着順が逆でも、billing version、対象Invoice、Stripe最新snapshotで同じ最終状態へ収束させる。

現行policyは`trial`から`active.pro`または`grace.pro`への直接遷移を許可しないため、Trial期限と初回請求結果を扱う専用internal commandを追加する。

Webhookが期限jobより先に到着し、`now >= trialEndsAt`で対象Invoiceとprovider対応が一致する場合は、このcommandが`initialPaymentPending`開始と支払い結果適用を一つの原子的処理として行い、必要な監査を両方記録する。

Webhookが`trialEndsAt`より前に到着した場合は0円Invoiceとして権限へ反映せず、期限境界に関係するEventはdeadline後の再照合まで保留または再試行する。

deadline jobも同じcommandを呼び、期待versionが古い場合はno-opにする。

### 8.4 Freeまたは制限中からProを開始

Hosted Checkoutの`mode=subscription`を使い、その場で初回請求する。

Checkout作成前に`pendingActivation.pro`へ移し、Freeまたは制限中のfallback snapshotを保持する。

success URLだけではProを有効化しない。

対象InvoiceがpaidでSubscriptionがactiveと確認できた後だけ`active.pro`へ移行する。

即時支払い失敗、追加認証未完了、Checkout失効では猶予を設けず、元のFreeまたは制限状態へ戻す。

### 8.5 Pro更新失敗

現在世代の更新Invoiceが最初に失敗した時刻を保存し、14日後を猶予終了に固定する。

同じInvoiceの再失敗やSmart Retriesで猶予を延長しない。

猶予中はProの30名、5店舗と有料機能を維持する。

支払い成功を確認した場合は`active.pro`へ戻す。

猶予終了直前にStripeの最新InvoiceとSubscriptionを再照合する。

未払いなら制限へ移行し、現在Subscriptionの取消operationを必ず継続する。

Subscription取消後は、対象Subscriptionのopenまたはdraft Invoiceで`auto_advance=false`になり、自動回収が停止したことを最新snapshotで確認する。

未払いInvoiceを`void`にするか`uncollectible`にするかは会計上の意味が異なるため、価格、税、返金方針と合わせてlive公開前に決定する。

その方針に従い、対象Invoiceの終端処理を冪等なoperationとして実行する。

Subscription取消と未払いInvoiceの回収停止が確認できるまでprovider世代をterminal完了にせず、新しいSubscription作成を許可しない。

取消またはInvoice終端処理が失敗した場合は`actionRequired`として再試行と運用probeの対象にし、ローカルを制限しただけで放置しない。

terminal化後の旧世代に遅延`invoice.paid`が届いた場合は自動復旧せず、二重請求の可能性がある異常として新規契約を停止し、承認済み方針に従って返金、credit、または手動確認を行う。

再開は旧世代の回収停止を確認した後、新しいSubscription世代で行う。

### 8.6 ProからFree

Freeで残す管理者と店舗を先に確定する。

Subscriptionへ`cancel_at_period_end=true`を設定し、`scheduledChange(pro -> free)`へ移行する。

期間末まではProを維持する。

予約取消はStripeとローカル状態を同じ論理operationで戻す。

期間末に利用人数5名以下、有効管理者1名、稼働店舗1件以下、保存済み選択の有効性を再確認する。

満たす場合だけFreeへ移行し、満たさない場合は制限へ移行する。

### 8.7 想定外終了

Stripe Dashboardなどから現行Subscriptionが想定外に終了した場合は、直前の管理者と稼働店舗をsnapshotし、`restricted(reason: unexpectedCancellation)`へ移行する。

予定したFree移行、未完了Checkout、猶予終了後の取消とはoperation IDとprovider世代で区別する。

### 8.8 無償Pro

`complimentary.pro`では次を常に0とする。

- Stripe Customer
- Stripe Subscription
- Checkout Session
- Customer Portal Session
- PriceまたはInvoiceの組織対応
- 課金通知
- 再同期対象
- provider migration対象
- Stripe client呼び出し

公開Action、Webhook、手動再同期、削除処理のすべてで、Stripe clientを呼ぶ前に拒否する。

metadataが無償Proのorganization IDを名乗っても状態を変えない。

## 9. Webhook

### 9.1 URL

Stripeの宛先はCloudflare Pagesではなく、Convex HTTP Actionへ直接向ける。

```text
https://<development-deployment>.convex.site/stripe/webhook
https://<production-deployment>.convex.site/stripe/webhook
```

`https://dev-yps-crispy-carnival.pages.dev/`はCheckoutとPortalの戻り先であり、Webhook受信先ではない。

現在のdestinationがPages URLまたは未実装URLなら、受信routeをdevelopmentへデプロイするまで無効化する。

Stripe Connectは使用しないため、イベント宛先スコープは「お客様のアカウント」とする。

### 9.2 登録イベント

destinationには次の8イベントだけを登録する。

- `checkout.session.completed`
- `checkout.session.expired`
- `customer.subscription.created`
- `customer.subscription.updated`
- `customer.subscription.deleted`
- `invoice.paid`
- `invoice.payment_failed`
- `invoice.payment_action_required`

Proが一種類になるため、pending updateイベントとSubscription Scheduleイベントは追加しない。

非同期支払い方法を採用しない初期段階では、`checkout.session.async_payment_*`も追加しない。

### 9.3 受信処理

`convex/http.ts`へ`POST /stripe/webhook`を追加する。

method、Content-Type、署名header長、raw body上限を先に確認する。

raw bodyをJSON parseする前に、Stripe公式SDKの非同期署名検証を行う。

署名timestampの既定5分を維持する。

署名失敗時は400を返し、DB、scheduler、Stripe APIの副作用を0にする。

署名検証済みEvent IDを保存して処理Actionを予約し、速やかに2xxを返す。

後続ActionはEvent payloadだけを信用せず、Customer、Subscription、InvoiceをStripe APIから再取得する。

Customer、Subscription、Price、livemode、provider世代、期待billing versionが一致しない場合はfail closedにする。

Event IDの再送は一回に収束させる。

別Event IDや順不同配信は、最新Stripe snapshotと原因ベース状態遷移で収束させる。

API versionは登録済みdestinationと同じ`2026-04-22.dahlia`をコードとfixtureへ固定する。

### 13.2 実値登録の順序

1. `convex/convex.config.ts`ではStripe変数をoptionalで宣言する。
2. `STRIPE_BILLING_MODE`未設定を`off`として扱う。
3. `scripts/setupEnv.ts`へ変数名だけを追加し、値をログへ出さない。
4. Phase 1からPhase 6までを、Stripe実値なし、`off`で実装・自動テスト・デプロイする。
5. Pro価格、税、請求周期、返金方針を決める。
6. ユーザーがStripe test環境へProduct、Price、専用Portal Configurationを作る。
7. Codexが必要な変数名、取得場所、登録順、destination URLをhandoffする。
8. ユーザーがtest値を`.env`またはConvex Dashboardへ登録し、`pnpm convex:env:setup`を実行する。
9. ユーザーがdevelopment destinationを有効化し、`STRIPE_BILLING_MODE=test`へ切り替える。
10. sandbox canary完了後、productionへコードを`off`で先行デプロイする。
11. ユーザーがlive値を登録し、production destinationを有効化する。
12. 最後に`STRIPE_BILLING_MODE=live`へ切り替える。

Codexはユーザーの明示依頼なしに、secretまたはPrice IDを外部環境へ登録しない。

停止時は`.env`へ`STRIPE_BILLING_MODE=off`を明示し、`pnpm convex:env:setup`で対象deploymentへ同期する。
ローカルの変数を削除しただけでは同期スクリプトがその項目をskipするため、Convex側に残った`test`または`live`を解除できない。

`off`は、ユーザー起点の新しいCheckout、Portal、Pro継続登録、Free変更予約を止める。

`off`でも、既存契約の安全に必要な署名済みWebhook受信、再照合、猶予終了時のSubscription取消、Invoice自動回収停止、すでに予約済みのFree移行、前述した安全operationの再試行は継続する。

Trial Subscription作成応答とローカルID保存の間で停止した場合は、Customer内のSubscriptionを最大100件だけ取得し、operation metadataが一致するobjectを一意に確認できたときだけ保存して取り消す。
既存objectが見つからない場合の同一idempotency key再送は、operation作成から23時間未満で、trial endが10分超先にあり即時課金されないTrialに限定する。
即時課金型、23時間以上経過、100件超、複数候補、metadata不一致では新しいSubscriptionを作らず、要対応として証拠を保持する。

これらを止めると、画面では制限中なのにStripeが再請求する状態を作るためである。

一件でも通常Pro Subscriptionが存在した後は、`STRIPE_SECRET_KEY`と`STRIPE_WEBHOOK_SECRET`を単純に削除して停止しない。

鍵のローテーションや障害時も、旧鍵の失効、新鍵の反映、Webhook destination切替を手順化し、安全処理を継続する。

## 16. 運用と回復

Stripe専用のbounded cronで、未処理Webhook Eventを少数ずつ回収する。
operationは一律に再実行せず、安定したidempotency keyと最新課金versionを再確認できる`reconcileSubscription`、`cancelSubscription`、`stopInvoiceCollection`、請求先メール同期、期間末変更と取消の期限切れprocessingまたは期限到来retryingだけを回収する。
Checkout、Customer作成、Portalと、通常のSubscription作成はcron再実行の対象にしない。不正Trial Subscriptionの専用取消だけは、作成元との束縛を再確認して回収する。

最初から用意するinternal probeは次のとおりとする。

- Webhook status別件数と最古の未処理時刻
- retryingとactionRequired件数
- ローカルCustomerの重複、課金状態欠落、SubscriptionとのID、livemode、グループの不一致
- 一グループに複数の現在Subscriptionがある件数
- 通常Proなのに現在Subscription対応がない件数
- 無償ProなのにStripe対応がある件数
- status sampleに依存しない最終Webhook成功時刻
- 未完了Subscription取消
- 自動回収が止まっていない旧Invoiceと未完了のInvoice終端処理
- legacy Business状態件数
- m018の未解消重複課金状態conflict件数

Invoiceの状態、`auto_advance`、Stripe上のPrice active、Subscription ItemのPrice一致はローカルDBだけでは証明しない。
Stripe APIを再取得するreconciliation、取消、請求停止actionで確認し、照合不能を`actionRequired`へ残す。

legacy Businessの0件確認は、cursor付き`verifyLegacyBusinessStates`を`isDone: true`まで全page実行して証明する。
bounded probeの`observedCount: 0`かつ`hasMore: true`を全件0とみなさない。

無償ProにStripe対応が一件でもある場合はP0相当とし、`.env`へ`STRIPE_BILLING_MODE=off`を明示して`pnpm convex:env:setup`を直ちに実行し、それ以降のCheckoutとPortalを停止する。
変数削除だけではConvex側modeを解除できない。
全組織を公開Actionごとに走査する自動グローバルゲートは設けず、組織単位のprovider呼出し前拒否とこの運用停止を組み合わせる。

問題時は`STRIPE_BILLING_MODE=off`で新しい外部副作用を止める。

外部決済の事実を失わないため、Webhook受信と再照合は秘密情報が有効な限り継続する。

Priceローテーションでは、先に`off`を同期し、`trialSetupCheckout`、`createTrialSubscription`、`immediateProCheckout`の未完了件数と安全operationのbacklogを確認する。
新Priceを登録しても旧Priceはすぐarchiveせず、新規operationだけを開始時のPrice snapshotへ結び付け、既存Subscriptionは保存済みPrice IDで照合する。
test canaryと旧Priceの進行中operation drain後にだけ旧Priceをarchiveし、ローカルSubscriptionのPrice IDを一括書換えしない。
rollbackは`off`同期、旧Priceの有効性確認、`STRIPE_PRO_PRICE_ID`の復元、canary、mode再開の順で行う。

- `stripe` SDKをexact versionで追加し、API versionを固定する。
- Stripe専用4テーブルとindexを追加する。
- config、Price allowlist、operation、retry、probeを追加する。
- `POST /stripe/webhook`、署名検証、dedupe、再照合を追加する。
- Stripe環境変数をoptionalで宣言する。
- `STRIPE_BILLING_MODE=off`のままデプロイできるようにする。

### Phase 5: Pro契約フローとUI

- Trial Setupとtrialing Pro Subscriptionを実装する。
- SetupIntentのPaymentMethodを検証し、Subscriptionの既定支払い方法へ明示設定する。
- Trial終了時の初回請求を接続する。
- Trial期限jobと先着Webhookが共有する原子的な初回請求commandを追加する。
- Freeと制限中からの即時Pro Checkoutを実装する。
- Pro更新失敗、猶予、復旧、取消を実装する。
- 猶予終了時のSubscription取消、Invoice回収停止、選択済み終端処理を実装する。
- ProからFreeの期間末変更を実装する。
- Customer PortalとPrice確認を実装する。
- placeholder Toastを実Actionへ置き換える。
- 無償Proの負の契約を全層で維持する。

### Phase 6: 自動検証と`off`デプロイ

- Logic、Migration、Function、Scenario、UIテストを完了する。
- `pnpm lint`、`pnpm type-check`、`pnpm test`を実行する。
- Full Regressionを実行する。
- コードレビューと簡素化確認を行う。
- Stripe実値なし、mode offでdevelopmentとproductionへ安全にデプロイできることを確認する。

### Phase 7: ユーザーによるtest設定

- 価格、税、請求周期、未払いInvoiceの終端、返金、credit、Stripe Tax、Smart Retriesを確定する。
- ユーザーへ環境変数とStripe上の取得場所をhandoffする。
- ユーザーがtest Product、Price、Portal Configuration、環境変数を登録する。
- developmentの`.convex.site/stripe/webhook`を有効化する。
- 登録対象の8イベントが過不足なく設定されていることを確認する。
- `STRIPE_BILLING_MODE=test`へ切り替える。
- 正常支払い、失敗、3DS、Trial、重複、逆順Webhookをsandbox canaryで確認する。

### Phase 8: live切替

- productionコードを`off`で先行デプロイする。
- ユーザーがlive値を登録する。
- production用destinationを別に作成する。
- 最小canary後に`STRIPE_BILLING_MODE=live`へ切り替える。
- probeを確認して一般公開する。
- 問題時はmodeをoffへ戻す。

## 18. PR分割

1. 4区分の仕様、Widen、上限変更、新規Business書込み停止。
2. BusinessからProへのmigration、probe、Free再評価。
3. Narrow、状態機械簡素化、UI、Story、文書。
4. Stripe専用Schema、config、operation、Webhook。
5. Trial、Pro開始、更新失敗、Free変更、Portal。
6. 回帰テスト、運用probe、環境変数handoff、切替手順。

各PRは、価格未決定かつ`STRIPE_BILLING_MODE=off`でもdeploy可能にする。

## 19. 受入条件

- ユーザーが選べる通常プランは無料とProだけである。
- Trialと無償ProはProと同じ30名、5店舗、有料機能を利用できる。
- Freeは管理者を含む利用人数5名、稼働店舗1件までである。
- 通常Proは30名、5店舗までである。
- 31人目と6店舗目にBusinessを案内しない。
- UI、公開DTO、新規state、通知にBusinessプランが残らない。
- legacy Business状態がmigration後に0件である。
- 無償ProはStripe API、Stripe専用テーブル、課金通知がすべて0である。
- 価格未設定またはmode offでCheckoutを開始できない。
- success URLだけではProを有効化しない。
- 同一または順不同Webhookで状態が過去へ戻らない。
- 一グループにCustomerが一つ、現在Subscriptionが一つ以下である。
- Trial中0円InvoiceでProを確定しない。
- 14日猶予が再失敗で延長されない。
- 猶予終了後の旧Invoiceで自動復旧しない。
- 猶予終了時のSubscription取消と未払いInvoice回収停止が完了するまで、新しいSubscriptionを作らない。
- mode offでも既存契約の取消と再請求停止を継続する。
- Customer Portalからプラン変更と契約取消ができない。
- removed、readOnly、別グループ管理者がCheckoutまたはPortalを作れない。
- 環境変数の実値は実装完了後にユーザーだけが登録する。

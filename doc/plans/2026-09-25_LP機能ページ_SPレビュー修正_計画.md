## 背景

LPはスマホで高さ約11,700px（画面約16枚分）ある。  
1文の長さと改行はよく調整されていたが、次の問題が残っていた。

- 最初の画面の登録ボタンから末尾の登録ボタンまで、約10,000pxの間に登録ボタンがない。
- LPは「毎月やることは3つだけ」、機能一覧はSTEP 1〜4で、同じ毎月の流れの数が合わない。
- 「トライアル後も無料プランあり」とFAQの回答が、Freeの上限を超えたときの制限を伝えていない。
- 機能一覧が、LPの「主な機能」と同じ5件・同じ説明文で、しかもカードが大きく一覧しにくい。
- 同じ主張のくり返し、見出しと本文の重複、製品内の言葉、何が誰に届くかの抜けがある。

## 方針

- 文言の長さと改行は`.agents/skills/ui-architect/references/mobile-landing.md`に従う。  
  本文は1文20字、カードの本文は16字、カードの見出しは15字、2列のラベルは9字前後を目安にする。
- 既存sectionの文言、並び、大きさを直すことを中心にし、新しいsectionや共通基盤は作らない。
- 料金とトライアルの説明は、`doc/features/public-pages.md`の「公開する利用条件」と、ヘルプの`trial-end-and-free-plan.mdx`に合わせる。  
  課金処理、認可、データ境界は変えない。
- 上限の数値は`ORGANIZATION_PLAN_LIMITS`から読み、文言へ数値を複製しない。

## Phase 1 登録導線と料金の誤解をなくす

### 1-1. 途中の登録ボタン

- `HowItWorksSection`のステップカードの下に「無料ではじめる」を置く。
- `PricingSection`の`ProTrialNotice`の条件行の下に「無料ではじめる」を置く。  
  トライアル枠が「クレジットカード不要」を示しているため、ボタンの下に`TrialReassurance`は重ねない。
- ボタンの見た目は、スマホでは幅いっぱい、高さ56pxとし、Heroの主ボタンと同じにする。
- `publicCtaIds`に`flow_signup`と`pricing_signup`を加え、`MeasurementLink`で計測する。  
  GTMは`content_id`をそのまま送るため、container側の変更が要らないことを実装時に確認する。

### 1-2. トライアル終了後の説明

LPのFAQ「トライアル終了後も無料で使えますか？」の回答を、次のように変える（`src/components/features/LandingPage/faqs.ts`）。

| 変更前 | 変更後 |
|---|---|
| はい、Freeプランで無料で使えます。 | はい、Freeプランで無料で使えます。 |
| 上限は利用人数5名（管理者を含む）です。 | 上限は利用人数5名（管理者を含む）です。 |
| 店舗は1つ、管理者は2名までです。 | 店舗は1つ、管理者は2名までです。 |
| 有料プランを申し込まない限り料金はかかりません。 | 超える間は、募集などの操作を制限します。 |
| | 上限内に戻すか有料プランで再開できます。 |
| | 申し込まない限り、料金はかかりません。 |

最後の文は、今の「かかりま／せん。」の孤立も同時に直す。  
`TrialReassurance`の「トライアル後も無料プランあり」は変えない。  
Freeの上限は3条件あり、1行に収まらないため、数値は料金sectionとFAQで示すという既存の判断を保つ。

### 1-3. 料金の表記

- Freeの金額を、有料プランと同じ整形関数で表示する。  
  今は「¥0 /月（税込）」、有料は「¥X,XXX(税込) / 1か月」の形で、括弧、単位、順番が違う。  
  Freeは`formatCurrencyAmount`と`formatBillingUnit`を使い、「¥0 / 1か月」とする。  
  0円に税区分は意味を持たないため付けない。
- 料金sectionのリードを、機能一覧と同じ説明にそろえる。

| 変更前 | 変更後 |
|---|---|
| どのプランでも基本機能は同じです。人数と店舗数に合わせて選べます。 | どのプランでも基本機能は同じです。違いは人数・店舗数・管理者数の上限です。 |

## Phase 2 流れの数と機能一覧をそろえる

### 2-1. 毎月の流れを3ステップにそろえる

LPの「毎月やることは3つだけ」（募集、組む、確定）を正とし、機能一覧をこの3つで分ける。

| 機能一覧の見出し | 並べる機能 |
|---|---|
| STEP 1 シフトを募集する | 希望シフトの回収、提出状況の確認と自動催促 |
| STEP 2 シフトを組む | シフト表の作成 |
| STEP 3 シフトを確定する | 確定シフトの共有 |
| 店舗とスタッフの管理 | 複数店舗・スタッフ管理 |

- `FeatureCard`の`stepNumber`と「STEP n」の表示を外し、番号は見出しだけで示す。
- 見出しと機能の対応は`FeaturesHub.tsx`の定数で持ち、`productFeatureContent.ts`には入れない。
- 「毎月のシフト作成で使う機能／使う順に並べています」の見出しは、上の分け方に置き換える。

### 2-2. 機能一覧に、LPにない情報を載せる

- 機能一覧のカードに、その機能の「できること」の見出し（`capabilities[].title`）を箇条書きで並べる。  
  LPの「主な機能」は名前と1文だけなので、機能一覧は「何ができるか」を全部見渡せるページにする。
- カードのイラストを外し、アイコン、名前、1文の説明、できることの一覧、「詳しく見る」の順にする。  
  イラストは各機能ページのHeroで見せる。
- スマホの高さは、5件で約2,500pxから約1,500pxになる見込みである。
- LPの「主な機能」の6枚目「機能一覧／すべての機能を確認できます」のカードを外し、グリッドの下に「機能一覧を見る」のテキストリンクを置く。
- 複数店舗の説明「まとめて管理できます」を、「掛け持ちも1名で管理できます」に変える。

### 2-3. 機能ページの関連リンクを短くする

- 「関連する機能」を、2-2と同じ小さいカード（できることの一覧なし）にする。  
  イラスト付きカード3枚の約1,500pxが、約350pxになる見込みである。
- ヘルプへのリンク一覧の見出し「使い方」を「ヘルプ」に変え、手順sectionの「使い方」と区別する。
- 2-2と2-3で同じカードを使い、今の`FeatureCard`をこの形に置き換える。  
  イラスト付きの大きいカードは使う場所がなくなるため残さない。

## Security Lens

- Actor: 未ログインの訪問者
- Asset: なし。表示するのは公開済みの料金、上限、機能の説明だけである。
- Trust boundary: 変わらない。公開ページはbuild時に静的生成し、Convex APIを呼ばない。
- Abuse case: 料金やトライアルの説明と実際の挙動が食い違い、利用者が誤認すること
- Server-side enforcement: 変えない。Free上限超過時の操作制限は既存のserver側の判定のまま
- Rate limit / idempotency: 対象外
- Lifecycle / recovery: 対象外
- Logs / PII: 追加する計測は登録済みのCTA IDだけを送り、個人情報を含めない
- Regression test: FAQの構造化データのLogic Testと、料金sectionのStoryで確認する

## 追加の修正（実装後のレビュー）

2026-09-25に、実装した画面をユーザーが確認し、次の指摘を受けて直した。  
Phase 3の「活用例sectionを残す」判断は、この指摘で変えた。

| 指摘 | 原因・判断 | 修正 |
|---|---|---|
| PCでsection間の余白が少ない | 課題、毎月の流れ、提出方法、活用例、主な機能のsectionが`py={{ base: 14, md: 18 }}`を指定していた。Chakraに`18`の余白tokenがないため、PCでは72pxではなく18pxになっていた | `md: 20`（80px）に直した |
| 「無料ではじめる」ボタンが唐突 | 毎月の流れのカードの下に、ボタンだけを置いていた | 末尾の登録sectionと同じ背景の`MidCtaSection`を毎月の流れの直後に置き、見出し「スタッフへの連絡は／シフトリに任せよう」、ボタン、無料の条件を並べた |
| 提出方法の下の機能説明が唐突 | 「前回と同じ希望を入力」「LINEを使わない人はメールで」「何度でも出し直せる」を見出しなしで並べていた。いずれもHero、FAQ、回収ページで説明済み | LPから外し、回収ページへのリンクに任せた |
| 業種の一覧は提出方法のsectionに入れたほうがよい | 提出方法と業種の相性を、別のsectionで2回示していた | 活用例sectionを消し、提出方法のカードに「向いているお店」として業種の画像と名前を並べた。統合したsectionのidを`use-cases`にし、headerとfooterの「活用例」の移動先を保った |
| 機能ページがスカスカ | 画面の画像がないページが2つあり、画像のない「できること」と「使い方」はカードの中身に対して余白とアイコンの行が大きかった | 下の2つを行った |

機能ページは、並べ方を詰める案と実際の画面を足す案を一度に行った。

- 困りごとは大きなsectionにせず、「できること」の前の帯にした。
- 画像のない「できること」は、アイコンを見出しの左に置いた2列の一覧にした。
- 「使い方」は、番号を見出しの左に置き、PCでは3つを線でつないだ。
- 画像がなかった催促ページと複数店舗ページに、実際の画面を2枚ずつ足した。

| 画面 | 元のStory | 使う場所 |
|---|---|---|

## 実装結果

- Phase 1〜4を実装した。Phase 5は計画どおり行っていない。
- 登録ボタンの位置は、TOPの幅360pxで上から269px、3,934px、7,649px、10,388pxになった。  
  登録ボタンのない区間は、約10,000pxから最大約3,700pxに縮んだ。
- TOPの高さは幅360pxで約11,700pxから11,437px、回収ページは6,543pxから5,797pxになった。
- `pnpm lint`、`pnpm type-check`、変更範囲のLogic TestとStorybookのplay、`pnpm build`が成功した。  
  buildしたTOPのFAQPage構造化データに、新しいFAQの回答が入っていることを確認した。
- 幅360pxと390pxで、今回変えた文言に3行以上の要素と末尾3字以下の孤立がないことを測った。
- 追加の修正の後、TOPの高さは幅360pxで11,036px、PCで各sectionの上下の余白は80pxになった。  
  複数店舗ページの「管理者を招待して、作業を分担できます」は末尾の1字が次の行に落ちたため、「管理者を招待して分担できます」に短くした。

# VRT・E2EレポートのCloudflare R2移行

作成日: 2026-09-05  
状態: Active（実装・PR確認中。repositoryのSecrets二つ・Variables三つを使うR2実接続確認は成功。baseline初期移行とPRのCI・公開を検証中）

VRT・E2Eの公開先を`hosting-pages`のGitHub PagesからCloudflare R2へ移す。  
公開対象を絞り、PRのclose／mergeで削除することで無料枠を目安に運用し、少額の超過は許容する。

比較元の全画像も公開してよいというユーザー判断に従い、公開bucket一つとread/writeキー一組で運用する。  
レポートと基準画像はログインなしで閲覧可能とし、非公開bucket、read-onlyキー、baseline取得専用jobは設けない。
公開URLにはCloudflareの`r2.dev`を使い、カスタムドメインやDNS設定は今回の初回導入に含めない。  
低コストと保守の容易さを優先し、既存CIとR2で完結させる。

## 合意した保存契約

| 対象 | R2 | GitHub Actions Artifact |
|---|---|---|
| PRのVRTレポート | HTML・結果データ・差分／追加／削除の確認に必要な画像を公開。PR終了時に全世代を削除 | 撮影した全画像を現行どおり3日保持。比較レポート一式も3日保持する |
| PRのE2Eレポート | 動画本体と動画への参照を除いたレポートを公開。PR終了時に全世代を削除 | privacy検査済みの完全版を現行どおり30日保持。生成された動画があれば残す |
| develop／mainのVRTレポート | 各branchの最新の公開完了一式を保持 | 比較レポート一式を3日保持する |
| develop／mainのVRT比較元画像 | 同じ公開bucketで全画像の圧縮archiveを保持 | 各runの撮影画像は上記の保持期間に従う |
| 公開管理メタデータ | 同じ公開bucketに、世代の確定・取得・削除に必要な最小情報を置く | 元Artifactの内部ファイルをそのまま公開しない |

PR終了による削除はR2の対象データに適用し、Artifactはそれぞれの保存期限まで残す。  
再open時は新しいCIでレポートを作り直す。

現在のCI E2Eのcoreシナリオは録画を無効にしているため、この移行で動画は新たに生成しない。  
認証情報や個人情報を扱うシナリオの録画設定を維持し、録画対象を増やす判断は別の変更とする。

対象はシフトリのレポート公開・比較元画像・削除処理とする。  
アプリのCloudflare Pages配信、Convexのschemaや各deployment、`hosting-pages`の`online-draft`など他用途は対象外とする。

## 保存先と公開方法

R2 Standardの公開bucketを一つ用意する。  
下記の名前は説明用の仮称であり、実装では登録済みの`REPORT_R2_PUBLIC_BUCKET`を使う。

| 保存先 | 仮称 | 内容・アクセス |
|---|---|---|
| 公開bucket | `shiftori-test-reports` | 選別したレポート、比較元画像の全件archive、最小の公開完了メタデータ。`https://pub-….r2.dev`から匿名で取得可能 |

レポートは`vrt/`と`playwright/`、比較元は`baselines/{branch}/{runId}-{attempt}.zip`、確定メタデータは`state/`配下に分ける。  
これは保存・削除対象を区別するためのprefixであり、公開範囲の境界には使わない。

PRの公開先は`{type}/pr-{number}/{runId}-{attempt}/index.html`、branchは`vrt/branches/{branch}/{runId}-{attempt}/index.html`とする。  
`type`は`vrt`と`playwright`、branchは`develop`と`main`に限定する。
PRコメントは公開成功時に最新runのURLへ更新する。  
R2のディレクトリindex解決に依存せず、リンクは明示的に`index.html`へ向ける。

公開完了メタデータは現行の`.report-meta.json`に相当する最小情報とし、repository、PRまたはbranch、source SHA、run ID／attempt、公開prefix、ファイル数・合計byte数を持つ。  
branchでは対応するbaseline archiveのkeyとchecksumも同じメタデータへ収め、レポートと比較元画像を同じrunに対応付ける。
メタデータも公開される前提で、上記の管理情報だけをtrustedな公開処理が生成し、秘密値や認証stateは含めない。

公開URLは`REPORT_PUBLIC_BASE_URL`から読み、アプリと別originの`r2.dev`を使う。  
R2のPublic Development URLを有効化し、カスタムドメインの接続やCloudflare Cache Rulesの設定は行わない。
公開objectには`Cache-Control: no-store`を付け、ブラウザ等による古いレポート・確定メタデータの再利用を防ぐ。
HTML、画像、JSONなどへ正しい`Content-Type`を設定する。  
同一origin内でレポートを構成し、不要なCORS許可は追加しない。

`r2.dev`は開発用途向けで、可変のリクエスト制限と帯域制限がある。  
レポート閲覧とCIのbaseline取得がこの制限を受ける前提で運用し、制限を回避するWorkerや別の配信基盤は追加しない。[R2の公開URL](https://developers.cloudflare.com/r2/buckets/public-buckets/#public-development-url)、[r2.devの制限](https://developers.cloudflare.com/r2/platform/limits/#rate-limiting-on-managed-public-buckets-through-r2dev)

将来、制限による失敗が続く場合にだけカスタムドメインへの切替を検討する。  
切替時はドメイン接続とキャッシュbypassを設定し、`REPORT_PUBLIC_BASE_URL`を更新する。保存先や認証キーは変更不要で、以降のCIが新しいURLを使う。過去のPRコメントのURLは再公開時に更新する。  
キャッシュ有効時には削除済みobject等が残る場合があるため、ドメイン切替後にも削除後404とメタデータ更新を検証する。[R2の整合性とキャッシュ](https://developers.cloudflare.com/r2/reference/consistency/)

## 公開用データの作成

完全版Artifactを保存した後、そのコピーから公開用データを作る。  
Artifactの元データを削除・書き換えない。

| 種類 | 公開処理 |
|---|---|
| VRT | `out.json`の変更・追加・削除一覧に基づき、対応する`actual`・`expected`・`diff`画像だけを選ぶ。公開HTMLでは変化なし画像の一覧・参照を省き、省略件数と完全版Artifactへの案内を表示する。結果データの原本は維持する |
| E2E | 完全版HTML内のreportデータから動画attachmentの参照を除き、動画本体も除外する。残った参照が必要とする画像等だけを含める |
| 共通 | 認証state、秘密値、不要な内部ファイル、symlink、範囲外pathを公開しない。公開管理メタデータは上記の項目だけを生成し、展開件数・容量・形式の上限を検査する |

変化なし画像の省略はレポートごとの重複保存を減らすためであり、基準画像のarchiveには全画像を含める。  
基準画像も圧縮前にprivacy検査と画像だけの構成確認を行い、撮影用ディレクトリの認証情報や補助ファイルを混入させない。

VRTの選別は`hosting-pages`の既存`report-site.mjs`にあるロジックを、このrepositoryへ移して再利用する。  
移植元のbaseline・メタデータを一律公開禁止にする検査は、新しい公開契約へ変更する。  
PR生成物から管理メタデータを持ち込ませない既存publisherの検査は維持し、公開するメタデータはtrusted側だけで生成する。
E2Eは拡張子で動画を消すだけでなく、再生リンクも消す。
実装時の固定されたPlaywrightバージョンで生成したfixtureを使い、埋込report形式を安全に扱えることを確認する。  
未知の形式や壊れた参照を検出した場合は公開を失敗させ、完全版Artifactを残す。

公開レポートのコピー、圧縮前の基準画像、生成した最小JSONをtrustedなprivacy検査で検査する。  
基準画像は画像ファイル単位で既存のprivacy検査を通してからZIP化する。  
取得時はZIP構造と展開量を検査し、展開した画像へ同じprivacy検査を適用する。
既存の`assertNoSensitiveArtifacts.mjs`を優先し、検査範囲や容量制限を狭めない。

## CIの構成と失敗時の動作

既存の`playwright.yml`と`vrt.yml`内に、R2公開専用jobを設ける。  
workflow完了後に起動する別publisherへは移さず、VRTの公開と差分承認の依存関係を同じworkflow内に保つ。

| jobの責務 | 入力と出力 |
|---|---|
| E2E実行 | 現行テスト・result gate・privacy検査を維持。完全版HTMLと機密値を除いた件数summaryをArtifact化 |
| VRT比較元の取得 | compare内で公開HTTPSから確定メタデータとbaseline archiveを取得する。専用jobとR2資格情報は不要 |
| VRT capture／compare | 4 shardの成功・完全性を確認。全撮影画像に加えて、HTML・`out.json`を含む比較レポート一式をArtifact化 |
| 公開 | 当該run／attemptのArtifactを検証し、公開用コピーを作成してR2へ転送。GitHub APIから最新headとPR状態を確認 |
| VRT承認 | compareの差分結果とpublishの結果を参照。既存の`vrt-approval`環境保護を維持 |

PRではマージ先branchのbaselineと比較し、基準画像を更新しない。  
feature等からdevelopへのPRはdevelop基準、developからmainへのPRはmain基準とする。
merge後のdevelop／mainへのpushで正常に撮影した全画像を、そのbranchの新しい基準にする。  
develop基準をmainへ単純コピーしたり、PRのVRT承認・終了イベントだけで更新したりしない。

E2Eのテスト失敗とVRT差分ありのrunも、レポート生成・privacy検査が成功していれば公開する。  
成功したrunだけへ公開条件を絞らない。
キャンセル済みrunや不完全な撮影結果は公開・baseline更新に使わない。

公開jobはレビューした固定commitのscript・lockfileへcheckoutをpinする。  
依存installやArtifact展開時にはR2書き込み資格情報を渡さず、R2操作stepだけへ注入する。
Artifact内のscript、PR由来のpackage scriptや依存installを、R2資格情報を持つ状態で実行しない。

同一repositoryのPRであることを明示確認し、forkへR2資格情報を渡さない。  
baseline更新はGitHubが確認した`push`イベントかつ`develop`／`main`に限定し、Artifact内のフラグを権限根拠にしない。

現在のテスト・result gate・privacy検査の失敗はblockingを維持する。  
R2への転送や公開確定の失敗もworkflowの失敗として示す。
公開確定後のHTTP到達確認timeoutとPRコメント権限エラーは、現行どおりwarningに分離する。  
R2の状態、テスト結果、Artifactへの案内を区別し、コメント失敗だけでアップロードをやり直さない。

公開HTTPSの取得では429・一時的な5xx・通信timeoutだけを、回数と合計待ち時間に上限を設けて再試行する。  
`Retry-After`があれば待ち時間上限内で尊重する。baseline取得が上限まで失敗した場合は比較を失敗させ、空baselineでの成功や基準更新へ進めない。  
これは公開確定後の到達確認warningとは別の契約であり、R2転送の成否と混同しない。

公開job分離により既存のrequired checkが意味を失わないよう、実装時にbranch protectionの参照名を確認する。  
必要なら既存check名の集約jobでテスト・公開のblocking契約を維持し、設定変更による検証回避は行わない。

## 公開確定と比較元画像の更新

1. GitHub APIでrepository、PRのopen状態、source SHA、run／attemptを確認し、対象prefixをtrusted側で組み立てる。
2. run固有prefixへファイルを転送する。branch更新では同じrunのbaseline archiveも同じbucketへ転送し、完全性を検証する。
3. 公開確定直前に最新head・PR状態を再確認し、確定メタデータをETagによる条件付きwriteで切り替える。新規作成も存在しないことを条件にする。
4. 確定済みメタデータのURLをHTTP確認し、PRコメントとjob summaryを更新する。前の公開世代はその後に削除する。
5. 転送・検証・確定に失敗した場合は直前の確定済みメタデータを保ち、今回の未確定世代だけを削除する。強制終了で残ったものは後述の日次処理で回収する。

同じrun／attemptは冪等に扱い、同じ識別子でsource SHAが異なればエラーにする。  
古いrunが後から完了しても、最新runを上書きしない。
R2のS3互換APIは`PutObject`の`If-Match`／`If-None-Match`をサポートする。[S3 API互換性](https://developers.cloudflare.com/r2/api/s3/api/)

baselineはbranchごと・runごとのZIPとして保存する。  
既存のZIP依存を使い、CRC、checksum、画像件数、容量、展開pathを検証する。
多数の画像を個別取得する操作回数を減らし、取得途中に別runの画像が混ざることを防ぐ。
比較jobは確定メタデータが指すarchiveだけを取得し、checksum・画像件数・展開pathを検査する。  
公開base URLと対象branchのbaseline prefixに取得先を限定し、任意の外部URLへ接続しない。  
PRでbaselineが欠落・破損している場合は失敗させ、自動的な空baselineやPR画像による再作成へ逃がさない。

現在参照中のbaselineは保持し、参照を外れた時刻から24時間残してから削除する。  
中断により参照解除時刻が残っていない旧ZIPは、日次処理で時刻を記録してから24時間保持する。
一時世代の回収を含めても、履歴を無期限に蓄積しない。

## PR終了時の削除と競合対策

`maintain-hosted-reports.yml`をR2用に置き換え、`pull_request_target`の`closed`を追加する。  
mergeもこのイベントで扱い、固定commitへpinしたtrustedな削除scriptだけを実行する。
PRのheadはcheckoutしない。
PRのマージ先はdevelop／mainの両方を対象にし、main向けVRTレポートも削除する。  
E2Eの実行対象は現行どおりdevelop向けPRだけとし、main向けPR等でE2Eの保存先が存在しない場合の削除はno-opにする。

「終了時の削除」は、イベントで起動したCIが対象PRのopen状態を再確認して削除することを指す。  
GitHub Actionsの待ち時間や環境保護の承認待ちはあり得るが、7日間の保持猶予は設けない。

| 条件 | 確認・動作 |
|---|---|
| close／merge | 対象PRのVRT・E2Eの全世代と対応メタデータを削除。baselineや他PRには触れない |
| publish中にclose | 同じ対象の削除jobを待機させる。publisherも確定直前に状態を再確認し、closedなら当該PRを削除して終了 |
| close後に古いpublishが開始 | closedを再確認し、アップロードせず対象PRの削除へ収束させる |
| 再open後に古いcleanupが開始 | 現在openなら削除しない。新しいCIが公開する |
| 削除途中の失敗 | listの全pageを読み、削除APIの部分失敗を確認。失敗を通知し、再実行で残りを削除 |

publish、接続確認、初期移行、cleanupの全R2変更jobは共通の`hosted-reports-r2-write`を使い、`cancel-in-progress: false`と`queue: max`を指定する。  
異なるPRとbranchも含めて直列化し、日次処理との競合を単一のconcurrencyで防ぐ。
待ち順だけを最新性の根拠にせず、開始時と確定直前のGitHub状態確認を必ず行う。  
workflow全体の自動キャンセルが書き込みjobを途中停止しないよう、既存のキャンセル設定をbuild／capture等のjobへ移す。
`queue: max`にも上限があるため、イベント処理だけに回収を依存させない。[GitHub Actionsのconcurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

現行の日次scheduleと手動実行を残し、closed PRの削除漏れと24時間以上経過した未確定世代・古いbaseline archiveを回収する。  
日次処理は全対象を取得し、共通concurrency内の一つのjobで順に処理する。
matrixは使わず、現在参照されている世代や作業中の新しい世代を削除しない。
一覧の全pageと削除結果を確認し、対象を黙って切り捨てない。

## 初回のCloudflare・GitHub設定

2026-09-05の会話で登録完了が報告され、実装時にrepository scopeのSecrets二つ・Variables三つの存在を確認した。  
URLとbucket名の形式を確認したが、秘密値は取得していない。
R2への保存・取得・条件付き更新・削除、公開URLと匿名更新拒否はCIで確認した。証跡は[リリース状態](../manual/release-status.md)を参照する。キーが他bucketも操作できないことまでは、この接続確認では検査していない。
既存設定を使って接続を確認し、設定不備を検出した場合は作業を止めてユーザーへ知らせる。
キー、bucket、登録値を自動で作り直さない。

| 場所 | 作業 | 完了確認 |
|---|---|---|
| Cloudflare | 使用accountを確定し、R2を有効化。Standardで公開bucketを一つ作成 | bucket名・endpointを記録 |
| Cloudflare | 対象bucketのPublic Development URLを有効化し、発行された`https://pub-….r2.dev`を使用 | レポート、baseline archive、確定メタデータを匿名で取得可能 |
| Cloudflare | 対象bucket一つに限定したread/writeキーを発行 | 保存・確認・削除ができ、匿名での書き込み・削除は拒否される |
| GitHub | repositoryのSecrets・Variablesに登録済みの値を使い、公開・削除jobの`Preview`環境保護を維持 | trustedな公開・削除jobだけがキーを参照。capture／compareへキーを渡さない |
| Cloudflare | 少額の超過を把握する予算メール通知を任意で設定。CI切替の必須条件にはしない | 設定する場合に通知先と金額を記録 |

| 区分 | 登録名 | 値 |
|---|---|---|
| Secret | `REPORT_R2_ACCESS_KEY_ID` | read/writeトークンのAccess Key ID |
| Secret | `REPORT_R2_SECRET_ACCESS_KEY` | 同じトークンのSecret Access Key |
| Variable | `REPORT_R2_ENDPOINT` | `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`。bucket名を末尾に付けない |
| Variable | `REPORT_R2_PUBLIC_BUCKET` | 実際に作成したbucket名 |
| Variable | `REPORT_PUBLIC_BASE_URL` | `https://pub-….r2.dev`。末尾の`/`は付けない |

設定の保存先はrepository scopeとし、R2の変更jobはGitHub Environmentの`Preview`を使う。develop／mainに向けたPRと、両branchのpush、PR終了時の公開・削除jobで同じ設定を使い、Environmentへの重複登録は不要とする。  
Environmentに同名設定がある場合の優先関係を確認し、古い値による不一致を残さない。
Environmentのbranch制限がある場合は対象のPR・branchが実行可能か確認し、既存の保護を回避しない。
以前の案の`REPORT_R2_READ_ACCESS_KEY_ID`、`REPORT_R2_READ_SECRET_ACCESS_KEY`、`REPORT_R2_PRIVATE_BUCKET`は不要。  
`REPORT_R2_ACCOUNT_ID`もendpointに含まれるためCIへ別途登録しない。登録済みの旧案の値があっても参照しない。

bucket公開とAPIキー発行の方法は[R2公開bucket](https://developers.cloudflare.com/r2/buckets/public-buckets/)と[R2認証](https://developers.cloudflare.com/r2/api/tokens/)を使う。  
予算アラートは通知機能であり、無料枠で停止する仕組みではない。[予算アラート](https://developers.cloudflare.com/billing/manage/budget-alerts/)

`pnpm-lock.yaml`はpackage managerでのみ更新する。
汎用ストレージ基盤や独自の常設server、Worker、queueは作らず、既存publisherに必要なS3操作だけを実装する。

## 検証契約

公開対象の選別・結果データ変換・run判定・削除対象の導出は、`scripts/`のLogic Testを主担当にする。  
R2とGitHub Actionsの実接続はCIで別の境界として検証する。

| 契約 | 検証 |
|---|---|
| 公開用コピーと完全版の分離 | 変化なしVRT画像・E2E動画・動画参照が公開レポートから消え、差分確認用画像とHTML表示資産が残る。全基準画像は別prefixのarchiveに含まれ、元Artifactは変更されない |
| 入力と最新性 | fork、偽PR／branch、古いSHA／attempt、同一runのSHA不一致、path traversal、symlink、壊れたarchiveを拒否 |
| 比較元の取得と更新 | develop向けPRはdevelop基準、main向けPRはmain基準。PRの成功・終了では更新せず、対象branchの正常なpush runだけが基準を更新する |
| 公開HTTPSの失敗 | 429・一時障害で上限付き再試行し、回復時は続行、上限到達時のbaseline取得は失敗。欠落・破損を空baselineへ置換しない |
| 公開・baseline確定 | 途中転送失敗と条件付きwrite競合で旧確定世代を維持。branchのreportとbaselineが同じ確定runを参照 |
| 即時削除 | close、merge、close中publish、遅延publish、reopen後cleanup、複数page、削除部分失敗を検証。他PRとbaselineを削除しない |
| 実接続と結果表示 | 失敗したE2Eのレポートも公開できる。登録済み設定でr2.devのレポート・baseline匿名取得、画像参照、削除後404、匿名更新の拒否、VRT承認、Artifact downloadをCIで確認 |

`publishHostingReport.test.ts`はGit snapshot固有の検証をR2移行後の入出力契約へ置き換える。  
移植元の`report-site.test.mjs`にあるbaseline・最小メタデータの公開禁止は更新し、レポートごとの変化なし画像の省略と、PR由来の管理メタデータ拒否は維持する。  
既存のprivacy検査とbaseline欠落検証は維持する。
`hostingWorkflowContract.test.ts`のYAML内step名・埋込文字列を固定する検証は撤去し、必要な意味上の判定はscriptのLogic Testへ移す。  
workflowの権限・trigger・実行順は差分レビューとActions上の結果で確認する。これは`test-strategy/references/test-writing-rules.md`の現行方針に従う。

ユーザーが指定した`babysit-pr`に従い、初回push前は対象Logic Test等で変更契約を確認し、全体lint・type-check・test・buildはGitHub Actionsで確認する。  
CI失敗には原因に対応する対象限定のローカル確認を行い、修正後の最新headでCIと自動レビューを再確認する。
別機能由来の失敗もユーザーの依頼範囲として原因を確認し、完了まで対応する。
実接続の確認はCIの自動検証で行い、AI Agentの手動ブラウザ操作による確認を追加しない。

## 切替・復旧と完了条件

検証済みhelperの固定commitを先にpushし、そのSHAへpinしたworkflowを導入branchへpushする。  
PR作成前に同じbranchのmaintenanceで`check`、次に`bootstrap`を実行し、登録済み設定とbaseline初期移行を確認してからPRのCIを起動する。
初回導入も任意のPR headを資格情報付きで実行せず、レビューしたhelperの固定commitを使う。
既存baselineを取得できない場合は、最後の正常なbase branch runの全画像Artifactを復旧候補にし、source SHA・全shard・画像件数を確認する。
取得元が確定できるまで、PRの比較元を自動再生成しない。

過去の全PRレポートは移行しない。  
open PRはCIを再実行してR2へ公開する。
旧GitHub PagesのURLは新URLへ自動移行できないため、既存コメントは対象PRの次回公開時に更新する。

切替失敗時は新しいR2公開を停止し、テスト結果とArtifactで確認できる状態を維持する。  
旧hosting先への復帰は旧経路の復旧を確認できた場合だけ行い、失敗する経路へ自動で戻さない。
正常baselineを保全し、不完全な転送結果を比較元へ昇格させない。

VRT・E2Eの公開、close／merge削除、reopen、公開baselineの取得・更新、Artifact保持が実CIで確認できたら切替完了とする。  
その後、シフトリの旧データだけを対象に旧保存先の整理を行い、他用途を残す。
`REPORT_PUBLISHER_HOSTING_PAGES_TOKEN`は初期移行で旧snapshotを取得するためだけに残す。  
初期移行経路を撤去し、シフトリ側の全参照がなくなったことを確認してから旧tokenの登録を外す。
他用途と共有しているtokenそのものを無条件に失効させない。

外部設定・実公開・削除の結果は証跡付きで`doc/manual/release-status.md`へ記録する。  
計画書の完了だけで外部状態を確認済みとは扱わない。

## 費用の前提

調査時点では直近30日でVRT 973回、E2E 872回、公開選別後の現存データとbaselineは約0.76GBだった。  
従来の画像個別転送を前提とした書き込み推計は約28〜40万回／月であり、無料枠内という見込みである。
本計画の即時削除・baseline archive化で保存量と操作数は変わるため、切替後の実測を優先する。

公開job summaryに送信ファイル数・byte数・削除件数を記録し、料金のための専用監視基盤は追加しない。  
R2 Standardの無料枠はaccount全体で共有され、無料枠超過を強制停止する機能はない。
少額の超過を許容する合意に従い、独自の課金停止機構は今回作らない。[R2料金](https://developers.cloudflare.com/r2/pricing/)

## Security Lens

| 観点 | この変更で守る境界 |
|---|---|
| Actor | 同一repositoryの検証済みrun、trustedな公開・削除job、匿名のレポート閲覧者 |
| Asset | R2資格情報、比較元画像、公開レポート、Artifact、使用量 |
| Trust boundary | PRコード／生成物から、資格情報を持つ公開・削除jobへの受渡し。レポート・baseline・最小メタデータの匿名readと、CIだけのwriteを分離 |
| Abuse case | 偽の保存先、別PR削除、baseline汚染、秘密情報の公開、古いrunによる復活、無制限な世代蓄積 |
| Server-side enforcement | GitHub APIによるrepository・PR状態・SHA検証、bucket限定権限、trusted script、入力検査、条件付きwrite |
| Rate limit / idempotency | 全R2変更jobの共通concurrency、run／attempt識別、上限付きretry、ファイル件数・容量上限 |
| Lifecycle / recovery | PR終了イベント＋日次回収、完全な世代だけ確定、旧確定世代とArtifactによる復旧 |
| Logs / PII | 件数・容量・run ID等だけを記録。資格情報・認証state・動画の新規録画を持ち込まない |
| Regression test | 上記Logic Testと実CIの匿名取得・認証付き保存／削除・匿名更新拒否の検証 |

# 事業者課金、複数店舗、複数管理者の実装計画

作成日: 2026-07-14

改訂日: 2026-07-15
状態: 実装前、軽量化済み

## 1. この計画の位置づけ

業務要件の正本は `doc/specs/organization-billing-business-flow.md` とする。

この文書は、現在の店舗単位モデルから事業者単位モデルへ移行するための実装順序と境界を定める。

実装の細部は、各フェーズで現行コードと公式ドキュメントを確認して決める。

規約にすでにある認証、認可、移行、テスト、リリース手順は、この計画へ重複して作り込まない。

独自のフェーズゲート、契約レジストリ、結果正規化基盤、実装計画検査コマンドは追加しない。

## 2. 目的

次の完成状態を、既存機能を止めずに実現する。

- 課金契約の単位を店舗から事業者へ変更する。
- 一つの事業者が複数店舗を管理できるようにする。
- 一つの事業者に複数の管理者が参加できるようにする。
- 同じ事業者内では、同じ人物を店舗ごとに重複作成しない。
- Trial、Free、Pro、Business、支払い猶予、契約制限中の業務動作を統一する。
- Stripeの結果を検証してから利用権限へ反映する。
- 既存店舗と既存データを、停止時間を前提にせず移行する。

## 4. 実装で守る契約

### 4.1 テナントと認可

- 認証済み利用者から有効な事業者所属を解決し、サーバー側で事業者境界を検証する。
- 店舗IDを受け取る処理では、その店舗が選択中の事業者に属することも検証する。
- クライアントから渡された事業者ID、店舗ID、権限名だけを信用しない。
- 店舗は日常業務の選択単位として残し、事業者は契約と管理の境界とする。
- すべての有効な管理者に同じ管理権限を与え、課金専用ロールは設けない。
- 最後の有効な管理者を失う操作は拒否する。
- 所属や管理権限を失った利用者は、以後のAPI呼び出しで直ちに拒否する。

### 4.2 人物と利用人数

- 同じ事業者内の同じ人物は一つの人物レコードで表す。
- 別事業者の人物は自動的に統合しない。
- 利用人数は仕様書の算入規則を一つのドメイン関数へ集約する。
- 未承認招待は利用人数へ含めないが、新しい人物への招待は一人分の利用枠を予約する。
- 招待の取消または期限切れでは予約を解放し、招待対象が既存人物になった場合は二重に数えない。
- 招待承認時のトランザクションで、招待、予約、現在の利用人数を再確認する。
- 事業者から人物を外す前に、将来シフトと請求先メールアドレスを解決し、所属、権限、リンク、招待、未送信通知へのアクセスを失効させる。
- 人物を再追加するときは既存人物を明示確認して再利用し、以前の権限、店舗所属、リンク、招待を自動復元しない。

### 4.3 課金状態と利用権限

- 事業者ごとに一つの課金状態を正本とする。
- Trial、Free、Pro、Businessと、猶予や契約制限の状態を重複保存しない。
- 画面やAPIが必要とする読み取り、書き込み、復旧操作の可否は、課金状態と所属から導出する。
- 復旧担当者や閲覧専用状態のためだけに、独立した状態テーブルを増やさない。
- Freeで残す有効管理者と稼働店舗の選択は、仕様上必要な識別子だけを課金状態に保持する。
- 利用制限はUI表示だけでなく、対象mutationの共通ガードで強制する。

### 4.4 Stripe

- 一つの事業者を一つのStripe Customerへ対応させる。
- 一つの事業者に有効なSubscriptionを同時に複数作らない。
- 金銭または契約を変更する処理には、論理操作を識別できる安定したキーを使う。
- Stripeへ変更を送る処理には、同じ論理操作を再実行できる冪等性キーを設定する。
- CheckoutやCustomer Portalから戻った画面だけを根拠に利用権限を開放しない。
- 署名検証済みWebhookまたはStripeとの再同期結果を根拠に、課金状態を更新する。
- WebhookはStripe Event IDで重複排除する。
- Webhookの到着順を前提にせず、古いイベントで新しい状態へ巻き戻さない。
- 支払い再試行回数などStripe側で変更できる値は、コードへ固定しない。
- CheckoutとCustomer Portalのセッション作成には、認証済み利用者と事業者を組み合わせた回数制限を設ける。

### 4.5 招待

- 招待トークンの平文を保存しない。
- 招待には事業者、対象メールアドレス、有効期限、失効状態、使用済み状態を結び付ける。
- 招待承認時に、認証済みメールアドレスとの一致を検証する。
- 招待は一回だけ使用でき、再発行時は古い招待を無効化する。
- 招待を発行した管理者が権限を失った場合は、その未承認招待を無効化する。
- 一つの事業者と正規化済みメールアドレスに対する有効な管理者招待は、一つまでとする。
- 招待承認時に所属と利用人数を再確認し、競合する承認を同じトランザクションで防ぐ。
- 招待の発行、再送、承認には、既存のrate limit基盤を使って回数制限を設ける。

### 4.6 通知、監査、個人情報

- 課金通知はメールだけとし、既存のNotification Outboxを再利用する。
- 課金専用のキュー、fanout、lease、reaperは新設しない。
- 所属や管理権限を失った利用者を、新しい課金通知の宛先にしない。
- Freeまたは契約制限中への移行時は、移行後に許可されない未送信の業務通知を停止する。
- 外部送信の直前に、課金状態、店舗状態、受信者の所属を再確認する。
- 監査対象は、プラン変更、契約終了、支払い状態変更、権限変更などの重要な業務変更に限定する。
- Customer Portalセッション作成のような一時操作を、すべて永続監査することは求めない。
- トークン、署名、決済情報、メール本文、不要な個人情報をログへ出さない。

## 5. 実装前に決める事項

次の事項はコードから決められないため、該当フェーズの着手前に確認する。

| 決定事項 | 決定期限 | 未決定時の扱い |
| --- | --- | --- |
| 既存利用者の移行先プラン | フェーズ2前 | 本番データを確認し、全員を特別プランへ入れる仮定は置かない |
| 同一メールアドレスの既存重複と空メールの扱い | フェーズ2前 | 自動統合せず、衝突として抽出する |
| 既存利用者の無料体験対象と初期請求連絡先 | フェーズ2前 | 新規利用者と同じ規則を適用しない |
| プラン価格、税、請求周期、日割り、返金 | フェーズ4前 | Stripe連携を開始しない |
| 未払い請求書を残した契約終了時の扱い | フェーズ4前 | Stripe設定と会計方針を確認する |
| Stripeのテスト用Product、Price、Portal設定 | フェーズ4前 | テスト環境の外部連携を有効化しない |
| Stripeの本番Product、Price、Portal設定 | 本番公開前 | 本番連携を有効化しない |
| 旧課金データと監査ログの保持期間 | 物理削除前 | 旧データを削除しない |

価格や会計上の決定は、実装計画で推測して補わない。

## 6. 最小設計方針

### 6.1 追加する主要概念

概念名は既存の命名規則に合わせて実装時に確定する。

- 事業者。
- 事業者に属する人物。
- 事業者の管理者所属。
- 店舗と事業者の関連。
- 事業者単位の課金状態。
- 管理者招待。
- Stripe Event IDの処理済み記録。
- 重要な課金変更の監査記録。

これらを細かな状態ごとのテーブルへ分割しない。

同じライフサイクルを持ち、同じトランザクションで更新する値は、まず同じ集約に置く。

### 6.2 時刻で変わる状態

無料体験終了、支払い猶予終了、予約したプラン変更には、既存のConvex schedulerを使う。

各scheduled functionは、対象IDと期待する状態またはバージョンを受け取る。

実行時に現在状態を再確認し、すでに変更済みなら何もせず終了する。

期限処理にStripeの取消などの外部副作用がある場合は、操作種別、冪等性キー、未完了状態を事業者課金状態へ先に記録する。

外部副作用が失敗した場合は、同じ論理操作をschedulerまたは再同期処理から再試行する。

古いSubscriptionの終了が未完了の間は、競合する新しいSubscriptionを開始しない。

単発の期限処理のために、汎用ジョブテーブル、lease、heartbeat、reaperを作らない。

件数や実行上限が実測上の問題になった場合だけ、耐久ワークフローへの変更を別計画にする。

### 6.3 Webhook

最初の実装は、署名検証、Event ID重複排除、対象事業者の特定、Stripe状態との照合、内部mutationによる反映で構成する。

HTTP Action内で外部照会が必要な場合は、照会結果を検証してから内部mutationへ渡す。

Webhook inboxや独自の処理leaseは、処理時間、再試行、障害回復に実際の不足が確認された場合だけ導入する。

### 6.4 移行

移行はWiden、Migrate、Narrowの順で行う。

既存の `@convex-dev/migrations` とリポジトリのmigration配置を使う。

Widen期間は、新旧データを読めるようにし、新規または更新データを必要な範囲で両方へ反映する。

バックフィルは再実行可能にし、衝突や不正データを件数と識別子で確認できるようにする。

参照先はユースケースごとに切り替え、一度に全機能を切り替えない。

停止時間を伴う全件書き換えは前提にしない。

本番データの事前確認でオンライン移行が成立しないと判明した場合だけ、保守時間を別途計画する。

## 7. 実装フェーズ

### フェーズ1: 契約と判断事項を確定する

#### 成果物

- 業務仕様書の未決定事項に対するプロダクト判断。
- 現行データを対象とした移行前チェック結果。
- 現在と完成形を区別した機能概要文書。
- 課金状態から各操作可否を導出する権限表。

#### 作業

1. `doc/specs/organization-billing-business-flow.md` の業務受入条件を、実装対象の正本として確認する。
2. 既存利用者、店舗所属、メールアドレス、店舗課金状態の件数と衝突条件を読み取り専用で確認する。
3. 既存利用者の移行先を決め、根拠のない特別プランを追加しない。
4. Trial、Free、Pro、Business、猶予、契約制限中から導く操作可否を表にする。
5. `doc/features/billing-plans.md` と `doc/features/manager-billing-roles.md` を、旧検討であることが分かる状態に保つ。
6. 新しい公開APIを追加する前に、事業者境界と店舗境界の認可契約をレビューする。

#### 完了条件

- 第5節のうちフェーズ2に必要な決定が完了している。
- 移行時に自動統合できないデータの扱いが決まっている。
- 状態ごとの許可操作が、UIとバックエンドで共通に解釈できる。

### フェーズ2: 事業者基盤とオンライン移行を実装する

#### 成果物

- 事業者、人物、管理者所属、店舗関連、事業者課金状態のschema。
- 既存店舗から事業者を作る再実行可能なmigration。
- 新旧モデルを扱う移行期間の読み書き境界。
- 事業者と選択中店舗を検証する認可wrapper。

#### 作業

1. 新しいfieldとtableをoptionalな参照から追加する。
2. 既存の一店舗を一事業者へ対応させる。
3. 異なる既存店舗を、名称やメールアドレスだけで同じ事業者へ自動統合しない。
4. 既存管理者を、その店舗から作った事業者の管理者へ対応させる。
5. 既存スタッフを事業者内の人物へ対応させ、同一店舗内の明らかな重複だけを規則に従って扱う。
6. 新規初期設定では、事業者、管理者、最初の店舗、課金状態を同じ処理で作る。
7. 管理者向けAPIが、認証、事業者所属、店舗所属をサーバー側で検証するようにする。
8. ユースケースごとに新モデルへ切り替え、切り替え中は必要な範囲だけ新旧へ書き込む。
9. migrationの残件、衝突、失敗を再実行前後で確認する。
10. `shopBillingStates` は分析と旧読み取りの互換性が不要になるまで残す。

#### 完了条件

- すべての既存店舗が一つの事業者へ対応している。
- すべての管理対象データが事業者境界と店舗境界の両方で検証される。
- 新規初期設定が新モデルだけで成立する。
- migrationを再実行しても重複した事業者や所属が作られない。
- 既存の主要導線が切り替え中も利用できる。

### フェーズ3: 複数店舗、複数管理者、プラン動作を実装する

#### 成果物

- 管理者招待と承認。
- 店舗追加、店舗切り替え、店舗アーカイブ。
- 事業者内で一意な人物管理。
- Stripeへ依存しない課金状態遷移と利用制限。
- 事業者設定画面と代表的な課金状態のUI。

#### 作業

1. 招待の一意な作成、枠予約、再発行、失効、予約解放、承認を同じ招待ライフサイクルとして実装する。
2. 招待の発行、再送、承認に回数制限を設け、承認時にメールアドレス、有効期限、最新性、予約、利用上限を再確認する。
3. すべての有効な管理者に、店舗と課金の同じ管理権限を与える。
4. 最後の有効な管理者の削除、無効化、離脱を拒否する。
5. 人物を店舗または事業者から外す処理と再追加を、将来シフト、請求先変更、アクセス失効、履歴保持、明示的な再有効化の規則に従って実装する。
6. 店舗の追加とアーカイブを、事業者単位の上限と将来データの契約に従って実装する。
7. 選択中の事業者と店舗を明示し、切り替え後のAPIが選択先を再検証する。
8. Trial、Free、Pro、Business、猶予、契約制限中のドメイン状態遷移を実装する。
9. Trial終了、猶予終了、期間末変更を、状態再確認付きのscheduled functionで処理する。
10. Free移行に必要な有効管理者と稼働店舗の選択を検証する。
11. 上限を超える追加操作と、契約制限中の更新操作をサーバー側で拒否する。
12. 支払い復旧やプラン変更に必要な操作だけを、契約制限中にも許可する。
13. 課金通知を既存Notification Outboxへ積み、制限移行時の未送信通知停止と送信直前の再確認を実装する。
14. 重要なプラン、支払い、管理権限の変更だけを監査する。
15. 事業者設定、店舗切り替え、招待、プラン、猶予、契約制限の画面状態を実装する。

#### UIの最低条件

- 現在の事業者、店舗、プラン、利用人数、上限、次の状態変更日が分かる。
- 操作できない理由と、復旧に必要な次の操作が分かる。
- Free移行で残す有効管理者と稼働店舗を、確定前に確認できる。
- 招待中、期限切れ、上限到達、競合、送信失敗を区別して表示する。
- Submit系操作には同期的な二重送信防止と、バックエンド側の競合防止を設ける。

#### 完了条件

- Stripeなしでも、各プランと制限状態の業務動作をテストできる。
- 管理者招待を同時承認しても、上限超過や重複所属が起きない。
- 複数店舗の切り替えで、別事業者または別店舗のデータが露出しない。
- 期限処理を再実行しても、通知や状態変更が重複しない。

### フェーズ4: Stripe連携を実装する

#### 着手条件

- プラン価格、税、請求周期、日割り、返金の方針が決まっている。
- Stripeのテスト用Product、Price、Customer Portal、Webhook endpointを用意できる。
- フェーズ3のプロバイダー非依存な状態遷移が動作している。

#### 成果物

- CheckoutまたはSetupに必要なAction。
- Customer Portalセッションを作るAction。
- 署名検証と重複排除を行うWebhook endpoint。
- Stripe状態と事業者課金状態の同期処理。
- 支払い成功、失敗、猶予、復旧、期間末変更の連携。

#### 作業

1. 事業者とStripe Customerを一対一で作成または再利用する処理を実装する。
2. 契約作成と変更で、論理操作ごとの冪等性キーと回数制限を使う。
3. Customer Portalセッションは、回数制限を適用し、認可済み事業者のCustomerに対してだけ作成する。
4. 一時的なPortal URLは永続保存しない。
5. Webhookのraw bodyに対してStripe署名を検証する。
6. Event IDを記録し、同じイベントの再配送を成功として無害化する。
7. CustomerとSubscriptionから事業者を特定し、対応が曖昧なイベントを適用しない。
8. 必要に応じてStripeの現在状態を取得し、イベントの到着順に依存せず正規化する。
9. 内部mutationでStripe参照と事業者課金状態を同じトランザクション内に反映する。
10. Checkout完了画面では処理中を表示し、検証済み状態が届くまで権限を開放しない。
11. 支払い失敗で猶予を開始し、猶予終了時に現在の支払い状態を再確認する。
12. Subscription終了を未完了操作として追跡し、成功するまで同じ論理操作を再試行する。
13. 復旧、上位プラン変更、期間末のFree移行または契約終了を業務状態へ反映する。
14. Stripeが送る支払いメールと、シフトリが送る業務状態メールの責務を分ける。

#### 完了条件

- Stripeの同じ操作またはイベントを再実行しても、二重契約や二重反映が起きない。
- Webhookの順序が入れ替わっても、課金状態が古い状態へ戻らない。
- 成功画面を直接開いても、有料機能が開放されない。
- 支払い失敗から猶予、制限、復旧までをテストモードで確認できる。
- Subscription終了が一時的に失敗しても再試行でき、完了前に新しいSubscriptionを作らない。
- Stripeとの不一致を安全に再同期できる。

#### 外部確認

テスト環境では通常のテストコマンドとStripe CLIまたはDashboardを使って最小の確認を行う。

専用のbilling canary runnerやpreview identity基盤は作らない。

最低限、契約作成、Webhook反映、Customer Portal起動、支払い失敗、復旧、期間末変更を確認する。

### フェーズ5: 観測後にNarrowする

#### 着手条件

- 新モデルへのbackfillが完了している。
- 新モデルの読み書きが本番相当環境で安定している。
- 旧モデルへ戻す必要がないと判断できる観測期間を終えている。

#### 作業

1. optionalだった事業者参照を、実データ確認後に必須化する。
2. 旧モデルへの書き込みとfallback読み取りを、利用箇所ごとに削除する。
3. 分析の日次snapshotが保持する過去のプラン意味を壊さないように切り替える。
4. 旧機能文書を、完成した新機能の概要文書へ置き換える。
5. 保持方針が決まった旧課金データだけを、別の削除作業として扱う。

#### 完了条件

- アプリケーションの通常処理が旧店舗課金状態を参照しない。
- 必須参照を持たないレコードが残っていない。
- 分析の過去値と新しい事業者課金値の意味が文書化されている。
- 物理削除を行う場合は、保持方針、対象件数、復旧手段について別途承認されている。

物理削除は本機能の公開条件にしない。

## 8. テスト方針

変更契約を最も直接検証できる一つの層を主担当にする。

すべての変更へLogic、UI、Convex、E2E、VRTを一律に追加しない。

| 主担当層 | 検証する契約 |
| --- | --- |
| Logic Test | 利用人数、上限、JST境界、状態遷移、操作可否の純粋ロジック |
| Convex Function Test | 認証、事業者境界、店舗境界、招待、競合、冪等性、Webhook反映 |
| Convex Scenario Test | 複数機能と時間経過をまたぐ主要状態遷移 |
| Storybook Behavior Test | 操作後に現れるエラー、確認、成功、制限状態 |
| VRT | 代表的な設定、Free選択、猶予、契約制限の画面状態 |
| E2E | ブラウザ境界でしか確認できない事業者切り替え、招待、Stripeからの復帰 |

### 8.1 主要Scenario Test

Scenario Testは次の主要契約に絞る。

1. Trial終了時にFree設定が成立すればFreeへ移り、成立しなければ契約制限中へ移る。
2. 支払い失敗から猶予、契約制限、支払い復旧までが重複なく遷移する。
3. 検証済みStripe状態だけが有料権限を開放し、期間末変更を正しく反映する。
4. 招待の枠予約、人物追加、承認が競合しても、予約の重複と利用人数超過が起きない。
5. 事業者と店舗を切り替えても、認可境界を越えない。

近いFunction Testで十分に検証できる場合は、同じ契約をScenario Testへ重複させない。

### 8.2 実装中の検証

各変更では、対象ファイルに近いテストと影響するprojectを実行する。

UIを変更した場合は、関連するStorybook検証とbuildも行う。

各フェーズの統合時に `pnpm lint`、`pnpm type-check`、関連テストを実行する。

Full Regressionは、大きな切り替え後と本番公開前に一度ずつ行う。

実装完了時は、自己レビューとCodexレビューで認可、競合、移行、不要な複雑さを確認する。

## 9. Security Lens

### 資産

- 事業者、店舗、人物、シフト、契約、請求参照、招待、監査記録。

### 境界

- 認証済み利用者と事業者所属の境界。
- 事業者と店舗の境界。
- Convex ActionまたはHTTP Actionと内部mutationの境界。
- シフトリとStripe、メール配信サービスの境界。

### 攻撃者

- 別事業者の正規利用者。
- 失効または転送された招待を持つ利用者。
- Webhookを偽装または再送する外部者。
- 同じ操作を連続実行する利用者または障害時の再試行。

### 失敗時の動作

- 所属、店舗、Stripe対応、招待対象を一意に検証できなければ拒否する。
- Stripeとの同期が不明なら有料権限を推測で開放しない。
- scheduled functionの期待状態が一致しなければ変更せず終了する。
- 通知失敗は課金状態のトランザクションを巻き戻さず、既存Outboxで再送する。

## 10. 本番操作の境界

本番データを変更するmigrationの実行は、コード実装とは別に明示的な承認を得る。

Stripe本番Product、Price、Webhook、Customer Portalの作成または変更も、実行前に明示的な承認を得る。

通常のCI、デプロイ、migration確認手順を使い、課金専用のリリースゲート基盤は作らない。

移行件数、エラー、Stripe同期失敗は、既存のログと運用画面で足りる範囲から始める。

専用監視基盤は、既存の観測手段で検知できない失敗が確認された場合だけ別途設計する。

## 11. この計画で採用しない設計

次の設計は、現在確認できる要件に対して過剰なため採用しない。

- 独自の `billing:phase:gate`、`billing:contracts:check`、fingerprint、plan checker。
- 契約レジストリ、検証結果schema、結果normalizer、計画専用fixture群。
- 課金専用のpreview identity、canary runner、リリース判定runner。
- 既存利用者全員へ自動付与する、要件未確定の `legacyBusiness` プラン。
- 招待本体と別ライフサイクルを持つ利用枠予約基盤。
- 復旧担当者、閲覧専用管理者、プラン停止店舗を表す独立状態テーブル。
- 単発期限処理のための汎用job、cursor、lease、heartbeat、reaper。
- 課金専用通知キューとfanout基盤。
- Webhook処理量の問題が未確認な段階でのinboxとlease基盤。
- Customer Portalセッションなど一時操作を含む全操作の永続監査。
- 全件停止移行、最初からの必須field化、移行中の新旧両読み取り禁止。
- 保持方針が未決定な旧データの物理削除と復元リハーサル。
- 各作業で全テスト層とFull Regressionを必須にする運用。
- 同じ手順を二つの改変不能な証跡へ保存する独自の証跡基盤。

将来、負荷、障害、監査要件によって必要性が確認されたものは、その観測結果を根拠に別計画で追加する。

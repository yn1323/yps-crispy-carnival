## 1. 結論

調査中のsnapshotでは、`doc/`に107件、約3.1万行のMarkdownがある。

本計画を含む`doc/plans/`は66件、約2.6万行を占め、全体の8割を超えている。

別チャットの変更で件数と行数は動いているため、数値は規模を把握する目安として扱い、実施時に再集計する。

量そのものより、現行仕様、未決提案、実装中の計画、完了済み計画、移行履歴、実環境の確認記録が同じ場所に並んでいることが問題である。

一方で、現行Feature Docに記載された完全修飾のConvex API参照は概ね解決でき、Markdownの相対リンクと見出しアンカーにも明確な切れは見つからなかった。

したがって、全面的に書き直す必要はない。

まず文書の役割と寿命を分け、読者の目的から入れるINDEXを作る。

次に、現行コードと明確に違う記述を直し、旧機能、廃止、置換、棄却済みの資料を`doc/archive/`へ移す。

最後に、判断が必要な差分を解決してから、長大な現行文書だけを分割して書き直す。

この順序なら、古い資料を磨き直す作業と、承認済み仕様を偶発的な実装へ合わせる事故を避けられる。

## 2. 現状の評価

### 2.1 残すべき強み

- `doc/features/`には、現在提供している主要機能の入口が揃っている。
- `doc/rules/`には、フロントエンド、テスト、セキュリティ、Convex設計の横断規約がある。
- 課金の主要な業務契約は`doc/specs/organization-billing-business-flow.md`へ分離されている。
- 現行Feature Doc、`doc/INDEX.md`、`doc/ARCHITECTURE.md`にある明示的なConvex API参照は概ね実在する。
- Markdownリンクと見出しアンカーは、調査時点で明確に壊れていない。

整理の中心は、正しい文書を捨てることではなく、正しい場所へ置き、現在性を判別できるようにすることである。

### 2.2 探しにくさの原因

現在の`doc/INDEX.md`は機能一覧としては使えるが、`doc/`全体の入口にはなっていない。

運用手順、未決提案、大半の計画、監査記録、プロダクト原則へINDEXから辿れない。

`doc/plans/`には、実装待ちの提案と、すでに完了または置換された実装計画が同居している。

読者は、ファイルの日付や本文の途中にあるステータスを読むまで、その資料を現在の判断に使ってよいか分からない。

### 2.3 構成上の不足

`doc/ARCHITECTURE.md`は全体構造を掲げているが、機能マッピングは主要画面の一部に限られる。

現行には25 pageディレクトリと34 top-level featureディレクトリがあり、多数のrouteがある一方、認証、公開サイト、課金、招待、通知、削除、内部分析、外部サービス境界への逆引きが弱い。

ルート`/`と`src/components/features/LandingPage/`にも独立した入口がなく、公開サイト全体の責務をどのFeature Docが所有するか判別しにくい。

`doc/features/organization-billing.md`は517行あり、現行機能、業務仕様、API一覧、migration、実環境の公開状態、障害対応、テスト配置を一つに抱えている。

`doc/features/shift-recruitment-management.md`も、募集管理、シフト表編集、入力検証、通知fanoutを一つの仕様メモに抱えている。

### 2.4 リポジトリ入口の問題

ルートの`README.md`はTanStackの初期テンプレートを残している。

Tailwind CSS、React Query、存在しない`pnpm check`を案内し、Chakra UIとConvexを使う現行構成や`doc/INDEX.md`への入口を示していない。

`doc/`だけを整えても発見できなければ役に立たないため、READMEの入口修正だけは本計画に含める。

## 3. 文書ごとの正本を決める

同じ事実を複数の文書で維持しない。

衝突時に何を優先するかを、文書種別ごとに次のように定める。

| 配置 | 所有する内容 | 衝突時の扱い |
|---|---|---|
| コード、schema、設定、テスト | 実行可能な現在の挙動 | 現在事実として確認するが、承認済み仕様との差は議論へ回す |
| `doc/specs/` | 承認済みの業務ルール、状態遷移、受入条件 | コードへ黙って合わせず、仕様変更か実装不備かを決める |
| `doc/rules/` | 横断的な設計原則、責務、レビュー基準 | 実装で強制するか、規約の約束を弱めるかを決める |
| `doc/features/` | 現在提供する機能、利用者の仕事、画面とコードの入口 | 実装が意図どおりなら文書を追従させる |
| `doc/manual/` | 人が繰り返し行う運用、確認、復旧手順 | コマンド、ファイル、環境名を現行へ追従させる |
| `doc/plans/` | 未決提案、進行中の計画、完了済み計画の履歴 | INDEXで`Proposed`、`Active`、`History`を分け、現在仕様の正本にはしない |
| `doc/archive/` | 廃止、置換、棄却された資料と時点監査 | 本文を現行へ追従させず、後継文書への案内だけを加える |

実装があることと、productionへ反映済みであることも分ける。

リポジトリ内の文書だけで確認できない公開状態やmigration状態は、検証日、対象deployment、証跡を持つ運用記録で管理する。

変動する状態の正本は次の一箇所に限定する。

| 状態 | 正本 | ほかの文書の扱い |
|---|---|---|
| 機能とコードの照合 | 各Feature Docの基準commit | Feature INDEXは入口だけを持ち、照合日を複製しない |
| 計画の進捗 | `plans/INDEX.md` | Plan本文は作成時の判断と受入条件を保持し、変動する進捗を複製しない |
| production公開とmigration | `manual/release-status.md` | Feature DocとPlanは状態値を複製せず、該当項目へリンクする |

実環境状態は、commit SHA、完全修飾deployment名、確認日時、CLIが表示した対象、アクセス制限済み証跡を一組で記録する。

調査中に追加された`doc/rules/agent-instructions.md`とルート`AGENTS.md`は、`doc/plans/`を計画時点の履歴として残す方針を示している。

本計画もこの方針へ揃え、完了済みでも現在の判断経緯として有効なPlanは`History`に残す。

Archiveへ移すのは、廃止、置換、棄却され、現行理解へ混ぜると誤解を生む資料に限る。

本計画では旧ファイルを復活させず、別チャットの完了後にINDEXから新しい正本へ案内する。

## 5. 必要なINDEX

### 5.1 `doc/INDEX.md`は質問から選べる入口にする

現在の機能表をそのまま拡張せず、読者が知りたいことから次のINDEXまたは正本へ案内する。

| 知りたいこと | 案内先 | 入口で示す内容 |
|---|---|---|
| 現在できること | `features/INDEX.md` | 利用者、主な画面、機能概要 |
| 業務上の確定事項 | `specs/` | 承認済み仕様と適用範囲 |
| システム全体とコード配置 | `ARCHITECTURE.md` | 境界、データフロー、逆引き |
| 実装とレビューの規約 | `rules/` | どの作業で何を読むか |
| リリース、migration、法務更新 | `manual/INDEX.md` | 人が行う手順と実環境確認 |
| 未決提案、進行中の変更、完了した判断 | `plans/INDEX.md` | `Proposed`、`Active`、`History`ごとの現在地 |
| 廃止、置換、棄却された資料 | `archive/INDEX.md` | archive理由と現行文書 |

ルートINDEXには個々のFeature Docを重複掲載しない。

ルートINDEXは地図に徹し、詳細一覧は各配下のINDEXが所有する。

### 5.2 `doc/features/INDEX.md`は利用者の仕事で分ける

機能名の単純な五十音順ではなく、次の業務単位で分類する。

1. 利用開始、認証、法務同意
2. グループ、店舗、人物、権限
3. 募集、希望提出、シフト編集、確定
4. 通知、再送、LINE連携
5. 課金、公開状態、削除
6. 公開サイト、ヘルプ、問い合わせ
7. 内部分析

各行は、対象利用者、主な画面、Feature Docだけを持つ。

API一覧や実装状況の詳細をINDEXへ複製しない。

状態と最終コード照合日はFeature Doc側だけが所有する。

### 5.3 `doc/plans/INDEX.md`は状態ごとに入口を分ける

`plans/`は計画時点の判断履歴として維持する。

INDEX内で、採否未決の`Proposed`、未完了の`Active`、完了済みの`History`を明確に分ける。

廃止、置換、棄却された資料だけを、後継を確認してArchiveへ移す。

| 項目 | 内容 |
|---|---|
| 計画 | 文書へのリンク |
| 状態 | `reviewing`、`approved`、`implementing`、`rollout`、`blocked`、`completed` |
| 未完了条件 | コード、migration、外部設定、判断待ちを区別した残件 |
| 現在の正本 | 関連Feature Doc、Spec、Manual |
| 最終更新 | 日付と基準commit、実環境状態は`manual/release-status.md`へのリンク |

`completed`は`History`へ移す。

`superseded`、`abandoned`、`rejected`は、現行文書への反映を確認した同じ変更でarchiveする。

### 5.4 `doc/manual/INDEX.md`は実行場面から選べるようにする

CI/CD、法務文書更新、migration、Stripe公開、障害対応、セキュリティ再検証の入口を並べる。

各手順には、対象環境、事前条件、停止条件、確認証跡、復旧先を示す。

特定日の監査結果と、繰り返し使う手順は別文書にする。

### 5.5 `doc/archive/INDEX.md`は後継を示す

Archive本文は現行仕様へ追従更新しない。

INDEX側で、元のパス、archive理由、archive日、後継文書を記録する。

理由は`superseded`、`abandoned`、`rejected`、`point-in-time-audit`、`removed-feature`から選ぶ。

## 6. 文書の状態と寿命

Archive外の文書には、文書種別を示す短いmetadataを付ける。

YAML frontmatterの全面導入はせず、既存Markdownと差分が小さい引用ブロックから始める。

```md
> 文書種別: feature
> 最終コード照合: 2026-07-23
> 基準commit: `<commit SHA>`
```

Feature Docだけが最終コード照合日と基準commitを持つ。

Plan本文は作成時の判断、対象範囲、受入条件、参考ファイルを保持し、変動する進捗と未完了条件はPlan INDEXだけが持つ。

Manualの実環境状態は`manual/release-status.md`だけに置き、Ruleには変動するstatusを持たせない。

Archiveでは、元のパス、archive理由、後継文書を持たせる。

文書の寿命は次の流れで管理する。

```text
Proposed plan
  ↓ 採用
active plan
  ↓ 実装、検証、公開
feature / spec / rule / manual を更新
  ↓ 現行契約の転記を確認
plan history

superseded / abandoned / rejected
  ↓ 後継を記録
archive
```

Planの完了条件に、現行文書の更新とHistoryへの分類を含める。

これにより、実装完了後も計画書だけがActive一覧に残る状態を防ぐ。

## 7. Archiveの判断

別チャットが触れた文書は、完了後に内容とstatusを再確認するまで移動も改稿もしない。

分類台帳には、現在の種別、status、後継文書に加え、その文書を参照しているファイルを記録する。

移動と同じ変更で被参照元を更新し、旧パス参照が残っていないことを完了条件にする。

### 7.1 最初にarchiveできる資料

本文自身が旧検討であることを明示する次のFeature Docは、現行課金文書への後継リンクを確認してarchiveできる。

- `doc/archive/features/billing-plans.md`
- `doc/archive/features/manager-billing-roles.md`

`doc/archive/audits/2026/security-validation-2026-07-21.md`は時点監査として保存し、現行の再検証手順は`doc/manual/security-validation.md`が所有する。

### 7.2 Planは別チャット完了後に再分類する

実装完了が確認できるPlanは、まず`plans/INDEX.md`の`History`へ分類する。

廃止、置換、棄却が確認でき、現行文書へ必要な契約が移っているPlanだけをArchive候補にする。

次は再判定の優先候補であり、現時点の移動対象ではない。

- `doc/plans/2026-07-03_複数店舗・複数マネージャー設計.md`
- `doc/plans/2026-07-16_店舗とアカウント削除_実装計画.md`
- `doc/plans/2026-07-18_店舗と組織の削除_個人情報匿名化_実装計画.md`
- `doc/plans/2026-07-20_Stripe課金連携_実装計画.md`

`doc/plans/2026-07-11_別端末ログイン本人確認_実装計画.md`には、本番相当Clerk設定と実環境受入確認が残っている。

実環境証跡を確認するまでは`Active`に残し、実装済みという理由だけでHistoryまたはArchiveへ移さない。

2026年3月から5月の設計書、実装プロンプト、初回リリース計画には、現行と合わないパスが多い。

一括移動せず、コードとテストに残る受入条件、被参照元、後継文書を台帳で確認してから、HistoryまたはArchiveへ分類する。

### 7.3 Archiveへ入れない資料

次は現行の正本または未完了作業を持つため、日付だけを理由にarchiveしない。

- `doc/rules/`の現行規約
- `doc/specs/organization-billing-business-flow.md`
- 旧検討と明示された2件を除く現行Feature Doc
- 再構成対象の`doc/ARCHITECTURE.md`
- 現行文書がproduction migrationとNarrowを未完了と記録している`doc/features/manager-shop-membership.md`
- repo内文書が実環境証跡を未確認と記録しているStripe、課金、削除、セキュリティ計画
- 現行化して`manual/`へ残す法務、CI/CD、migration、復旧手順

repoだけでは実際のproduction状態を確定できないため、これらの未完了を現在事実として断定しない。

### 7.4 未決提案はPlanの`Proposed`へ分ける

次は古い現行仕様ではなく、未実装で採否未決の案である。

- `doc/plans/2026-07-03_AIシフト下書き機能.md`
- `doc/plans/2026-07-03_AIシフト下書き機能_実装仕様書.md`
- `doc/plans/2026-07-04_メールアドレス任意化_設計.md`

AIシフト下書きの主要な`src/`と`convex/`境界は現行コードに存在しない。

スタッフのメールアドレスも、現行schema、mutation、画面型では必須である。

採用を継続するならPlan INDEXの`Proposed`へ載せ、見送るなら理由を記録してarchiveする。

## 8. 現行コードとの差分は別紙で管理する

現行コードとの明確な差分、要議論事項、Security Lensは、[doc現行コード差分調査](2026-07-23_doc現行コード差分調査.md)へ分離した。

明確な記述差分はPhase 2で直す。

プロダクト、セキュリティ、外部公開状態の判断はPhase 4で別課題へ引き渡し、INDEX作成とArchive整理を止めない。

## 9. 読んで理解できる現行文書へ直す

Archive候補を磨き直さず、今後も参照する文書から優先する。

### 9.1 Feature Docの共通構成

Feature Docは、詳細仕様の複製ではなく、現在の機能とコードへ到達するための地図にする。

次の順序へ揃える。

1. 誰が何を完了できる機能か
2. 保証する範囲と保証しない範囲
3. 主な画面と状態遷移
4. 現在の業務契約
5. フロントエンドとバックエンドの入口
6. Public APIと重要なinternal境界
7. 関連するSpec、Rule、Manual
8. 最終コード照合日

ファイル一覧を増やしすぎず、機能の所有者となる入口を示す。

細かなvalidator、migration履歴、運用コマンド、テストケース一覧は、それぞれコード、Archive、Manual、テストへ委ねる。

### 9.2 優先して分割する文書

`doc/features/organization-billing.md`は、次の四つへ責務を分ける。

- Feature Docには、利用者に見える機能、主要状態、画面、API入口を残す。
- `doc/specs/organization-billing-business-flow.md`には、プラン、権限、状態遷移、受入条件を集約する。
- `doc/manual/`には、Stripe設定、migration確認、障害対応を移す。
- Plan INDEXには未完了条件と`manual/release-status.md`へのリンクを置き、実環境状態を複製しない。

`doc/features/shift-recruitment-management.md`は、募集管理とシフト表編集を分ける。

- 現行文書には、募集作成、一覧、削除を残す。
- 新しい`doc/features/shift-board.md`には、編集、保存、確定、validation、PCとモバイルの差を置く。
- 通知fanout、lease、dedupe、再開は`doc/features/notification-outbox.md`を正本にする。

`doc/features/line-notification.md`は、利用者向け連携と、Webhook防御、rate limit、環境変数、移行互換を分ける。

利用者に見える状態はFeature Docに残し、繰り返し行う設定と障害対応はManual、横断的な安全契約はRuleへリンクする。

`doc/archive/audits/2026/security-validation-2026-07-21.md`は特定commitの監査snapshotとして保存し、現在も使う再検証手順は`doc/manual/security-validation.md`へ分ける。

Snapshotは`doc/archive/audits/2026/`へ移し、未完了の実環境確認は現行Manualへ抽出する。

`doc/features/public-pages.md`は「公開サイト」へ改題し、公開サブページだけでなくルート`/`を所有する文書へ広げる。

画面と関連ファイルに`src/pages/home/`、`src/components/features/LandingPage/`を加え、TOPとFAQ、HowTo、記事、デモの責務を一つの入口から辿れるようにする。

### 9.3 `doc/ARCHITECTURE.md`は一覧ではなく境界を描く

すべてのファイルを列挙しない。

次の四つの入口から、Feature Docとコードへ辿れる構成にする。

1. route、page、feature、domainからなるフロントエンド境界
2. query、mutation、action、HTTP、cron、migrationからなるConvex境界
3. Clerk、LINE、Resend、Stripe、Cloudflareとの外部境界
4. 通知outbox、fanout、migrationなどの非同期処理

詳細なAPI一覧はFeature Docまたは生成可能な索引へ委ねる。

逆引きには、少なくとも`src/domains/shop/`、`src/domains/organizationBilling/`、`CreateRecruitmentForm`、公開TOP、法務の汎用route、シフトリンク再発行を含める。

## 10. 文章の再構成方針

現行文書を書き直すときは、事実の分類とコード照合を先に終える。

文章だけを先に滑らかにすると、古い前提まで読みやすく保存してしまう。

各節は結論から始め、その段落が説明する一つの主張を置く。

一文には一つの判断だけを書き、理由、例外、手順を必要に応じて次の文へ分ける。

箇条書きは一覧と手順に限り、前後の因果関係は文章でつなぐ。

短い観察、判断に必要な比較、結論を交互に置き、長い表が続く箇所には読み手が現在地を取り戻せる要約を入れる。

ただし、読みやすさのために不確実性を消さない。

実環境未確認、product policy未決、migration途中は、その状態が見える文として残す。

## 11. 実施フェーズ

### Phase 0: 現在のworktreeを再基準化する

`doc/plans/`を中心とするプログラミング系文書の修正が、別チャットで進行している。

別チャットが完了するまでは、その変更対象を移動、改稿、stageしない。

完了後に最新差分と最終statusを確認し、その成果を本計画の新しい基準にする。

別チャットの完了、対象commitとdirty状態の記録、対象パスの所有者確認が揃うまで、Phase 1以降を開始しない。

調査中には、`doc/manual/ci-cd.md`、`doc/rules/agent-instructions.md`、`doc/rules/ui-design.md`、関連計画の追加と、多数の指示文書の再構成が確認できた。

本計画はそれらを変更していない。

実施開始時に最新のworktreeを再読し、同時進行の文書変更を取り込んだ分類台帳を作る。

台帳には、全Markdownの種別、状態、現行の正本、移動先、被参照元、要確認事項を一行ずつ記録する。

別チャットと本計画が同じファイルを変更する場合は、どちらが最終編集を所有するかを台帳へ記録する。

完了条件は、Archive移動前に全対象の行き先が確定し、ユーザーの別変更へ上書きが発生しないことである。

### Phase 1: 文書の役割と入口を作る

ルートINDEXを目的別の入口へ変え、Feature、Plan、Manual、ArchiveのINDEXを作る。

別チャットが更新した`AGENTS.md`と`doc/rules/agent-instructions.md`へ、Planの`Proposed`、`Active`、`History`分類とArchiveの役割を最小限追記する。

別チャットの文章をこのPhaseで再編集せず、役割に関する最小限の記述とINDEXだけを揃える。

READMEからルートINDEXへ案内し、各INDEXの所有範囲が重複しないようにする。

Feature Docへ基準commitを段階的に追加し、計画進捗と実環境状態はそれぞれPlan INDEXと`manual/release-status.md`だけに置く。

完了条件は、Archive外の全文書へルートINDEXから二遷移以内で到達できることである。

### Phase 2: 明確な差分を修正する

別紙第2章の差分を、同じcommitのコードとテストへ再照合して修正する。

特定日の監査記録は書き換えず、現行チェックリストを分離して修正する。

プロダクト判断を含む別紙第4章の項目は、このPhaseへ混ぜない。

完了条件は、現行文書内のrepo相対パスが実在し、確認済みの記述差分が解消されることである。

### Phase 3: 廃止、置換、棄却資料をarchiveする

第7章の高確度候補を`git mv`で移し、履歴を保持する。

各文書へarchive理由と後継を付け、`doc/archive/INDEX.md`から辿れるようにする。

Planは`Proposed`、`Active`、`History`へ先に分類する。

3月から5月の資料は一括移動せず、残存契約をコードとテストへ照合してから分類する。

完了条件は、Plan INDEXの`Active`に完了済み資料が混ざらず、Archive文書の被参照元が新しいパスまたは後継文書へ更新されることである。

### Phase 4: 要議論の差分を別課題へ引き渡す

別紙第4章の項目を、仕様、実装、外部公開状態のどれに属するか分けて決定する。

コード変更が必要な項目は、文書整理とは別の実装単位にする。

別紙のプロダクトとセキュリティの判断は、Phase 1から3の情報設計を止めない。

セキュリティ、persisted shape、public Convex APIへ触れる場合は、対応するSecurity Lensとmigration計画を先に確定する。

完了条件は、各論点にowner、次の判断、変更対象、検証方法が記録され、必要な別計画へ引き渡されることである。

### Phase 5: 長大な現行文書を再構成する

`ARCHITECTURE.md`、課金、募集管理、LINE通知、セキュリティ検証を、第9章の責務へ分ける。

事実確認後に、日本語技術文書として段落、見出し、表、文の密度を整える。

完了条件は、各文書が一つの役割を持ち、別文書の詳細を複製せず、読者が次に読む正本を判断できることである。

### Phase 6: 文書の退行を検知する

既存のMarkdownリンク検査だけでなく、バッククォート内のrepo相対パスとINDEX掲載状態を検査する。

`scripts/checkDocs.ts`と`pnpm docs:check`の追加を候補とし、少なくとも次を自動確認する。

1. 相対Markdownリンクと見出しアンカーが解決する。
2. 現行文書内のrepo相対パスが実在する。
3. 完全修飾された`api.*`と`internal.*`が、現行Convex moduleのexportへ解決する。
4. 記載されたHTTP route、cron、migration名が`convex/http.ts`、`convex/crons.ts`、`convex/migrations/index.ts`へ解決する。
5. Archive外のMarkdownがいずれか一つのINDEXに所属する。
6. Plan INDEXのActive行に状態と未完了条件がある。
7. Archive文書に理由と後継がある。
8. 自動生成ファイルと未来の提案パスを誤検知しない。

コードとの意味上の一致は自動判定しきれないため、Feature Docの最終照合日とレビューを残す。

完了条件は、文書の追加、移動、削除で検査が失敗し、正しいINDEXまたは参照を追加すると成功することである。

## 12. 検証方針

文書移動だけの変更で、アプリケーションの全テストを機械的に要求しない。

各Phaseで次を確認する。

- Markdownリンクと見出しアンカーの解決
- repo相対パスの存在
- INDEXからの到達性
- `rg`による旧パス、旧製品名、旧状態表現の残存確認
- `git diff --find-renames`による移動と改稿の分離
- Archive候補から現行契約が失われていないことのレビュー

検査scriptを追加した場合は、`pnpm lint`、`pnpm type-check`、scriptの単体テストを実行する。

UI、Convex、public assetを変更した場合は、その変更契約を直接守る主担当層のテストを追加または更新する。

本番migrationと公開状態は、repo内のテスト成功だけで完了扱いにしない。

- `doc/INDEX.md`が、機能一覧ではなく`doc/`全体の目的別入口になっている。

- Plan INDEXで`Proposed`、`Active`、`History`が分かれ、現在の作業と履歴が同じ一覧に混在していない。
- 未実装で採否未決の案はPlan INDEXの`Proposed`に分離されている。
- 廃止、置換、棄却されたArchive文書には、archive理由と後継文書がある。
- 現行文書のrepo相対パスと主要API参照が実在する。
- Feature Doc、Spec、Rule、Manual、Plan、Archiveの優先関係が明示されている。
- `ARCHITECTURE.md`から主要なフロントエンド、Convex、外部連携、非同期処理へ辿れる。
- `ARCHITECTURE.md`の逆引きに`src/domains/shop/`、`src/domains/organizationBilling/`、`CreateRecruitmentForm`、公開TOP、法務の汎用route、シフトリンク再発行が含まれる。
- 課金、募集管理、LINE通知、セキュリティ検証の文書が、一つの文書へ複数の役割を抱えていない。
- コードと仕様の要議論項目にownerと次の判断が記録され、必要な別課題へ引き渡されている。
- READMEから`doc/INDEX.md`へ到達できる。
- 文書のリンク、パス、INDEX所属を継続的に検査できる。

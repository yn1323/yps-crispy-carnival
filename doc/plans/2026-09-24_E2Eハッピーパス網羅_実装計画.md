- 作成日: 2026-09-24

- 現在の正本: [テスト方針](../rules/testing-strategy.md)、[Full Regression横断契約表](../specs/full-regression-contracts.md)、`e2e/AGENTS.md`

この文書は、エラー系を除く利用者向けのハッピーパスをPRゲートのcore E2Eで網羅するために、追加する契約、テストの作り方、改訂する規約を決めた記録である。  
現在仕様の正本ではない。  
2026-09-24に規約改訂と12契約の実装を行い、各契約はローカルのConvex deploymentで成功した。  
PR PreviewでのCI実行、burn-in、同一SHAの反復は未確認である。

## 背景

2026-08-03の[E2E安定性改善・スコープ再設計](2026-08-03_E2E安定性改善_実行計画.md)で、core E2Eを実ブラウザ境界でしか検知できない代表導線へ絞った。  
その結果、core E2Eはdesktop 15契約とmobile 1契約になり、actor固定、seedからの開始、result gate、burn-inで安定性を確保している。

現在のシフトリは軽い保守が中心で、Pull Requestを作ってから数日以内にリリースする。  
PRの時点で主要なハッピーパスの回帰を止めたいが、2026-09-24時点のcore E2Eには次の空白がある。

- 提出方法：`E2E-SHIFT-01`と`E2E-MOBILE-01`はどちらもseedの既定値である時間指定だけを通り、日付選択とパターン選択の提出・割当・閲覧を通していない。
- シフト運用の後半：再提出、下書き保存後の再読み込み、確定後の再確定、募集の条件編集と削除、シフト対象外を通していない。
- 運用と復旧：通知不達への対応、スタッフ参加申請の承認、LINE連携、閲覧リンクの再発行を通していない。
- 利用開始と端末：Dashboardの体験ガイドと、スマートフォンのシフト表（日別表示）を通していない。

core E2Eの契約数は複数の文書へ転記されており、値もそろっていない。  
`e2e/AGENTS.md`と`doc/manual/ci-cd.md`はdesktop 15契約、[Full Regression横断契約表](../specs/full-regression-contracts.md)はdesktop 13契約と書いている。  
正しい値は`scripts/assertE2ECoreResults.mjs`の`EXPECTED_CORE_CONTRACTS`にある。

## ユーザーと合意した前提

| 項目 | 決定 |
|---|---|
| 実行タイミング | core E2EとしてPRゲートに含める |
| 範囲 | エラー系を除くハッピーパス。課金とスケジュール系（cronによる催促やdigest）は対象外 |
| LINE連携 | LINE Loginの画面とcode交換だけをE2E専用seedで代替し、それ以外は画面で操作する |

| Clerkユーザー | 追加してよい。まず既存の6名で始め、実行時間を測ってから増やすか決める |

## 方針

### core E2Eの役割を変える

core E2Eの役割を「実ブラウザ境界でしか検知できない代表導線」から「エラー系を除く利用者向けハッピーパスを機能ごとに一つずつ持つ」へ広げる。  
validationの全分岐、通知の対象集合、dedupe、DBの細部、境界値は、これまでどおりLogic、Behavior、Convex Function、Convex Scenarioが主担当である。

一本の長い通しテストは作らない。  
CIは`retries: 1`と`failOnFlakyTests`を組み合わせているため、retryで成功してもPRは失敗する。  
1操作の成功率が99.5%でも60操作をつなぐと通しの成功率は約74%になり、長いテストほどPRを偶然止める確率が高くなる。  
そこで各契約は開始状態をseedで作り、独立して並列実行できる大きさに保つ。

### 1契約で確認すること

各契約は、seedで前提状態を作り、利用者の操作と確認を画面で行う。  
これは既存の`testing:seedNotificationSubmitScenario`が採っている「seedは前提状態だけを作り、募集作成・通知・token発行はブラウザ操作から通す」構成と同じである。

各契約には、前の機能で作ったものを次の機能で使う受け渡しを少なくとも一つ含める。  
たとえば提出方法の契約では、店舗設定で変えた提出方法が、募集、スタッフの提出画面、シフト表、確定後の閲覧まで引き継がれることを確認する。  
この受け渡しが、機能ごとの下位層テストでは検知できない失敗境界になる。

匿名のスタッフ操作は、管理者のstorage stateを持たない新しいbrowser contextで行う。  
提出linkや閲覧linkなどのcapabilityは、既存の`e2e/helpers/notificationTokens.ts`と同じく、E2E専用helperから必要なtokenだけを取得する。  
capabilityや個人情報を扱う契約は`e2e/fixtures/artifactSafeTest.ts`を使い、trace、screenshot、videoを保存しない。

### 外部providerと失敗状態の扱い

**provider代替seed**：外部providerの本人確認を通らないと進めない区間だけを、アプリ本体と同じ内部処理を呼ぶE2E専用関数で代替するseedを指す。  
LINE連携では、管理者が画面で連携URLを発行した後、E2E専用のinternal関数が同じ人物の最新の未使用連携tokenを探し、`internal.line.mutations.validateLinkToken`と`internal.line.mutations.finalizeLinking`を偽のLINE user IDで呼ぶ。  
アプリ側に「テスト時はcode交換を省く」分岐を足すと、認証経路に本番でも到達し得る抜け道ができるため、この方法を採る。  
代替した区間（LINE Login、code交換、profile取得）はE2Eの保証に含めず、`/line/callback`の結果表示はBehavior、token検証はFunction Testが守る。

通知不達は、通知処理が準備に失敗したときに呼ぶ記録mutation（`internal.notificationOutbox.mutations.recordDeliveryEvent`）をseedから呼んで作る。  
`DEBUG_NOTIFICATION_DELIVERY_MODE=force-failure`はdeployment全体に効くため、並列で動く他の契約の通知まで失敗させる。  
E2E実行中にこの設定を切り替えることはしない。

スタッフ参加申請のTurnstileは、E2Eで突破しない。  
当初はCloudflare公式のテスト用キーを使う予定だったが、2026-09-24時点のローカルdeploymentとフロントエンドは本番用のキーを使っており、キーの切り替えは開発者の手動確認にも影響する。  
そこで、匿名contextで登録画面が開くことまでを画面で確認し、Turnstile通過後の申請作成だけを、HTTP Actionと同じ`submitRegistrationRequestFromHttp`を呼ぶE2E専用関数で代替する。  
bot対策、rate limit、Originの検証はFunction Testが守る。

各契約で下位層に任せる範囲は次のとおりである。

| 契約 | 下位層に任せる範囲 |
|---|---|
| 提出方法と再提出（`E2E-SHIFT-02`から`E2E-SHIFT-04`） | 方式ごとの入力validation、保存形式への変換、置換更新の完全性はFunction Test、入力UIの分岐はBehavior |
| 下書きと再確定（`E2E-SHIFT-05`） | 差分再通知の対象集合とdedupeはScenario Test、未保存変更の確認Dialogの挙動はBehavior |
| 募集の編集と削除（`E2E-RECRUITMENT-01`） | 編集できる期間の境界と変更通知の対象はFunction TestとScenario Test |
| シフト対象外（`E2E-EXCLUSION-01`） | 旧linkの失効、通知対象からの除外、提出率の母数はScenario Test |
| 通知不達（`E2E-NOTIFY-01`） | 再通知の受付、`retrying`への遷移、配送後の再失敗、30日後の失効はFunction TestとScenario Test |
| 参加申請（`E2E-REGISTRATION-01`） | bot対策、rate limit、却下、申請上限はFunction Test |
| LINE連携（`E2E-LINE-01`） | token期限、使用済み、他人物の拒否、Webhook署名はFunction Test、callback画面の状態表示はBehavior |
| リンク再発行（`E2E-REISSUE-01`） | 旧linkの扱い、応答の同一性、連続要求の制限はFunction Test |

`E2E-NOTIFY-01`では、再通知の後に「一定時間待っても不達が戻らない」ことを確認しない。  
[通知不達Dashboard](../features/notification-failure-dashboard.md)の仕様上、再読み込み後は`status = open`の不達だけを表示し、`retrying`の通知は表示しない。  
このため再読み込み直後の非表示を確認すれば、配送処理の進み具合に左右されない。

| 対象 | 理由 | 守る層または再評価条件 |
|---|---|---|
| 課金、プランと支払い | ユーザー指定で対象外 | 既存の課金Function Test、Scenario Test、Stripe canary |

| アカウント削除 | 共有しているE2E用Clerkユーザー自体が消える | Function Test、Scenario Test。使い捨てClerkユーザーを用意できた場合に再評価する |
| ログイン方法の追加と変更 | Clerkの画面が主体で、アプリ側の接続は`E2E-AUTH-01`が守る | Clerk設定の運用確認 |
| 問い合わせ | ResendとSlackへの外部送信が成功条件になる | Function Test、Behavior、Deployed Smoke |
| 要望送信、スタッフの並び順、お知らせ表示 | 実ブラウザでしか起きない失敗境界がない | Scenario Test、Behavior、VRT |
| 管理者の法務再同意 | 法務文書の版を上げたときだけ発生する | Scenario Test、Behavior。版更新の運用が定常化したら再評価する |
| LINEとメールの実到着、LINE Login画面 | 外部providerの状態に左右される | 人が行う運用手順 |

## Security Lens

- Actor：E2E実行者（ローカルのadmin credential、CIの`CONVEX_DEPLOY_KEY`）、E2E用Clerkユーザー、匿名のスタッフcontext。
- Asset：提出、閲覧、LINE連携、参加申請、管理者招待のcapability、スタッフの氏名とメールアドレス、不達記録、LINE連携状態、deploy key、E2E用Clerkのpassword。
- Trust boundary：`convex run`からinternal関数への呼出し、`DEBUG_MODE`によるE2E専用関数の有効化、PreviewとProductionのdeploymentの分離、R2へ公開するPlaywright report。
- Abuse case：E2E専用関数がProductionで実行されてLINE連携を偽造する。provider代替seedが別組織の人物を連携させる。参加申請の代替関数が別組織の店舗の登録linkで申請を作る。capability URLや個人情報が公開reportへ残る。偽のLINE user IDが実在の利用者と衝突する。
- Server-side enforcement：新しい関数はinternal関数だけにし、最初に`assertE2EHelpersEnabled`を呼ぶ。provider代替seedは、seed済みの組織と人物の対応を確認し、同じ人物の最新の未使用tokenだけを本番と同じ検証処理へ通す。偽のLINE user IDはLINEの形式と衝突しない接頭辞を付け、workerと実行ごとに一意にする。
- Rate limit / idempotency：参加申請、再発行、再通知のrate limitは変更しない。メールアドレスと店舗を実行ごとに一意にする。参加申請の代替関数はHTTP Actionのrate limitを通らないため、burn-inでIP単位の上限に当たらない。
- Lifecycle / recovery：`testing:resetManagerScenarioData`は`lineLinkTokens`、`lineAccounts`、`notificationFailureInbox`、`staffRegistrationRequests`を既に削除対象にしている。新しいseedが作るdocumentがresetの対象に入ることをFunction Testで確認する。
- Logs / PII：token、メールアドレス、seedの引数をerror、attachment、reportへ出さない。`e2e/helpers/convex.ts`の失敗fingerprint化とprivacy reporter、`scripts/assertNoSensitiveArtifacts.mjs`を新しい契約にも適用する。
- Regression test：新しいE2E専用関数ごとに、`DEBUG_MODE`無効時の拒否と、対象外の組織・人物を指定したときの拒否を`convex/testing.test.ts`へ足す。2026-09-24に、不達seed、参加申請の代替関数、LINE連携の代替関数について`DEBUG_MODE`無効時の拒否、別actorの対象の拒否、未発行tokenの拒否を追加した。

## flakeと実行時間の予算

core E2Eの契約を増やすほど、PRが偶然失敗する確率が上がる。  
1契約あたりのflake率が0.2%なら、28契約で約5%のPRが偶然失敗する。  
0.1%まで下げても約3%である。

このため、契約は1つずつ追加し、次の順で確認してからresult gateへ登録する。

1. 対象の契約を`pnpm e2e <file> --retries=0 --workers=1`で成功させる。
2. `pnpm e2e:burn-in`で、retryなしの10回反復をすべて初回成功させる。
3. `scripts/assertE2ECoreResults.mjs`の`EXPECTED_CORE_CONTRACTS`と契約表へ同じ変更で登録する。

Phase 0で、2026-09-17から09-23の成功した4回のPRを測った。  
「Run Playwright tests」stepの中央値は約3分25秒、job全体は約4分40秒である。  
許容上限は、同じstepで8分とする。  
実行時間は、Phase 0で直近のPRのPlaywright結果から契約ごとの所要時間とwall timeを測り、許容する上限をこの計画へ記録する。  
上限を超えた場合は、Clerkユーザーを追加して通常workerを増やす。  
ただし`e2e/helpers/e2eUsers.ts`はユーザー数を6名、通常workerを3に固定しており、GitHub ActionsのrunnerはVite開発サーバーとChromeを同時に動かすため、worker数はCIで実測してから決める。

## 実装フェーズ

### Phase 0：規約、Skill、契約表を改訂する

「規約とSkillの改訂」の表にある7文書を改訂する。  
core E2Eの契約数の転記を削除し、`scripts/assertE2ECoreResults.mjs`を正本にする。  
直近のPRのPlaywright結果から実行時間のbaselineを測り、許容上限を決める。

検証は`pnpm docs:check`と`pnpm lint`で行う。

### Phase 1：既存seedの拡張で作れる契約を追加する

`E2E-SHIFT-02`、`E2E-SHIFT-03`、`E2E-SHIFT-04`、`E2E-SHIFT-05`、`E2E-RECRUITMENT-01`、`E2E-EXCLUSION-01`を追加する。  
seedは既存の`createManagerScenario`と`createRecruitment`に引数を足す範囲で作り、Page Objectは`e2e/pages/`の既存クラスへ必要な操作だけを足す。

提出方法の契約は、seedで提出方法を直接指定しない。  
店舗設定の画面で変更することが、この契約の受け渡しだからである。

### Phase 2：E2E専用関数と環境設定が必要な契約を追加する

`E2E-NOTIFY-01`、`E2E-REGISTRATION-01`、`E2E-LINE-01`を追加する。  
不達seedとprovider代替seedを実装し、Security Lensの回帰テストを同じ変更に含める。

`E2E-REGISTRATION-01`は、方針の節に書いたとおりTurnstile通過後の申請作成だけを代替したため、Preview環境変数の追加設定は不要になった。

### Phase 3：残りのP2契約を追加する

`E2E-REISSUE-01`、`E2E-ONBOARDING-01`、`E2E-MOBILE-02`を追加する。  
`E2E-ONBOARDING-01`では、既存seedが作る管理者がオンボーディング終了済みになっていないかを先に確認し、必要ならseedへ引数を足す。  
`E2E-MOBILE-02`はmobile projectに置き、desktop projectの完了後に同じ通常ユーザーで実行する既存の構成に従う。

### Phase 4：CIで安定性と実行時間を確認する

全core契約で`pnpm e2e:burn-in`を実行し、同じhead SHAのCIを3回実行する。  
実行時間がPhase 0で決めた上限を超えた場合は、Clerkユーザーの追加とworker数の変更を別のPull Requestで行う。  
契約表の状態欄をPreviewでの実行結果に合わせて更新し、この計画を`History`へ移す。

## 2026-09-24の検証結果

ローカルのConvex deployment（`dev:fortunate-mallard-809`）と既存の開発サーバーで、次を実行した。

| 検証 | 結果 |
|---|---|
| 追加した12契約を`--retries=0 --workers=1`で個別実行 | すべて成功 |
| `pnpm e2e:ci`（全28契約、3 worker） | 1回目は`E2E-NOTIFY-01`が残した意図的な不達で後続seedの監査が失敗した。同契約の後処理を直した2回目は、`E2E-MOBILE-01`の1件を除き成功 |
| `pnpm e2e:burn-in:desktop`（26契約を各10回） | 260回中258回が初回成功。失敗2件はConvex管理API（`api.convex.dev`）の503でseedのCLIが失敗したもの |
| `pnpm e2e:burn-in:mobile`（2契約を各10回） | `E2E-MOBILE-02`は10回成功。`E2E-MOBILE-01`は10回中1回、Clerkの開発用scriptが`Failed to fetch`をconsoleへ出して失敗 |
| `convex/testing.test.ts`、result gateのLogic Test、`pnpm lint`、`pnpm type-check` | 成功 |

`E2E-MOBILE-01`のClerk由来の失敗は既存契約で2回再現しており、今回の変更とは別に原因を調べる必要がある。  
ローカルの`pnpm test:convex`は34件失敗するが、今回の変更を退避しても同じ34件が失敗する。  
ローカルの`.env`と`.env.local`に定義された`DEBUG_NOTIFICATION_DELIVERY_MODE`がVitestへ読み込まれていることが原因と考えられる。

| 項目 | 内容 | 確認する時期 |
|---|---|---|

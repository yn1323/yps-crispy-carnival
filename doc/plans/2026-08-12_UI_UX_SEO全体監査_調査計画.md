## 1. 調査の結論

この監査では、画面の見た目を採点するのではなく、利用者が仕事を完了できるかを起点に「使い心地」を評価する。
Dashboardと非ログインページは目的が異なるため、単一の総合点へまとめない。

優先順位は次のとおりとする。

1. 主タスクの完了、現在状態と次の行動、誤操作からの回復
2. 情報階層、用語、操作数、モバイルでの効率
3. 公開ページの製品理解、信頼形成、デモ、登録・問い合わせへの導線
4. 公開ページのSEOと検索意図への適合
5. 表示・操作性能と実利用者計測の不足
6. 主要タスクを妨げるアクセシビリティ上の重大阻害

アクセシビリティは独立したWCAG監査にしない。
Chakra UIと共通UI部品が基礎的なセマンティクスを提供する前提を置き、主要タスクを完了できない問題だけをガードレールとして確認する。
UIフレームワークでは保証できない画面合成、文言、focus遷移、拡大時の欠落で重大阻害が見つかった場合は、通常のUX findingとして記録する。

「全体」は全URLを同じ深さで操作することを意味しない。
全routeを棚卸ししたうえで、固有テンプレート、主要journey、正常・空・待機・失敗・権限差を網羅し、同一テンプレートの繰り返しは代表サンプルで確認する。

## 2. 監査ゴール

### Dashboard

Dashboardの中心タスクは、現行機能から次のように仮置きする。

> 次の期間の希望を集め、シフトを確定し、スタッフが確認できる状態にする。

主な流れは「募集を準備する → スタッフへ知らせる → 希望を集める → 未提出へ対応する → シフトを調整する → 確定して共有する」である。
これは利用者調査で確定した事実ではないため、現在状態、次の一手、作業を止める問題が画面から分かるかをブラウザで検証する。

### 非ログインページ

未ログインの利用者が、次のいずれかを完了できることを検証する。

- 自分の店舗に関係する製品か判断し、デモ、登録、問い合わせへ進む。
- 検索で着地した記事、FAQ、HowToから疑問を解決し、次の行動を選ぶ。
- 登録なしのデモで価値を体験し、やり直すか登録へ進む。
- ログイン、登録、招待、スタッフ用リンクから安全に目的を完了し、失敗時に回復する。
- 誤ったURL、期限切れ、処理受付後の画面から行き止まりにならず復帰する。

### SEO

SEOは公開ページの検索適格性、検索意図、検索結果からの理解を評価する。
Dashboardと認証・Capability routeでは順位改善を扱わず、非公開情報が検索結果へ出ないこと、公開ページとの境界が正しいことを評価する。

## 3. 対象範囲と対象外

### 対象

- `/dashboard`の初回、日常業務、例外競合、複数店舗、利用制限、待機・失敗状態
- Dashboardの主アクションを完了確認するための募集作成Dialog、スタッフ関連Dialog、ShiftBoardへの最初の遷移
- Static Prerendering対象の全公開route
- `/login`、`/signup`、`/forgot-password`などの認証境界
- `/manager-invite`、スタッフ登録、希望提出・閲覧・再発行、法務同意、LINE callbackなどの匿名Capability境界
- 実HTTP status、response header、raw HTML、rendered DOM、metadata、robots、sitemap
- 利用可能な場合のSearch Console、CrUX、PageSpeed Insights、RUM、product analytics
- PCとスマートフォンの情報順、操作、表示・操作性能

### 対象外

- Dashboard以外のログイン後画面を独立した製品監査として網羅すること
- ShiftBoardの編集機能全体、組織設定全体、アカウント設定全体の詳細監査
- 網羅的なWCAG 2.2適合監査、全要素のcontrast測定、実機screen reader試験
- 監査中のUI修正、実装、migration、計測基盤の追加
- 深い認可・IDOR・rate limit・token実装のコードセキュリティ監査
- 実ユーザーの満足度、継続率、完了率を、AI一人の操作から推定すること
- 同一テンプレートの記事、FAQ、HowToを内容差なく全件同じ深さで操作すること
- Productionでの通知、招待、課金、削除、確定共有など、外部副作用または不可逆な変更

## 4. 証拠のレイヤー

異なる証拠を混ぜず、各findingへどのレイヤーを使ったかを記録する。

| レイヤー | 確認できること | 確認できないこと |
|---|---|---|
| 対象環境のBrowser | 表示順、文言、操作、到達不能、状態遷移、DOM、network、局所的なlab値 | 実利用者の母集団、継続率、満足度 |
| Production HTTP・raw HTML | status、header、SSG本文、canonical、robots、redirect、404 | Googleが実際に選択したcanonical、実CTR |
| Search Console・CrUX・RUM・analytics | index状態、query、impression、CTR、field CWV、実タスクevent | 個別利用者が迷った理由 |
| Repository・Story | route、実装契約、状態分岐、再現fixture、現在コードの根拠 | Production公開済みか、実利用者影響があるか |
| 専門家レビュー | 認知負荷、信頼低下、離脱要因の検証仮説 | 利用者影響の確定 |

ブラウザで観察した配置や挙動は事実として扱える。
「分かりにくいので離脱する」「信頼を失う」「順位が下がる」といった影響は、field dataまたは利用者調査がない限りHypothesisとする。

### 証拠metadata

Browser、HTTP、field、repositoryの全証拠へ、`source`、target originまたはproperty、取得日時、対象期間、URLまたはoriginの粒度、device、filter・aggregation、sampleの有無、対応するcommitまたはreleaseを記録する。
対応releaseを特定できない過去期間のdataを、現在deployの効果として扱わない。

field evidenceは次を別々の行へ記録する。

| Source | 記録と制約 |
|---|---|
| URL Inspectionのindexed result | Googleが最後に取得した版、最終crawl日時、Google-selected canonicalを記録する。現在deployのlive結果とはみなさない |
| URL Inspectionのlive test | 現在URLの取得・render・index適格性を記録する。Google-selected canonicalの予測には使わない |
| Search Console Performance | property、期間、search type、query・page・country・device filter、aggregation、fresh dataの有無を記録する |
| CrUX | URLまたはorigin粒度、device、28日rolling期間を記録する。現在deployだけの性能証明には使わない |
| RUM | target origin、release、期間、device・route・sampling・集計条件を記録する |
| Product analytics | event定義、対象release、期間、母数、filter、重複排除、consent・sampling条件を記録する |

URL Inspectionのindexed resultとlive testの違いは[GoogleのURL Inspection](https://support.google.com/webmasters/answer/9012289?hl=ja)、CrUXの粒度とrolling期間は[Chrome UX Report API](https://developer.chrome.com/docs/crux/api)を判断基準にする。

### 判定軸

三つの軸を混ぜずに記録する。

- **Claim**：`Confirmed`または`Hypothesis`。対象環境で再現できる観察事実だけをConfirmedにする。現在checkoutで確認したrepository contractだけを根拠にする画面・利用者影響はHypothesisとする。
- **Coverage**：`Reviewed`、`Sampled`、`Excluded`、`Blocked`。必要な環境、role、fixture、権限がなく安全に確認できない範囲はBlockedにする。
- **Measurement**：`Measured`または`Not measured`。Search Console、RUM、実利用者調査などのdata欠如はNot measuredであり、監査全体の停止理由にはしない。

コード上の事実だけを確認できた場合、実装事実は根拠へ書けるが、画面上の利用者影響はHypothesisのままにする。

## 5. 評価指標

### UXとタスク達成

| 観点 | Browserで記録するもの | 追加データで測るもの |
|---|---|---|
| 完了 | 完了可否、到着した状態、誤った完了、dead end | 実タスク完了率、誤完了率 |
| 効率 | 操作数、画面遷移数、scroll、戻り、再入力、待機 | 実所要時間の分布、頻度別の負担 |
| 情報階層 | 初期viewportにある目的、対象、状態、主CTA、阻害要因 | 5秒テストの正答率、最初の注視点 |
| 認知負荷 | 内部用語、記憶依存、対象の再確認、同時に強調される操作 | 利用者の発話、迷い、援助要求 |
| 状態と回復 | Loading、Empty、Error、Success、Acceptedの区別、取消、再試行 | エラー発生率、回復率、問い合わせ率 |
| モバイル | 情報順、片手での主操作、keyboard表示、長い名称、Dialog | 端末別完了率、端末別離脱率 |
| 信頼 | 料金・制約・運営主体・処理結果・問い合わせ先の表示事実 | 安心度、登録を止めた理由 |

AIブラウザが初期viewportを評価しても、人間の5秒テストを実施したとは表現しない。
手順数と所要時間も一つの環境における専門家レビューの値として扱い、実利用者平均と呼ばない。

### Performance

代表ページではLCP、INP、CLSと、意味のある表示段階を確認する。
Dashboardでは対象店舗表示、次の行動表示、募集一覧表示を分ける。

同じ条件で安全に測定できる場合は3回測定し、中央値と範囲を記録する。
開発buildの数値をProduction性能として評価せず、Browserのlab値とCrUX、Search Console、RUMのfield値を別表にする。

Core Web VitalsのGood目安は、75パーセンタイルでLCP 2.5秒以下、INP 200ms以下、CLS 0.1以下とする。
この閾値は[web.devのCore Web Vitals](https://web.dev/articles/vitals)を参照する。

### 公開ページSEO

- 実HTTP statusとsoft 404の有無
- robots、meta robots、`X-Robots-Tag`、canonical、sitemapの意図整合
- raw HTMLとrendered DOMにあるtitle、description、H1、主要本文
- page固有の検索意図と、title、H1、冒頭、CTAの一致
- `<a href>`による到達可能な内部リンクと説明的なanchor text
- PCとmobileでの主要本文、metadata、structured dataの同等性
- structured dataと画面表示内容の一致
- 更新日、運営主体、問い合わせ、料金・制約などの信頼根拠
- Search Consoleが利用できる場合のindex状態、Google-selected canonical、query、impression、click、CTR、平均掲載順位

Googleの最低技術要件を満たしてもindexは保証されないため、技術的なindex適格性と現在のindex状態を分ける。
判断基準は[Google Search technical requirements](https://developers.google.com/search/docs/essentials/technical)、[URL Inspection](https://support.google.com/webmasters/answer/9012289?hl=ja)、[Search Console Performance](https://support.google.com/webmasters/answer/7042828?hl=ja)を参照する。

### アクセシビリティのガードレール

次のいずれかが主要journeyを妨げた場合だけfindingへ含める。

- keyboardだけでは主CTA、店舗切替、Dialogの完了・終了を操作できない。
- focus trap、focus消失、固定要素による操作対象の完全な隠れがある。
- 重要なbutton、link、inputに理解できる名前またはlabelがない。
- 重要な状態やエラーを色だけで伝え、操作判断ができない。
- mobileまたは200%拡大時に主要内容や操作が失われる。
- Error、Saving、Loading、Successを区別できず、二重操作や行き止まりが発生する。
- Loginでpasteまたはpassword managerを妨げる。

共通部品の細かな規格違反、Lighthouse Accessibility score、全ページのcontrast一覧は作成しない。
主要journeyの通常操作中に観察できる重大阻害をguardrailとしてsmokeする。
Dashboard主CTA・店舗切替、公開header・CTA、認証form、スタッフ提出を横断する網羅的なkeyboard smokeや200%拡大は独立アクセシビリティ監査に含め、本監査のComplete条件にはしない。
未実施の範囲はExcludedまたはNot testedとして理由を記録する。

## 7. 非ログインページの代表群

固定routeと動的routeは、実行時に`scripts/staticSite.ts`、router、sitemap、画面navigationから再棚卸しする。

発見した具体URLは、代表操作の対象外でもcoverage matrixへ一行ずつ残す。
各行へURL、route type（SSG、CSR shell、alias、404）、canonicalとindex方針、template・family、確認深度、Coverage、HTTP・Browser結果、証拠IDを記録する。
深い操作は代表sampleでよいが、公開routeとCSR shellのtrailing slash、旧記事alias、未知記事slug、未知root URLは配信variantとして明示的に確認する。

| 群・代表route | 利用者の目的 | Browserで必ず確認すること | Production・field証拠 |
|---|---|---|---|
| 公開マーケティング `/` `/features` `/contact` | 価値と適合性を判断し、デモ・登録・相談へ進む | 初期viewport、価値と対象者、CTA優先度、navigation、formの入力・失敗・完了、PC/SPの情報順 | 200、raw HTML、metadata、canonical、CWV、query・CTR、CTA event |
| 記事 `/articles`、カテゴリ、代表記事、旧slug、未知slug | 検索課題を解決し、関連記事または製品理解へ進む | 検索意図、title/H1/冒頭、目次、更新日、関連記事、CTA、OGP、旧slug、404 | status、Google canonical、index、query・CTR、sitemap `lastmod` |
| FAQ・HowTo `/faq` `/howto#slug` | 短い結論または操作手順を見つけ、業務へ戻る | fragment直開き、検索、category、0件、FAQからHowTo、SPの到達距離 | raw HTML、単一canonical、JSON-LD、query集約、記事分離候補 |
| デモ `/demo/flow` `/demo/shiftboard` | 登録前に価値を体験し、導入判断する | 開始、進行、skip、reset、完了、再体験、CTA、PC推奨理由、SP代替、失敗回復 | 200、SSG本文、canonical、CWV、開始率・完了率・CTA率 |
| 認証 `/login` `/signup` `/forgot-password` `/sso-callback` | 認証または回復後に元の仕事へ戻る | redirect保持、入力・provider Error、Loading、再試行、戻る、autofill、SP keyboard | neutral CSR shell、noindex、no-store、no-referrer、canonicalなし |
| 管理者招待 `/manager-invite` | 招待対象を理解し、認証後に参加する | 正常、token欠落、期限切れ、使用済み、認証往復、参加後の到着先、回復文言 | noindex、no-referrer、tokenのHTML・referrer・analytics非露出 |
| スタッフCapability `/staff/register` `/shifts/*` `/legal/staff/consent` `/line/callback` | アカウントなしで登録、提出、閲覧、同意、再発行を完了する | smartphone優先、token状態、店舗・期間、入力・確認・完了、通信失敗、担当者への回復 | noindex、no-store、no-referrer、neutral shell、秘密値非露出 |
| 法務・信頼 `/terms*` `/privacy*` | 適用文書を確認し、同意または信頼判断をする | manager/staff版、更新情報、発見性、読みやすさ、戻り先 | 200、canonical、現在のnoindex方針、index方針の判断 |
| 404・utility | 誤URLや処理後から復帰する | 未知URL、未知記事、`/cache-reset`、`/account-deletion-accepted`、TOPへの復帰 | 実404、noindex、soft 404なし、Clear-Site-Data、no-store |

記事は一覧、カテゴリ、詳細、alias、not-foundを最低1件ずつ確認する。
スタッフCapabilityは入力系、閲覧系、callback系を最低1件ずつ確認し、残りはroute coverage表へ確認深度を残す。

## 8. デモの確認契約

デモはマーケティングページの一部として眺めるだけでなく、次の価値体験を独立して確認する。

- 利用者が自分で開始できる。
- 準備済みの問題から、製品価値を生む操作へ短く到達できる。
- 操作完了に応じて進行し、説明の「次へ」だけで進まない。
- skipが常に分かり、skipしても現在状態を破棄しない。
- resetの結果が予測でき、再読み込み後の状態も説明できる。
- 完了後も製品contextを保ち、再体験または登録を選べる。
- precision操作が必要なデモには、Mobileで代替またはPC継続の明示がある。
- `demo_loaded`、`tour_started`、`step_completed`、`aha_reached`、`cta_clicked`を計測できるか確認する。

実イベントが未実装の場合、監査失敗ではなく測定不能なfunnelとして記録する。

## 9. 実行フェーズ

### Phase 0: 環境と安全境界

1. 監査日時、target origin、local・preview・Production、commit、build種別を記録する。
2. 使用できるmanager role、招待・スタッフ用の安全なfixture、Search Console・RUM等の有無を記録する。
3. route、sitemap、navigation、主要Storyを棚卸しし、route familyごとの確認深度を決める。
4. Productionでは参照だけに限定し、test fixtureでない外部副作用を禁止する。
5. target originを特定できない場合はBrowser・HTTP phaseを開始せず、repositoryによるroute inventoryだけを継続する。
6. originは既知だがdeploymentまたはbuild種別を特定できない場合は`Environment: Unknown`とし、Production相当のread-only制約で継続する。availabilityとperformanceの環境依存claimはBlockedにする。

### Phase 1: 全体のbreadth pass

1. 全routeを直接開き、正常表示、navigation、HTTP status、index方針を確認する。
2. 発見した具体URLをcoverage matrixへ一行ずつ追加し、route type、index方針、確認深度、結果を記録する。
3. 各routeを`Reviewed`、`Sampled`、`Excluded`、`Blocked`のいずれかに分類する。
4. trailing slash、旧記事alias、未知記事slug、未知root URLの配信variantを確認する。
5. 固有テンプレート、主要CTA、Mobileの情報順、行き止まり候補を抽出する。
6. この段階では解決案へ飛ばず、再現すべきjourneyを確定する。

### Phase 2: Dashboardのtask pass

1. D1からD7を安全な環境またはStory fixtureで再現する。
2. 主タスク、完了条件、操作数、戻り、scroll、状態変化、回復可否を記録する。
3. Production、local、Storyの証拠を混ぜない。再現できない範囲はCoverageをBlockedとし、repository contractから推定する影響は別のHypothesisへ分ける。

### Phase 3: 非ログインjourneyのtask pass

1. 公開TOPから製品理解、デモ、登録・問い合わせへのjourneyを確認する。
2. 検索着地を想定して記事、FAQ、HowToを直接開き、疑問解決後の導線を確認する。
3. デモを開始から完了、skip、reset、Mobile代替まで操作する。
4. 認証・招待・Capabilityの正常・失敗・回復を、安全なfixtureの範囲で確認する。

### Phase 4: SEO、性能、field evidence

1. Production HTTP、raw HTML、rendered DOM、robots、sitemap、canonical、structured dataを確認する。
2. 代表テンプレートのlab performanceを同一条件で測る。
3. Search Console、CrUX、RUM、analyticsが利用できる場合だけfield evidenceを取得する。
4. field evidenceがない項目は問題なしとせず、Not measuredへ分類する。

### Phase 5: 統合と報告

1. 同じ根本原因による複数routeの症状を一つのfindingへ統合する。
2. Confirmed observationと、それを根拠にするHypothesisを分ける。
3. 維持すべきStrengthを先に特定し、改善で失わない契約を示す。
4. Confirmed problemだけに修正priorityを付け、Hypothesisには検証priorityを付ける。
5. Completeでは最終報告・改善計画、Partialでは中間報告を`doc/plans/`へ保存し、監査状態に合わせて`doc/plans/INDEX.md`を更新する。
6. チャットで結論、重要finding、未確認範囲、報告書へのlinkを伝える。

## 10. Findingの記録形式

各findingは次の項目を持つ。

| 項目 | 内容 |
|---|---|
| ID・Title | `D-UX-01`、`P-SEO-02`のような安定IDと短い題名 |
| Claim status | `Confirmed`または`Hypothesis` |
| Root evidence ID | 根拠となるConfirmed observationまたは現在checkoutのrepository contractのID |
| Finding type | `Problem`または`Strength` |
| Domain・Surface | UX、SEO、Performance、Trust、Accessibility guardrail。Public、Dashboard、Shared |
| Context | role、user goal、journey、route family、state、viewport、environment |
| Observation | 観察事実と判断基準。推測を混ぜない |
| Consequence | Confirmedでは観察済みの直接結果だけを書く。離脱・信頼・検索への未確認影響は別Hypothesisへ分ける |
| Evidence | screenshot、interaction、DOM、network、lab、field、repository contract |
| Reproduction | 手順、日時、環境、必要なfixture |
| Reach | 影響するrole、route family、template |
| Priority | Confirmed problemのP0からP4、またはHypothesisのPotential priority |
| Confidence | Low、Medium、Highと、その根拠 |
| Direction | 改善の方向。詳細実装は決めすぎない |
| Acceptance | 改善後に観察できる完了条件と検証方法 |
| Related IDs | 親となるevidence、派生Hypothesis、同じ根本原因の関連finding |
| Limitations | 未取得のfield data、利用者調査、環境差 |

証拠へ画面画像を残す場合は個人情報とtokenをredactする。
画像をrepositoryへ保存する必要がある場合だけ、`doc/archive/audits/YYYY/YYYY-MM-DD-ui-ux-seo-audit/`を使い、`doc/archive/INDEX.md`から参照する。

## 11. 優先順位

単一の総合UX点、SEO点、サイト点は作らない。
Confirmed problemだけに修正優先度を付ける。

### Confirmed problem

| 要素 | 段階 |
|---|---|
| Impact `I` | 4: task不能・誤確定・data loss・privacy露出。3: 重要な判断不能・高い失敗。2: 明確な遅延・往復。1: 局所的friction |
| Task criticality `C` | 3: 日常主要業務・初回価値・主要獲得導線。2: 主要タスクを支える管理・確認。1: 補助・低頻度。0: 装飾 |
| Reach `R` | 3: 全利用者または共通template。2: 主要roleまたはroute family。1: 特定条件。0: 極めて限定的 |
| Encounter likelihood `E` | 3: journeyで必ず遭遇。2: 一般的分岐。1: 低頻度分岐。0: 稀なedge case |

`Priority score = 4I + 3C + 2R + E`とする。

- P1: 26から34
- P2: 17から25
- P3: 8から16
- P4: 0から7

P0は数式で付けない。
広範な主要サービス停止、不可逆なdata loss、機密情報の公開、課金・削除などの重大な誤確定を対象環境でConfirmedにした場合だけoverrideする。

工数はpriorityから差し引かず、`Effort: S / M / L / XL`として別に記録する。
Impactが観察できない場合はConfirmed problemとして採点せず、Confirmed observationとimpact Hypothesisへ分ける。
数値に根拠がない場合は段階を推測せず、追加検証へ戻す。

### Hypothesis

Hypothesisには修正priorityを付けない。
確認された場合のPotential priorityと、検証によって変わる意思決定を示す。
Potential priority scoreは、仮説が確認された場合を仮定し、同じ`4I + 3C + 2R + E`で算出する0から34の値とする。
仮定したI、C、R、Eを個別に記録する。

`Validation value = Potential priority score × Decision leverage / Validation effort`を検証順の補助にする。

- Decision leverage 3: 情報設計・主要journey・価値訴求を変える。
- Decision leverage 2: 複数画面または共通componentを変える。
- Decision leverage 1: 局所調整だけを変える。
- Validation effort 1: 既存dataまたは短い追加Browser確認。
- Validation effort 2: instrumentationまたは短い利用者テスト。
- Validation effort 3: 継続計測または複数role調査。

HypothesisのRoot evidenceには、Confirmed observationまたは現在checkoutで確認したrepository contractを要求する。
repository contractだけを根拠にする場合は`Evidence layer: Repository`と明記し、画面・利用者影響をConfirmedにしない。
どちらの根拠もない自由な憶測は、最終報告・改善計画へ含めない。

## 13. 停止条件と安全境界

次の場合は対象範囲だけをBlockedにし、他の範囲は継続する。

- target originを特定できない場合、Browser・HTTP phaseを停止し、repositoryによるroute inventoryだけを継続する。
- originは既知だがdeploymentまたはbuild種別が不明な場合、`Environment: Unknown`かつProduction相当のread-only制約で継続し、availability・performanceの環境依存claimだけをBlockedにする。
- 必要なroleへ安全にloginできない。
- serverまたはrouteへ再試行と直接URLでも到達できない。
- Productionの不可逆操作または既存利用者data変更が必要になる。
- 通知、招待、課金、削除、確定共有を安全なfixtureなしに実行する必要がある。
- 個人情報、raw token、secretを記録・共有する危険がある。
- 対象origin外のサービス操作または新しい権限が必要になる。

Search Consoleやanalyticsへアクセスできないこと、CrUX dataがないこと、実機screen readerを使えないことは監査全体の停止理由にしない。
それぞれMeasurementをNot measured、またはCoverageをBlockedとして残す。

### Security Lens

- **Actor**：匿名の導入検討者、認証済み管理者、管理者招待の受領者、bearer linkを持つスタッフ、crawler。
- **Asset**：組織・店舗・スタッフdata、個人情報、capability token、通知、課金・削除状態。
- **Trust boundary**：公開ページ・CSR shell・backend、外部認証、検索crawler、analytics・referrer。
- **Abuse case**：tokenや個人情報の報告書混入、Production副作用、期限切れ状態からの列挙、非公開routeのindex。
- **Server-side enforcement**：本監査では実装の安全性を保証せず、画面と配信境界の観察に限定する。
- **Rate limit / idempotency**：Productionで連打・replay試験をせず、安全な下位テストの提案だけを行う。
- **Lifecycle / recovery**：欠落・期限切れ・使用済みtokenは安全なfixtureまたはStoryで確認する。
- **Logs / PII**：raw token、full email、氏名、実店舗dataをscreenshot、URL、報告書へ残さない。
- **Regression test**：改善提案ごとに必要な検証層を示すが、この監査ではtestを実装しない。

同じ条件で安全に測れる代表ページは3回測定し、中央値と範囲を記録してください。
開発buildの値をProduction性能と呼ばないでください。
Search Console、CrUX、RUM、analyticsが利用できない場合は問題なしとせず、Not measuredとして残してください。
field dataの各値にはsource、propertyまたはorigin、取得日時、対象期間、URLまたはorigin粒度、device、filter・aggregation、sampleの有無、対応releaseを付けてください。
URL Inspectionのindexed resultとlive test、Search Console Performance、CrUX、RUM、product analyticsを別々の証拠として記録してください。
CrUXの28日rolling dataや対応release不明の過去dataを、現在deployだけの効果として扱わないでください。

## 証拠とclaim

Claim、Coverage、Measurementを別軸にしてください。
ClaimはConfirmedまたはHypothesis、CoverageはReviewed・Sampled・Excluded・Blocked、MeasurementはMeasuredまたはNot measuredです。

全findingをConfirmedまたはHypothesisへ分けてください。
配置、文言、挙動、HTTP responseなどを対象環境で再現したものだけをConfirmedにしてください。
混乱、離脱、信頼低下、検索流入、実利用者性能への影響は、追加dataがない限りHypothesisです。

観察事実と影響解釈が混ざる場合は、Confirmed observationと、それを参照するHypothesisへ分割してください。
ConfirmedにはURL、role、state、viewport、環境、再現手順、観察結果、screenshot・DOM・network・trace等の証拠を必ず付けてください。
HypothesisにはRoot evidence ID、対象利用者、反証可能な検証方法、必要data、confidence、確認時に変わる意思決定を付けてください。
Root evidenceにはConfirmed observationまたは現在checkoutで確認したrepository contractを使えます。
repositoryだけが根拠なら`Evidence layer: Repository`と明記し、画面・利用者影響はHypothesisのままにしてください。

Confirmed problemだけに計画の式でP0からP4を付けてください。
Hypothesisには修正priorityを付けず、Potential priorityとValidation valueを付けてください。
Impactを観察できない場合はConfirmed problemとして採点せず、impact Hypothesisへ分けてください。
Potential priorityでは仮説が確認された場合のI、C、R、Eを個別に明記してください。
工数は`Effort: S / M / L / XL`としてpriorityと分離してください。

## 安全境界

Productionでは参照だけに限定してください。
安全なtest fixtureであると明示されていない通知、招待、課金、削除、確定共有、個人情報変更を実行しないでください。
必要な場合は確認画面までで止めるか、Story fixtureを使い、証拠レイヤーを明記してください。

raw token、full email、氏名、実店舗dataをURL、screenshot、trace、報告書へ残さないでください。
安全に進めない範囲だけをBlockedにし、他の監査は継続してください。
実装、修正、test追加、commit、push、Pull Request作成は行わないでください。

## 最終成果物

監査状態をComplete、Partial、Blockedのいずれかに判定してください。
Completeには、対象appのDashboard中心journey一件以上と公開側主要獲得journey一件以上を、DesktopとMobileの双方で実操作した証拠が必要です。

Completeなら、実行日の`doc/plans/YYYY-MM-DD_UI_UX_SEO全体監査_最終報告・改善計画.md`へ、計画の構成で最終成果を保存してください。
Partialなら`doc/plans/YYYY-MM-DD_UI_UX_SEO全体監査_中間報告.md`を保存し、この調査計画をActiveに残してください。
Blockedでもroute inventoryと阻害条件を保存し、この調査計画をActiveに残してください。

最終報告・改善計画は、時点監査を根拠とする採否未決のroadmapであり、現在仕様やProduction availabilityの正本ではないと明記してください。
参考にしたroute、機能文書、規約、コード、一次資料のpathまたはURLを記載してください。

Completeでは最終報告・改善計画を`doc/plans/INDEX.md`のProposedへ`reviewing`として追加し、この調査計画をHistoryへ移してください。
raw screenshot、trace、coverage snapshotをrepositoryへ保存する場合だけ、個人情報とtokenを除外して`doc/archive/audits/YYYY/`へ分け、`doc/archive/INDEX.md`を更新してください。
文書だけを変更し、`pnpm docs:check`と`git diff --check`を実行してください。

最後のチャットでは、監査状態、全体結論、監査scopeとBlocked scope、P0・P1、最重要Confirmed UX finding最大5件、最重要Hypothesis最大3件、field data gap、保存した文書へのlinkを簡潔に報告してください。

単発のLighthouse結果や最初に見つけた問題だけで終了しないでください。
安全に取得できる証拠を使い切り、残件が外部権限またはfixture待ちだけなら無期限に待機せずPartialとして終了してください。

# レスポンシブナビゲーションの実データ・操作接続 Phase 2 実装計画

作成日: 2026-08-14  
状態: Active（Phase 2-0から2-6と、Phase 2-7の新E2E・result gate artifactは実装済み。Phase 2-8の正式切替、canonical data readiness、Production・CI証跡は未完了）  
対象: `/app/*`の15画面、組織・店舗scope、既存業務機能の再接続、正式切替前の自動テスト  
対象外: 外部メール・LINE・Stripeの実到着確認、Production deploy、新しい課金仕様、既存データ形式の変更、分析画面、公開Capability画面のURL変更

## 1. 結論

[Phase 1](2026-08-14_レスポンシブナビゲーションと固定画面遷移_Phase1実装計画.md)で完成したレイアウトと画面遷移を維持し、固定fixtureを画面単位で実query、既存mutation、既存Dialogへ置き換える。

既存のquery、mutation、action、Dialog、controllerは削除せず、現在の業務契約を新しいページcompositionから再利用する。
すべてを包む新しいmutationや、未対応項目を複製保存する新tableは作らない。

最初に、店舗選択や先頭店舗fallbackに依存しない`activeOrg`の認証・認可境界を作る。
その後、Homeは既存の店舗scope APIへ、Shifts、Staff、Actions、Manageは新しい組織scopeのread APIへ接続する。

Storybook、Behavior Test、SP・PC VRT、Frontend Unit Test、Convex Function Test、Convex Scenario Test、E2Eを実装対象に含める。
各契約は一つの主担当層へ置き、同じシナリオを複数層で総当たりしない。

正式入口の切替と旧管理routeの削除は、15画面の実データ接続と自動テストが完了した後の最終phaseとする。

2026-08-14時点で、`/app/*`の15画面はproduction routeから実page、canonical organization scope、既存Dialog・controllerへ接続した。
`AppNavigationPrototype`はStorybookの固定fixtureとしてのみ残し、production routeからのimportは0件である。

一方、旧routeの正式切替、認証後default・既発行URLの変更、migration readiness確認、Production deploy、CI VRT、core E2Eの全件実走は行っていない。
そのため、本計画はPhase 2-8を未完了のまま`Active`に置く。

## 2. 完了条件

Phase 2は、次をすべて満たした時に完了とする。

- `/app/*`の15画面が、固定fixtureではなく認証中の組織・店舗・人物・募集を表示する
- Homeは選択した1店舗、Shiftsは組織内の店舗ごとのシフト、Staffは組織全体の人物、Actionsは組織内の未解決業務、Manageは組織設定を表示する
- 読み込み、空、失敗、閲覧のみ、契約制限、処理中、成功の各状態が既存UI規約で表示される
- 募集作成、スタッフ追加、LINE連携、所属変更、申請審査、通知復旧、管理者招待、組織・店舗編集、課金、アカウント操作が既存Dialogまたは既存集中フローから実行できる
- Headerの要望送信がstaleな`selectedShopAtom`に依存せず、activeOrgと明示shopの一致をserverで検証する
- 画面表示後に権限や対象状態が変わっても、mutation側の再検証で他組織・他店舗・処理済み対象を変更できない
- 固定fixtureと`Prototype*`のproduction importが0件になる
- 新しい組織scope queryが店舗数分のclient subscriptionを作らず、明示した上限内で返る
- Storybook、Behavior Test、VRT、Frontend Unit、Convex Function・Scenario、E2Eの契約表に未分類がない
- 既存13件のcore E2Eを新routeへ更新し、navigation用の代表契約1件を加えた14件がskip、retry、flakyなしで通る
- `pnpm test`、`pnpm type-check`、`pnpm lint`、`pnpm build`が通り、CIのVRTとPlaywright差分を確認できる

外部providerへの実配送、決済完了、Production反映は、この完了条件に含めない。

## 4. scopeとURLの契約

### 4.1 3つの状態を分ける

| 状態 | 意味 | 変更元 | 利用画面 | 認可への利用 |
|---|---|---|---|---|
| `activeOrg` | 現在表示している組織 | Homeの組織選択、初回canonical解決 | Home以外を含む業務画面全体 | serverでcanonical membershipを再検証する |
| `homeShop` | Homeに表示する1店舗 | Homeの店舗selector | Homeだけ | Homeのshop-scope APIへ明示的に渡す |
| `shopFilter` | 組織全体一覧の表示を店舗で絞る | Staff、Actionsのfilter | Staff、Actionsだけ | 認可には使わず、serverで同一組織かを検証する |

Shiftsはfilterを置かず、組織内の店舗を縦に並べる。
Manageは店舗一覧自体をdrilldown入口にするため、`shopFilter`を持たない。

`すべて`は店舗IDではない。
`ShopContextOption`やmutation引数へ架空の店舗として混ぜない。

### 4.2 route searchのallowlist

Phase 1の「`/app/*`は全searchを除去する」契約を、画面別allowlistへ置き換える。

| route | 許可するsearch | 用途 |
|---|---|---|
| `/app/home` | `org`, `shop` | activeOrgとhomeShop |
| `/app/shifts` | `org` | 店舗別に並べる組織 |
| `/app/staff` | `org`, `shopFilter` | 組織全人物と任意の店舗絞り込み |
| `/app/actions` | `org`, `shopFilter` | 組織内の未解決項目と任意の店舗絞り込み |
| `/app/manage*` | `org` | 管理対象の組織 |
| `/app/staff/:personId*` | `org` | 人物と組織の一致検証 |
| `/app/shifts/:recruitmentId/board` | `org` | 募集と組織の一致検証 |
| `/app/account` | `flow`, `oauth` | 既存LoginMethodsの復帰契約 |

未知のsearch、空値、許可されない組み合わせは、認証復帰URLを作る前に除去する。
`token`、`code`、`state`などを別routeへ持ち越さない。

未指定の`org`は、認証済み利用者が所属するcanonicalな候補から初期値を選び、`replace`でURLへ正規化する。
明示された`org`が候補外なら別組織へfallbackせず、「この組織を開けません」を表示する。

### 4.3 canonical organization context

新しい`listMyOrganizationContexts`は、Clerk identityからusers、`organizationMembers`、`organizationPeople`を直接検証し、利用可能な組織をcursor paginationで返す。
所属組織数は固定上限を仮定しない。
organization rowへ全店舗をinlineせず、Homeで選択できるactive店舗は`listOrganizationActiveShops`からcursor paginationで取得する。

`maxActiveShops`は新規作成を制限するentitlementであり、保存済みactive店舗数のcardinality保証には使わない。
restricted・migration途中・過去仕様の組織ではactive店舗数が上限を超え得るため、安全なpage sizeとoverflow状態を使い、黙ってtruncateしない。

URLに明示された`organizationId`は、selector一覧の取得済みpageから探さず、`getOrganizationContext({ organizationId })`で直接canonical membershipを検証する。
これにより、一覧の2page目以降にある組織を「候補外」と誤判定しない。

組織全体のqueryには、必須`organizationId`を持つ`organizationQuery`を追加する。

- queryは`active`または`readOnly`のcanonical memberだけを許可する
- mutationは原則`active` memberだけを許可する
- person、user、member、organizationの一意な対応を検証する
- 削除済み組織を返さない
- `shopMembers`だけのlegacy fallbackを組織authorityに使わない
- clientから渡された組織名、店舗一覧、plan、capabilityを信頼しない

通常の組織業務writeだけを共通`organizationMutation`へ載せる。
課金復旧、削除、管理者交代など独自capabilityを持つ既存action・mutationは、既存serviceの認可を維持する。

既存routeが利用するpublic query、mutation、actionの引数を曖昧なoptional `organizationId`で拡張しない。
旧入口は現在のsignatureを維持し、新画面にはorganization-scopeの兄弟functionを追加するか、両方から呼ぶinternal serviceへ既存処理を抽出する。
正式切替後も、業務use-caseのmutationと外部副作用契約は削除しない。

新画面からshop・person・recruitmentを対象にするread、write、actionは、`expectedOrganizationId`と対象IDをserverへ渡す。
serverはactorをcanonical organization memberとして解決した後、対象entityの`organizationId`が`expectedOrganizationId`と一致することを確認する。
既存APIがshopを認可anchorにしている場合も、画面表示中のorganizationと対象shopの一致をclient判定だけに任せない。

管理者招待、課金、組織情報のようにasset自体がorganization-scopeの操作は、app用兄弟functionで`organizationId`を直接受け、canonical organization actorを解決する。
これらの操作に、先頭店舗や現在のHome店舗を認可anchorとして要求しない。

canonical membershipが未整備の利用者は、先頭店舗で黙って続行せず移行待ち状態を表示する。
正式切替は、既存migrationのreadiness検証でlegacy-only対象が残っていないことをgateにする。

### 4.4 正式切替のcanonical data readiness

正式切替する各deploymentについて、完全修飾deployment名と対象revisionを固定し、次を一組の証跡として記録する。

- m025からm028が`isDone: true`かつ`state: "success"`
- 専用runnerのm029が`isDone: true`かつ`state: "success"`
- `verifyShops`、`verifyOrganizations`、`verifyStaffs`、`verifyLegacyShopMembers`、`verifyOrganizationMigrationConflicts`を`isDone: true`まで全page走査
- `verifyShops`のorganization・operating status欠損、dangling、scope anomalyが0件
- `verifyLegacyShopMembers.activeRows: 0`
- 関連readinessの`anomalies`・`unresolvedRows`と未解消migration conflictが0件

status成功とreadiness 0件は別々に確認する。
一つでも未達ならPhase 2-8を停止し、旧routeとlegacy fallbackを削除しない。
m029の実行やProduction操作は本計画の作成・承認だけでは許可せず、[Narrow Migrationの運用](../manual/narrow-migrations.md)に従って対象deploymentごとに別途判断する。

## 5. frontendの責務分担

### 5.1 page、container、View

| 層 | 責務 |
|---|---|
| route | params/search validation、head、shell宣言、page呼び出し |
| page | activeOrg解決、route-wide query、entity不在、初期Loading・Error |
| feature container/controller | Dialog状態、mutation/action、single-flight、Toast、reactiveな再取得後の整合 |
| View・Section | propsから表示し、業務queryやrouterへ依存しない |

`AppNavigationPrototype`へ実queryを追加してproduction container化しない。
画面ごとのpage moduleへ分け、純粋ViewだけをStorybookから使用できる形にする。

候補は次のとおりとする。

```text
src/pages/app-home/
src/pages/app-shifts/
src/pages/app-staff/
src/pages/app-actions/
src/pages/app-manage/
```

既存の`src/pages/shift-board/`、`user-detail/`、`user-shop-detail/`、`manager-settings/`、`shop-detail/`、`account-security/`は、routeとnavigation callbackを差し替えて再利用する。

### 5.2 明示的な対象ID

新しい画面から既存shop-scope mutationを呼ぶ時は、globalな`selectedShopAtom`から対象を推測しない。

- Homeの操作は`homeShop.shopId`
- Shiftsの操作は店舗sectionが持つ`shopId`
- Action itemの操作はquery DTOが返したorganizationまたはshop scopeと対象ID
- 詳細画面の操作はroute paramをserverで検証して得た対象ID

既存controllerは`expectedOrganizationId`、対象`shopId`またはorganization-scopeのmutation adapterをpropsで受け取れるようにし、旧routeでは現在の`useShopMutation`をそのまま利用できる後方互換を保つ。

### 5.3 shellのscope付き導線

primary navigationだけでなく、Header brand、detailの戻る、focused flowの戻る、ページ内CTAも現在の`org`を引き継ぐ。
共通のnavigation target resolverでrouteごとのsearch allowlistを通し、文字列連結でsearchを複製しない。
`/app/account`は組織から独立するため`org`を持ち込まず、AccountからHomeへ戻る時はcanonicalなdefault organizationを改めて解決する。

Headerの「要望を送る」は、`hasSelectedShopAtom`と`useShopMutation`へ依存させない。
app用`FeatureRequestAction`へ`activeOrg`と明示shopを渡し、backendの兄弟mutationでorganizationとshopの一致を確認する。

- Homeとshop detailでは、画面でserver検証済みのshopを既定にする
- Shifts、Staff、Actions、Manageなど組織全体画面では、Dialog内でactive店舗を明示選択してから送信する
- active店舗がない場合は送信入口を無効にし、問い合わせなど利用可能な代替導線を示す
- Accountはorganization非依存のため、app用要望入口の対象外にする

既存`featureRequests.shopId`とrate limit、requestId冪等性を維持し、初期Phase 2で保存形式を変更しない。
旧routeの`FeatureRequestAction`は現行signatureのまま残す。

### 6.2 Home

Homeだけは店舗scopeの完成済みDashboard APIのservice・DTOを再利用する。
app用query adapterへ`expectedOrganizationId`と`homeShop`を明示し、serverで両者の一致を確認して次を購読する。

- `getDashboardShop`
- `getDashboardPlanUsage`
- `getDashboardRecruitments`
- `getDashboardStaffs`
- 必要な時だけ`getPendingRequests`
- 必要な時だけ`listOpenFailures`

組織や店舗selectorの選択後に、前の店舗のデータを新しい見出しの下へ残さない。
route-wide contextが切り替わる間は既存Skeletonを表示し、旧query結果を別店舗の結果として描画しない。

### 6.3 Shifts

clientから店舗数分の`getDashboardRecruitments`を購読しない。
`listOrganizationRecruitments`をactive店舗単位のcursor paginationにし、serverでcanonical orgを確認して店舗ごとの現在募集を返す。
一つのpaginated query familyを使い、`shops.map(() => useQuery(...))`にはしない。
page sizeは安全な固定上限を持つが、`maxActiveShops`を返却上限にせず、制限超過中のactive店舗にも追加pageから到達できるようにする。
archived店舗は日常シフト画面へ混ぜず、Manageのstatus別一覧から確認・再開する。

返却は店舗ごとの次の構造とする。

```ts
type OrganizationRecruitmentSection = {
  shop: { shopId: Id<"shops">; shopName: string; operatingStatus: ShopStatus };
  currentGroups: DashboardRecruitmentGroup[];
  hasPastRecruitments: boolean;
  actions: { canCreate: boolean; createDisabledReason?: string };
};
```

過去募集は初期DTOへ無制限に含めない。
利用者が店舗sectionの履歴を開いた時だけ、その店舗の既存paginated queryを明示`shopId`で開始する。

募集作成・削除は既存mutationを使い、各店舗sectionが対象shopをcontrollerへ渡す。
作成成功後は該当店舗sectionへreactiveに現れ、削除成功後は該当行だけ消える。

### 6.4 Staff

`getSettings`を人物一覧のread modelとして流用しない。
同queryはpeople、shops、members、招待履歴、LINE、billingを同時に読み、組織全体一覧には広すぎる。

`listOrganizationPeople`はcursor paginationとし、1pageの安全な上限内で次だけを返す。
`maxPeople`は新規追加を制限するentitlementであり、保存済み人物数のcardinality保証には使わない。
restricted・migration途中・過去仕様で上限を超えた人物にも追加pageから到達でき、整理・削除による復旧を妨げない。

- person ID、表示名、連絡先の表示用値
- manager role
- LINE連携状態
- 所属shop IDと表示名
- 人物rowで必要なcapability
- 全件数、表示件数、上限

`shopFilter`は`all | shopId`とし、shop指定時はserverで同一organization、非削除状態を確認する。
filterはpaginationより前にserver側で適用し、filter変更時は前のcursorと表示済みpageを破棄する。
一覧rowの店舗表示と詳細遷移は既存`PeopleSection`の見た目を維持する。

スタッフ詳細、LINE連携、所属変更、削除は既存`UserDetail` controllerとDialogを再利用する。
人物IDだけでなく`person.organizationId === activeOrg`をqueryとmutationの両方で確認する。

### 6.5 Actions

`getActionInbox`は、source tableを複製せず次の4種類を最小DTOへ投影する。

1. 締切済み・未確定などシフト調整が必要な募集
2. pendingのスタッフ登録申請
3. managerが復旧できるopen notification failure
4. `sendFailed`、`limitReached`、`conflict`の管理者招待

各sourceと全体に明示した上限を設け、priority、発生時刻、stable item IDで順序を固定する。
返却DTOには`kind`、対象scope、対象ID、表示用最小metadata、capability、時刻を含める。

`shopFilter`は`all | shopId`をquery引数にする。
`all`はorganization-scope itemと全shop-scope itemを含み、shop指定時は同一organizationをserverで確認したうえで、そのshop-scope itemだけを含める。
shop指定時のmanager invitationなどorganization-scope itemは除外する。
filterはsource別上限と全体上限を適用する前にserver側で適用し、別店舗のitemが上限を消費して対象店舗のitemを隠さないようにする。

対象scopeは、店舗業務と組織業務を混ぜず次のdiscriminated unionにする。

```ts
type ActionInboxScope =
  | { kind: "shop"; organizationId: Id<"organizations">; shopId: Id<"shops"> }
  | { kind: "organization"; organizationId: Id<"organizations"> };
```

shift、staff registration、notification failureはshop scope、manager invitationはorganization scopeとする。
管理者招待のために先頭店舗や現在のHome店舗を認可anchorとして選ばない。
org-scopedの招待再送・取消境界を追加し、canonical organization actorと招待のorganization一致を直接確認する。

初期queryは次を返し、上限超過を0件と同じ状態にしない。

```ts
type ActionInboxPage = {
  items: ActionInboxItem[];
  continuationByKind: Partial<Record<ActionInboxItem["kind"], string>>;
  hasMoreByKind: Partial<Record<ActionInboxItem["kind"], boolean>>;
  nextRefreshAt?: number;
};
```

`hasMoreByKind`がある時は「さらに表示」からsource別continuationを取得し、stable item IDで重複を除いて同じpriority順へ追加する。
continuationにはorganization、filter、並び順のsnapshotを結び付け、scope変更後のcursorを再利用しない。
これにより、上限より古い未対応itemにも到達できる。

締切到来のような時刻だけで変わる判定は、serverの現在時刻を正本にする。
queryは次に分類が変わる`nextRefreshAt`を返し、clientはその時刻とtab再表示時に無害なrefresh bucketを更新して再購読する。
refresh bucketは再実行の契機にだけ使い、client時刻を締切判定や認可へ使わない。

Action itemのcard registryを作らず、`ActionInboxItem`のdiscriminated unionとuse-case別adapterを維持する。
すべてを処理する`resolveAction` mutationは作らない。

| item | 既存操作 | UI完了条件 |
|---|---|---|
| shift | シフト表へ遷移 | focused routeが開く |
| staff registration | `approveRequest`、`rejectRequest` | 成功後にqueryから対象itemが消える |
| notification failure | `resendFailure`、`resolveFailure` | 受付成功後に対象状態を再取得し、対象itemが消えるかretrying表示になる |
| manager invitation | `resend`、`revoke` | 招待version・statusの更新後にitemが消えるか新状態になる |

cardは現在のフラットUIを維持する。
再送や承認のために一覧全体をDialogへ戻さない。
却下、対応済み、取消など結果を取り消しにくい操作だけ、既存確認Dialogまたは同じ規約の確認Dialogを使う。

成功時の右退場と繰上げは、mutationの受付成功後だけ開始する。
失敗時はcardを残し、inline errorと`aria-live`で再試行可能な状態を示す。
「受付」「再送を開始」とproviderへの実到着を区別する。

### 6.6 ManageとAccount

Manage topは`getSettings`全体を購読せず、組織名、plan、利用数、管理者数、店舗status別件数、capabilityだけを返す`getManageOverview`を使う。
店舗実体は`listOrganizationShops`からcursor paginationで取得する。
`maxActiveShops`は新規作成のentitlementであり、保存済みactive店舗数は超過し得る。
archived店舗も累積して5件を超え得るため、全非削除店舗を5件でtruncateしない。

組織名、組織作成、店舗追加・編集、所属スタッフ、管理者、課金のViewとDialogは既存実装を再利用する。
旧`/settings`や`/dashboard`への遷移をcomponent内部へ固定せず、完了先と戻り先をcallbackで注入する。

課金actionは既存のserver-side actor、purpose、永続operation、Stripe idempotency key、leaseの契約を変えない。
新画面から開始するbilling actionは`organizationId`を直接受け、canonical organization actorとbilling対象organizationの一致をserverで確認する。
app用actionで先頭店舗やHome店舗を認可anchorにしない。
新規sessionの`return_url`は`/app/manage/billing?org=...`へ更新する。

切替前に発行済みのCheckout・Customer Portal sessionはreturn URLを書き換えられない。
一般的な旧route互換は追加しないが、`/settings?tab=billing`だけは既発行sessionの復帰専用compat routeとして猶予期間中維持する。
切替時刻より前に作成されたsessionがproviderの最大有効期間と安全bufferを越えたことを確認してから、このcompat routeを削除する。

組織・店舗・アカウント削除は、受付を物理削除完了と表示しない。
既存の`accepted`、`processing`、`completed`、`actionRequired`相当の状態と復旧導線を維持する。

`/app/account`は組織scopeから独立する。
LoginMethodsの`flow`とGoogle OAuthの`oauth`だけを許可し、組織・店舗searchを受け取らない。

### 8.2 partial failure

組織全体の初期queryは一つの整合単位とし、途中のread失敗を空店舗へ変換せずpage Errorにする。
初期queryとは独立して遅延mountした過去履歴やDialog previewの失敗は、取得済みの他sectionを消さず局所Errorにする。
認可やtenant整合性の失敗はpartial表示せず、組織全体をfail closedにする。

Actionsの集約queryはsource別内部失敗を黙って空件数へ変換しない。
integrity errorは明示的な状態として返し、0件と区別する。

### 9.1 新規・変更するread境界

| API候補 | scope | 上限 | 用途 |
|---|---|---|---|
| `listMyOrganizationContexts` | authenticated user | cursor pagination、店舗はinlineしない | 組織selectorのcanonical候補 |
| `getOrganizationContext` | authenticated user + organization | 1組織のsummaryとcapability | URLで明示されたactiveOrgの直接認可 |
| `listOrganizationActiveShops` | organization | cursor pagination、entitlement超過をtruncateしない | Home店舗selector |
| `listOrganizationRecruitments` | organization | active店舗単位のcursor pagination、店舗ごとのcurrent候補上限 | Shifts |
| `listOrganizationPeople` | organization + `shopFilter` | cursor pagination、entitlement超過をtruncateしない | Staff |
| `getActionInbox` | organization + `shopFilter` | source別上限＋総件数上限、kind別continuation、`nextRefreshAt` | Actions |

既存helper、validator、presentation DTOを再利用し、公開queryの返却に内部document、token、provider error、不要なemail履歴を含めない。

### 9.2 N subscriptionを避ける

Shifts、Staff、Actionsのpage componentで、`shops.map(() => useQuery(...))`を作らない。
組織全体の一つのqueryまたはpaginated query familyでbounded mergeし、対象店舗の詳細・過去履歴・Dialog用previewだけを利用者操作後に遅延購読する。

現在のplan上限はactive店舗5、人40だが、read側のcardinality保証には使わない。
Shiftsなどactive店舗だけを扱う画面も、restricted・migration途中の超過を想定したcursor paginationにする。
Staff、archivedを含む店舗一覧、所属組織一覧も同様にcursor paginationを使う。
`collect()`へ依存せず、`take(limit + 1)`またはpaginateでoverflowを検知する。

### 9.3 schemaとmigration

初期Phase 2では新table、persisted field、backfillを追加しない。
`actionInbox`をmaterializeしない。

既存のshops、organizationPeople、organizationMembers、recruitments、staffRegistrationRequests、notificationFailureInbox、organizationInvitationsのindexで実装する。

実装時のread計測で既存indexではbounded queryを成立させられない場合だけ、index追加を別変更単位にする。
既存documentが新schemaに合わなくなる場合は、本計画へ直書きせず`convex-migration-helper`でwiden-migrate-narrow計画を追加する。

将来、店舗上限を5より増やし、全sourceを厳密な一つの時系列で無制限paginationする要件が出た時だけ、organizationIdのdenormalizeやmaterialized inboxを再検討する。

### 9.4 横断設計の確認

| 観点 | 完成形 |
|---|---|
| actor | Clerk identityからcanonical user・member・personを解決する |
| tenant | `activeOrg`を主境界にし、shop・person・recruitment・request・failure・invitationをその配下で再検証する |

## 10. Security Lens

| 観点 | 本計画の契約 |
|---|---|
| Actor | Clerk identityに対応するcanonical user、organization member、organization person。readは`active/readOnly`、通常writeは`active` |
| Asset | 組織・店舗、募集・割当、スタッフPII、登録申請、通知失敗、管理者権限・招待、契約・請求、削除状態 |
| Trust boundary | browserの`org`、`shop`、`shopFilter`、entity ID、request ID、表示中capabilityはすべて不信。Convex public functionで再検証する |
| Abuse case | 他組織IDOR、他店舗itemの操作、権限喪失後のstale mutation、再送連打、同一request replay、削除受付を完了と誤表示、PII・tokenのlog流出 |
| Server enforcement | identityからmembershipを解決し、`expectedOrganizationId`、organization、shop、entityの一致、削除・status、billing、capacityをqueryとmutationで確認する。organization-scope itemにshop fallbackを使わない。DTOの`can*`は表示用 |
| Rate limit・idempotency | notificationはrate limitとfailure state・Outbox dedupe、管理者招待と課金はrequestId・version・永続operation、登録申請はpending state遷移で重複を拒否する |
| Lifecycle・recovery | 通知はacceptedとdeliveredを分離する。組織・店舗・account削除はaccepted、processing、completed、actionRequiredを分離する |
| Log・PII | route template、scope kind、action kind、結果categoryだけを記録し、氏名、email、token、provider error全文を出さない |
| Regression | 別org、画面org=A/対象shop・entity=B、organization itemへのshop混入、removed/readOnly、削除済み、stale、二重操作、拒否時副作用0件をFunction・Scenario Testで守る |

Action itemには、実mutationへ渡すorganizationまたはshop scopeとtarget IDをserver DTOから含める。
現在のHome店舗やfilter値から対象scopeを推測しない。

## 15. release gateとrollback

### 15.1 release gate

- fixed fixtureを参照する新routeがない
- 正式切替対象deploymentでm025からm029のstatus成功と、4.4の全page canonical readiness 0件が確認済み
- 所属組織一覧のpaginationと、明示organizationの直接canonical認可が確認済み
- activeOrgが先頭店舗やlegacy membershipへfallbackしない
- org-wide queryがboundedで、clientの店舗数分subscriptionがない
- entitlement超過中のactive店舗を黙ってtruncateせず、追加pageから到達できる
- archived店舗をactive店舗上限でtruncateせず、paginationで到達できる
- entitlement超過中の人物を`maxPeople`でtruncateせず、paginationで到達できる
- readOnly、restricted、削除済み、別tenantの負契約が通る
- Dialogの二重送信、close、error recoveryが通る
- Action inboxのexact setと副作用集合が通る
- 新Stripe URL発行への切替と、旧session用billing returnの猶予・削除時刻が記録されている
- E2E 14 contractとVRT差分が確認済み
- 現行機能文書を新routeと新scopeへ更新済み

### 15.2 rollback

正式切替前は旧routeを維持するため、画面単位で新page importを固定Viewへ戻せる。
新しいread queryは既存tableを変更せず、旧queryと併存できる。

正式切替後のrollbackは、旧route entryを同じcommitから戻し、Header・認証後default・生成URLを旧routeへ戻す。
mutationや永続データのrollbackを必要とする設計にしない。

切替前後に発行されたStripe sessionのreturn URLは書き換えられない。
rollback可能期間中も新旧両方のbilling returnを受けられるよう、復帰専用compat routeはproviderの最大有効期間と安全bufferを満たすまで先に削除しない。

Stripe operation、通知Outbox、削除cleanupなど、すでに受け付けた外部・非同期処理はUI rollbackで取り消さない。
既存のstatusと復旧手順で完了またはactionRequiredを扱う。

## 16. 主なリスク

| リスク | 対策 |
|---|---|
| `selectedShopAtom`をactiveOrg authorityにして別組織を読む | canonical org contextとrequired `organizationId`を先に実装する |
| Header要望送信がstaleな旧店舗へ紐づく | app用FeatureRequest adapterでactiveOrgと明示shopをserver検証する |
| brand・戻る導線で`org`を落として別組織へ移る | primary以外も共通navigation target resolverを使いUnit・Behaviorで守る |
| 画面org=Aのままshop・entity=Bの既存APIを呼べる | app用境界で`expectedOrganizationId`を必須にし、serverで対象organizationとの一致を検証する |
| 管理者招待を現在店舗へ誤って結びつける | Action scopeをorganization/shop unionにし、招待はcanonical org actorで直接認可する |
| Shifts・Actionsで店舗数分queryを購読する | server-side bounded mergeを一つのqueryまたはpaginated query familyで返す |
| entitlement超過店舗、archived店舗、多数の所属組織を固定上限で欠落させる | entitlementとread上限を分け、組織・店舗一覧をcursor paginationする |
| entitlement超過人物がStaffから見えず整理できない | `listOrganizationPeople`をfilter適用後のcursor paginationにする |
| Action上限より古いitemへ到達できない | kind別continuationと`hasMoreByKind`を返し追加取得する |
| 画面を開いたまま締切を越えてもActionが更新されない | server判定の`nextRefreshAt`とrefresh bucket、visibility再取得を使う |
| `getSettings`を全画面で使いread量とPIIを増やす | 画面目的別の最小DTOを追加する |
| cardのfilter店舗でmutation対象を推測する | query DTOのorganization/shop scopeとtarget IDを使いserverで再認可する |
| stale画面から権限喪失後も操作できる | mutationでmembership、status、billingを再判定する |
| 再送二重clickで通知・招待が重複する | frontend single-flightとbackend rate limit・version・dedupeを両方維持する |
| `/app/*`のsearch除去がAccount OAuthを壊す | route別allowlistとUnit Testを先に実装する |
| 既存controllerが旧URLを内部に固定する | navigation callbackを注入し、旧routeと新routeで分ける |
| acceptedをdelivered・deletedと誤表示する | lifecycleごとの状態とマイクロコピーを維持する |
| 既発行Stripe sessionが削除済み旧URLへ戻る | billing returnだけ猶予期間を維持し、provider TTL drain後に削除する |
| StorybookとE2Eで同じ表示を重複検証する | UI操作はBehavior、見た目はVRT、実接続だけE2Eへ置く |

# CSR画面遷移パフォーマンス改善 実装計画

作成日: 2026-08-03  
状態: implemented  
対象: メインアプリのCSR遷移、表示ライフサイクル、frontend bundle

## 1. 目的

主要なCSR遷移の体感待ち時間と、非表示UIが持つ不要な購読を減らす。
APIの呼び出し箇所数だけを原因とせず、主要contentを止める依存、query waterfall、購読の生存時間、初期bundleを調査してから変更対象を選ぶ。

調査結果から効果が高く安全に変更できる上位3から5導線を選び、フロントエンドの実装、Frontend Unit Test、Storybook Behavior Test、production buildの確認まで完了する。

## 5. 調査と対象選定

route、page、主要featureを確認し、候補導線ごとに次を整理する。

| 項目 | 確認内容 |
|---|---|
| route成立 | page全体をLoadingにしているqueryと、その必要性 |
| critical path | 主要contentの表示を止めている依存とwaterfall |
| 非表示UI | tab、Dialog、折りたたみ領域が非表示中も購読していないか |
| viewport | 初期表示に不要な下位sectionが先にmount、import、購読されていないか |
| module | 大きなfeature、form、chart、tour、外部SDKが初期chunkへ入っていないか |
| preload | 遷移確率と通信量に見合うroute preload候補があるか |
| prewarm | queryと引数を共有でき、副作用なく有限時間だけ先行取得できるか |
| 状態保持 | unmountによって入力、scroll位置、未確定状態を失わないか |
| 失敗境界 | chunkまたはAPI取得失敗が画面全体へ波及しないか |
| 検証 | 変更契約を直接守る既存Unit Test、Story、Behavior Testがあるか |

選定では、APIの本数ではなく次を評価する。

- 利用者を待たせるcritical path
- queryの依存関係と読み取り量
- 購読数、生存時間、invalidationsの範囲
- 初期routeが読むJS総量
- 遅延chunkの大きさと個数
- 操作感、状態保持、回復導線への影響

runtimeの安定した計測が得られない場合は、p50やp95を推測しない。
その場合は、依存関係、購読開始条件、bundle差分を選定根拠にする。

## 6. 実装契約

### 段階表示とquery waterfall

ページ全体を止めるqueryは、認証、主要entity、操作の安全性に必要な成立判定へ限定する。
補助情報はsection単位のLoading、Empty、Errorを持ち、取得済みの兄弟sectionをSkeletonへ戻さない。

互いの結果を引数に使わないqueryは並列に開始する。
queryを統合する目的でbackend契約を変更せず、フロント側の開始条件とLoading境界を整理する。

### 非表示UIと状態保持

Dialog、非選択tab、折りたたみ領域、viewport外の専用queryは、表示条件が成立するまで`"skip"`または既存の無効化手段で停止する。
CSSによる非表示だけで購読停止とみなさない。

重いsubtreeでは既存UI primitiveの`lazyMount`を検討する。
`unmountOnExit`は、入力、scroll位置、未確定状態を破棄してよい場合だけ使う。
状態保持が必要な場合は、subtreeを保持して専用queryだけ停止する。

### Moduleのlazy loadと失敗境界

大きなform、editor、chart、tour、外部SDKをdynamic importの候補とする。
小さなleaf componentを細分化せず、routeまたは独立したfeatureの境界を優先する。

lazy moduleには対象領域と対応するLoadingとError Boundaryを置く。
chunk取得失敗やdeployment更新後の不整合を対象領域へ閉じ込め、必要に応じて再試行または再読み込みへ進める。

query引数が確定している場合は、module preloadと副作用のないreadを独立して開始してよい。
moduleの評価とmountが終わるまでread開始も待つ新しいwaterfallを作らない。

### Preloadとprewarm

route遷移は既存のTanStack RouterのLinkとpreload機能を優先する。
hover、focus、pointer intentなど、遷移確率が高まった時点でroute moduleをpreloadしてよい。
一覧の全行や未表示の全routeを一括でpreloadしない。

queryをprewarmする場合は、queryと引数が表示先の購読と一致し、引数が決定的で、保持時間と総購読数を制限できることを確認する。
paginated query、時刻や乱数で変わる引数、一覧行ごとの大量購読は対象にしない。

preload、hover、focus、viewport進入からmutation、通知、課金変更などの副作用を実行しない。
preloadが失敗しても通常のclick経路で同じ結果へ到達できるようにする。

### Viewport遅延

長いページの下位にある補助sectionは、viewportへ入る少し前にmoduleと副作用のないreadを開始してよい。
初期viewport内の主要作業、認証、認可、操作可否、route成立に必要な主要entityは遅延しない。

anchor linkやfocus移動で直接指定されたsectionは、viewport監視を待たずに開始する。
observer、listener、idle callbackはcleanupし、再renderで重複登録しない。

### LoadingとError

Loadingは対象領域の見出しまたはlandmarkと対応させ、支援技術と自動テストが処理中と完了を識別できるようにする。
moduleまたはデータ取得に失敗した場合は、失敗した領域だけをErrorへ切り替え、取得済みの兄弟sectionとnavigationを操作可能なままにする。

## 7. テスト契約

主担当はFrontend Unit TestとStorybook Behavior Testとする。

### Frontend Unit Test

変更に該当する契約だけを確認する。

- 非表示中はqueryが`"skip"`または無効状態になる
- 表示条件成立時に正しい引数へ切り替わる
- 表示条件解除時に不要な購読を停止する
- Intersection Observer、listener、idle callbackの開始前、開始後、cleanup
- 再renderでobserverやlistenerを重複登録しない
- 状態保持またはresetの条件
- preloadがなくても通常経路が成立する

DOM APIはテストからcallbackを制御し、固定時間で待たない。

### Storybook Behavior Test

利用者から観測できる変更契約を確認する。

- tabまたはDialogの操作後に初めて内容を表示する
- 局所Loading後に内容を表示する
- moduleまたはデータ失敗時に局所Errorと回復操作を表示する
- 再表示時に入力や未確定状態を保持またはresetする
- 取得済みの兄弟sectionをLoadingへ戻さない

出現待ちは`findBy...`を優先する。
初期表示の静的文言だけを確認するplay functionは追加しない。

### VRTとE2E

見た目の意味が変わる場合は、代表Story、Loading、Error、モバイル、tag、`parameters`を更新する。
VRTはローカルで実行せず、完了報告に「VRTはCI確認方針のため未実行」と記載する。

E2Eは追加、変更、実行しない。

## 8. 計測とbundle確認

変更前後のproduction buildで、対象導線について次を比較する。

- 初期routeが読むchunk
- 遅延chunkの大きさと個数
- 共通chunkの重複
- dynamic importが実際に遅延chunkを生成しているか
- page全体を止める依存
- 非表示中の購読開始条件
- query waterfallの有無
- preloadとprewarmの対象および上限

CSR遷移を計測できる場合は、clickまたはkeyboardによる遷移開始から、route module、route成立、主要content表示を分ける。
intent preloadのhitとmiss、cache条件が異なる値を同じ分布へ混ぜない。

計測名はrouteを正規化し、document ID、店舗ID、ユーザーID、検索語、個人情報を含めない。

## 9. 実装順序

1. route、page、feature、query、bundleを棚卸しする。
2. 候補導線を比較し、上位3から5導線と選定理由を記録する。
3. 段階表示と不要購読の停止を先に実装する。
4. 効果が見込める境界へlazy mount、lazy load、preload、viewport遅延を追加する。
5. Frontend Unit TestとStorybook Behavior Testを追加または更新する。
6. 必要なStory、VRT tag、`parameters`を更新する。
7. targeted test、lint、type-check、production buildを実行する。
8. bundle差分と残ったボトルネックを確認する。
9. 自己レビューで不要なwrapper、helper、細かすぎるchunk分割を取り除く。

## 13. 実施結果

実施日: 2026-08-03

### 13.1 選定した導線

候補をcritical path、非表示中の購読、初期module量、状態保持への影響で比較し、次の4導線を対象にした。

| 導線 | 選定根拠 | 実施した判断 |
|---|---|---|
| Dashboard初期表示 | 募集中シフト、スタッフ、参加申請の独立した取得を、3件すべて完了するまで画面全体のSkeletonで止めていた | 主要contentの成立に必要な募集情報だけを全体Loading条件に残し、スタッフ一覧はsection単位のSkeletonへ分離した。オンボーディング判定だけはスタッフと参加申請の完了を待ち、取得途中の誤判定を防いだ |
| Dashboardのスタッフ招待・詳細Dialog | 2つの大きなDialog moduleがDashboard初期chunkに入り、スタッフ詳細の通知履歴は非表示tabでも生存し得る境界だった | 2 moduleをdynamic importし、招待buttonとスタッフ行のpointer・focus intentでpreloadする。chunk待機と失敗はDialog内のLoading・Errorへ閉じ込め、通知履歴は通知tab選択中だけmountする |
| グループ設定のtabと招待Dialog | 初期表示で選ばれていないtab subtreeまでmountする構成で、店舗、支払い、設定、招待方法の内容を先に評価していた | 上位tab、管理者招待tab、スタッフ招待tabへ`lazyMount`を適用した。上位tabは訪問後のsubtreeを保持し、入力や表示状態を切り替えだけで破棄しない |
| ユーザー店舗詳細の通知section | 長い詳細画面の下位sectionで、募集2 readと通知履歴1 readが初期表示から開始していた | sectionの320px手前で一度だけ有効化するviewport境界を追加し、有効化前は3 readを`"skip"`またはunmountで停止した。focus時の直接有効化、Observer非対応時の通常表示、対象変更時の再監視も用意した |

TanStack Routerは既にroute単位でmoduleを分割し、`src/router.tsx`で`defaultPreload: "intent"`を使っていたため、route設定は変更していない。  
query prewarmは、候補がpaginated queryまたは行ごとに引数が異なるqueryで購読上限を安全に定めにくいため採用しなかった。

### 13.2 critical pathと購読開始条件

| 対象 | 変更前 | 変更後 |
|---|---|---|
| Dashboard全体Loading | 募集、スタッフ、参加申請のいずれかが初回Loadingなら全体Skeleton | 募集の初回Loadingだけで全体を止め、スタッフは局所Skeleton、参加申請は取得完了後にactionへ反映する |
| スタッフ詳細の通知履歴 | Dialogへ通知履歴要素を常に渡し、tabの表示ライフサイクルと購読停止の契約が不明確 | 通知tabがactiveの間だけ要素をrenderし、tabを離れるとunmountする |
| グループ設定tab | 非選択tabも初回からmount | 初回選択時までmountせず、一度選択した上位tabは状態保持のため残す |
| ユーザー店舗詳細の通知 | route成立直後から3 readを開始 | viewport接近またはfocusまで停止し、有効化後だけ購読する |

backend queryの依存関係と引数は変更していない。段階表示と購読開始条件だけをfrontendで変更した。

### 13.3 bundle比較

一時ディレクトリでbaseline commitをbuildし、変更後buildと比較した。  
各routeについてTanStack Start manifestの`preloads`に列挙されたJavaScriptを重複除外し、raw bytesとNode.js `zlib.gzipSync`の合計を算出した。キャッシュ済み共通chunkを差し引かないcold preload上限の比較である。

| route | 指標 | 変更前 | 変更後 | 差分 |
|---|---:|---:|---:|---:|
| Dashboard | raw | 542,363 B | 479,965 B | -62,398 B（-11.5%） |
| Dashboard | gzip | 179,212 B | 161,519 B | -17,693 B（-9.9%） |
| グループ設定 | raw | 167,589 B | 172,194 B | +4,605 B（+2.7%） |
| グループ設定 | gzip | 56,369 B | 58,753 B | +2,384 B（+4.2%） |
| ユーザー店舗詳細 | raw | 137,773 B | 115,528 B | -22,245 B（-16.1%） |
| ユーザー店舗詳細 | gzip | 47,396 B | 39,464 B | -7,932 B（-16.7%） |

Dashboardでは、初期preloadに含まれない`StaffInvitationDialog` 14,051 B、gzip 4,960 Bと、`StaffDetailDialog` 15,211 B、gzip 4,762 Bの独立chunkが生成された。intent preloadが失敗しても、通常click時のdynamic importで同じDialogへ到達する。

グループ設定は`lazyMount`によって初回render作業を遅延したが、tab module自体は静的importのままである。Rollupの共有chunk再配置を含むcold preload総量は増加したため、初期JavaScript削減としては未達であり、後続候補へ残す。

### 13.5 残った候補

#### Frontend

- Dashboardの募集情報は主要contentと操作可否に必要なため、引き続き全体成立条件に残る
- Dashboardの通知履歴moduleは初期preloadに残る。購読は停止できたが、専用の非同期section境界へ移せばJavaScriptも通知tab選択時まで遅延できる
- グループ設定は全tabと複数Dialog moduleを静的importしている。入力状態、controllerの生存期間、chunk失敗時の回復を設計したうえで、Dialog単位またはtab単位のdynamic importを検討する
- ユーザー店舗詳細では人物と店舗membershipを返す主要query、LINE連携sectionはroute成立時に必要なままである
- runtimeのp50、p95は安定した計測環境がないため推測していない。今回の根拠はcritical path、購読開始条件、production bundleである

#### Backend

frontend調査だけでは、backendのread amplification、index、返却DTOが主因だと示す証拠は得られなかった。  
Convex API、schema、query、mutation、actionは変更していない。実運用で待ち時間が残る場合は、Dashboard募集、グループ設定、ユーザー詳細のread量と実行時間を別計画で計測する。

#### 将来のE2E影響

Dialog内の操作要素はdynamic chunkの局所Loading後に現れ、非選択tabの内容はtab操作後に初めてmountされる。ユーザー店舗詳細の通知操作はviewport接近後に有効になる。  
将来E2Eを更新する場合は固定時間待ちではなく、Dialog、tab内容、局所Loading完了を観測して待つ必要がある。この計画では`e2e/`を監査・変更していない。

# E2E安定性改善・スコープ再設計 実行計画

- 作成日: 2026-08-03
- 状態: rollout
- 対象: Playwright E2E、Convex E2E helper、GitHub Actions Preview実行
- 関連計画: `doc/plans/2026-07-13-e2e-full-regression.md`

## 1. 目的

E2Eを、実ブラウザ、実認証、実frontend、実Convex Previewの接続でしか検知できない代表導線へ絞る。

同じcommitと入力で初回成功と初回失敗が揺れる状態を減らし、失敗時には再実行より先に原因境界を特定できる状態にする。

固定時間待機、不要なnegative polling、Convex CLIの多重起動を削減し、成功時に待ち時間を消費しない構造へ変える。

retry回数を増やして見かけ上の成功率を上げるのではなく、workflow排他、ユーザー所有権、データ隔離、待機条件、selector、時刻、診断の順に原因を除去する。

## 2. 前提となる決定

Full RegressionをE2E単独の責務から外す。

Full Regressionは、Logic、Frontend Unit、Behavior、VRT、Convex Function、Convex Scenario、E2E、Deployed Smokeを横断した契約マップとして扱う。

E2Eは全validation、通知組合せ、DB完全性、tenant不変条件、削除競合、billing状態を総当たりしない。

既存の`doc/plans/2026-07-13-e2e-full-regression.md`は時点監査として残すが、同文書のE2E拡張項目を本計画の完了条件にはしない。

E2Eから契約を削除する前に、主担当となる下位層のテストを確認または追加し、回帰検知の空白を作らない。

E2Eの本数自体は目標にしない。

## 3. 用語と判定

本計画でいうflakeは、同じhead SHA、同じ設定、同じテストデータ契約で、初回失敗後のretryだけが成功するか、複数回の実行結果が成功と失敗の間で揺れる状態である。

製品不具合、契約どおりの失敗、credential不足、外部障害、Preview deploy失敗はflakeへ混ぜず、別の失敗分類として扱う。

待機時間は、成功時にも必ず消費する固定待機と、状態成立までだけ待つ上限付き待機を分ける。

Playwrightの`expect`、action、navigation、test timeoutは成功時に満額を消費する待機ではないため、実測なしに一括で短縮しない。

## 4. 2026-08-03時点の根拠

### 4.1 workflowの競合

`.github/workflows/playwright.yml`にはworkflow-levelの`concurrency`がない。

同じPull Requestの複数runは、同じ`pr-{PR番号}-e2e` Preview、同じClerkテストユーザー、同じreport公開先を共有する。

各runは`ORGANIZATION_INVITATION_SIGNING_SECRET`を新しく生成して同じPreviewへ設定する。

旧runと新runが重なると、frontendとbackendのhead SHA不一致、owner graphのreset競合、OCC、招待token digestと署名secretの不一致、古いreportの上書きが起こり得る。

これは最初に除去する構造的な競合であり、個別specの待機時間調整より優先する。

### 4.2 workerとテストユーザー

CIは`E2E_WORKERS=3`で通常E2Eを実行する。

`e2e/fixtures/e2eTest.ts`はworker内の`testOrdinal`を進め、1 workerにつき複数のClerkユーザーを順番に割り当てる。

Playwrightが失敗後にworker processを再作成するとordinalが0へ戻るため、retryした同じtestが初回と異なるユーザーを使い得る。

seedとresetはmanager identityを所有境界にしているため、retry時のユーザー変更は前回状態の診断と回収を不安定にする。

### 4.3 pollingとCLI

`e2e/helpers/convex.ts`は各probeでConvex CLIを同期processとして起動し、個別commandのtimeoutを持たない。

通知と招待のpositive pollは最大20回、500ms間隔であり、現在は最終試行後にもsleepする経路がある。

token待機は最大12回、500ms間隔の経路があり、同様に最終試行後のsleepを含む。

`assertNoNotificationOutbox`は4回観測と3回のsleepを行い、通知が将来も増えないことをE2E内の時間窓で推測している。

通知probe系helperは少なくとも16個のscenario fileから使われ、1シナリオ内で複数のCLI processを繰り返す。

`scenarioSeeds.ts`のOCC backoffは実際のreset競合が起きた時だけ待つため、固定待機と同列に削除しない。

### 4.4 Playwright待機

`e2e/`には`page.waitForTimeout()`と`page.waitForLoadState("networkidle")`は存在しない。

したがって、画面操作の無条件な数秒待機を探すより、backend probe、negative observation、selectorの瞬間判定を主対象にする。

通知testへ設定される150秒はtest全体の上限であり、成功時に150秒待つ処理ではない。

この上限はprobe回数と実時間を計測した後に校正し、先に短縮して別のflakeへ置き換えない。

### 4.5 selectorと時刻

一部Page Objectは、非同期に変わり得る状態を`isVisible()`で瞬間判定して分岐する。

`.first()`にはresponsive DOMの重複を意図した箇所と、scope不足を隠している可能性がある箇所が混在する。

Node側の日付helperは実行hostの現在時刻を使い、main Playwright configはbrowserの`locale`と`timezoneId`を明示していない。

深夜、日曜から月曜への境界、催促予約時刻付近では、hostとbrowserの暦日差がfixtureの意味を変え得る。

### 4.6 suiteの責務

`e2e/scenarios/`には37個のscenario fileがあり、通知集合、token lifecycle、tenant不変条件、削除状態、billing上限、UI validationまで含む。

多くの契約には、すでに`convex/_scenario/`、Convex Function Test、Storybook Behavior Testの主担当候補がある。

現在の広いE2Eを維持したままpollingだけを共通化すると、削除予定のDB詳細検証へ新しい基盤を作ることになる。

先に契約を適切な層へ移し、残ったcapability待機だけを最小化する。

## 5. 成功指標

### 5.1 安定性

- 同じPull Requestで実行中の認証付きE2E runは常に1件以下である。
- 同じ`parallelIndex`の初回とretryは同じClerkユーザーを使う。
- core E2Eを`retries=0`、CIと同じworker数で10回繰り返し、初回失敗を0件にする。
- 同じhead SHAのcore E2EをCIで3回連続実行し、`unexpected`、`flaky`、理由のない`skipped`を0件にする。

### 5.2 待機

- `page.waitForTimeout()`と`networkidle`を0件のまま維持する。
- E2EのDB完全性確認を目的とするnegative pollingを0件にする。
- retained pollは最終試行後にsleepせず、総deadlineと1 commandのtimeoutを持つ。
- core E2Eでは通知outbox集合を待たず、実画面遷移に必要なcapabilityだけを待つ。

### 5.3 実行時間

- Phase 0で同じhead SHAとworker条件のbaseline medianを記録する。
- scope縮小後のcore E2E wall spanをbaseline medianから30%以上短縮する。
- 個別specの改善はwall spanだけでなく、Convex CLI call数、poll attempt数、poll実時間で説明する。
- 数値はreportに安全な集計値として残し、token、email、payloadを含めない。

### 5.4 診断

- 失敗をworkflow競合、auth、seed/reset、OCC、capability deadline、selector/state、date/time、browser runtime、製品回帰、外部環境、unknownへ分類できる。
- PR summaryにhead SHA、run attempt、project、初回かretryか、test duration、安全な失敗分類を表示する。
- raw token、full email、credential、provider payloadをtrace、report、artifact、PRコメント、CLI errorへ含めない。

## 6. 対象範囲

- `.github/workflows/playwright.yml`の排他、実行command、summary、artifact公開条件。
- `playwright.config.ts`のproject、worker、retry、trace、locale、timezone、timeout。
- `e2e/fixtures/`のユーザー割当、reset、診断、sensitive artifact制御。
- `e2e/helpers/`のConvex command、capability poll、日付、safe diagnostics。
- `e2e/pages/`のretained selectorとcapability navigation。
- `e2e/scenarios/`の全37 fileの契約移管、統合、削除。
- `convex/testing.ts`の既存E2E helperを、必要な最小internal APIへ縮小する変更。
- E2Eから移す契約のConvex Function、Convex Scenario、Logic、Frontend Unit、Behavior Test。
- `package.json`のE2E commandと、CI結果を判定する純粋script。
- `doc/rules/testing-strategy.md`、`doc/manual/ci-cd.md`、関連planの参照整合。

## 7. 対象外

- Production、実利用者、実店舗データを使った検証。
- Resend、LINE、Clerk、決済providerへの実到着。
- E2E専用のpublic query、public mutation、public action、HTTP testing APIの追加。
- schema変更、backfill、migration。
- retry回数の増加、`failOnFlakyTests`の無効化、flakeの許容list化。
- `workers=1`を恒久設定にして競合を隠す対応。
- 固定sleepの追加と、`networkidle`への置換。
- E2E実行履歴を保存する新しい監視serviceまたはDB。
- 全Page Objectの一括rewrite。
- 外部機能フラグが無効な導線を、conditional skipのままcore gateへ含めること。

## 8. 固定する実装判断

1. CIの`retries=1`と`failOnFlakyTests=true`は維持する。
2. 原因分析用のburn-inだけ`retries=0`で実行する。
3. 同一PR runはworkflow-level concurrencyで直列化し、古いrunをcancelする。
4. 通常E2Eは1 workerにつき1 Clerkユーザーを固定し、test ordinalでrotateしない。
5. multi-actorがcoreに残る場合は通常workerと重ならない専用3ユーザーを予約し、1 workerで直列実行する。
6. 現在の`E2E_TESTING_ENABLED=true`とdeployment URL完全一致の二重gateを弱めない。
7. 通知はdry-runを維持し、外部配送を成功条件にしない。
8. 通知outboxの完全一致、非選択channelの不在、dedupe、対象集合はConvex FunctionまたはScenarioを主担当にする。
9. E2Eでraw capabilityが必要な場合も、専用internal helperから必要最小限だけ取得する。
10. capabilityを開くspecは通常traceから分離し、tokenを含むURLをartifact化しない。
11. workflow YAMLの文字列やstep順序をLogic Testで固定しない。
12. E2E削除前に下位層の回帰テストを成功させ、同じユーザーストーリーを丸ごと複製しない。

## 11. Security Lens

- Actor: 同一repositoryのPull Requestを実行するGitHub Actions runner、E2E用Clerkユーザー、ローカルでE2Eを実行する開発者。
- Asset: Convex Previewのtenant graph、Clerk testing session、招待・提出・閲覧・LINE連携のbearer token、run単位の署名secret、Playwright reportとartifact。
- Trust boundary: GitHub runnerからClerk、GitHub runnerからConvex Preview、browserからfrontendとConvex、Playwright reportからGitHub artifactとPages公開先。
- Abuse case: 重複runが同じPreviewをdeploy・resetする、古いrunが新しいreportを上書きする、raw tokenやfull emailがtrace・CLI error・PRコメントへ残る、testing helperが別deploymentで有効になる。
- Server-side enforcement: E2E helperはinternalのまま維持し、`E2E_TESTING_ENABLED=true`と`E2E_TESTING_DEPLOYMENT_URL=CONVEX_CLOUD_URL`の完全一致を必須にする。
- Rate limit / idempotency: workflow concurrencyで同一PRを1 runへ制限し、通知はdry-run、resetはowner graphだけを対象にし、retryで別ownerへ切り替えない。
- Lifecycle / recovery: 古いrunをcancelし、新runがPreviewを再deployしてsetup時に自分のユーザーgraphだけを回収する。
- Logs / PII: user index、parallel index、project、attempt、duration、安全なerror code、pathnameだけを記録し、query string、raw token、full email、payload、child processの生stderrを記録しない。
- Regression test: ユーザー割当、poll deadline、command timeout、error redaction、artifact privacy、E2E safety gate、result gateを各主担当層で検証する。

## 13. 実装フェーズ

### Phase 0: 契約マップとbaselineを固定する

1. 全37 scenario fileの各assertionを、実browser境界、UI behavior、単一API、複数API状態、見た目、外部運用へ分類する。
2. 上表の初期判定を、既存のFunction、Scenario、Storyへ実file単位で対応付ける。
3. 下位層にない契約だけを追加候補として記録する。
4. 直近の同一条件runから、head SHA、run ID、初回結果、retry結果、duration、失敗spec、run重複の有無を収集する。
5. 履歴が10 run未満なら存在する全runをbaselineにし、不足を推測値で埋めない。
6. 現行workflowのCI worker数と古い計画文書のworker記述の差を解消する。

完了条件は、全assertionに主担当層があり、E2Eに残す理由が「実browser境界」で説明できることである。

### Phase 1: 同一PR runの競合を止める

1. `.github/workflows/playwright.yml`のworkflow top-levelへ、workflow名とPull Request番号をkeyにする`concurrency`を追加する。
2. `cancel-in-progress: true`を設定する。
3. report summaryへhead SHA、run ID、run attemptを表示する。
4. cancel済みrunがreport upload、Pages publish、PR comment更新を実行しない条件を差分確認する。
5. 同じPull Requestへ連続pushし、旧runがcancelされ、新runだけがtestとreport公開を完了することをActionsで確認する。

workflow実行契約はActions上の証跡で検証し、YAMLをparseするLogic Testは追加しない。

### Phase 2: ユーザー所有権とresetを決定的にする

1. 通常E2Eのユーザー割当を`parallelIndex -> user index`の固定対応へ変える。
2. worker scopedの`testOrdinal`と`nextE2EClerkUser`を削除する。
3. `workers=1`、`2`、`3`でactive worker間の重複がなく、retryでも同じuser indexになるLogic Testを追加する。
4. CIの通常worker上限を3とし、user 0から2をcore poolにする。
5. multi-actorを残す場合はuser 3から5を専用poolにし、1 worker、serial、通常poolとの同時使用なしを保証する。
6. coreで使わないユーザーはsetup loginとforce resetの対象から外す。
7. resetは自分のowner graphだけを対象にし、global deleteや他workerのteardownを追加しない。
8. OCC retry回数と合計backoff時間を安全なmetricへ記録する。
9. reset失敗をsafe error codeで分類し、token、email、生stderrをerrorへ連結しない。

### Phase 3: artifactと診断を安全にする

1. capability URLを開くspecを識別できるtagまたは専用fixtureを追加する。
2. capability specではtrace、video、screenshotを無効にし、raw URLをtest step名とerrorへ含めない。
3. capability navigationは失敗をcatchして安全なerror codeへ変換し、製品契約が許す場合は安全なlandmark到達後にURL queryを履歴から除去する。
4. report upload前に、capability query、credential、session、非placeholder emailを検出するprivacy gateを実行する。
5. privacy gateは一致値を出力せず、検査不能なopaque artifactを成功扱いしない。
6. 通常traceのZIPはboundedに展開して内容を検査し、安全に検査できない場合は公開しない。
7. 通常specでは`trace: on-first-retry`を維持する。
8. page fixtureで`pageerror`、allowlist外の`console.error`、同一origin 5xxを収集し、queryを除いたpathnameとredacted messageだけを残す。
9. diagnostic sanitizerへemail、token、JWT、URL query、authorization、provider payloadの回帰テストを追加する。
10. testごとにproject、parallel index、user index、retry、CLI call数、poll回数、OCC回数、durationを安全なJSONとして集計する。

raw bearer tokenを扱うspecは、privacy gateが成立するまでPages reportの公開対象にしない。

### Phase 4: 下位層へ契約を移してE2Eを縮小する

次の順で小さな差分へ分ける。

1. 通知matrix、negative channel、dedupe、retry、failure recoveryをFunction・Scenarioへ移す。
2. organization、tenant、権限、削除、billingの不変条件をFunction・Scenarioへ移す。
3. shift方式、再提出、対象変更、追加スタッフ、snapshotをScenarioとBehaviorへ移す。
4. validation、Dialog、toast、pagination、onboarding、法務表示をBehaviorまたはFrontend Unitへ移す。
5. public routeとhydrationをDeployed Smokeへ統合する。
6. 各batchで下位層testを先に成功させ、対応するE2E assertionとspecを削除する。
7. 使用されなくなったPage Object method、seed、probe、tag、timeoutを同じbatchで削除する。
8. core E2Eには利用者に見える開始、主要操作、最終状態だけを残す。

notification matrix全体を新しいE2E helperへ移植しない。

### Phase 5: 残ったCLIとcapability pollだけを最小化する

1. `convexRun`へ1 command単位のtimeoutを追加する。
2. child process errorをfunction名、安全なexit分類、message fingerprintへ変換し、生args、生stdout、生stderrをreportへ出さない。
3. retained capability waitを共通のdeadline-based pollerへ載せる。
4. pollerは最初のprobeを即時実行し、成功後はsleepしない。
5. 次のprobeをdeadline内に完了できない場合はsleepせず、安全なtimeout errorで終了する。
6. 固定attempt数ではなくmonotonic clockの総deadlineを正本にする。
7. 1 command timeoutは残りdeadline以下にする。
8. 並列workerが同時刻にCLIを起動し続けないbackoffを、Phase 3の実測から決める。
9. E2Eから削除した`assertNoNotificationOutbox`と通知集合pollを削除する。
10. 実画面遷移にtokenが必要なspecでも、outbox probeとtoken probeを二重に待たない。

### Phase 6: retained selectorと時刻を決定的にする

1. retained specが使うPage Objectだけを再監査する。
2. 非同期状態への即時`isVisible()`分岐を、`expect(locator.or(...))`または状態固有のweb-first assertionへ変える。
3. `.first()`はresponsive duplicateの理由を説明できる箇所だけ残し、それ以外はDialog、section、row、landmarkへscopeを狭める。
4. Loading消滅だけでなく、操作可能なbutton、heading、statusなど利用者向け完了状態を待つ。
5. `playwright.config.ts`へ`locale: ja-JP`と`timezoneId: Asia/Tokyo`を明示する。
6. Node側の日付helperをJST基準かつ`now`注入可能な純粋処理へし、日曜、月曜、深夜、催促17時境界をLogic Testで守る。
7. backendの実時計と矛盾するfake clockを通常E2Eへ持ち込まない。

### Phase 7: CI gate、timeout、burn-inを校正する

1. broadな`@release`をcore E2Eの意味で再利用せず、`@e2e-core`と`pnpm e2e:ci`へ切り替える。
2. workflowを`pnpm e2e:ci`へ変更する。
3. core contract ID、expected project、skip 0、flaky 0、unexpected 0をJSON resultから検証する純粋scriptとLogic Testを追加する。
4. file数とtest数の下限はgateにしない。
5. 必須credentialやfeature flag不足をconditional skipにせず、実行前preflight failureにする。
6. `NOTIFICATION_TEST_TIMEOUT_MS=150_000`を削除し、retained specの実測に基づく局所timeoutへ置き換える。
7. `workers=1`と`workers=3`を`retries=0`で比較し、worker数でのみ失敗する場合は共有状態の残存として扱う。
8. desktop 4契約とmobile 1契約をproject単位で直列化し、それぞれ`workers=3`、`retries=0`、`repeat-each=10`で実行する。
9. 同じhead SHAのCIを3回直列実行する。
10. baselineと比較し、flake、wall span、CLI call、poll、OCC、failure categoryを完了記録へ残す。

## 17. ロールバックと失敗時の判断

workflow concurrencyのgroup keyが広すぎて別Pull Requestを止める場合は、concurrency差分だけを戻し、Pull Request番号を含むkeyへ修正する。

stable user mapping後に状態汚染が増えた場合は、ordinal rotationへ戻す前に、該当ownerのreset漏れとtest間共有状態を特定する。

poll deadlineが短すぎる場合は、attempt数を無制限に増やさず、CLI call時間とbackend成立時間の実測からdeadlineを再校正する。

移管先のtestが元E2E契約を守れていない場合は、そのbatchのE2E削除だけを戻し、主担当層を再設計する。

一時的な外部障害では同じhead SHAを状態確認後に再実行し、retry追加、固定sleep追加、失敗allowlistで通さない。

security gateがreportを拒否した場合はartifact公開を止めたまま原因を除去し、検査対象を除外して公開しない。

### 19.5 追加レビューで確定した保全条件

core E2Eを5契約へ絞ったこと自体は、下位層への移管とretryなしのburn-in結果によって安定化の根拠になる。
ただし、テスト件数の減少だけでは網羅性の根拠にならないため、次のbrowser-only契約を別の完了条件として扱う。

- 現在の`E2E-AUTH-01`は匿名の保護route redirectを守るが、旧E2Eにあったlogout後の保護route再アクセスを置き換えない。coreまたは独立browser smokeで補う。
- 旧`release-support-accessibility.test.ts`と`e2e/helpers/accessibility.ts`の削除後、現行E2Eにはaxe検査の代替経路がない。core外の独立a11y smokeまたはStorybook accessibilityを追加・有効化するまで、a11y観点は未完了として扱う。
- `E2E-MULTI-01`はmanager invitationのfeature flagをenabled環境で運用する段階に入った時点で追加する。flagのskipはカバレッジ済みと数えない。

この追加レビューはフロントエンド実装を戻す理由にはならない。
該当ケースが落ちる場合は、現行frontend契約を正としてE2E側のselector、待機、fixture、assertionまたはbrowser smokeの構成を見直す。

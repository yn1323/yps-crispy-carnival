## 1. 全体結論

シフトリは、公開サイトの「製品理解から登録前体験まで」と、非公開routeの配信境界に強い土台がある。
TOPの価値訴求、登録とデモの二つのCTA、FAQからHowToへの復帰、登録不要デモの完走、公開SSG、実404、CSR neutral shellは維持すべきである。
Dashboardの募集作成も、PCとスマートフォンの双方で最終確認まで進められ、通知対象と副作用を確定前に理解できた。

一方、日常Dashboardは店舗・組織contextがTODOより先に常設され、利用者の仕事より内部構造が第一視界を占める。
匿名スタッフ導線では、無効URLからの回復文言と実際の操作が一致しない画面、前の提出がなくても成功を断言する完了URL、必須query欠落時に再読込しか提示しない画面を確認した。
ShiftBoardデモは、PCツアーの終了操作が画面上に現れず、スマートフォンでは操作可能な別デモへ直接移れない。

P0とP1は確認されなかった。
再現済みの主要問題はP2であり、まず匿名スタッフの誤完了・行き止まりとShiftBoardデモの回復を直す。
measurement gapは利用者影響として採点せず、以後の改善判断に必要な基盤として並行して埋める。
その後、`H-DUX-01`の比較で効果を確認できた場合に、Dashboardを「対象context → 日常タスク」ではなく「日常タスク → 必要な対象context」の順へ再構成する。

検索配信の基礎契約は良好である。
indexable canonical 24件とsitemap 24件は一致し、棚卸しした公開SSG base 33件がraw HTMLへ非空の本文・title・description・H1・canonicalを持つ（旧aliasの本文とmetadataは現slugと同一）。
ただし、一記事の表示更新日とsitemap `lastmod`が不一致である。
robots.txtでcrawlを止めたrouteへ同時に`noindex`を返す方針は、実index状態をSearch Consoleで確認してから整理する必要がある。

性能はProduction TOPのPageSpeed mobileを1回だけ有効測定でき、LCP 3.0秒、CLS 0だった。
続く2回はPageSpeed側の`ERR_ACCESS_DENIED`で失敗したため、中央値は算出していない。
CrUX、Search Console、RUM、product analyticsのfield dataは取得できず、実利用者の速さ、検索流入、タスク完了率への影響は未測定である。

### 2.2 利用できた環境

- Local Vite `:3000`とStorybook `:6006`は既に起動済みのものを使用し、新規serverは起動していない。
- Local Dashboardには既存の認証済みsessionがあり、現在状態を読み取った。実データの値は記録していない。
- Productionは匿名・読み取り専用で確認した。通知、招待、課金、削除、募集作成、確定共有は実行していない。
- Local Dashboardの募集作成はPC・SPとも最終確認まで進め、通知発生前に閉じた。
- StorybookのConvex・Clerk mockを使い、D1〜D6のisolated component Storyで代表状態をSampledした。full compositionは4.1に記した範囲でruntime errorまたは統合fixture不足によりBlockedである。
- Accessibility guardrailは、ShiftBoardツアーのEscape終了、主要actionの可視性、募集作成DialogのSP横overflowに限定してsmokeした。計画に挙げたDashboard主CTA・店舗切替、公開header・CTA、認証form、スタッフ提出の網羅的なkeyboard smoke、200%拡大、screen readerはNot testedである。アクセシビリティの優先度を下げるという依頼に従い、主要UX・SEO・配信境界を優先したためである。

Production `robots.txt`はCloudflare Managed Content Signalsの規則を先頭へ付加した実応答で、repositoryの`public/robots.txt`とbyte単位では同一ではない。
Google Search向けのroute prefix規則はrepository由来部分と照合したが、Production robots全体をrepository fileだけから推定していない。

### 2.3 BlockedまたはExcluded

| 範囲 | Coverage | 理由 |
|---|---|---|
| Productionの正常な管理者招待、スタッフ登録、提出、閲覧、同意、LINE callback | Blocked | 安全な使い捨てtokenがなく、実利用者の状態変更・通知につながるため |
| Productionでの募集作成・確定・通知再送・参加申請処理 | Blocked | 外部副作用または実データ変更を伴うため |
| D2「全員提出済みかつ締切前」の実画面 | Blocked | 専用fixtureがなく、Productionデータを作れないため。repository contractだけ確認 |
| D3処理後のTODO再計算、D4店舗切替後の全section整合、D5 full read-only | Blocked | full Dashboard Storyが不足またはruntime errorで描画不能 |
| Search Console URL Inspection / Performance | Not measured | property接続なし |
| CrUX APIのURL・origin 28日rolling値 | Not measured | PageSpeed上で要求URLのfield dataが「データなし」。origin fallbackは未確認 |
| RUM、product analytics、実利用者調査 | Not measured | property・event data・利用者sessionへ接続なし |
| 網羅的WCAG、contrast全件、screen reader実機 | Excluded | 本監査では主要journeyを妨げる重大阻害だけを対象としたため |
| Dashboard主CTA・店舗切替、公開header・CTA、認証form、スタッフ提出の網羅的keyboard smokeと200%拡大 | Excluded | アクセシビリティの優先度を下げる依頼に従い、ShiftBoardツアーのEscape終了、action可視性、SP overflowの重大阻害smokeへ限定したため |
| Dashboard以外のログイン後画面、ShiftBoard編集全体 | Excluded | 調査計画の対象外。Dashboardからの入口と公開デモに必要な範囲だけ確認 |

- Observation: Production robotsのGoogle Search向け規則は`/dashboard`、`/shiftboard`、`/shifts`、`/staff/register`、`/line/callback`、`/legal/staff/consent`、`/sso-callback`をDisallowし、同じprefixのlive responseは`X-Robots-Tag: noindex, nofollow`を返す。Production robotsにはCloudflare Managed Content Signalsも付加される。
- Evidence: `E-HTTP-PROD`、`public/robots.txt`。
- Reproduction: Production `robots.txt`と七prefixのbase response headerを匿名GETして比較する。
- Direct consequence: crawlerへ「取得しない」と「取得した場合はindexしない」を同時に指定する配信状態である。実indexの有無はSearch Console未接続のため未測定。
- Confidence: High（配信状態）。検索結果への影響は未確認。
- Effort: M。URL Inspection、Capability安全境界の確認、crawl方針変更後のdeployed smokeを含む。
- Direction: crawler制御を安全境界として扱わず、URL Inspectionで実状態を確認してからDisallowとnoindexの役割を一本化する。
- Acceptance: 七prefixについてindexed resultとlive testを別に記録し、認証・Capabilityのserver-side enforcementを変えずに採用方針を決める。

### `O-PERF-01` 公開raw HTMLが多数のmoduleをpreloadする

- Claim: Confirmed observation。
- Surface: Performance / public SSG。
- Observation: 公開代表routeのraw HTMLに53〜68件の`modulepreload`があり、TOPは63 JS・圧縮GET合計306,381 bytesだった。そのうちdashboard・auth・Capabilityに固有のchunkは19件・23,503 bytesだった。
- Evidence: `E-HTTP-PROD`。
- Reproduction: 公開raw HTMLの`link[rel="modulepreload"]`を列挙し、参照JSを圧縮転送で取得してroute分類ごとに合計する。
- Direct consequence: 公開routeで取得候補になるresourceが多い。実際のrequest priority、unused JS、LCP・main-thread影響はtrace未取得のため未測定。
- Confidence: High（HTMLとbytes）。性能影響は未確認。
- Effort: L。traceで原因を特定した後のbundle・preload境界変更を想定。
- Direction: modulepreload数だけを目標にせず、Production相当traceで取得・実行・LCPへの寄与を特定してからroute境界を変える。
- Acceptance: 同一条件の三回以上のtraceでrequest priority、unused JS、LCP elementを比較し、変更前後の中央値と範囲を残す。

### `O-SEO-04` FAQとHowToは各一URLへ項目を集約する

- Claim: Confirmed observation。
- Surface: SEO / `/faq`、`/howto`。
- Observation: FAQ回答とHowTo手順はfragmentで一ページへ集約され、各項目は固有のtitle、canonical、sitemap URLを持たない。
- Evidence: `E-HTTP-PROD`、`E-BR-PROD`。
- Reproduction: `/faq`と`/howto`のcanonical、sitemap loc、各項目のfragment linkを比較する。
- Direct consequence: 検索対象となるdocumentはFAQとHowToの各一件である。個別URL化による流入増減や重複は未測定。
- Confidence: High（URL構造）。検索機会への影響は未確認。
- Effort: L。需要検証後に情報設計、routing、metadata、内部linkを変更する場合。
- Direction: 現在の探索性を維持し、GSCで独立意図と需要を確認できた項目だけURL分離を試す。
- Acceptance: query・page data、既存記事との重複、個別URLの固有title・canonical・内部linkを採否表へ残す。

# 問い合わせと要望受付機能 実装計画

**ステータス：実装完了**

公開問い合わせフォームと、ログイン後に要望を短く送れる導線を追加する。

問い合わせはメールを正として、メール送信を受け付けた後にSlackへ通知する。

ログイン後の要望はメールやSlackへ送らず、店舗と送信者を紐づけてDBへ保存し、analytics-dashboardの一覧で確認する。

---

## 1. ゴールと対象範囲

### 1.1 公開問い合わせフォーム

- Googleフォームへ遷移せず、シフトリ内の `/contact` で問い合わせを完了できる。
- 迷惑送信と連続送信を抑止しながら、問い合わせ先メールアドレスへ内容を送る。
- メール送信の受付成功後、同じ送信処理からSlack Incoming Webhookへ通知する。
- Slack通知の失敗で、メール送信済みの問い合わせをユーザー側の失敗扱いに戻さない。

### 1.2 ログイン後の要望受付

- 管理ユーザーが現在の作業を離れず、ヘッダーから200文字以内の要望を送れる。
- 店舗と送信者は認証済みのサーバー情報から確定し、フォーム入力として受け取らない。
- 要望を新しい順にanalytics-dashboardで確認できる。

### 1.3 初期スコープに含めないもの

- 要望送信時のメール通知とSlack通知。
- 要望への返信、対応状況、担当者、優先度、タグ。
- 要望の検索、絞り込み、並び替え変更。
- analytics-dashboardからの要望編集と削除。
- 問い合わせ内容のDB保存と問い合わせ管理画面。
- メール受信箱を外部サービスから監視してSlackへ転送する構成。

---

## 2. 機能の分離

| 導線 | 利用者 | 入力 | 保存先 | 通知 | 確認先 |
|---|---|---|---|---|---|
| 問い合わせ | 未ログインを含む一般利用者 | 種別、氏名、メールアドレス、店舗名または会社名、問い合わせ内容 | 初期版では本文をDB保存しない | メール、成功後にSlack | メールとSlack |
| 要望 | ログイン済み管理ユーザー | 要望のみ | `featureRequests` | なし | analytics-dashboard |

問い合わせと要望のバックエンドを分ける。

問い合わせは外部通知を扱う `contact` ユースケース、要望は永続化を扱う `featureRequest` ユースケースとする。

## 3. 公開問い合わせフォーム

### 3.1 画面構造

`/contact` は中央1カラムで、フォームの最大幅を640px前後とする。

ページ上部に問い合わせ先と回答方針を短く示し、その下にフォームを置く。

入力項目は次のとおりとする。

| 項目 | 必須 | 制約 |
|---|---|---|
| 問い合わせ種別 | 必須 | 選択式。利用開始について、機能や使い方、不具合・トラブル、その他 |
| 氏名 | 必須 | 1〜100文字 |
| メールアドレス | 必須 | メール形式、最大254文字 |
| 店舗名または会社名 | 任意 | 最大100文字 |
| 問い合わせ内容 | 必須 | 1〜2,000文字 |
| プライバシーポリシーへの同意 | 必須 | ポリシーへのリンクを併記する |

電話番号は初期版では取得しない。

送信ボタンは `問い合わせを送る` とし、常時押せる状態で、押下後にフィールドエラーを表示する。

送信成功後はフォームを再表示せず、同一ページ内の完了表示へ切り替える。

完了文言は `お問い合わせを受け付けました。内容を確認してご連絡します。` とする。

### 3.2 状態とエラー

- 送信中：ボタンをloading表示にし、`useSingleFlight`で同期的な連打を止める。
- 入力エラー：各フィールドの直下に修正方法を表示する。
- 迷惑送信判定：詳細を開示せず、再試行可能な共通エラーを表示する。
- メール送信失敗：入力値を残し、時間をおいて再送するよう案内する。
- Slack通知失敗：ユーザーには成功表示を維持し、本文を含めない安全な運用ログだけを残す。

### 3.3 送信処理

想定フローは次のとおりとする。

```text
ブラウザ
  -> contact public HTTP action
  -> 入力のサーバーバリデーション
  -> Turnstile検証
  -> 送信頻度制限
  -> Resendで問い合わせメール送信
  -> メール受付成功後にSlack Incoming Webhookへ通知
  -> acceptedを返す
```

メールを問い合わせの正とする。

Resend APIが送信を受け付けた後にSlack通知を実行し、Slackだけ成功してメールが存在しない状態を作らない。

Slack通知には問い合わせ種別、氏名、返信先メールアドレス、店舗名または会社名、問い合わせ内容、リクエストIDを含める。

通知先は問い合わせ担当者だけが参加する非公開チャンネルとする。

Slack Webhook URLは `SLACK_CONTACT_WEBHOOK_URL` としてサーバー環境変数に置き、ブラウザbundleへ含めない。

メールの送信先もサーバー環境変数で管理し、未設定時は送信処理を503相当の設定エラーとして扱う。

### 3.4 迷惑送信と二重送信

- Cloudflare Turnstileのトークンをサーバー側で検証する。
- 送信回数を短時間と一定時間の二段階で制限する。
- レート制限キーには、正規化したメールアドレスと安全に取得できるリクエスト文脈を使う。
- クライアントで生成した `requestId` をResendのidempotency keyへ含める。
- Slack通知にも同じ `requestId` を表示し、運用上の重複を判別できるようにする。
- 初期版では問い合わせ本文をDBへ保存しないため、メール成功後かつレスポンス前に通信が切れた場合のSlack重複を完全には排除できない。

Slack通知の厳密な一度だけ実行が必要になった場合は、本文を保存しない技術的な送信receiptテーブルを追加し、メールとSlackの処理状態を `requestId` 単位で管理する。

## 4. ログイン後の要望モーダル

### 4.1 ユーザータスク

プライマリータスクは、思いついた要望を短く送ることだけとする。

問い合わせ先の選択、返信先の入力、カテゴリ選択は置かない。

要望の採用や返信を約束する文言も置かない。

### 4.2 ヘッダーへの配置

ログイン後ヘッダーのユーザーメニュー手前にトリガーを置く。

- PC：アイコンと `要望を送る` のラベルを表示する。
- SP：横幅を圧迫しないアイコンボタンとし、`aria-label="要望を送る"` を付ける。
- 選択中店舗がない場合：トリガーを表示しない。

`Header`テンプレートには汎用的なアクションslotだけを追加する。

要望Mutation、選択中店舗、モーダル状態は `AuthenticatedHeader`から呼ぶfeatureコンポーネントが担当する。

### 4.3 モーダルのサイズ

SPでもフルスクリーンにしない。

入力が1項目で短く完了するため、通常サイズの中央Dialogとする。

- PC：最大幅448px前後。
- SP：左右16pxの余白を残した幅。
- Textarea：最小高120px前後。
- キーボード表示時：`keyboardAwareViewport`を使い、FooterがIMEに隠れないようにする。
- モバイルでは自動フォーカスせず、Dialogを開いた直後にキーボードが画面を覆わないようにする。
- 200文字の入力なので、閉じる際の未保存確認は設けない。

### 4.4 文言

| 要素 | 文言 |
|---|---|
| トリガー | 要望を送る |
| タイトル | 要望を送る |
| 入力案内 | どんな機能や改善があるとうれしいですか？ |
| 補足 | いただいた内容は、今後の改善の参考にします。 |
| 送信ボタン | 要望を送る |
| 文字数エラー | 要望は200文字以内で入力してください |
| 成功Toast | 要望を受け付けました |
| 失敗Toast | 要望を送信できませんでした。少し時間をおいて、もう一度お試しください |

送信成功時はDialogを閉じて入力をリセットする。

送信失敗時はDialogと入力内容を残す。

## 5. 要望データとMutation

### 5.1 テーブル

新規テーブル名は `featureRequests` とする。

```text
featureRequests
  shopId: Id<"shops">
  userId: Id<"users">
  comment: string
  requestId: string
  _creationTime: number
```

`_creationTime`を受付日時として使い、同じ意味の `createdAt` は追加しない。

`requestId` はユーザー入力ではなく、二重登録防止に使う技術項目である。

次のindexを追加する。

- `by_shopId`：将来、店舗単位で取得するときに使う。
- `by_userId_and_requestId`：同じユーザーの同一送信を重複登録しない。

新規テーブルとindexの追加なので、既存データのバックフィルと `@convex-dev/migrations` は不要である。

### 5.2 登録Mutation

`featureRequest.mutations.submit` は `managerMutation` を使う。

フロントから受け取る引数は `comment` と `requestId` だけとする。

`shopId` は `useShopMutation` が選択中店舗として渡すが、サーバー側の `managerMutation` がactiveな店舗所属を検証する。

`userId` は引数として受け取らず、`ctx.user._id`から確定する。

サーバー側では次を実施する。

- ZodとConvex validatorの両方で入力を検証する。
- 前後の空白を除去し、空白だけの入力を拒否する。
- 1〜200文字に制限する。
- 同じ `userId` と `requestId` が存在する場合は、登録済みとして成功を返す。
- ユーザー単位の短時間制限と日次制限を設ける。初期値は1分1件、1日10件を候補とする。
- 返り値は `{ status: "accepted" }` のような最小DTOにする。
- コメント本文をサーバーログへ出さない。

フロントでも `useSingleFlight` を使い、loading表示だけに二重送信防止を依存させない。

## 6. analytics-dashboardの要望タブ

### 6.1 タブと一覧

既存タブの末尾に `要望` を追加する。

初期版はKPIカード、チャート、検索、フィルターを置かず、届いた要望の一覧だけを表示する。

一覧は登録順の新しいものから古いものへ固定する。

| 列 | 内容 |
|---|---|
| 受付日時 | `_creationTime`を日時表示する |
| 店舗 | 現在の店舗名を表示する |
| 送信者 | 現在のユーザー名を表示し、補助情報としてuserIdを表示できるようにする |
| 要望 | 200文字以内の本文を改行を保って表示する |

管理ユーザーのメールアドレスは返却DTOと画面へ含めない。

ユーザーまたは店舗が削除済み、もしくは参照できない場合は、`削除済みユーザー`、`削除済み店舗`のような表示用fallbackを返す。

空状態は `届いた要望はまだありません。` とする。

### 6.2 取得とページング

初回50件を取得し、`もっと見る`で次の50件を取得する。

Convex internal queryでは `featureRequests` を `_creationTime` の降順でpaginateし、1ページ分だけ店舗とユーザーを参照する。

analytics-dashboardを開いただけでは取得せず、`要望`タブを選択したときに初回取得する。

そのため、現在Dashboard内部にある `activeView` をDashboardPageへ引き上げ、TanStack Queryの `enabled` とページング状態をページ側で管理する。

### 6.3 BFF経路

ブラウザからConvex public queryを直接呼ばない。

既存の次の経路を維持する。

```text
analytics-dashboard
  -> POST /api/analytics
  -> Cloudflare Worker
  -> Convex HTTP action
  -> internal query
  -> featureRequests
```

`AnalyticsDashboardRequest` に次の取得種別を追加する。

```text
kind: "featureRequests"
cursor: string | null
limit: number
```

`limit` は1〜50、cursorは文字列またはnullとしてHTTP action到達前に検証する。

レスポンスは次の形を基本とする。

```text
kind: "featureRequests"
rows:
  id
  shopId
  shopName
  userId
  userName
  comment
  createdAt
continueCursor
isDone
```

`SHIFTORI_INTERNAL_API_SECRET` による既存認証と `cache-control: no-store` を維持する。

## 7. Security Lens

### 7.1 公開問い合わせ

- **Actor**：未ログインを含む一般利用者とbot。
- **Asset**：問い合わせ先メール、Slackチャンネル、ResendとSlackの送信コスト、入力された個人情報。
- **Trust boundary**：ブラウザからpublic HTTP actionへ渡る全フォーム値、Turnstile token、requestId。
- **Abuse case**：大量送信、長文送信、メールやSlackへの迷惑投稿、Webhook URL漏洩、ログへの個人情報混入。
- **Server-side check**：runtime validator、Zod、本文上限、Turnstile検証、レート制限、サーバー環境変数。
- **Rate limit / idempotency**：短時間と一定時間の制限、`useSingleFlight`、Resend idempotency key。
- **Logs / PII**：氏名、メールアドレス、問い合わせ本文、Turnstile token、Webhook URLをログへ出さない。
- **Regression test**：入力境界、Turnstile失敗、レート制限、メール失敗時にSlackを呼ばないこと、Slack失敗時にメール受付成功を維持すること。

### 7.2 ログイン後の要望

- **Actor**：Clerk認証済みで、選択中店舗へactiveな所属を持つ管理ユーザー。
- **Asset**：店舗との紐づき、送信者情報、自由記述の要望、内部analytics画面。
- **Trust boundary**：ブラウザからMutationへ渡るcomment、requestId、選択中shopId。
- **Abuse case**：他店舗名義での登録、他ユーザー名義での登録、連打、コメント本文のログ漏洩、analytics APIの外部閲覧。
- **Server-side check**：`managerMutation`、activeな `shopMembers`、`ctx.user`からのuserId確定、文字数制限、レート制限、analytics BFF secret。
- **Rate limit / idempotency**：1分1件と日次上限、`userId + requestId` の一意な扱い、`useSingleFlight`。
- **Logs / PII**：commentと管理ユーザーのメールアドレスをログへ出さない。analytics DTOへメールアドレスを含めない。
- **Regression test**：未認証、未所属店舗、別店舗shopId、重複requestId、レート制限、返却DTOの最小化。

## 8. プライバシーと保持方針

公開問い合わせでは氏名、メールアドレス、店舗名または会社名、自由記述をResendとSlackへ送る。

問い合わせフォームにプライバシーポリシーへのリンクと同意欄を置き、外部サービスを含む取り扱いの記載を実装前に確認する。

要望は店舗ID、ユーザーID、自由記述を期限を定めず保存する初期案のため、管理ユーザー向けプライバシーポリシーの取得情報と利用目的を確認する。

現在の利用目的にサービス改善と問い合わせ対応が含まれていても、自由記述を保存して内部分析画面へ表示する事実を明記するか判断する。

文書を変更する場合は `documentVersion` を更新し、再同意が必要な変更であれば `requiredConsentVersion` も更新する。

要望保存による変更対象は管理ユーザー向けポリシーだけである。

一方、公開問い合わせは管理ユーザー以外も利用でき、現在の管理ユーザー向けとスタッフ向けポリシーがどちらもサービス上の問い合わせフォームを案内しているため、問い合わせデータをResendとSlackへ送る記載が両方で足りているか確認する。

要望の削除依頼や保持期間が運用上必要になった場合は、analytics-dashboardへ直接削除機能を足さず、別途権限と監査を含めて設計する。

## 10. テスト計画

- 問い合わせの必須、任意、最大文字数、メール形式、空白正規化。
- 要望の空文字、空白のみ、1文字、200文字、201文字、trim。
- analytics表示用の日付、削除済み名称fallbackなど、純粋変換を追加した場合のテスト。

### 10.2 Storybook Behavior TestとVRT

- 問い合わせフォームの通常、入力エラー、送信中、送信失敗、完了。
- 要望DialogのPC通常幅とSP通常幅。
- SPでフルスクリーンにならないことと、アイコンボタンのaccessible name。
- 要望の空入力エラー、200文字、送信中、失敗時の入力保持、成功時のcloseとToast。

### 10.3 Convex Function Test

- 問い合わせのTurnstile失敗、レート制限、Resend失敗、メール成功後のSlack実行、Slack失敗時の成功扱い。

- 要望の文字数境界、同一requestIdの冪等性、短時間と日次レート制限。
- 要望一覧の新しい順、50件上限、cursor継続、店舗とユーザーの参照。
- analytics DTOにメールアドレスが含まれないこと。
- analytics HTTP actionのsecret不一致とrequest validation。

### 10.4 Scenario TestとE2E

要望登録からanalytics一覧への反映は複数APIと別アプリ表示用queryをまたぐため、代表シナリオをConvex Scenario Testへ追加する。

```text
管理ユーザーが要望を登録
  -> 同一requestIdを再送
  -> DB上は1件
  -> analytics internal queryで新しい順に1件取得
  -> 店舗と送信者が正しい
```

問い合わせの外部サービス実送信は自動テストで行わず、Resend、Turnstile、Slackをmockする。

analytics-dashboardは現行ルールに従いStorybook、E2E、VRTを初期スコープへ追加せず、DTO、schema、internal query、必要な純粋関数をテストする。

## 12. 実装前に確定する項目

| 項目 | 推奨案 |
|---|---|
| 問い合わせ先メールアドレス | 専用の受信アドレスを環境変数で設定する |
| Slack通知先 | 問い合わせ担当者だけの非公開チャンネル |
| Slack失敗時 | メールが成功していれば問い合わせ成功として扱う |
| 問い合わせ本文のDB保存 | 初期版では保存しない |
| Slackの厳密な重複防止 | 初期版ではrequestIdで運用識別し、必要になればreceiptテーブルを追加する |
| 問い合わせ種別 | 利用開始について、機能や使い方、不具合・トラブル、その他 |
| 要望の最大長 | 200文字 |
| 要望通知 | メール、Slackともに送らない |
| SP要望Dialog | フルスクリーンにせず、左右16px余白の通常サイズ |
| analyticsの並び | `_creationTime`の新しい順で固定 |
| analyticsの取得件数 | 50件ずつ、もっと見る方式 |
| 要望の対応ステータス | 初期版では持たない |
| 要望の保持期間 | 初期版では期限なし。プライバシー確認時に再判断する |

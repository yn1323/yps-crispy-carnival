# スタッフ通知履歴の実装計画

作成日: 2026-07-19

状態: 実装済み（リリース作業待ち）

実装日: 2026-07-19

コード、自動テスト、Feature Docの更新まで完了している。
本番でメールを「配信済み」へ更新するには、バックエンド反映後にResend管理画面で`email.delivered`のWebhook購読を有効化する必要がある。

## 1. 目的

ダッシュボードのスタッフ詳細で、そのスタッフへ送った通知の履歴を確認できるようにする。

履歴には、通知日時、メールまたはLINEのチャネル、表示用タイトル、送信結果を表示する。

メールは、Resendが受信側メールサーバーへの到達を通知した場合だけ「配信済み」と表示する。

LINEは個別端末への到達を確認できないため、Messaging APIが送信要求を受け付けた状態を「送信済み」と表示し、「配信済み」や「届きました」とは表示しない。

通知本文、送信先メールアドレス、LINE user ID、token付きURL、providerのraw errorは、表示用履歴へ保存しない。

## 2. 決定事項

この計画では、実装後に新しくenqueueされた通知だけを履歴へ記録する。

デプロイ前の通知と、デプロイ時点ですでにOutboxへ存在する通知は履歴へ含めない。

履歴の開始時刻は専用設定値で管理せず、履歴行が作成された時点を開始条件とする。

新しい履歴テーブルは空で開始するため、既存データのbackfillと`@convex-dev/migrations`によるデータ移行は行わない。

既存`notificationDeliveryEvents.errorMessage`のoptional化もwideningであり、既存documentはそのまま有効なためbackfillを行わない。

バックエンドとフロントエンドは同じ変更で実装し、バックエンドを先にデプロイする。

## 3. スコープ

### 3.1 対象

- `notificationOutbox`を通る実通知のうち、`shopId`と`staffId`を持つスタッフ向け通知
- 通知enqueue時の履歴作成
- Outboxの送信、再試行、失敗、キャンセルと履歴状態の同期
- Resendの`email.delivered`を使ったメール配信状態の更新
- スタッフ別の通知履歴を返すmanager query
- スタッフ詳細の「通知」タブでの履歴表示
- 店舗境界、最小DTO、削除処理への組み込み
- Function Test、Scenario Test、Logic Test、Storybook、VRTの更新
- Feature Docと`doc/INDEX.md`の更新

### 3.2 対象外

- デプロイ前の通知履歴のbackfill
- デプロイ前に作成済みのpending Outboxを履歴へ取り込む処理
- 通知本文と実際の宛先の画面表示
- メール開封確認
- LINEの個別到達確認と既読確認
- LINE Reply APIなど、Notification Outboxを通らないメッセージ
- Clerkなど外部認証サービスが独自に送るメール
- グループ設定の人物詳細を使った複数店舗横断の通知履歴
- 履歴の検索、期間絞り込み、CSV出力
- 既存`notificationOutbox.payload`のbackfill、削除、redaction
- 現行Outboxのlease、reaper、fanout設計の変更
- 通知配送を抑止する既存E2Eでの履歴作成確認

既存Outboxの本文保持期間とredactionは、通知履歴とは失敗時の再送契約が異なるため、別のセキュリティ改善として扱う。

## 5. 完成形のデータ契約

### 5.1 `notificationHistory`テーブル

`convex/schema.ts`へ、表示用metadataだけを持つ`notificationHistory`テーブルを追加する。

| フィールド | 型 | 契約 |
| --- | --- | --- |
| `outboxId` | `Id<"notificationOutbox">` | 元になったOutbox。1 Outboxにつき履歴1件 |
| `shopId` | `Id<"shops">` | manager queryのtenant key |
| `staffId` | `Id<"staffs">` | スタッフ詳細の対象 |
| `channel` | `"email" \| "line"` | 実際に使用したチャネル |
| `notificationKind` | `string` | 通知目的を表す安全な分類名 |
| `displayTitle` | `string` | 画面表示用タイトル。本文を含めない |
| `sendStatus` | `"queued" \| "sent" \| "failed" \| "cancelled"` | Outboxの送信状態を正規化した値 |
| `deliveryStatus` | `"not_supported" \| "unknown" \| "delivered" \| "delayed" \| "failed" \| "bounced" \| "suppressed"` | providerが返す配信状態 |
| `requestedAt` | `number` | enqueue時刻 |
| `sentAt` | `number?` | provider API成功時刻 |
| `deliveredAt` | `number?` | メールサーバー到達時刻 |
| `failedAt` | `number?` | 最終送信失敗時刻 |
| `deliveryStatusAt` | `number?` | 最後に反映したprovider event時刻 |
| `updatedAt` | `number` | 最終更新時刻 |

次のindexを追加する。

```ts
.index("by_outboxId", ["outboxId"])
.index("by_shopId_and_staffId_and_requestedAt", ["shopId", "staffId", "requestedAt"])
```

`by_outboxId`は履歴作成と状態更新で`.unique()`を使う。

`by_shopId_and_staffId_and_requestedAt`は、選択店舗とスタッフで絞り、最新順にページングする。

### 5.2 永続化しない情報

`notificationHistory`には次を保存しない。

- メールアドレス
- LINE user ID
- メールHTML
- LINE本文
- Flex Message JSON
- magic link、同意URL、招待URL
- provider error本文
- Webhook body
- Resend署名

`displayTitle`は120文字を上限とし、内部producerが決めた固定文言またはメール件名だけを使用する。

### 5.3 保持と削除

履歴metadataは、対象スタッフまたは店舗が削除されるまで保持する。

通常のスタッフ削除は論理削除であるため、`staff.deleteStaff`がスタッフを論理削除する同じtransactionで、`shopId`と`staffId`を指定した履歴削除internal mutationをschedulerへ登録する。

履歴削除internal mutationは、`shopId`と`staffId`のindexを使って100件ずつ削除し、残りがあれば自分自身を再度scheduleする。

スタッフは論理削除直後からquery対象外になるため、非同期cleanup中の履歴が画面へ再露出することはない。

店舗削除と組織削除では、既存の`deletionCleanup`へ履歴削除phaseと完了検証を追加し、`shopId`のindexを使ってbounded batchで削除する。

履歴のためだけの新しいcron、永続jobテーブル、監視基盤は追加しない。

## 6. enqueue契約

### 6.1 表示用metadata

`EnqueueNotificationInput`へ、スタッフ向け通知で必須となる表示用metadataを追加する。

```ts
type NotificationHistoryInput = {
  notificationKind: string;
  displayTitle: string;
};
```

共通validatorとinsert直前の正規化で、`notificationKind`は`^[a-z][a-zA-Z0-9._-]{0,79}$`に制限する。

`displayTitle`はtrimし、空ならproducerの実装不備としてenqueueを失敗させ、120文字を超える場合は通知配送を止めず120文字へ切り詰める。

この境界値は定義元のFunction Testで一度だけ検証する。

スタッフ向け通知の型は、`staffId`と`history`を同時に要求するdiscriminated unionにする。

スタッフを対象にしない通知は、現在と同じく`history`を持たなくてよい。

これにより、新しいスタッフ向け通知を追加したとき、タイトルの指定漏れをTypeScriptで検出する。

現在`staffId`付き通知をenqueueする次のproducerをすべて追従更新する。

- `convex/notification/actions.ts`
- `convex/notification/reminderActions.ts`
- `convex/line/actions.ts`
- `convex/legal/actions.ts`

### 6.2 タイトルの決定

メールは、実際に送る件名と同じ値を`displayTitle`へ渡し、履歴保存時だけ上限へ正規化する。

LINEは本文から先頭行を切り出さず、通知テンプレートごとに短いタイトルを指定する。

例を次に示す。

| 通知 | 表示用タイトル |
| --- | --- |
| シフト募集 | シフト募集のお知らせ |
| 提出催促 | シフト提出のお願い |
| 確定シフト | 確定シフトのお知らせ |
| LINE連携案内 | シフト通知をLINEで受け取れます |
| 法務同意 | 利用規約への同意のお願い |

通知文面のテンプレートと表示用タイトルが別々に増殖しないよう、既存の件名定数または通知producerの近くで定義する。

### 6.3 履歴作成

`notificationOutbox.mutations.enqueue`は、新しいOutboxをinsertした同じtransactionで履歴をinsertする。

初期状態は次とする。

```ts
{
  sendStatus: "queued",
  deliveryStatus: channel === "email" ? "unknown" : "not_supported",
  requestedAt: now,
  updatedAt: now,
}
```

activeな同一`dedupeKey`が見つかり、既存Outboxを返す場合は履歴を追加しない。

履歴作成前に、配送直前と同じ`isNotificationDeliverySuppressed({ suppressDelivery: payload.suppressDelivery })`を使う。

明示的な`suppressDelivery`に加え、`NOTIFICATION_DELIVERY_MODE`が`dry-run`、`disabled`、`mock`の通知も履歴へ保存しない。

配送抑止条件をenqueue側へ複製せず、既存helperを単一の判定元とする。

履歴対象となる実通知では、Outbox作成と履歴作成の片方だけが成功する状態を作らない。

### 6.4 LINEからメールへのfallback

LINE payloadの`fallbackEmail`へ、メール側の`history` metadataをoptional fieldとして追加する。

既存のpending Outboxにはこのfieldがないため、schema上はoptionalから始める。

新しいproducerは必ずfallback用の`notificationKind`と`displayTitle`を設定する。

`EnqueueNotificationInput`には、旧Outboxからのfallback専用となる明示的な`historyMode: "legacy_no_history"`分岐を用意する。

通常のproducerはこの分岐を使わず、`staffId`と`history`を必ず同時に渡す。

デプロイ前に作成されたLINE Outboxの`fallbackEmail.history`がない場合だけ、この互換分岐でメール配送を継続し、履歴は作成しない。

`history` metadataを持つ新しいLINE通知からfallbackメールOutboxを作った場合は、メールとして別の履歴行を作る。

画面では、元のLINE失敗とfallbackメールの送信結果を別々に表示する。

## 7. 状態遷移

### 7.1 Outboxとの同期

履歴は、既存Outboxのstate machineを置き換えない。

Outboxを配送処理の正、`notificationHistory`を管理画面向けの読み取りモデルとする。

| 既存処理 | 履歴更新 |
| --- | --- |
| 新規enqueue | `sendStatus = queued` |
| `claimDue` | 更新しない。画面上は送信待ちを維持する |
| `markRetry` | `sendStatus = queued` |
| `markSent` | `sendStatus = sent`、`sentAt = now` |
| `markFailed` | `sendStatus = failed`、`failedAt = now` |
| cancel | `sendStatus = cancelled` |
| `email.delivered` | `deliveryStatus = delivered`、`deliveredAt = occurredAt` |
| `email.delivery_delayed` | `deliveryStatus = delayed` |
| `email.failed` | `deliveryStatus = failed` |
| `email.bounced` | `deliveryStatus = bounced` |
| `email.suppressed` | `deliveryStatus = suppressed` |

`claimDue`で履歴を更新しないのは、短時間のprocessingを表示するためだけに追加writeを発生させないためである。

### 7.2 既存Outboxとの互換性

デプロイ前のOutboxには履歴行が存在しない。

`markSent`、`markRetry`、`markFailed`、cancel、Resend webhookは、対応する履歴がなければ履歴更新だけをskipし、既存処理を続行する。

履歴がないことをエラーにすると、デプロイ前のpending通知を配送できなくなるため、この動作は採用しない。

### 7.3 provider eventの順序

Resend webhookは`email.delivered`を対象eventへ追加する。

既存の署名検証、body上限、`svix-id`によるevent重複排除を維持する。

全受信event用の`resendProviderEventTypeValidator`を追加し、既存の`resendProviderIssueEventTypeValidator`はFailureInboxへ流す問題系event専用として維持する。

`notificationDeliveryEvents.eventType`へ`provider_delivery_update`を追加し、`email.delivered`も既存の`by_providerEventId`で重複排除できるようにする。

`notificationDeliveryEvents.errorMessage`はoptionalへwidenし、成功eventである`email.delivered`には保存しない。

コード上のinsert inputはdiscriminated unionにし、既存の失敗・retry系eventでは引き続き`errorMessage`を必須、`provider_delivery_update`では指定不可とする。

架空のエラー文言や空文字でschemaを満たさない。

既存`notificationOutbox.resendDeliveryStatus`は問題系eventの互換fieldとして維持し、`delivered`へwidenしない。

正常到達の表示元は`notificationHistory.deliveryStatus`とする。

これらはvalidatorのliteral追加とfieldのoptional化によるwideningであり、既存documentの書き換えを必要としない。

`deliveryStatusAt`より古いprovider eventは履歴状態を上書きしない。

`markSent`は`deliveryStatus`を変更しない。

これにより、`email.delivered`が`markSent`より先に処理されても、後続の`markSent`で「配信済み」を「送信済み」へ戻さない。

FailureInboxへ新しい警告を作成するのは、現在と同じく遅延と問題系eventだけとする。

時系列判定を通過した`email.delivered`を反映したときは、同じOutboxに紐づくopenなprovider由来FailureInboxを解消する。

これにより、一度`email.delivery_delayed`になったメールが後から配信された場合に、既存の「送れなかった通知」へ古い警告を残さない。

## 8. Manager API

### 8.1 `listStaffNotificationHistory`

`convex/notificationOutbox/queries.ts`へ、ページングqueryを追加する。

```ts
api.notificationOutbox.queries.listStaffNotificationHistory
```

関数固有の引数は`staffId`とConvex標準の`paginationOpts`とする。

`managerQuery`が追加する`shopId`を含め、クライアントから見た実引数は`shopId`、`staffId`、`paginationOpts`である。

フロントエンドhookは選択店舗の`shopId`を必ず渡し、wrapperがその店舗へのactiveまたはread-only membershipを検証する。

queryは次を順に確認する。

1. Clerk identityから選択店舗のmanager query contextを解決する。
2. `staffId`でスタッフを取得する。
3. スタッフが論理削除されていないことを確認する。
4. `staff.shopId === ctx.shop._id`を確認する。
5. 履歴を`shopId`と`staffId`のindexで最新順にページングする。

存在しないスタッフ、別店舗スタッフ、削除済みスタッフは同じ空ページを返す。

返却DTOは次に限定する。

```ts
{
  _id,
  requestedAt,
  sentAt,
  channel,
  displayTitle,
  displayStatus,
}
```

`displayStatus`はDBの`sendStatus`と`deliveryStatus`からサーバー側で正規化した機械値とする。

正規化の優先順は次とする。

1. `sendStatus === cancelled`なら`cancelled`
2. `deliveryStatus`が`delivered`なら`delivered`
3. `deliveryStatus`が`delayed`なら`delayed`
4. `deliveryStatus`が`failed`、`bounced`、`suppressed`なら`failed`
5. `sendStatus === failed`なら`failed`
6. `sendStatus === sent`なら`sent`
7. それ以外は`queued`

日本語ラベルと色はフロントエンドで決める。

### 8.2 ページング

Convex標準の`paginationOptsValidator`と`paginationResultValidator`を使う。

初回取得は20件、追加取得は20件とする。

`paginationOpts`は組み替えず、そのまま`.paginate()`へ渡す。

全件`.collect()`とクライアント側の全件filterは行わない。

## 9. Security Lens

- **Actor**：選択店舗を閲覧できる管理者
- **Asset**：スタッフごとの通知日時、チャネル、タイトル、送信状態
- **Trust boundary**：クライアントから渡される`shopId`、`staffId`、pagination cursor
- **Abuse case**：別店舗のスタッフIDを指定した履歴取得、payloadや宛先の露出、LINE到達の誤表示
- **Server-side check**：`managerQuery`、activeまたはread-only membership、非削除店舗、`staff.shopId === ctx.shop._id`
- **Rate limit and boundedness**：新しいpublic mutationは追加せず、queryはtenant indexとConvex paginationでboundedにする
- **Idempotency**：Outboxと履歴を同じtransactionで作り、`outboxId`で履歴を一意にする
- **Provider boundary**：Resend署名とevent ID重複排除が成功した後だけ履歴を更新する
- **Lifecycle**：通常のスタッフ削除からbounded cleanupをscheduleし、店舗・組織削除の既存cleanupにも履歴を追加する。既存`prepareForDelivery`の送信直前チェックを維持し、削除後に新しい外部送信を開始しない
- **Deletion race**：外部API呼び出し開始後の送信は取り消せない。スタッフは削除直後から履歴query対象外とし、履歴metadataはcleanupで削除する
- **Logs and PII**：本文、宛先、LINE user ID、token URL、Webhook bodyを新たにログまたは履歴へ保存しない
- **Regression test**：未認証、別店舗、削除済み、最小DTO、event重複と順序逆転をFunction Testで確認する

## 10. フロントエンド

### 10.1 取得境界

スタッフ一覧の`getDashboardStaffs`へ履歴を含めない。

共通の`src/components/features/StaffNotificationHistory/`へ取得hookと表示コンポーネントを置く。

ユーザー詳細ページでは選択店舗のmembershipが持つ`staffId`を渡し、「通知」タブを開いている間だけ履歴queryを実行する。

`organizationPersonId`が未設定のスタッフは、既存のスタッフ詳細Dialogから同じ共通コンポーネントを使用する。

query結果は、描画可能なViewModelとして次の順に渡す。

```text
UserDetail
  -> UserNotificationTab
    -> StaffNotificationHistory

StaffManagement（未移行スタッフ）
  -> StaffManagementView
    -> StaffDetailDialog
      -> StaffDetailNotificationTab
        -> StaffNotificationHistory
```

Storybookではqueryを実行せず、履歴ViewModelをpropsで注入する。

### 10.2 画面構造

既存の「情報 / 通知 / LINE / 設定」の4タブを維持する。

「通知」タブの既存再送領域を「通知を送る」として残し、その下へ「これまでの通知」を追加する。

新しい5つ目のタブは作らない。

現在は4タブ全体が`disabled={isReadOnly}`の`fieldset`内にあるが、履歴のページングは読み取り操作である。

共通`fieldset`を各タブの編集・送信操作の周囲へ移し、「これまでの通知」と「もっと見る」は`fieldset`外へ配置する。

これにより、グループ管理などでスタッフ編集が読み取り専用でも、通知履歴の閲覧と追加読み込みを可能にする。

PCでは次の4列のTableを表示する。

| 列 | 内容 |
| --- | --- |
| 日時 | `sentAt ?? requestedAt`をJSTで表示 |
| チャネル | メールまたはLINE |
| タイトル | `displayTitle` |
| 状況 | 正規化した状態Badge |

スマホでは1通知を1カードとして縦に並べる。

タイトルはPCでは省略とTooltip、スマホでは2行まで表示する。

履歴は最新順とし、初回20件の後に「もっと見る」を表示する。

### 10.3 表示状態

| 状態 | 表示 |
| --- | --- |
| Loading | 履歴セクション内のSkeleton |
| Empty | Title「送った通知はまだありません」 / Description「今後、このスタッフに送った通知がここに表示されます。」 |
| Error | Title「通知履歴を読み込めませんでした」 / Description「画面を再読み込みしてください。」 |
| CanLoadMore | 「もっと見る」 |
| LoadingMore | 既存行を維持し、「もっと見る」をloadingにする |

履歴取得の失敗で、スタッフ情報、LINE設定、既存の通知再送操作を使えなくしない。

### 10.4 状況文言

| 機械値 | 表示 |
| --- | --- |
| `queued` | 送信待ち |
| `sent` | 送信済み |
| `delivered` | 配信済み |
| `delayed` | 配信が遅れています |
| `failed` | 送れませんでした |
| `cancelled` | キャンセル |

履歴セクションに次の補足を置く。

> 配信済みは、メールサーバーまで届いた状態です。LINEの端末到達や開封は確認できません。

### 16.1 ロールバック

フロントエンドを戻しても、既存画面は新テーブルを参照しないため従来どおり動作する。

バックエンドを戻す場合も、`notificationHistory`テーブル、Outbox payloadのoptionalな`history`、provider event validator、optional化した`errorMessage`を受理するwidened schemaは残す。

履歴のwrite、query、Webhook反映だけを止める互換版へ戻し、既存Outbox配送は停止させない。

新しいshapeのpending Outboxや配送eventが残る状態で、変更前schemaへ単純にrevertしない。

Resendの`email.delivered`購読が残っていても、旧Webhook実装は対象外eventを`200`で無視する。

作成済みの履歴は削除せず、再デプロイ後に継続利用する。

将来schema自体を完全に戻す必要が生じた場合だけ、writer停止、pending Outbox確認、履歴と新eventのbounded cleanup、残存確認を経てnarrowする。

# URLクエリ順序とエラー復旧画面の修正計画

作成日: 2026-09-08  
状態: Active（実装済み。追加したTOP導線を含む最新PR headのCI・自動レビューによる検証待ち）

クエリのキーと値が同じなら、並び順が違ってもそのまま画面を表示する。  
あわせてエラー画面を「再読み込み → シフトリTOPから再ログイン → 問い合わせ」の3段階にし、問い合わせにコピーする詳細へRouterが保持するエラーを追記する。

## 1. 問題と対象

現行の正規化処理は、クエリ文字列をそのまま比較している。キーの順序だけが異なるURLでもリダイレクトするが、TanStack Routerが同じ内容のsearchオブジェクトを再利用して順序を維持するため、同じURLへのリダイレクトが繰り返される。

ローカルでは、実際に使用しているRouterと正規化処理を組み合わせたテストで、逆順のURLから`Too many redirects`になることを確認した。従来のChakra依存のエラー表示を組み合わせると、二次的な`ChakraProvider`エラーが表示されることも再現した。これはローカルの再現結果であり、問い合わせ端末の例外履歴や配信済みコードを直接取得した証跡とは区別する。

| 対象画面 | パス | 受け入れる順序の例 |
|---|---|---|
| ダッシュボード | `/dashboard` | `shop→org`、`org→shop` |
| シフト | `/shifts` | `shopFilter→org`、`org→shopFilter` |
| スタッフ | `/staff` | `shopFilter→org`、`org→shopFilter` |
| 要対応 | `/actions` | `shopFilter→org`、`org→shopFilter` |
| プランと支払い | `/manage/billing` | `stripe→org`、`org→stripe` |
| アカウント設定 | `/account` | `flow→org`、`oauth→flow`、`org・flow・oauth`の各順序 |

旧URL専用の修正は対象に含めない。Cloudflare設定、認証方式、Cookie・サイトデータの削除、監視基盤の追加も今回の変更には含めない。

## 2. URLの比較方法

`getCanonicalAppHref`と`needsAccountSecuritySearchCanonicalization`の比較を、順序に依存しない方式へ変更する。現在のクエリと、既存の検証・正規化で得たクエリを、それぞれ`URLSearchParams`として読み、比較用のコピーだけをキーでソートして比較する。

| 入力の状態 | 処理 |
|---|---|
| 許可されたキーと値が同じで、キーの順序だけが異なる | リダイレクトしない。入力されたURLをそのまま使う |
| `%20`と`+`など、デコード後のキー・値が同じ | 表記差だけを理由にリダイレクトしない |
| 未知のキー、空値、許可されない値、既存規則で除去する前後空白がある | 現在の正規化規則を適用し、有効なクエリへ収束させる |
| 同じキーが重複している | 比較時に重複を潰さず検出し、現在の正規化規則に従って整理する |

許可キー、値の意味、組織・店舗の選択、`stripe`・`flow`・`oauth`の検証規則は維持する。`/account`は認証ルートの`beforeLoad`と画面内の正規化処理が同じ判定を使うため、両方が収束することを確認する。

URLを生成する側の既存のキー順序は維持する。Routerの依存更新・パッチ、全体のsearch文字列化の変更、`validateSearch`のキー順変更は行わない。

## 3. エラー画面と追加情報

### 手順と文言

「1〜2時間ほど時間をおいてから」という待機手順を削除し、2番にはシフトリTOPからログインをやり直す導線を置く。

| 番号 | 見出し | 本文・操作 |
|---|---|---|
| 1 | ページを再読み込みする | 既存の再読み込みボタン、PCの強制再読み込み・スマートフォンの案内を維持する |
| 2 | シフトリTOPから再度ログインする | ボタンの見た目を持つ「シフトリTOPへ」リンクで、`https://shiftori.app`を同じタブで開く |
| 3 | それでも改善しない場合 | 「エラーの詳細を表示し、内容をコピーしてお問い合わせの本文に貼り付けてお送りください。」と案内する |

TOPへの導線は`<a href="https://shiftori.app">`を使い、Routerの画面遷移処理へ依存させない。詳細の開閉と「以下の内容をすべてコピーしてください。」を維持する。問い合わせ先は`https://shiftori.app/contact`を直接指定した通常の別タブリンクとし、`target="_blank"`と`rel="noopener noreferrer"`を維持する。画面は既存のHTML・CSSを使い、ヘッダーやダークモード対応は追加しない。

### 同じエラー欄に追記する内容

現在表示している`error.message`を先頭に残し、その下へ次の抽出結果に相当する情報を整形して追記する。

```ts
window.__TSR_ROUTER__?.state.matches
  .filter((match) => match.status === "error")
  .map((match) => ({
    route: match.routeId,
    message: match.error?.message,
  }));
```

表示例:

```text
useContext returned 'undefined'. Seems you forgot to wrap component within <ChakraProvider />

ルーター内のエラー:
[
  {
    "route": "__root__",
    "message": "Too many redirects"
  }
]
```

エラー画面のクライアント側のeffectで、表示対象のエラーごとに一度スナップショットを取得する。サーバーレンダリング中と初回描画では`window`を読まず、Chakra・RouterのContextに依存するhookも追加しない。取得・型の確認・整形を例外処理で保護し、Routerが存在しない場合や読み取りに失敗した場合も元のエラーを表示する。

Routerから得るのは、`status === "error"`のmatchの`routeId`と文字列の`message`だけとする。取得できた項目がない場合は追記部分を表示しない。Reactの描画例外がRouterのmatchに残らない場合もあるため、追加情報が空であることを「エラーなし」と扱わず、元のメッセージを置き換えない。

Storybookには任意の表示用props `routerErrors`で固定データを渡せるようにする。props省略時だけ実Routerを読み取り、各Storyの共通argsには空配列、詳細Storyには上記のようなデータを渡す。他のStoryが持つRouterの状態には依存させない。

### Security Lens

利用者の入力境界はURLクエリであり、順序に依存しない比較はアクセス権の判定には使用しない。既存の入力検証、ログイン、組織・店舗のサーバー側認可を維持する。`stripe`や`oauth`がURLに存在するだけで支払い・本人確認を完了扱いにする変更は加えない。

追加情報は利用者が問い合わせへコピーするテキストとして扱う。Router全体、実URL、params、Cookie、認証状態は付加せず、元のエラーと追加情報を同じ`pre[data-clarity-mask="true"]`内に表示する。メッセージ自体に値が含まれる可能性は残るため、HTMLとして解釈せず、問い合わせURLや自動送信ログにも追加しない。

## 4. 変更箇所と検証

| ファイル・配置 | 変更内容 |
|---|---|
| `src/components/features/AuthenticatedApp/appRoutePolicy.ts` | 現在のクエリと正規化後のクエリを順序に依存せず比較する |
| `src/pages/account-security/search.ts` | アカウント画面の正規化判定にも同じ比較方式を適用する |
| `src/lib/searchParams.ts` | 上記2箇所で使う、順序に依存しない比較を所有する |
| `src/components/ui/RouteErrorFallback/index.tsx` | 待機手順の削除、TOPへの再ログイン導線、番号・見出しの調整、Routerエラーの取得・追記。必要な補助処理は同フォルダーに置く |
| `src/components/ui/RouteErrorFallback/index.stories.tsx` | 3段階の手順、TOPと問い合わせへのリンク、追加情報あり・なし、PC/SPの長文表示を固定データで確認する |
| 既存の正規化テストと`src/router.test.tsx` | 値の維持、正規化の収束、実Routerによる遷移、一次・二次エラーの併記を確認する |
| `doc/features/public-pages.md` | 復旧手順を再読み込み・TOPからの再ログイン・問い合わせの3段階へ更新し、エラー詳細の追加項目を記載する |

URLの契約は`logic` projectのテストを主担当とする。対象6画面について有効なキーの順序を入れ替え、実Routerによる遷移が完了し、`Too many redirects`にならず、値が維持されることを検証する。`/account`の組織指定なし、クエリなし・単一キー、未知のキー・空値・不正値も含める。生のクエリ文字列の重複キーとエンコードの比較は、正規化helperの単体テストで確認する。RouterはbeforeLoadに渡す前に重複キーを配列へ変換するため、今回の順序修正ではその既存仕様を変更しない。Router内部の再試行回数はテストの期待値に固定しない。

エラー情報の検証は、Routerのerror状態だけを抽出すること、Router不在・取得例外で画面が壊れないことをFrontend Unitで確認する。既存のRouter結合テストでは「root loaderの一次例外 → rootのエラー表示の二次例外 → 最上位の画面に両方が残る」を検証する。サーバー側の描画とクライアント側の追加情報取得も確認する。

表示と操作は既存Storybook Behaviorを更新する。手順数、詳細の開閉、元のエラーとRouterエラーの併記、再読み込み操作、マスク属性、TOPの同一タブリンク、問い合わせの別タブリンクを確認し、PC/SPの代表状態をVRT対象とする。実装開始時の依頼で指定された`babysit-pr`の手順に従い、初回push前のローカル全体検証は行わず、CIでlint・型・テスト・buildを確認する。失敗した場合は対応する対象だけをローカルで確認し、修正後の最新headを再検証する。VRTはprepare・build・全captureの成功とcompare開始までを確認し、差分の承認は行わない。Production反映は別の状態として報告する。

## 5. 完了条件と参照

対象のURLを順序に関係なく開け、必要な正規化も収束すること。エラー画面は再読み込み・TOPからの再ログイン・問い合わせの3段階の復旧案内となり、取得可能なRouterエラーを同じ欄へコピーでき、追加情報が取得できなくても元のエラー表示を継続できること。この契約を自動テストと関連文書へ反映した時点で実装完了とする。

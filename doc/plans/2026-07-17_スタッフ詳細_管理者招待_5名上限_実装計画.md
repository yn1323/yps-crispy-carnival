# スタッフ詳細からの管理者招待とグループ5名上限の実装計画

作成日: 2026-07-17

状態: 実装済み（2026-07-17）

## 1. 目的

ダッシュボードのスタッフ詳細から、選択した既存スタッフへ管理者招待を送れるようにする。

管理者権限は招待の承認後に付与し、現在のメール招待、本人確認、監査、通知のライフサイクルを維持する。

Free以外では、有効管理者と有効な追加招待を合わせてグループ全体で5枠までとする。

Freeでは、現在と同じく有効管理者を1名に限定し、既存スタッフとの管理者交代だけを許可する。

Freeの交代が承認されたら、旧管理者の管理者権限と、交代したグループの管理画面を閲覧する権限を失効させる。

旧管理者のログインアカウント、グループ内の人物所属、交代前から存在する店舗のスタッフ所属は維持し、シフトとスタッフ向け通知の対象判定を変更しない。

画面では「グループ」を使い、コード、DB、APIの内部名は`organization`のまま維持する。

## 2. スコープ

この計画には次を含める。

- スタッフ詳細の「設定」タブへ管理者招待の開始導線を追加する。
- 選択したスタッフを安定したIDで指定する管理者招待mutationを追加する。
- Trial、Pro、Business、無償Businessの管理者上限を5名へ統一する。
- 有効な追加招待に管理者枠を予約し、作成、再送、承認、取消、期限切れで一貫して移動または解放する。
- Freeの管理者交代では、承認と同時に旧管理者の管理画面へのアクセスだけを失効させ、スタッフ所属を維持する。
- ダッシュボードの管理者表示と招待状態を、グループ所属を正として返す。
- グループ設定の招待可否、再送可否、上限文言を同じ契約へ揃える。
- Function Test、Logic Test、Convex Scenario Test、StorybookのBehavior Test、VRT用Story、仕様書を更新する。
- リリース前に、既存の上限超過データと、交代後も閲覧できる旧管理者データを監査し、安全に整理する。

この計画では次を行わない。

- スタッフを承認なしで直接管理者へ変更しない。
- スタッフ詳細へ招待の再送と取消を追加しない。
- 招待トークン、7日間の有効期限、単回利用、メール通知、Outboxの設計を変更しない。
- 課金専用管理者など、新しい権限ロールを追加しない。
- 5名上限への変更だけを理由に、既存のactive管理者を機械的に降格または削除しない。
- 管理者交代を理由に、旧管理者の`organizationPeople`または`staffs`を削除しない。
- 新しいcounter、queue、workflow、監視基盤を追加しない。
- E2EとAIによるブラウザ操作を追加しない。

`isManager`の現在の意味では、閲覧中の本人以外の管理者兼スタッフを正しく表示できない。

実際の有効管理者は承認時の再検証で5名を超えないが、後から承認できない招待を発行するため、今回の完成形にはしない。

現在のFree管理者交代は、旧管理者を「管理者ではないスタッフ」へ戻す要件とも一致しない。

`readOnly`は管理画面のqueryを許可する状態であり、交代後の旧管理者へ使うと店舗情報が残るためである。

## 4. 完成形の業務契約

### 4.1 プラン別の上限

| プランまたは状態 | 有効管理者と有効な追加招待の合計上限 |
| --- | ---: |
| Trial | 5 |
| Free | 有効管理者1名、追加招待0件 |
| Pro | 5 |
| Business | 5 |
| 無償Business | 5 |

無償BusinessはBusinessのpolicyを利用するため、Businessの上限変更をそのまま適用する。

`active`だけを管理者枠へ数え、`readOnly`と`removed`は数えない。

`readOnly`は、管理者としての関係を維持したまま書き込みだけを制限する状態に限定する。

管理者ではなくなった人物は`removed`とし、権限解除を`readOnly`で代用しない。

この状態変更は管理画面の権限だけを表すため、`organizationPeople.status`と既存の`staffs.isDeleted`、`staffs.excludedFromShift`は変更しない。

### 4.2 管理者枠の予約

管理者枠の使用数を次で定義する。

```text
見込み管理者数
= activeのorganizationMembers件数
+ 期限内かつpendingのmanagerAddition招待件数
```

`freeManagerExchange`は現在の1名と新しい1名を入れ替えるため、追加管理者枠を予約しない。

期限切れ、取消済み、承認済みの招待は管理者枠へ数えない。

既存スタッフへの招待は利用人数枠を増やさないが、追加管理者枠を1枠予約する。

新しい人物への招待は、現在の`reservedSeat`で利用人数枠を予約し、同時に追加管理者枠も予約する。

利用人数枠と管理者枠は意味が異なるため、`reservedSeat`を管理者枠のフラグとして再利用しない。

管理者枠は招待のstatus、purpose、有効期限から導出し、管理者枠専用の永続フィールドは追加しない。

スタッフ対象の招待だけは対象人物を承認まで固定するため、後述の`targetPersonId`をbusiness-optionalな永続フィールドとして追加する。

### 4.3 状態遷移ごとの上限処理

| 操作 | 管理者枠の扱い |
| --- | --- |
| 追加招待の新規作成 | 現在の見込み管理者数へ1を加えて5以下か確認する |
| 期限内招待の再送 | 古い招待の1枠を除外し、新しい招待の1枠へ付け替える |
| 期限切れ招待の再送 | 古い招待には予約がないため、新しい1枠を取得する |
| 追加招待の承認 | 対象招待の予約を除外し、同じtransactionでactive所属へ移す |
| Free管理者交代の承認 | 追加枠を使わず、新管理者をactive、旧管理者の管理者所属をremoved、旧管理者の旧店舗管理権限を削除済みにする。人物所属とスタッフ所属は同じtransactionで維持する |
| 取消または期限切れ | pending状態を終了し、導出される予約を解放する |

作成、再送、承認は同じグループのactive所属とpending招待のindex範囲を読み、同じtransactionで招待または所属を書き換える。

異なるメールへの同時招待でも、最初の書き込み後にConvexのOCCで再実行され、後続処理は更新後の見込み管理者数を確認する。

別のcounter文書を追加しない。

### 4.4 Freeで管理者ではなくなった後の所属と閲覧

管理者交代またはFree適用で管理者ではなくなった人物は、グループ人物を維持し、交代前からある店舗のスタッフ所属も維持したまま、管理画面の権限だけを失う。

交代前に店舗のスタッフ所属がなかった人物は、グループ人物だけを維持し、未所属店舗へ自動でスタッフ登録しない。

| データ | 交代承認後の状態 | 維持する業務 |
| --- | --- | --- |
| ログインアカウント | 維持する | ログイン自体は許可する |
| `organizationPeople` | activeのまま維持する | グループ内で同一人物として扱う |
| `staffs` | 交代前から存在する行の`isDeleted`と`excludedFromShift`を変更しない | 交代前にシフト対象だった店舗では、シフト作成、送信、通知、スタッフ向け導線の対象に残す |
| `organizationMembers` | 旧管理者の行を`removed`にする | 管理者queryとmutationを拒否する |
| 旧`shopMembers` | 旧管理者の行を`isDeleted: true`にする | 旧モデルのfallbackから管理権限が復活しないようにする |

`organizationMembers`は名前に`Members`を含むが、この画面ではグループ管理者の認可を表す。

スタッフとしてのグループ所属は`organizationPeople`、店舗所属は`staffs`を正とする。

交代を理由に、旧管理者を所属していなかった店舗へ新しくスタッフ登録しない。

全店舗へスタッフ行を作ると、意図しない店舗のシフト通知対象になるためである。

交代を承認するまでは、現在の管理者が引き続き管理画面を利用できる。

承認したtransactionが確定した時点で、旧管理者の`getMyShops`から交代したグループの全店舗を外し、グループ設定、店舗ダッシュボード、店舗名を含む管理画面のデータを返さない。

旧管理者がログイン中でも強制ログアウトは行わない。

購読更新を受けた`AuthGuard`が保存済みの選択店舗を消去し、消去が完了するまで旧店舗の子画面を描画しない。

その後は、管理できる店舗がないことだけを示す共通状態を表示し、旧グループ名と旧店舗名を表示しない。

旧管理者が別グループで有効な管理者である場合は、その別グループの権限まで失効させない。

### 4.5 スタッフを対象にした招待API

スタッフ詳細専用に`api.organizationInvitation.mutations.createForStaff`を追加する。

引数は`shopId`、`staffId`、`requestId`だけとし、メールアドレスとグループIDをクライアントから受け取らない。

サーバーは次を順に確認する。

1. 呼び出し元が選択中店舗と同じグループの有効管理者である。
2. `staffId`が選択中店舗の論理削除されていないスタッフである。
3. `organizationId`と`organizationPersonId`が両方設定されている。
4. 対象人物が呼び出し元と同じグループに属し、activeである。
5. スタッフと人物の正規化済みメールアドレスが現在も一致する。
6. 対象人物がすでにactive管理者ではない。
7. 契約状態、管理者枠、必要な利用人数枠が許可する。

別店舗、別グループ、削除済み、移行未完了、人物対応が曖昧な対象は、列挙可能な差を返さず`Not found`または共通の利用不可エラーにする。

招待先メールアドレスは、現在の`organizationPeople`からサーバー側で解決する。

これにより、スタッフ詳細を開いた後に別の管理者がメールアドレスを更新しても、古いメールを別人物として招待しない。

作成した招待には`targetPersonId`として対象の`organizationPeople._id`を保存する。

承認、公開preview、送信直前の再確認では、`targetPersonId`がある招待をメール検索だけで別人物へ付け替えない。

対象人物が削除された場合、または別グループへ変わった場合は、その招待を`conflict`または`unavailable`として拒否する。

招待後に対象人物のメールアドレスが変わった場合は、古い招待の承認と通常の再送を拒否する。

現在のスタッフ詳細から招待し直すときは、同じ`targetPersonId`の期限内pending招待を検出し、古い招待を`revoked`、現在メールへの新しい招待を`pending`へ同じtransactionで付け替える。

この付け替えでは古い招待の管理者予約を除外して新しい招待へ移し、一時的にも二枠を消費しない。

古いtokenは同じtransactionで失効させ、古いメールから別人物を管理者化しない。

同じ`targetPersonId`に複数の期限内pending招待があるなど対応が曖昧な場合は、副作用なしで`conflict`にする。

`targetPersonId`がない既存招待とグループ設定からの任意メール招待は、現在と同じメールアドレス対象の契約を維持する。

グループ設定の`create(email)`は任意メールアドレス招待の既存契約として維持する。

`create(email)`と`createForStaff(staffId)`は、private helperへ切り出した作成処理を共有する。

共有対象は、契約判定、重複招待判定、上限、rate limit、`requestId`による監査冪等性、token発行、期限処理、Outbox予約、監査イベントである。

管理者権限は招待承認でだけ付与し、`createForStaff`から直接所属を有効化しない。

### 4.6 招待ライフサイクル

次の既存契約は変更しない。

- URLへメールアドレス、グループID、権限名を含めない。
- tokenはdigestだけを保存する。
- 有効期限は発行から7日間とする。
- 一度だけ利用できる。
- 再送時は古い未使用招待を無効にする。
- 承認時はログイン済みアカウントの確認済みメールアドレスと招待先を一致させる。
- 招待元管理者、対象人物、契約、上限を承認時にも再確認する。
- `targetPersonId`がある招待は、承認時に同じ人物と招待時メールの一致を再確認し、新しい人物へfallbackしない。
- 発行、再送、承認は既存のrate limitを利用する。
- メール配送は既存Notification Outboxを利用する。
- token、メール本文、不要な個人情報を監査metadataへ保存しない。

### 4.7 ダッシュボードDTO

`getDashboardStaffs`の`isManager`は、対象スタッフの`organizationPersonId`と同じグループの`organizationMembers.status === "active"`を正として導出する。

閲覧中利用者との一致だけで管理者判定しない。

スタッフ詳細が表示に必要な招待状態を、次のようなdiscriminated unionで追加する。

```ts
type StaffManagerInvitationState =
  | { kind: "available"; mode: "addition" | "freeManagerExchange"; replacesStaleInvitation: boolean }
  | { kind: "pending"; mode: "addition" | "freeManagerExchange" }
  | { kind: "unavailable"; reason: string };
```

DTOには招待token、他人の招待ID、グループ全体の利用者一覧を含めない。

グループ設定用の大きな`getSettings` DTOをダッシュボードから購読しない。

`getDashboardStaffs`内で、選択中グループのpolicy、見込み管理者数、有効な招待を一度解決し、ページ内の対象スタッフへ状態を割り当てる。

`targetPersonId`がある招待は人物IDを先に照合し、現在メールも一致する有効な招待があれば`pending`を返す。

同じ`targetPersonId`で招待時メールだけが古い場合は、`available`と`replacesStaleInvitation: true`を返す。

`targetPersonId`がない既存招待は、現在どおり同じメールへの有効な招待を`pending`として扱う。

active管理者、メール未設定、移行未完了、閲覧のみの呼び出し元、契約制限中、5枠到達では`unavailable`と理由を返す。

Freeでは、既存の管理者交代条件を満たす対象だけ`freeManagerExchange`の`available`にする。

画面表示は先回りの案内であり、mutationは同じ条件を必ず再確認する。

### 4.8 スタッフ詳細のUI

「設定」タブへ「管理者権限」セクションを追加し、シフト対象の後、削除操作の前に置く。

状態ごとの表示は次とする。

| 状態 | 表示 |
| --- | --- |
| 追加招待可能 | 「管理者として招待」ボタンを表示する |
| Freeの交代可能 | 「管理者交代を依頼」ボタンを表示する |
| active管理者 | 「管理者」Badgeと「このスタッフは管理者です」を表示する |
| 同じ対象への有効な招待あり | 「招待中」Badgeと、再送と取消はグループ設定で行う案内を表示する |
| 招待後に対象人物のメール変更あり | 「新しいメールへ招待し直す」ボタンを表示する |
| 5枠到達 | ボタンを無効にし、グループ全体の上限と解決方法を表示する |
| メール未設定 | ボタンを無効にし、スタッフ情報へのメール登録を案内する |
| 移行未完了 | ボタンを無効にし、グループ単位の設定移行完了を待つよう案内する |
| 閲覧のみまたは契約制限中 | ボタンを無効にし、サーバーが返した理由を表示する |

5枠到達時の基本文言は「管理者と招待中の管理者は、グループ全体で5名までです。管理者権限を外すか、招待を取り消してからもう一度お試しください。」とする。

追加招待の確認表示は次を基本とする。

- 見出しは「{スタッフ名}さんを管理者として招待しますか？」とする。
- 本文は「{メールアドレス}に招待メールを送ります。承認後、このグループのすべての店舗と、プランと支払いを含む契約設定を管理できるようになります。」とする。
- 取消は「やめる」、確定は「招待メールを送る」とする。

メール変更後の招待し直しでは、「以前の招待を無効にして、現在のメールアドレスへ招待を送ります」と補足する。

Freeの確認表示は次を基本とする。

- 見出しは「{スタッフ名}さんへ管理者を交代しますか？」とする。
- 本文は「承認されると、{スタッフ名}さんが新しい管理者になります。現在の管理者は、このグループのすべての店舗とグループ設定を開けなくなります。スタッフとしての所属と、シフト対象・通知の設定は変更されません。」とする。
- 補足は「招待が承認されるまでは、現在の管理者が引き続き利用できます。」とする。
- 取消は「やめる」、確定は「交代の招待を送る」とする。

グループ設定の既存`ManagerInvitationDialog`も同じ説明へ変更し、旧管理者が閲覧のみになるとは案内しない。

確認は既存の削除確認と同じインライン表示とし、Dialogの上へ別のDialogを重ねない。

`PendingAction`へ管理者招待を追加し、スタッフ詳細を閉じたとき、対象スタッフが変わったとき、capabilityを失ったときに確認状態を破棄する。

送信処理は新しい`useStaffManagerInvitation` controllerが所有する。

controllerは`useSingleFlight`、`crypto.randomUUID()`の`requestId`、最新propsの再確認、成功Toast、エラー表示を担当する。

成功時は追加招待なら「管理者招待を送りました」、Free交代なら「管理者交代の招待を送りました」と表示する。

上限競合や通信失敗で自動再送せず、確認表示を維持して理由を確認できるようにする。

## 5. 実装手順

### 5.1 上限policyを5名へ変更する

`convex/organizationBilling/policy.ts`の`ORGANIZATION_PLAN_LIMITS`を変更する。

Trial、Pro、Businessの`maxActiveManagers`を5にし、Freeの1は維持する。

`convex/organizationBilling/policy.test.ts`で、各planの上限値、5名は許可、6名は`activeManagers`違反になる境界を固定する。

### 5.2 見込み管理者数を共通化する

`convex/organization/service.ts`の`OrganizationUsageSnapshot`へ、期限内の追加招待数と見込み管理者数を追加する。

purpose未設定の既存招待は、現在のfallbackと同じく`managerAddition`として安全側に数える。

純粋なpurpose fallbackは`convex/organizationInvitation/purpose.ts`へ分け、`organization/service.ts`と`organizationInvitation/service.ts`の循環依存を作らない。

対象招待自身の予約だけを除外できるoptionを追加し、organizationId、pending、有効期限、purposeが一致する場合だけ除外する。

`convex/organizationBilling/service.ts`の`requireOrganizationCapacity`は、active管理者数ではなく見込み管理者数へ増分を加えて判定する。

エラー文言は、利用人数上限と管理者5枠上限を区別する。

`convex/organizationBilling/mutations.ts`の有料契約開始、有料復旧、Pro変更予約、有料planの期限適用も見込み管理者数を利用する。

Freeまたは契約制限中への移行では、既存の`revokePendingManagerInvitations`を同じtransactionで維持し、追加招待を失効させて管理者予約を解放する。

Free移行は、失効予定の追加招待を理由に拒否しない。

`convex/organizationBilling/mutations.ts`の`applyFreeOrRestricted`は、Free成立時と契約制限継続時の所属状態を区別する。

- 次状態が`active.free`なら、選択管理者だけをactiveにし、選択されなかった旧管理者を`removed`にする。
- 次状態が`restricted`なら、復旧担当者は既存どおりactiveまたは`readOnly`で維持する。
- Free成立時に`removed`へ変更する人物も、`organizationPeople`と既存の`staffs`は変更しない。
- Free成立時に`removed`へ変更する人物の旧`shopMembers`も、同じtransactionで削除済みにする。

Free適格性を確定する前に永続statusを変更せず、見込み状態で利用人数と管理者数を評価してから、`active.free`または`restricted`に対応するstatusを一度だけ保存する。

### 5.3 招待の作成、再送、承認へ予約移動を接続する

`convex/organizationInvitation/mutations.ts`の共通作成処理をprivate helperへ分ける。

`create`と新しい`createForStaff`から同じhelperを呼ぶ。

新規作成は追加管理者枠を1枠取得する。

再送は、期限内の元招待だけを除外して1枠を付け替える。

承認は、対象招待の予約を除外してactive所属を1件増やす。

Free交代では追加管理者数を0とする。

Free交代の承認では、次の変更を招待の承認、新管理者のactive化、`freeManagerPersonId`の更新、監査と同じtransactionで確定する。

- 旧管理者の`organizationMembers.status`を`readOnly`ではなく`removed`へ変更する。
- 旧管理者の対象グループ配下にある旧`shopMembers`を`isDeleted: true`へ変更する。
- 旧管理者の`organizationPeople`と既存の`staffs`は更新または削除せず、`staffs.isDeleted`と`staffs.excludedFromShift`を変更しない。
- 旧管理者が所属していなかった店舗へ、新しい`staffs`を作成しない。
- `organization.manager_role_removed`を記録し、旧管理者に有効な`staffs`があれば`toState: "staffOnly"`、なければ`toState: "personOnly"`とする。
- 既存の招待承認とFree選択変更の監査も維持する。
- 承認中の交代招待を除き、旧管理者を`inviterMemberId`とする他のpending招待を同じtransactionでrevokedにする。
- 旧管理者向けの未送信の管理者通知と課金通知は、既存`cancelOrganizationRecipientBusinessNotifications`を`preserveStaffNotificationsForUser: true`で呼んでcancelし、スタッフとして受け取るシフト通知はcancelしない。

招待が未承認、取消済み、期限切れ、または承認失敗のときは、旧管理者の権限とスタッフ所属を変更しない。

取消と期限切れはstatus変更だけで予約を解放できることを維持する。

### 5.4 スタッフIDの対象検証を追加する

`convex/organizationInvitation/mutations.ts`へ`createForStaff`を追加する。

`convex/staff/service.ts`の`getActiveStaffInShop`を利用し、選択中店舗との一致を検証する。

`organizationPeople`との完全なリンク、active状態、メール一致、管理者所属を検証する。

`convex/schema.ts`の`organizationInvitations`へ`targetPersonId: v.optional(v.id("organizationPeople"))`を追加する。

`targetPersonId`はスタッフ対象招待だけに必要なbusiness-optional fieldであり、既存招待のbackfillと将来のNarrowは行わない。

承認処理は`targetPersonId`がある場合にその人物を再取得し、メール検索から新しい人物を作るfallbackへ入らない。

`createForStaff`は同じ`targetPersonId`のpending招待も検索する。

招待メールが現在の人物メールと一致する場合は`alreadyPending`を返す。

一致しない場合は、古い招待を`revoked`にして予約を除外し、新しい招待を作成する処理を同じtransactionで行う。

この処理でも作成rate limit、`requestId`の冪等性、監査、Outboxを再利用する。

`convex/organizationInvitation/schemas.ts`は`requestId`の既存schemaを再利用し、必要ならスタッフ対象の入力schemaを追加する。

public mutationには`args`と`returns` validatorを定義し、既存の作成結果DTOを再利用する。

### 5.5 グループ設定の招待表示を揃える

`convex/organization/queries.ts`の`canInviteManagerAddition`を、見込み管理者数が5未満かで判定する。

招待ごとの再送判定では、その招待自身の予約だけを差し引いて再取得できるか確認する。

上限で承認できない招待は`limitReached`とし、5名上限と解決操作を表示する。

`src/components/features/OrganizationSettings/index.stories.tsx`の上限到達Storyを、利用人数ではなく管理者枠だけが5に到達したfixtureへ更新する。

`src/components/features/OrganizationSettings/ManagerInvitation/ManagerInvitationDialog.tsx`のFree交代説明を、旧管理者の管理画面アクセスが失効し、スタッフ所属とシフト対象・通知設定は変わらない説明へ変更する。

`src/components/features/OrganizationSettings/PlanAndPaymentSection.tsx`のFree選択説明も同じ契約へ揃える。

- 「選ばなかった管理者は、Free適用後も閲覧のみで残ります」は、「選ばなかった管理者は、Free適用後、このグループの管理画面を開けなくなります。スタッフとしての所属とシフト対象・通知設定は変更されません」へ変更する。
- 「閲覧のみになる管理者」は「管理者権限が外れる人」へ変更する。
- 契約制限中の復旧担当者を表す`readOnly`の案内は変更しない。

### 5.6 ダッシュボードDTOを拡張する

`convex/dashboard/queries.ts`の`dashboardStaffValidator`へ管理者招待状態を追加する。

`isManager`を対象人物のactiveなグループ所属から導出する。

### 5.7 交代後のログイン状態を同期する

`convex/dashboard/queries.ts`の`getMyShops`は、`removed`の管理者所属から交代したグループの店舗を返さない契約を維持する。

## 8. 移行とリリース

### 8.1 Persisted shape

管理者予約は既存招待から導出するため、予約専用のschema変更とbackfillは不要とする。

`reservedSeat`の意味も変更しない。

スタッフ対象を固定する`targetPersonId`はoptional fieldとして追加する。

このfieldは既存招待と任意メール招待では存在しないことが正しいため、backfill、migration runner、`TODO[narrow]`は追加しない。

既存の`create(email)`は維持し、`createForStaff`とDashboard DTOは追加契約として導入する。

管理者所属の`active`、`readOnly`、`removed`は既存validatorで表現できるため、この状態変更にschemaのWidenとNarrowは不要である。

ただし、現行処理で交代済みの旧管理者を`readOnly`から`removed`へ直すデータ移行は必要になる。

### 8.2 交代済み旧管理者のデータ移行

既存の`@convex-dev/migrations`基盤を使い、実装時点の次の連番で二つの冪等なmigrationを追加する。

現状の連番を前提にすると、`m013_former_managers_remove_manager_access.ts`と`m014_removed_organization_members_delete_legacy_shop_members.ts`になる。

先行する`m012`が固定seriesへ未登録または未完了なら連番を飛ばさず、`m012`の成功を確認してから`m013`と`m014`をseriesへ追加する。

ただし、migrations component上で`m012`が完了していることだけを開始条件にしない。

`migrationSourceShopId`があるグループは、m012が所有する未解決conflictが0件であり、課金状態が一意な`complimentary.business`になったことを確認できるまで、`m013`の自動変更対象から外す。

m012がconflictを記録して終了したグループを誤ってFreeと判定し、旧管理者を失効させないためである。

`m013`は`organizationMembers`を小さいbatchで走査し、現在のstatusが`readOnly`で、次のいずれかを満たす行だけを`removed`へ変更する。

- 対象グループの有効な権利がFreeで、課金状態の`freeManagerPersonId`が存在し、対象行の`personId`と異なる。
- 対象memberを`inviterMemberId`に持つacceptedの`freeManagerExchange`招待と、それに対応する`organization.free_selection_changed`監査から、対象人物が旧管理者だったことを一意に確認できる。
- `organization.billing_state_changed`の`toState: "free"`と同じ時刻に対象memberが`readOnly`へ更新され、Freeで選択されなかった旧管理者だと一意に確認できる。

Free管理者交代の監査で旧管理者を一意に確認できる場合は、現在のプランが有料または無償Businessでも自動移行の対象にする。

これにより、Free交代後にProまたはBusinessへ移り、再開管理者に選ばれなかった旧管理者も取りこぼさない。

過去の交代を根拠にする場合は、招待の`acceptedAt`と`acceptedByPersonId`、監査の`fromState: "manager:{旧personId}"`と`toState: "manager:{新personId}"`、correlationを相互確認する。

過去のFree適用を根拠にする場合は、課金状態変更監査の`occurredAt`、memberの`updatedAt`、Free選択変更の監査履歴を相互確認する。

当時の選択管理者と非選択管理者を履歴から復元できない場合は、自動変更しない。

交代後に対象人物を`acceptedByPersonId`とする`managerAddition`が承認されている場合、memberの`updatedAt`が交代時刻より後である場合、または履歴が複数あって最新の役割を一意に決められない場合は、自動変更せずconflictにする。

現在が契約制限中なら、`recoveryManagerPersonIds`に含まれる人物は`readOnly`を維持する。

交代由来と一意に確認でき、現在の`recoveryManagerPersonIds`に含まれない旧管理者だけを`removed`へ変更する。

`recoveryManagerPersonIds`に含まれず、交代または過去のFree適用由来とも一意に確認できない`readOnly`は、`restricted_read_only_origin_ambiguous`を記録して手動整理の対象にする。

Free判定は既存の課金policyと状態射影を再利用し、migration内へ別の状態判定を複製しない。

候補となる旧管理者は、同じグループとpersonにcanonicalな`organizationMembers`が一件だけあり、personがactiveで、personとmemberのuserが一致する場合に限る。

候補のpersonが現在の`freeManagerPersonId`または契約制限中の`recoveryManagerPersonIds`から参照されている場合は、同じtransactionで安全な代替を確定できない限り自動変更しない。

現在Freeであることを根拠にする場合は、`freeManagerPersonId`も同じグループのactiveなperson、一意なactive所属、整合するuserを持つことを確認する。

現在の有効権利が契約制限中以外なら、候補を`removed`へ変更した後も、同じグループに少なくとも一人の整合するactive管理者が残ることを確認する。

現在が契約制限中なら、候補を除いた後も、`recoveryManagerPersonIds`に含まれる整合したactiveまたは`readOnly`の復旧担当者が少なくとも一人残ることを確認する。

選択管理者、課金状態、人物対応、交代監査が欠損または曖昧な行は自動変更せず、既存のmigration conflictへ個人情報を含まないcodeで記録する。

Free以外かつ契約制限中ではない状態の`readOnly`で、`freeManagerPersonId`とは異なるが交代履歴を一意に確認できない行は、`former_manager_origin_ambiguous`として手動整理の対象にする。

契約制限中では、現在の`recoveryManagerPersonIds`を過去の交代履歴より優先し、復旧担当者を自動変更しない。

`convex/migrations/organizationMigrationHelpers.ts`の`sourceType`型へ`organizationMember`を追加する。

`organizationMigrationConflicts.sourceType`は既に`v.string()`なので、この追加にschema変更は不要である。

変更時は`organization.manager_role_removed`をmigration固有のcorrelationで一度だけ監査する。

対象人物に有効な`staffs`があれば`toState: "staffOnly"`、なければ`toState: "personOnly"`とする。

対象memberを発行元とするpending招待をrevokedにし、対象user向けの未送信の管理者通知と課金通知は、既存`cancelOrganizationRecipientBusinessNotifications`を`preserveStaffNotificationsForUser: true`で呼んでcancelする。

スタッフとしてのシフト通知とLINE通知はcancelしない。

`m013`は`users`、`organizationPeople`、`staffs`を更新しない。

`m014`は旧`shopMembers`を走査し、対応するcanonicalな`organizationMembers`が`removed`の管理者行だけを`isDeleted: true`へ変更する。

店舗の`organizationId`、同じグループとuserの`organizationPeople`、同じグループとpersonの`organizationMembers`が一意に対応するときだけ変更する。

対応が欠損または曖昧なら`shopMember`のmigration conflictを記録し、旧`shopMembers`を自動変更しない。

各migrationは所有する`CONFLICT_CODES`を`as const`で定義し、解消済みの行を再評価したときはそのmigrationが所有するcodeだけを解決済みにする。

他のmigrationが記録したconflictを変更しない。

`m014`も`staffs`を更新せず、店舗スタッフ所属を削除しない。

曖昧なconflictを安全に裁定するため、新規`internal.organization.migrations.resolveFormerManagerAccessConflict`を追加する。

このinternal mutationは`conflictId`、`organizationMemberId`、`expectedUpdatedAt`、`expectedBillingVersion`、`expectedBillingStateKind`、`decision`、固定enumの`reasonCode`、`requestId`だけを受け取る。

`decision`は`removeManagerAccess`または`keepAuthorizedReadOnly`とする。

`removeManagerAccess`では、conflictの所有code、未解決状態、memberの`readOnly`、グループ、person、user、現在の課金状態、契約制限中以外で残るactive管理者、契約制限中で残る復旧担当者を再確認する。

対象personが`freeManagerPersonId`または`recoveryManagerPersonIds`から参照中なら、副作用なしで拒否し、先に既存の選択操作で代替を確定させる。

条件を満たしたら、memberを`removed`にし、同じグループだけの旧`shopMembers`を削除済みにし、役割解除監査とowned conflict解決を同じtransactionで行う。

同じtransactionで対象memberが発行したpending招待をrevokedにし、同じ通知cancel helperと`preserveStaffNotificationsForUser: true`を使う。

`keepAuthorizedReadOnly`では、現在の認可理由とmemberの整合を再確認し、新しい`organization.manager_access_reviewed`監査を`toState: "authorizedReadOnly:{reasonCode}"`で記録してowned conflictを解決する。

維持裁定監査のcorrelationは`${conflictId}:manager-access-reviewed:${expectedUpdatedAt}:${expectedBillingVersion}`とし、`by_correlationId`で完全一致検索できる決定的キーにする。

監査の`fromState`にも課金state kindとversionを含める。

`m013`は、source IDとowned codeで取得したconflictが解決済みであり、そのconflict IDと現在のmember更新時刻に対応する維持裁定監査が一件だけある場合、`recordOrganizationMigrationConflict`を呼ばずにskipする。

memberの`updatedAt`、課金state kind、課金version、契約制限中のrecovery所属のいずれかが裁定後に変わった場合は、以前の維持裁定を流用せず、現在の状態を再評価する。

internal mutationをクライアントへ公開せず、自由記述の裁定理由と個人情報を引数または監査へ保存しない。

同じ`requestId`の再実行は監査と状態変更を重複させない。

両migrationはdry run、件数確認、実行、component status確認、残件検証の順で進める。

`convex/migrations/index.ts`へm013とm014だけを順番に実行する専用`runFormerManagerAccessCleanup` runnerを追加する。

conflict裁定後の再評価はこの専用runnerだけを`reset: true`で実行し、m001から始まる固定series全体をresetしない。

検証では、対象となる`readOnly`行と旧`shopMembers`の残件が0件であり、対象人物の`organizationPeople`と既存の`staffs`が変更されていないことを確認する。

### 8.3 リリース前監査

本番反映前に、グループごとに次を読み取りで確認する。

- activeな`organizationMembers`が5件を超えるグループ。
- active管理者と期限内pendingの`managerAddition`招待の合計が5を超えるグループ。
- purpose未設定の期限内pending招待。
- 同じ人物または同じメールへの重複したactive所属とpending招待。
- `migrationSourceShopId`があるのに、m012-owned conflictが未解決または課金状態が一意な`complimentary.business`ではないグループ。
- 有効な権利がFreeで、`freeManagerPersonId`以外に残る`readOnly`の管理者所属。
- Free以外かつ契約制限中ではない状態で`freeManagerPersonId`以外に残り、Free交代由来か一意に判定できない`readOnly`の管理者所属。
- 契約制限中で`recoveryManagerPersonIds`に含まれず、役割の由来を一意に判定できない`readOnly`の管理者所属。
- `former_manager_origin_ambiguous`を含む、今回のmigrationが所有する未解決conflict。
- canonicalな管理者所属が`removed`なのに`isDeleted: false`で残る旧`shopMembers`。
- canonicalな管理者所属が欠損または曖昧なまま`isDeleted: false`で残り、legacy fallbackが有効になり得る旧`shopMembers`。

purpose未設定は`managerAddition`として安全側に数える。

上限超過がある場合は、自動的に残す管理者を選ばない。

曖昧な`readOnly`は、監査履歴と現在の業務上の役割を確認し、internal裁定mutationで`removeManagerAccess`または`keepAuthorizedReadOnly`を確定する。

現行の公開`removeManagerRole`はactive所属だけを対象とするため、readOnly conflictの解消には使わない。

既存の管理者権限解除でactive管理者を整理し、既存の招待取消で余分なpending招待を解放する。

「反映直後から最大5枠」と「交代済み旧管理者が旧店舗を閲覧できない」を満たすため、監査、migration、整理の完了をリリースゲートにする。

### 8.4 適用順序

監査後から反映までの間に新しい招待が増える競合を避けるため、Backend guardとFrontendを段階リリースする。

1. Policy、見込み管理者数、予約移動、`targetPersonId`、`createForStaff`、Free交代時の管理者権限失効、Backend testを実装する。
2. 既存Frontendと互換なBackend guardを先に反映し、以後の6枠目と、旧管理者を`readOnly`へ残す新しい交代を停止する。
3. Backend guard反映後にm012の課金状態とowned conflictを確認し、未解決を0件にしてから本番監査とm013、m014のdry runを行う。
4. `m013`と`m014`を順番に実行し、交代済み旧管理者の管理権限だけを失効させる。
5. owned conflictを一件ずつ裁定し、m013とm014を再実行して未解決を0件にする。
6. 上限超過のactive所属とpending招待を整理する。
7. 最終監査で、全グループが5枠以下であり、今回のmigrationが所有する未解決conflictがなく、対象の旧管理者が交代したグループを閲覧できず、既存のスタッフ所属が残ることを確認する。
8. Dashboard DTO、スタッフ詳細UI、AuthGuard test、Story、仕様書を反映する。

Backend guardの先行反映前に監査結果だけを確定値として扱わない。

Frontend導線の公開は最終監査をリリースゲートとする。

## 9. 受け入れ条件

- active管理者が5名未満で枠が空いているとき、スタッフ詳細から招待確認へ進める。
- 招待メールは選択スタッフに対応する現在のグループ人物のメールアドレスへ送られる。
- 招待発行後に対象人物のメールが変わっても、古い招待から別人物を管理者化しない。
- メール変更後にスタッフ詳細から招待し直すと、古いtokenを失効させ、管理者枠を増やさず現在メールへ付け替える。
- 承認前は管理者権限を付与しない。
- active管理者と有効な追加招待の合計は、Free以外で5を超えない。
- Freeは有効管理者1名を維持し、既存スタッフとの交代だけを許可する。
- Free管理者交代の承認後、旧管理者はログインできるが、交代したグループの店舗選択、グループ設定、店舗ダッシュボード、店舗名を含む管理画面データを取得できない。
- Free管理者交代の承認後、旧管理者の`organizationPeople`と交代前から存在する`staffs`を維持し、`staffs.isDeleted`と`staffs.excludedFromShift`を変更しない。
- 交代前にシフト対象だった旧管理者は、交代後もシフト送信とスタッフ向け通知の宛先選定対象に残る。
- Free管理者交代を理由に、旧管理者を所属していなかった店舗へ自動でスタッフ登録しない。
- 旧管理者が別グループで持つ有効な管理者権限は失効しない。
- 交代済みの既存旧管理者にも同じ権限失効を適用し、スタッフ所属は維持する。
- Free適用で選ばれなかった旧管理者にも同じ権限失効を適用し、契約制限中の復旧担当者はreadOnlyのまま維持する。
- active管理者4名から異なる対象へ同時招待しても、5枠目を取得する招待は1件だけである。
- 招待の承認は予約をactive所属へ移し、管理者枠を二重に数えない。
- 招待の取消と期限切れで管理者枠を解放する。
- 既存スタッフを管理者にしても、グループ人物と利用人数を重複作成しない。
- 別店舗、別グループ、削除済み、移行未完了のスタッフIDでは、招待、監査、通知を作成しない。
- 閲覧中の本人以外の管理者兼スタッフにも、一覧と詳細で管理者状態を表示する。
- 同じ対象への有効な招待があるとき、スタッフ詳細は「招待中」を表示し、重複送信しない。
- 5枠到達時は、グループ上限と管理者権限解除または招待取消の解決方法を表示する。
- 招待token、7日TTL、単回利用、再送時失効、確認済みメール一致、Outbox、監査の既存契約を維持する。
- lint、型チェック、対象テスト、全テストが成功する。
- Codexのコードレビューで要修正指摘が残っていない。

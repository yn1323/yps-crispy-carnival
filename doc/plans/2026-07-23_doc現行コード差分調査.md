## 5. 店舗固定スタッフ登録リンクのSecurity Lens

この論点は、現時点で確定した脆弱性ではなく、実装と承認済みRulesの間にあるlifecycleの設計差分である。

現行実装と、別計画で決める目標契約を分ける。

| 観点 | 現行実装で確認できたこと | 別計画で決めること |
|---|---|---|
| ActorとAsset | managerが`managerMutation`で固定リンクを作成、再表示し、未認証者が参加申請する | 固定QRを維持するか、誰が失効と再発行を行うか |
| Trust boundary | manager APIと、tokenをcredentialとして受ける匿名HTTP境界に分かれる | 漏れたQR、古いtoken、申請spamへの許容範囲 |
| Server-side enforcement | `revokedAt`、店舗と課金状態、Origin、body上限、Turnstile、多軸rate limit、pending上限、generic responseを確認済み | managerのrevokeとrotate、旧tokenの即時拒否を追加するか |
| Lifecycle | manager向けのrevokeとrotate API、明示的なTTLは見つからず、生tokenは再表示のため保存される | 長期利用理由、raw保持範囲、監査、rotationの原子性 |
| Regression | 現行のHTTP防御と申請制限には近いFunction Testがある | 決定後に、単一APIはFunction Test、複数API後の旧token失効だけはScenario Testを主担当にする |

rotate、revoke、schema、CI、テストの実装は親計画へ含めない。

採用するlifecycleが決まった後、Security Lens、migration要否、回帰テストを持つ別計画を作る。

## 6. 生のConvex public functionに関する設計上の位置付け

調査時点のraw public functionは、staff capability、法務、LINE、Stripeなど、意図した公開境界に概ね収まっている。

静的検査が見つからないこと自体を、直ちに公開中の脆弱性とは扱わない。

不足しているのは、将来allowlist外のpublic functionが増えたときに、Rule違反を自動で検知する強制機構である。

検査を追加する場合は、現在のpublic surfaceを棚卸しし、認証wrapper、匿名capability、provider callbackを区別したallowlistを正本にする。

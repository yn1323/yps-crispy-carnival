# LINE連携トークン使い回しの実装計画

作成日: 2026-10-31  
状態: Active（repository実装済み。CI・自動レビューと実環境への反映待ち）

スタッフ登録時に届くLINE登録メールとシフト募集メールのLINE連携リンクを、同じトークンにそろえる。  
メール経由の発行だけ、条件に合う既存トークンを使い回し、管理者のQR・URL発行は従来どおり毎回作り直す。

## 1. 問題

スタッフ追加と登録承認では、LINE登録メール（`line.actions.sendInviteEmail`）と募集メール（`notification.actions.sendOpenRecruitmentNotificationEmailsForStaff`）を、どちらも`runAfter(0)`で並列にスケジュールする。  
両方のメールが`createLinkTokenInternal`で連携トークンを発行し、`issueLinkToken`は発行時に同じ組織人物の未使用トークンをすべて失効させる。

そのため、後から発行された方のリンクだけが有効になる。  
実行順は保証されないので、どちらのメールのリンクが有効かは実質ランダムである。  
失効した方のリンクを押すと、callback画面に「リンクが無効です」と表示される。

## 2. 方針

| 発行経路 | 変更後の挙動 |
|---|---|
| メール経由（`createLinkTokenInternal`） | 条件に合う有効トークンがあれば使い回す。なければ従来どおり旧トークンを失効させて新しく発行する |
| 管理者のQR・URL発行（`generateLinkToken`） | 従来どおり、毎回旧トークンを失効させて新しく発行する |

使い回すトークンは、次の条件をすべて満たす最新の一件とする。

- 未使用で、失効していない。
- `staffId`、`shopId`、`organizationId`、`lineLinkGenerationAtIssue`が、発行時の現在scopeと一致する。
- 有効期限が48時間以上残っている。

有効期限は延長しない。  
残りが48時間を切ったあとのメール送信では、新しいトークンを発行して旧トークンを失効させる。  
発行から24時間以内に送ったメールは同じリンクになり、どのメールのリンクも最低48時間は有効である。

複数トークンを同時に有効にする案も比較した。  
登録時の2通は同時に届くため使い回しで十分であり、有効トークンを人物ごとに1件に保てる使い回しを採用した。

シフト連絡先メールを変更したときは、同じ組織人物の未使用トークンをすべて失効させる。  
従来は変更後の宛先へ送るメールで新しいトークンが発行され、変更前の宛先に届いたリンクが結果的に失効していた。  
使い回しを入れるとこの失効が起きず、誤った宛先に届いたリンクが変更後の宛先にも送られて有効なまま残るため、メール変更時に明示的に失効させる。

schemaの変更、migration、UIの変更は行わない。

## 3. 実装

1. `convex/constants.ts`に`LINE_LINK_TOKEN_REUSE_MIN_REMAINING_MS`（48時間）を追加する。
2. `convex/line/mutations.ts`の`issueLinkToken`に`mode: "rotate" | "reuse"`を追加する。
3. `createLinkTokenInternal`は`"reuse"`、`generateLinkToken`は`"rotate"`で呼ぶ。
4. `"reuse"`で使い回す場合も、使い回すトークン以外の有効トークンは失効させ、有効トークンが人物ごとに1件という不変条件を保つ。
5. `convex/notificationOutbox/mutations.ts`の「呼ぶたびに新しいトークンを発行」というコメントを更新する。
6. `convex/organization/personProfile.ts`の`updateOrganizationPersonProfile`で、メールアドレスが変わった場合に`revokeOrganizationPersonLineTokens`を呼ぶ。

並列に発行しても、両方のmutationが同じ`by_organizationPersonId_and_expiresAt`の範囲を読むため、Convexの楽観的並行制御で後発のmutationが再実行され、先に作られたトークンを使い回す。

使い回しの対象は、`createLinkTokenInternal`を通るすべてのメールである。

- `sendInviteEmail`：スタッフ追加、登録承認、管理者の連携依頼、失敗時の再送、初回セットアップ
- `buildLineCtaForStaff`：募集、確定、リマインドのメール末尾CTA

## 4. Security Lens

- Actor：スタッフ、管理者、メールの転送先にいる第三者
- Asset：LINE連携トークン（bearer token、72時間有効、1回だけ使える）
- Trust boundary：未認証のLINE OAuth callbackから呼ばれる`validateLinkToken`
- Abuse case：流出した古いメールのリンクで第三者が連携する。誤った宛先に届いたリンクが、宛先を直したあとのメールで使い回される。別店舗スタッフのトークンが混ざる。管理者の再発行後に旧トークンが残る。
- Server-side enforcement：使い回しの条件でscopeの全項目一致を確認する。シフト連絡先メールの変更時に旧トークンを失効させる。callback時の組織、人物、連携世代の再検証は変更しない。
- Rate limit / idempotency：既存の`lineInviteShort`とredeemのrate limitを維持する。並列発行はmutationの直列化で同じトークンへ収束する。
- Lifecycle / recovery：有効トークンは人物ごとに1件のままとする。連携時、管理者の再発行時、連携世代の変更時の失効は維持する。期限は延長しない。
- Logs / PII：変更しない。
- 補足：使い回しはraw tokenの再表示を前提にする。現行もraw tokenを保存しているため、悪化はしない。

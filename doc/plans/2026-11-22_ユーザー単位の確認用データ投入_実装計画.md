# ユーザー単位の確認用データ投入（/seed）実装計画

> 文書種別: plan
>
> 作成日: 2026-11-22
>
> 状態: 依頼者が推奨案で承認し、実装した。ローカルで通しの実行を確かめた。8章の`/seed-max`もローカルで通しの実行を確かめ、画面での確認が残る

## 1. 目的

ローカル、PR環境（Convex preview）、developで、画面から作ったユーザーに、シフト作成の確認に使うデータをまとめて入れる。  
これまでは一時的なmutationを書いて実行し、消していた。  PR環境はプッシュのたびにデータが消えるため、同じ作業を何度も繰り返していた。

本番は対象外である。

## 2. 決めたこと

| 項目 | 決定 |
|---|---|
| 起動 | 手動専用のSkill `/seed`。`disable-model-invocation: true`にする |
| 実行先 | 毎回聞く。ローカル、PR環境（PR番号）、developから選ぶ。本番は選べない |
| ユーザー | 実行先のユーザーが1人ならその人、複数なら一覧から選んでもらう |
| 既存データ | 選んだユーザーが唯一の有効な管理者である組織を、画面からの組織削除と同じ処理で論理削除する。ユーザーの行（ログインとのひも付け）は残す。ほかの管理者がいる組織は消さずに知らせる |
| 削除の前の確認 | 消す組織の名前と、消さない組織を出して、もう一度確認を取る |
| 入れるデータ | 新しいTrial組織に、3つの集め方の店舗とそのデータを網羅的に入れる（4章） |
| 日付 | 実行した日（JST）を基準にする |
| 乱数 | 毎回変える。使った値を表示する |
| 関数の置き場 | リポジトリに置き、コードと一緒にデプロイする。一時ファイルを`--push`する方法は、developへ未マージのコードを上書きするため使わない |

## 3. 有効にする条件

`doc/manual/debug-mode.md`の運用に合わせ、`DEBUG_MODE=true`の実行先だけで動かす。  新しい環境変数は作らない。

- 各internal functionの先頭で`DEBUG_MODE=true`を確かめる。
- `CONVEX_CLOUD_URL`が本番（`proficient-kookabura-834`）なら、`DEBUG_MODE`にかかわらず拒否する。
- PR環境には`DEBUG_MODE`がないため、Skillが依頼者に確かめてから`--deployment preview/pr-<番号>-deploy`へ設定する。
- `DEBUG_NOTIFICATION_DELIVERY_MODE`が`dry-run`でない実行先では、Skillが知らせて続けるかを聞く。

## 4. 入れるデータ

| 対象 | 内容 |
|---|---|
| 組織 | Trial。組織名は「シフトリ確認用グループ」 |
| 店舗 | 時間指定（6:00〜24:00）、日付選択（木曜定休、休憩の決まりあり）、パターン選択（早番・遅番・夜番、月火定休、休憩の決まりあり） |
| ポジション | 時間指定はホール・キッチン、日付選択は販売・製造、パターン選択はホール・キッチン・ドリンク |
| スタッフ | 20人（`devstaffNN@example.com`）と管理者本人を全店舗に入れる。担当外と見習いはランダム。各店舗で1人をシフト対象外にする |
| 必要人数 | 平日、土日、祝日のテンプレート。人数はランダム。1日だけ別のテンプレートを当てる |
| 募集 | 店舗ごとに、確定済み（前の期間）、確定後に変更あり（今の期間）、締め切り後で下書きあり（次の期間）、募集中（その次の期間） |
| 希望 | メモを先に決め、その日の希望をメモに合わせる。未提出の人を残す |
| 割り当て | 確定済みと下書きの募集に、希望に沿った割り当てを入れる。確定済みには確定通知の記録（snapshot）と確定時のポジション・必要人数を入れる |
| 登録申請 | 日付選択の店舗に、承認待ちの申請を1件入れる |

LINE連携、通知の失敗、決済の記録は入れない。

## 6. Security Lens

- **Actor**：Convex CLIでその実行先へログイン済みの開発者だけ。internal functionなので、ブラウザやスタッフからは呼べない。
- **Asset**：実行先の組織データ、管理者ユーザーの名前とメールアドレス。
- **Trust boundary**：CLIからinternal functionへ渡す`userId`。サーバーで存在、削除状態、所属を確かめてから使う。
- **Abuse case**：本番での実行、別のユーザーの組織の削除、実在のメールアドレスへの通知、途中で失敗した状態の放置、組織の作成上限への到達。
- **Server-side enforcement**：各functionで`DEBUG_MODE`と本番URLを確かめる。削除は唯一の管理者である組織に限り、既存の削除条件（課金、ほかの管理者、店舗の削除中）を通す。新しい組織は削除済みを数えない作成上限の範囲で作る。
- **Rate limit / idempotency**：手動の開発操作なので回数制限は付けない。削除は既存のcorrelationIdで重ねて受け付けない。投入は1回のmutationで全件を書き、失敗すれば何も残らない。
- **Lifecycle / recovery**：削除した組織の後片付けは既存のcleanup jobに任せる。投入が失敗したら、削除済みのまま再実行できる。
- **Logs / PII**：functionはログを出さない。ユーザーの一覧はCLIを実行した開発者のターミナルにだけ出す。スタッフのメールは`@example.com`にし、通知を予約しない。
- **Regression test**：`DEBUG_MODE`がない、本番URLのときに拒否してDBを変えないこと。ほかのユーザーと共同管理の組織を消さないこと。投入後に予約された処理が0件で、スタッフのメールがすべて`@example.com`であること。

## 8. 上限の確認用データ（/seed-max）

2026-11-23に、依頼者が推奨案で承認して追加した。  
`/seed`と同じ流れで、画面で登録できる上限の数と長さのデータを入れる。  入れる中身の一覧は`doc/manual/user-seed.md`を正本とする。

### 決めたこと

| 項目 | 決定 |
|---|---|
| 起動 | 手動専用のSkill `/seed-max`。`/seed`の手順を読み、投入と報告だけを置き換える |
| 組織 | 作れる上限の3つを作る。1つ目だけを上限いっぱいにし、残りは`/seed`の1店舗ぶんにする |
| 店舗 | 上限いっぱいの組織に5件。3つの集め方を割り振り、全員を5店舗すべてに所属させる |
| 人数 | 組織全体で50名。シフト表が読める200人は、登録できる人数ではないため使わない |
| 管理者 | 本人と、招待中の4件で5名にする。有効な管理者を増やすと、次の入れ直しで組織を消せなくなるため |
| 募集 | 店舗ごとに4つの状態を作り、どれも31日にする |
| 書き方 | 組織を作るmutationのあと、募集ごとのmutationを20回、actionから順に呼ぶ |

1つの募集では、希望、メモ、割り当てを合わせて約4,700件を書く。  1店舗の4つの募集を1回のmutationで書くと、Convexの上限（1回に16,000件）を超える。  
このため、募集ごとに分けた。  途中で失敗するとそこまでの分が残るため、やり直しは「消して入れ直す」にする。

Convexの上限は公式ドキュメントの[Limits](https://docs.convex.dev/production/state/limits)で確かめた（1件を全文読んだ）。

### Security Lens

- **Actor**：`/seed`と同じ。Convex CLIでその実行先へログイン済みの開発者だけ。
- **Asset**：実行先の組織データ、管理者の招待。
- **Trust boundary**：CLIから渡す`userId`と、募集を入れるmutationへ渡す`shopId`。
- **Abuse case**：本番での実行、別のユーザーや別の組織の店舗への大量の書き込み、招待を使った管理者権限の取得、同じ募集の二重投入。
- **Server-side enforcement**：追加したactionとmutationのすべてで、`DEBUG_MODE`と本番URLを確かめる。募集を入れるmutationは、選んだユーザーが作った上限いっぱいの組織の店舗にだけ書く。同じ期間の募集がすでにある店舗には書かない。
- **招待**：tokenの照合値には実際のtokenからは作れない値を入れる。この招待から管理者になることはできない。宛先は`@example.com`で、通知と期限切れの処理は予約しない。隣の開発用網羅シードは招待を作らないが、ここでは管理者の上限の表示を確かめるために、使えない招待だけを作る。
- **Lifecycle / recovery**：招待は7日で期限切れの扱いになる。組織を消すと、既存のcleanup jobが招待を失効させる。
- **Regression test**：`DEBUG_MODE`がない、本番URLのときに、actionと2つのmutationが拒否してDBを変えないこと。他人の店舗、自分の別の組織の店舗、入れ済みの募集を拒否すること。上限の数まで組織を作れないときに1つも作らないこと。招待の照合値が使えない形であること。予約された処理が0件で、メールアドレスがすべて`@example.com`であること。

## 9. ユーザーがいない実行先（2026-11-24）

PR環境はプッシュのたびにpreviewが作り直され、データと一緒にユーザーの行も消える。  そのたびに画面でログインと初期設定をやり直す手間をなくすため、ユーザーの行を作る処理を足した。

### 比べた案

| 案 | 決定 |
|---|---|
| previewを作り直さず使い回す（`--preview-name`） | 見送り。古いデータと新しいコードの不整合が出やすいと、依頼者が判断した |
| プッシュのたびにCIで入れる | 見送り。依頼者がローカルからの実行を選んだ |
| ローカルから`/seed`で入れ、ユーザーがいなければ作る | 採用 |

### 決めたこと

| 項目 | 決定 |
|---|---|
| 利用者の指定 | 開発用網羅シードと同じ環境変数`DEBUG_SEED_PRIMARY_AUTH_TOKEN_IDENTIFIER`を使う。引数では受け取らない。Clerk User IDをコマンド履歴へ残さない決まり（`doc/manual/development-seed.md`）に合わせるためである |
| PR環境への設定 | Convexのプロジェクトの既定の環境変数（`npx convex env default set ... --type preview`）へ、依頼者が1回入れる。Skillは値を受け取らず、設定もしない |
| 作る行 | `users`の1行だけ。名前は「確認用ユーザー」、メールアドレスは`@example.com`にする |
| 同意の記録 | 作らない。本人の操作ではないためである。同意の記録がない管理者には、ログイン後のホームで同意の確認が出るため、本人がそこで同意する |
| すでに行がある場合 | 新しく作らず、その行を返す。削除済みか、アカウント削除を受け付けた行は拒否する |

### Security Lens

- Actor: Convex CLIで実行先へログインした開発者。関数はinternal functionで、ブラウザからは呼べない。
- Asset: ログインの識別子とアプリ内のユーザーの対応。そのユーザーが管理者として持つ確認用データ。Clerk利用者の識別子。
- Trust boundary: CLIからinternal functionへの呼び出し。実行先の環境変数。
- Abuse case: Productionで実行して、利用者に管理者の行を作る。引数で別の利用者の識別子を渡して、取り違えた利用者を管理者にする。別のClerk instanceの識別子で行を作る。削除済みのユーザーを作り直す。識別子がコマンド履歴や出力に残る。
- Server-side enforcement: `assertUserSeedEnabled`でProductionを拒否し、`DEBUG_MODE=true`を求める。識別子は環境変数だけから読み、形と、実行先の`CLERK_JWT_ISSUER_DOMAIN`との一致を確かめる。同じ識別子の行が削除済みなら拒否する。
- Rate limit / idempotency: 同じ識別子の行があれば作らないため、何度呼んでも1行である。
- Lifecycle / recovery: PR環境の行は、previewの作り直しで消える。ローカルとdevelopの行は残り、画面で作ったユーザーと同じに扱う。
- Logs / PII: 返り値は`userId`と、作ったかどうかだけである。識別子とメールアドレスを返さず、ログにも書かない。
- Regression test: `convex/userSeed/mutations.test.ts`の`ensureSeedUser`。`DEBUG_MODE`なし、Production、識別子の未設定・不正・issuerの不一致、削除済みの行で、ユーザーを作らないことを確かめる。

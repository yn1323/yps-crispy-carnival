# ユーザー単位の確認用データ

> 文書種別: manual
>
> 対象: local、PR環境（Convex preview）、Developmentのdeployment。Productionは対象外

管理者ユーザー1人に、シフト作成の確認に使うデータをまとめて入れます。  入れ先は画面で作ったユーザーです。  ユーザーがまだいない実行先では、[環境変数で指定した利用者のユーザーを作ってから入れます](#画面でユーザーを作らずに入れる)。  
[開発用網羅シード](development-seed.md)と違い、全テーブルは空にしません。  選んだユーザーの組織だけを消して、入れ直します。

## 使い方

Claude Codeで`/seed`と入力します。  手動専用のSkillで、ほかの依頼から自動では動きません。

1. 実行先（ローカル、PR環境、develop）を選びます。  PR環境はPR番号も確かめます。
2. 実行先の`DEBUG_MODE`が`true`でなければ、設定してよいかを聞かれます。
3. ユーザーが2人以上いる実行先では、入れる先のユーザーを選びます。
4. 消す組織と残す組織が示されます。  了承すると、消してから入れ直します。

ユーザーが1人もいない実行先では、3の代わりに、環境変数で指定した利用者のユーザーを作ります。  指定がなければ、設定の方法を示して止まります。

## 画面でユーザーを作らずに入れる

PR環境は、プッシュでpreviewが作り直されると、データと一緒にユーザーも消えます。  そのたびに画面でログインと初期設定をやり直さなくて済むよう、実行先の環境変数でClerk利用者を指定しておけます。

| 環境変数 | 値 |
|---|---|
| `DEBUG_SEED_PRIMARY_AUTH_TOKEN_IDENTIFIER` | ログインに使うClerk利用者の`identity.tokenIdentifier`（ClerkのissuerのURLと`user_`で始まるIDを、縦棒でつないだ値） |

[開発用網羅シード](development-seed.md)と同じ環境変数です。  値はコマンドの引数に書かず、対話で入力します。

```bash
# これから作られるPR環境のすべてに設定する（1回で済む）
npx convex env default set DEBUG_SEED_PRIMARY_AUTH_TOKEN_IDENTIFIER --type preview

# いまある実行先だけに設定する
npx convex env set --deployment TARGET_DEPLOYMENT_NAME DEBUG_SEED_PRIMARY_AUTH_TOKEN_IDENTIFIER
```

1つ目は、Convexのプロジェクトの「既定の環境変数」に入れる方法です。  設定したあとに作られるPR環境へ、自動で入ります。  すでにあるPR環境には入りません。

設定してある実行先で`/seed`か`/seed-max`を実行すると、次のユーザーを作ってからデータを入れます。

| 項目 | 値 |
|---|---|
| 名前 | 確認用ユーザー |
| メールアドレス | `user-seed-manager@example.com` |
| 利用規約などへの同意の記録 | 作りません。本人の操作ではないためです |

指定したClerk利用者でログインすると、初期設定を通らずに、入れたデータが出ます。  同意の記録がないため、ホームで利用規約などへの同意の確認が出ます。

同じ利用者のユーザーがすでにある実行先では、新しく作らず、そのユーザーへ入れます。  名前とメールアドレスは変えません。

次の場合は、ユーザーを作らずに止まります。

- 環境変数が設定されていない。
- 値が、ClerkのissuerのURLと`user_`で始まるIDを縦棒でつないだ形でない。
- 値のissuerが、実行先の`CLERK_JWT_ISSUER_DOMAIN`と合わない。
- その利用者のユーザーが、削除済みか、アカウント削除を受け付けている。

Clerk User IDと`identity.tokenIdentifier`の値は、Git、コマンド履歴、Issue、ログ、スクリーンショット、共有文書へ残しません。

## 消すもの

選んだユーザーが唯一の有効な管理者である組織を、画面からの組織削除と同じ処理で論理削除します。  権限や連絡手段の後片付けは、そのあと自動で進みます。

ユーザーの行（ログインとのひも付け）は残します。  ほかの管理者がいる組織、有料契約の組織、店舗の削除中の組織は消さずに残し、理由を示します。

ほかの管理者が[確認用の管理者](#管理者とシフトの対象から外す人)だけの組織は、その管理者の権限を外してから消します。  画面で招待した管理者が1人でもいる組織は、消さずに残します。

## 入れるもの

Trialの組織「シフトリ確認用グループ」を作り、次の3店舗を入れます。

| 店舗 | 集め方 | ポジション | 定休日 |
|---|---|---|---|
| 時間指定 | 6:00〜24:00 | ホール、キッチン | なし |
| 日付選択 | 日付だけ | 販売、製造 | 木 |
| パターン選択 | 早番、遅番、夜番 | ホール、キッチン、ドリンク | 月、火 |

各店舗には、スタッフ20人と管理者4人が入ります。  熟練度（担当外、見習い）はランダムです。  
必要人数のテンプレートは平日、土日、祝日の3種類で、募集中の期間の1日だけ別のテンプレートを当てます。

### 管理者とシフトの対象から外す人

管理者は本人と、`/seed`が入れる確認用の管理者3人（石川 誠、藤井 香織、岡田 修）です。  4人とも3店舗すべてに所属します。

シフトの対象から外す人は、店舗ごとに次のとおりです。

| 店舗 | 外す管理者 | 外すスタッフ |
|---|---|---|
| 時間指定 | 藤井 香織 | ランダムに3人 |
| 日付選択 | 本人、岡田 修 | ランダムに3人 |
| パターン選択 | 石川 誠 | ランダムに3人 |

シフトに入る確認用の管理者は、スタッフと同じように希望を出し、割り当てを受けます。  本人は希望を出しません。

確認用の管理者のユーザーはログインできない識別子で作ります。  入れ直すときは同じユーザーを使うため、ユーザーは増えません。  `/seed`で入れ先を選ぶ一覧にも出ません。

### LINE連携

スタッフ20人からランダムに選んだ8人を、LINE連携済みにします。  連携は1人に1つで、3店舗のどこでも連携済みと表示されます。  管理者は連携しません。

LINEの利用者のIDには、LINEが発行する形と違う値を入れます。  このIDを宛先にした送信は、だれにも届きません。

### 募集

募集は実行した日を基準に4つ入れます。

| 募集 | 期間 | 状態 |
|---|---|---|
| 確定済み | 10日前〜4日前 | 確定して通知済み |
| 確定後に変更あり | 3日前〜3日後 | 確定して通知済み。2人は通知のあとで勤務が増えている |
| 下書きあり | 4日後〜10日後 | 締め切り後。割り当ての下書きを保存済み |
| 募集中 | 11日後〜24日後 | 受付中。4〜8人が未提出 |

希望にはメモを添えます。  メモを先に決めて、その日の希望をメモに合わせるため、「閉店作業まで入れます」の日の希望は閉店までになります。  
日付選択の店舗には、承認待ちの登録申請が1件入ります。

### 通知の記録

実際には送らずに、送ったことにした通知の記録を入れます。  スタッフ詳細の通知履歴で、いつ、どの連絡手段で、何が届いたかを確かめられます。

| 通知 | 届いた時刻 | 届く人 |
|---|---|---|
| シフトリの使い方のご案内 | 30日前 | 管理者ではないスタッフの全員 |
| シフト通知をLINEで受け取れます | 30日前 | 管理者ではないスタッフの全員 |
| 希望シフトの提出のお願い（募集の通知） | 提出期限の7日前の10:00 | シフトの対象の全員 |
| 提出の催促 | 提出期限の前日の17:00 | その募集に提出していない人 |
| シフト確定のお知らせ | 確定した時刻 | 確定済みの募集で、勤務が入った人 |

募集中の募集は、催促の時刻がまだ来ていないため、催促の記録を入れません。

LINE連携済みの8人は3日前から25日前のどこかで連携したことにし、連携より前の通知をメール、あとの通知をLINEで届いた記録にします。  連携した日は人ごとに違うため、メールからLINEへ切り替わる時期も人ごとに違います。  連携していない人と確認用の管理者は、すべてメールです。

メールは「配信済み」、LINEは「送信済み」の状態で入れます。  LINEは配信の結果を受け取れないため、本来の送信でも「送信済み」までです。  
管理者本人への通知の記録は入れません。  届かなかった通知と、決済の記録も入れません。

宛先のメールアドレス、LINEの利用者のID、本文は記録に入れません。  保存期間を過ぎて本文を消した通知と同じ形です。

## 上限の確認用データ

Claude Codeで`/seed-max`と入力します。  実行先とユーザーを選び、消す組織を確かめるまでは、`/seed`と同じ流れです。  
入れる中身だけが違い、画面で登録できる上限の数と長さで作ります。  長い名前や件数の多い画面で、表示の崩れや重さを確かめるときに使います。

### 作る組織

自分で作れる上限の3つを作ります。  投入のあとは組織をこれ以上作れない状態になります。

| 組織 | 中身 |
|---|---|
| シフトリ上限確認用グループ（80文字の名前） | 上限いっぱいの組織。次の節のとおり |
| シフトリ確認用グループ（2つ目） | `/seed`の「時間指定」の店舗1つ。スタッフ10人 |
| シフトリ確認用グループ（3つ目） | `/seed`の「パターン選択」の店舗1つ。スタッフ10人 |

2つ目と3つ目の組織は、管理者が本人だけで、シフトの対象から外すスタッフは1人です。  LINE連携は入れません。

消さずに残した組織のために3つを作れないときは、何も作らずに止まります。

### 上限いっぱいの組織

| 対象 | 入れる数と長さ |
|---|---|
| 組織名、店舗名、スタッフ名 | 80文字 |
| 店舗 | 5件 |
| 利用人数 | 50名（管理者本人とスタッフ49名）。全員が5店舗すべてに所属します |
| 管理者 | 5名（本人と、招待中の4名） |
| ポジション | 店舗ごとに10個。名前は20文字 |
| 必要人数のテンプレート | 店舗ごとに10個。名前は20文字。必要人数は1つのポジションに50人 |
| パターン選択のパターン | 4つ。名前は30文字 |
| 時間指定の受付時間 | 0:00〜翌12:00（選べるいちばん長い時間） |
| 募集の期間 | 31日 |
| 希望 | 1人が1つの募集に31件（営業する日のすべて） |
| メモ | 営業する日のすべてに100文字 |
| 休憩 | 「時間指定」の店舗で、受付時間いっぱいの勤務に20件 |
| 承認待ちの登録申請 | 「日付選択」の店舗に20件 |

5つの店舗は次のとおりです。  前の3つは定休日がなく、全員がシフトの対象です。

| 店舗 | 集め方 | 定休日 | シフトの対象から外す人 |
|---|---|---|---|
| 時間指定 | 0:00〜翌12:00 | なし | なし |
| 日付選択 | 日付だけ | なし | なし |
| パターン選択 | 早番、遅番、夜番、深夜番 | なし | なし |
| 時間指定（定休日あり） | 6:00〜24:00 | 水 | 1人 |
| パターン選択（定休日あり） | 早番、遅番、夜番、深夜番 | 月、火 | 1人 |

募集は店舗ごとに4つ入れます。  どの募集も、管理者本人のほかは全員が提出済みです。

| 募集 | 期間 | 状態 |
|---|---|---|
| 確定済み | 46日前〜16日前 | 確定して通知済み |
| 確定後に変更あり | 15日前〜15日後 | 確定して通知済み。2人は通知のあとで勤務が増えている |
| 下書きあり | 16日後〜46日後 | 締め切り後。すべての希望を割り当てた下書きを保存済み |
| 募集中 | 47日後〜77日後 | 受付中 |

メモは`/seed`と同じ短いメモを先に決め、その日の希望をメモに合わせてから、100文字になるまで文を足します。  
5人に1人は2日を休みにするため、その人の希望は29件です。

### 上限に届かないもの

- シフト表は1つの募集の希望と割り当てを2,000件ずつまで読めます。  50名が31日ぶんの希望を出しても約1,500件のため、2,000件には届きません。
- メールアドレスは`@`より前を64文字にしています。  `@example.com`のままにするため、全体の上限の254文字には届きません。
- 休憩の決まり（何分以上の勤務に何分）は、通常の値です。

### 気をつけること

- 招待中の4件は7日たつと期限切れの扱いになり、管理者の数に数えられなくなります。  この招待から管理者になることはできません。
- 投入では、組織を作ったあと、上限いっぱいの組織の募集を1つずつ、20回に分けて書きます。  途中で止まると、そこまでの分が残ります。  そのときはもう一度`/seed-max`を実行し、消してから入れ直します。

## 通知

投入では通知を予約しません。  [通知の記録](#通知の記録)も送ったことにした記録を書くだけで、メールもLINEも送りません。  スタッフのメールアドレスはすべて`@example.com`です。

ただし、入れたデータを画面で操作すると、管理者本人のメールアドレスへ通知が届く場合があります。  届かないようにするには、実行先の`DEBUG_NOTIFICATION_DELIVERY_MODE`を`dry-run`にします（[デバッグ環境変数の運用](debug-mode.md)）。

確認用の管理者のメールアドレスも`@example.com`です。  LINE連携済みのスタッフへLINEで送っても、LINEの利用者のIDが実在しないため、だれにも届きません。

## PR環境

PR環境は、プッシュでpreviewが作り直されるとデータが消えます。  プレビューを作るCIが、作るたびに`/seed`と同じデータを入れます（[CI/CDの運用](ci-cd.md#pull-request)）。  `develop`とProductionへのdeployでは入れません。

CIが入れるには、[環境変数で利用者を指定しておく](#画面でユーザーを作らずに入れる)必要があります。  PR環境すべてに効く既定の環境変数（`npx convex env default set ... --type preview`）で設定します。  設定がないと、CIは警告を出して投入を飛ばします。

CIのあとで入れ直したいときは、`/seed`も使えます。  `DEBUG_MODE`はCIが設定済みです。

## 安全の仕組み

- 関数はinternal functionで、ブラウザからは呼べません。  Convex CLIで実行先へログインした開発者だけが実行できます。
- `DEBUG_MODE=true`の実行先でだけ動きます。
- Productionのdeploymentでは、`DEBUG_MODE`にかかわらず拒否します。
- ユーザーを作る処理は、利用者の識別子を引数で受け取りません。  実行先の環境変数の値だけを使い、結果にも識別子を含めません。

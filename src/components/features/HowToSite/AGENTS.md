# HowToSite 編集ガイド

このディレクトリは、シフトリを利用中の管理者やスタッフが、疑問や問題を短時間で解消して作業へ戻るためのヘルプです。
シフトリの全機能を説明するマニュアルや、検索流入を目的としたSEO記事にはしません。

## ヘルプの目的

記事では、必要に応じて次の疑問へ答えます。

- やりたい操作をどこから、どう進めるか
- 操作後に何が起きるか
- 管理者とスタッフのどちらに何が表示されるか
- 誰に、いつ、LINEとメールのどちらで通知されるか
- 操作できない原因と、作業を再開する方法
- シフトリ固有のルールや、UIだけでは分からない挙動

記事数や文字数を増やすことは目的にしません。
読者が答えを得たあと、迷わず元の作業へ戻れることを完了条件にします。

## SEO記事との役割分担

`/articles` のSEO記事は、シフトリを利用していない人も対象に、一般的な課題、背景、選択肢、運用の知識を説明します。

`/howto` のヘルプは、主にシフトリを利用中の人が抱えている現在の疑問へ直接答えます。
一般論や背景を広げず、検索流入のために文章を長くしません。

## 記事候補の判断

新しい候補は、本文を書く前に次のいずれかへ分類します。

### A：公開を優先する

- 分からないとシフト運用や作業が止まる
- 通知、確定、修正、削除など影響の大きい操作に関係する
- UIだけでは操作結果や対象者が分からない
- 管理者またはスタッフが強い不安を感じやすい
- 1回の誤操作でも影響が大きい

### B：問い合わせを見て追加する

- 現時点では問題が確認されていない
- 利用頻度が低く、迷う人が限られる
- 問い合わせが発生した時点で、既存記事への追記か新規記事かを判断できる

### C：UI改善で対応する

- 多くの人が同じ画面、同じ入力、同じボタンで迷う
- 記事を読まないと操作できない
- ラベル、補足、状態表示、エラー、導線を直せば画面内で解決できる

### D：説明しない

- UIだけで十分に理解できる
- 失敗しても簡単に元へ戻せる
- ほかの記事の一部として短く説明できる
- 記事化してもユーザーの判断や行動が変わらない

候補が増えたときは、先にCとDを除きます。
機能を網羅するためだけにAやBへ分類してはいけません。

## 優先して調査する疑問

次の疑問は、作業停止、不安、問い合わせにつながりやすいため優先します。

- LINEやメールが届かない
- いつ、誰に、どの通知が送られるか
- 自動催促が送られる条件
- 確定後に変更すると何が起きるか
- 削除すると何が消え、何が残るか
- 警告とエラーは何が違うか
- 管理者の操作後、スタッフ側に何が表示されるか
- 提出用リンクを開けない、または提出できない
- シフトを確定、修正、再送できない
- スタッフ登録とLINE連携がどの状態にあるか

問い合わせが1回でも運用停止や大きな誤操作につながった場合は、発生回数にかかわらず記事化を検討します。

## 記事化しない内容

次の内容は追加しません。

- 画面内の説明をそのまま繰り返す内容
- ボタンや入力欄を上から順に読み上げるだけの手順
- UIを見れば迷わない単純操作
- 一般的なシフト管理の知識や長い背景説明
- 現時点で存在しない機能、画面、運用
- 確認できていない仕様の推測

同じ質問が増えた場合も、記事を増やす前にUI側の改善で解決すべき問題か確認します。

## 1記事で扱う範囲

1記事は、ユーザーの1つの目的または困りごとを扱います。

よい単位:

- スタッフを追加する
- 未提出のスタッフに催促する
- 自動催促はいつ送られますか
- 確定したシフトを修正する
- LINE通知が届かないとき
- スタッフを削除するとどうなりますか

分けすぎた単位:

- 追加ボタンを押す
- 名前を入力する
- メールアドレスを入力する
- 保存ボタンを押す

上記の操作は「スタッフを追加する」の1記事にまとめます。
記事が長くなった場合は、文章を削る前に複数の目的や困りごとが混ざっていないか確認します。

## タイトル

タイトルは、コード上の機能名や画面名ではなく、ユーザーが探す言葉にします。

次の形を優先します。

- `〇〇したい`
- `〇〇できない`
- `〇〇するとどうなる`
- `〇〇はいつ実行される`
- `〇〇を間違えた`
- `〇〇が届かない`

避ける例:

- `催促機能について`
- `Notification Failure`
- `RecruitmentBoardの使い方`
- `スタッフ管理機能の概要`

## 本文に含める情報

冒頭で、ユーザーが探している答えを提示します。
その後に、作業を再開するために必要な情報だけを続けます。

操作や状態の確認場所を案内する記事では、`画面 → セクション → 対象行またはタブ → 操作名`の順で、たどる場所を具体的に書きます。
`ダッシュボードから操作できます`、`スタッフ一覧で確認できます`のように、対象箇所を特定できない案内だけで終えてはいけません。

候補となる情報:

- 操作する場所と最小限の操作方法
- 操作後に起きること
- 管理者側とスタッフ側の見え方
- 通知対象、通知先、通知タイミング
- LINEとメールの使い分け
- うまくいかない原因と対処方法
- 次に発生しやすい疑問への関連記事

すべてを毎回書く必要はありません。
現在の疑問を解決しない情報は含めません。

## 長さと文体

文字数の下限は設けません。
多くの記事は数段落以内で完結させます。

MDX本文は一文ごとに改行します。
画面上でも段落を分けたい箇所には空行を入れます。
改行だけではMarkdown上の同じ段落として表示されるため、話題、操作、結果が変わる箇所は空行で区切ります。

- 単純な操作: 50〜200文字
- 通知や仕様: 100〜300文字
- トラブル対応: 200〜500文字
- 全体の流れ: 300〜700文字

目安を満たすために文章を増やしてはいけません。
専門用語や内部名を避け、忙しい管理者やスタッフが普段使う言葉で書きます。
内部処理を説明する必要がある場合も、`scheduler`、`outbox`、`queue`、`mutation`などの実装語をそのまま出しません。

## 記事作成前の調査

本文を書く前に、関連するUI、Feature Doc、テスト、Convex関数を確認します。
次の仕様を推測で書いてはいけません。

- 通知対象、通知タイミング、LINEとメールの分岐、再送条件
- 自動催促の条件
- 確定後の修正時の挙動
- 削除後に残るデータ
- エラーと警告の条件
- スタッフ側に表示される内容
- 操作できる役割と権限

調査時は、次を整理します。

- 誰が、何を達成したいか
- 現在どの状態で困っているか
- UIだけで理解できるか
- UIから分からない挙動は何か
- 失敗すると運用が止まるか
- 管理者やスタッフが不安になる点は何か
- 参照したファイル、コンポーネント、関数、テスト
- 確認できた仕様と、確認できなかった仕様

確認できなかった仕様は本文に書きません。
通知、認証、権限、token、個人情報を扱う記事では、`shiftori-security-review` と `doc/rules/security-strategy.md` も確認します。

## カテゴリと検索語

ヘルプは次の3つの入口で整理します。

- やりたいことから探す
- 困りごとから探す
- シフトリの仕組みを知る

カテゴリは記事数に合わせて必要なものだけ追加します。
初期候補を一度に空カテゴリとして作りません。

ユーザーは正確な機能名を知らない前提で、`title`、`description`、本文、`keywords`、カテゴリを検索対象にします。
`keywords`には開発用語ではなく、次のような表記揺れを入れます。

- 催促 / リマインド
- スタッフ / メンバー / 従業員
- 確定 / 決定
- 届かない / 来ない / 送られない
- 削除 / 消す
- 募集 / シフト提出依頼

## 関連記事と画面からの導線

関連記事は、現在の問題を解決したあとに発生しやすい次の疑問だけを選びます。
関連性の低い記事を数合わせで並べません。

記事を追加したら、関連する管理画面から `/howto#slug` へ直接リンクする価値があるか確認します。

候補例:

- 送れなかった通知 → 通知が届かないとき
- 確定時の警告 → シフト確定時の警告
- LINE未連携表示 → LINEを連携してもらう方法
- 自動催促設定 → 自動催促が送られる条件
- スタッフ削除確認 → スタッフを削除するとどうなるか

導線を追加する場合も、画面をリンクだらけにしないよう、ユーザーが困る状態の近くに限定します。

## UIコンポーネントと画像

短い文章だけで理解できる記事には、画像やコンポーネントを追加しません。

実際の状態差や通知経路を見せる価値がある場合は、スクリーンショットより表示専用の既存UIまたはヘルプ用コンポーネントを優先します。
ヘルプ対応のために、使う予定のない既存コンポーネントを先回りして共通化してはいけません。

MDX内のコンポーネントはpropsまたはfixtureで状態を再現し、次のものへ接続しません。

- Mutation、Query、実ユーザーデータ、本番店舗データ
- 認証状態
- 実際の通知、削除、確定処理

スクリーンショットは、画面全体の位置関係、PCとSPで大きく異なる配置、外部サービスの設定画面など、UI部品だけでは場所が伝わらない場合に限ります。

AI生成画像は、通知経路、役割、処理の流れなどの概念を補助するときだけ使用します。
実際の操作場所や正確な画面を表現する用途には使いません。
装飾目的で画像を追加せず、文字、数字、ロゴ、実在しないUI、本文にない仕様を画像へ含めません。
画像を使う場合は、画像が補助する意味を説明する`alt`を必ず設定します。

## 問い合わせと機能変更から更新する

問い合わせが発生しても、機械的に新規記事を作りません。
次のいずれかを選びます。

- 既存記事を改善する
- 新しい記事を追加する
- 管理画面から該当記事への導線を追加する
- UI自体を改善する
- 説明不要と判断する

次の機能変更では、`features`を検索して関連する記事を確認します。

- 操作手順や表示内容
- 通知対象、条件、タイミング、文面、LINEとメールの分岐
- 自動催促条件
- エラーや警告条件
- 削除時の挙動
- 確定後の修正挙動
- 権限
- スタッフ側画面

関連する記事がある場合は、実装変更と同時に更新します。

## 画面とMDXの管理

- URLは `/howto` の1ページだけです。
- 1つの目的または質問につき、`content/`へ1つのMDXファイルを作成します。
- 個別記事ページは作らず、各項目を `/howto#slug` で直接示します。
- 短い回答をアコーディオンで隠さず、原則として常時表示します。
- StorybookはHowToページ全体のPC/SPレイアウトVRTだけを持ち、記事ごとのStoryは作りません。

## frontmatter

```mdx
---
title: LINE通知が届かないとき
description: LINEの連携状態と、送れなかった通知を確認する方法です
category: notification-trouble
keywords:
  - LINEが届かない
  - 通知が来ない
features:
  - line
  - notification
related:
  - automatic-reminder
order: 10
---
```

- `title`: ユーザーが探す言葉で書いた記事タイトル
- `description`: 一覧や検索結果で疑問への対応範囲が分かる短い説明
- `category`: `helpContent.ts`に存在するカテゴリ
- `keywords`: ユーザーが入力しそうな言葉と表記揺れ
- `features`: 機能変更時に更新対象を探すための機能領域
- `related`: 同じディレクトリに存在する関連記事のslug
- `order`: 同じカテゴリ内の表示順

カテゴリを追加する場合は、`helpContent.ts`のカテゴリとナビゲーション分類も更新します。

## AIが記事を作る順序

AIは記事本文を先に量産せず、次の順序で進めます。

1. 対象機能、記事、コード変更、画像生成の範囲を確認する
2. UI、関数、通知、権限、エラー、スタッフ側の挙動を調査する
3. 確認できた仕様と確認できなかった仕様を報告する
4. 候補をA、B、C、Dに分類する
5. `title`、`slug`、`description`、`category`、`keywords`、`features`、`related`を設計する
6. 記事で答える疑問と、含めない内容を決める
7. 画像またはUIコンポーネントが本当に必要か判断する
8. 合意した設計に基づき、最小限のMDX本文を書く
9. 実装との矛盾、重複、長さ、ユーザー語彙、検索語を確認する

## 完了条件

MDXファイルを追加しただけでは完了としません。

- 実装に基づいた内容である
- 1つの目的または困りごとに答えている
- 冒頭で答えが分かり、不要に長くない
- 一文一行で書かれ、話題が変わる箇所に空行がある
- どの画面のどの場所で操作・確認するか特定できる
- 検索語がユーザーの言葉になっている
- 既存記事と重複していない
- 関連記事が次の疑問として適切である
- 必要な場合だけ画像または表示専用UIを使っている
- 管理画面から直接リンクすべき場所を確認している
- 機能変更時に`features`から追跡できる

共通レイアウト、MDX変換、frontmatter、検索を変更した場合は、最低限次を実行します。

```bash
pnpm vitest --project=logic src/components/features/HowToSite/helpContent.test.ts
pnpm lint
pnpm type-check
pnpm build
```

個別MDXの本文だけを変更した場合、記事専用のStoryやテストは追加しません。

# シフトリUI文言

忙しい店舗運営者とスタッフが、シフト作業を迷わず終えられる日本語を書く。
装飾よりも、事実、状態、次の行動を優先する。

## 文言を決める手順

1. 利用者を決める。
   管理者、スタッフ、未ログイン利用者のどれかを明確にする。
2. タスクを一つ決める。
   その文言を読んだ人が、何を判断し、何をするかを言語化する。
3. システムが保証する事実をコードで確認する。
   通知、削除、権限、課金、法務同意、リンク状態、バックグラウンド処理は推測で書かない。
4. 状態、影響、次の行動の順で最小限に書く。
5. 同じ概念を持つ画面、通知、FAQ、使い方、Story、テストを検索して揃える。

Surfaceは Manager app、staff-facing link、auth、landing/demo、operational notification、public page に分ける。
Button、label、helper、dialog、toast、empty、error、loading、table column、section headingのどれかも明確にする。

## 状態と確度

`受け付けた`、`送った`、`届いた` を分ける。

| 実際の状態 | 表現 |
|---|---|
| 公開リクエストを受け付けたが、対象の存在や処理結果を明かせない | `受け付けました` |
| 通知送信・再送の操作が成功した | `送りました` / `再送しました` |
| 配送完了を確認していない | `届きました` を使わない |
| 今後使える受信経路を説明する | `LINEで受け取れます` |
| 通常経路とフォールバックを説明する | `通常はLINEへ送ります。LINEで送れない場合は、メールでお知らせすることがあります。` |

- 通知以外の非同期処理は、完了を確認するまで `完了しました` と書かない。
- scheduler、outbox、queue、retryなどの内部処理を説明しない。
- 送信結果が不明なエラーでは、すぐ再送させて二重処理を招く案内を避ける。
- 成功Toastは短くする。必要な場合だけ対象を入れる。
  例: `変更があるスタッフに通知を送りました`。
- `メールではなくLINE` のように経路を排他的に断定しない。フォールバックがあるなら明記する。

## 公開応答とプライバシー

登録有無、申請済み、失効、使用済みなどを外部から判別させない設計では、文言でも区別しない。

- 失効理由を一つに断定せず、タスク単位で `このリンクではLINE連携できません`、`このリンクでは同意できません` と書く。
- 必要なら `リンクが無効または使用済みの可能性があります` のように候補をまとめ、どれかを特定しない。
- 公開フォームの完了画面は `申請を受け付けました` とし、登録済み・申請済みで出し分けない。
- 後続処理を保証できない場合は `必要な場合は、入力したメールアドレスへ案内を送ります` と書く。
- `登録済みです`、`申請済みです`、`期限切れです` の表示が列挙攻撃や状態推測につながらないか確認する。
- 認証・認可・rate limitの契約を文言変更で弱めない。

## 日本語の構造

### 基本

- ふつうの現代的な日本語を使う。過度な敬語、役所語、社内用語を避ける。
- 1文1アイデアにする。Bodyは原則1〜2文にする。
- 名詞を連結せず、誰が何をするかを動詞で書く。
  `再通知の実行` より `もう一度送る`。
- 状態、影響、次の行動を同じ文に詰め込まない。
- 不安を下げるが、説明しすぎない。
- タイトルとボタンは原則として句読点を付けない。本文には句読点を付ける。
- `〜となります`、`〜にて`、不要な `可能です` を避ける。
- 一般向けのUI・文章では、月数を`1か月`、`2か月`のように書き、助数詞の`か`をひらがなに統一する。

### 動的値

動的値と日本語の助詞の間に空白を入れない。

```tsx
// Good
<Text>{periodLabel}のシフト</Text>
const message = `${shopName}で使うシフトリの案内です`;

// Avoid
<Text>{periodLabel} のシフト</Text>
const message = `${shopName} で使うシフトリの案内です`;
```

英数字を含むメールアドレスや人名でも、助詞の前へ日本語には不要な空白を足さない。

### 説明の役割分担

同じ説明を見出し、カード、フローで繰り返さない。

- 見出し: 結論を伝える。
- 導入文: 利用者にとっての意味を伝える。
- カード: 選択肢や機能の違いを伝える。
- フロー: 操作の順序だけを伝える。
- FAQ: 結論を1〜2文で即答する。
- 使い方: 画面経路、手順、例外、操作後の結果を説明する。

## 要素別ルール

### Buttons and CTAs

- 目的語と動詞を使う: `変更を保存`、`この募集を削除`、`希望シフトを提出する`。
- `OK`、`こちら`、対象のない `送信` や `確認` を避ける。
- 押した時点で受け取れない操作を `受け取る` と書かない。
  再発行の公開リクエストなら `新しい閲覧リンクを申し込む`、`再発行を申し込む` とする。
- 遷移後の結果までボタン名で明確にする。
  未保存確認は `保存して戻る` / `保存せず戻る` とする。
- スタッフ向けは短くする: `提出する`、`もう一度開く`、`同意して続ける`。
- 破壊的操作はButton、Dialog title、bodyで対象と結果を揃える。

### Dialogs

- Titleは対象 + 行動または状態にする。
- Bodyは操作後に何が起きるかを書く。
- 不可逆性を直接書く。
  `本当に削除してよろしいですか？` より `この募集を削除すると元に戻せません。`
- 非同期処理の下流結果を断言しない。

### Toasts

- 短い結果文にする。
- 通知送信・再送は `送りました` / `再送しました` と書く。
- enqueueやscheduleの成功だけで `届きました` と書かない。
- 役に立つ場合だけ対象を足す。

### Empty States

- `事実 + 次の一歩` で書く。
- `ありません` だけで終わらせない。
- 初回はCTAを置く。
  例: `シフト期間と提出期限を決めて、スタッフに希望を聞きましょう。`
- 処理済みは安心させる。
  例: `もう一度送る必要がある通知はすべて処理済みです。`

### Errors

- 何が起きたか、どう回復するかを書く。
- ユーザーを責めない。
- `エラーが発生しました` だけで終わらせない。
- バックエンドの日本語エラーを、日本語であることだけを理由にそのまま表示しない。
- 公開可能な既知エラーへ対応付け、内部語や原因を含む未知エラーは安全な汎用文へ置き換える。
  例: `操作を完了できませんでした。少し時間をおいて、もう一度お試しください。`
- スタッフリンクでは `このリンクでは提出できません` のように、できないタスクを書く。
- 通信や端末の問題は、結果が不明でない場合に限り `再読み込み`、`少し時間をおく`、`Safari、Chrome、Edgeで開く` など具体的な行動を書く。
- フィールドエラーはその場で直せる文にする。
  例: `メールアドレスの形式で入力してください。`

### Tables and Labels

- 短い名詞を使う: `スタッフ名`、`通知種別`、`募集期間`、`チャネル`、`検知日時`。
- ヘッダーに文章を書かない。
- 提出パターンは `日ごと`、`時間指定`、`勤務区分` に統一する。

## 画面別ルール

### スタッフ向け画面

- 管理画面の内部状態を知らない前提で書く。
- リンク不可や受付終了は、タスク単位で伝える。
- 次の行動は `シフト作成担当者に連絡してください` のように具体化する。
- 調整中、提出済み、受付終了の状態を簡潔に伝える。

### 通知

- CTAは `対象 + 動詞` にする。
  `提出はこちら` より `希望シフトを提出する`。
- タイトルだけで目的を判別できるようにする。
  `提出リマインド` より `提出期限が近づいています`。
- 未提出を断定できない場合は `まだ提出していない場合は` と書く。
- メール、LINE、Flex Messageで同じ用語と行動を使う。

### Landing

- 抽象的な万能感ではなく、利用者が実行できる一連の操作を書く。
  `まるごとおまかせ` より `未提出の確認から確定通知までを、同じ画面で進められます`。
- 見出しで結論を伝え、カード本文で差を説明する。
- UI内の正式名称とマーケティング文言を揃える。

### Demo

- 実データを保存しないなら `このデモでの操作は保存されません` と書く。
- 通知しないなら、実運用の通知成功を説明しない。
- CTAは `確定後の画面を見る` のように、デモで実際に起きることを書く。

## 用語

### シフト管理の基本用語

| 用語 | 指すもの | 避ける表現 |
|---|---|---|
| シフト募集 | 管理者が作成する、シフト期間と希望シフトの提出期限を持つ募集 | 募集シフト |
| 希望シフト | スタッフが提出する勤務希望の日付・時間 | シフト希望 |
| 確定シフト | 管理者が確定した勤務予定 | 確定したシフト、確定済みシフト（名称として使う場合） |
| 提出期限 | 希望シフトを提出・更新できる期限 | 提出締切、締切 |

画面、通知、HelpCenter、現在仕様の文書では、この用語に統一する。
操作を表す場合は、`シフトを募集する`、`希望シフトを提出する`、`シフトを確定する`のように動詞で書く。
名称と操作を混同して、`確定シフトを確定する`のような表現にしない。

### 内部語を利用者の行動へ変える

| 内部・曖昧な表現 | 利用者向け表現 | 判断 |
|---|---|---|
| Clerkのログイン情報 | ログイン用アカウント | 認証基盤名を操作説明へ出さない |
| 店舗人物 / organizationPeople | 組織のユーザー | データモデルではなく画面上の対象を示す |
| アカウント連携 | 案内先のメールアドレスでログインし、招待を受け入れる | 実際の行動へ分解する |
| 一意に照合できません | 組織設定の「ユーザー」で登録内容を確認してください | 原因を断定せず回復場所を示す |
| サブスクリプション | 有料契約 / プラン変更の予約 | 課金の状態を利用者語彙で示す |
| outbox / scheduler / retry / queue | 表示しない | 内部実装を説明しない |
| magic link / token / ID | 登録リンク / 閲覧リンク / 案内 | タスクに応じて言い換える |
| 不達通知 | 送れなかった通知 | 運用語を日常語へ変える |

原因候補が複数ある場合は、もっともらしい一つへ断定しない。
決済先やプライバシーポリシーなど、固有名詞そのものが利用者の判断材料になる場面では provider 名を残してよい。

### Preferred Terms

| Prefer | Avoid | Note |
|---|---|---|
| 送れなかった相手を確認して、もう一度送れます。 | 送信できなかった通知を確認して再通知できます | 人と行動を出す |
| 再送済み | 再通知済み、再送受付済み | 内部受付を説明しない。`届きました` と断言しない |
| スタッフ登録申請 | スタッフ参加申請 | 店舗運用では登録が自然 |
| スタッフ本人が登録できます | スタッフ自ら登録できます | 堅さを落とす |
| メールで送ります | メールにて送付します | 送信側の説明では `送る` を使う |
| このリンクでは提出できません | このリンクは使用できません | タスクを明示する |
| 要シフト調整 | 要対応 | 業務意味を具体化する |
| 友だち追加 | 友達追加 | LINEの公式表記に合わせる |
| 組織 | 事業者 | 利用者向け表示。内部の型・APIは`organization`のままにする |

### 採用済みのローカル文言

- スタッフ登録申請を断る操作は `却下` を使う。`承認しない` へ自動で言い換えない。
- Dashboardの回収中表示は `シフト回収中です。しばらくお待ちください。` を使う。
- メール形式のバリデーションは `メールアドレスの形式で入力してください` を使う。
- LINE連携案内メールの件名は `シフト通知をLINEで受け取れます` を使う。
- スタッフ詳細タブは `情報 / 通知 / LINE / 設定` とする。

## 横断レビューと検証

### 優先順位

1. 誤った状態や完了を伝える文言を直す。
2. プライバシー、認証、権限、課金、削除の誤解を直す。
3. 内部語や原因断定を直す。
4. CTA、正式名称、通知チャネルを横断で揃える。
5. 冗長さ、重複、動的値の空白を直す。

### レビュー方法

- 画面単位だけでなく、同じ操作を説明するUI、Toast、通知、FAQ、使い方を一組として読む。
- 文字列を抽出し、`届きました`、`完了しました`、`こちら`、内部語、動的値の空白を検索する。
- 見出し、導入、カード、フローが同じ内容を繰り返していないか確認する。
- Article、FAQ、使い方など、依頼で除外された領域へ広げない。
- 並行差分がある場合は、編集直前に対象ファイルのdiffを確認し、他の変更を上書きしない。

### 検証

- 文言変更後に旧文言を `rg` で検索する。
- Storybook play test、Logic Test、E2E Page Object、通知テンプレートの厳密期待値を追従する。
- 静的文言の存在確認だけを目的とするplay testは追加しない。
- 折り返しやカード高が変わる文言は、DesktopとMobileのVRT対象を確認する。
- FAQのIDや外部アンカーは維持する。分割する場合も既存IDを一つ残す。

既存文言レビューを求められたら、指定がなければ次を使う。

| 優先度 | 画面 | 要素 | 現在の文言 | 違和感 | 改善案 |
|---|---|---|---|---|---|

優先度は `高 / 中 / 低` とする。
画面名は利用者が分かる名前を使い、要素は `Toast`、`Dialog title`、`CTAボタン`、`Empty state`、`説明文`、`テーブル列` などで書く。

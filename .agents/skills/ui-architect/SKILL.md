# シフトリのUIを設計する

UI作業を、利用者のタスクから検証まで順に進める。
安定した設計原則はこのスキルへ複製せず、正本を参照する。

## 正本と現状を確認する

1. `doc/rules/ui-design.md` を読む。
2. `src/`を扱う場合は`doc/rules/frontend-architecture.md`と対象範囲の`AGENTS.md`を読む。
3. 対象画面、近い既存UI、共通コンポーネント、Storyを確認する。
4. 表示文言が権限、課金、通知、削除、非同期処理を説明する場合は、実際の状態遷移をコードで確認する。
5. スクリーンショットや実画面への指摘では、見えている要素と変更対象が一致するまで確認する。

コードと文書が食い違う場合、現在の挙動はコードを正とする。
目標状態は実装済みの事実として扱わない。

## 1. 利用者のタスクを定義する

- 画面で最初に完了させる主タスクを一つ決める。
- 補助タスクと、この画面では扱わないタスクを分ける。
- 利用者の役割、利用頻度、端末、急ぎや不安の有無を確認する。
- データ量、更新頻度、権限、完了条件を確認する。
- 不足情報が結果を変える場合だけ、短く確認する。

## 2. 画面構造とコンポーネントを決める

- 主タスク、必要情報、主操作の順に画面構造を組む。
- 既存の共通コンポーネントと近いfeature実装を優先する。
- 並べ替え、曜日の色、Loading、Empty、バッジ、セクションの説明など、ほかの画面にもある役割の部品は、作る前に`references/components.md`の「基準にする既存実装」と照合する。
- 新しいwrapperは、業務上の意味、状態分岐、レイアウト責務のいずれかを持つ場合だけ作る。
- モバイルはPC版の縮小ではなく、情報順序と操作方法を端末に合わせる。
- LP・機能ページなど登録前の人が読む公開ページでは、`references/mobile-landing.md`を読み、スマホで読む長さ、改行、CTAの配置を決める。
- 破壊的操作、長い編集、URL共有、戻る操作の要否から、Dialogと専用ページを選ぶ。
- Dialogは、編集、確認、閲覧、複数段階のどれかに分類し、各ボタンのPrimary、Secondary、Destructiveの意味を決める。
- Dialogを扱う場合は、`doc/rules/ui-design.md`の「Dialogのアクション」を適用し、終了操作、inline confirmation、close lock、scroll時のaction areaを設計する。

## 3. 状態を設計する

次のうち、対象機能に存在する状態を明示する。

- Loading
- Empty
- Error
- Success
- PendingまたはAccepted
- 権限不足
- 利用不可

ページ全体、Card、sectionなどまとまった領域のLoadingは、`doc/rules/ui-design.md`の共通Loading基準に照らして`src/components/ui/ShiftoriLoading`を使う。
ボタン内や小さなinline処理は、操作対象に対応する局所的な進行表示を使う。
Loading、Empty、Error、Successの部品選定に迷う場合は`references/states.md`を読む。

非同期処理では、受付、送信、到達、完了を実際の保証に合わせて区別する。
送信操作は、見た目のloadingやdisabledだけでなく、フロントの同期ガードと必要なバックエンドの冪等性で二重実行を防ぐ。

## 4. マイクロコピーを書く

- ボタンは操作、見出しは対象、エラーは原因と次の行動を書く。
- シフト管理の正式用語は`references/ui-writing.md`の「シフト管理の基本用語」を正本とする。
- 内部の型名、状態名、queue、tokenなどをそのまま表示しない。
- 利用者に見える事実だけを書き、未完了の処理を完了と表現しない。
- placeholderを設計または監査する場合は、`references/ui-writing.md`の「Placeholders」を読み、入力種別、事前値、補足文との役割を区別する。
- ボタン、ラベル、Toast、表見出しは短くする。
- ボタンやラベルなどの短いUI文言にも、`../japanese-tech-writing/SKILL.md`の「直接的で自然な文」を適用する。
- 複数文の説明を構成から推敲する場合は`japanese-tech-writing`を使う。
- 読み物としての緩急が必要な長い説明だけに`cognitive-rhythm-writing`を併用する。
- HelpCenterのFAQ・使い方は`write-help-content`、ArticleSiteの記事は`seo-article-writer`へ分ける。

## 5. 実装の前に案を合意する

画面構造やレイアウトを変える場合と、文言に複数の妥当な書き方がある場合は、実装の前に案を示して選択を待つ。
依頼が変更内容を具体的に指定している場合は、案を出さずに実装へ進む。

- 案を作る前に`references/preferences.md`を読み、過去に選ばれた形と理由を確認する。
- 2〜3案を、周囲の見出しや文脈と合わせて示す。
- 各案に、前提にした条件と、既存のレイアウトで移動または削除する箇所の有無を書く。
- 対象が1つしかないと決めつけず、複数ある場合をコードで確認する。例は1店舗に管理者が複数いる場合である。
- 依頼されていない要素の追加と、セクションの移動、並び替え、削除は案に含めず、必要なら別の提案として分ける。
- 入力UIの案には現実にある入力例での操作回数を書く。例は「昼は3人、直後に1人、夜は5人」の必要人数である。
- 操作の多い入力UIは本実装の前に操作できる試作を作り、ユーザーに確かめてもらう。
- 調査に基づく案だと述べる場合は、日本語の情報源と競合製品を含めて調べる。
- ユーザーが案を選んだら、`references/preferences.md`の形式で、条件、選んだ形、理由、基準にする画面を記録する。

## 6. 実装する

- `doc/rules/frontend-architecture.md`の責務と依存方向に従う。
- 現在のUI部品、theme token、form、date、state管理の使い方は、共通実装と近い既存コードを正本にする。
- UIだけで認可、入力制約、データ境界、冪等性を保証しない。
- 依頼と関係しない画面や共通基盤へ変更を広げない。

## 7. 検証する

- 主タスクが最短の導線で完了するか確認する。
- Loading、Empty、Error、Successなど変更に関係する代表状態を確認する。
- デスクトップとモバイルで情報順序、折り返し、操作領域を確認する。
- 公開ページの文言は、`references/mobile-landing.md`の「確認の手順」で幅360pxの行数と孤立した末尾を確認する。
- DialogはPCとSPでDOM順と見た目の順、action areaの配置、長い文言、本文scroll、safe areaを確認する。
- 閲覧専用を含む終了操作、すべてのclose経路、close lockの開始と解除、Dialogを重ねない確認遷移を確認する。
- キーボード操作、フォーカス、ラベル、コントラストを確認する。
- hover、disabled、選択中の各状態で、文字とアイコンが読めることを確認する。
- 名前などの長い値を入れ、決めた領域の中で省略されることを確認する。
- 経緯を知らない人が画面だけを見て、何をするページで、どこまで進めればよいかが分かるか確認する。新しい画面と、操作の流れを変えた画面では、`first-use-reviewer`に確認を任せる。
- テスト層や新しい検証契約を設計する場合は`test-strategy`を使う。
- 対象範囲の`AGENTS.md`に従ってlint、型、テストを実行する。

## 8. 結果を報告する

- 利用者の主タスク
- 採用した画面構造と状態
- 実装または提案した変更
- 実施した検証
- 変更を見られる場所（ローカルだけか、pushしたあとのPull Requestのプレビューか）
- 未確認事項と残る制約

ユーザーから「見た目が違う」と指摘された場合は、原因を推測する前に、ユーザーが見ている環境と版を確かめる。

プロダクト全体の安定したUI原則を追加する場合は、`doc/rules/agent-instructions.md`の配置基準に従い、`doc/rules/ui-design.md`を更新する。
このスキルには作業手順だけを残す。

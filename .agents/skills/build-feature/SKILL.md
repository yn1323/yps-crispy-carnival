# 機能を聞き取ってから作る

このスキルは、ユーザーが `/build-feature` で起動した場合だけ使う。
ユーザーへの質問は聞き取りの段階にまとめ、計画の承認を得たあとは検証まで止まらずに進める。

各作業の進め方と設計原則はこのスキルへ複製しない。
`AGENTS.md`の「正本と参照順」と「Skillの発動条件」が示す正本とSkillに従う。

## 1. 依頼とコードを読む

- 起動時の引数と会話から、作りたい機能を把握する。引数も会話もない場合は、作りたい機能を最初に聞く。
- 対象の画面、近い既存実装、対応する`doc/features/`、関連する`doc/plans/`を読む。
- 次の5点を、依頼とコードから分かるものと分からないものに分ける。
  1. 誰がどの場面で困っているか
  2. どうなれば完成か
  3. 今回やらないこと
  4. すでに決まっていることと、好みがある箇所
  5. データの形や権限に触れる場合の業務上の決まり

## 2. 聞く

- 分からない項目のうち、答えによって作るものが変わるものだけを聞く。
- コードを読めば分かることは聞かない。
- 質問には選択肢を付け、勧める選択肢を先頭に置く。
- 完成の状態、扱う情報、画面の形の順に聞く。
- 画面構造や文言に妥当な形が複数ある場合は、`ui-architect`の「実装の前に案を合意する」に従って案を示し、この段階で選んでもらう。
- `AGENTS.md`の「Skillの発動条件」に当たる作業を洗い出し、ユーザーの判断が要る点を質問に含める。
- 完成条件を1行ずつ書ける状態になるまで聞く。

## 3. 完成条件を計画に残す

- `doc/plans/YYYY-MM-DD_<機能名>_実装計画.md`を作り、`doc/plans/INDEX.md`の`Active`へ追加する。
- 計画には次の内容を書く。
  - 目的と前提（5点の答え）
  - 完成条件（利用者に見える結果を1行ずつ）
  - 各完成条件を守る自動テストと主担当層（`test-strategy`で選ぶ）
  - 今回やらないこと
  - 参考にしたファイルのパス
- 完成条件と守るテストの一覧を示し、この内容で進めてよいかを確認する。
- 承認を得たら、完成条件を`/goal`の条件1行にまとめて示す。使うかどうかはユーザーが決める。

## 4. 実装する

- 計画の完成条件を作業の一覧にし、順に進める。
- 承認のあとは次の場合だけ止まる。
  - 計画にない破壊的な操作またはデータの移行が必要になった。
  - 完成条件どうしが両立しないと分かった。
  - 業務要件と現行実装が食い違い、「要件判断」が必要になった。
- それ以外の判断は計画と近い既存実装に合わせて決め、決めた内容と理由を報告に残す。
- 実装中に画面や文言の妥当な形が新しく複数見つかった場合も止まらない。`ui-architect`の`references/preferences.md`と近い既存画面に合わせて選び、選んだ形を報告に残す。

## 5. 検証する

- 完成条件ごとに対象のテストを実行し、そのあとで`AGENTS.md`の「検証」のコマンドを実行する。
- 見た目を変えた箇所は`.claude/rules/stories.md`に従って目視確認する。
- 失敗したテストは原因を直して再実行する。
- 今回の変更と関係しない失敗は直さず、関係しないと判断した根拠を報告に残す。
- 検証が通ったら、計画文書のパスと変更したファイルの一覧を`plan-reviewer`へ渡して照合させ、正しさに関わる不足だけを直す。
- 現在の機能概要を変えた場合は、対応する`doc/features/`を更新する。

## 6. 報告する

- 完成条件を1つずつ、守っているテストまたは確認結果と対にして示す。
- 実行したコマンドと結果を添える。
- 自分で決めた判断、未確認の事項、残る作業を示す。
- 計画文書の状態と、`doc/plans/INDEX.md`の未完了条件を更新する。
- コミットとPull Requestの作成は行わない。

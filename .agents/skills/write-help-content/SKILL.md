# ヘルプコンテンツを作成する

小規模店舗で初めて操作する店長またはスタッフが、迷わず作業を完了できる文章を作る。
機能を詳しく説明することより、現在の画面で疑問を解消し、必要な操作を完了できることを優先する。

## 編集範囲を守る

- ユーザーが明示的に依頼していない限り、既存のFAQ・使い方を更新または削除しない。
- 機能変更に伴って既存記事の更新が必要に見える場合も、依頼範囲に含まれなければ変更せず、必要性だけを成果物の報告に記載する。
- 新規記事を追加した場合は、成果物の報告で新規追加した記事であることを明示する。

## 正本を確認する

1. `doc/rules/agent-instructions.md` と `doc/features/help-center.md` を読む。
2. 対象範囲の `AGENTS.md` と `src/components/features/HelpCenter/AGENTS.md` を読む。
3. 対象機能の画面、ルート、状態分岐、表示文言をコードで確認する。
4. 同じtaskのFAQ・使い方を読み、重複、frontmatter、relationを確認する。

コードと記事が食い違う場合は、現在のコードを正とする。
将来の予定は、実装済みの操作として書かない。

文章の校正だけを依頼され、機能事実を変更しない場合は、入力された記事を事実の範囲とする。
新しい情報を補わず、UI名称を変更しない。

## 執筆前に整理する

本文を書く前に、入力情報と確認した正本から次を整理する。

- 読者
- 読者が達成したいこと
- 操作を開始する画面
- 使用する画面名、項目名、ボタン名
- 操作完了後の状態
- 事前条件
- 操作できない条件
- 関連する例外

仕様にない動作は推測しない。
不明な情報は創作せず、下書きへ`[要確認: 内容]`と記載する。
公開するMDXへ未解決の`[要確認: 内容]`を残す場合は、公開状態にせず成果物の報告にも記載する。

## 記事化を判断する

本文を書く前に、次のいずれかを選ぶ。

- **公開する**: 分からないと作業が止まる、誤操作の影響が大きい、UIだけでは結果や対象者が分からない。
- **既存記事を直す**: 同じ目的の記事があり、追記または構成変更で疑問を解消できる。
- **UIを直す**: 多くの利用者が同じ画面で迷い、ラベル、補足、状態、エラー、導線で解決できる。
- **記事にしない**: UIだけで分かる、簡単に元へ戻せる、既存記事の一部で足りる、行動が変わらない。

問い合わせが少なくても、運用停止、通知、確定、削除、権限など影響が大きい疑問は公開を優先する。
機能を網羅するためだけに記事を増やさない。

## FAQか使い方かを決める

- 読者の役割と、解決したいやりたいこと・困りごとを一つに絞る。
- 既存のtaskを選び、同じ疑問を扱うFAQ・使い方がないか確認する。
- 短い結論で解決できる場合はFAQ、画面操作を完了する必要がある場合は使い方を選ぶ。
- FAQから主な使い方へ案内する場合だけ`primaryGuide`を設定する。
- 主従関係ではない関連する疑問だけを`related`へ設定する。
- 到達点を「どの状態になれば完了か」で定義する。
- 画面上の順序に合わせて手順を並べる。
- 分岐は、権限、設定、端末、機能状態など、実装に存在するものだけを書く。
- 操作できない場合は、原因の見分け方と次の連絡先または代替操作を書く。
- 詳しい背景説明が必要な文章では `$japanese-tech-writing` を使う。
- 読み物として長い解説に緩急が必要な場合だけ `$cognitive-rhythm-writing` を併用する。

## FAQを書く

- 最初の一文で回答し、判断に必要な条件と例外だけを補う。
- 詳しい画面操作は書かず、必要な場合は`primaryGuide`へ案内する。
- 原則として画像を使わない。

## 使い方を書く

- タイトルは`# 〇〇する`の形にする。
- 冒頭は2文以内で、何ができるかと操作前に必要な条件を書く。
- 必要な前提、画面順の手順、完了後の状態、失敗時の次の行動を書く。
- 通知が発生する場合は、誰への送信操作かを示し、配送確認がない状態を「届きました」と書かない。

### 手順

- `## 手順`の下に番号付きリストで書く。
- 1項目には一つの操作だけを書く。
- 実際に表示される画面名、項目名、ボタン名は**太字**にする。
- 操作結果は、次の操作や完了判断に必要な場合だけ書く。
- 注意事項は、関係する操作の直前に置く。

### 完了すると

- `## 完了すると`の下に、操作後に何が変わるかを1〜2文で書く。

### うまくいかないとき

- 実際に起こりやすい問題がある場合だけ`## うまくいかないとき`を追加する。
- 問題と解決方法をセットで書く。
- FAQへ分離できる例外を基本手順へ詰め込まない。

## 日本語を整える

- `../japanese-tech-writing/SKILL.md`の「直接的で自然な文」を、FAQや手順などの短い文章にも適用する。
- シフト管理の正式用語は`../ui-architect/references/ui-writing.md`の「シフト管理の基本用語」に合わせる。
- 1文では一つの内容だけを伝える。
- 長い文は分割し、1文60文字以内を目安にする。
- 結論や操作を文の前半に置く。
- 同じ内容を言い換えて繰り返さない。
- 読者に不要な内部仕様や背景説明を書かない。
- 見出し直後に、見出しを言い換えた説明を書かない。
- 補足情報を手順の途中に大量に入れない。
- 「押下」ではなく「選択」または「クリック」を使う。
- 「上記」「下記」「右側」「左側」ではなく、画面名や項目名を使う。
- 利用者に表示される名称は、画面と完全に一致させる。

次の冗長表現は短くする。

| 使用しない表現 | 置き換え |
|---|---|
| 〜することができます | 〜できます |
| 〜を行います | 〜します |
| 〜となります | 〜です |
| 〜していただく必要があります | 〜してください |
| こちらの画面 | 正確な画面名 |
| 該当するユーザー | 具体的な対象 |
| 基本的に、原則として | 具体的な条件 |
| 必要に応じて | どのような場合か |

タイトルや見出しから分かる内容を繰り返さない。
次の導入文は使用しない。

- ここでは、〇〇について説明します
- シフトリでは、〇〇することができます
- 〇〇機能を利用することで、便利に管理できます
- 以下の手順に従って操作してください
- まずは〇〇画面を開きましょう

## 記事を校正する

- 新しい情報を追加せず、元の意味を変えない。
- 重複、操作に不要な背景説明、冗長表現を削る。
- 1文1情報に分ける。
- UI名称を変更しない。
- 注意事項を関係する手順の直前へ移す。
- 初めて利用する人が、画面を見ながら操作できる順序と表現にする。
- 会話上で記事の校正結果を直接返す場合は、校正後の記事本文だけを出力する。

## MDXを作成・更新する

1. 既存記事と重複する場合は、新規作成より改稿を優先する。
2. `content/faqs/<id>.mdx`または`content/guides/<id>.mdx`へ1記事1ファイルで置き、taskと対象者を指定する。記事ごとのdirectoryと`index.mdx`は作らない。
3. 前提条件、操作手順、完了状態、失敗時の対処を必要な範囲で書く。
4. ボタン名やラベルは実装と同じ表記にする。
5. 画像は操作対象の特定に役立つ場合だけ`content/images/<guide-id>/`へ置き、装飾目的では追加しない。
6. 同じ説明をFAQと使い方へ複製せず、`primaryGuide`と`related`で関連付ける。
7. frontmatter、slug、公開状態は既存schemaに従う。

## 検証する

- 記載した画面、操作、分岐、完了状態をコードと照合する。
- task、relation、slug、frontmatter、MDX構文、画像参照を確認する。
- 同じ文言を持つ既存記事と矛盾しないか検索する。
- 使い方では、冒頭、`手順`、`完了すると`、必要な場合の`うまくいかないとき`が上記の構成に従うか確認する。
- 1項目1操作、UI名称、注意事項の位置、冗長表現を確認する。
- 対象範囲の既存テストとリポジトリの検証手順に従う。
- 未確認事項は推測で補わず、`[要確認: 内容]`として明示し、成果物の報告にも記載する。

## 成果物を報告する

- 作成または更新した記事。新規記事は、新規追加であることを明示する。
- 根拠として確認した実装と機能文書
- 実施した検証
- 実装との差異や未確認事項

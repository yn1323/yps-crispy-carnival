# ヘルプコンテンツを作成する

HelpCenterでは、利用者が現在の画面で疑問を解消し、必要な操作を完了できることを優先する。

## 正本を確認する

1. `doc/rules/agent-instructions.md` と `doc/features/help-center.md` を読む。
2. 対象範囲の `AGENTS.md` と `src/components/features/HelpCenter/AGENTS.md` を読む。
3. 対象機能の画面、ルート、状態分岐、表示文言をコードで確認する。
4. 同じtaskのFAQ・使い方を読み、重複、frontmatter、relationを確認する。

コードと記事が食い違う場合は、現在のコードを正とする。
将来の予定は、実装済みの操作として書かない。

## 記事化を判断する

本文を書く前に、次のいずれかを選ぶ。

- **公開する**: 分からないと作業が止まる、誤操作の影響が大きい、UIだけでは結果や対象者が分からない。
- **既存記事を直す**: 同じ目的の記事があり、追記または構成変更で疑問を解消できる。
- **UIを直す**: 多くの利用者が同じ画面で迷い、ラベル、補足、状態、エラー、導線で解決できる。
- **記事にしない**: UIだけで分かる、簡単に元へ戻せる、既存記事の一部で足りる、行動が変わらない。

問い合わせが少なくても、運用停止、通知、確定、削除、権限など影響が大きい疑問は公開を優先する。
機能を網羅するためだけに記事を増やさない。

## FAQか使い方かを決める

- 読者の役割と、解決したいやりたいこと・困りごとを一つに絞る。
- 既存のtaskを選び、同じ疑問を扱うFAQ・使い方がないか確認する。
- 短い結論で解決できる場合はFAQ、画面操作を完了する必要がある場合は使い方を選ぶ。
- FAQから主な使い方へ案内する場合だけ`primaryGuide`を設定する。
- 主従関係ではない関連する疑問だけを`related`へ設定する。
- 到達点を「どの状態になれば完了か」で定義する。
- 画面上の順序に合わせて手順を並べる。
- 分岐は、権限、設定、端末、機能状態など、実装に存在するものだけを書く。
- 操作できない場合は、原因の見分け方と次の連絡先または代替操作を書く。
- 詳しい背景説明が必要な文章では `$japanese-tech-writing` を使う。
- 読み物として長い解説に緩急が必要な場合だけ `$cognitive-rhythm-writing` を併用する。

## FAQを書く

- 最初の一文で回答し、判断に必要な条件と例外だけを補う。
- 詳しい画面操作は書かず、必要な場合は`primaryGuide`へ案内する。
- 原則として画像を使わない。

## 使い方を書く

- 必要な前提、画面順の手順、完了後の状態、失敗時の次の行動を書く。
- 通知が発生する場合は、誰への送信操作かを示し、配送確認がない状態を「届きました」と書かない。

## MDXを作成・更新する

1. 既存記事と重複する場合は、新規作成より改稿を優先する。
2. `content/faqs/<id>/index.mdx`または`content/guides/<id>/index.mdx`へ置き、taskと対象者を指定する。
3. 前提条件、操作手順、完了状態、失敗時の対処を必要な範囲で書く。
4. ボタン名やラベルは実装と同じ表記にする。
5. 画像は操作対象の特定に役立つ場合だけ使い、装飾目的では追加しない。
6. 同じ説明をFAQと使い方へ複製せず、`primaryGuide`と`related`で関連付ける。
7. frontmatter、slug、公開状態は既存schemaに従う。

## 検証する

- 記載した画面、操作、分岐、完了状態をコードと照合する。
- task、relation、slug、frontmatter、MDX構文、画像参照を確認する。
- 同じ文言を持つ既存記事と矛盾しないか検索する。
- 対象範囲の既存テストとリポジトリの検証手順に従う。
- 未確認事項は推測で補わず、記事内に含めないか、未確認として報告する。

## 成果物を報告する

- 作成または更新した記事
- 根拠として確認した実装と機能文書
- 実施した検証
- 実装との差異や未確認事項
